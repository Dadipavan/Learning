14.1 Quantization

INTUITION
A ruler marked in millimetres can measure a desk to the nearest millimetre. A ruler marked only in centimetres is shorter to print and quicker to read, and for most jobs good enough. Quantization replaces the model's precise 32-bit decimals with small whole numbers (8-bit or 4-bit) plus one scale factor, like switching to a coarser ruler. The model gets 2 to 8 times smaller and often faster, and usually loses little accuracy.

Words you need

WordPlain meaning
fp32 / fp1632-bit / 16-bit floating point numbers (4 and 2 bytes each)
int8 / int4Whole numbers using 8 / 4 bits (1 and 0.5 byte each); int8 holds −128 to 127
Scale sThe size of one integer step in real units
Zero pointAn integer that stands for real 0 in asymmetric schemes
PTQPost-training quantization: quantize an already trained model, no retraining
QATQuantization-aware training: simulate quantization during training so the model adapts

How it works (symmetric int8)

scale  s = max(|w|) / 127
q      = round(w / s), clipped to [−127, 127]      (stored as int8)
w_hat  = q × s                                      (dequantized value)

The biggest possible error for any weight is half a step, s / 2, as long as no clipping occurs.

Problem 14.1.1 Quantize w = (0.31, −0.84, 0.05, 1.29, −0.60, 0.02) to int8.

Asymmetric quantization and the outlier problem

Some values (for example outputs of ReLU) are never negative. Asymmetric quantization maps [min, max] to [0, 255] using a scale s = (max − min)/255 and a zero point z = round(−min/s); q = round(x/s) + z. For x = (0, 0.5, 2, 6) this gives q = (0, 21, 85, 255), z = 0, dequantized (0, 0.4941, 2.0, 6.0).

Does accuracy survive? A measured example

We train a small network (2 inputs, 64 ReLU hidden units, 1 output; 257 parameters) on two interleaved half-moons (the data shape from Chapter 2), then quantize its weights to fewer bits and test.

import numpy as np
rng = np.random.default_rng(0)
def moons(n, noise=0.15):
    t = rng.uniform(0, np.pi, n//2)
    a = np.c_[np.cos(t), np.sin(t)]; b = np.c_[1 - np.cos(t), 0.5 - np.sin(t)]
    X = np.r_[a, b] + noise * rng.standard_normal((n, 2)); y = np.r_[np.zeros(n//2), np.ones(n//2)]
    return X, y
Xtr, ytr = moons(600); Xte, yte = moons(600)
H = 64
W1 = rng.standard_normal((2, H)) * 0.5; b1 = np.zeros(H); W2 = rng.standard_normal((H, 1)) * 0.5; b2 = np.zeros(1)
sig = lambda z: 1/(1+np.exp(-z))
def fwd(X, W1, b1, W2, b2): h = np.maximum(0, X@W1 + b1); return sig(h@W2 + b2)[:, 0], h
lr = 0.5
for ep in range(3000):
    p, h = fwd(Xtr, W1, b1, W2, b2); d = (p - ytr)[:, None] / len(Xtr)
    gW2 = h.T @ d; gb2 = d.sum(0); dh = d @ W2.T * (h > 0); gW1 = Xtr.T @ dh; gb1 = dh.sum(0)
    W1 -= lr*gW1; b1 -= lr*gb1; W2 -= lr*gW2; b2 -= lr*gb2
acc = lambda W1, W2: (((fwd(Xte, W1, b1, W2, b2)[0] > 0.5) == yte).mean())
print("full-precision test accuracy", acc(W1, W2), " params", W1.size + W2.size + H + 1)
def quant(W, bits):
    qmax = 2**(bits-1) - 1; s = np.abs(W).max() / qmax; return np.round(W/s).clip(-qmax, qmax) * s
for bits in (8, 4, 3, 2): print("int%d weights: accuracy" % bits, acc(quant(W1, bits), quant(W2, bits)))
full-precision test accuracy 0.985  params 257
int8 weights: accuracy 0.985
int4 weights: accuracy 0.985
int3 weights: accuracy 0.9866666666666667
int2 weights: accuracy 0.7666666666666667

Reading it: 8, 4 and even 3 bits keep accuracy (0.985 to 0.987; the tiny rise at 3 bits is noise on 600 test points, not a real gain). At 2 bits (only levels −1, 0, 1) accuracy falls to 0.767. The model has a comfortable margin, so quantization is almost free until a cliff. The cliff is the lesson: always measure on your own test set.

PTQ, QAT and where it runs

  • Post-training quantization (PTQ): easiest; a small calibration set gives the ranges of activations. Good for int8 on vision models and for 4-bit LLM weights.
  • Quantization-aware training (QAT): simulate rounding in the forward pass, let the model adapt. Needed when PTQ loses too much (small models, 4-bit or lower).
  • Speed: int8 needs hardware support (many CPUs and GPUs have it). Smaller weights also mean less memory traffic, which is often the real bottleneck for LLM generation.
  • Formats: fp16 and bf16 (training and serving), int8 (vision and classical models), int4 variants (GPTQ, AWQ, GGUF for local LLMs).

14.2 Pruning and Knowledge Distillation

INTUITION
Pruning is trimming a bush: cut the small branches that add little, and the bush keeps its shape. Distillation is a student learning from a teacher's explanations, not just the final answers. If the teacher says "this is a 7, but it looks a bit like a 1", that extra detail teaches the student more than the plain label "7".

Pruning

Magnitude pruning sets the smallest weights (by absolute value) to zero. Unstructured pruning zeros single weights (flexible, but only fast on special hardware or sparse kernels). Structured pruning removes whole neurons, channels or attention heads, which gives real speed-up on ordinary hardware. After pruning, a short fine-tune often restores accuracy.

Problem 14.2.1 Prune the trained half-moons network and watch accuracy. A weight is zeroed if its absolute value is below the chosen percentile of all weights in that matrix.

Step 1Prune 50% of each weight matrix: 96 of the 192 weights remain.
Step 2Prune 80%, 90%, 95% and 99%, each time testing on the 600 test points.
AnswerAccuracy: 0.985 at 0% pruning; 0.990 at 50%; 0.963 at 80%; 0.673 at 90%; 0.593 at 95%; 0.5 at 99%.
CheckAt 99% only 3 weights remain, so the output is nearly constant and accuracy is 0.5 (a coin flip on balanced classes), as expected.
InterpretationLike quantization, pruning has a safe zone and a cliff. This network can lose half of its weights with no loss (it was bigger than needed), but at 90% it collapses. Without fine-tuning, the cliff comes earlier than with it.
# continues the half-moons script in 14.1 (uses acc, W1, W2, H)
def prune(W, frac):
    thr = np.quantile(np.abs(W), frac); return np.where(np.abs(W) < thr, 0, W)
for fr in (0.0, 0.5, 0.8, 0.9, 0.95, 0.99):
    print("prune %.0f%%: accuracy" % (fr*100), acc(prune(W1, fr), prune(W2, fr)), " nonzero", int((prune(W1, fr) != 0).sum() + (prune(W2, fr) != 0).sum()))

Knowledge distillation

A big teacher model produces output probabilities. A small student is trained to copy them. To expose the teacher's finer opinions we soften its probabilities with a temperature T: divide the logits by T before softmax. A higher T makes the distribution flatter, so the "dark knowledge" (how likely it thinks the wrong classes are) becomes visible.

soft loss = T² × KL( softmax(teacher/T) ‖ softmax(student/T) )
total loss = α × soft loss + (1 − α) × normal cross-entropy with the true label

The T² factor keeps gradient sizes comparable when T changes. α balances the two terms.

Problem 14.2.2 Teacher logits (4, 1, 0), student logits (2, 1.5, 0.5), true class 0. Compute softened probabilities at T = 1 and T = 4, then the distillation loss.

Step 1T = 1, teacher: e⁴ = 54.60, e¹ = 2.718, e⁰ = 1, sum 58.32, probabilities (0.9362, 0.0466, 0.0171).
Step 2T = 4, teacher logits become (1, 0.25, 0): e = (2.718, 1.284, 1), sum 5.002, probabilities (0.5434, 0.2567, 0.1999). The student at T = 4: (0.3891, 0.3434, 0.2674).
Step 3KL = Σ p_t ln(p_t/p_s) = 0.5434·ln(0.5434/0.3891) + 0.2567·ln(0.2567/0.3434) + 0.1999·ln(0.1999/0.2674) = 0.1815 − 0.0747 − 0.0581 = 0.0487. Times T² = 16: about 0.78 (code: 0.7768; the small difference is rounding in my hand steps).
Step 4Hard loss: the student's T = 1 probability of the true class is 0.5465, so −ln 0.5465 = 0.6041. With α = 0.5: 0.5·0.7768 + 0.5·0.6041 = 0.6905.
AnswerSoft loss 0.7768, hard loss 0.6041, total (α = 0.5) 0.6905.
CheckIf the student matched the teacher exactly, the KL would be 0. Also, at T = 4 the teacher still ranks class 0 first but reveals that class 1 (0.257) is a bit likelier than class 2 (0.200): that is the extra information.
InterpretationThe student gets a richer target than a one-hot label: it learns the teacher's similarities between classes.
import numpy as np
np.set_printoptions(precision=4, suppress=True)
def softmax(z): z = z - z.max(); e = np.exp(z); return e / e.sum()
t_logits = np.array([4.0, 1.0, 0.0]); s_logits = np.array([2.0, 1.5, 0.5])
for T in (1, 4):
    print("T", T, "teacher", softmax(t_logits / T), "student", softmax(s_logits / T))
def kl(p, q): return (p * np.log(p / q)).sum()
T = 4; pt, ps = softmax(t_logits/T), softmax(s_logits/T)
soft = T**2 * kl(pt, ps); hard = -np.log(softmax(s_logits)[0])
print("soft loss (T^2 * KL)", round(soft, 4), " hard CE (true class 0)", round(hard, 4))
for alpha in (0.5, 0.9): print("alpha", alpha, "total", round(alpha*soft + (1-alpha)*hard, 4))

14.3 Deployment: ONNX, Runtimes, and Measuring Latency

INTUITION
A model trained in PyTorch is like a document written in one word processor. To open it on any machine you save it as a PDF. ONNX (Open Neural Network Exchange) is the PDF of models: a framework-neutral file describing the computation graph and weights, so many different engines can run it fast.

Measure before you promise

Do not guess; measure, and report percentiles. Two numbers matter: latency (time for one request) and throughput (requests handled per second). The p50 is the median time, and the p95 is the time that 95% of requests beat; it shows the slow tail that users notice. Batching raises throughput because the hardware does more useful work per call, but it can increase latency, like a delivery van that waits until it is full before leaving: the van is more efficient, but the first parcel waits longer.

import numpy as np, time
rng = np.random.default_rng(0)
W = rng.standard_normal((1024, 1024)).astype(np.float32)
def bench(B, reps=200):
    x = rng.standard_normal((B, 1024)).astype(np.float32)
    for _ in range(10): x @ W                         # warm-up, not counted
    lat = []
    for _ in range(reps):
        t0 = time.perf_counter(); x @ W; lat.append((time.perf_counter() - t0) * 1000)
    lat = np.array(lat); return np.percentile(lat, 50), np.percentile(lat, 95)
for B in (1, 8, 64, 256):
    p50, p95 = bench(B); print("batch %3d  p50 %.3f ms  p95 %.3f ms  throughput %8.0f samples/s  per-sample %.4f ms" % (B, p50, p95, B/(p50/1000), p50/B))

Serving checklist

  1. Fix the service level: a p95 latency target, a throughput, and a cost per 1,000 requests.
  2. Profile the whole path, not only the model: image decoding and resizing on the CPU are often slower than the network (the data-loader lesson from Chapter 5).
  3. Try in order: batching, fp16 or int8, a faster runtime (ONNX Runtime or TensorRT), a smaller model (distillation or pruning).
  4. Warm up at start (the first request is slow: model load, kernel compile).
  5. Load-test with a tool such as Locust or k6 at realistic image sizes and concurrency.
  6. Monitor in production: latency percentiles, GPU memory, input drift and the distribution of prediction confidence (models fail silently, as noted in _missing_topics.md).
  7. Version the model and keep the old one for roll-back.

  1. What is ONNX? Answer: an open, framework-neutral model file format that many runtimes can execute.
  2. Why discard warm-up runs? Answer: first runs are slower (caches, thread start, compilation) and are not typical.

14.4 Distributed Training: Awareness

INTUITION
One person copying a 1,000-page book takes weeks. Hire four people and give each 250 pages and it takes a quarter of the time, but they must agree on the final page numbering. Training on several GPUs is the same: split the work, then synchronise.

Words you need

WordPlain meaning
Data parallel (DDP)Every GPU holds the full model and sees a different slice of the batch; gradients are averaged
All-reduceThe collective operation that sums (then averages) a tensor across all GPUs
Model / tensor parallelOne layer or one model is split across GPUs because it does not fit
Pipeline parallelDifferent layers on different GPUs, with micro-batches flowing through
FSDP / ZeROShard the weights, gradients and optimizer state across GPUs; gather them just in time
Gradient accumulationAdd up gradients over several small steps before one update, to fake a bigger batch

Problem 14.4.1 Show that data parallelism gives the same gradient as one big batch. A regression problem with 64 samples; 4 "GPUs" take 16 samples each.

Formulathe mean-squared-error gradient of a batch is the average of per-sample gradients, so the average of four equal-size sub-batch gradients equals the full-batch gradient.
Step 1Compute the gradient on all 64 samples.
Step 2Compute four gradients on 16 samples each and average them.
AnswerBoth give (−0.09289, 1.17808, −2.34498, −7.8122, −2.83867), and the checker prints True. One worker alone gives something quite different, (0.46031, 1.15345, −3.99136, −3.78263, −4.69383).
CheckThe sub-batches have equal size (16). With unequal sizes you must weight by size.
InterpretationDDP is just a way to compute the same update faster. Averaging gradients is the all-reduce. As a consequence, the effective batch size is per-GPU batch × number of GPUs, which is why learning-rate scaling and warmup matter when you add GPUs (the linear scaling rule listed in _missing_topics.md: when the batch grows by a factor k, try scaling the learning rate by about k, with warmup).
import numpy as np
rng = np.random.default_rng(0)
X = rng.standard_normal((64, 5)); y = X @ np.array([1., -2., 0.5, 3., 0.]) + 0.1*rng.standard_normal(64)
w = rng.standard_normal(5)
grad = lambda Xs, ys, w: 2 * Xs.T @ (Xs @ w - ys) / len(Xs)
full = grad(X, y, w)
workers = [grad(X[i*16:(i+1)*16], y[i*16:(i+1)*16], w) for i in range(4)]   # each "GPU" sees 16 samples
avg = np.mean(workers, axis=0)
print("full-batch gradient     ", full.round(5)); print("average of 4 workers    ", avg.round(5)); print("equal:", np.allclose(full, avg))
print("one worker alone        ", workers[0].round(5))
P = 7e9
bytes_per_param = 2 + 2 + 4 + 4 + 4
print("bytes/param", bytes_per_param, " 7B model:", P*bytes_per_param/1e9, "GB before activations")
for n in (1, 8): print("sharded across", n, "GPUs:", P*bytes_per_param/n/1e9, "GB per GPU")
N = 8; size = 14e9
print("ring all-reduce bytes sent per GPU for 14 GB of gradients on 8 GPUs:", 2*(N-1)/N*size/1e9, "GB")

Problem 14.4.2 Why can a 7-billion-parameter model not be trained on one 80 GB GPU with plain Adam in mixed precision?

Formulacommon estimate of bytes per parameter: fp16 weights 2 + fp16 gradients 2 + fp32 master weights 4 + Adam first moment 4 + Adam second moment 4 = 16.
Compute7 × 10⁹ × 16 = 112 × 10⁹ bytes = 112 GB, before counting activations.
AnswerIt needs about 112 GB for model state alone: more than one 80 GB GPU. Sharding the state across 8 GPUs (FSDP or ZeRO style) brings it to 14 GB per GPU, which fits with room for activations.
CheckThis matches the rule in Chapters 2.1 and 5: memory is roughly parameters + stored activations + optimizer state (plain fp32 with Adam also gives 16 bytes per parameter: 4 weights + 4 gradients + 8 Adam state).
InterpretationThis is why large-model training needs sharding, gradient checkpointing (recompute activations to save memory; see _missing_topics.md) and lower precision. The 16 bytes per parameter figure is the usual rule of thumb for this recipe; other recipes differ.

The last line of the output is the ring all-reduce cost: each GPU sends about 2 × (N−1)/N × size bytes, here 24.5 GB for 14 GB of gradients on 8 GPUs, nearly independent of N. That is why fast links between GPUs (NVLink, InfiniBand) matter: communication can become the bottleneck, just as a slow road limits a fleet of delivery vans however many you buy.

14.6 Interview Bank (Chapters 1 to 14)

Practise answering aloud in 60 seconds each. Answers are model answers; add your own project examples.

Foundations and training (Chapters 1 to 5)

  1. Why do we need non-linear activations? Without them, stacked linear layers collapse into one linear map, so the network could not even solve XOR (Chapter 1).
  2. Walk me through backpropagation. A forward pass stores intermediates; the loss gradient flows backward by the chain rule; each layer multiplies the incoming gradient by its local derivative and produces gradients for its weights; the optimizer updates them (Chapter 2). Verify with a numerical gradient check.
  3. Training loss will not go down. What do you do? Overfit one small batch first; check the data and labels, learning rate, loss function and gradient norms; look for vanishing or exploding gradients; then scale up (Chapter 4).
  4. Adam versus SGD with momentum? Adam adapts a step size per parameter and works well with little tuning; SGD with momentum often generalises well on vision with a tuned schedule. AdamW decouples weight decay (Chapter 3).
  5. Batch norm versus layer norm? Batch norm normalises across the batch and needs reasonable batch sizes; layer norm normalises across features of each sample and is standard in transformers (Chapters 3 and 11).
  6. What does model.eval() do and what does torch.no_grad() do? eval() switches layers such as dropout and batch norm to inference behaviour; no_grad() stops building the autograd graph to save memory and time. You usually need both for inference (Chapter 5).

Vision (Chapters 6 to 9, 12)

  1. Why do CNNs use fewer parameters than dense networks on images? Weight sharing and local connections: parameters depend on kernel size and channels, not image size (Chapter 6).
  2. What problem do residual connections solve? They give gradients a direct path, so very deep networks stay trainable; each block learns a small correction (Chapter 6).
  3. Your classifier has 98% accuracy, but the business is unhappy. Why? Possibly class imbalance, wrong metric, or distribution shift. Look at the per-class confusion matrix and use production-like test data.
  4. What is IoU and mAP? IoU is overlap area divided by union area of two boxes; mAP averages precision across recall levels and classes at chosen IoU thresholds (Chapter 9).
  5. How does a ViT differ from a CNN? It cuts the image into patches and uses global attention with little built-in locality, so it needs more data or pretraining (Chapter 12).
  6. Explain CLIP and zero-shot classification. Two encoders trained with a symmetric contrastive loss on an N×N cosine table; at test time compare an image with text prompts for each class (Chapter 12).

Transformers and generative models (Chapters 10, 11, 13)

  1. Derive self-attention and explain each shape. softmax(QKᵀ/√d_k)V; for (B, T, D) input, heads give (B, H, T, d_h), scores (B, H, T, T), output back to (B, T, D) (Chapter 11).
  2. Why scale by √d_k? Dot products of d_k-long vectors have standard deviation about √d_k; scaling stops softmax from saturating.
  3. What is the KV cache and why is memory the limit in LLM serving? Stored keys and values of past tokens avoid recomputation; they grow with layers, heads, context length and number of users (2.1 GB for one 4,096-token chat in our example).
  4. Why did transformers replace RNNs? They process all tokens in parallel, so training scales on GPUs, and attention gives direct long-range paths (Chapters 10 and 11).
  5. VAE versus GAN versus diffusion? VAE: smooth latent space, blurrier; GAN: sharp and fast, unstable, mode collapse; diffusion: stable training and high quality, slower sampling (Chapter 13).
  6. What does a diffusion network predict, and what is classifier-free guidance? It predicts the added noise at step t; guidance extrapolates ε_uncond + w(ε_cond − ε_uncond) to follow the prompt more strongly.

Efficiency and production (Chapter 14)

  1. Explain int8 quantization. Map floats to integers with a scale s = max|w|/127; dequantize by q×s; error at most half a step; per-channel scales and outlier handling matter; check accuracy per class.
  2. Pruning versus distillation? Pruning removes weights from a trained model (structured pruning for real speed-up); distillation trains a smaller model to mimic a larger teacher's softened outputs.
  3. A model is too slow in production. What is your process? Measure p50/p95 for the whole path, find the bottleneck (preprocessing, model, I/O), then batch, lower precision, change runtime (ONNX Runtime, TensorRT), and finally shrink the model; re-test.
  4. How would you estimate GPU memory to fine-tune a 7B model? About 16 bytes per parameter for mixed-precision Adam (112 GB) plus activations; reduce with sharding (FSDP), LoRA, quantized base weights and gradient checkpointing.
  5. Why does DDP give the same result as one big batch? Averaging equal-size sub-batch gradients equals the full-batch gradient (we checked); only the speed changes.
  6. How do you detect that a deployed vision model is silently failing? Monitor input statistics and prediction confidence, track metrics on a regularly labelled sample, and alert on drift in lighting, camera or product changes.
  7. Tell me about a project and what failed. Use the "What failed and why" section of your capstone.

Chapter recap

  • Quantization stores weights as small integers with a scale: s = max|w|/127, error up to s/2; int8 and often int4 keep accuracy (our measured model held 0.985 down to 4 bits, and broke at 2 bits); outliers need per-channel scales.
  • Memory for weights is parameters times bytes: 7B parameters is 28 GB in fp32, 14 GB in fp16, 3.5 GB in int4.
  • Pruning removes small weights (our model lost nothing at 50%, collapsed at 90%); only structured pruning gives easy speed-ups; fine-tune after pruning.
  • Distillation trains a small student on the teacher's temperature-softened probabilities: α·T²·KL + (1−α)·CE.
  • ONNX is a portable model file; runtimes (ONNX Runtime, TensorRT, OpenVINO, TFLite, Core ML) fuse operators and lower precision; verify exported outputs match.
  • Measure before you promise: warm up, report p50/p95, trade batch size between throughput and latency, profile the whole path.
  • Data parallel training equals a big-batch update (average gradients); big models need sharding (about 16 bytes per parameter for mixed-precision Adam); communication can be the bottleneck.
  • Capstone projects need numeric acceptance criteria, a baseline and an honest failure analysis.

Practice set

1. (easy) Quantize w = 0.5 with s = 0.01. What is q and the dequantized value? Answer: q = round(0.5/0.01) = 50; dequantized 50 × 0.01 = 0.5.

2. (easy) Memory of a 3-billion-parameter model in fp16 and in int4. Answer: fp16 3 × 2 = 6 GB; int4 3 × 0.5 = 1.5 GB.

3. (computation) Weights (0.2, −0.9, 0.45), symmetric int8. Find s and the codes. Answer: s = 0.9/127 = 0.007087. Codes: 0.2/0.007087 = 28.2, so 28; −0.9 gives −127; 0.45/0.007087 = 63.5, exactly halfway, so rounding depends on the rule (NumPy's round-half-to-even gives 64).

4. (what is the output?) softmax([2, 0]) and softmax([2, 0]/4) (first entry). Answer: 0.8808 and softmax([0.5, 0]) = e^0.5/(e^0.5+1) = 1.6487/2.6487 = 0.6225. The temperature flattens it.

5. (computation) Teacher probabilities (0.7, 0.2, 0.1) and student (0.5, 0.3, 0.2) at T = 1. Compute the KL. Answer: 0.7·ln(0.7/0.5) + 0.2·ln(0.2/0.3) + 0.1·ln(0.1/0.2) = 0.7·0.3365 + 0.2·(−0.4055) + 0.1·(−0.6931) = 0.2355 − 0.0811 − 0.0693 = 0.0851.

6. (computation) A batch of 32 takes 8 ms (p50). What is the throughput and the per-sample time? Answer: 32/0.008 = 4,000 samples/s; 8/32 = 0.25 ms per sample.

7. (find the bug) After ONNX export, the outputs differ from PyTorch by 0.2. What do you check first? Answer: whether model.eval() was called before export (dropout and batch-norm behaviour), then the preprocessing (same normalisation and resize), then the input shape and dynamic axes.

8. (find the bug) A team multiplied GPUs by 8 and the loss became unstable at the same learning rate. Why? Answer: the effective batch grew 8 times. Scale the learning rate (about linearly) and add warmup, then verify convergence.

9. (computation) Per-GPU batch 24, 8 GPUs, accumulation 4. What is the effective batch? Answer: 24 × 8 × 4 = 768.

10. (scenario) An image service has p95 of 400 ms but needs 150 ms. Preprocessing takes 220 ms (CPU image decoding and resizing), the model 140 ms. What do you do first? Answer: the bottleneck is preprocessing (220 of 360 ms), not the model, so shrinking the model first would be wasted effort. Move decoding to a faster library or the GPU, resize once, parallelise, cache; then batch and quantize the model if still needed. Re-measure percentiles.

11. (interview) "You must run a 13B-parameter model on a 24 GB GPU for inference. Is it possible?" Answer: fp16 weights need 26 GB, too big. With 8-bit weights 13 GB, with 4-bit about 6.5 GB. Both fit, leaving room for the KV cache (Chapter 11). Check quality on your task after quantizing.

12. (interview) "How would you prove that a compressed model is as good as the original?" Answer: keep one fixed, representative test set; compare overall and per-class metrics, calibration and tail latency (p95); test on recent production samples; run a shadow deployment or A/B test before switching; keep roll-back ready.
