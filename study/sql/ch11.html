Bad data usually starts as a bad table design. A customer's city stored in five places gives five different answers. A comma-separated list in one column makes "which orders contain a mouse?" painful. And a dashboard that joins ten tables for every click is slow and hard to understand. In this chapter you learn to design a schema in three steps: draw it (ER diagram), clean it (normalization), then reshape it for reporting (star schema and slowly changing dimensions). By the end you can take a messy spreadsheet and turn it into sound tables, and explain in an interview when you would break the rules.

We keep using the shop database from Chapter 2 (customers, products, orders, order_items). All SQL ran in SQLite 3.51, except where I write not run here.

11.1 ER Diagrams, Keys and Naming

INTUITION
Before building a house, an architect draws a plan: rooms and doors. An ER diagram (Entity-Relationship diagram) is the plan of a database: the things you store, and how they connect. Drawing takes ten minutes. Changing a live table with 50 million rows takes weeks.

Words you need

  • Entity: a kind of thing you store (customer, product, order). It becomes a table.
  • Attribute: a property of an entity (name, price). It becomes a column.
  • Relationship: how two entities connect (a customer places orders). It becomes a foreign key, or a separate table.
  • Cardinality: how many on each side: one-to-one (1:1), one-to-many (1:N), many-to-many (M:N).
  • Junction table (also bridge or associative table): a table that turns M:N into two 1:N.

How to read the diagram

 CUSTOMER 1 ----< places >---- N ORDER N ----< contains >---- M PRODUCT
 (PK customer_id)               (PK order_id,                  (PK product_id)
                                 FK customer_id)
 
 M:N ORDER-PRODUCT becomes a junction table ORDER_ITEM:

 +-----------+ 1     N +---------+ 1      N +------------+ N     1 +-----------+
 | customers |---------| orders  |----------| order_items|---------| products  |
 +-----------+         +---------+          +------------+         +-----------+
 customer_id PK        order_id PK          (order_id, product_id) PK   product_id PK
                       customer_id FK       qty, unit_price

Read "1 --- N" as "one customer has many orders." The line sits on the "many" side where the foreign key lives. Rule: the foreign key always goes on the "many" side.

RelationshipHow to build itExample
1:Nforeign key on the N sideorders.customer_id
M:Njunction table with two FKs (+ own attributes)order_items(order_id, product_id, qty, unit_price)
1:1FK with UNIQUE, or merge into one tableuser and user_profile

Worked examples

Problem 11.1.1 A learning platform has students, courses and enrollments (a student takes many courses, a course has many students, and each enrollment has a grade). Design the tables.

Step 1Entities: students, courses.
Step 2Students to courses is M:N, and the grade belongs to the pair. So we need a junction table enrollments.
Step 3Primary key of the junction table is the pair (student_id, course_id), so a student cannot enroll twice in one course.
CREATE TABLE students (student_id INTEGER PRIMARY KEY, name TEXT NOT NULL);
CREATE TABLE courses  (course_id  INTEGER PRIMARY KEY, title TEXT NOT NULL);
CREATE TABLE enrollments (
  student_id INTEGER NOT NULL REFERENCES students(student_id),
  course_id  INTEGER NOT NULL REFERENCES courses(course_id),
  grade      INTEGER CHECK (grade BETWEEN 0 AND 100),
  PRIMARY KEY (student_id, course_id)
);
  • Answer Three tables. Each fact lives once: a student's name in students, a grade in enrollments.
  • Check If the grade were put in students, which course would it belong to? It has no home. That tells you it belongs on the relationship.

Problem 11.1.2 Where does the foreign key go for "an employee works in one department; a department has many employees"?

Step 1One department, many employees: department is the "one" side.
Step 2The FK goes on the "many" side: employees.department_id REFERENCES departments(department_id).
AnswerThe employees table holds the FK. Chapter 1 already did this with departments and employees.

Surrogate keys, data types and naming (small rules that matter)

  • Use a surrogate primary key (customer_id) and a UNIQUE constraint on the natural key (see 9.2).
  • Pick the smallest sensible type: INTEGER ids, NUMERIC(12,2) for money, TIMESTAMPTZ for event times (store UTC), DATE for dates, BOOLEAN for flags. Never store dates as text in PostgreSQL (SQLite has no date type; it stores text, as in our shop data).
  • Naming: snake_case, same name for the same thing everywhere (customer_id in both tables), no spaces, no reserved words like order or group, tables as plural nouns, and booleans as is_active.

Connection to the real job

In design reviews and interviews you are often asked "draw the schema for X." The expected answer: entities, keys, cardinalities, the junction tables, and the reasons. Analysts read an ER diagram first when they join a new company's database.

Applications

  • Back ends: model users, orders, payments before writing code.
  • Data Engineering: read the source system's ER diagram before building a pipeline.
  • Data Analytics: know which join key to use and which side repeats rows (Chapter 4).
  • ML: features come from joins: the ER diagram tells you how rows multiply.

Check yourself

  1. Where does the foreign key go in a 1:N relationship?

Answer: On the "many" side.

  1. How do you model a many-to-many relationship?

Answer: With a junction table holding two foreign keys.

  1. Why is order a bad table name?

Answer: It is a reserved SQL word (ORDER BY), so it needs quoting; use orders.

11.2 Normalization: 1NF, 2NF, 3NF and BCNF

INTUITION
Imagine writing a customer's phone number on every sales slip. When they change number, you must find and fix every slip, and if you miss one, two numbers exist for one person. Normalization is the discipline of writing each fact in one place only. The slogan: every non-key column depends on the key, the whole key, and nothing but the key.

Words you need

  • Functional dependency (FD): "A determines B," written A → B: if two rows have the same A, they must have the same B. Example: product_id → product_name.
  • Candidate key: a minimal set of columns that identifies a row.
  • Anomaly: a bug caused by repeated data. Three kinds: update anomaly (change in some places only), insert anomaly (cannot store a fact without another), delete anomaly (deleting a row loses an unrelated fact).
  • Normal form: a level of tidiness. Each form includes the one before it.

The messy starting point

CREATE TABLE flat (
  order_id INT, product_id INT, product_name TEXT, category TEXT,
  customer_id INT, customer_city TEXT, qty INT,
  PRIMARY KEY (order_id, product_id));
INSERT INTO flat VALUES
 (101,1,'Keyboard','Electronics',1,'Pune',1),
 (101,3,'Notebook','Stationery',1,'Pune',2),
 (103,1,'Keyboard','Electronics',1,'Pune',1),
 (102,2,'Mouse','Electronics',2,'Mumbai',1);

Keyboard's name and category repeat in rows 1 and 3. Customer 1's city repeats three times. This is a spreadsheet pretending to be a table.

The forms, one at a time

FormRuleViolation looks like
1NFeach cell holds one value; no repeating groups; rows are identified by a keyproducts = 'Keyboard,Mouse' in one cell
2NFin 1NF, and no non-key column depends on part of a composite keyproduct_name depends only on product_id, not on (order_id, product_id)
3NFin 2NF, and no non-key column depends on another non-key columncustomer_city depends on customer_id, which is not the key
BCNFfor every dependency A → B, A must be a candidate keysee the course example below

1NF in action. A table stores products as 'Keyboard,Mouse' in one cell. Which orders contain a mouse?

CREATE TABLE orders_bad (order_id INT, customer TEXT, city TEXT, products TEXT);
INSERT INTO orders_bad VALUES
 (1,'Asha','Pune','Keyboard,Mouse'),(2,'Asha','Pune','Notebook'),(3,'Ravi','Mumbai','Mouse');
SELECT count(*) AS orders_with_mouse FROM orders_bad WHERE products LIKE '%Mouse%';
orders_with_mouse
-----------------
2
  • Step 1 LIKE '%Mouse%' finds orders 1 and 3, so 2 is right today.
  • Step 2 It would also match a product named Mouse Pad or Bluetooth Mouse: wrong count with no error. It cannot use an index (Chapter 10, leading wildcard). You cannot join the list to products.
  • Answer The count is right by luck. The fix for 1NF is one row per (order, product), which is exactly the order_items table you already know.

Problem 11.2.1 (find the functional dependency). Does product_id → product_name hold in flat? Test it with SQL: group by the left side and count distinct values on the right. Any group with more than 1 value is a violation.

SELECT product_id, COUNT(DISTINCT product_name) AS names
FROM flat GROUP BY product_id HAVING COUNT(DISTINCT product_name) > 1;
(no rows)
  • Step 1 No product has two names, so the FD holds in today's data.
  • Step 2 Now simulate the update anomaly: someone fixes the name in one row only, with a typo.
UPDATE flat SET product_name = 'Keybord' WHERE order_id = 101 AND product_id = 1;
-- run the same check again
product_id  names
----------  -----
1           2
  • Answer Product 1 now has two names. The same fact is stored twice, so the copies drifted apart. This is why we split the table.
  • Meaning Careful: data can only disprove an FD. A test that finds no violation shows the FD holds in this data, not that it must hold forever. The business rule decides.

Problem 11.2.2 (normalize to 3NF). Apply the rules to flat.

Step 1 (2NF)product_name and category depend only on product_id, part of the key (order_id, product_id). Move them to a products table keyed by product_id.
Step 2 (3NF)customer_city depends on customer_id, which depends on order_id. Move customer and city into a table keyed by the customer, and keep customer_id on the order. (Our quick script keeps a combined orders table with customer_city for brevity; a full design has a separate customers table like Chapter 2.)
Step 3What remains, (order_id, product_id, qty), has only qty, which depends on the whole key.
CREATE TABLE p  AS SELECT DISTINCT product_id, product_name, category FROM flat;
CREATE TABLE o  AS SELECT DISTINCT order_id, customer_id, customer_city FROM flat;
CREATE TABLE oi AS SELECT order_id, product_id, qty FROM flat;
SELECT (SELECT count(*) FROM flat) AS flat_rows, (SELECT count(*) FROM p) AS p,
       (SELECT count(*) FROM o) AS o, (SELECT count(*) FROM oi) AS oi;
flat_rows  p  o  oi
---------  -  -  --
4          3  3  4
  • Check (lossless) Join the pieces back; we must get the original 4 rows with the same facts:
SELECT o.order_id, p.product_name, oi.qty, o.customer_city
FROM oi JOIN p USING (product_id) JOIN o USING (order_id) ORDER BY 1,2;
order_id  product_name  qty  customer_city
--------  ------------  ---  -------------
101       Keyboard      1    Pune         
101       Notebook      2    Pune         
102       Mouse         1    Mumbai       
103       Keyboard      1    Pune
  • Answer Four rows, identical to the original facts. p has 3 rows (Keyboard stored once, not twice) and o has 3 orders. The city is stored once per order here and once per customer in a full design, so changing Pune takes one UPDATE.
  • Why it matters A good decomposition is lossless: joining the parts gives back exactly the original, with no missing and no extra rows.

BCNF. 3NF still allows one odd case. Take a table enroll(student, course, instructor) where each instructor teaches only one course (instructor → course), but the key is (student, course).

student  course  instructor
Asha     SQL     Rao
Ravi     SQL     Rao
Asha     Python  Iyer
Meena    Python  Iyer

Here instructor → course, but instructor is not a candidate key. That breaks BCNF. Rao's course is repeated in every student row. Test the FD:

SELECT instructor, COUNT(DISTINCT course) AS courses FROM enroll GROUP BY instructor;
instructor  courses
----------  -------
Iyer        1      
Rao         1

Each instructor has exactly one course in this data, consistent with the rule. The fix: teaches(instructor, course) and enrollment(student, instructor). BCNF is rarely a problem in practice; most designs that reach 3NF are already in BCNF. (4NF and 5NF deal with multi-valued dependencies; just know the names.)

COMMON MISTAKE
Treating normal forms as magic words. Ask the simple question instead: "If this fact changes, how many rows must I edit?" The answer should be one.
COMMON MISTAKE
Concluding an FD from a small sample. city → state looks true until a second Springfield appears. FDs come from business rules, so ask the business.

Connection to the real job

Operational (OLTP) databases are normalized to 3NF so writes are safe and fast. When you query them for analysis you re-join the pieces back, which is why Chapter 4 on joins matters so much.

Applications

  • Back ends: 3NF keeps checkout, user and inventory data consistent.
  • Data Engineering: you split wide source files (CSV exports) into clean tables when loading.
  • Data Analytics: you read the normalized source to find where each metric lives.
  • Data quality: FD checks with GROUP BY ... HAVING COUNT(DISTINCT ...) > 1 find dirty data.

Check yourself

  1. What does A → B mean?

Answer: Whenever two rows have the same A, they have the same B.

  1. Which normal form removes dependency on part of a composite key?

Answer: 2NF.

  1. Name the three anomalies.

Answer: Update, insert and delete anomalies.

11.3 Denormalization and OLTP vs OLAP

INTUITION
A restaurant kitchen is organised for cooking: ingredients stored once in separate shelves (normalized). But the menu card the customer reads has everything pre-combined: "Paneer wrap with fries and a drink, Rs 250" (denormalized). Cooking and menu-reading are different jobs, so you organise differently for each. In databases the two jobs are OLTP (taking orders) and OLAP (reading reports).

Words you need

  • OLTP (Online Transaction Processing): many small, fast reads and writes (place an order, update an address). Like the billing counter of a shop.
  • OLAP (Online Analytical Processing): fewer, heavy queries that scan lots of rows and aggregate (revenue by month and city).
  • Denormalization: deliberately storing repeated or pre-joined data to make reads faster or simpler.
  • Data warehouse: a database built for OLAP, fed from many OLTP systems.
  • Row store vs column store: a row store keeps a whole row together (good for OLTP). A column store keeps each column together (good for scanning one column across many rows: ClickHouse, BigQuery, Snowflake, Redshift, and Parquet files).

Problem 11.3.1 Our dashboard shows revenue per customer city. Normalized, that needs customers JOIN orders JOIN order_items. Estimate the work, then reduce it with a summary table.

CREATE TABLE city_revenue AS
SELECT c.city, SUM(i.qty * i.unit_price) AS revenue
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
JOIN order_items i ON i.order_id = o.order_id
WHERE o.status = 'paid'
GROUP BY c.city;
  • Step 1 Run the 3-table join once, store the result. The dashboard now reads the small summary table.
  • Step 2 With 100 million order items and 50 cities, each dashboard view reads 50 rows instead of scanning and joining 100 million.
  • Answer Reads are far cheaper, in exchange for a refresh job and staleness: the table is only as fresh as its last refresh.
  • Check The summary must equal the live query. Compare SUM(revenue) from both; they must match, otherwise the refresh has a bug.
COMMON MISTAKE
Denormalizing first "for speed." Normalize first, measure, and denormalize only the proven hot path. Every copy needs a plan to keep it in sync (a trigger, a refresh job, or one code path).
PROFESSOR'S NOTE
You will hear "NoSQL denormalizes everything." Document stores such as MongoDB embed related data inside one document, which is denormalization again. This document teaches relational design only.

Connection to the real job

Data engineers move data from OLTP databases (normalized) to a warehouse (denormalized). This is the ETL or ELT job (extract, transform, load): extract from the source, reshape, load into star schemas. Analysts live on the OLAP side; back-end developers live on the OLTP side. Knowing both lets you talk to both teams.

Applications

  • Data Analytics: dashboards read pre-aggregated tables, not raw logs.
  • Data Engineering: nightly jobs fill warehouse tables from operational ones.
  • ML: training tables are wide and flat, with one row per example.
  • Operations: heavy reports must not run on the primary OLTP database during the busiest sale hours; use a replica or warehouse.

Check yourself

  1. Which workload uses normalized tables, OLTP or OLAP?

Answer: OLTP.

  1. Give one risk of denormalization.

Answer: The repeated copies can become inconsistent unless you keep them in sync.

  1. Why are column stores good for analytics?

Answer: A query reading one or two columns over millions of rows reads only those columns from disk.

11.4 Star and Snowflake Schemas

INTUITION
Imagine a receipt (the event: what was sold, how many, how much) surrounded by description cards: who bought (customer), what (product), when (date). The receipt is the fact. The cards are dimensions. Draw the receipt in the middle and the cards around it: a star.

Words you need

  • Fact table: one row per business event (a sale line, a page view). Mostly numbers (measures: qty, revenue) and keys to dimensions. Usually the biggest table.
  • Dimension table: descriptive attributes used to filter and group (city, category, month). Usually small and wide.
  • Grain: what one row of the fact table means. Decide the grain first. Ours: one row per order line.
  • Measure: a number you add up (revenue).
  • Surrogate key in a dimension: a warehouse-made id (cust_sk), needed for slowly changing dimensions (11.5).

Build one from the shop

CREATE TABLE dim_product  AS SELECT product_id AS product_key, name AS product_name, category FROM products;
CREATE TABLE dim_customer AS SELECT customer_id AS customer_key, name AS customer_name, city FROM customers;
CREATE TABLE dim_date (date_key TEXT PRIMARY KEY, year INT, month INT, month_name TEXT);
INSERT INTO dim_date
SELECT DISTINCT order_date, CAST(strftime('%Y',order_date) AS INT), CAST(strftime('%m',order_date) AS INT),
       CASE strftime('%m',order_date) WHEN '01' THEN 'Jan' WHEN '02' THEN 'Feb' WHEN '03' THEN 'Mar' ELSE 'Apr' END
FROM orders;
CREATE TABLE fact_sales AS
SELECT o.order_id, o.order_date AS date_key, o.customer_id AS customer_key,
       i.product_id AS product_key, i.qty, i.qty * i.unit_price AS revenue
FROM orders o JOIN order_items i USING (order_id)
WHERE o.status = 'paid';
SELECT count(*) AS fact_rows, sum(revenue) AS total FROM fact_sales;
fact_rows  total
---------  -----
18         12660

Problem 11.4.1 Revenue for March by product category and customer city.

SELECT d.month_name, p.category, c.city, SUM(f.revenue) AS revenue
FROM fact_sales f
JOIN dim_date     d ON d.date_key     = f.date_key
JOIN dim_product  p ON p.product_key  = f.product_key
JOIN dim_customer c ON c.customer_key = f.customer_key
WHERE d.month = 3
GROUP BY d.month_name, p.category, c.city
ORDER BY revenue DESC;
month_name  category     city       revenue
----------  -----------  ---------  -------
Mar         Electronics  Pune       1200   
Mar         Home         Mumbai     900    
Mar         Stationery   Mumbai     440    
Mar         Stationery   Bengaluru  360    
Mar         Stationery   Pune       80
  • Step 1 The query starts at the fact table and joins to each dimension on its key: one join per dimension, always the same shape.
  • Step 2 Filters and groupings come from dimension columns (month, category, city). Sums come from the fact (revenue).
  • Check by hand Order 106 (March, customer 1 in Pune) is 2 mice at 600 = 1200 plus a notebook at 80. The mouse line is Electronics/Pune = 1200, the notebook line is Stationery/Pune = 80. Both match. Order 108 (customer 2, Mumbai, Home) is 900, also matching.
  • Check (total) All paid revenue directly from the source tables was also 12,660, equal to the fact total.
  • Answer A star schema answers any "measure by attributes" question with the same simple pattern.

The picture

                     dim_date
                        |
 dim_customer ------ fact_sales ------ dim_product
   (who)          (order_id, date_key,      (what)
                   customer_key,

The fact table is in the middle. Each arm is one join. Dimensions are denormalized: category sits right in dim_product.

Star vs snowflake

A snowflake schema normalizes the dimensions further: dim_product points to dim_category, which points to dim_department. It saves some storage and keeps one copy of the category name, but needs more joins.

StarSnowflake
Dimension tablesdenormalized, flatnormalized, split into sub-tables
Joins per queryfewermore
Storageslightly moreslightly less
Query simplicityhighlower
Usedefault for BI tools and warehouseswhen a dimension is huge or shared, or hierarchies need their own maintenance

Storage is cheap and analyst time is not, so star is the usual choice.

Date dimension and calendar tables

A dim_date table with one row per day (year, quarter, month, week, is_weekend, holiday flags) is standard. It lets analysts group by "Q1" or "weekend" without date functions, and it supplies days with zero sales, which a plain GROUP BY on the fact table cannot show (the date spine idea from the analytics section).

Connection to the real job

Tools such as Power BI, Tableau and Looker expect star schemas. dbt projects name models fact_ and dim_. In an interview "design a data model for an e-commerce / food-delivery / ride-share app" means: pick the grain, list the facts, list the dimensions, mention the date dimension.

Applications

  • Data Analytics: BI dashboards built on facts and dimensions.
  • Data Engineering: warehouse models in dbt, Snowflake, BigQuery.
  • ML: feature tables made by joining a fact table to dimensions.
  • Healthcare: a star model for appointments: fact_appointments with dim_doctor, dim_patient and dim_date makes trend reports simple.

Check yourself

  1. What is the grain of fact_sales above?

Answer: One row per paid order line (an order and a product).

  1. Fact or dimension: revenue? city?

Answer: revenue is a fact measure; city is a dimension attribute.

  1. Why is a star usually preferred to a snowflake?

Answer: Fewer joins and simpler queries; the extra storage is cheap.

11.5 Slowly Changing Dimensions (SCD)

INTUITION
Asha lived in Pune and ordered in January. In March she moves to Delhi and orders again. If you simply overwrite her city with Delhi, then January's order looks as if it came from Delhi, and your "revenue by city" history is rewritten and wrong. A dimension attribute that changes slowly and occasionally is a slowly changing dimension. The question is: do you want history or not?

The types

TypeWhat it doesHistory kept?Use when
SCD 0never changesn/afixed values (birth date)
SCD 1overwrite the old valueNocorrections, typos, values nobody analyses by time
SCD 2add a new row, close the old one with datesFull"as it was then" reporting (the common choice)
SCD 3add a column previous_cityOnly one previous valuerare, "current and previous" only

SCD 1: overwrite

CREATE TABLE d1 (customer_id INT PRIMARY KEY, city TEXT);
INSERT INTO d1 VALUES (1,'Pune');
UPDATE d1 SET city = 'Delhi' WHERE customer_id = 1;
SELECT * FROM d1;
customer_id  city 
-----------  -----
1            Delhi

Pune is gone. January's orders will now report Delhi.

SCD 2: add a row

Each version of a customer gets its own row, a new surrogate key, a validity period and an is_current flag. The natural key customer_id repeats.

Problem 11.5.1 Asha (customer 1) moves from Pune to Delhi on 2024-03-10. Record it as SCD 2, then find the city on the date of each order.

CREATE TABLE dim_cust (
  cust_sk INTEGER PRIMARY KEY, customer_id INT, name TEXT, city TEXT,
  valid_from TEXT, valid_to TEXT, is_current INT);
INSERT INTO dim_cust (customer_id,name,city,valid_from,valid_to,is_current) VALUES
 (1,'Asha','Pune','2024-01-05','9999-12-31',1),
 (2,'Ravi','Mumbai','2024-01-12','9999-12-31',1);

BEGIN;
UPDATE dim_cust SET valid_to = '2024-03-10', is_current = 0
 WHERE customer_id = 1 AND is_current = 1;
INSERT INTO dim_cust (customer_id,name,city,valid_from,valid_to,is_current)
 VALUES (1,'Asha','Delhi','2024-03-10','9999-12-31',1);
COMMIT;
SELECT * FROM dim_cust ORDER BY cust_sk;
cust_sk  customer_id  name  city    valid_from  valid_to    is_current
-------  -----------  ----  ------  ----------  ----------  ----------
1        1            Asha  Pune    2024-01-05  2024-03-10  0         
2        2            Ravi  Mumbai  2024-01-12  9999-12-31  1         
3        1            Asha  Delhi   2024-03-10  9999-12-31  1
  • Step 1 Close the old row: set valid_to to the change date and is_current = 0.
  • Step 2 Insert a new row with a new cust_sk (3), the new city, valid_from = the change date, and the far-future 9999-12-31 as "open end."
  • Step 3 Both statements sit in one transaction (Chapter 9), so no reader sees a customer with zero or two current rows.

Now link orders to the version that was true on the order date:

CREATE TABLE fact_o (order_id INT, customer_id INT, order_date TEXT, revenue INT);
INSERT INTO fact_o VALUES (101,1,'2024-01-10',1660),(106,1,'2024-03-20',680);
SELECT f.order_id, f.order_date, d.city
FROM fact_o f
JOIN dim_cust d ON d.customer_id = f.customer_id
 AND f.order_date >= d.valid_from AND f.order_date < d.valid_to
ORDER BY f.order_id;
order_id  order_date  city 
--------  ----------  -----
101       2024-01-10  Pune 
106       2024-03-20  Delhi
  • Answer The January order shows Pune, the March order shows Delhi. History is preserved.
  • Check Each order matched exactly one dimension row: 2 orders in, 2 rows out. If a join like this ever returns more rows than the fact table, your validity periods overlap (a data bug). The interval is inclusive at the start, exclusive at the end (>= valid_from AND < valid_to) so the change date belongs to only one row.
  • Alternative Many warehouses store the surrogate key in the fact table at load time (customer_sk), so the fact points straight to the right version and no date join is needed.

SCD 3 adds a column such as previous_city. It keeps one step of history only, and is used rarely. There are also hybrid types (SCD 4, 6); just know they exist.

COMMON MISTAKE
Forgetting to filter is_current = 1 when you want today's customers: each moved customer is counted twice. And forgetting that COUNT(DISTINCT customer_id), not COUNT(*), counts people in an SCD 2 table.
COMMON MISTAKE
Using SCD 2 for everything. Every tracked column multiplies rows. Track only attributes the business analyses over time (city, plan tier, sales region), and use SCD 1 for typo fixes.

Connection to the real job

SCD 2 is a favourite interview topic for data engineering. dbt offers snapshots that implement SCD 2 for you. In customer analytics ("did churn differ by plan tier at the time?"), history decides whether the answer is right.

Applications

  • Data Engineering: SCD 2 loads in warehouses; dbt snapshots.
  • Data Analytics: "as-was" reporting of region or plan tier.
  • ML: point-in-time correct features (no peeking at attributes the customer got later), which prevents data leakage.
  • Finance: historical price lists and tax rates.

Check yourself

  1. Which SCD type keeps full history?

Answer: Type 2.

  1. Why does SCD 2 need a surrogate key?

Answer: The natural key (customer_id) repeats across versions, so each row needs its own unique key.

  1. Why use valid_to as exclusive in the join?

Answer: So the change date matches only one version, not two.

11.6 Modelling Extras: Functional-Dependency Closure, BCNF by Algorithm, and Patterns You Will Meet

INTUITION
Section 11.2 found normalization problems by eye. Eyes miss things in a table with twelve columns. Database theory gives a mechanical test: write the rules of the data as functional dependencies (FDs), compute what each column set determines (its closure), and read off the keys and the violations. Then you decompose by algorithm, and prove with a query that nothing was lost.

Words you need

  • Functional dependency X -> Y: whenever two rows agree on X they must agree on Y. 'course -> teacher' says each course has one teacher.
  • Closure of a set X, written X+: every column determined by X, found by applying the FDs again and again.
  • Superkey: a column set whose closure is all columns. A candidate key is a minimal superkey.
  • BCNF: every FD X -> Y has a superkey on the left. Any FD that breaks this is a violation.

Problem 11.6.1 A table enrol(student, course, grade, teacher, office) has the rules: (student, course) -> grade, course -> teacher, teacher -> office. Find the candidate key and the BCNF violations. Predict first: the key is (student, course), and both course -> teacher and teacher -> office violate BCNF.

from itertools import combinations
attrs = {"student", "course", "grade", "teacher", "office"}
fds = [({"student", "course"}, {"grade"}), ({"course"}, {"teacher"}), ({"teacher"}, {"office"})]

def closure(x):
    """everything that x determines, by repeatedly applying the rules"""
    x = set(x)
    changed = True
    while changed:
        changed = False
        for left, right in fds:
            if left <= x and not right <= x:
                x |= right
                changed = True
    return x

print("closure of {course}          :", sorted(closure({"course"})))
print("closure of {student,course}  :", sorted(closure({"student", "course"})))
keys = [set(c) for n in range(1, 4) for c in combinations(sorted(attrs), n) if closure(c) == attrs]
minimal = [k for k in keys if not any(o < k for o in keys)]
print("candidate keys:", [sorted(k) for k in minimal])
for left, right in fds:
    ok = closure(left) == attrs
    print("%-18s -> %-8s left side is a superkey: %s" % (",".join(sorted(left)), ",".join(sorted(right)), ok))
closure of {course}          : ['course', 'office', 'teacher']
closure of {student,course}  : ['course', 'grade', 'office', 'student', 'teacher']
candidate keys: [['course', 'student']]
course,student     -> grade    left side is a superkey: True
course             -> teacher  left side is a superkey: False
teacher            -> office   left side is a superkey: False
Step 1Closure of {course}: start with course. Rule 2 adds teacher. Rule 3 then adds office. Nothing else applies: {course, office, teacher}. It is missing student and grade, so course alone is not a key.
Step 2Closure of {student, course}: rule 1 adds grade, rule 2 teacher, rule 3 office. That is all five columns, so it is a key, and it is minimal because neither student nor course alone reaches everything.
Step 3Check each rule's left side. (student, course) is a superkey, so rule 1 is fine. course is not, so course -> teacher violates BCNF. teacher is not, so teacher -> office violates too.
MeaningThe violations are exactly the redundancy you would see: the office of 'Iyer' is repeated for every enrolment of every course Iyer teaches, and an office change has to be made in several rows.

The decomposition algorithm and the lossless check

Pick a violating FD X -> Y. Split the table into (X plus Y) and (everything except Y, which keeps X). Repeat on each piece until none violates. Here: split on teacher -> office first (teacher_office), then course -> teacher (course_teacher), leaving (student, course, grade). Because each split keeps the determinant X as the join column, the pieces rejoin exactly. The code builds the three tables and proves it:

import sqlite3
db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE enrol (student TEXT, course TEXT, grade TEXT, teacher TEXT, office TEXT);
INSERT INTO enrol VALUES
 ('Asha','SQL','A','Rao','B12'), ('Ravi','SQL','B','Rao','B12'),
 ('Asha','Stats','B','Iyer','C03'), ('Meena','Stats','A','Iyer','C03'),
 ('Ravi','ML','A','Iyer','C03');
-- BCNF decomposition from the closure analysis
CREATE TABLE teacher_office (teacher TEXT PRIMARY KEY, office TEXT);
CREATE TABLE course_teacher (course TEXT PRIMARY KEY, teacher TEXT REFERENCES teacher_office);
CREATE TABLE grade_of (student TEXT, course TEXT REFERENCES course_teacher, grade TEXT, PRIMARY KEY (student, course));
INSERT INTO teacher_office SELECT DISTINCT teacher, office FROM enrol;
INSERT INTO course_teacher SELECT DISTINCT course, teacher FROM enrol;
INSERT INTO grade_of SELECT student, course, grade FROM enrol;
""")
rebuilt = db.execute("""SELECT g.student, g.course, g.grade, c.teacher, t.office
  FROM grade_of g JOIN course_teacher c ON c.course = g.course JOIN teacher_office t ON t.teacher = c.teacher
  ORDER BY 1, 2""").fetchall()
original = db.execute("SELECT * FROM enrol ORDER BY 1, 2").fetchall()
print("rows original:", len(original), "| rows rebuilt:", len(rebuilt), "| identical:", rebuilt == original)
db.execute("UPDATE teacher_office SET office = 'D07' WHERE teacher = 'Iyer'")   # one place to change
print(db.execute("SELECT DISTINCT course, office FROM course_teacher c JOIN teacher_office t USING (teacher) ORDER BY 1").fetchall())
rows original: 5 | rows rebuilt: 5 | identical: True
[('ML', 'D07'), ('SQL', 'B12'), ('Stats', 'D07')]
Step 1Three small tables, each with a key that is the left side of its FD.
Step 2Joining them back gives the same 5 rows as the original: a lossless decomposition.
Step 3The office of Iyer now lives in one row. One UPDATE changed it for both Stats and ML. In the original table you would have had to update 3 rows and could easily miss one.
COMMON MISTAKE
Splitting a table into two pieces that share no determining column, for example (student, grade) and (course, teacher). Joining them back on nothing, or on a non-key column, creates spurious rows that never existed. A decomposition is only safe when the shared columns form a key of at least one piece, which is exactly what the algorithm guarantees.
GOING DEEPER
BCNF can lose a dependency: some decompositions mean an FD can no longer be checked inside one table, which is why many designers stop at 3NF, which always preserves dependencies. 4NF goes one step further for multi-valued facts: if a person has independent sets of skills and languages, one table of (person, skill, language) must list every combination, and the fix is two tables (person, skill) and (person, language). In practice: aim for 3NF in transactional systems, check by FD closure when a design feels wrong, and denormalize deliberately (Section 11.3) only in analytics layers.

Pattern 1: soft delete without breaking uniqueness

Soft delete means marking a row deleted (deleted_at) instead of removing it, so history survives and mistakes can be undone. The trap: a normal UNIQUE (email) blocks a person who deleted their account from signing up again. A partial unique index enforces uniqueness only among live rows.

import sqlite3
db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE users (id INTEGER PRIMARY KEY, email TEXT NOT NULL, deleted_at TEXT);
CREATE UNIQUE INDEX users_email_live ON users(email) WHERE deleted_at IS NULL;
INSERT INTO users (email) VALUES ('a@x.com');
UPDATE users SET deleted_at = '2024-05-01' WHERE email = 'a@x.com';
INSERT INTO users (email) VALUES ('a@x.com');     -- allowed: the old row is soft-deleted
""")
print(db.execute("SELECT id, email, deleted_at FROM users ORDER BY id").fetchall())
try:
    db.execute("INSERT INTO users (email) VALUES ('a@x.com')")   # a second live row with the same email
except sqlite3.IntegrityError as e:
    print("blocked:", e)
print("live users:", db.execute("SELECT count(*) FROM users WHERE deleted_at IS NULL").fetchone()[0])
[(1, 'a@x.com', '2024-05-01'), (2, 'a@x.com', None)]
blocked: UNIQUE constraint failed: users.email
live users: 1
Step 1Row 1 is soft-deleted, so the live-only index ignores it, and a second row with the same email is accepted.
Step 2A third insert would create two live rows with that email, and the index rejects it.
NoteEvery query must now remember WHERE deleted_at IS NULL. Hide that behind a view (CREATE VIEW live_users AS ...), or the first forgotten filter shows deleted data. In PostgreSQL row-level security can enforce it.

Pattern 2: multi-tenant design that cannot cross tenants

In a SaaS product many customers (tenants) share tables. The worst bug is one tenant seeing another's data. Put tenant_id in every key, and make foreign keys include it, so the database itself refuses a cross-tenant reference.

import sqlite3
db = sqlite3.connect(":memory:")
db.execute("PRAGMA foreign_keys = ON")
db.executescript("""
CREATE TABLE customer (tenant_id INTEGER, customer_id INTEGER, name TEXT, PRIMARY KEY (tenant_id, customer_id));
CREATE TABLE orders (
  tenant_id INTEGER, order_id INTEGER, customer_id INTEGER,
  PRIMARY KEY (tenant_id, order_id),
  FOREIGN KEY (tenant_id, customer_id) REFERENCES customer (tenant_id, customer_id));
INSERT INTO customer VALUES (1, 10, 'Asha'), (2, 10, 'Zed');
INSERT INTO orders VALUES (1, 100, 10);     -- tenant 1 order for tenant 1 customer: fine
""")
try:
    db.execute("INSERT INTO orders VALUES (1, 101, 99)")      # tenant 1 pointing at a customer tenant 1 does not have
except sqlite3.IntegrityError as e:
    print("blocked:", e)
print(db.execute("SELECT * FROM orders").fetchall())
blocked: FOREIGN KEY constraint failed
[(1, 100, 10)]
Step 1The primary key of customer is (tenant_id, customer_id). Both tenants have a customer 10, which is fine.
Step 2The foreign key in orders is composite. A tenant-1 order can only point to a (1, customer) pair that exists, so a typo or an attack that points at tenant 2's customer is refused.
Step 3The failing insert shows the database error. Add row-level security (Section 9.6) so queries are also filtered by tenant.

Pattern 3: polymorphic references, done safely

Comments that can belong to a post or a photo are often stored as (target_type, target_id). That cannot have a foreign key, so orphans creep in. A safe design uses one nullable foreign key per parent and a CHECK that exactly one is set:

import sqlite3
db = sqlite3.connect(":memory:")
db.execute("PRAGMA foreign_keys = ON")
db.executescript("""
CREATE TABLE post (post_id INTEGER PRIMARY KEY);
CREATE TABLE photo (photo_id INTEGER PRIMARY KEY);
CREATE TABLE comment (
  comment_id INTEGER PRIMARY KEY,
  post_id  INTEGER REFERENCES post,
  photo_id INTEGER REFERENCES photo,
  body TEXT,
  CHECK ((post_id IS NOT NULL) + (photo_id IS NOT NULL) = 1)   -- exactly one parent
);
INSERT INTO post VALUES (1); INSERT INTO photo VALUES (1);
INSERT INTO comment (post_id, body) VALUES (1, 'nice post');
""")
for sql in ["INSERT INTO comment (post_id, photo_id, body) VALUES (1, 1, 'two parents')",
            "INSERT INTO comment (post_id, body) VALUES (77, 'ghost post')",
            "INSERT INTO comment (body) VALUES ('orphan')"]:
    try:
        db.execute(sql); print("accepted:", sql[:44])
    except sqlite3.IntegrityError as e:
        print("blocked :", e)
blocked : CHECK constraint failed: (post_id IS NOT NULL) + (photo_id IS NOT NULL) = 1
blocked : FOREIGN KEY constraint failed
blocked : CHECK constraint failed: (post_id IS NOT NULL) + (photo_id IS NOT NULL) = 1
Step 1Two parents set: the CHECK rejects it.
Step 2A post that does not exist: the foreign key rejects it.
Step 3No parent at all: the CHECK rejects it. The two-column design needs a new column per new parent type, but the database now guards every row.

Surrogate versus natural keys, and where this meets data engineering

A natural key comes from the real world (email, ISBN); a surrogate key is a meaningless number the database hands out. Natural keys change (people change email) and cost more to join on, so use a surrogate primary key and keep a UNIQUE constraint on the natural one, as Section 9.1 advised. For many-to-many relations the junction table's key is the pair of foreign keys. In a warehouse the same ideas reappear as layers: raw tables as loaded, staging models that rename and clean, and mart models shaped as stars. Data Vault is a warehouse modelling style that separates stable business keys (hubs), relationships (links) and changing attributes (satellites) so history is never rewritten; it suits many source systems, and costs more joins. A tool such as dbt expresses each layer as a SQL model (see the Data Engineering document).

Practice with answers

Problem 11.6.2 Given R(a, b, c) with FDs a -> b and b -> c, what is the closure of {a} and is a the key? (easy)

Answer: a determines b, b then determines c, so the closure is {a, b, c}: all columns. a is a key. The FD b -> c violates BCNF (b is not a key), but it is a transitive dependency, so it also violates 3NF.

Problem 11.6.3 Decompose R(a, b, c) from the previous problem. (medium)

Answer: Split on b -> c: R1(b, c) with key b, and R2(a, b) with key a. They share b, which is a key of R1, so the join is lossless.

Problem 11.6.4 Why does UNIQUE (email) plus soft delete cause trouble, and give two fixes. (find the bug)

Answer: A deleted row keeps its email, so the person cannot register again. Fix 1: a partial unique index where deleted_at IS NULL (PostgreSQL, SQLite). Fix 2: on deletion, rewrite the email to a unique tombstone, or move the row to an archive table. MySQL has no partial indexes, so use the second or a generated column.

Problem 11.6.5 Why should every table in a multi-tenant database include tenant_id in its primary key and foreign keys? (interview)

Answer: So the schema itself prevents cross-tenant references and makes per-tenant queries and sharding natural; a plain integer key would let a bug link tenant 1 to tenant 2's data, which is a data-leak class of defect. It costs a wider index and slightly larger keys.

Chapter recap

  • An ER diagram lists entities, attributes and relationships. The foreign key goes on the "many" side; many-to-many needs a junction table.
  • Use surrogate primary keys, sensible types and consistent snake_case names.
  • Normalization stores each fact once. 1NF: single values. 2NF: no dependency on part of a key. 3NF: no dependency on non-key columns. BCNF: every determinant is a candidate key.
  • An FD A → B can be tested with GROUP BY A HAVING COUNT(DISTINCT B) > 1.
  • A good decomposition is lossless: joining the parts returns the original rows.
  • OLTP uses normalized tables for fast safe writes; OLAP uses denormalized tables for fast big reads.
  • Denormalize only measured hot paths, and own the sync plan.
  • A star schema has one fact table (the grain) and flat dimension tables. A snowflake normalizes dimensions further. Star is the usual default.
  • SCD 1 overwrites, SCD 2 adds a row with validity dates, SCD 3 adds a column.
  • Always verify by totals: the star's SUM(revenue) must equal the source query.

Practice set

Problem 11.P.1 (easy) Where does the foreign key go: one author writes many books? Answer: On books (books.author_id), the many side.

Problem 11.P.2 (easy) Is a cell containing 'red,green,blue' in 1NF? Answer: No. Use one row per value in a child table.

Problem 11.P.3 (what is the output?) In a table t(a, b) with rows (1,'x'), (1,'y'), (2,'z'), what does SELECT a, COUNT(DISTINCT b) FROM t GROUP BY a HAVING COUNT(DISTINCT b) > 1 return? Answer: One row: a = 1, count 2. So a → b does not hold.

Problem 11.P.4 (computation) A fact table has 50 million rows. A dimension has 200 cities. A summary table by city and day for 365 days has how many rows at most, and what is the reduction? Answer: 200 × 365 = 73,000 rows. 50,000,000 / 73,000 is about 685, so the dashboard reads about 685 times fewer rows.

Problem 11.P.5 (find the bug) A table has columns (order_id, product_id, product_name, qty) with PK (order_id, product_id). Which normal form is violated and why? Answer: 2NF. product_name depends on product_id alone, only part of the key. Move it to products.

Problem 11.P.6 (find the bug) After an SCD 2 load, COUNT(*) of customers is 1,240 but the company has 1,100. What happened? Answer: Moved customers have two or more rows (one per version). Count current rows (WHERE is_current = 1) or COUNT(DISTINCT customer_id).

Problem 11.P.7 (find the bug) The SCD 2 join returns 3 rows for 2 orders. Give the likely cause. Answer: Overlapping validity periods (for example both valid_to = '2024-03-10' and an inclusive <= in the join), so an order matches two versions. Make the end exclusive and check for overlaps.

Problem 11.P.8 (scenario) Design a star schema for ride-share trips. Name the grain, one fact table, and four dimensions. Answer: Grain: one row per completed trip. Fact fact_trips (trip_id, keys, distance_km, fare, duration_min). Dimensions: dim_date (and a time-of-day dimension), dim_rider, dim_driver, dim_location (pickup, and a second role for drop-off), dim_vehicle_type.

Problem 11.P.9 (scenario) Marketing wants "revenue by customer region as it was when the order happened" but the region team often reassigns customers. What do you do? Answer: Make region an SCD 2 attribute in the customer dimension (valid dates), and join the fact by order date or store the dimension's surrogate key in the fact at load time.

Problem 11.P.10 (interview) When would you deliberately denormalize? Answer: When measurement shows a read path is hot and the join cost is real, and I have a sync plan (summary table with a refresh job, trigger, or single write path). For analytics I model a star schema. I normalize first because it prevents anomalies, then relax for evidence.

Problem 11.P.11 (interview) Explain OLTP vs OLAP and why you would not run a big report on the production OLTP database. Answer: OLTP is many short transactions needing low latency; OLAP is few heavy scans. A big report scans many rows, uses CPU, memory and I/O, and can hold resources that slow checkout. Run it on a replica or in a warehouse.
