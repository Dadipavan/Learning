A hiring manager does not read your certificates. She opens your repository and asks one question: "Can this person take a vague business question and turn it into a correct, explained answer?" This chapter shows you how to build projects that answer yes. First you learn the working method that every good project shares: plan, layout, data, commits, tests, README, post. Then you build three projects end to end: a funnel and cohort-retention analysis, an RFM customer segmentation with a written report, and a sales database designed from scratch with twenty business queries. Every query below was run in SQLite 3.50 and the output shown is the real output. By the end you will have three finished repositories and the words to talk about them in an interview.

15.1 How to Run a Project in This Area

BASIC EXPLANATION
A project is a complete piece of work that goes from a question to a result. This section gives a step-by-step method for planning, building, checking and presenting one.
INTUITION
Think of a project like cooking a meal for guests, not like doing homework. You decide the menu first (the question), buy the ingredients (the data), cook step by step tasting as you go (tests), and finally you plate it nicely and write the menu card (README). A great dish with no menu card, or a menu card with no dish, both disappoint.

Plan the question and the success criteria

Write the question as one sentence a manager would say, then write how you will know you are right. Do this before any SQL.

ItemWeak versionStrong version
Question"Analyse the shop data""Which signup channel loses the most visitors before payment, and do buyers come back?"
Success criteria"Make some queries""Funnel counts reconcile with the orders table; cohort retention matches an independent Python check; 1-page report with 3 recommendations"
Out of scope(nothing)"No forecasting, no dashboards"

Repository layout

sql-project-name/
  README.md              the front door (template below)
  data/
    generate_data.py     creates the database; fixed random seed
    (no big files; the generator rebuilds them)
  sql/
    00_schema.sql        tables, constraints, indexes
    01_checks.sql        row counts, NULLs, duplicates
    02_analysis.sql      the real queries, numbered, commented
  tests/
    test_results.py      Python asserts that cross-check the SQL
  report/
    findings.md          the written answer for a manager
  images/                charts or screenshots for the README

Environment and dependencies

SQLite ships inside Python, so python3 plus the sqlite3 command-line tool is enough for every project in this chapter. Nothing to install. If you prefer PostgreSQL, keep the SQL portable and note the few date functions that change (Chapter 14). Record your versions in the README: python3 --version and sqlite3 --version.

Data sourcing or generation

Use public data (government open-data portals, Kaggle, UCI) when the licence allows, and write the licence and source URL in the README. When no good data exists, generate it with a script and a fixed seed, so anyone gets identical numbers. Say clearly that the data is synthetic. A generator also lets you plant a known pattern (for example "social channel converts badly") and check that your SQL finds it. That is a real test.

Commit rhythm and good commit messages

Commit after every working step, at least once per session. A message says what and why in the present tense:

Good:  Add strict funnel query; count users by order of events
Good:  Fix cohort month maths: use year*12+month, not date subtraction
Weak:  update
Weak:  final final v2

A history of ten honest commits shows how you think. One giant commit shows nothing.

Definition of done

  • The question and success criteria are written in the README.
  • One command rebuilds the database; another runs the tests; both are in the README.
  • Every headline number is reproduced a second way (Python, a hand count, or a reconciliation to a total).
  • Edge cases are handled and mentioned: NULLs, ties, incomplete months, cancelled orders.
  • The report states what the data cannot tell you.
  • A stranger can follow the README without asking you anything.

Demo and deploy options

SQL has no "server" to deploy, so show the work this way. (1) A public GitHub repository with a good README and a few result tables pasted in. (2) A screenshot or a chart image from matplotlib (not run in this chapter; see Chapter 13 for the Python bridge). (3) A short screen recording or GIF walking through the findings. (4) A free hosted notebook, if you like, that runs the same SQL. Option 1 plus the report is enough.

How to write the LinkedIn or blog post

Use four short paragraphs: the question (one sentence a non-technical person understands), the surprising finding (one number), how you checked it (one sentence; this earns trust), the link. Do not paste code. Do not claim business impact you did not measure; say "on synthetic data" when it is synthetic.

Testing and debugging checklist for SQL projects

  1. Row counts: after every join, count again. A join that changes the row count unexpectedly means a duplicate key or a many-to-many.
  2. Reconcile: pieces must add up to the whole (revenue by region equals total revenue).
  3. Count people, not rows: use COUNT(DISTINCT user_id) for funnels and retention.
  4. NULL check: COUNT(*) versus COUNT(column) for every column you group or join on.
  5. Boundary dates: first and last day, and months that are only partly in the data (right-censoring).
  6. Ties: if ORDER BY has ties and you use LIMIT, add a tie-breaker column, or the answer can change run to run.
  7. Independent check: recompute one headline number in Python or by hand on a small sample.
  8. Read the plan (EXPLAIN QUERY PLAN) if a query takes more than a second.

Check yourself

  1. Why do we generate data with a fixed random seed? Answer: so everyone, including you next month, gets exactly the same numbers and the tests stay valid.
  2. Name two ways to verify a headline number. Answer: recompute it in Python, and reconcile parts to a known total.
  3. What does a commit message explain that the code cannot? Answer: why the change was made.

15.2 Project: Funnel and Cohort-Retention Analysis for an E-Commerce Shop

Goal and why employers care

Question: where do visitors drop out before paying, does it differ by signup channel, and do buyers come back in later months? Funnels tell a company where to fix the website. Retention tells it whether customers like the product after the first purchase. Almost every analyst job description for an online business contains these two words. Showing both, with checks, is a strong portfolio piece.

Skills used

  • Conditional aggregation with MIN(CASE ...): Aggregation, GROUP BY, HAVING and FILTER (Chapter 3).
  • Joins to attach channel to users: Joins (Chapter 4).
  • CTEs to build the answer in readable layers: Subqueries and CTEs (Chapter 5).
  • Dates and printf: CASE, Strings, Dates and Times, JSON and Arrays (Chapter 6).
  • The funnel and cohort patterns themselves: Analytics SQL Patterns (Chapter 12).

Data

Three tables: users (who and which channel), events (view, cart, checkout, pay with a timestamp), orders (what was paid). The generator plants a known pattern: social visitors convert badly, referral and email users buy again more. Save as data/generate_data.py.

import sqlite3, random, sys
from datetime import date, datetime, timedelta
random.seed(42)
con = sqlite3.connect(sys.argv[1])
con.executescript("""
DROP TABLE IF EXISTS users; DROP TABLE IF EXISTS events; DROP TABLE IF EXISTS orders;
CREATE TABLE users  (user_id INTEGER PRIMARY KEY, signup_date TEXT NOT NULL, channel TEXT NOT NULL);
CREATE TABLE events (event_id INTEGER PRIMARY KEY, user_id INTEGER NOT NULL, event TEXT NOT NULL, ts TEXT NOT NULL);
CREATE TABLE orders (order_id INTEGER PRIMARY KEY, user_id INTEGER NOT NULL, order_date TEXT NOT NULL, amount REAL NOT NULL);
""")
start = date(2024, 1, 1); end = date(2024, 6, 30)
channels = [("search",.4,1.0),("social",.3,.7),("email",.2,1.3),("referral",.1,1.5)]  # name, share, quality
users=[]; events=[]; orders=[]
for uid in range(1, 3001):
    d = start + timedelta(days=random.randint(0, 150))
    r = random.random(); acc=0
    for ch,share,q in channels:
        acc+=share
        if r<=acc: break
    users.append((uid, d.isoformat(), ch))
    t = datetime(d.year,d.month,d.day,random.randint(8,22),random.randint(0,59))
    events.append((None,uid,'view',t.isoformat(' ')))
    if random.random() < .60*min(q,1.2):
        t += timedelta(minutes=random.randint(1,30)); events.append((None,uid,'cart',t.isoformat(' ')))
        if random.random() < .55:
            t += timedelta(minutes=random.randint(1,15)); events.append((None,uid,'checkout',t.isoformat(' ')))
            if random.random() < .70*min(q,1.1):
                t += timedelta(minutes=random.randint(1,10)); events.append((None,uid,'pay',t.isoformat(' ')))
                orders.append((None,uid,t.date().isoformat(),round(random.lognormvariate(3.9,.5),2)))
                p = .35*q                      # chance of buying again, shrinks each month
                for m in range(1,6):
                    if random.random() < p:
                        od = t.date()+timedelta(days=30*m+random.randint(-5,5))
                        if od<=end: orders.append((None,uid,od.isoformat(),round(random.lognormvariate(3.9,.5),2)))
                    p *= .75
con.executemany("INSERT INTO users VALUES (?,?,?)", users)
con.executemany("INSERT INTO events VALUES (?,?,?,?)", events)
con.executemany("INSERT INTO orders VALUES (?,?,?,?)", orders)
con.commit()
for t in ("users","events","orders"):
    print(t, con.execute(f"select count(*) from {t}").fetchone()[0])
users 3000
events 6345
orders 1209

Step-by-step build

  1. Generate and sanity-check. Run python3 data/generate_data.py shop.db. Then check that the two tables tell the same story: every pay event should have an order.
SELECT (SELECT COUNT(*) FROM events WHERE event='pay') AS pay_events,
       (SELECT COUNT(DISTINCT user_id) FROM orders)    AS buyers;
pay_events  buyers
----------  ------
648         648
  1. Strict funnel by channel. A user counts at a step only if the earlier steps happened earlier (Chapter 12.1). Predict first: which channel do you think is worst? Then run.
WITH t AS (
 SELECT user_id,
  MIN(CASE WHEN event='view'     THEN ts END) t_view,
  MIN(CASE WHEN event='cart'     THEN ts END) t_cart,
  MIN(CASE WHEN event='checkout' THEN ts END) t_check,
  MIN(CASE WHEN event='pay'      THEN ts END) t_pay
 FROM events GROUP BY user_id),
s AS (
 SELECT u.channel, 1 AS s1,
  CASE WHEN t_cart  > t_view THEN 1 ELSE 0 END AS s2,
  CASE WHEN t_check > t_cart AND t_cart > t_view THEN 1 ELSE 0 END AS s3,
  CASE WHEN t_pay > t_check AND t_check > t_cart AND t_cart > t_view THEN 1 ELSE 0 END AS s4
 FROM t JOIN users u USING(user_id))
SELECT channel, SUM(s1) viewers, SUM(s2) carted, SUM(s3) checkout, SUM(s4) paid,
       ROUND(100.0*SUM(s2)/SUM(s1),1) view_to_cart,
       ROUND(100.0*SUM(s3)/SUM(s2),1) cart_to_check,
       ROUND(100.0*SUM(s4)/SUM(s3),1) check_to_pay,
       ROUND(100.0*SUM(s4)/SUM(s1),1) overall
FROM s GROUP BY channel;
channel   viewers  carted  checkout  paid  view_to_cart  cart_to_check  check_to_pay  overall
--------  -------  ------  --------  ----  ------------  -------------  ------------  -------
email     606      427     246       187   70.5          57.6           76.0          30.9
referral  287      209     122       93    72.8          58.4           76.2          32.4
search    1201     724     389       272   60.3          53.7           69.9          22.6
social    906      379     201       96    41.8          53.0           47.8          10.6

Adding an ALL row with the same sums gives 3000, 1739, 958, 648 and an overall 21.6%. Social loses people at two places: view to cart (41.8%, against 60 to 73 elsewhere) and checkout to pay (47.8%, against 70 to 76). That matches the planted pattern, so the query works.

  1. Cohort retention. Cohort = the month of a customer's first order. Retention at month k = share of that cohort who ordered again k months later. We turn each date into a month number year*12 + month so that "k months later" is simple subtraction.
WITH mi AS (
  SELECT user_id, order_date,
         CAST(substr(order_date,1,4) AS INTEGER)*12 + CAST(substr(order_date,6,2) AS INTEGER) AS mon
  FROM orders),
first_o AS (SELECT user_id, MIN(mon) AS first_mon FROM mi GROUP BY user_id),
last_data AS (SELECT MAX(mon) AS last_mon FROM mi),
act AS (SELECT DISTINCT m.user_id, f.first_mon, m.mon - f.first_mon AS k
        FROM mi m JOIN first_o f USING(user_id)),
sizes AS (SELECT first_mon, COUNT(*) size FROM first_o GROUP BY first_mon)
SELECT printf('%d-%02d', (s.first_mon-1)/12, (s.first_mon-1)%12+1) AS cohort,
       s.size,
       ROUND(100.0*SUM(a.k=1)/s.size,1) AS m1,
       CASE WHEN s.first_mon+2 <= (SELECT last_mon FROM last_data)
            THEN ROUND(100.0*SUM(a.k=2)/s.size,1) END AS m2,
       CASE WHEN s.first_mon+3 <= (SELECT last_mon FROM last_data)
            THEN ROUND(100.0*SUM(a.k=3)/s.size,1) END AS m3
FROM sizes s JOIN act a USING(first_mon)
GROUP BY s.first_mon ORDER BY s.first_mon;
cohort   size  m1    m2    m3
-------  ----  ----  ----  ----
2024-01  139   34.5  30.9  18.0
2024-02  124   37.1  25.8  23.4
2024-03  133   33.8  33.8  25.6
2024-04  131   33.6  32.1
2024-05  121   40.5

Read row one: 139 customers first bought in January; 34.5% (48 people) bought again in February. Blank cells are not zero. They are months the data has not reached yet (the data ends in June). Without the two CASE lines the same cells show a false 0.0.

  1. Test with an independent calculation. Save as tests/test_results.py. It recomputes retention in plain Python and asserts the SQL agrees.
import sqlite3, collections
con = sqlite3.connect("shop.db")
months = collections.defaultdict(set)
for u, d in con.execute("SELECT user_id, order_date FROM orders"):
    months[u].add(int(d[:4]) * 12 + int(d[5:7]))
cohort = collections.defaultdict(list)
for u, s in months.items():
    cohort[min(s)].append(u)
py = {c: (len(us), round(100 * sum(c + 1 in months[u] for u in us) / len(us), 1)) for c, us in cohort.items()}
rows = con.execute(open("sql/03_cohort.sql").read()).fetchall()
for label, size, m1, *_ in rows:
    y, m = map(int, label.split("-"))
    assert py[y * 12 + m] == (size, m1), label
print("all checks passed:", len(rows), "cohorts match")
all checks passed: 5 cohorts match
  1. Write the findings (see README outline). Three sentences: social converts at 10.6% against 22.6% for search; about one in three first-time buyers returns the next month, and by month three 18 to 26% still buy; the fix to test first is the social checkout page.

Evaluation and acceptance criteria

  • Funnel step counts never increase from one step to the next; ALL equals the sum of channels.
  • Distinct buyers in orders equals paid users in the funnel (648 = 648 here).
  • Cohort sizes add up to the number of buyers (139+124+133+131+121 = 648).
  • The Python test passes; unseen cohort months show blank, not zero.
  • Report names the worst channel with its number and one limit.

Common pitfalls

  1. Counting events, not users. Symptom: step 1 is bigger than the user count. Detect: compare COUNT(*) with COUNT(DISTINCT user_id).
  2. Ignoring step order. Symptom: a user who paid without carting appears in the final step. Detect: the t_cart > t_view conditions; list users who break order.
  3. False zeros at the edge of the data. Symptom: the newest cohorts show 0% retention. Detect: compare cohort month plus k with the last data month.
  4. Date maths with text. Symptom: '2024-03' - '2024-01' gives 0. Use the year*12+month number.
  5. Averaging percentages across cohorts instead of dividing summed counts. Detect: recompute from raw counts.

Three extensions

  1. Weekly cohorts and a retention heatmap with matplotlib (not run here).
  2. Time-to-convert: median minutes from view to pay per channel, using window functions (Chapter 8).
  3. Add revenue per cohort (customer lifetime value so far) and compare channels.

Interview talking points

  1. Why count users, not events, in a funnel? A person who views five times is still one person. Counting events makes step 1 too big and every conversion rate too small.
  2. What is right-censoring in a cohort table? Young cohorts have not had time to reach month 3. A blank means "not observed yet", and a zero means "observed and nobody came". Mixing them gives a false story that new customers are worse.
  3. How did you know your SQL was right? I recomputed retention in Python with plain sets and asserted that every cohort matches, and I reconciled paid events to the orders table.

README outline

Title with result; question; data (generator, 3 tables, counts); how to run (3 commands); funnel table; cohort table; 3 findings; checks (reconciliation, Python test); limits (synthetic data, no seasonality, one-month granularity); next steps.

15.3 Project: RFM Customer Segmentation in SQL with a Written Report

Goal and why employers care

Question: who are the shop's best customers, who is slipping away, and what should marketing do for each group? RFM (Recency, Frequency, Monetary value) is the oldest and most used customer segmentation: simple, explainable to a manager, and needs only an orders table. Employers like it because the real skill is the last step: turning scores into actions in a short report.

Skills used

  • GROUP BY summaries and julianday date maths: Aggregation, GROUP BY, HAVING and FILTER; CASE, Strings, Dates and Times, JSON and Arrays.
  • NTILE scoring: Window Functions in Depth (Chapter 8).
  • CASE rules to name segments: Chapter 6.
  • Percent-of-total with scalar subqueries: Subqueries and CTEs.
  • RFM overview: Analytics SQL Patterns, section on RFM.

Data

Reuse shop.db from project 15.2 (the orders table: 1,209 orders from 648 customers, 2 January to 30 June 2024). Only customers who ordered are scored. The snapshot date is 2024-07-01: recency is measured from this day, not from today, so the answer never changes.

Architecture

orders --> rfm_base (R, F, M per customer) --> rfm (scores 1-4) --> seg (named segments)
                                                              |
                                                              +--> summary table --> report/findings.md

Step-by-step build

  1. Compute raw R, F, M and look at the ranges first. Never score blindly.
CREATE TEMP VIEW rfm_base AS
SELECT user_id,
       CAST(julianday('2024-07-01') - julianday(MAX(order_date)) AS INTEGER) AS recency_days,
       COUNT(*) AS frequency,
       ROUND(SUM(amount),2) AS monetary
FROM orders GROUP BY user_id;

SELECT COUNT(*) customers, MIN(recency_days) min_r, MAX(recency_days) max_r,
       MIN(frequency) min_f, MAX(frequency) max_f, MIN(monetary) min_m, MAX(monetary) max_m FROM rfm_base;
customers  min_r  max_r  min_f  max_f  min_m  max_m
---------  -----  -----  -----  -----  -----  ------
648        1      181    1      5      16.08  345.52

Frequency only runs from 1 to 5. Quartiles on frequency would be mostly ties, so we use fixed business bins for F (1, 2, 3, 4 or more orders) and NTILE(4) for R and M.

  1. Score 1 to 4, where 4 is best. For recency, a smaller number of days is better, so we sort descending: the oldest customers get score 1.
CREATE TEMP TABLE rfm AS
WITH sc AS (
 SELECT *,
  NTILE(4) OVER (ORDER BY recency_days DESC) AS r_score,
  NTILE(4) OVER (ORDER BY monetary)          AS m_score
 FROM rfm_base)
SELECT user_id, recency_days, frequency, monetary, r_score,
  CASE WHEN frequency=1 THEN 1 WHEN frequency=2 THEN 2 WHEN frequency=3 THEN 3 ELSE 4 END AS f_score,
  m_score
FROM sc;

SELECT r_score, COUNT(*) n, MIN(recency_days) mn, MAX(recency_days) mx FROM rfm GROUP BY 1 ORDER BY 1;
SELECT f_score, COUNT(*) n FROM rfm GROUP BY 1 ORDER BY 1;
r_score  n    mn   mx
-------  ---  ---  ---
1        162  100  181
2        162  58   98
3        162  31   58
4        162  1    31

f_score  n
-------  ---
1        238
2        285
3        103
4        22

Check: 4 groups of 162 = 648. Notice that 58 days appears in both score 2 and score 3. NTILE splits equal values arbitrarily at a boundary. This is a real property you must write in the report.

  1. Name the segments with rules a manager can read. Order of the WHEN lines matters: the first match wins.
CREATE TEMP TABLE seg AS
SELECT *, CASE
  WHEN r_score>=3 AND f_score>=3 THEN 'Champions'
  WHEN f_score>=3 THEN 'Loyal but fading'
  WHEN r_score>=3 AND f_score=2 THEN 'Potential loyalists'
  WHEN r_score>=3 AND m_score>=3 THEN 'Big new spenders'
  WHEN r_score>=3 THEN 'New / small'
  WHEN m_score>=3 THEN 'At risk (big spenders)'
  ELSE 'Hibernating' END AS segment
FROM rfm;

SELECT segment, COUNT(*) customers, ROUND(100.0*COUNT(*)/(SELECT COUNT(*) FROM seg),1) pct_cust,
  ROUND(SUM(monetary)) revenue, ROUND(100.0*SUM(monetary)/(SELECT SUM(monetary) FROM seg),1) pct_rev,
  ROUND(AVG(recency_days)) avg_r, ROUND(AVG(frequency),1) avg_f
FROM seg GROUP BY segment ORDER BY revenue DESC;
segment                 customers  pct_cust  revenue  pct_rev  avg_r  avg_f
----------------------  ---------  --------  -------  -------  -----  -----
Potential loyalists     169        26.1      18073.0  27.6     27.0   2.0
Champions               92         14.2      15919.0  24.3     25.0   3.3
At risk (big spenders)  94         14.5      12472.0  19.0     102.0  1.9
Hibernating             197        30.4      10239.0  15.6     111.0  1.2
Loyal but fading        33         5.1       5181.0   7.9      81.0   3.1
New / small             54         8.3       2658.0   4.1      45.0   1.0

  1. Reconcile. Segments must cover every customer and every rupee: SELECT SUM(monetary) FROM seg returns 65574.04 and SELECT ROUND(SUM(amount),2) FROM orders returns 65574.04. Customers add up too: 169+92+94+197+33+54+9 = 648.
  1. Write the report (below). Keep it to one page: headline, table, three actions, limits.
# Findings: customer segments (snapshot 1 July 2024, 648 customers)
Headline: 19.3% of customers (Champions plus Loyal but fading) bring 32.2% of revenue;
the 94 "At risk" big spenders hold 19.0% of revenue and have been silent ~100 days.
Actions: (1) Champions: early access, no discounts. (2) At risk: personal win-back
offer within 2 weeks. (3) Potential loyalists (2 orders, recent): nudge a third order.
Limits: synthetic data; scores are relative to this population; ties at quartile edges.

Check the two headline numbers: (92+33)/648 = 19.3%; (15919+5181)/65574 = 32.2%. Both match the table.

Evaluation and acceptance criteria

  • Every customer has exactly one segment (COUNT(DISTINCT user_id) = COUNT(*) = 648).
  • Segment revenue sums to total revenue to the paisa.
  • Score groups are near equal size (162 each) for R and M.
  • Segment names are mutually exclusive by construction (first-match CASE).
  • The report has at least three actions, each tied to a number in the table.

Common pitfalls

  1. Recency direction reversed. Symptom: "Champions" have the longest silence. Detect: check avg_r per segment; Champions must have a small number.
  2. Using today's date. Symptom: results change every day. Fix: a fixed snapshot date in the README.
  3. Ties at quartile edges. Symptom: reversing ORDER BY moves a few customers between segments (when I first wrote this with ascending order, Champions were 90, not 92). Detect: print MIN and MAX per score; accept small movement and say so.
  4. CASE order mistakes. A broad rule above a narrow one hides the narrow segment. Detect: count per segment; a segment with 0 is suspicious.
  5. Including cancelled or refunded orders in M. Decide the rule and write it down.

Three extensions

  1. Compare 3-bin and 5-bin scoring and measure how many customers change segment.
  2. Join with the funnel's channel to see which channel produces Champions.
  3. Add a 90-day "customer lifetime value so far" and rank segments by it.

Interview talking points

  1. What is RFM? Three numbers per customer: how recently they bought, how often, how much in total. Score each from 1 to 4, then name groups such as Champions.
  2. Why a fixed snapshot date? So the report can be rebuilt and checked later with the same answer. With today's date every number moves daily.
  3. When does RFM fail? When purchases are rare (cars, mattresses), when the data is short, or when F is mostly 1. Then use fewer bins or another method, such as the clustering in the machine-learning study documents.

README outline

Title; question; snapshot date and order rules; how to run; score definitions with ranges; segment rules table; summary table; one-page report; checks; limits; extensions.

15.4 Project: Design a Sales Database from Scratch, with 20 Business Queries

Goal and why employers care

Question: can you design tables that protect the data, fill them, and answer the business? Most tutorials start with a ready database. Employers want to see you build one: keys, constraints, seed data, indexes, and then queries that reconcile. This shows the whole chain from design to insight.

Skills used

  • Primary keys, foreign keys, CHECK, UNIQUE, NOT NULL: DDL, DML, Constraints, Upserts and Transactions (Chapter 9) and Databases and the Relational Model (Chapter 1).
  • Normalization and many-to-many tables: Schema Design, Normalization and Data Warehouse Modeling (Chapter 11).
  • Joins, self join, anti-join: Joins. Aggregates: Chapter 3. Windows: Window Functions in Depth.
  • Indexes on foreign keys: Indexes, EXPLAIN and Query Optimization.

Data

You write the schema, and a Python script seeds it with a fixed seed: 4 regions, 9 employees (one manager, eight reps), 60 customers, 4 categories, 24 products, 240 orders, 606 order lines.

Architecture

regions <--- employees (manager_id points back to employees)
   ^             ^
   |             |
customers <--- orders ---> order_items ---> products ---> categories

One order has many items; one product appears in many orders. order_items is the bridge table for that many-to-many link, and its primary key is the pair (order_id, product_id).

Step-by-step build

  1. Write the schema (sql/00_schema.sql). Each constraint is a business rule the database enforces for you.
PRAGMA foreign_keys = ON;
CREATE TABLE regions (region_id INTEGER PRIMARY KEY, region_name TEXT NOT NULL UNIQUE);
CREATE TABLE employees (
  employee_id INTEGER PRIMARY KEY, full_name TEXT NOT NULL,
  region_id   INTEGER NOT NULL REFERENCES regions(region_id),
  manager_id  INTEGER REFERENCES employees(employee_id),
  hired_on    TEXT NOT NULL);
CREATE TABLE customers (
  customer_id INTEGER PRIMARY KEY, full_name TEXT NOT NULL,
  email  TEXT NOT NULL UNIQUE CHECK (email LIKE '%_@_%'),
  region_id INTEGER NOT NULL REFERENCES regions(region_id), joined_on TEXT NOT NULL);
CREATE TABLE categories (category_id INTEGER PRIMARY KEY, category_name TEXT NOT NULL UNIQUE);
CREATE TABLE products (
  product_id INTEGER PRIMARY KEY, sku TEXT NOT NULL UNIQUE, name TEXT NOT NULL,
  category_id INTEGER NOT NULL REFERENCES categories(category_id),
  unit_price REAL NOT NULL CHECK (unit_price > 0),
  unit_cost  REAL NOT NULL CHECK (unit_cost >= 0),
  CHECK (unit_cost <= unit_price));
CREATE TABLE orders (
  order_id INTEGER PRIMARY KEY,
  customer_id INTEGER NOT NULL REFERENCES customers(customer_id),
  employee_id INTEGER NOT NULL REFERENCES employees(employee_id),
  order_date TEXT NOT NULL,
  status TEXT NOT NULL CHECK (status IN ('paid','shipped','cancelled','refunded')));
CREATE TABLE order_items (
  order_id   INTEGER NOT NULL REFERENCES orders(order_id) ON DELETE CASCADE,
  product_id INTEGER NOT NULL REFERENCES products(product_id),
  quantity   INTEGER NOT NULL CHECK (quantity > 0),
  unit_price REAL NOT NULL CHECK (unit_price > 0),
  PRIMARY KEY (order_id, product_id));
CREATE INDEX ix_orders_customer ON orders(customer_id);
CREATE INDEX ix_orders_date     ON orders(order_date);
CREATE INDEX ix_items_product   ON order_items(product_id);

Evaluation and acceptance criteria

  • All 5 bad inserts fail with a constraint error; PRAGMA foreign_key_check; returns no rows.
  • Row counts equal the seed script's counts.
  • Revenue by category equals revenue by region equals total revenue.
  • Every table has a primary key; every relationship has a foreign key and an index on the child column.
  • All 20 queries run and each has a comment with the business question.

Common pitfalls

  1. Foreign keys silently off (SQLite). Detect: try the bad insert; if it succeeds, the pragma is missing.
  2. Join fan-out. Joining orders to order_items before summing an order-level amount counts the amount once per item. Detect: reconcile to a known total.
  3. Storing computed totals in orders, which later disagree with the lines. Compute them in queries or views.
  4. Using the current price instead of the price at sale time. Detect: change a product price, rerun Q3; the total must not change.
  5. Ties under LIMIT. Q6 uses ORDER BY units DESC, p.product_id so the answer is stable.

Three extensions

  1. Add a payments table (one order, many partial payments) and a view v_order_revenue.
  2. Write a migration script that adds a discount column and backfills it inside a transaction (Chapter 9).
  3. Add an audit_log table filled by a trigger when an order status changes.

Interview talking points

  1. Why a bridge table? One order holds many products and one product appears in many orders. Putting both ids in one table with a combined key removes repeated data and keeps each fact once.
  2. Why constraints if the app already validates? Apps have bugs and other apps write to the same database. The database is the last guard, and it never forgets.
  3. How do you know your 20 queries are right? Two different splits of revenue reconcile to the same total, row counts match the seed script, and I tested one query by hand on three orders.

15.5 Worked Extension: Compare Channels, Catch a Fan-Out and Test the Gap

BASIC EXPLANATION
This worked extension compares results between channels, checks a query for a fan-out error, and tests whether a difference is real. It is used to confirm that the numbers in a project can be trusted.
INTUITION
A project is not finished when the queries run. It is finished when someone can trust the numbers and act on them. This walkthrough takes the funnel database from Section 15.2 (3,000 users, 6,345 events, 1,209 orders, built by its generator with seed 42) and does the three things a reviewer will ask: compare segments, check that totals reconcile, and say whether a gap is real. The SQL output below was produced by running the generator and these queries on SQLite 3.50.4.

Step 1: conversion by channel

COMMON MISTAKE
Joining two tables that both have many rows per key (orders and events per user) and then summing. The rule: aggregate each side to one row per key first, then join, or do not join at all if you do not need the column. Detect it every time with the reconciliation habit: compare count(*) after the join with the count before, and compare the grand total with a query that has no joins.
SELECT u.channel, round(sum(o.amount), 1) AS revenue, count(*) AS orders
FROM orders o JOIN users u ON u.user_id = o.user_id
GROUP BY u.channel
UNION ALL
SELECT 'TOTAL', round(sum(amount), 1), count(*) FROM orders;

referral  10904.0  204
search    26060.4  478
social    7811.1   146

The final TOTAL row is the reconciliation built into the output. A reviewer who sees a total that equals the independent figure of 65,574.0 trusts the table.

Step 3: is the social gap real or noise?

Social converts 10.6 percent and search 22.6. With 906 and 1,201 users, could that gap be luck? The standard check is a two-proportion z-test (the Statistics document, Chapter 6, explains it fully). The code below computes it by hand:

Problem 15.5.3 Test social against search and give an interval for the gap. Predict first: a gap of 12 points on groups of about a thousand is far outside random wobble.

import math
# social: 96 buyers of 906 users.  search: 272 buyers of 1201 users.
x1, n1, x2, n2 = 96, 906, 272, 1201
p1, p2 = x1 / n1, x2 / n2
pool = (x1 + x2) / (n1 + n2)
se = math.sqrt(pool * (1 - pool) * (1 / n1 + 1 / n2))
z = (p2 - p1) / se
print("social %.1f%%  search %.1f%%  gap %.1f points" % (100 * p1, 100 * p2, 100 * (p2 - p1)))
print("z = %.1f" % z)
se_gap = math.sqrt(p1 * (1 - p1) / n1 + p2 * (1 - p2) / n2)
lo, hi = (p2 - p1) - 1.96 * se_gap, (p2 - p1) + 1.96 * se_gap
print("95%% interval for the gap: %.1f to %.1f points" % (100 * lo, 100 * hi))
social 10.6%  search 22.6%  gap 12.1 points
z = 7.2
95% interval for the gap: 9.0 to 15.2 points
Step 1Pool the two groups: (96 + 272) / (906 + 1201) = 17.5 percent buyers overall. Under 'no difference' both channels share that rate.
Step 2The standard error of the gap under that assumption combines both group sizes. The z score is the gap divided by it.
Step 3A z of about 7.2 is enormous (anything beyond 2 or 3 is already unlikely by chance). The 95 percent interval for the gap runs from about 9.0 to 15.2 points and excludes zero.
AnswerThe gap is real. Write it as: 'social converts 10.6 percent (96 of 906) versus 22.6 percent for search (272 of 1,201); the gap of 12.1 points has a 95 percent interval of 9.0 to 15.2 points.'
GOING DEEPER
Significance says the gap is not luck. It does not say why. Social users may be browsing from phones, or arriving from a different campaign, or just less intent. The data cannot separate those; only a test or a better variable can. Say so in the report, in the limits paragraph. Also note the multiple-comparison issue: if you test every pair of channels and every segment, some gaps will pass by chance. Decide the comparisons before you look.

Practice with answers

Problem 15.5.4 Referral has 287 users and 93 buyers. Compute its conversion and say how many users you would need in each of social and referral to compare them with confidence. (easy)

Answer: 93 / 287 = 32.4 percent. The group sizes here (906 and 287) are already large enough, because the gap is more than 20 points. Small gaps need more users, big gaps need fewer.

Problem 15.5.5 A revenue table by channel adds to 262,296.2 but finance says 65,574.04. First check? (find the bug)

Answer: Compare row counts: count(*) of the final joined result with count(*) of orders. A ratio of 4 points to a join with events. Remove the join or aggregate events to one row per user first.

Problem 15.5.6 Why is 'average revenue per user' by channel computed with a LEFT JOIN from users, and what changes with an inner join? (medium)

Answer: A LEFT JOIN from users keeps non-buyers, so the denominator is every user, and the average is revenue per visitor. An inner join drops non-buyers, so the denominator is buyers only and the figure is revenue per buyer, much higher, and not comparable across channels with different conversion.
