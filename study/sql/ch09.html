Up to now you only read data. A real job also needs you to create tables, load rows, fix wrong values, and do all of it while other people and programs use the same database. One careless DELETE without a WHERE, or one bank-style transfer that stops half way, can cost a company real money. In this chapter you learn the commands that define and change data, the rules (constraints) that stop bad data from entering, and the transaction system that makes a group of changes all-or-nothing. By the end you can build a safe table, load and correct data, write an upsert, and explain ACID, isolation levels, locks and deadlocks in an interview.

All examples run in SQLite 3.51 unless I say not run here. SQLite is a little different from PostgreSQL in places (I will point these out), but the ideas are identical. We reuse the shop database from Chapter 2, plus a few small tables.

9.1 DDL: CREATE, ALTER, DROP, Data Types and Constraints

BASIC EXPLANATION
DDL (data definition language) statements define the structure of a database. CREATE, ALTER and DROP make, change and remove objects such as tables, using data types and constraints.
INTUITION
Think of building a school register. Before any student is written down, you print the form: columns for name, roll number, marks, and rules such as "roll number must be unique" and "marks must be 0 to 100." DDL (Data Definition Language) is the set of commands that prints the form. Constraints are the rules printed on it. The database then refuses any entry that breaks a rule, even if your Python code has a bug.

Words you need

  • DDL: commands that define structure (CREATE, ALTER, DROP). DML: commands that change rows (INSERT, UPDATE, DELETE).
  • Constraint: a rule the database checks on every change. Primary key: unique, never NULL, identifies a row. Foreign key: must match a primary key in another table (Chapter 1).

The constraints

ConstraintRule it enforcesExample
NOT NULLvalue must existemail TEXT NOT NULL
UNIQUEno two rows share the valueemail TEXT UNIQUE
PRIMARY KEYunique + not null, identifies the rowrating_id INTEGER PRIMARY KEY
FOREIGN KEYvalue must exist in the parent tableREFERENCES customers(customer_id)
CHECKany true/false test on the rowCHECK (score BETWEEN 1 AND 5)
DEFAULTvalue used when you give nonestatus TEXT DEFAULT 'new'

Data types matter too. Common PostgreSQL types: INTEGER, BIGINT, NUMERIC(10,2) for exact money, TEXT, BOOLEAN, DATE, TIMESTAMPTZ (time with time zone), JSONB. Use NUMERIC for money, never floating point, because 0.1 + 0.2 is not exactly 0.3 in floating point. SQLite is loosely typed: it has only a few storage classes (INTEGER, REAL, TEXT, BLOB), and by default it lets you store the wrong type, as you will see below.

Real-world mapping

Worked examples

Problem 9.1.1 Create a ratings table where score must be 1 to 5, email must exist and be unique, and status defaults to 'new'. Insert one valid row. Predict first: the SELECT shows the default in status.

CREATE TABLE ratings (
  rating_id INTEGER PRIMARY KEY,
  email     TEXT NOT NULL UNIQUE,
  score     INTEGER NOT NULL CHECK (score BETWEEN 1 AND 5),
  status    TEXT NOT NULL DEFAULT 'new'
);
INSERT INTO ratings (email, score) VALUES ('a@x.com', 4);
SELECT * FROM ratings;
rating_id  email    score  status
---------  -------  -----  ------
1          a@x.com  4      new
  • Answer One row. rating_id was auto-filled (SQLite) and status came from the DEFAULT, because we did not name it.

Now break each rule on purpose. Run these one at a time and read each error.

INSERT INTO ratings (email, score) VALUES ('a@x.com', 3);   -- same email
INSERT INTO ratings (email, score) VALUES ('b@x.com', 9);   -- score out of range
INSERT INTO ratings (email, score) VALUES (NULL, 3);        -- missing email
Error: stepping, UNIQUE constraint failed: ratings.email (19)
Error: stepping, CHECK constraint failed: score BETWEEN 1 AND 5 (19)
Error: stepping, NOT NULL constraint failed: ratings.email (19)
  • Answer All three were rejected by the database, not by application code, and the table still has one row.

Problem 9.1.2 Change a table later with ALTER TABLE: ALTER TABLE ratings ADD COLUMN note TEXT; adds a column (old rows get NULL), ALTER TABLE ratings RENAME COLUMN note TO comment; renames it, and DROP TABLE IF EXISTS s2; removes a table without an error when it is missing. Run PRAGMA table_info(ratings); to list columns (in PostgreSQL use \d ratings in psql). Plain DROP TABLE s2; on a missing table gives Error: in prepare, no such table: s2.

Foreign keys and ON DELETE

A foreign key says "this value must exist in the parent." What should happen when the parent row is deleted? You choose.

OptionMeaning
ON DELETE RESTRICT (or no action)refuse to delete the parent if children exist (the default behaviour)
ON DELETE CASCADEdelete the children too
ON DELETE SET NULLkeep children, set their FK to NULL

Problem 9.1.3 Show the difference between a delete that is refused and one that cascades. First, in the shop database, try to delete customer 1, who has orders:

PRAGMA foreign_keys = ON;
DELETE FROM customers WHERE customer_id = 1;
Error: stepping, FOREIGN KEY constraint failed (19)

Now a cascading design with shopping carts and their items:

PRAGMA foreign_keys = ON;
CREATE TABLE carts (cart_id INTEGER PRIMARY KEY, name TEXT NOT NULL);
CREATE TABLE cart_items (
  item_id INTEGER PRIMARY KEY,
  cart_id INTEGER NOT NULL REFERENCES carts(cart_id) ON DELETE CASCADE,
  price INTEGER CHECK (price >= 0)
);
INSERT INTO carts VALUES (1,'birthday'),(2,'groceries');
INSERT INTO cart_items(cart_id,price) VALUES (1,120),(1,340),(2,95);
DELETE FROM carts WHERE cart_id = 1;
SELECT * FROM cart_items;
item_id  cart_id  price
-------  -------  -----
3        2        95
  • Step 1 Deleting cart 1 removed its two items automatically.
  • Step 2 Cart 2 and its item stayed.
  • Answer The restrict rule protected customer 1; the cascade rule cleaned up cart 1.
COMMON MISTAKE
In SQLite, foreign keys are off by default for each new connection. I ran the same cascade script in a new session without PRAGMA foreign_keys = ON, but deleted cart 2 (the groceries cart). The check SELECT count(*) FROM cart_items returned 3: nothing cascaded, and the item of the deleted cart survived as an orphan row. PostgreSQL, MySQL (InnoDB) and SQL Server enforce foreign keys always. In SQLite, put the PRAGMA at the top of every script.
COMMON MISTAKE
Trusting SQLite types. In a plain SQLite table CREATE TABLE s(n INTEGER); INSERT INTO s VALUES('abc'); succeeds, and typeof(n) says text. SQLite is "flexibly typed." Adding the keyword STRICT at the end of CREATE TABLE makes it refuse: cannot store TEXT value in INTEGER column s2.n. PostgreSQL always refuses. Do not build habits on the lenient behaviour.

Connection to the real job

A data engineer designs tables with constraints so pipelines cannot load garbage. An analyst reads constraint names to learn which columns can be trusted: if email is UNIQUE NOT NULL, you can join on it without fear of duplicates. In ML, a clean constrained feature table saves days of debugging.

Applications

  • Data Engineering: UNIQUE keys make nightly loads safe to repeat; Analytics: a NOT NULL UNIQUE column is safe to join on.

Check yourself

  1. Which constraint stops two customers from having the same email?

Answer: UNIQUE on the email column.

  1. What does ON DELETE CASCADE do?

Answer: When the parent row is deleted, the child rows pointing to it are deleted too.

  1. Why should money be NUMERIC and not floating point?

Answer: Floating point cannot store values like 0.1 exactly, so sums drift; NUMERIC is exact.

9.2 DML: INSERT, UPDATE, DELETE, Upserts, Views and Friends

BASIC EXPLANATION
DML (data manipulation language) statements change data. INSERT adds rows, UPDATE changes rows, DELETE removes rows, an upsert inserts or updates, and a view is a saved query.
INTUITION
Imagine a shared Google Sheet used by a team. You add rows, fix wrong cells, delete old rows. The risky moment is when you fix "all rows where..." and the filter is wrong. DML is the same, but the sheet has a million rows and no undo button, except the one you build yourself (transactions, section 9.3).

Words you need

  • Upsert: "update + insert": update the row if it exists, insert it if not. Conflict: an insert that would break a UNIQUE or primary-key rule.
  • View: a saved query used like a table (no data of its own). Temp table: disappears when your session ends.

INSERT, UPDATE, DELETE

INSERT INTO table (col1, col2) VALUES (v1, v2), (v3, v4);
UPDATE table SET col = expression WHERE condition;
DELETE FROM table WHERE condition;

Always name the columns in INSERT. If someone later adds a column, an unnamed INSERT breaks or fills the wrong column. And always write the WHERE first, then the rest.

Problem 9.2.1 The prices of the Home products rise by 50. Update and show the result. Predict: Desk Lamp 900 becomes 950, Mug 250 becomes 300.

UPDATE products SET price = price + 50 WHERE category = 'Home';
SELECT product_id, name, price FROM products WHERE category = 'Home';
product_id  name       price
----------  ---------  -----
5           Desk Lamp  950  
6           Mug        300
  • Step 1 WHERE category = 'Home' selects products 5 and 6 only.
  • Step 2 price = price + 50 reads the old price on the right and writes the new price on the left.
  • Check 900 + 50 = 950 and 250 + 50 = 300.
  • Answer Two rows changed, and no other row was touched.

INSERT ... RETURNING product_id, name; (SQLite 3.35+, PostgreSQL) gives back the new row in one step, avoiding a race with other sessions.

PROFESSOR'S NOTE
Before any risky UPDATE or DELETE, run the same WHERE as a SELECT COUNT(*) first. If you expect 2 rows and the count says 2,000,000, you just avoided a disaster. Better still, run it inside a transaction (section 9.3) and look before you commit.
COMMON MISTAKE
DELETE FROM customers; with no WHERE removes every row. UPDATE products SET price = 0; sets every price to zero. The database does not ask "are you sure?". Use a transaction, or a SELECT first.

TRUNCATE, COPY and bulk loading

TRUNCATE TABLE t; empties a table fast (PostgreSQL, MySQL, SQL Server; not run here; SQLite uses DELETE FROM t;). COPY t FROM 'file.csv' WITH (FORMAT csv, HEADER); bulk-loads a CSV into PostgreSQL (not run here; \copy in psql; SQLite: .mode csv then .import). Loading a million rows with one autocommitted INSERT each is slow because every commit waits for the disk: batch them in one transaction or use COPY.

Upsert: INSERT ... ON CONFLICT

The problem. A nightly job loads stock counts. Some products are already in the table, some are new. If you just INSERT, existing ones fail with a duplicate-key error. If you check first (SELECT), then insert, two jobs can both see "not there" and both insert. An upsert does the whole thing in one safe statement.

CREATE TABLE stock (product_id INTEGER PRIMARY KEY, qty INTEGER NOT NULL);
INSERT INTO stock VALUES (1,10),(2,20);

-- product 1 exists: add to quantity
INSERT INTO stock VALUES (1,5)
  ON CONFLICT (product_id) DO UPDATE SET qty = qty + excluded.qty;
-- product 3 is new: plain insert
INSERT INTO stock VALUES (3,7)
  ON CONFLICT (product_id) DO UPDATE SET qty = qty + excluded.qty;
-- product 2 exists, ignore the new value
INSERT INTO stock VALUES (2,99)
  ON CONFLICT (product_id) DO NOTHING;
SELECT * FROM stock;
product_id  qty
----------  ---
1           15 
2           20 
3           7
  • Step 1 The first statement conflicts on product_id = 1. DO UPDATE runs. excluded is a special name for "the row I tried to insert," so excluded.qty is 5, and qty is the existing 10. Result 10 + 5 = 15.
  • Step 2 Product 3 has no conflict. It is inserted as 7.
  • Step 3 Product 2 conflicts, but DO NOTHING skips the new row. Qty stays 20.
  • Check 15, 20, 7 matches the output.
  • Answer One statement handled update, insert and ignore, atomically.

The same syntax works in PostgreSQL. MERGE is the SQL-standard alternative (PostgreSQL 15+, SQL Server, Oracle). Not run here. In MySQL the equivalent is INSERT ... ON DUPLICATE KEY UPDATE.

COMMON MISTAKE
Using INSERT OR REPLACE (SQLite) or REPLACE INTO (MySQL) as an upsert. It deletes the old row and inserts a new one, so other columns you did not mention are reset to defaults. I ran INSERT OR REPLACE INTO stock VALUES (1,1); after the script above and product 1 went from 15 to 1: the whole row was replaced. Prefer ON CONFLICT ... DO UPDATE, which changes only the columns you name.

Views, temp tables and identity columns

Views give a name to a query so everyone uses the same definition of "revenue."

CREATE VIEW paid_revenue AS
SELECT o.order_id, SUM(i.qty * i.unit_price) AS total
FROM orders o JOIN order_items i USING (order_id)
WHERE o.status = 'paid'
GROUP BY o.order_id;

SELECT * FROM paid_revenue LIMIT 3;
order_id  total
--------  -----
101       1660 
102       600  
103       1020

Check by hand: order 101 has 1 keyboard at 1500 plus 2 notebooks at 80, so 1500 + 160 = 1660. Order 103: 900 + 120 = 1020.

Temp tables (CREATE TEMP TABLE big AS SELECT ...) hold intermediate results for your session only. Identity: PostgreSQL uses id BIGINT GENERATED ALWAYS AS IDENTITY (not run here); SQLite's INTEGER PRIMARY KEY auto-numbers, and ids are never guaranteed gap-free (I deleted id 2 from a 2-row table and the next insert got id 3 with AUTOINCREMENT). Awareness, not run here: CREATE MATERIALIZED VIEW plus REFRESH MATERIALIZED VIEW stores a heavy query's result; triggers and stored procedures hide logic in the database, so use them rarely.

Surrogate vs natural keys

A natural key is real-world data (an email) and can change. A surrogate key is a meaningless id the database makes (customer_id). Practice: surrogate primary key, plus UNIQUE on the natural key.

Connection to the real job

Upserts are in every incremental data pipeline: "load today's changes into the table without duplicating yesterday's." Views are how analytics teams share one definition of a metric. COPY and bulk loads are how data engineers fill warehouses.

Applications

  • Data Engineering: idempotent loads with ON CONFLICT; Analytics: shared views so dashboards agree; ML: temp tables to build a training set.

Check yourself

  1. What does excluded.qty mean inside ON CONFLICT DO UPDATE?

Answer: The value from the row that you tried to insert.

  1. Why is INSERT OR REPLACE dangerous as an upsert?

Answer: It deletes the whole old row and inserts a new one, so unmentioned columns are lost.

  1. What is the first thing to do before a risky DELETE?

Answer: Run the same WHERE in a SELECT COUNT(*), and ideally work inside a transaction.

9.3 Transactions and ACID

BASIC EXPLANATION
A transaction is a group of statements that are saved together or not at all. ACID stands for atomicity, consistency, isolation and durability, the four properties that make transactions reliable.
INTUITION
You move Rs 300 from Asha to Ravi. That is two steps: subtract from Asha, add to Ravi. If the power fails between the steps, Rs 300 vanishes. A transaction wraps both steps in one box that either happens fully or not at all. Think of a bank counter: deposit, stamp and receipt are many small actions but one business step with one result.

Words you need

  • Transaction: a group of statements treated as one unit.
  • COMMIT: make all the changes permanent.
  • ROLLBACK: undo all the changes since BEGIN.
  • Savepoint: a bookmark inside a transaction you can roll back to.
  • Autocommit: the default mode in which each single statement is its own transaction.

ACID

LetterNamePlain meaningIf it were missing
AAtomicityall steps happen, or nonehalf a transfer
CConsistencyrules (constraints) hold before and afternegative balances
IIsolationconcurrent transactions do not see each other's half-done workwrong totals in reports
DDurabilityonce committed, it survives a crashlost orders after power cut

Durability is usually done with a write-ahead log (WAL): the database writes the change to a log file on disk first, and updates the table files later. After a crash it replays the log.

Problem 9.3.1 Transfer Rs 300 from Asha (id 1) to Ravi (id 2), first rolled back, then committed.

CREATE TABLE accounts (
  id INTEGER PRIMARY KEY, owner TEXT,
  balance INTEGER NOT NULL CHECK (balance >= 0));
INSERT INTO accounts VALUES (1,'Asha',1000),(2,'Ravi',500);

BEGIN;
UPDATE accounts SET balance = balance - 300 WHERE id = 1;
UPDATE accounts SET balance = balance + 300 WHERE id = 2;
SELECT * FROM accounts;
ROLLBACK;
SELECT * FROM accounts;

BEGIN;
UPDATE accounts SET balance = balance - 300 WHERE id = 1;
UPDATE accounts SET balance = balance + 300 WHERE id = 2;
COMMIT;
SELECT * FROM accounts;
id  owner  balance
--  -----  -------
1   Asha   700    
2   Ravi   800    
id  owner  balance
--  -----  -------
1   Asha   1000   
2   Ravi   500    
id  owner  balance
--  -----  -------
1   Asha   700    
2   Ravi   800
  • Step 1 Inside the first transaction we see the new balances (700 and 800). This is our own view.
  • Step 2 ROLLBACK undoes both updates: 1000 and 500 again.
  • Step 3 The second run ends in COMMIT, so 700 and 800 become permanent.
  • Check 700 + 800 = 1500 = 1000 + 500. Money is conserved.
  • Answer Both steps happen together or not at all.

Problem 9.3.2 (find the bug) A script runs a transfer that should fail: Asha has only 700 but we try to move 5,000. We add 500 to Ravi first, then subtract 5,000 from Asha. The CHECK (balance >= 0) will reject the second step. Predict the final balances if the script continues after the error.

BEGIN;
UPDATE accounts SET balance = balance + 500 WHERE id = 2;
UPDATE accounts SET balance = balance - 5000 WHERE id = 1;
COMMIT;
SELECT * FROM accounts;
Runtime error near line 5: CHECK constraint failed: balance >= 0 (19)
id  owner  balance
--  -----  -------
1   Asha   700    
2   Ravi   1300
  • Step 1 The first UPDATE worked: Ravi 800 to 1300.
  • Step 2 The second UPDATE failed. Only that one statement was undone, not the transaction.
  • Step 3 The sqlite3 shell continued and ran COMMIT, which saved the half-done work.
  • Answer Ravi gained 500 from nowhere. Total money rose from 1500 to 2000.
  • Fix Your program must check for an error and issue ROLLBACK itself. In Python: try: ... conn.commit() except: conn.rollback(). In PostgreSQL an error inside a transaction puts the whole transaction in an "aborted" state, and COMMIT then behaves as a rollback. That is safer, but still handle errors in code.
COMMON MISTAKE
Assuming "an error cancels the whole transaction." Behaviour depends on the database and the shell. Always handle the error and roll back explicitly.

Savepoints (SAVEPOINT s1; ... ROLLBACK TO s1;) undo only part of a transaction. I ran a +1 update, a savepoint, a +100 update, ROLLBACK TO s1, then COMMIT: Ravi went from 1300 to 1301 only.

Connection to the real job

Every payment, order and booking system relies on atomic transactions. In data engineering, a pipeline loads a day of data in one transaction so dashboards never see half a day. Keep transactions short: a long open transaction holds locks and blocks others (section 9.4). It is the same as one slow customer at a bank counter holding up the whole queue.

Applications

  • Back ends: checkout, transfers, seat booking. Data Engineering: swap a staging table in one transaction.

Check yourself

  1. What does the A in ACID guarantee?

Answer: A transaction's steps all happen or none do.

  1. Which ACID property is delivered by the write-ahead log?

Answer: Durability.

  1. Why keep transactions short?

Answer: Open transactions hold locks and block other users; long ones cause waits and deadlocks.

9.4 Isolation Levels, MVCC, Locks and Deadlocks

BASIC EXPLANATION
An isolation level sets how much one transaction can see of the changes made by others at the same time. MVCC keeps several versions of rows, locks block conflicting access, and a deadlock happens when transactions wait for each other.
INTUITION
Two clerks edit the same customer file in a bank at the same moment. Clerk 1 reads "balance 1000" and wants to subtract 100. Clerk 2 also read "1000" and subtracts 200. If both write back, one change is lost. Isolation is the set of rules for what each clerk may see and when one must wait. It is the same issue as two people updating one shared tally sheet: without a guard, the final value is wrong.

Words you need

  • Concurrent: happening at the same time.
  • Dirty read: reading another transaction's uncommitted data (which may be rolled back).
  • Non-repeatable read: reading the same row twice in one transaction and getting two different values, because someone committed in between.
  • Phantom read: running the same query twice and getting extra rows, because someone inserted rows in between.
  • Lock: a flag that makes others wait before touching a row or table.
  • MVCC (Multi-Version Concurrency Control): the database keeps old versions of a row, so readers see a stable snapshot and do not block writers.
  • Deadlock: two transactions each wait for a lock the other holds, forever.

The four isolation levels (SQL standard)

LevelDirty readNon-repeatable readPhantom
READ UNCOMMITTEDpossiblepossiblepossible
READ COMMITTEDnopossiblepossible
REPEATABLE READnonopossible (standard), not in PostgreSQL
SERIALIZABLEnonono

Facts about real databases (check the version docs for details): PostgreSQL's default is READ COMMITTED; it treats READ UNCOMMITTED the same as READ COMMITTED, so it never allows dirty reads. Its REPEATABLE READ is a snapshot, and SERIALIZABLE may abort a transaction with a "serialization failure," which your code must retry. MySQL InnoDB defaults to REPEATABLE READ. You set the level with BEGIN ISOLATION LEVEL REPEATABLE READ; in PostgreSQL (not run here).

Higher isolation means fewer strange results and more waiting or retries. Most systems use READ COMMITTED and add explicit locks only where needed.

SQLite is different (and simpler)

SQLite allows one writer at a time for the whole database, and its transactions are serializable. That makes it easy to demonstrate. I used Python's sqlite3 module with two connections, A and B, to the same file.

Problem 9.4.1 A updates a balance but has not committed. What does B see? Can B also write?

a.execute("BEGIN IMMEDIATE")
a.execute("UPDATE accounts SET balance = 700 WHERE id = 1")
print("A sees :", a.execute("SELECT balance FROM accounts").fetchone())
print("B sees :", b.execute("SELECT balance FROM accounts").fetchone())
b.execute("BEGIN IMMEDIATE")      # B also wants to write
A sees : (700,)
B sees : (1000,)
B error: database is locked
after commit B sees: (700,)
  • Step 1 A changed the balance to 700 but has not committed.
  • Step 2 A sees its own change, 700. B still sees 1000. No dirty read.
  • Step 3 B tries to start a write and gets database is locked, because A holds the write lock. (I set the wait time to 0 so the error appears at once. Normally you set a timeout and B simply waits.)
  • Step 4 After A commits, B sees 700.
  • Answer Readers see committed data only, and a second writer must wait.

Problem 9.4.2 (lost update) Both connections read the balance (1000) into Python, subtract in Python and write back. A subtracts 100, B subtracts 200. The right answer is 700.

bal_a = a.execute("SELECT balance FROM accounts").fetchone()[0]   # 1000
bal_b = b.execute("SELECT balance FROM accounts").fetchone()[0]   # 1000
a.execute("UPDATE accounts SET balance = ?", (bal_a - 100,))      # writes 900
b.execute("UPDATE accounts SET balance = ?", (bal_b - 200,))      # writes 800
expected 700, got: 800
  • Step 1 Both read 1000.
  • Step 2 A writes 900. Then B writes 800, based on its old read, wiping A's change.
  • Answer One withdrawal of 100 was lost. This is the lost update problem.

The fix is to let the database do the arithmetic in one statement:

a.execute("UPDATE accounts SET balance = balance - 100")
b.execute("UPDATE accounts SET balance = balance - 200")
expected 700, got: 700

balance = balance - 100 reads and writes under one lock, so each change builds on the last. Other fixes: SELECT ... FOR UPDATE (PostgreSQL, not run here) locks the row while you read it; or use SERIALIZABLE and retry; or optimistic locking with a version column (UPDATE ... WHERE id = 1 AND version = 7, then check that 1 row changed).

COMMON MISTAKE
Read-modify-write in application code (x = SELECT ...; UPDATE ... SET v = x - 100). This is the classic cause of lost updates. Do the maths inside the SQL statement whenever possible.

Locks and MVCC in PostgreSQL

An UPDATE writes a new version of the row and keeps the old one for earlier transactions. Readers never block writers; writers block writers only on the same row. Dead versions are cleaned by VACUUM (Chapter 10). ALTER TABLE takes a strong table lock and can stall a busy table.

Deadlocks

A deadlock needs two transactions and two rows. Think of two cars on a narrow bridge, each waiting for the other to back up.

 time   Transaction T1                   Transaction T2
  1     UPDATE acct SET .. WHERE id=1   (locks row 1)
  2                                     UPDATE acct SET .. WHERE id=2  (locks row 2)
  3     UPDATE acct SET .. WHERE id=2   waits for T2
  4                                     UPDATE acct SET .. WHERE id=1  waits for T1
        --> each waits for the other: DEADLOCK

PostgreSQL detects this (after deadlock_timeout, 1 second by default), kills one transaction with ERROR: deadlock detected, and lets the other finish. The killed program must retry. Not run here (SQLite avoids it by having one writer).

How to avoid deadlocks (all databases):

  1. Touch rows in the same order everywhere (always lower id first).
  2. Keep transactions short; no user input or network calls in the middle.
  3. Take stronger locks early (SELECT ... FOR UPDATE) when you know you will write.
  4. Retry on deadlock and serialization errors. Your code should expect them.

Connection to the real job

A hot row (one counter row updated by every request) is a classic performance bottleneck: throughput is capped by how fast one lock can pass from transaction to transaction. Picture one bank counter: more customers join the queue, the number served per hour stays flat, and waiting times climb. The cure is the same as for any queue: shorter hold time, or spread the work across many rows.

Applications

  • Back ends: inventory and wallets (atomic updates, FOR UPDATE). Operations: lock waits show as slow pages with low CPU use.

Check yourself

  1. Which anomaly is "same query, extra rows the second time"?

Answer: Phantom read.

  1. What does MVCC let readers do?

Answer: Read a consistent older version of rows without waiting for writers.

  1. Name two ways to avoid deadlocks.

Answer: Lock rows in the same order everywhere; keep transactions short (also: retry on failure).

9.5 Transaction Anomaly Lab: Seeing Each Problem Happen

BASIC EXPLANATION
Transaction anomalies are incorrect results caused by concurrent transactions, such as dirty reads, non-repeatable reads and phantom reads. This lab reproduces each one so you can see when it happens.
INTUITION
Section 9.4 gave you the names. Here you watch each problem happen, one step at a time, in a two-session timeline. Think of two cashiers sharing one cash register ledger. An anomaly is simply a moment where a cashier acts on a fact that stopped being true. Each isolation level is a rule about which stale facts a cashier is allowed to act on.

Every timeline below uses two sessions, A and B, and one table. Time runs downward. PostgreSQL timelines are not run here (no PostgreSQL server in this environment); I only state behaviour that the PostgreSQL manual documents. The SQLite examples were run for real.

Example 1: dirty read (and why you will rarely meet it)

t1A: BEGIN; UPDATE accounts SET balance = 700 WHERE id = 1; (not committed)
t2B: SELECT balance FROM accounts WHERE id = 1;
t3A: ROLLBACK; (the 700 never existed)
Dirty readIf B saw 700 at t2, B acted on a number that was never real. PostgreSQL never allows this, even at READ UNCOMMITTED (it behaves as READ COMMITTED). MySQL InnoDB allows it only if you choose READ UNCOMMITTED.

Example 2: non-repeatable read

The balance starts at 1000. B is a report that reads the same row twice inside one transaction.

t1B: BEGIN; SELECT balance ... returns 1000
t2A: UPDATE accounts SET balance = 900 WHERE id = 1; COMMIT;
t3B: SELECT balance ... again. READ COMMITTED returns 900. REPEATABLE READ returns 1000.
MeaningAt READ COMMITTED, B's report can contain two different values for one row. At REPEATABLE READ, B works from one snapshot.

SQLite runs in serializable mode, but in WAL mode (a journal mode that lets readers and one writer work at once) a transaction reads one snapshot, so I can show the REPEATABLE READ behaviour for real. I also try to write from the stale snapshot, which is the next lesson.

Problem 9.5.1 Show a stable snapshot and what happens when B tries to write after A committed. Predict first: B reads 1000 twice, then its write is refused, because its snapshot is out of date.

import sqlite3, tempfile
d = tempfile.mkdtemp(); p = d + "/bank.db"
setup = sqlite3.connect(p); setup.execute("PRAGMA journal_mode=WAL")
setup.execute("CREATE TABLE accounts (id INTEGER PRIMARY KEY, balance INTEGER)")
setup.execute("INSERT INTO accounts VALUES (1, 1000)"); setup.commit(); setup.close()
a = sqlite3.connect(p, isolation_level=None, timeout=0)
b = sqlite3.connect(p, isolation_level=None, timeout=0)
b.execute("BEGIN")
print("B first read :", b.execute("SELECT balance FROM accounts WHERE id=1").fetchone()[0])

Step 1B opens a transaction and reads 1000. Its snapshot is fixed now.
Step 2A commits 900. B reads again and still gets 1000: a repeatable read.
Step 3B tries to change the row from a snapshot that is no longer current. SQLite refuses (the message is the same wording as an ordinary lock error). PostgreSQL does the same at REPEATABLE READ with ERROR: could not serialize access due to concurrent update (not run here).
Step 4B rolls back and starts again. Its fresh snapshot reads 900 and the retry works.
AnswerA snapshot gives stable reads, and the price is that a stale writer must retry.

Example 3: phantom read

t1B: BEGIN; SELECT count(*) FROM orders WHERE status = 'pending'; returns 3
t2A: INSERT INTO orders ... 'pending'; COMMIT;
t3B: the same SELECT count(*). READ COMMITTED returns 4 (a new "phantom" row appeared). PostgreSQL REPEATABLE READ returns 3.

The difference from a non-repeatable read is that no row B already saw changed. A new row joined the set. Row locks cannot stop this, because there is no row to lock yet. That is why the SQL standard lists phantoms separately.

Example 4: lost update (the application version)

You met this in Problem 9.4.2. In timeline form, with A subtracting 100 and B subtracting 200 from 1000:

t1A: reads 1000. B: reads 1000.
t2A: UPDATE ... SET balance = 900, commit.
t3B: UPDATE ... SET balance = 800, commit. Final balance 800, should be 700.
Fixes(1) SET balance = balance - 200, atomic. (2) SELECT ... FOR UPDATE so B waits at t1. (3) PostgreSQL REPEATABLE READ or SERIALIZABLE: B's write at t3 fails with a serialization error and you retry. (4) A version column checked in the WHERE.
COMMON MISTAKE
Believing "REPEATABLE READ means no lost updates" in every database. In PostgreSQL the second writer gets an error, which is safe if you retry. In MySQL InnoDB, plain SELECT reads a snapshot but an UPDATE acts on the latest committed row, so an application-level read, compute, write still loses an update. Use the atomic SET x = x - 200 form, or FOR UPDATE, on both.

Example 5: write skew (the one that fools experts)

A hospital rule: at least one doctor must stay on call. Today Asha and Ravi are both on call. Each wants to leave.

t1A (Asha): BEGIN; SELECT count(*) FROM doctors WHERE on_call; returns 2, so leaving is allowed.
t2B (Ravi): BEGIN; SELECT count(*) FROM doctors WHERE on_call; returns 2, so leaving is allowed.
t3A: UPDATE doctors SET on_call = false WHERE name = 'Asha'; COMMIT;
t4B: UPDATE doctors SET on_call = false WHERE name = 'Ravi'; COMMIT;
ResultZero doctors on call. A and B updated different rows, so no row conflict was detected, yet together they broke the rule.

This is write skew: each transaction made a decision from a read that the other transaction invalidated. Snapshot isolation (PostgreSQL REPEATABLE READ) allows it. PostgreSQL SERIALIZABLE detects it and aborts one transaction with SQLSTATE 40001. You can also lock the rows that your decision depends on: SELECT ... FROM doctors WHERE on_call FOR UPDATE at t1 and t2 makes B wait until A finishes (not run here).

Deadlock reproduction and the retry loop

The deadlock timeline from 9.4 can be reproduced in PostgreSQL with two psql windows (not run here). The fix on the application side is always the same: catch the error, roll back, wait a little, and run the whole transaction again. PostgreSQL signals deadlocks with SQLSTATE 40P01 and serialization failures with 40001. This helper is generic Python and I ran it with a fake job that fails twice and then succeeds:

import time, random
random.seed(1)
class Retryable(Exception):
    pass
def run_with_retry(job, tries=5):
    for attempt in range(1, tries + 1):
        try:
            return job(attempt)
        except Retryable as e:
            wait = 0.01 * 2 ** attempt + random.random() * 0.01
            print("attempt", attempt, "failed:", e, "| wait about", round(wait, 2), "s")
            time.sleep(wait)
    raise RuntimeError("gave up after %d tries" % tries)
def job(attempt):
    if attempt < 3:
        raise Retryable("deadlock detected")
    return "committed on attempt %d" % attempt
print(run_with_retry(job))
attempt 1 failed: deadlock detected | wait about 0.02 s
attempt 2 failed: deadlock detected | wait about 0.05 s
committed on attempt 3
  • Step 1 The helper runs the whole job again, not just the failed statement. A rolled-back transaction leaves nothing behind, so the retry starts clean.
  • Step 2 The wait doubles each time (exponential backoff) plus a random bit (jitter) so two retrying sessions do not collide again in lockstep.
  • Step 3 There is a cap on attempts, because a bug that always fails must not loop forever.

Job queue: claim one task safely

Several workers pull tasks from one jobs table. The danger is two workers claiming the same task. The fix is a single statement that finds and marks the task together. In PostgreSQL the pattern is SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1: rows locked by another worker are skipped instead of waited for (not run here). SQLite has one writer, so a plain atomic UPDATE ... RETURNING does the job, and I ran it:

Problem 9.5.2 Three tasks are queued and four workers each claim one. Predict first: workers 1 to 3 get ids 1 to 3, worker 4 gets nothing.

import sqlite3
db = sqlite3.connect(":memory:", isolation_level=None)
db.execute("CREATE TABLE jobs (id INTEGER PRIMARY KEY, status TEXT, worker TEXT)")
db.executemany("INSERT INTO jobs (status) VALUES (?)", [("queued",)] * 3)
claim = """UPDATE jobs SET status = 'running', worker = ?
           WHERE id = (SELECT id FROM jobs WHERE status = 'queued' ORDER BY id LIMIT 1)
           RETURNING id"""
for w in ["w1", "w2", "w3", "w4"]:
    print(w, "claimed", db.execute(claim, (w,)).fetchall())
print(db.execute("SELECT * FROM jobs").fetchall())
w1 claimed [(1,)]
w2 claimed [(2,)]
w3 claimed [(3,)]
w4 claimed []
[(1, 'running', 'w1'), (2, 'running', 'w2'), (3, 'running', 'w3')]
  • Step 1 The inner SELECT picks the lowest queued id, and the outer UPDATE marks it in the same statement, so no other worker can slip in between.
  • Step 2 RETURNING id hands the claimed id back without a second query.
  • Step 3 Worker 4 finds nothing queued, so it gets an empty list and should sleep.
  • Answer Each task was claimed exactly once.
GOING DEEPER
Without SKIP LOCKED, workers using FOR UPDATE line up behind the first locked row and the queue runs at the speed of one worker. With it, each worker takes the next free row, so throughput grows with the number of workers. Add an index ON jobs (id) WHERE status = 'queued' (a partial index, Chapter 10) so finding the next task stays fast as finished jobs pile up. If a worker dies after claiming, the task stays "running" forever, so real systems add a heartbeat or a claimed_at timeout column that lets another worker reclaim it.

9.6 Security: SQL Injection, Permissions and Row-Level Security

BASIC EXPLANATION
SQL injection is an attack where user input is treated as SQL code, and it is prevented with parameterized queries. Permissions control who can run which statements, and row-level security limits which rows a user can see.
INTUITION
Imagine a bank clerk who types in whatever a customer says out loud, including the sentence "and also hand me the vault key." SQL injection is that: your program glues user text into a SQL command, so the text can become part of the command. The cure is to hand the database the command and the values separately, so the values can never be read as commands.

Words you need

  • SQL injection: an attack where user input changes the meaning of a query.
  • Parameterized query (prepared statement): the SQL text has placeholders (? in sqlite3, %s in psycopg) and the values travel separately.
  • Privilege: permission to do one kind of action on one object. Role: a named bundle of privileges you can give to users.
  • Least privilege: give every account only what it needs and nothing more.

Example 1: the attack, step by step

Problem 9.6.1 A web page lets users type a city and returns customer names. The developer builds the query with string joining. The table also holds a secret column that the page is never supposed to show. Predict first: a normal input returns two names, a crafted input returns the secrets.

import sqlite3
db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE customers (customer_id INTEGER PRIMARY KEY, name TEXT, city TEXT, secret TEXT);
INSERT INTO customers VALUES (1,'Asha','Pune','card-1111'),(2,'Ravi','Mumbai','card-2222'),(3,'Meena','Pune','card-3333');
""")
def bad(city):
    sql = "SELECT name FROM customers WHERE city = '" + city + "'"
    return db.execute(sql).fetchall()
def good(city):
    return db.execute("SELECT name FROM customers WHERE city = ?", (city,)).fetchall()
evil = "x' UNION SELECT secret FROM customers --"
print("bad normal :", bad("Pune"))
print("bad evil   :", bad(evil))
print("good evil  :", good(evil))
try:
    bad("x'; DROP TABLE customers; --")
except Exception as e:
    print("stacked    :", type(e).__name__, e)
bad normal : [('Asha',), ('Meena',)]
bad evil   : [('card-1111',), ('card-2222',), ('card-3333',)]
good evil  : []
stacked    : ProgrammingError You can only execute one statement at a time.
  • Step 1 With the input Pune the glued text is WHERE city = 'Pune'. Fine.
  • Step 2 With the evil input the glued text becomes WHERE city = 'x' UNION SELECT secret FROM customers --'. The quote closes the string early, UNION adds a second query, and -- comments out the leftover quote. The page prints the card numbers.
  • Step 3 The parameterized version sends the same evil text as a plain value. No city is literally named x' UNION ..., so it returns an empty list.
  • Step 4 The last line shows that Python's sqlite3 refuses two statements in one call, which blocks the DROP TABLE trick. PostgreSQL drivers do not all behave this way when you send a simple query string, so never rely on it.
COMMON MISTAKE
Thinking an f-string is safe because "the input comes from our own dropdown." Anyone can send any HTTP request, dropdown or not. Also, escaping quotes by hand fails in many corner cases. Placeholders are the only reliable rule: cursor.execute("... WHERE city = %s", (city,)) in psycopg (not run here, same idea as the ? above).

What placeholders cannot do

Placeholders replace values only. They cannot stand in for a table name, a column name or ASC/DESC. If a user can pick the sort column, check the choice against a fixed allow-list in your code, then join the approved word into the text:

import sqlite3
db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE products (name TEXT, price INTEGER)")
db.executemany("INSERT INTO products VALUES (?, ?)", [("Mug", 250), ("Pen Pack", 120), ("Lamp", 900)])
ALLOWED = {"name": "name", "price": "price"}
def list_products(sort_by):
    col = ALLOWED.get(sort_by)
    if col is None:
        raise ValueError("bad sort column: " + sort_by)
    return db.execute("SELECT name FROM products ORDER BY " + col).fetchall()
print(list_products("price"))
try:
    list_products("price; DROP TABLE products")
except ValueError as e:
    print("rejected:", e)
[('Pen Pack',), ('Mug',), ('Lamp',)]
rejected: bad sort column: price; DROP TABLE products

Example 2: views as access filters

A view is a saved query that behaves like a table. Give analysts the view, not the table, and they can only see the columns and rows you chose. We hide referrer_id and show only Pune customers to a regional team:

CREATE VIEW pune_customers AS
SELECT customer_id, name, signup_date FROM customers WHERE city = 'Pune';
SELECT * FROM pune_customers;

  • Step 2 Asking the view for referrer_id fails, because the view never exposed it.
  • Answer A view narrows both columns and rows. In PostgreSQL, you then GRANT SELECT on the view and not on the table (not run here). Note that in PostgreSQL a view runs with the privileges of its owner by default, so a view can expose rows the viewer could not read directly. That is the point of using it as a filter, and also the reason to be careful about who owns it.

Example 3: GRANT, REVOKE and roles (PostgreSQL, not run here)

-- one role per job, not per person
CREATE ROLE analyst NOLOGIN;
CREATE ROLE etl_loader NOLOGIN;
GRANT SELECT ON orders, order_items, products TO analyst;
GRANT SELECT, INSERT, UPDATE ON orders TO etl_loader;
-- people inherit a role
CREATE ROLE priya LOGIN PASSWORD '...';
GRANT analyst TO priya;
-- take a right away again
REVOKE UPDATE ON orders FROM etl_loader;
  • Step 1 Create roles that match jobs. Roles without LOGIN are groups.
  • Step 2 Grant only what each job needs: analysts read, the loader reads and writes orders, nobody can DROP anything.
  • Step 3 Add a person by granting the role, remove them by revoking it. You never edit per-table rights for one human again.
KEY IDEA
The application should connect with an account that can only run the statements the application needs (usually SELECT, INSERT, UPDATE, DELETE on a few tables), never as the database owner. Then even a successful injection cannot drop tables. Least privilege is the second wall behind parameterized queries.

Going deeper: row-level security (PostgreSQL, not run here)

Row-level security (RLS) lets the database filter rows per user, so every query, including a mistaken one, is filtered. A multi-tenant example, where each tenant sees only its own orders:

ALTER TABLE orders ADD COLUMN tenant_id INTEGER;
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = current_setting('app.tenant_id')::integer);
-- each request, after connecting:
SET app.tenant_id = '7';
SELECT count(*) FROM orders;  -- counts tenant 7 only

Two facts to remember. Table owners and superusers bypass RLS unless you also run ALTER TABLE ... FORCE ROW LEVEL SECURITY (superusers bypass it regardless). And a policy with USING filters reads and the matching rows for updates, while WITH CHECK controls what new rows may be written.

9.7 Programmability: Views, Triggers, Generated Columns, Identity and MERGE

BASIC EXPLANATION
Database programmability features put logic inside the database. Views are saved queries, triggers run automatically on changes, generated columns are computed, identity columns auto-number rows, and MERGE inserts, updates or deletes in one statement.
INTUITION
So far the database stored data and you sent it commands. Programmability lets the database react and derive by itself, like a spreadsheet: a formula column that is always up to date, a rule that writes a log line whenever a cell changes. It is powerful and also easy to overuse, so this section ends with when not to.

Views and materialized views

A normal view stores only the query, so it is always fresh and as slow as the query. A materialized view stores the result, so it is fast and stale until refreshed. PostgreSQL has CREATE MATERIALIZED VIEW and REFRESH MATERIALIZED VIEW name (CONCURRENTLY keeps readers working but needs a unique index; not run here). SQLite has no materialized views, so I imitate one with a table and a refresh script, which shows exactly what staleness means.

Problem 9.7.1 Build a view and a "materialized" copy of paid revenue per customer, add a new paid order, and compare. Predict first: the view includes the new order, the copy does not until refreshed.

CREATE VIEW paid_rev_v AS
SELECT o.customer_id, sum(i.qty * i.unit_price) AS revenue
FROM orders o JOIN order_items i ON i.order_id = o.order_id
WHERE o.status = 'paid' GROUP BY o.customer_id;

CREATE TABLE paid_rev_m AS SELECT * FROM paid_rev_v;

INSERT INTO orders VALUES (115, 6, '2024-04-25', 'paid', NULL);
INSERT INTO order_items VALUES (115, 1, 1, 1500);

SELECT v.customer_id, v.revenue AS view_now, m.revenue AS copy_stale
FROM paid_rev_v v JOIN paid_rev_m m USING (customer_id) WHERE v.customer_id = 6;

  • Step 2 After order 115 (1500) the view says 440 + 1500 = 1940, while the copy still says 440.

Triggers: an audit log

A trigger is code that runs automatically when a row is inserted, updated or deleted. The classic use is an audit trail: who changed a price, from what to what.

Problem 9.7.2 Log every real price change in products. Update product 1 from 1500 to 1600, product 2 from 600 to 620, and product 3 to the same 80. Predict first: two log rows, because the trigger ignores the no-change update.

CREATE TABLE price_audit (
  audit_id   INTEGER PRIMARY KEY,
  product_id INTEGER, old_price INTEGER, new_price INTEGER
);
CREATE TRIGGER trg_price_audit
AFTER UPDATE OF price ON products
WHEN OLD.price <> NEW.price
BEGIN
  INSERT INTO price_audit (product_id, old_price, new_price)
  VALUES (OLD.product_id, OLD.price, NEW.price);
END;

UPDATE products SET price = 1600 WHERE product_id = 1;
UPDATE products SET price = 620  WHERE product_id = 2;
UPDATE products SET price = 80   WHERE product_id = 3;
SELECT * FROM price_audit;
audit_id  product_id  old_price  new_price
--------  ----------  ---------  ---------
1         1           1500       1600
2         2           600        620
  • Step 1 AFTER UPDATE OF price fires only when the price column is in the SET list.
  • Step 2 WHEN OLD.price <> NEW.price skips the third update, where nothing changed.
  • Step 3 OLD and NEW are the row before and after. The trigger writes both into the log inside the same transaction, so a rollback removes the log row too.
  • Answer Two audit rows, ids 1 and 2.
COMMON MISTAKE
Hiding business rules in triggers nobody remembers. A trigger runs on every write, including bulk loads, so it can silently make a 10-minute load take 2 hours, and it makes behaviour hard to read from the application code. Use triggers for audit logs and invariants the database must guarantee. Put ordinary business logic where it can be tested and seen. In PostgreSQL a trigger calls a function (CREATE FUNCTION ... RETURNS trigger LANGUAGE plpgsql, not run here), and a bulk COPY still fires row triggers.

Generated columns

A generated column is computed by the database from other columns. VIRTUAL computes it when read; STORED saves it on write (SQLite supports both when you create the table; ALTER TABLE ADD COLUMN accepts only VIRTUAL). PostgreSQL supports GENERATED ALWAYS AS (...) STORED (virtual generated columns arrived only in PostgreSQL 18).

Identity columns and sequences

An identity column hands out the next number for you. PostgreSQL writes id BIGINT GENERATED ALWAYS AS IDENTITY and uses a sequence underneath (not run here). One fact surprises beginners: a sequence never goes backwards, so a rolled-back insert leaves a gap. Gaps are normal and harmless; never use ids as a gap-free counter such as an invoice number. SQLite shows a related choice, whether a deleted top id may be reused:

CREATE TABLE t_plain (id INTEGER PRIMARY KEY, v TEXT);
CREATE TABLE t_auto  (id INTEGER PRIMARY KEY AUTOINCREMENT, v TEXT);
INSERT INTO t_plain (v) VALUES ('a'),('b'),('c');
INSERT INTO t_auto  (v) VALUES ('a'),('b'),('c');
DELETE FROM t_plain WHERE id = 3;
DELETE FROM t_auto  WHERE id = 3;
INSERT INTO t_plain (v) VALUES ('d');
INSERT INTO t_auto  (v) VALUES ('d');
SELECT 'plain' AS tbl, max(id) AS newest FROM t_plain
UNION ALL SELECT 'autoincrement', max(id) FROM t_auto;
tbl            newest
-------------  ------
plain          3
autoincrement  4

The plain table reused id 3, the AUTOINCREMENT table gave out 4. If other systems, such as logs or caches, remember id 3, reuse can attach old facts to a new row, so prefer the never-reuse behaviour for ids that leave your database.

MERGE, the standard upsert

ON CONFLICT (Chapter 9.2) is PostgreSQL and SQLite syntax. The SQL standard form is MERGE, available in PostgreSQL 15 and later, SQL Server, Oracle, Snowflake and BigQuery, but not in SQLite or MySQL (not run here):

MERGE INTO stock s
USING incoming n ON s.product_id = n.product_id
WHEN MATCHED AND n.qty = 0 THEN DELETE
WHEN MATCHED THEN UPDATE SET qty = s.qty + n.qty
WHEN NOT MATCHED THEN INSERT (product_id, qty) VALUES (n.product_id, n.qty);

Read it as a join with three outcomes. Matched rows can be updated or deleted by a condition, unmatched rows are inserted, and one statement does it all. ON CONFLICT cannot delete, and it needs a unique index to conflict on; MERGE works on any join condition. PostgreSQL 17 added a RETURNING clause to MERGE. Under concurrency MERGE in PostgreSQL can still raise a unique violation if two sessions insert the same key at once, so keep the retry loop from 9.5.

REAL JOB
Stored functions and procedures (PostgreSQL CREATE FUNCTION, CREATE PROCEDURE, CALL) put code next to the data and cut network round trips. Teams use them for batch maintenance and triggers. Most teams keep ordinary business logic in application code or in dbt models instead, because that code is easier to version, test and review.

Chapter recap

  • DDL defines structure (CREATE, ALTER, DROP). Constraints (NOT NULL, UNIQUE, PRIMARY KEY, FOREIGN KEY, CHECK, DEFAULT) make the database reject bad data.
  • SQLite needs PRAGMA foreign_keys = ON each session and is loosely typed unless STRICT; PostgreSQL always enforces both.
  • Use NUMERIC for money. Prefer surrogate primary keys plus a UNIQUE natural key.
  • INSERT, UPDATE, DELETE: write the WHERE first and test it with a SELECT COUNT(*).
  • Upsert is INSERT ... ON CONFLICT DO UPDATE / DO NOTHING; do not use REPLACE, which deletes the whole row.
  • A transaction groups statements: BEGIN, then COMMIT or ROLLBACK. Handle errors in code.
  • ACID: atomic, consistent, isolated, durable. The write-ahead log gives durability.
  • Isolation levels trade safety for speed: READ COMMITTED is the PostgreSQL default; SERIALIZABLE needs retries.
  • Never read, then write back a computed value in app code; use SET x = x - 100 or FOR UPDATE.
  • Deadlocks: lock in a fixed order, keep transactions short, retry.

Practice set

Problem 9.P.1 (easy) Which constraint ensures age is between 0 and 120? Answer: CHECK (age BETWEEN 0 AND 120).

Problem 9.P.2 (what is the output?) CREATE TABLE t (a INTEGER PRIMARY KEY, b TEXT DEFAULT 'x'); INSERT INTO t (a) VALUES (5); SELECT * FROM t; Answer: One row: 5 and x. The default fills b.

Problem 9.P.3 (find the bug) DELETE FROM orders WHERE status = 'cancelled' OR 'refunded'; What is wrong? Answer: OR 'refunded' is not a comparison. Write status IN ('cancelled','refunded'). In SQLite the text 'refunded' evaluates as 0 (false), so only cancelled rows would go, a silent bug. Check with a SELECT COUNT(*) first.

Problem 9.P.4 (find the bug) A function reads bal = SELECT balance ..., then runs UPDATE accounts SET balance = <bal - 100>. Two users run it at once from balance 1000. What can the final balance be, and what is the fix? Answer: 900 instead of 800 (lost update). Fix: UPDATE accounts SET balance = balance - 100 WHERE id = 1 AND balance >= 100, and check that one row changed.

Problem 9.P.5 (scenario) A nightly job loads 2 million rows with one INSERT each, autocommit on, and takes 3 hours. Suggest two improvements. Answer: Wrap batches (say 10,000 rows) in one transaction, so there are fewer commits and disk waits. Better, use COPY (PostgreSQL) or a multi-row INSERT. Also drop or defer heavy indexes during the load (Chapter 10).

Problem 9.P.6 (scenario) Your app logs deadlock detected about 5 times a day. Two functions update accounts row 1 then row 2, and row 2 then row 1. Fix it. Answer: Make both lock rows in the same order (lowest id first), keep the transaction short, and retry the transaction when the error occurs.

Problem 9.P.7 (interview) Explain the difference between READ COMMITTED and REPEATABLE READ with an example. Answer: In READ COMMITTED each statement sees data committed so far, so two identical SELECTs in one transaction can differ if someone commits between them (non-repeatable read). In REPEATABLE READ the transaction sees one snapshot taken at its start, so both SELECTs agree. Cost: REPEATABLE READ may need retries on write conflicts.

Problem 9.P.8 (interview) Why does PostgreSQL not block a long report query when an UPDATE hits the same table? Answer: MVCC. The report reads a snapshot of old row versions, while the UPDATE writes new versions. Readers and writers do not block each other. The cost is dead rows that VACUUM must clean later.

Problem 9.P.9 (easy) Name the anomaly: a report reads a customer's balance twice in one transaction and gets 1000 then 900 because another session committed in between. Answer: Non-repeatable read. REPEATABLE READ prevents it by giving the transaction one snapshot.

Problem 9.P.10 (what is the output?) Two doctors are on call and the rule is "at least one." Each transaction checks the count (2), then sets its own doctor off call, and both commit at READ COMMITTED. How many are on call after? Answer: Zero. This is write skew. Each wrote a different row, so there was no row conflict. Fix with SERIALIZABLE plus retry, or lock the rows read with SELECT ... FOR UPDATE.

Problem 9.P.11 (find the bug) db.execute(f"SELECT * FROM users WHERE name = '{name}'"). What input returns every user, and how do you fix it? Answer: ' OR '1'='1 turns the filter into name = '' OR '1'='1', which is true for every row. Fix: db.execute("SELECT * FROM users WHERE name = ?", (name,)).

Problem 9.P.12 (scenario) A page lets users sort by a column chosen in the URL. Why can you not use a placeholder for it, and what do you do? Answer: Placeholders carry values, not identifiers such as column names. Check the requested name against an allow-list dictionary in code and reject anything else, then place the approved word in the SQL text.

Problem 9.P.13 (scenario) Ten workers pull from a jobs table with SELECT ... FOR UPDATE LIMIT 1 and throughput does not grow past one worker. Why, and what changes it? Answer: Every worker waits for the same first locked row. Add SKIP LOCKED so each worker skips rows that are locked and takes the next free one. Keep a partial index on the queued rows.

Problem 9.P.14 (what is the output?) In SQLite, a table t(id INTEGER PRIMARY KEY) without AUTOINCREMENT holds ids 1, 2, 3. You delete id 3 and insert a new row. What id does it get, and what with AUTOINCREMENT? Answer: Without it, 3 (the largest id plus one). With it, 4, because SQLite remembers the largest id ever used.

Problem 9.P.15 (find the bug) A trigger on orders sends an HTTP request to a billing service for every inserted row. Why is this dangerous? Answer: It runs inside the writing transaction: a slow or failing service blocks or rolls back inserts, and the request cannot be undone if the transaction later rolls back. A bulk load of 1 million rows makes 1 million calls. Write the event into an outbox table in the same transaction and let a separate worker send it.

Problem 9.P.16 (interview) Explain least privilege using the database accounts of a web application. Answer: The app connects with a role that has only the rights it uses (for example SELECT, INSERT, UPDATE on three tables), not the owner role. Migrations run under a different role that can alter tables. Then a leaked password or a successful SQL injection cannot drop tables or read unrelated data. Combine it with parameterized queries, because privileges limit the damage and placeholders prevent the attack.

Problem 9.P.17 (interview) When would you choose a materialized view over a normal view, and what is the cost? Answer: When the query is expensive (large joins or aggregates) and users accept data that is as old as the last refresh, such as a nightly dashboard. The cost is staleness, storage, and a refresh job that takes time and, without CONCURRENTLY, blocks readers in PostgreSQL while it runs.
