Joins put tables side by side. This chapter is about the other directions. How do you stack two lists into one? How do you find who is in list A but not in list B (churn, missing data)? 7.1 UNION, UNION ALL, INTERSECT, EXCEPT

BASIC EXPLANATION
UNION combines the rows of two queries and removes duplicates, and UNION ALL keeps duplicates. INTERSECT returns rows found in both queries, and EXCEPT returns rows in the first but not the second.
INTUITION
Think of two attendance sheets for two classes. Put both sheets in one pile: that is UNION ALL. Put them in one pile but write each name only once: UNION. Names that appear on both sheets: INTERSECT. Names on the first sheet but not on the second: EXCEPT (called MINUS in Oracle).

Words you need

  • Set operation: combines the rows of two queries (not the columns, as a join does).
  • Compatible: both queries must return the same number of columns, with compatible types, in the same order.
  • Duplicate-free: UNION, INTERSECT and EXCEPT remove duplicate rows from the result; UNION ALL does not.

Definitions

OperatorResultRemoves duplicates?Speed note
A UNION ALL Ball rows of A, then all rows of Bnofastest
A UNION Brows in A or Byesneeds a sort or hash
A INTERSECT Brows in bothyes
A EXCEPT Brows in A that are not in Byesorder matters

Rules: column names come from the first query. ORDER BY goes once, at the very end. NULLs are treated as equal to each other when removing duplicates (unlike =). PostgreSQL also has INTERSECT ALL and EXCEPT ALL, which keep duplicate counts.

Real-world mapping

Problem 7.1.5 A precedence trap. In standard SQL (and PostgreSQL) INTERSECT binds tighter than UNION. What does the following give? Predict with the standard rule, then see what SQLite does.

SELECT 1 AS n UNION SELECT 2 INTERSECT SELECT 2;
n
-
2
  • Compute Standard rule: 1 UNION (2 INTERSECT 2) is {1} ∪ {2} = {1, 2}. Left-to-right rule: (1 UNION 2) INTERSECT 2 is {1, 2} ∩ {2} = {2}.
  • Check The printed answer shows which rule SQLite follows.
  • Answer SQLite evaluates compound operators from left to right with equal priority, so the result is 2. PostgreSQL would return 1 and 2.

The picture

   A (Feb buyers)     B (April buyers)

    A EXCEPT B   INTERSECT   B EXCEPT A

Connection to the real job

UNION ALL is how you combine partitioned or monthly tables. EXCEPT and INTERSECT are standard tools for data validation: "rows in the source but not in the warehouse", "keys in both systems". In performance work: "endpoints that appear in the old test but not in the new one".

Applications

  • Data Analytics: retained vs lost vs new customers; overlap between campaigns.
  • Data Engineering: reconciliation between source and target; combining sharded tables.
  • Data Science: removing test-set rows from a candidate training set (EXCEPT).
  • Operations: diff of product codes or delivery areas between two weekly stock lists.
COMMON MISTAKE
Using UNION when UNION ALL is meant (silently loses duplicate records and is slower), and assuming columns are matched by name. They are matched by position, so keep the same column order in every query.

  1. Is A EXCEPT B the same as B EXCEPT A?

  1. Are columns matched by name or by position?

7.2 Pivot and Unpivot

BASIC EXPLANATION
Pivot turns row values into columns, and unpivot turns columns into rows. They are used to reshape data between long and wide layouts for reports.
INTUITION
A long table is like a ledger: one line per fact (Electronics, January, 2100). A wide table is like a report card: one line per subject, with one column per month. People read wide tables; databases store and analyse long tables. Pivot converts long to wide. Unpivot converts wide to long.

Words you need

  • Long format (tidy): one row per observation; few columns (category, month, revenue).
  • Wide format: one column per value of a category (jan, feb, mar, apr).
  • Pivot key: the column whose values become new column headers (month).

How: standard SQL has no PIVOT keyword

The portable method is the conditional aggregation you know from Chapters 3 and 6: one SUM(CASE WHEN ... THEN value END) per new column. Note: you must know the column values in advance. SQL cannot create columns whose names depend on the data in a plain query. (Dynamic pivots need generated SQL or a tool such as pandas pivot_table.)

Native keywords exist in some products: SQL Server and Oracle and Snowflake have PIVOT/UNPIVOT; PostgreSQL has the crosstab function in the tablefunc extension; BigQuery has PIVOT.

Real-world mapping

ShapeExampleWhere it appears in the job
Long(category, month, revenue)warehouse fact tables, ML training data
Widecategory x four month columnsExcel and dashboard layouts
Unpivotwide survey columns to rowscleaning spreadsheet exports

Worked examples

Problem 7.2.1 Build a wide table: paid revenue by category (rows) and month (columns).

Step 1Join order_items, orders and products; keep paid orders.
Step 2One conditional sum per month, wrapped in COALESCE(..., 0) so empty cells show 0 instead of NULL.
Step 3Add a row total as another column.
CREATE TABLE cat_month AS
SELECT p.category,
       COALESCE(SUM(CASE WHEN substr(o.order_date,1,7) = '2024-01' THEN oi.qty*oi.unit_price END), 0) AS jan,
       COALESCE(SUM(CASE WHEN substr(o.order_date,1,7) = '2024-02' THEN oi.qty*oi.unit_price END), 0) AS feb,
       COALESCE(SUM(CASE WHEN substr(o.order_date,1,7) = '2024-03' THEN oi.qty*oi.unit_price END), 0) AS mar,
       COALESCE(SUM(CASE WHEN substr(o.order_date,1,7) = '2024-04' THEN oi.qty*oi.unit_price END), 0) AS apr,

FROM order_items oi
JOIN orders o   ON o.order_id = oi.order_id AND o.status = 'paid'
JOIN products p ON p.product_id = oi.product_id
GROUP BY p.category;

7.3 GROUPING SETS, ROLLUP and CUBE

BASIC EXPLANATION
GROUPING SETS, ROLLUP and CUBE calculate aggregates for several groupings in one query. ROLLUP adds subtotals and a grand total, and CUBE adds totals for all combinations.
INTUITION
A finance report shows revenue per product, a subtotal per category, and a grand total at the bottom. Without special syntax you would write three queries and stack them. ROLLUP does it in one. GROUPING SETS lets you pick exactly which groupings you want. CUBE gives all combinations.

Words you need

  • Grouping set: one particular GROUP BY list, such as (category, product) or (category) or ().
  • Subtotal row: a row that summarises a group; the grouped-out columns appear as NULL.
  • Grand total: the grouping set (), which has no columns, so everything is one group.

Definitions (PostgreSQL, SQL Server, MySQL 8, Oracle, Snowflake, BigQuery; not SQLite)

  • GROUP BY GROUPING SETS ((a, b), (a), ()) computes each listed grouping.
  • GROUP BY ROLLUP (a, b) is shorthand for GROUPING SETS ((a, b), (a), ()). It rolls up from the right: n columns give n + 1 sets.
  • GROUP BY CUBE (a, b) is shorthand for GROUPING SETS ((a, b), (a), (b), ()): all combinations, 2 to the power n sets.
  • The function GROUPING(col) returns 1 when the column was rolled up in this row and 0 otherwise. Use it to tell a rolled-up NULL from a real NULL in the data.

Real-world mapping

FeatureExampleWhere it appears in the job
ROLLUP (category, product)product rows, category subtotals, grand totalfinance and sales reports
CUBE (region, product)totals for every sliceOLAP cubes, pivot-like analysis
GROUPING SETSonly the slices you ask fordashboards with several summary levels

Worked examples

SQLite does not have these three, but we can prove what they mean by writing the same thing with UNION ALL (which SQLite runs), and then show the standard syntax.

Problem 7.3.1 (the long way) Revenue by category and product, with category subtotals and a grand total, using UNION ALL. All orders count here.

Step 1Detail rows: group by (category, product).
Step 2Subtotals: group by (category), with product shown as 'ALL'.
Step 3Grand total: no grouping, with both labels 'ALL'.
SELECT p.category, p.name AS product, SUM(oi.qty*oi.unit_price) AS revenue
FROM order_items oi JOIN products p ON p.product_id = oi.product_id
GROUP BY p.category, p.name
UNION ALL
SELECT p.category, 'ALL', SUM(oi.qty*oi.unit_price)
FROM order_items oi JOIN products p ON p.product_id = oi.product_id
GROUP BY p.category
UNION ALL
SELECT 'ALL', 'ALL', SUM(oi.qty*oi.unit_price)
FROM order_items oi
ORDER BY 1, 2;

The same result in PostgreSQL, one query:

-- PostgreSQL syntax, not run here
SELECT COALESCE(p.category, 'ALL')                 AS category,
       COALESCE(p.name, 'ALL')                      AS product,
       SUM(oi.qty * oi.unit_price)                  AS revenue,
       GROUPING(p.category, p.name)                 AS grouping_level
FROM order_items oi JOIN products p ON p.product_id = oi.product_id
GROUP BY ROLLUP (p.category, p.name)
ORDER BY p.category NULLS LAST, p.name NULLS LAST;

GROUPING(p.category, p.name) is a bit mask: 0 means detail row, 1 means product rolled up (category subtotal), 3 means both rolled up (grand total).

Connection to the real job

Management reports always have subtotals. BI tools (Power BI, Tableau) compute these on their own, but in a warehouse you often produce them in SQL. CUBE and ROLLUP are the SQL idea behind OLAP (Chapter 11).

7.4 Reporting Lab: ROLLUP, Pivot and Unpivot You Can Run Anywhere

BASIC EXPLANATION
This lab uses small tables to practise ROLLUP, pivot and unpivot with queries that run on any database. It is used to check that you can produce subtotals and reshape results.
INTUITION
A finance report has detail lines, a subtotal under each group and a grand total at the bottom. ROLLUP is the keyword that produces all of those in one query. SQLite does not have it, but a report is only a stack of group-by queries at different levels, so UNION ALL builds the same thing. Doing it by hand once shows exactly what ROLLUP and GROUPING() do for you.

Problem 7.4.1 Build a revenue report by category and month with a subtotal per category and a grand total, using only portable SQL. First a view of paid lines, then three group-by levels. Predict first: 3 categories x months with sales, plus one subtotal row per category, plus one grand-total row.

CREATE VIEW paid_lines AS
SELECT p.category, substr(o.order_date, 1, 7) AS month, i.qty * i.unit_price AS amt
FROM orders o JOIN order_items i ON i.order_id = o.order_id JOIN products p ON p.product_id = i.product_id
WHERE o.status = 'paid';

  SELECT category, 'ALL', sum(amt) FROM paid_lines GROUP BY category

  SELECT 'ALL', 'ALL', sum(amt) FROM paid_lines

ALL          ALL      12660
Step 1Level 0 groups by both columns: the detail rows. Level 1 groups by category only and writes the text ALL in the month column. Level 2 has no group at all, one grand-total row.
Step 2All three branches have the same column list and types, so UNION ALL is legal. Use UNION ALL, not UNION, so identical totals are not merged.
Step 3The three queries sit inside one outer SELECT because an ORDER BY on a UNION may only name result columns. The outer ORDER BY puts the ALL rows after the details by sorting on the boolean tests (month = 'ALL'), which are 0 or 1.
CheckEach category subtotal equals the sum of its detail rows, and the grand total equals the sum of the three subtotals.
PostgreSQL formGROUP BY ROLLUP (category, month) gives the same rows, with NULL instead of ALL, in one pass over the data (not run here). Use GROUPING(month), which is 1 when the NULL is a subtotal marker and 0 when the data itself was NULL, to label them.
COMMON MISTAKE
Using COALESCE(month, 'ALL') to label subtotal rows in a ROLLUP query. If the data has a real NULL month, it is also relabelled ALL and you cannot tell a data gap from a subtotal. Use CASE WHEN GROUPING(month) = 1 THEN 'ALL' ELSE month END. The same holds for the hand-made version here: if month could be NULL, the detail branch must handle it first.
OperatorLevels produced for (a, b)Rows if a has 3 values and b has 4 (all combinations present)
GROUP BY a, b(a,b)12
ROLLUP (a, b)(a,b), (a), ()12 + 3 + 1 = 16
CUBE (a, b)(a,b), (a), (b), ()12 + 3 + 4 + 1 = 20
GROUPING SETS ((a),(b))exactly the sets you list3 + 4 = 7

Rule of thumb: ROLLUP is for hierarchies (country, state, city), where the order of columns matters. CUBE is for independent dimensions where you want every cross-total. GROUPING SETS is for when you know exactly which levels the report needs, and it is the cheapest.

Dynamic pivot: the column list comes from the data

Plain SQL cannot create columns whose names depend on data, but your program can write the SQL. Query the distinct values, build one SUM(CASE ...) per value, then run the generated text. This is the standard answer to the interview question "pivot when I do not know the months in advance".

Problem 7.4.2 Generate a pivot of sales by category with one column per month found in the data. Predict first: two month columns now, and three after a March row arrives.

import sqlite3
db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE sales (category TEXT, month TEXT, amt INTEGER);
INSERT INTO sales VALUES ('Electronics','2024-01',2100),('Electronics','2024-02',1500),
 ('Stationery','2024-01',160),('Stationery','2024-02',120),('Home','2024-02',900);
""")
months = [r[0] for r in db.execute("SELECT DISTINCT month FROM sales ORDER BY month")]
cols = ",\n  ".join("sum(CASE WHEN month = '%s' THEN amt ELSE 0 END) AS \"m%s\"" % (m, m.replace("-", "_")) for m in months)
sql = "SELECT category,\n  " + cols + "\nFROM sales GROUP BY category ORDER BY category"
print(sql)
print()
cur = db.execute(sql)
print([d[0] for d in cur.description])
for row in cur: print(row)
db.execute("INSERT INTO sales VALUES ('Home','2024-03',250)")
months = [r[0] for r in db.execute("SELECT DISTINCT month FROM sales ORDER BY month")]
print("after a new month arrives, columns would be:", months)
SELECT category,
  sum(CASE WHEN month = '2024-01' THEN amt ELSE 0 END) AS "m2024_01",
  sum(CASE WHEN month = '2024-02' THEN amt ELSE 0 END) AS "m2024_02"
FROM sales GROUP BY category ORDER BY category

['category', 'm2024_01', 'm2024_02']
('Electronics', 2100, 1500)
('Home', 0, 900)
('Stationery', 160, 120)
after a new month arrives, columns would be: ['2024-01', '2024-02', '2024-03']
Step 1The first query asks the data which months exist.
Step 2A string join builds one aggregate column per month. Column aliases are quoted and cleaned (- becomes _), since a name like 2024-01 is not a legal bare identifier.
Step 3The generated SQL is ordinary SQL, so you can print and inspect it. Electronics has 2100 in January and 1500 in February, as the data says.
Step 4When March data appears, the list of months grows to three and the next run of the generator produces three columns. Nobody edits the query.
COMMON MISTAKE
Building a dynamic pivot by pasting user-supplied values into the SQL text. The month list above comes from your own table, but if it came from a web form, it would be an injection hole (Section 9.6). Validate values against the database, or against an allow-list, before they become identifiers. Placeholders cannot be used for column names.

Unpivot: wide back to long

The reverse trip, one row per (category, quarter), is needed whenever a spreadsheet-style table must be loaded into a tidy fact table or plotted. The portable way is one SELECT per column joined by UNION ALL:

Problem 7.4.3 Turn the wide targets table (one column per quarter) into a long table. Predict first: 2 categories x 3 quarters = 6 rows.

CREATE TABLE targets (category TEXT, q1 INTEGER, q2 INTEGER, q3 INTEGER);
INSERT INTO targets VALUES ('Electronics', 5000, 5500, 6000), ('Home', 2000, 2100, 2300);
SELECT category, 'q1' AS quarter, q1 AS target FROM targets
UNION ALL SELECT category, 'q2', q2 FROM targets
UNION ALL SELECT category, 'q3', q3 FROM targets
ORDER BY category, quarter;
category     quarter  target
-----------  -------  ------
Electronics  q1       5000
Electronics  q2       5500
Electronics  q3       6000
Home         q1       2000
Home         q2       2100
Home         q3       2300
Step 1Each SELECT reads one wide column and writes its name as text in the quarter column.
Step 2Six rows come back, as predicted: 2 categories times 3 quarters.
Native formsSQL Server and Oracle write UNPIVOT (target FOR quarter IN (q1, q2, q3)). PostgreSQL writes CROSS JOIN LATERAL (VALUES ('q1', q1), ('q2', q2), ('q3', q3)) AS v(quarter, target). BigQuery has UNPIVOT. Snowflake has UNPIVOT too. None of these four were run here.

SQLite can also do it by expanding a JSON object, which scales to many columns without repeating the pattern. It returns the same six rows:

SELECT t.category, j.key AS quarter, j.value AS target
FROM targets t, json_each(json_object('q1', t.q1, 'q2', t.q2, 'q3', t.q3)) AS j
ORDER BY t.category, j.key;
category     quarter  target
-----------  -------  ------
Electronics  q1       5000
Electronics  q2       5500
Electronics  q3       6000
Home         q1       2000
Home         q2       2100
Home         q3       2300
GOING DEEPER
A pivot is a GROUP BY with an aggregate per output column, so it is only correct when each (row key, column key) pair has at most one source row or you intend to aggregate duplicates. If the long table has two rows for (Home, 2024-02), SUM silently adds them and MAX silently drops one. Before pivoting, check uniqueness: SELECT category, month, count(*) FROM sales GROUP BY 1, 2 HAVING count(*) > 1. Wide tables are for people and charts; keep storage and joins long.

Practice with answers

Problem 7.4.4 A report needs revenue per (region, product) with a subtotal per region only and a grand total, but no per-product subtotal across regions. Which operator? (easy)

Answer: ROLLUP (region, product) gives (region, product), (region) and the grand total, which is exactly this. CUBE would add a per-product-across-regions row set you do not want.

Problem 7.4.5 ROLLUP (a, b, c) on 2 x 3 x 4 distinct combinations, all present, how many rows? (medium)

Answer: Levels: (a,b,c) = 24, (a,b) = 6, (a) = 2, () = 1. Total 24 + 6 + 2 + 1 = 33.

Problem 7.4.6 A teammate writes the hand-made rollup with UNION instead of UNION ALL. Name two problems. (find the bug)

Answer: First, UNION removes duplicate rows, so any two branches that happen to produce an identical row (same labels, same amount) would silently lose one, and the totals would no longer add up. Second, UNION must sort or hash all rows to find duplicates, which costs time for nothing. Use UNION ALL whenever you know the branches do not overlap.

Chapter recap

  • UNION ALL stacks all rows; UNION also removes duplicates; use UNION ALL unless you need de-duplication.
  • INTERSECT finds rows in both; EXCEPT finds rows in the first but not the second, and order matters.
  • Set operations match columns by position and need compatible types; ORDER BY goes at the end.
  • Use brackets when mixing set operators; databases differ in precedence.
  • Pivot (long to wide) is SUM(CASE WHEN ...) per output column; the values must be known in advance.
  • Unpivot (wide to long) is one SELECT per column joined by UNION ALL, or LATERAL (VALUES ...).
  • GROUPING SETS, ROLLUP and CUBE make subtotals in one pass; SQLite lacks them, emulate with UNION ALL.
  • CUBE and ROLLUP never create empty groups.

Problem 7.P.8 (scenario) You must compare the list of customer ids in last quarter's mailing with this quarter's, and report who dropped off, who is new, and who stayed. Which operators? Problem 7.P.9 (interview) UNION versus UNION ALL: differences and when to prefer each. Answer: UNION removes duplicate rows (it needs sorting or hashing, so it is slower); UNION ALL keeps everything and is faster. Prefer UNION ALL unless you need unique rows, and when you know the inputs cannot overlap, use UNION ALL for speed.

Problem 7.P.10 (interview) Explain ROLLUP versus CUBE with an example for (year, region). Answer: ROLLUP (year, region) gives rows for (year, region), (year), and grand total: a hierarchy. CUBE (year, region) also adds (region): all combinations. For 2 columns: ROLLUP has 3 grouping sets, CUBE has 4.
