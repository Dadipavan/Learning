A manager never asks "write me a LEFT JOIN". She asks: "Of the people who viewed a product, how many paid?", "Do customers who joined in January still buy in April?", "Who are our best customers?", "Is revenue growing?". Each of these is a known pattern: a standard shape of SQL that thousands of analysts reuse. In this chapter you will learn the six most common patterns, built only from tools you already know (joins from Chapter 4, CTEs from Chapter 5, CASE and dates from Chapter 6, window functions from the window chapters). By the end you can answer all the questions above on real data, and check that your answer is not silently wrong.

We reuse the shop database from Chapter 2 (customers, products, orders, order_items) and add small new tables when a pattern needs them. All outputs below were produced with sqlite3. Date functions differ by database, so each dialect-specific piece is marked and the differences are collected in Chapter 14.

12.1 Funnel Analysis and Churn

INTUITION
A funnel is a leaking pipe. 100 people enter at the top (view a product). Some leave before the next stage (add to cart), more leave before checkout, and only a few come out at the bottom (pay). The analyst's job is to measure how many are left after each stage, and to find the stage where the pipe leaks most. It is like an online shop checkout: you check how many visitors complete step 1, step 2, step 3.

Words you need

WordMeaning
EventOne row saying "user X did action Y at time T"
Funnel stepOne stage in the ordered path (view, cart, checkout, pay)
Conversion rateUsers who reached a step, divided by users who reached an earlier step, as a percent
ChurnA customer who was active in one period and not active in the next

How it works

  1. Turn the event log into one row per user, with the first time they did each step (MIN + CASE, the conditional aggregation of Chapter 3).
  2. Mark a user as "reached step N" only if the earlier steps happened earlier in time.
  3. Count users per step and divide.

Our running table for this section:

CREATE TABLE events (user_id INTEGER, event TEXT, ts TEXT);
INSERT INTO events VALUES
 (1,'view','2024-05-01 10:00:00'),(1,'cart','2024-05-01 10:05:00'),(1,'checkout','2024-05-01 10:09:00'),(1,'pay','2024-05-01 10:12:00'),
 (2,'view','2024-05-01 11:00:00'),(2,'cart','2024-05-01 11:30:00'),(2,'checkout','2024-05-01 11:40:00'),
 (3,'view','2024-05-01 12:00:00'),(3,'cart','2024-05-01 12:02:00'),
 (4,'view','2024-05-01 13:00:00'),
 (5,'view','2024-05-01 14:00:00'),(5,'view','2024-05-01 14:01:00'),(5,'cart','2024-05-01 14:03:00'),(5,'checkout','2024-05-01 14:05:00'),(5,'pay','2024-05-01 14:08:00'),
 (6,'view','2024-05-01 15:00:00'),(6,'pay','2024-05-01 15:02:00');

User 5 viewed twice (a repeat). User 6 paid without a cart or checkout (maybe a "buy now" link, or a tracking bug).

Worked examples

Problem 12.1.1 (tiny) How many rows and how many distinct users have a view event? Predict: user 5 has two views, so rows and users differ.

SELECT COUNT(*) AS views_rows, COUNT(DISTINCT user_id) AS viewers
FROM events WHERE event='view';
views_rows  viewers
----------  -------
7           6
  • Answer 7 rows but 6 people.
  • Why it matters A funnel counts people, not events. COUNT(*) would inflate step 1 and make every conversion rate look worse.

Problem 12.1.2 Build the strict funnel: a user counts at a step only if all earlier steps happened earlier in time.

Step 1One row per user with the first time of each step.
Step 2Use CASE to give 1 or 0 for "reached step N in order". A comparison with NULL gives NULL, which is not true, so the ELSE 0 catches users who never did the step.
Step 3Sum the 1s, then compute percentages.
WITH t AS (
 SELECT user_id,
  MIN(CASE WHEN event='view'     THEN ts END) t_view,
  MIN(CASE WHEN event='cart'     THEN ts END) t_cart,
  MIN(CASE WHEN event='checkout' THEN ts END) t_check,
  MIN(CASE WHEN event='pay'      THEN ts END) t_pay
 FROM events GROUP BY user_id),
s AS (
 SELECT user_id,
  1 AS s1,
  CASE WHEN t_cart  > t_view  THEN 1 ELSE 0 END AS s2,
  CASE WHEN t_check > t_cart  AND t_cart > t_view THEN 1 ELSE 0 END AS s3,
  CASE WHEN t_pay > t_check AND t_check > t_cart AND t_cart > t_view THEN 1 ELSE 0 END AS s4
 FROM t),
c AS (SELECT SUM(s1) a, SUM(s2) b, SUM(s3) c, SUM(s4) d FROM s)
SELECT 'view' step, a users, 100.0 AS pct_of_top, NULL AS pct_of_prev FROM c
UNION ALL SELECT 'cart', b, ROUND(100.0*b/a,1), ROUND(100.0*b/a,1) FROM c
UNION ALL SELECT 'checkout', c, ROUND(100.0*c/a,1), ROUND(100.0*c/b,1) FROM c
UNION ALL SELECT 'pay', d, ROUND(100.0*d/a,1), ROUND(100.0*d/c,1) FROM c;
step      users  pct_of_top  pct_of_prev
--------  -----  ----------  -----------
view      6      100.0                  
cart      4      66.7        66.7       
checkout  3      50.0        75.0       
pay       2      33.3        66.7
  • Check by hand Users 1, 2, 3, 5 carted after viewing: 4. Of those, 1, 2, 5 checked out: 3. Of those, 1 and 5 paid: 2. User 6 paid but is not counted, because the cart and checkout steps are missing.
  • Answer 6 viewers, 4 carted (66.7%), 3 reached checkout (75% of carts), 2 paid (66.7% of checkouts), overall 33.3%.
  • Meaning The biggest leak, as a share of the previous step, is view to cart: 1 in 3 viewers leaves. With real traffic that is where you would start testing.

Problem 12.1.3 (combine) Monthly churn from the shop: customers with a paid order in March who have no paid order in April.

WITH a AS (SELECT DISTINCT customer_id, substr(order_date,1,7) ym
           FROM orders WHERE status='paid')
SELECT COUNT(*) AS active_mar,
  SUM(NOT EXISTS (SELECT 1 FROM a b WHERE b.customer_id=a.customer_id AND b.ym='2024-04')) AS churned,
  ROUND(100.0*SUM(NOT EXISTS (SELECT 1 FROM a b
        WHERE b.customer_id=a.customer_id AND b.ym='2024-04'))/COUNT(*),1) AS churn_pct
FROM a WHERE ym='2024-03';
active_mar  churned  churn_pct
----------  -------  ---------
4           1        25.0
  • Check March buyers: customers 1, 2, 5, 6. April buyers: 1, 2, 4, 5. Only customer 6 is missing in April: 1 of 4, so 25%.
  • Answer Churn from March to April is 25%.
  • Meaning One in four active customers did not come back the next month. NOT EXISTS is the anti-join of Chapter 4. SUM(boolean) works in SQLite and MySQL; in PostgreSQL write SUM(CASE WHEN ... THEN 1 ELSE 0 END) (not run here).

The picture

 6 users  view   ############################  100%
 4 users  cart   ###################           66.7%   (-2 left)
 3 users  check  ##############                50.0%   (-1 left)
 2 users  pay    #########                     33.3%   (-1 left)

Each bar is the number of distinct users who reached that step in the correct order. The shorter the next bar, the bigger the leak between the two steps.

Connection to the real job

Product and marketing analysts get funnel questions weekly. Data engineers build the "one row per user" table once so that dashboards do not recompute it.

Applications

  • Data Analytics: checkout funnel, onboarding funnel, signup funnel.
  • Operations: a hospital visit is a funnel (register, consult, test, pharmacy); the longest queue shows the weak step.
  • Data Science: drop-off rates feed churn-prediction features.
COMMON MISTAKE
Counting events instead of distinct users, and ignoring the order of steps. User 6 paid without a cart. A sloppy "did they ever pay" count gives 3 payers, the strict funnel gives 2. Decide your rule first, write it down, then query.

Check yourself

  1. Why do we use MIN(ts) per step? Answer: to get the first time the user did it, one value per user.
  2. In 12.1.2, why is pct_of_prev for checkout 100.0*c/b? Answer: it divides checkout users (3) by cart users (4) to get 75%.
  3. What does a user with t_cart NULL get at step 2? Answer: 0, because NULL > t_view is not true and the ELSE branch runs.

12.2 Cohort Retention

INTUITION
A school follows each admission batch separately. "Of the 2024 batch, how many are still enrolled after 1 year, after 2 years?" You compare batches fairly because each is measured from its own start. A cohort is a group of customers who started in the same period. Retention is the share of the cohort still active n periods later.

How it works

  1. Find each customer's cohort: the month of their first paid order.
  2. For every later paid month compute month_n = months between the cohort month and that month.
  3. Count distinct customers per (cohort, month_n). Divide by cohort size (month 0).

Worked examples

Problem 12.2.1 (tiny) In which month did customers 1 and 2 start? Predict: customer 1's first paid order is 101 (January 10), customer 2's is 102 (January 15).

SELECT customer_id, MIN(substr(order_date,1,7)) AS cohort
FROM orders WHERE status='paid' AND customer_id IN (1,2) GROUP BY customer_id;
customer_id  cohort 
-----------  -------
1            2024-01
2            2024-01
  • Answer Both belong to the 2024-01 cohort. substr(order_date,1,7) cuts 'YYYY-MM' from the text date. We reuse this MIN idea in the next problem.

Problem 12.2.2 Build the cohort table (months 0 to 3).

WITH paid AS (
  SELECT customer_id, substr(order_date,1,7) AS ym
  FROM orders WHERE status='paid' GROUP BY 1,2),
first AS (SELECT customer_id, MIN(ym) AS cohort FROM paid GROUP BY customer_id),
j AS (
  SELECT f.cohort,
   (CAST(substr(p.ym,1,4) AS INT)*12 + CAST(substr(p.ym,6,2) AS INT))
   -(CAST(substr(f.cohort,1,4) AS INT)*12 + CAST(substr(f.cohort,6,2) AS INT)) AS m,
   p.customer_id
  FROM paid p JOIN first f USING (customer_id))
SELECT cohort, COUNT(DISTINCT customer_id) AS size,
  COUNT(DISTINCT CASE WHEN m=0 THEN customer_id END) AS m0,
  COUNT(DISTINCT CASE WHEN m=1 THEN customer_id END) AS m1,
  COUNT(DISTINCT CASE WHEN m=2 THEN customer_id END) AS m2,
  COUNT(DISTINCT CASE WHEN m=3 THEN customer_id END) AS m3
FROM j GROUP BY cohort ORDER BY cohort;
cohort   size  m0  m1  m2  m3
-------  ----  --  --  --  --
2024-01  2     2   1   2   2 
2024-02  1     1   0   1   0 
2024-03  2     2   1   0   0
  • Step 1 Month number = year*12 + month for both dates, then subtract. This avoids a date-difference function that differs by dialect. In PostgreSQL you would use DATE_TRUNC and AGE or the same arithmetic (not run here).
  • Check January cohort is customers 1 and 2. In February only customer 1 bought (m1 = 1). In March both (m2 = 2). In April both (m3 = 2). February cohort is customer 4: bought in February and April (m2 = 1). March cohort is customers 5 and 6: in April only customer 5 (m1 = 1).
  • Answer The January cohort retains 50% in month 1, 100% in months 2 and 3.
  • Meaning Retention does not have to fall every month. Customers skip a month and return.

Problem 12.2.3 Turn counts into percent with a window function.

WITH paid AS (
  SELECT customer_id, substr(order_date,1,7) AS ym
  FROM orders WHERE status='paid' GROUP BY 1,2),
first AS (SELECT customer_id, MIN(ym) AS cohort FROM paid GROUP BY customer_id),
j AS (
  SELECT f.cohort,
   (CAST(substr(p.ym,1,4) AS INT)*12 + CAST(substr(p.ym,6,2) AS INT))
   -(CAST(substr(f.cohort,1,4) AS INT)*12 + CAST(substr(f.cohort,6,2) AS INT)) AS m,
   p.customer_id
  FROM paid p JOIN first f USING (customer_id)),
c AS (SELECT cohort, m, COUNT(DISTINCT customer_id) n FROM j GROUP BY 1,2)
SELECT cohort, m AS month_n, n,
  ROUND(100.0*n/FIRST_VALUE(n) OVER (PARTITION BY cohort ORDER BY m),0) AS retention_pct
FROM c ORDER BY cohort, m;
cohort   month_n  n  retention_pct
-------  -------  -  -------------
2024-01  0        2  100.0        
2024-01  1        1  50.0         
2024-01  2        2  100.0        
2024-01  3        2  100.0        
2024-02  0        1  100.0        
2024-02  2        1  100.0        
2024-03  0        2  100.0        
2024-03  1        1  50.0
  • Why FIRST_VALUE Month 0 is the first row of each cohort, and it is the cohort size, so every row divides by it.
  • Meaning This long form is what you feed into a heatmap in Power BI or Python.

The picture

 cohort    m0    m1    m2    m3
 2024-01   100%  50%   100%  100%
 2024-02   100%  --    100%   ?
 2024-03   100%  50%    ?     ?
           ('?' = month has not happened yet, we have data to April only)

Rows are start months, columns are months since start. Reading across shows one cohort ageing. Reading down compares cohorts at the same age.

Connection to the real job

Retention tables are the main product-health chart in SaaS, apps and e-commerce. Investors ask for them.

Applications

  • Data Analytics: weekly active-user retention, repeat-purchase rate.
  • Data Science: retention curves feed survival models and lifetime-value forecasts.
  • Marketing: compare cohorts from different campaigns.
COMMON MISTAKE
Reading a missing cell as zero retention. In the real output the February cohort has m3 = 0, but month 3 of that cohort is May, and we only have data until April. The 0 means "not observed yet", not "everyone left". Compare the cohort's age with the last date in your data before you draw conclusions.

Check yourself

  1. What is a cohort? Answer: customers who started in the same period.
  2. Why COUNT(DISTINCT customer_id)? Answer: a customer with two orders in a month must count once.
  3. What would a cohort of size 1 tell you? Answer: very little; its percentages jump between 0 and 100.

12.3 RFM Segmentation and Customer Lifetime Value

INTUITION
A shopkeeper knows three things about regulars: how recently they came, how often they come, and how much they spend. A customer who came yesterday, comes weekly and spends a lot is a champion. One who spent a lot but vanished six months ago needs a phone call. RFM = Recency, Frequency, Monetary value.

How it works

  • Recency = days since the last paid order, measured against a fixed "as-of" date (never now() when you want a repeatable answer).
  • Frequency = number of paid orders.
  • Monetary = total paid money.
  • Give each a score (1 to 3 here) with CASE thresholds, or with NTILE (equal-sized buckets) when you have many customers. Then name segments.

Worked examples

Problem 12.3.1 Compute raw R, F, M for each paying customer, as of 2024-04-30.

WITH rev AS (
  SELECT o.customer_id, o.order_id, o.order_date, SUM(oi.qty*oi.unit_price) AS amt
  FROM orders o JOIN order_items oi USING(order_id)
  WHERE o.status='paid' GROUP BY o.order_id),
rfm AS (
  SELECT customer_id,
    CAST(julianday('2024-04-30') - julianday(MAX(order_date)) AS INT) AS recency_days,
    COUNT(*) AS frequency, SUM(amt) AS monetary
  FROM rev GROUP BY customer_id)
SELECT * FROM rfm ORDER BY customer_id;
customer_id  recency_days  frequency  monetary
-----------  ------------  ---------  --------
1            28            4          4560    
2            10            3          3600    
4            21            2          3300    
5            15            2          760     
6            31            1          440
  • Step 1 The inner query sums line values per order first, so frequency counts orders and not order lines (the duplicate trap of Section 4.4).
  • Check Customer 1's last paid order is 2024-04-02, which is 28 days before April 30. The monetary values add to 12,660, the paid total we know from Chapter 3.
  • Answer Customer 2 is the most recent (10 days); customer 1 spends the most (4,560).
  • Meaning Customers 3, 7 and 8 do not appear: they have no paid orders, so they have no RFM at all. Decide what to do with them separately.

Problem 12.3.2 Score and name segments. Thresholds are business choices; here recency <= 20 days scores 3, <= 45 scores 2; frequency >= 4 scores 3, >= 2 scores 2; monetary >= 3000 scores 3, >= 1000 scores 2.

WITH rev AS (
  SELECT o.customer_id, o.order_id, o.order_date, SUM(oi.qty*oi.unit_price) AS amt
  FROM orders o JOIN order_items oi USING(order_id)
  WHERE o.status='paid' GROUP BY o.order_id),
rfm AS (
  SELECT customer_id,
    CAST(julianday('2024-04-30') - julianday(MAX(order_date)) AS INT) AS recency_days,
    COUNT(*) AS frequency, SUM(amt) AS monetary
  FROM rev GROUP BY customer_id),
sc AS (
  SELECT *,
   CASE WHEN recency_days<=20 THEN 3 WHEN recency_days<=45 THEN 2 ELSE 1 END AS r,
   CASE WHEN frequency>=4 THEN 3 WHEN frequency>=2 THEN 2 ELSE 1 END AS f,
   CASE WHEN monetary>=3000 THEN 3 WHEN monetary>=1000 THEN 2 ELSE 1 END AS m
  FROM rfm)
SELECT customer_id, recency_days, frequency, monetary, r,f,m,
  CASE WHEN r=3 AND f>=2 AND m>=2 THEN 'Champion'
       WHEN r=1 THEN 'At risk' WHEN f=1 THEN 'New / one-time' ELSE 'Regular' END AS segment
FROM sc ORDER BY customer_id;
customer_id  recency_days  frequency  monetary  r  f  m  segment       
-----------  ------------  ---------  --------  -  -  -  --------------
1            28            4          4560      2  3  3  Regular       
2            10            3          3600      3  2  3  Champion      
4            21            2          3300      2  2  3  Regular       
5            15            2          760       3  2  1  Regular       
6            31            1          440       2  1  1  New / one-time
  • Answer Customer 2 is our only Champion. Customer 6 bought once.
  • Meaning The CASE order matters: the first true branch wins (Chapter 6).

Problem 12.3.3 (combine) A simple lifetime-value estimate and the median-style split with NTILE.

FormulaAverage order value (AOV) = paid revenue / paid orders = 12,660 / 12 = 1,055.
FormulaSimple CLV = AOV x orders per customer per year x expected years.
WITH rev AS (SELECT o.customer_id, SUM(oi.qty*oi.unit_price) m
  FROM orders o JOIN order_items oi USING(order_id)
  WHERE o.status='paid' GROUP BY o.customer_id)
SELECT customer_id, m, NTILE(2) OVER (ORDER BY m DESC) AS half FROM rev;
customer_id  m     half
-----------  ----  ----
1            4560  1   
2            3600  1   
4            3300  1   
5            760   2   
6            440   2
  • Check 5 rows into 2 buckets gives 3 and 2 (the extra row goes to the first bucket).
  • Answer The top half holds three customers who give 11,460 of 12,660: about 90.5% of revenue.
  • Meaning A few customers carry most revenue, the usual "80/20" shape.
  • Limit Real CLV uses retention curves (12.2) and margins, not just revenue. A formula with one AOV hides differences between customers.
COMMON MISTAKE
Computing recency with now(). Your answer changes every day and nobody can reproduce last month's report. Pass a fixed as-of date.

Connection to the real job

CRM and marketing teams use RFM to choose who gets a discount or a win-back email. It needs no machine learning, which is why it is still popular.

Applications

  • Marketing analytics: target champions with loyalty offers, at-risk customers with win-back.
  • Data Science: R, F, M are strong features for churn models.
  • Finance: concentration risk (how much revenue comes from the top 3 customers).

Check yourself

  1. What does high recency days mean? Answer: the customer bought long ago (bad).
  2. Why aggregate by order before counting frequency? Answer: otherwise each order line counts as an order.
  3. Difference between CASE scoring and NTILE? Answer: CASE uses thresholds you choose; NTILE forces equal-sized groups.

12.4 Period-over-Period: Running Totals, MoM and YoY

INTUITION
"Revenue is 2,980." Is that good? Only compared with something: last month (MoM, month-over-month), or the same month last year (YoY, year-over-year). YoY removes seasonality: December is always strong, so compare December with December.

How it works

  • Growth % = (this period - previous period) / previous period x 100.
  • LAG(value, 1) OVER (ORDER BY period) brings the previous row's value onto the current row.
  • A running total is SUM(...) OVER (ORDER BY period); a moving average adds a frame such as ROWS BETWEEN 1 PRECEDING AND CURRENT ROW.

Worked examples

Problem 12.4.1 MoM growth, running total and 2-month moving average of paid revenue.

WITH m AS (
  SELECT substr(o.order_date,1,7) AS ym, SUM(oi.qty*oi.unit_price) AS rev
  FROM orders o JOIN order_items oi USING(order_id)
  WHERE o.status='paid' GROUP BY 1)
SELECT ym, rev,
  LAG(rev) OVER (ORDER BY ym) AS prev_rev,
  ROUND(100.0*(rev-LAG(rev) OVER (ORDER BY ym))/LAG(rev) OVER (ORDER BY ym),1) AS mom_pct,
  SUM(rev) OVER (ORDER BY ym) AS running,
  ROUND(AVG(rev) OVER (ORDER BY ym ROWS BETWEEN 1 PRECEDING AND CURRENT ROW),1) AS avg2
FROM m ORDER BY ym;
ym       rev   prev_rev  mom_pct  running  avg2  
-------  ----  --------  -------  -------  ------
2024-01  2260                     2260     2260.0
2024-02  2520  2260      11.5     4780     2390.0
2024-03  2980  2520      18.3     7760     2750.0
2024-04  4900  2980      64.4     12660    3940.0
  • Compute March: (2980 - 2520) / 2520 = 460 / 2520 = 0.1825, so 18.3%. April: (4900 - 2980) / 2980 = 1920 / 2980 = 0.6443, so 64.4%.
  • Check The last running total, 12,660, equals the paid total. January has no previous month, so growth is NULL: correct, not zero.
  • Answer Revenue grew in every month; April grew 64.4%.
  • Meaning The average of the first row uses only one row because the frame cannot reach back.

Problem 12.4.2 (YoY, the trap) A table of monthly sales for two years, with 4 months each.

CREATE TABLE monthly_sales (ym TEXT, rev INTEGER);
INSERT INTO monthly_sales VALUES
('2023-01',1000),('2023-02',1100),('2023-03',1200),('2023-04',1500),
('2024-01',1300),('2024-02',1210),('2024-03',1800),('2024-04',1500);
SELECT ym, rev, LAG(rev,12) OVER (ORDER BY ym) AS wrong_lag12
FROM monthly_sales ORDER BY ym;
ym       rev   wrong_lag12
-------  ----  -----------
2023-01  1000              
2023-02  1100              
2023-03  1200              
2023-04  1500              
2024-01  1300              
2024-02  1210              
2024-03  1800              
2024-04  1500

LAG(rev,12) counts 12 rows back, not 12 months. Here only 8 rows exist, so all values are NULL. If a month were missing, it would silently pick the wrong month. The safe method joins on the calendar:

SELECT c.ym, c.rev, p.rev AS last_year,
  ROUND(100.0*(c.rev-p.rev)/p.rev,1) AS yoy_pct
FROM monthly_sales c
LEFT JOIN monthly_sales p
  ON p.ym = strftime('%Y-%m', date(c.ym||'-01','-1 year'))
WHERE c.ym >= '2024-01' ORDER BY c.ym;
ym       rev   last_year  yoy_pct
-------  ----  ---------  -------
2024-01  1300  1000       30.0   
2024-02  1210  1100       10.0   
2024-03  1800  1200       50.0   
2024-04  1500  1500       0.0
  • Check March: (1800 - 1200) / 1200 = 0.5, so 50%. April: 0 change.
  • Answer YoY growth is 30%, 10%, 50% and 0%.
  • Meaning Compared with last year, April stood still, even though April grew strongly against March (MoM).
  • Fix for gaps Build a date spine (a table with one row per month, from a recursive CTE, Chapter 5) and LEFT JOIN data onto it, so missing months appear as rows with 0 or NULL (the spine query is standard; PostgreSQL has generate_series instead, not run here).

The picture

 revenue
 4900 |                      ##
 2980 |              ##      ##
 2520 |      ##      ##      ##
 2260 | ##   ##      ##      ##
      +-----------------------------
        Jan  Feb    Mar     Apr
 MoM compares each bar with the bar to its left.
 YoY compares it with the same month a year earlier (different chart row).

Connection to the real job

Every business dashboard has a "vs last month" and "vs last year" number. Getting them wrong is a classic incident: a LAG over data with missing months.

Applications

  • Data Analytics: weekly, monthly and yearly KPI reports.
  • Finance: budget versus actual, year-to-date running totals.
  • Logistics: compare this month's 95th-percentile delivery time with last month's (the same formula).
COMMON MISTAKE
Dividing by zero or by NULL. If last year was 0, (c.rev-p.rev)/p.rev fails or gives NULL. Guard with NULLIF(p.rev,0).

Check yourself

  1. Why is growth in the first month NULL? Answer: there is no earlier row to compare with.
  2. When is LAG(x,12) wrong for YoY? Answer: when months are missing, since it counts rows, not months.
  3. Why is SUM() OVER (ORDER BY ym) a running total? Answer: the default frame runs from the first row to the current row.

12.5 Sessionization and Gaps and Islands

INTUITION
You scroll a shopping app for 20 minutes, go for lunch, then return. Is that one visit or two? Analysts say a new session starts after a long silence, often 30 minutes. A similar puzzle: a gym app wants "longest streak of consecutive days". Both are "break a sorted list wherever there is a gap". Each unbroken stretch is an island; the breaks are gaps.

How it works (sessions)

  1. For each click, compute the gap in minutes from the previous click of the same user (LAG).
  2. Mark 1 when the gap is missing or longer than 30 minutes (a session start), else 0.
  3. A running SUM of those marks gives the session number.

Worked examples

Problem 12.5.1 Compute the gaps.

CREATE TABLE clicks (user_id INTEGER, ts TEXT);
INSERT INTO clicks VALUES
(1,'2024-05-01 09:00:00'),(1,'2024-05-01 09:10:00'),(1,'2024-05-01 09:25:00'),
(1,'2024-05-01 11:00:00'),(1,'2024-05-01 11:20:00'),

Problem 12.5.3 Gaps and islands: longest login streak. Trick: subtract the row number (in days) from each date. In a run of consecutive days the result is constant.

CREATE TABLE logins (user_id INTEGER, d TEXT);
INSERT INTO logins VALUES (1,'2024-05-01'),(1,'2024-05-02'),(1,'2024-05-03'),
  (1,'2024-05-06'),(1,'2024-05-07'),(1,'2024-05-09');
WITH r AS (SELECT user_id, d, ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY d) rn FROM logins),
i AS (SELECT *, date(d, '-'||rn||' days') AS grp FROM r)
SELECT user_id, MIN(d) AS streak_start, MAX(d) AS streak_end, COUNT(*) AS days
FROM i GROUP BY user_id, grp ORDER BY streak_start;
user_id  streak_start  streak_end  days
-------  ------------  ----------  ----
1        2024-05-01    2024-05-03  3   
1        2024-05-06    2024-05-07  2   
1        2024-05-09    2024-05-09  1
  • Why it works For 05-01, 05-02, 05-03 the row numbers are 1, 2, 3. Subtracting gives 04-30 each time. After the gap (05-06 with row 4) we get 05-02, a new value, so a new island.
  • Answer The longest streak is 3 days (May 1 to 3).
  • Limit The trick needs one row per day (use DISTINCT first). In PostgreSQL write d - rn with a date column (not run here).

The picture

 time -->  9:00  9:10  9:25            11:00  11:20             next day 8:00
 gap:        -    10    15     95       -> 20          1240
 new_s:      1     0     0      1          0             1
 session:    1     1     1      2          2             3

The gap row above each click is the silence before it. A 1 starts a new session. The running sum counts how many starts we have seen so far.

Connection to the real job

Web and app analytics tools compute sessions in this way. A session is like one visit to a shop: a long gap between actions means the visitor left and later came back as a new visit.

Applications

  • Product analytics: sessions per user, pages per session, session length.
  • Data Engineering: building a sessions table from raw click logs.
  • Operations: find outage windows (islands of consecutive error minutes).
COMMON MISTAKE
Forgetting PARTITION BY user_id in LAG. Then the first click of user 2 is compared with the last click of user 1, giving a nonsense gap.

Check yourself

  1. Why do we mark a session start when the gap is NULL? Answer: the first click has no previous click, so it must start session 1.
  2. What is constant inside an island? Answer: date minus row number.
  3. Why does a one-click session have duration 0? Answer: start and end are the same timestamp.

12.6 Deduplication, Late Data and Data-Quality Queries

INTUITION
Before you trust a report, you inspect the ingredients, as a cook sniffs the milk. Duplicate rows, missing values, impossible numbers and orphan references are the four common problems. You find each with a short query. Keep these queries and run them after each data load; this is "testing for data".

How it works

  • Deduplication: ROW_NUMBER() OVER (PARTITION BY the-real-key ORDER BY the-tie-breaker), keep rn = 1.
  • Late data: records that arrive after their period closed. Keep an updated_at or loaded_at column and pick the latest version per key.
  • Checks: count NULLs, duplicates, out-of-range values; find orphans with an anti-join.

Running table:

CREATE TABLE signups_raw (id INTEGER, email TEXT, plan TEXT, updated_at TEXT, age INTEGER);
INSERT INTO signups_raw VALUES
(1,'asha@x.com','free','2024-05-01',29),
(2,'ravi@x.com','free','2024-05-01',31),
(3,'ravi@x.com','pro','2024-05-03',31),
(4,'Meena@x.com','pro','2024-05-02',NULL),
(5,'meena@x.com ','pro','2024-05-04',27),
(6,'john@x.com','free','2024-05-02',250),
(7,NULL,'free','2024-05-02',40);

Look carefully: Meena appears twice with different case and a trailing space. Ravi appears twice (an upgrade). Row 6 has age 250. Row 7 has no email.

Worked examples

Problem 12.6.1 Keep the newest row per person. Predict: 4 people, so 4 rows.

WITH r AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY lower(trim(email))
                               ORDER BY updated_at DESC, id DESC) AS rn
  FROM signups_raw WHERE email IS NOT NULL)
SELECT id, lower(trim(email)) AS email, plan, updated_at FROM r WHERE rn=1 ORDER BY id;
id  email        plan  updated_at
--  -----------  ----  ----------
1   asha@x.com   free  2024-05-01
3   ravi@x.com   pro   2024-05-03
5   meena@x.com  pro   2024-05-04
6   john@x.com   free  2024-05-02
  • Step 1 Normalise before comparing: lower(trim(email)) makes 'Meena@x.com' and 'meena@x.com ' the same person.
  • Step 2 ORDER BY updated_at DESC, id DESC: newest first; id breaks ties so the result is stable.
  • Check 7 rows, minus 1 null email, minus 2 older duplicates = 4.
  • Answer Ravi is kept as pro, Meena as the May 4 row.
  • Meaning Without the lower(trim()), Meena would survive twice and your user count would be wrong by one.

Problem 12.6.2 A data-quality report in one row.

SELECT COUNT(*) AS total_rows,
  SUM(email IS NULL) AS null_email,
  COUNT(email) - COUNT(DISTINCT lower(trim(email))) AS dup_extra_rows,
  SUM(age IS NULL) AS null_age,
  SUM(age < 0 OR age > 120) AS bad_age
FROM signups_raw;

----------  ----------  --------------  --------  -------
7           1           2               1         1
  • Check COUNT(email) ignores NULL: 6. Distinct cleaned emails: 4. So 2 extra rows. age IS NULL is only row 4. age > 120 is only row 6. Note age IS NULL rows are not counted in bad_age, since a comparison with NULL is not true (Chapter 2).
  • Answer 1 missing email, 2 extra duplicate rows, 1 missing age, 1 impossible age.
  • Meaning Report these numbers to the data owner before building on the table.

Connection to the real job

Data engineers wrap such queries in tests (dbt tests, Great Expectations) that run after every load. An analyst who runs them first avoids embarrassing corrections.

Applications

  • Data Engineering: dedupe CDC (change data capture) feeds by updated_at.
  • Data Science: clean training data before modelling.
  • Compliance: prove that every order has a customer.
COMMON MISTAKE
Using SELECT DISTINCT * to dedupe. It removes only rows that are identical in every column; the Ravi rows differ in plan, so both stay. Pick the business key and a rule for the winner.

Check yourself

  1. Why include a tie-breaker in ORDER BY of ROW_NUMBER? Answer: equal timestamps would give an unpredictable winner.
  2. How do you find orphans? Answer: LEFT JOIN to the parent and keep rows where the parent key is NULL.
  3. Why use median instead of mean for waiting times? Answer: outliers do not move the median much.

12.7 Advanced Pattern Library: Top-N, Graphs, Medians, Intervals and Division

INTUITION
Senior analysts do not invent a new query for every question. They recognise a shape: 'best per group', 'path through a network', 'typical value', 'merge overlapping ranges', 'who did all of these'. Each shape has a standard solution. This section is a pattern library: for each shape you get the picture, the query, real output on the shop data or a small table, and the trap.

Everything here ran on SQLite 3.50.4 against the shop database from Chapter 2 (or the small tables created in the example). PostgreSQL-only alternatives are shown but marked not run here.

Pattern 1: top N per group

Problem 12.7.1 Find the two best-selling products by paid revenue in each category. Predict first: Electronics has two products, so both appear; Home has only one sold product; Stationery has two.

WITH rev AS (
  SELECT p.category, p.name, sum(i.qty * i.unit_price) AS revenue
  FROM order_items i
  JOIN orders o   ON o.order_id = i.order_id AND o.status = 'paid'
  JOIN products p ON p.product_id = i.product_id
  GROUP BY p.category, p.name
),
ranked AS (
  SELECT *, row_number() OVER (PARTITION BY category ORDER BY revenue DESC) AS rn
  FROM rev
)
SELECT category, name, revenue, rn FROM ranked WHERE rn <= 2 ORDER BY category, rn;
category     name       revenue  rn
-----------  ---------  -------  --
Electronics  Keyboard   4500     1
Electronics  Mouse      3000     2
Home         Desk Lamp  3600     1
Stationery   Pen Pack   840      1
Stationery   Notebook   720      2
Step 1The CTE rev sums paid revenue per product. Cancelled and refunded orders are filtered in the JOIN condition.
Step 2row_number() OVER (PARTITION BY category ORDER BY revenue DESC) restarts the count at 1 inside each category.
Step 3The outer WHERE rn <= 2 keeps the top two. Electronics: Keyboard 4500 (1500 x 3 paid orders), Mouse 3000. Home: Desk Lamp 3600, and Mug never sold, so it has no row. Stationery: Pen Pack 840, Notebook 720.
AnswerFive rows. A group with fewer than N items returns what it has.
COMMON MISTAKE
Using row_number() when ties matter. If two products tie on revenue, row_number() breaks the tie arbitrarily, so a rerun can return a different product. Use rank() or dense_rank() to keep all tied rows (you may then get more than N rows), or add a unique second sort key such as the product id to make the order stable. Also, a window function cannot be used directly in WHERE, which is why the ranking sits in a CTE.

PostgreSQL and MySQL 8 also offer CROSS JOIN LATERAL: FROM categories c CROSS JOIN LATERAL (SELECT ... WHERE category = c.category ORDER BY revenue DESC LIMIT 2) t (not run here). It can be faster when you already have a small list of groups and an index on the sort column, because it stops after N rows per group instead of ranking everything.

Pattern 2: paths through a graph, with cycle protection

Problem 12.7.2 Flights connect cities, and the network has a loop (BLR back to PNQ). Find the three fastest routes from PNQ to BLR. Predict first: the direct-looking route through BOM, 0.5 + 1.7 = 2.2 hours, wins.

CREATE TABLE flights (src TEXT, dst TEXT, hours REAL);
INSERT INTO flights VALUES ('PNQ','BOM',0.5),('BOM','DEL',2),('PNQ','DEL',2.5),
  ('DEL','BLR',2.5),('BOM','BLR',1.7),('BLR','PNQ',1.4),('DEL','BOM',2);
WITH RECURSIVE route(city, hops, hrs, path) AS (
  SELECT 'PNQ', 0, 0.0, ',PNQ,'
  UNION ALL
  SELECT f.dst, r.hops + 1, r.hrs + f.hours, r.path || f.dst || ','
  FROM route r JOIN flights f ON f.src = r.city
  WHERE r.path NOT LIKE '%,' || f.dst || ',%'   -- cycle guard: never revisit a city
    AND r.hops < 4                               -- depth limit: a second safety net
)
SELECT trim(path, ',') AS path, hops, hrs FROM route WHERE city = 'BLR' ORDER BY hrs LIMIT 3;
path             hops  hrs
---------------  ----  ---
PNQ,BOM,BLR      2     2.2
PNQ,DEL,BLR      2     5.0
PNQ,BOM,DEL,BLR  3     5.0
Step 1The recursive CTE starts at PNQ with an empty route. Each round follows one more flight and adds its hours.
Step 2The path is kept as text, ,PNQ,BOM,, and the guard NOT LIKE '%,' || dst || ',%' refuses to visit any city already in the path. That is the cycle protection.
Step 3The depth limit hops < 4 is a second safety net, because one bad row could still make a recursion run for ever.
Step 4Filter to arrivals at BLR and sort by hours. Best is PNQ,BOM,BLR at 2.2 hours. Two routes tie at 5.0 hours (PNQ,DEL,BLR is 2.5 + 2.5, PNQ,BOM,DEL,BLR is 0.5 + 2 + 2.5).
AnswerA shortest path by total weight, found by listing every acyclic path and sorting. That is fine for small graphs, and a bad idea for large ones (see below).

To see why the guard matters, run the same walk with only a depth limit and no cycle check:

WITH RECURSIVE route(city, hops) AS (
  SELECT 'PNQ', 0
  UNION ALL
  SELECT f.dst, r.hops + 1 FROM route r JOIN flights f ON f.src = r.city
  WHERE r.hops < 5
)
SELECT count(*) AS rows_without_cycle_guard FROM route;
rows_without_cycle_guard
------------------------
41

With 7 flights and a loop, the walk produced 41 rows by depth 5, because it keeps travelling around the cycle. Without any limit it would never stop (SQLite stops when you press cancel; PostgreSQL runs until memory or time runs out unless you add a limit). PostgreSQL 14 added CYCLE city SET is_cycle USING path to do this bookkeeping for you (not run here).

GOING DEEPER
Listing every path grows exponentially with the size of the graph, so this pattern suits hundreds of nodes, not millions. Real shortest-path problems on large graphs belong in a graph database (Chapter 13) or in code (Dijkstra's algorithm). Inside SQL it is still the right tool for hierarchies, which are trees (no cycles), and for 'can I get from A to B in at most 3 steps' questions.

Pattern 3: bill of materials, exploding quantities

Problem 12.7.3 A bike needs 1 frame and 2 wheels. A wheel needs 1 rim, 32 spokes, 1 tyre and 2 bolts. A frame needs 3 tubes and 8 bolts. How many of each raw part for one bike? Predict first: spokes 2 x 32 = 64, bolts 8 + 2 x 2 = 12.

CREATE TABLE bom (parent TEXT, child TEXT, qty INTEGER);
INSERT INTO bom VALUES ('bike','frame',1),('bike','wheel',2),('wheel','rim',1),('wheel','spoke',32),
  ('wheel','tyre',1),('frame','tube',3),('frame','bolt',8),('wheel','bolt',2);
WITH RECURSIVE x(part, need) AS (
  SELECT 'bike', 1
  UNION ALL
  SELECT b.child, x.need * b.qty FROM x JOIN bom b ON b.parent = x.part
)
SELECT part, sum(need) AS total FROM x
WHERE part NOT IN (SELECT parent FROM bom)      -- keep only raw parts (leaves)
GROUP BY part ORDER BY part;
part   total
-----  -----
bolt   12
rim    2
spoke  64
tube   3
tyre   2
Step 1Start with 1 bike. Each round joins the BOM and multiplies the quantity needed by the quantity per parent: x.need * b.qty.
Step 2A part such as bolt is reached by two routes (via frame: 8, via wheel: 2 wheels x 2 bolts = 4), so it appears twice in the recursion. That is why we sum() at the end.
Step 3Keep only leaves: parts that are never a parent. Result: bolt 12, rim 2, spoke 64, tube 3, tyre 2.
AnswerThe multiplication in the recursive step is the whole trick. The same pattern computes org-chart cost roll-ups and recipe ingredient lists.

Pattern 4: median and percentiles, and why the mean lies

Problem 12.7.4 Ten page-load times in milliseconds contain two slow outliers. Compute the mean, the median and the 90th percentile. Predict first: the mean is dragged far above the typical value by the 900.

CREATE TABLE lat (id INTEGER PRIMARY KEY, ms INTEGER);
INSERT INTO lat (ms) VALUES (12),(15),(11),(250),(14),(16),(13),(18),(12),(900);
WITH s AS (SELECT ms, row_number() OVER (ORDER BY ms) AS rn, count(*) OVER () AS n FROM lat)
SELECT (SELECT avg(ms) FROM lat) AS mean_ms,
       (SELECT avg(ms) FROM s WHERE rn IN ((n + 1) / 2, (n + 2) / 2)) AS median_ms,
       (SELECT min(ms) FROM s WHERE rn >= 0.9 * n) AS p90_ms;
mean_ms  median_ms  p90_ms
-------  ---------  ------
126.1    14.5       250
Step 1Sorted: 11, 12, 12, 13, 14, 15, 16, 18, 250, 900. The mean is 1261 / 10 = 126.1.
Step 2The median of 10 values is the average of the 5th and 6th: (14 + 15) / 2 = 14.5. The trick rn IN ((n+1)/2, (n+2)/2) picks the one middle row when n is odd and the two middle rows when n is even (integer division).
Step 3The 90th percentile by the nearest-rank method is the value at position 0.9 x 10 = 9, which is 250.
AnswerThe mean says 126 ms, which describes nobody. The median 14.5 ms is the typical user and the p90 of 250 ms is what one user in ten feels. Report medians and percentiles for latency.

PostgreSQL has percentile_cont(0.5) WITHIN GROUP (ORDER BY ms), which interpolates between neighbours, and percentile_disc, which returns an actual value. SQL Server, Oracle and Snowflake have similar functions. The nearest-rank query above is the portable version. The two methods can give slightly different p90 values, so state which one you use (not run here).

Pattern 5: merging overlapping intervals

Problem 12.7.5 Room bookings are given as start and end times. Merge overlapping or touching bookings into blocks per room, and also list every pair that overlaps. Predict first: room A has 09:00 to 12:00 (three chained bookings) and 13:00 to 14:00 (13:30 to 13:45 sits inside it).

CREATE TABLE booking (room TEXT, s TEXT, e TEXT);
INSERT INTO booking VALUES ('A','09:00','10:00'),('A','09:30','11:00'),('A','11:00','12:00'),
  ('A','13:00','14:00'),('A','13:30','13:45'),('B','09:00','09:30');
WITH m AS (
  SELECT *, max(e) OVER (PARTITION BY room ORDER BY s, e
                         ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING) AS prev_end
  FROM booking
),
g AS (
  SELECT *, sum(CASE WHEN prev_end IS NULL OR s > prev_end THEN 1 ELSE 0 END)
            OVER (PARTITION BY room ORDER BY s, e) AS grp
  FROM m
)
SELECT room, min(s) AS start, max(e) AS finish FROM g GROUP BY room, grp ORDER BY room, start;
room  start  finish
----  -----  ------
A     09:00  12:00
A     13:00  14:00
B     09:00  09:30
Step 1Sort bookings by start inside each room. For each, prev_end is the latest end among all earlier bookings in that room, via max(e) over a frame that stops one row before the current one.
Step 2A booking starts a new block when it begins after everything before it has finished (s > prev_end), or when it is the first. The running sum of those flags is a block number: the gaps-and-islands idea from Section 12.5.
Step 3Group by block: min start, max end. Room A: 09:00 to 12:00 and 13:00 to 14:00. Room B: 09:00 to 09:30.
Step 4The 11:00 booking starts exactly when 09:30-11:00 ends. We used >, so touching bookings merge. Use >= if back-to-back bookings should stay separate.
Overlap testTwo intervals overlap when a.s < b.e AND b.s < a.e, the one condition to memorise. The pair list below shows the two overlaps, and a.rowid < b.rowid stops each pair appearing twice.
SELECT a.room, a.s, a.e, b.s AS other_s, b.e AS other_e
FROM booking a JOIN booking b
  ON a.room = b.room AND a.rowid < b.rowid AND a.s < b.e AND b.s < a.e;
room  s      e      other_s  other_e
----  -----  -----  -------  -------
A     09:00  10:00  09:30    11:00
A     13:00  14:00  13:30    13:45
COMMON MISTAKE
Writing the overlap test as a.s BETWEEN b.s AND b.e. It misses the case where a starts before b and ends after it (a wraps b): neither of a's ends is between b's ends, yet they overlap. Always use the two-inequality form a.s < b.e AND b.s < a.e, which covers every arrangement. PostgreSQL has range types and the && overlap operator (not run here).

Pattern 6: running distinct count

Problem 12.7.6 Visits by day: how many users per day, how many were seen for the first time that day, and how many distinct users so far? Predict first: day 1 has 2 users, day 2 adds user 3, day 3 adds user 4, so the running total is 2, 3, 4.

CREATE TABLE visit (day TEXT, uid INTEGER);
INSERT INTO visit VALUES ('d1',1),('d1',2),('d1',1),('d2',2),('d2',3),('d3',1),('d3',3),('d3',4);
WITH f AS (SELECT day, uid, row_number() OVER (PARTITION BY uid ORDER BY day) AS rn FROM visit)
SELECT day,
       count(DISTINCT uid)  AS daily_users,
       sum(rn = 1)          AS new_users,
       sum(sum(rn = 1)) OVER (ORDER BY day) AS cumulative_distinct
FROM f GROUP BY day ORDER BY day;
day  daily_users  new_users  cumulative_distinct
---  -----------  ---------  -------------------
d1   2            2          2
d2   2            1          3
d3   3            1          4
Step 1count(DISTINCT uid) per day works for the daily number, but a window cannot do count(DISTINCT ...) OVER (PostgreSQL and SQLite reject it).
Step 2The workaround: number each user's visits in time order with row_number(). The row with number 1 is the first time that user was ever seen, so sum(rn = 1) counts new users per day.
Step 3A running sum of new users is the running distinct count: 2, 3, 4.
AnswerUser 1 appears twice on day 1 (a duplicate event). The daily count is still 2 because of DISTINCT, and only the first of user 1's rows has rn = 1 (the other has rn = 2), so user 1 counts once as new.

Pattern 7: relational division, 'who did all of these'

Problem 12.7.7 Which customers have bought every Electronics product (at least once, paid orders)? Predict first: Electronics has two products (Keyboard and Mouse), so we need customers with both: Asha and Ravi.

SELECT c.name
FROM customers c
JOIN orders o      ON o.customer_id = c.customer_id AND o.status = 'paid'
JOIN order_items i ON i.order_id = o.order_id
JOIN products p    ON p.product_id = i.product_id AND p.category = 'Electronics'
GROUP BY c.customer_id
HAVING count(DISTINCT p.product_id) = (SELECT count(*) FROM products WHERE category = 'Electronics');
name
----
Asha
Ravi
Step 1Restrict to paid orders and to Electronics products with the join conditions.
Step 2Group by customer and count distinct products bought. The distinct matters, because buying the keyboard twice is still one product.
Step 3Compare to the total number of Electronics products from a subquery, so the query keeps working when the catalogue grows.

The same shape answers 'users who completed every onboarding step', 'stores that stock all items on a list', and 'students who passed all required courses'. The pattern: count distinct matches per candidate, compare with the size of the required set.

Practice with answers

Problem 12.7.8 Why does the top-N pattern use a CTE or subquery instead of putting rn <= 2 in the same query as the window function? (easy)

Answer: WHERE runs before window functions are computed, so rn does not exist yet at that stage. The window query goes in a CTE or subquery and the outer query filters it. (PostgreSQL has no QUALIFY, but BigQuery, Snowflake and DuckDB do and it removes the extra layer.)

Problem 12.7.9 In the bill of materials, what changes if a part can appear in two different parents at different depths and you forget to sum()? (find the bug)

Answer: You would list bolt twice (8 and 4) instead of once as 12, so purchasing would order too few bolts. The recursion correctly produces one row per path, and the final aggregation combines paths.

Problem 12.7.10 A table of 500 intervals per user needs the longest single block of continuous activity. Outline the query. (medium)

Answer: Merge intervals into blocks as in 12.7.5, then compute max(finish - start) per user over the blocks. In SQL: the grouped result is a CTE, and the outer query takes the maximum duration per user.

Problem 12.7.11 Why is a recursive path-listing query risky on a social network with millions of users? (expert)

Answer: The number of paths grows exponentially with depth (each person has many friends), so even depth 4 or 5 can create billions of rows, and the cycle guard that tests a growing path string costs more at every step. Use a graph database or an algorithm in code (breadth-first search with a visited set), or limit the depth to 2 or 3 and start from a single person.

Chapter recap

  • A funnel counts distinct users who did each step in order; divide by the previous step to find the leak.
  • A cohort is a group that started together; retention is the share of the cohort active n periods later. Unobserved months are not zeros.
  • RFM scores recency, frequency and money; fix an as-of date and aggregate by order first.
  • MoM compares with the previous period, YoY with the same period last year; LAG(x,12) counts rows, so use a calendar join when months can be missing.
  • Sessions: gap from LAG, flag gap > threshold, running SUM gives the session number.
  • Islands: date minus row number is constant inside a consecutive run.
  • Dedupe with ROW_NUMBER over a normalised key; never rely on DISTINCT *.
  • Data-quality queries count NULLs, duplicates, out-of-range values and orphans; run them after each load.

Practice set

Problem 12.P.1 (easy) In the funnel data, how many users have a cart event? Answer: 4 (users 1, 2, 3, 5). Each user has one cart row, so COUNT(*) also gives 4, but COUNT(DISTINCT user_id) is the safe habit.

Problem 12.P.2 (easy) Overall view-to-pay conversion in the strict funnel. Answer: 2 paid of 6 viewers = 33.3%.

Problem 12.P.3 (what is the output?) The January cohort has 2 customers; 1 of them buys in February. What is month-1 retention? Answer: 1 / 2 = 50%, matching the table in 12.2.

Problem 12.P.4 (find the bug) A funnel query uses COUNT(*) on events WHERE event='view' and reports 7 viewers. What is wrong? Answer: User 5 viewed twice. Use COUNT(DISTINCT user_id); the correct number is 6.

Problem 12.P.5 (find the bug) YoY with LAG(rev,12) returns NULL for every row of an 8-row table. Why, and what do you do? Answer: There are only 8 rows, so no row is 12 rows back; LAG counts rows, not months. Join the table to itself on the month one year earlier (12.4.2).

Problem 12.P.6 Using the click data, how many sessions exist if the timeout is 60 minutes instead of 30? Answer: 4. With a 60-minute rule the 45-minute gap of user 2 no longer splits, so user 2 has 1 session. User 1 still splits at 95 and 1240 minutes into 3 sessions. Total 3 + 1 = 4 (verified by running the query).

Problem 12.P.7 For each product category, which product has the highest paid revenue? Answer: Using RANK() OVER (PARTITION BY category ORDER BY rev DESC) and rk = 1: Electronics Keyboard 4500, Home Desk Lamp 3600, Stationery Pen Pack 840 (verified by running).

Problem 12.P.8 (scenario) Customer 3 has only a cancelled order. Does customer 3 belong to the January cohort, to churn, or to RFM? Answer: To none of them. All three patterns filter status='paid', so customer 3 has no paid orders. Whether cancelled orders should count as activity is a business definition to agree before reporting.

Problem 12.P.9 (interview) Write the pattern to find users who logged in on at least 3 consecutive days. Answer: Make one row per user per day (DISTINCT), compute d - ROW_NUMBER() as the island key as in 12.5.3, group by user and key, and keep groups with COUNT(*) >= 3.

Problem 12.P.10 (interview) A table has duplicate rows per order_id from a retry bug. Delete-free way to get one row per order, keeping the latest loaded_at? Answer: ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY loaded_at DESC) in a CTE, then WHERE rn = 1. Mention a tie-breaker column.

Problem 12.P.11 (computation) Revenue was 2,520 in February and 2,980 in March. What is MoM growth, to one decimal? Answer: (2980 - 2520) / 2520 = 460 / 2520 = 0.1825 = 18.3%.
