CHAPTER 5

Subqueries and CTEs (Including Recursive CTEs)

Building a big answer from small steps: queries inside queries, named steps with WITH, and loops that walk through trees and graphs.

Real questions have steps. "Which customers spent more than the average customer?" needs two answers: first the average, then the comparison. "Show the whole reporting chain under the CEO" needs a query that repeats until it reaches the bottom. SQL gives you three tools for this: subqueries (a query inside a query), CTEs (named steps written with WITH) and recursive CTEs (a step that feeds itself). After this chapter you can break any hard question into small readable steps, test each step alone, and handle trees such as org charts or category hierarchies.

5.1 Subqueries: Scalar, Derived Table, Correlated

INTUITION
When you cook, you do not do everything at once. You first chop onions, then fry them. A subquery is "do this small job first, and use its result in the main job". The result can be one value (the average), a list (customer ids), or a whole small table.

Words you need

  • Subquery: a SELECT written inside brackets inside another query.
  • Scalar subquery: returns exactly one value (one row, one column). It can be used anywhere a number can.
  • Derived table: a subquery in FROM that returns a table. It must have an alias.
  • Correlated subquery: refers to a column of the outer query, so it is (conceptually) re-run for every outer row.
  • Uncorrelated subquery: stands alone; it runs once.

Real-world mapping

KindExampleWhere it appears in the job
Scalarprice > (SELECT AVG(price) FROM products)compare each row with a global benchmark
Derived tableFROM (SELECT customer_id, SUM(...) ... GROUP BY ...) taggregate first, then filter or join
IN (subquery)customer_id IN (SELECT ...)audience lists
Correlatedprice > (SELECT AVG(price) ... WHERE category = p.category)compare with the row's own group

Worked examples

Problem 5.1.1 (trivial) Products priced above the average product price. Predict: the average is 3450 / 6 = 575. Which products exceed it?

Step 1The inner query returns one number: SELECT AVG(price) FROM products.
Step 2The outer query compares each price to it.
SELECT name, price
FROM products
WHERE price > (SELECT AVG(price) FROM products)
ORDER BY price DESC;
name       price
---------  -----
Keyboard   1500 
Desk Lamp  900  
Mouse      600
  • Check Prices: 1500, 600, 80, 120, 900, 250. Above 575: 1500, 600, 900.
  • Answer Keyboard, Desk Lamp and Mouse.
  • Meaning You never had to type the number 575. If prices change, the query adapts.

Problem 5.1.2 (derived table) Which customers spent more than the average paying customer, counting paid orders only?

Step 1Inner query: total paid spend per customer. It returns a small table (5 customers have paid orders).
Step 2Take the average of those totals: 12660 / 5 = 2532.
Step 3Keep customers above 2532.
SELECT t.customer_id, t.spent
FROM (
  SELECT o.customer_id, SUM(oi.qty * oi.unit_price) AS spent
  FROM orders o JOIN order_items oi ON oi.order_id = o.order_id
  WHERE o.status = 'paid'
  GROUP BY o.customer_id
) AS t
WHERE t.spent > (SELECT AVG(spent) FROM (
                   SELECT SUM(oi.qty * oi.unit_price) AS spent
                   FROM orders o JOIN order_items oi ON oi.order_id = o.order_id
                   WHERE o.status = 'paid' GROUP BY o.customer_id))
ORDER BY t.spent DESC;
customer_id  spent
-----------  -----
1            4560 
2            3600 
4            3300
  • Compute Customer spends: 4560, 3600, 3300, 760, 440. Sum 12660. Average 12660 / 5 = 2532.
  • Check 4560, 3600 and 3300 are above 2532; 760 and 440 are not.
  • Answer Customers 1, 2 and 4.
  • Meaning The query repeats the same inner block twice. That hurts readability, and section 5.2 shows how a CTE fixes it.

Problem 5.1.3 (correlated) Which products cost more than the average price of their own category?

Step 1For each product p, the inner query averages the prices where the category equals p.category. The link p.category is what makes it correlated.
Step 2Compare.
SELECT p.name, p.category, p.price
FROM products p
WHERE p.price > (SELECT AVG(p2.price) FROM products p2 WHERE p2.category = p.category)
ORDER BY p.category;
name       category     price
---------  -----------  -----
Keyboard   Electronics  1500 
Desk Lamp  Home         900  
Pen Pack   Stationery   120
  • Compute Electronics: (1500 + 600) / 2 = 1050, so the Keyboard (1500) is above. Stationery: (80 + 120) / 2 = 100, so the Pen Pack (120) is above. Home: (900 + 250) / 2 = 575, so the Desk Lamp (900) is above.
  • Check Each category with two products has exactly one product above its average, which is always true for two different prices.
  • Answer Keyboard, Pen Pack, Desk Lamp.
  • Meaning Correlated subqueries are easy to read but, on huge tables, can be slow because they conceptually run once per row. Window functions (Chapter 8) often do the same job faster.

Problem 5.1.4 IN versus EXISTS, and a scalar subquery in SELECT. Show each customer's name with their number of orders, using a scalar correlated subquery.

SELECT c.name,
       (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.customer_id) AS n_orders
FROM customers c
ORDER BY n_orders DESC, c.name;
name   n_orders
-----  --------
Asha   4       
Priya  3       
Ravi   3       
John   2       
Kabir  1       
Meena  1       
Sana   0       
Tom    0
  • Check 4, 3, 3, 2, 1, 1, 0, 0 add to 14 orders.
  • Answer Asha 4; Priya and Ravi 3; John 2; Kabir and Meena 1; Sana and Tom 0.
  • Meaning This gives zero for Sana and Tom without a LEFT JOIN. It is simple, but it runs the inner query for every customer.

IN versus EXISTS: which one?

  • IN (subquery) is clear for a short list of values. The risk: NOT IN with NULLs (Chapter 2).
  • EXISTS (subquery) stops at the first match and handles NULLs safely. Modern optimisers (PostgreSQL, SQL Server, MySQL 8) usually produce the same plan for both when they are logically equal. Use EXISTS/NOT EXISTS for "has / has no" questions, IN for readability with small lists.

The picture

 outer query:  SELECT ... FROM products p WHERE p.price > ( ??? )
                                                          |
                          inner query runs, returns ONE number (575)
                          ---------------------------------------
 uncorrelated: runs once         -> 575 for every row
 correlated:   runs per outer row -> 1050 for Electronics, 100 for Stationery, 575 for Home

Connection to the real job

Comparing "each row with a benchmark" is everywhere: users above average spend, deliveries slower than the overall 95th percentile, products priced above category average. Interviews love the "second highest salary" question, which is a scalar subquery: SELECT MAX(x) FROM t WHERE x < (SELECT MAX(x) FROM t).

Applications

  • Data Analytics: compare segments with global or group benchmarks.
  • Data Engineering: filtering a big table by a small list of keys (IN).
  • Data Science: outlier detection with group averages.
  • Logistics: find deliveries slower than the overall average.
COMMON MISTAKE
A scalar subquery that returns more than one row. PostgreSQL stops with more than one row returned by a subquery used as an expression. SQLite silently uses the first row. Always make sure the inner query returns a single value (an aggregate or a unique key).

Check yourself

  1. What does "correlated" mean?

Answer: The inner query uses a column from the outer query.

  1. Must a derived table have an alias?

Answer: Yes, in PostgreSQL and most databases.

  1. What does a scalar subquery return?

Answer: One row and one column.

5.2 CTEs: Naming Your Steps with WITH

INTUITION
In Problem 5.1.2 we copied the same inner query twice. It was hard to read. Imagine a recipe where steps are numbered and each step has a name: "Step 1: chopped_onions". A CTE (Common Table Expression) is exactly that: you give a query a name at the top, then use the name below like a table.

How it works

WITH step1 AS ( SELECT ... ),
     step2 AS ( SELECT ... FROM step1 ... )
SELECT ... FROM step2 ...;
  • The CTE exists only for that one statement. It is not stored.
  • A later CTE can use earlier ones (chained CTEs). Each step is a small query you can test on its own by running SELECT * FROM step1.
  • You can use one CTE several times in the main query (no copy-paste).
  • In PostgreSQL 12 and later, a CTE used once is normally inlined like a subquery; a CTE used twice may be computed once. You can force it with MATERIALIZED or NOT MATERIALIZED. In older versions every CTE was a "fence" computed once. This matters for speed, not for correctness.

Real-world mapping

Step nameWhat it holdsWhere it appears in the job
paid_linesorder lines of paid orderscleaning step: filter bad rows first
customer_spendone row per customeraggregation step
finalranking or share of totalpresentation step

Worked examples

Problem 5.2.1 (trivial) Rewrite 5.1.2 with a CTE. Same answer, easier to read.

WITH customer_spend AS (
  SELECT o.customer_id, SUM(oi.qty * oi.unit_price) AS spent
  FROM orders o JOIN order_items oi ON oi.order_id = o.order_id
  WHERE o.status = 'paid'
  GROUP BY o.customer_id
)
SELECT customer_id, spent
FROM customer_spend
WHERE spent > (SELECT AVG(spent) FROM customer_spend)
ORDER BY spent DESC;
customer_id  spent
-----------  -----
1            4560 
2            3600 
4            3300
  • Check Same output as 5.1.2: customers 1, 2, 4 with 4560, 3600, 3300.
  • Answer The CTE customer_spend is defined once and used twice.
  • Meaning Same logic, half the text, and each step has a name that tells the reader what it is.

Problem 5.2.2 (chained CTEs) For every paying customer show the customer's share of total paid revenue, in percent.

Step 1paid_totals: revenue per customer.
Step 2grand: the total across all customers.
Step 3Divide: spent / total × 100.
WITH paid_totals AS (
  SELECT o.customer_id, SUM(oi.qty * oi.unit_price) AS spent
  FROM orders o JOIN order_items oi ON oi.order_id = o.order_id
  WHERE o.status = 'paid'
  GROUP BY o.customer_id
),
grand AS (
  SELECT SUM(spent) AS total FROM paid_totals
)
SELECT p.customer_id, p.spent, g.total,
       ROUND(100.0 * p.spent / g.total, 1) AS share_pct
FROM paid_totals p CROSS JOIN grand g
ORDER BY p.spent DESC;
customer_id  spent  total  share_pct
-----------  -----  -----  ---------
1            4560   12660  36.0     
2            3600   12660  28.4     
4            3300   12660  26.1     
5            760    12660  6.0      
6            440    12660  3.5
  • Compute 4560 / 12660 = 0.3602, so 36.0 percent. 3600 / 12660 = 28.4. 3300 / 12660 = 26.1. 760 / 12660 = 6.0. 440 / 12660 = 3.5.
  • Check 36.0 + 28.4 + 26.1 + 6.0 + 3.5 = 100.0.
  • Answer Customer 1 36.0 percent, customer 2 28.4, customer 4 26.1, customer 5 6.0, customer 6 3.5.
  • Meaning The top three customers bring about 90 percent of paid revenue. (In Chapter 8, SUM() OVER () computes the same share in one step.)

Problem 5.2.3 (combine ideas) The monthly revenue, and the month with the highest revenue. Use two CTEs and a filter on the max.

WITH monthly AS (
  SELECT substr(o.order_date,1,7) AS month, SUM(oi.qty * oi.unit_price) AS revenue
  FROM orders o JOIN order_items oi ON oi.order_id = o.order_id
  WHERE o.status = 'paid'
  GROUP BY substr(o.order_date,1,7)
)
SELECT month, revenue
FROM monthly
WHERE revenue = (SELECT MAX(revenue) FROM monthly);
month    revenue
-------  -------
2024-04  4900
  • Check From Chapter 3: paid revenue by month is 2260, 2520, 2980, 4900. The maximum is April's 4900.
  • Answer 2024-04 with 4900.
  • Meaning If two months tied for the max, both would appear, which is usually what you want.

The picture

 orders+items --> [paid_totals] --> [grand] --\
                        |                     +--> final SELECT
                        +---------------------/
 Each box is a named step. You can run SELECT * FROM <box> to test it alone.

Connection to the real job

Production SQL (dbt models, dashboards) is written as long chains of CTEs: source, cleaned, joined, aggregated, final. Reviewers read top to bottom. Style rules used by many teams: lowercase keywords or uppercase, consistent; one CTE per idea; descriptive CTE names (paid_orders, not a, b); comments with -- on non-obvious logic; and move repeated logic into a view (Chapter 9).

Applications

  • Data Analytics: readable multi-step reports.
  • Data Engineering: dbt models are chains of CTEs.
  • Data Science: feature queries built step by step.
  • Interviews: interviewers prefer CTEs to deeply nested subqueries because they are easier to explain.
COMMON MISTAKE
Assuming a CTE is faster than a subquery. It is mainly a readability tool. Also, in some databases a CTE used many times can be recomputed each time. Check the plan (Chapter 10) if speed matters.

Check yourself

  1. Can a CTE be used after the statement ends?

Answer: No. It lives for one statement only.

  1. How do you test a middle step?

Answer: Replace the final select with SELECT * FROM that_step.

  1. What is a chained CTE?

Answer: A CTE that uses an earlier CTE.

5.3 Recursive CTEs

INTUITION
To list everyone under the CEO: first find the CEO. Then find the people who report to the CEO. Then find people who report to those people. Repeat until nobody new appears. That is a loop. Normal SQL has no loop, so SQL gives you the recursive CTE: a query that uses its own output as input in the next round.

Words you need

  • Anchor member (base case): the starting rows. Runs once.
  • Recursive member: refers to the CTE's own name; takes the rows from the previous round and produces new rows.
  • Termination: the recursion ends when a round produces no new rows.
  • Hierarchy / tree: rows pointing to a parent (employee to manager).
  • Graph: nodes joined by edges; may contain cycles.

Shape

WITH RECURSIVE name(columns) AS (
    <anchor query>                 -- starting rows
    UNION ALL                      -- or UNION to remove duplicates
    <recursive query using name>   -- builds the next layer
)
SELECT ... FROM name;

RECURSIVE is required in PostgreSQL and MySQL; SQL Server writes just WITH. SQLite accepts WITH RECURSIVE.

Real-world mapping

UseExampleWhere it appears in the job
Hierarchyorg chart, category treereporting lines, product categories
Date seriesone row per daycalendar tables for gap-free charts
Graph traversalroutes, dependencieslineage of tables in a data warehouse
Number series1 to Ngenerating test data

Worked examples

Problem 5.3.1 (trivial) Count from 1 to 5, and also compute factorials, to see how rounds work.

Step 1Anchor: n = 1, f = 1.
Step 2Recursive: n + 1, f × (n + 1), while n < 5. The WHERE is the stopping rule.
WITH RECURSIVE t(n, f) AS (
  SELECT 1, 1
  UNION ALL
  SELECT n + 1, f * (n + 1) FROM t WHERE n < 5
)
SELECT n, f FROM t;
n  f  
-  ---
1  1  
2  2  
3  6  
4  24 
5  120
  • Check 1! = 1, 2! = 2, 3! = 6, 4! = 24, 5! = 120.
  • Answer Five rows, one per round.
  • Meaning Round 0 gives (1,1). Round 1 reads that row and creates (2,2). It continues until the WHERE fails and no new row is created.

Problem 5.3.2 (hierarchy) A small company. Show everyone under the CEO with their level and their full chain of command.

Step 1Create staff with manager_id. The CEO has NULL.
Step 2Anchor: the row with manager_id IS NULL, level 0.
Step 3Recursive: join staff to the previous layer where s.manager_id = tree.id, level + 1, and build a path string.
CREATE TABLE staff (id INTEGER PRIMARY KEY, name TEXT, manager_id INTEGER);
INSERT INTO staff VALUES
 (1,'Meera',NULL),(2,'Arun',1),(3,'Bina',1),
 (4,'Chetan',2),(5,'Divya',2),(6,'Esha',3),(7,'Farid',4);

WITH RECURSIVE tree(id, name, level, path) AS (
  SELECT id, name, 0, name FROM staff WHERE manager_id IS NULL
  UNION ALL
  SELECT s.id, s.name, tree.level + 1, tree.path || ' > ' || s.name
  FROM staff s JOIN tree ON s.manager_id = tree.id
)
SELECT id, level, path FROM tree ORDER BY path;
id  level  path                         
--  -----  -----------------------------
1   0      Meera                        
2   1      Meera > Arun                 
4   2      Meera > Arun > Chetan        
7   3      Meera > Arun > Chetan > Farid
5   2      Meera > Arun > Divya         
3   1      Meera > Bina                 
6   2      Meera > Bina > Esha
  • Check Meera is level 0. Arun and Bina report to Meera: level 1. Chetan, Divya report to Arun and Esha to Bina: level 2. Farid reports to Chetan: level 3. Seven rows, as in staff.
  • Answer Each person appears once, with the chain such as Meera > Arun > Chetan > Farid.
  • Meaning One query walked four levels deep, though we never said how many levels there were.

Problem 5.3.3 (date series) A day-by-day count of orders for 5 to 11 March 2024, with zeros on empty days.

Step 1Generate 7 dates with recursion: date(d, '+1 day').
Step 2LEFT JOIN orders by date and count.
WITH RECURSIVE days(d) AS (
  SELECT '2024-03-05'
  UNION ALL
  SELECT date(d, '+1 day') FROM days WHERE d < '2024-03-11'
)
SELECT days.d, COUNT(o.order_id) AS n_orders
FROM days LEFT JOIN orders o ON o.order_date = days.d
GROUP BY days.d
ORDER BY days.d;
d           n_orders
----------  --------
2024-03-05  1       
2024-03-06  0       
2024-03-07  1       
2024-03-08  0       
2024-03-09  0       
2024-03-10  0       
2024-03-11  0
  • Check Orders in this window: 106 on March 5 and 107 on March 7 (108 is on the 18th, outside). So counts are 1, 0, 1, 0, 0, 0, 0.
  • Answer Seven rows; only March 5 and March 7 have an order.
  • Meaning Without a date series, a chart would skip the empty days and mislead the viewer. This is the "date spine".

PostgreSQL has generate_series('2024-03-05'::date, '2024-03-11'::date, interval '1 day') for this, which is shorter:

-- PostgreSQL syntax, not run here
SELECT d::date
FROM generate_series(DATE '2024-03-05', DATE '2024-03-11', INTERVAL '1 day') AS g(d);

Problem 5.3.4 (graph with a cycle) A table of one-way links between four services: A to B, B to C, C to D, B to D, D to A. Which services can be reached from A? The graph has a cycle (A, B, C, D, A), so UNION ALL would never stop.

Step 1Use UNION (not UNION ALL). UNION removes duplicate rows, so a node already found is not added again, and the loop ends.
Step 2Show the safer habit too: a depth limit.
CREATE TABLE links (src TEXT, dst TEXT);
INSERT INTO links VALUES ('A','B'),('B','C'),('C','D'),('B','D'),('D','A');

WITH RECURSIVE reach(node) AS (
  SELECT 'A'
  UNION
  SELECT l.dst FROM links l JOIN reach r ON l.src = r.node
)
SELECT node FROM reach ORDER BY node;
node
----
A   
B   
C   
D
WITH RECURSIVE walk(node, depth) AS (
  SELECT 'A', 0
  UNION ALL
  SELECT l.dst, w.depth + 1 FROM links l JOIN walk w ON l.src = w.node
  WHERE w.depth < 4
)
SELECT depth, node FROM walk ORDER BY depth, node;
depth  node
-----  ----
0      A   
1      B   
2      C   
2      D   
3      A   
3      D   
4      A   
4      B
  • Check From A you reach B, then C and D, then A again (already found). So the set is A, B, C, D.
  • Answer All four nodes. The second query shows every walk of length up to 4 (the same node can repeat because routes differ), and the depth < 4 guard makes sure it stops.
  • Meaning Always give recursion a stop: either UNION on a finite set, or a depth guard. PostgreSQL also has a CYCLE clause (version 14 and later) to detect loops.

The picture

 round 0 (anchor)   round 1            round 2          round 3
 [Meera]  -------->  [Arun, Bina] --->  [Chetan, Divya,  ---> [Farid]
                                         Esha]
 Each round finds the children of the previous round. Stop when a round is empty.

Connection to the real job

Data engineers use recursion for lineage ("which tables depend on this table?"), bill-of-materials explosions and category trees. Analysts use it to build date spines when no calendar table exists. For very large graphs, a graph database (Chapter 13) is better.

Applications

  • Data Analytics: category roll-ups, org-chart reports.
  • Data Engineering: lineage and dependency graphs; calendar tables.
  • Data Science: friend-of-friend features on small graphs.
  • Operations: train-route chains (which station connects to which).
COMMON MISTAKE
No stop condition. The query loops until the database kills it. Always add WHERE depth < N while developing, or use UNION. Another mistake: columns in the anchor and the recursive part with different types or order. They must match exactly.

Check yourself

  1. What are the two parts of a recursive CTE?

Answer: The anchor (start) and the recursive member (next layer), joined by UNION [ALL].

  1. When does recursion stop?

Answer: When a round returns no new rows.

  1. Why UNION in the cycle example?

Answer: It removes already-seen rows, so the cycle cannot grow forever.

5.4 Choosing the Right Tool, and Writing Readable SQL

INTUITION
The same answer can be written five ways. A good engineer picks the way that the next reader (and you, six months later) can understand in one minute.

Decision table

SituationBest tool
One number used as a filterscalar subquery
"Has / has no" a matchEXISTS / NOT EXISTS
Several steps, or reuse one step twiceCTE
Per-row comparison with its groupwindow function (Chapter 8)
Tree, graph, date seriesrecursive CTE
Same logic needed by many queriesview (Chapter 9)
Very expensive step reused many timestemporary table (Chapter 9)

Worked examples

Problem 5.4.1 The "second highest price" interview question, three ways. Predict: the prices are 1500, 900, 600, 250, 120, 80, so the second highest is 900.

SELECT MAX(price) AS second_highest
FROM products
WHERE price < (SELECT MAX(price) FROM products);
second_highest
--------------
900
SELECT price AS second_highest FROM products ORDER BY price DESC LIMIT 1 OFFSET 1;
second_highest
--------------
900
WITH ranked AS (
  SELECT price, DENSE_RANK() OVER (ORDER BY price DESC) AS r FROM products
)
SELECT price AS second_highest FROM ranked WHERE r = 2;
second_highest
--------------
900
  • Check All three print 900.
  • Answer 900, three ways.
  • Meaning The LIMIT/OFFSET way breaks when prices tie (two products at 1500 would make the answer 1500). The DENSE_RANK way is correct with ties, and the subquery way as well.

Problem 5.4.2 Style makeover. Here is hard-to-read SQL:

select c.name,sum(oi.qty*oi.unit_price) s from customers c join orders o on o.customer_id=c.customer_id join order_items oi on oi.order_id=o.order_id where o.status='paid' group by c.name having sum(oi.qty*oi.unit_price)>2000 order by s desc;
name  s   
----  ----
Asha  4560
Ravi  3600
John  3300

And the same query, readable:

-- Customers whose paid revenue is above 2000, biggest first
SELECT
    c.name,
    SUM(oi.qty * oi.unit_price) AS paid_revenue
FROM customers   AS c
JOIN orders      AS o  ON o.customer_id = c.customer_id
JOIN order_items AS oi ON oi.order_id   = o.order_id
WHERE o.status = 'paid'
GROUP BY c.name
HAVING SUM(oi.qty * oi.unit_price) > 2000
ORDER BY paid_revenue DESC;
name  paid_revenue
----  ------------
Asha  4560        
Ravi  3600        
John  3300
  • Check Customers with paid revenue above 2000: Asha 4560, Ravi 3600, John 3300.
  • Answer Same result. The second is easier to read and review.
  • Meaning Style rules: one clause per line, aligned joins, meaningful aliases, a comment that states the purpose, uppercase keywords (or consistently lowercase), AS for aliases, explicit ON.

Connection to the real job

Code review of SQL is a real part of data teams. Clean SQL reduces bugs and onboarding time. Many companies use a formatter (such as sqlfluff) in their pipeline.

Applications

  • Data Analytics: reusable report queries other people can maintain.
  • Data Engineering: version-controlled SQL models with review.
COMMON MISTAKE
Writing 200-line queries with nested subqueries four levels deep. Break them into CTEs with names that explain each step.

Check yourself

  1. Why is LIMIT 1 OFFSET 1 risky for "second highest"?

Answer: Ties: duplicates of the top value make the answer wrong.

  1. Name two style rules for readable SQL.

Answer: Descriptive aliases and one clause per line (also comments, CTEs).

  1. When prefer EXISTS over IN?

Answer: When asking has / has no a match, especially when NULLs are possible.

Chapter recap

  • A subquery is a query inside brackets; scalar means one value, derived means a table, correlated means it uses the outer row.
  • IN and EXISTS often behave the same; NOT IN is dangerous with NULLs.
  • A CTE names a step with WITH; chains read like a recipe.
  • A CTE is mostly about readability; check the plan for speed.
  • A recursive CTE has an anchor and a recursive member; it stops when no new rows appear.
  • Always give recursion a stop: UNION, or a depth limit.
  • Use recursion for trees, graphs and date series.
  • Prefer clear names, comments and one clause per line.

Practice set

Problem 5.P.1 (easy) Customers who signed up before the average signup date. Show names. (Dates are text, so compare using Julian day numbers.)

SELECT name, signup_date FROM customers
WHERE julianday(signup_date) < (SELECT AVG(julianday(signup_date)) FROM customers)
ORDER BY signup_date;
name   signup_date
-----  -----------
Asha   2024-01-05 
Ravi   2024-01-12 
Meena  2024-01-20 
John   2024-02-02

Answer: Asha, Ravi, Meena and John. Counting days from 1 January: the signups are day 4, 11, 19, 32, 44, 60, 74 and 91. They add to 335, and 335 / 8 = 41.9, which is about 11 February. Only the first four signed up before that. (PostgreSQL has no julianday; there you can average EXTRACT(EPOCH FROM signup_date).)

Problem 5.P.2 (easy) Customers who have at least one cancelled or refunded order, using IN.

SELECT name FROM customers
WHERE customer_id IN (SELECT customer_id FROM orders WHERE status <> 'paid')
ORDER BY name;
name 
-----
Meena

Problem 5.P.3 (what is the output?) What does this recursive query print?

WITH RECURSIVE c(n) AS (SELECT 10 UNION ALL SELECT n - 3 FROM c WHERE n > 0)
SELECT n FROM c;
n 
--
10
7 
4 
1 
-2

Answer: 10, 7, 4, 1, -2. The test n > 0 is checked on the previous row: 1 is still above 0, so one more row (-2) is produced; then -2 fails the test and recursion stops.

Problem 5.P.4 (find the bug) A recursive query lists all descendants of a manager, but never ends. What is missing?

-- buggy idea: UNION ALL on a table with a cycle, no depth limit

Answer: Either a depth guard (WHERE depth < 10) or UNION so repeated rows are dropped. Data with a manager cycle (A manages B, B manages A) loops forever otherwise.

Problem 5.P.8 (scenario) The CFO wants "revenue by month, with a column showing the previous month's revenue". Without window functions, how would you start? Answer: Build a CTE monthly, then self-join it on "month = previous month". Chapter 8 shows LAG, which is simpler. The CTE is the right first step in both approaches.

Problem 5.P.9 (interview) What is the difference between a subquery and a CTE? Answer: A CTE is a named subquery defined before the main query, which can be referenced several times and chained. Logically they give the same result. CTEs improve readability and are the only way to write recursion. Performance depends on the optimiser; do not assume a CTE is faster.

Problem 5.P.10 (interview) Explain how a recursive CTE works and how you prevent infinite loops. Answer: An anchor query produces the first rows. The recursive part joins the CTE to the base table to produce the next layer, repeated until a round returns nothing. Prevent infinite loops with a depth counter and WHERE depth < N, with UNION instead of UNION ALL, or with PostgreSQL's CYCLE clause.
