Reading data from one table: filtering, sorting, removing duplicates, and understanding the strange behaviour of NULL.

Every data job starts with the same request: "show me the rows that matter." Which customers live in Pune? Which three products cost the most? Which orders have no coupon? In this chapter you learn the five tools that answer these questions on a single table: SELECT, WHERE, ORDER BY, LIMIT and DISTINCT. Then you meet the one idea that fools even experienced engineers, NULL. By the end you can read any simple table, and you can predict what a query returns before you run it.

2.1 SELECT, Columns, Expressions and Aliases

INTUITION
SELECT is a window cut into a table. You choose which columns you want to look at, and you can even make new columns by calculating. Think of a school mark sheet: you pick which columns to show (name, maths, science), and add a calculated one such as percentage.

Words you need

  • Query: one SQL question sent to the database.
  • Clause: one part of a query, such as FROM or WHERE.
  • Expression: anything that produces a value: a column name, a number, qty * unit_price.
  • Alias: a nickname for a column or table, given with AS.

Real-world mapping

SQL ideaExampleWhere it appears in the job
Column listSELECT name, citychoosing report columns
Expressionqty * unit_price AS line_totalrevenue, margin, error-rate columns
LIMIT 10first ten rowsquick look at a new table

Syntax

SELECT  <expressions>
FROM    <table>;
  • * means "all columns". Handy for a quick look. Avoid it in production code (Chapter 10 explains why).
  • AS gives an alias, a new name for a column or table. Aliases make results readable.
  • An expression can use + - * /, functions and || (text join in SQLite and PostgreSQL).

Connection to the real job

Almost every dashboard tile is a SELECT with a calculated column. Good analysts give clear aliases (revenue_inr, not col1) because the alias becomes the column title that business users read.

Applications

  • Feature engineering columns for ML

COMMON MISTAKE
Integer division. In SQLite and PostgreSQL, 7 / 2 is 3, not 3.5, when both are integers. Write 7 * 1.0 / 2 or CAST(7 AS REAL) / 2.

Predict: what will each of these two columns print?

SELECT 7 / 2 AS int_div, 7 * 1.0 / 2 AS real_div;
int_div  real_div
-------  --------
3        3.5

The first is 3 (both numbers are integers, so the answer is an integer and the .5 is thrown away). The second is 3.5, because 1.0 makes the whole expression decimal.

Check yourself

  1. What does AS do?

Answer: It gives a column or table a new name (alias).

  1. What is 10 / 4 with integers in SQLite?

Answer: 2 (integer division).

  1. Why avoid SELECT * in production?

Answer: It reads unneeded columns and breaks when columns change.

2.2 Filtering Rows with WHERE

INTUITION
WHERE is a bouncer at the door. Each row is tested. If the test says true, the row enters the result. If the test says false or unknown, the row stays out. (Unknown is the key to NULL, see 2.4.)

Words you need

  • Condition (or predicate): a test that is TRUE, FALSE or UNKNOWN for each row, such as city = 'Pune'.
  • String literal: text written in single quotes, like 'Pune'. Double quotes are for column names in standard SQL.

Real-world mapping

ConditionExampleWhere it appears in the job

order_date >= '2024-03-01'a time windowmonthly dashboards

name LIKE 'M%'a text patternsearching logs and names

Operators

OperatorMeaningExample

AND OR NOTcombine testscity = 'Pune' AND ...
IN (a,b,c)equals any listed valuecity IN ('Pune','Delhi')

Precedence: NOT, then AND, then OR. Use brackets to be clear.

Worked examples

Problem 2.2.1 Customers in Pune or Delhi who signed up in February or later.

Step 1Write city IN ('Pune','Delhi').
Step 2Add signup_date >= '2024-02-01'. Dates stored as YYYY-MM-DD text compare correctly in order.
SELECT name, city, signup_date
FROM customers
WHERE city IN ('Pune','Delhi') AND signup_date >= '2024-02-01';
name  city   signup_date
----  -----  -----------
John  Delhi  2024-02-02 
Sana  Delhi  2024-03-15 
Tom   Pune   2024-04-01
  • Check Pune customers are Asha (Jan 5), Meena (Jan 20), Tom (Apr 1). Delhi customers are John (Feb 2) and Sana (Mar 15). Only the February-or-later ones remain.
  • Answer John (Delhi, Feb 2), Sana (Delhi, Mar 15) and Tom (Pune, Apr 1). Asha and Meena signed up in January.
  • Meaning Both tests must be TRUE for a row to pass, because of AND.

Problem 2.2.2 Products priced from 100 to 900 inclusive whose name contains the letter p (any case).

SELECT name, price FROM products
WHERE price BETWEEN 100 AND 900 AND name LIKE '%p%';
name       price
---------  -----
Pen Pack   120  
Desk Lamp  900
  • Check Products in range 100 to 900: Mouse (600), Pen Pack (120), Desk Lamp (900), Mug (250). Of these, names with a p: Pen Pack and Desk Lamp (Lamp). Mouse and Mug have none.
  • Answer Desk Lamp (900) and Pen Pack (120). Notebook (80) is below 100 and Keyboard (1500) is above 900.
  • Meaning LIKE '%p%' ignores case in SQLite, so the capital P in Pen Pack also matched. In PostgreSQL you would write ILIKE.

Problem 2.2.3 The precedence trap. Find customers who are in Pune, or who are in Delhi and signed up after March 1.

SELECT name, city, signup_date FROM customers
WHERE city = 'Pune' OR city = 'Delhi' AND signup_date > '2024-03-01';
name   city   signup_date
-----  -----  -----------
Asha   Pune   2024-01-05 
Meena  Pune   2024-01-20 
Sana   Delhi  2024-03-15 
Tom    Pune   2024-04-01
  • Answer Because AND binds tighter, this means Pune OR (Delhi AND after Mar 1). John (Delhi, February) is dropped, and Sana (Delhi, March 15) stays. All three Pune customers stay.
  • Check If you add brackets as (Pune OR Delhi) AND after Mar 1 you get only Sana and Tom. Different brackets, different answer.
  • Meaning Always write the brackets you mean.

Connection to the real job

Every real question has filters: "paid orders in March", "users from India on Android". Business rules like "exclude test accounts" live in WHERE. A missing filter is a silent wrong number.

Applications

  • Cohort selection for experiments
  • Removing test or bot traffic from logs
  • Selecting training rows for a model
COMMON MISTAKE
Mixing AND and OR without brackets. Always bracket mixed conditions: WHERE (a OR b) AND c.

Check yourself

  1. Is BETWEEN 1 AND 5 inclusive?

Answer: Yes, both 1 and 5 match.

  1. What does 'a_c' match with LIKE?

Answer: Three-letter text with any middle character, like abc.

  1. Which binds first, AND or OR?

Answer: AND.

2.3 ORDER BY, LIMIT/OFFSET and DISTINCT

INTUITION
A table has no order. If you do not say ORDER BY, the database may return rows in any order, and that order can change tomorrow. ORDER BY sorts, LIMIT takes the top few, DISTINCT removes repeats. Together they answer "top 3 most expensive products" or "which cities do we serve?".

Words you need

  • Sort key: the column used to order rows.
  • Pagination: showing results in pages (page 1, page 2).
  • Duplicate: two result rows that are identical in every selected column.

Real-world mapping

ToolExampleWhere it appears in the job
ORDER BY price DESC LIMIT 3top 3 productsleaderboards, slowest-requests lists
LIMIT 20 OFFSET 40page 3website lists, API responses
SELECT DISTINCT cityunique citiesprofiling a column

Rules

  • ORDER BY col [ASC|DESC] sorts. Default is ASC. You can sort by several columns, by an alias, or by position (ORDER BY 2, avoid).
  • LIMIT n keeps n rows. OFFSET k skips k first. LIMIT 10 OFFSET 20 is "page 3 of size 10". (SQL Server uses OFFSET ... FETCH or TOP.) Large offsets are slow because the database still counts the skipped rows.
  • DISTINCT removes duplicate whole rows of the selected columns.
  • Where NULLs sort: SQLite puts NULL first in ASC. PostgreSQL puts NULL last in ASC. Use NULLS LAST in PostgreSQL to be explicit.

The logical order SQL reads your query

You write SELECT first, but the engine thinks in this order. This explains many errors.

 1 FROM / JOIN      -> find the tables, combine them
 2 WHERE            -> keep rows
 3 GROUP BY         -> make groups
 4 HAVING           -> keep groups
 5 SELECT           -> compute columns, aliases are born here
 6 DISTINCT
 7 ORDER BY         -> may use aliases
 8 LIMIT / OFFSET

So WHERE cannot use a SELECT alias (the alias is not born yet), but ORDER BY can.

Problem 2.3.1 The three most expensive products.

SELECT name, price * 2 AS double_price FROM products ORDER BY double_price DESC LIMIT 2;
name       double_price
---------  ------------

Desk Lamp  1800
SELECT name, price * 2 AS double_price FROM products WHERE double_price > 1000;
name       double_price
---------  ------------

Mouse      1200

  • Answer The first works. The second fails in PostgreSQL (column "double_price" does not exist). Look at the output: SQLite is lenient and accepted it. That is a SQLite quirk; do not rely on it. Repeat the expression: WHERE price * 2 > 1000.

Connection to the real job

"Top N" is the most common analyst request. In APIs, pagination uses LIMIT/OFFSET or, better for big tables, keyset pagination (WHERE id > last_seen_id ORDER BY id LIMIT 10), which stays fast on deep pages.

Applications

  • Leaderboards and top-N reports
  • Dashboard pagination
  • Listing unique values to profile a column

By role: Data Analytics shows top-N tables; Data Engineering uses keyset pagination for APIs; Logistics lists the slowest deliveries.

COMMON MISTAKE
Using LIMIT without ORDER BY. The "first 5 rows" are then random-ish and may differ between runs. Always sort when you limit.

Check yourself

  1. What does LIMIT 5 OFFSET 10 return?

Answer: Rows 11 to 15 of the sorted result.

  1. Can ORDER BY use a SELECT alias?

Answer: Yes. WHERE cannot.

  1. What does DISTINCT city, name remove?

Answer: Rows where both city and name repeat.

2.4 NULL and Three-Valued Logic

INTUITION
NULL is "I do not know". Is an unknown number equal to another unknown number? You cannot say yes. You cannot say no. The honest answer is "unknown". SQL has three truth values: TRUE, FALSE, UNKNOWN (written NULL). WHERE keeps only TRUE rows.

Words you need

  • NULL: a marker meaning "no value here" (missing or unknown).
  • Three-valued logic: a test can be TRUE, FALSE or UNKNOWN.
  • Aggregate: a function (like SUM) that combines many rows into one value. Chapter 3 teaches these fully.

Real-world mapping

ColumnNULL meansWhere it appears in the job
customers.referrer_idno one referred this customermarketing attribution
orders.couponno coupon useddiscount analysis
a lost parcel's delivery_daysthe parcel never arrivedcourier records

The rules

  • Any comparison with NULL gives UNKNOWN: NULL = NULL, NULL <> 5, NULL > 3 are all UNKNOWN.
  • Test with IS NULL / IS NOT NULL, never = NULL.
  • Logic tables: TRUE AND UNKNOWN = UNKNOWN. FALSE AND UNKNOWN = FALSE. TRUE OR UNKNOWN = TRUE. NOT UNKNOWN = UNKNOWN.
  • Arithmetic with NULL gives NULL: 5 + NULL is NULL.
  • Aggregates (SUM, AVG, COUNT(col)) ignore NULLs. COUNT(*) counts rows.
  • COALESCE(a, b, c) returns the first non-NULL value. NULLIF(a, b) returns NULL if a = b, else a. Great for avoiding divide-by-zero: x / NULLIF(y, 0).
  • DISTINCT and GROUP BY treat all NULLs as the same group. UNIQUE constraints in most databases allow many NULLs.

The truth picture

  AND   | T  F  U         OR    | T  F  U         NOT
  ------+---------        ------+---------        ---------
   T    | T  F  U          T    | T  T  T          T -> F
   F    | F  F  F          F    | T  F  U          F -> T
   U    | U  F  U          U    | T  U  U          U -> U

Worked examples

Problem 2.4.1 Which customers have no referrer? Then show why = NULL fails.

SELECT name FROM customers WHERE referrer_id IS NULL;
name

SELECT name FROM customers WHERE referrer_id = NULL;

  • Answer IS NULL returns Asha, Priya and Sana. = NULL returns nothing, because the test is UNKNOWN for every row.
  • Check The customers table shows NULL in referrer_id for customers 1, 5 and 7: Asha, Priya, Sana.

Problem 2.4.2 The silent loss. How many customers have referrer_id <> 1? Eight customers exist. Two were referred by customer 1 (Ravi and Meena), so you might expect 6.

Step 1Run the query.
Step 2Count again by hand. Three customers have NULL referrer, so their test is UNKNOWN and they vanish.
SELECT name, referrer_id FROM customers WHERE referrer_id <> 1;
name   referrer_id
-----  -----------
John   2          
Kabir  5          
Tom    3
SELECT name, referrer_id FROM customers
WHERE referrer_id <> 1 OR referrer_id IS NULL;

-----  -----------
Asha   NULL       
John   2          
Priya  NULL       
Kabir  5          
Sana   NULL       
Tom    3
  • Answer The first query returns only 3 rows (John, Kabir, Tom). The fixed query returns 6, because NULL rows must be asked for explicitly.
  • Check 3 rows with referrer 2, 5, 3 plus 3 NULL rows is 6. And the 2 customers with referrer 1 are the only ones excluded: 8 - 2 = 6.
  • Meaning Without the NULL clause the query silently dropped three real customers. No error was shown.

Problem 2.4.3 COUNT(*) vs COUNT(col), COALESCE and NULLIF.

SELECT COUNT(*) AS all_orders,
       COUNT(coupon) AS with_coupon,
       COUNT(*) - COUNT(coupon) AS without_coupon
FROM orders;
all_orders  with_coupon  without_coupon
----------  -----------  --------------
14          3            11
SELECT order_id, coupon, COALESCE(coupon, 'NO COUPON') AS coupon_label
FROM orders LIMIT 4;
order_id  coupon  coupon_label
--------  ------  ------------
101       NULL    NO COUPON   
102       SAVE10  SAVE10      
103       NULL    NO COUPON   
104       NULL    NO COUPON

safe_divide  normal_divide
-----------  -------------
NULL         25
  • Check Coupons appear on orders 102, 105 and 110: 3, and 14 - 3 = 11.
  • Answer 14 orders, 3 with coupons, 11 without. COALESCE replaces NULL with a label. NULLIF(0,0) is NULL, so 100 / NULL is NULL instead of an error.
  • Meaning Use COALESCE for display and NULLIF for safe division.

Problem 2.4.4 The NOT IN trap, a famous interview question. Find customers who never referred anyone.

Step 1Natural attempt: customer_id NOT IN (SELECT referrer_id FROM customers).
Step 2The list contains NULL. 5 NOT IN (1, 2, NULL) becomes 5<>1 AND 5<>2 AND 5<>NULL, which is UNKNOWN. No rows pass.
Step 3Fix: filter the NULLs out, or use NOT EXISTS (Chapter 4).
SELECT name FROM customers
WHERE customer_id NOT IN (SELECT referrer_id FROM customers);
(no rows)
SELECT name FROM customers
WHERE customer_id NOT IN (SELECT referrer_id FROM customers WHERE referrer_id IS NOT NULL);
name 
-----
John 
Kabir
Sana 
Tom
  • Answer The first returns zero rows (wrong). The second returns the customers nobody referred: John, Kabir, Sana, Tom (customers 4, 6, 7, 8).

Connection to the real job

Real data is full of NULLs: missing phone numbers, pending shipments, optional fields. Most "my numbers do not add up" bugs are NULL bugs. Always ask: "can this column be NULL, and what should that mean in my metric?"

Applications

  • Data-quality checks (how many NULLs per column)
  • Safe ratio metrics (NULLIF in denominators)
  • Filling missing values before ML (imputation starts with understanding NULL)

By role: Data Analytics writes NULL-safe KPIs; Data Science and ML decides how to impute missing values; Data Engineering adds NOT NULL constraints and NULL-count checks to pipelines.

COMMON MISTAKE
Writing WHERE col <> 'x' and expecting NULL rows to appear. They do not. Add OR col IS NULL, or use IS DISTINCT FROM (PostgreSQL; SQLite spells it IS NOT).

Check yourself

  1. What is NULL = NULL?

Answer: UNKNOWN (NULL), not TRUE.

  1. What does COUNT(col) do with NULLs?

Answer: It skips them. COUNT(*) counts all rows.

  1. What is COALESCE(NULL, NULL, 7)?

Answer: 7.

Chapter recap

  • SELECT chooses columns and can compute new ones; use aliases.
  • Integer division truncates; make one side decimal.
  • WHERE keeps only rows where the test is TRUE.
  • AND binds tighter than OR; use brackets.
  • A table has no order unless you use ORDER BY; always sort before LIMIT.
  • The engine runs FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT, in that order.
  • NULL means unknown; comparisons with NULL are UNKNOWN; use IS NULL.
  • COALESCE fills NULLs; NULLIF prevents divide-by-zero.
  • NOT IN with a NULL in the list returns nothing: a classic trap.

Problem 2.P.9 (interview) Explain why SELECT * FROM t WHERE x NOT IN (SELECT y FROM u) can return zero rows when u.y contains a NULL, and give two fixes. Answer: x NOT IN (...) expands into many <> tests joined by AND. A comparison with NULL is UNKNOWN, so the whole AND is never TRUE. Fixes: add WHERE y IS NOT NULL inside the subquery, or use NOT EXISTS.

Problem 2.P.10 (interview) What is the difference between COUNT(*), COUNT(col) and COUNT(DISTINCT col)? Answer: COUNT(*) counts rows. COUNT(col) counts rows where col is not NULL. COUNT(DISTINCT col) counts distinct non-NULL values. Example on our data: COUNT(*) of customers is 8, COUNT(referrer_id) is 5.
