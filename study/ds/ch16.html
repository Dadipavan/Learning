16.1 Project: Two-stage recommender with NDCG@10 and cold start (#27)

Goal and why employers care. Real recommenders cannot score every item for every user in real time. They use two stages: a fast candidate generator picks about 100 items, then a slower ranker orders them. Building this, measuring it with a ranking metric and handling brand-new items shows you understand how large systems work.

Skills used. Chapter 10, Recommendation, Ranking and Search (retrieval, ranking, NDCG, cold start); Chapter 5, Feature Engineering I (item features); Chapter 4, Statistical Thinking (baselines and fair comparison).

Data. A MovieLens-style table made by the generator: 600 users, 300 items, about 40 ratings per user, ratings 1 to 5 from hidden taste factors plus item popularity. The last 30 items are cold: they have no training interactions. For each user, the 5 highest-rated liked items (rating 4 or 5) are held out as the test. The real MovieLens data (free, with a research licence; read it before use) can replace the generator. Not run here: real MovieLens.

Architecture.

ratings -> train / test (per-user holdout; cold items only in test)
             |
   stage 1:  item-item similarity (70 candidates) + popularity (30)  -> 100 candidates
             |
   stage 2:  ranker = global mean + item bias + user bias + ALS factors
             |                        cold items: item features -> predicted scores
             v
   top 10 -> NDCG@10     (compare: popularity baseline, random cold ranking)

Step-by-step build.

  1. Generate the data. Make interactions depend on taste (exp(1.2 × score)), otherwise popularity wins and no personal model can show value.
  2. Define NDCG@10: reward each relevant item in the top 10 by 1/log2(rank+1), divide by the best possible. Build the popularity baseline first.
  3. Stage 1: cosine similarity between items using the "liked" matrix; for each user sum the similarity to items they liked; add the most popular unseen items so a user with a thin history still gets candidates.
  4. Stage 2: a small matrix-factorisation model by alternating least squares (ALS: fix user factors, solve items by least squares, then swap) on ratings after removing the global mean and biases.
  5. Cold start: fit a Ridge regression from item features to the predicted-score column on warm items, then predict score columns for cold items.
  6. Judge on three views: all test items, warm-only items, and a cold-only ranking.

Before you run it, predict: will the two-stage system beat popularity on all items? On warm items only?

import numpy as np
# Step 1: synthetic MovieLens-style data (users, items, ratings, cold items)
r = np.random.default_rng(11)
U, I, K = 600, 300, 6
uf = r.normal(size=(U,K)); itf = r.normal(size=(I,K))
pop = r.normal(size=I)*0.8
score = uf@itf.T/np.sqrt(K) + pop
# user rates 40 items drawn with popularity bias; rating = 1..5 from score
cold = set(range(I-30, I))                          # last 30 items are cold: no training interactions
rows=[]
for u in range(U):
    pu = np.exp(1.2*score[u]); pu/=pu.sum()
    items = r.choice(I, 40, replace=False, p=pu)
    for i in items:
        rating = int(np.clip(np.round(3+score[u,i]+r.normal(0,.5)),1,5))
        rows.append((u,i,rating))
rows = np.array(rows)
# hold out each user's 5 highest-rated items (relevant = rating>=4) as test; cold items only in test
test=[]; train=[]
for u in range(U):
    ru = rows[rows[:,0]==u]
    rel = ru[(ru[:,2]>=4)]
    t_items = set(rel[:5,1]) if len(rel) else set()
    for (_,i,rt) in ru:
        (test if (i in t_items or i in cold) else train).append((u,i,rt))
test=np.array([x for x in test if x[2]>=4]); train=np.array(train)
print("train", len(train), "test positives", len(test), "cold-item test positives", int(np.isin(test[:,1], list(cold)).sum()))
seen = {u:set(train[train[:,0]==u][:,1]) for u in range(U)}
rel_by_user = {u:set(test[test[:,0]==u][:,1]) for u in range(U)}

# Step 2: metric and popularity baseline
def ndcg_at_k(ranked, relevant, k=10):
    dcg = sum(1/np.log2(i+2) for i,x in enumerate(ranked[:k]) if x in relevant)
    ideal = sum(1/np.log2(i+2) for i in range(min(k,len(relevant))))
    return dcg/ideal if ideal else np.nan
def evaluate(rank_fn, k=10):
    v=[ndcg_at_k(rank_fn(u), rel_by_user[u], k) for u in range(U) if rel_by_user[u]]
    return float(np.nanmean(v))

# baseline: popularity
cnt = np.bincount(train[:,1], minlength=I)
poprank = np.argsort(-cnt)
pop_fn = lambda u: [i for i in poprank if i not in seen[u]]
print("popularity NDCG@10:", round(evaluate(pop_fn),3))

# stage 1: candidate generation = item-item cosine on 'liked' (>=4) matrix, 100 candidates
M = np.zeros((U,I)); M[train[train[:,2]>=4][:,0], train[train[:,2]>=4][:,1]] = 1
norm = np.linalg.norm(M,axis=0)+1e-9
S = (M.T@M)/np.outer(norm,norm)
# Step 3: stage 1, candidate generation (item-item + popularity)
feat = itf + r.normal(0,.5,itf.shape)                   # item content features (noisy)
def candidates(u, n_cf=70, n_pop=30):
    liked = list(np.where(M[u]>0)[0])
    s_ = S[:, liked].sum(axis=1) if liked else np.zeros(I)
    s_ = s_.copy(); s_[list(seen[u])] = -1
    cf = list(np.argsort(-s_)[:n_cf])
    pp = [i for i in poprank if i not in seen[u] and i not in cf][:n_pop]
    return cf + pp
cg_fn = lambda u: candidates(u)
print("candidate gen only NDCG@10:", round(evaluate(cg_fn),3))
recall = np.mean([len(set(candidates(u)) & rel_by_user[u])/len(rel_by_user[u]) for u in range(U) if rel_by_user[u]])
print("candidate recall@100 (item-item + popularity):", round(float(recall),3))

# Step 4: stage 2, ranker (biases + ALS factors): ranker = matrix factorisation by ALS-lite (SVD of mean-centred ratings) blended with popularity
R = np.zeros((U,I)); Mk = np.zeros((U,I))
R[train[:,0],train[:,1]] = train[:,2]; Mk[train[:,0],train[:,1]] = 1
mu = R.sum()/Mk.sum()
bi = ((R-mu)*Mk).sum(0)/(Mk.sum(0)+5)                  # item bias, shrunk
bu = (((R-mu)-bi)*Mk).sum(1)/(Mk.sum(1)+5)             # user bias
def als(Rc, Mk, k=6, lam=8.0, iters=12, seed=0):
    g = np.random.default_rng(seed); P = g.normal(0,.1,(Rc.shape[0],k)); Q = g.normal(0,.1,(Rc.shape[1],k))
    for _ in range(iters):
        for u in range(P.shape[0]):
            m = Mk[u]>0; A = Q[m]; P[u] = np.linalg.solve(A.T@A+lam*np.eye(k), A.T@Rc[u,m])
        for i in range(Q.shape[0]):
            m = Mk[:,i]>0
            if m.any(): A = P[m]; Q[i] = np.linalg.solve(A.T@A+lam*np.eye(k), A.T@Rc[m,i])
    return P, Q
Pf, Qf = als(R-mu-bi-bu[:,None], Mk)
pred = mu + bi[None,:] + bu[:,None] + Pf@Qf.T
# Step 5: cold items: feature -> predicted-score columns learn feature -> predicted-score columns on warm items, apply to cold items
from sklearn.linear_model import Ridge
warm = [i for i in range(I) if i not in cold]; cl = sorted(cold)
W = Ridge(alpha=5).fit(feat[warm], pred[:, warm].T)
pred_full = pred.copy(); pred_full[:, cl] = W.predict(feat[cl]).T
# add a small cold-item content source to candidates
def cands2(u):
    c = candidates(u, 60, 20)
    liked = [i for i in seen[u] if R[u,i]>=4]
    w = feat[liked].mean(axis=0) if liked else np.zeros(K)
    extra = [i for i in np.argsort(-(feat[cl]@w)) ]
    return c + [cl[j] for j in extra[:20]]
def rank_fn(u):
    return sorted(cands2(u), key=lambda i: -pred_full[u,i])
print("two-stage NDCG@10:", round(evaluate(rank_fn),3))
cold_rel = {u: rel_by_user[u] & cold for u in range(U)}
def cold_eval(fn):
    v=[ndcg_at_k(fn(u), cold_rel[u]) for u in range(U) if cold_rel[u]]; return float(np.mean(v)), len(v)
# Step 6: fair view: judge only on warm positives (cold items cannot be found from history)
warm_rel = {u: rel_by_user[u]-cold for u in range(U)}
def warm_eval(fn):
    return float(np.mean([ndcg_at_k(fn(u), warm_rel[u]) for u in range(U) if warm_rel[u]]))
print("warm-only NDCG@10 popularity:", round(warm_eval(pop_fn),3))
print("warm-only NDCG@10 two-stage :", round(warm_eval(rank_fn),3))
# Step 7: cold-start check: rank only the 30 new items for each user who liked some of them
g = np.random.default_rng(0)
rand_fn = lambda u: list(g.permutation(cl))
feat_fn = lambda u: sorted(cl, key=lambda i: -pred_full[u,i])
print("cold-catalogue NDCG@10 random      :", tuple(round(x,3) for x in cold_eval(rand_fn)))
print("cold-catalogue NDCG@10 feature->emb:", tuple(round(x,3) for x in cold_eval(feat_fn)))

popularity NDCG@10: 0.198
candidate gen only NDCG@10: 0.293
candidate recall@100 (item-item + popularity): 0.536

Reading the output. Popularity scores NDCG@10 of 0.198. The candidate stage alone gives 0.293 and the two-stage system 0.297. The ranker adds little overall because 1,944 of the 4,623 test positives are cold items, which stage 1 cannot find from history. On warm items only, the gap is clear: 0.273 for popularity against 0.409 for two-stage. For cold items, ranking the 30 new items with the feature-based predictor gives 0.388, against 0.227 for random order. Candidate recall at 100 is only 0.536, which caps what any ranker can do, so improving stage 1 is the next win. Always report recall of stage 1 and NDCG of stage 2 separately.

Evaluation and acceptance criteria.

  • NDCG@10 of two-stage greater than the popularity baseline on the warm-only view, with the numbers in a table.
  • Candidate recall@100 reported; target above 0.5 here.
  • Cold-catalogue NDCG@10 above the random-order value (0.227 here) by a clear margin.
  • Items the user already saw are never recommended (add a test).

Common pitfalls and how to detect them.

  1. Weak baseline: forgetting popularity. Detect: print it first.
  2. Test items in training: leakage. Detect: assert that no (user, item) pair is in both sets.
  3. Recommending seen items: detect with an assertion.
  4. Evaluating the ranker on a bad candidate list: low recall hides ranker quality. Detect: report recall.
  5. Judging cold start with all-item NDCG: cold items never reach the top 10, so the score is zero. Detect: use a cold-only ranking, as above.

Three extensions.

  1. Replace ALS with a two-tower neural model and compare NDCG (not run here).
  2. Add diversity: limit to 3 items from one category in the top 10 and measure the NDCG cost.
  3. Simulate an online test of the recommender with a click model and size it with your Chapter 15 A/B toolkit.

Interview talking points.

  • Q: Why two stages? A: Scoring every item for every user is too slow. A cheap first stage picks a few hundred plausible items and a richer second stage orders them.
  • Q: How do you handle a new item with no ratings? A: Use its features (genre, text, price) to predict how users would score it, mix in some exploration, and switch to behaviour data as it arrives.
  • Q: Why can NDCG go up offline and fail online? A: Offline data only shows what users saw before. The model may favour popular items, and real users react to the new list differently, so you confirm with an A/B test.

16.2 Project: Credit-risk scorecard with WoE, KS, Gini and PSI (#28)

Goal and why employers care. Banks still rely on scorecards: a points table that anyone can audit. Building one proves you can bin variables safely, fit a logistic model, measure separation (KS, Gini), convert to points and monitor drift (PSI). It is a classic of regulated data science.

Skills used. Chapter 5, Feature Engineering I (binning and encoding); Chapter 11, Applied Domains (credit risk); Chapter 12, From Prediction to Decision (cut-offs); Chapter 13, Communication, Stakeholders, Ethics, Reproducibility and Taking Work to Production (monitoring and explainability).

Data. The generator makes 30,000 loan applicants with age, income, credit utilisation and number of past late payments, and a default flag (bad, 12.5%) from a known formula. A free real alternative is a public credit-default file; check its licence. Note that fairness rules apply to real credit data; do not use protected attributes.

Architecture.

applicants -> first 20,000 train / last 10,000 test
   |
   v
bin each variable (quantile bins, rule for late payments)
   |
   v
WoE per bin = ln(share of goods / share of bads);  IV = sum (diff of shares x WoE)
   |
   v
logistic regression on WoE columns -> probability of bad
   |
   v
points = offset + factor x ln(odds good)   ->  KS, Gini, PSI

Step-by-step build.

  1. Split in a fixed order (train earlier, test later), like a real lending timeline.
  2. For each variable, make about 5 bins from the training data only, count goods and bads per bin (add 0.5 to avoid log of zero), and compute WoE and IV. A common rule: IV below 0.02 is useless, 0.1 to 0.3 medium, above 0.3 strong. Here the IVs are modest.
  3. Replace each value with its bin's WoE and fit logistic regression. Because WoE already points the right way, the coefficients should be near -1 (the sign comes from modelling bad as 1 while WoE is defined with goods on top).
  4. Report AUC, Gini = 2 × AUC − 1 and KS (the biggest gap between the score distributions of bad and good customers).
  5. Scale to points: 600 points at odds 50 to 1, and 20 points to double the odds (PDO = 20).
  6. Compute PSI (population stability index): Σ (actual% − expected%) × ln(actual% / expected%) across 10 score bins, for the test set and for a drifted applicant group.
import numpy as np, pandas as pd
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import roc_auc_score
from scipy.stats import ks_2samp

def make_loans(n=30000, seed=5, shift=0.0):
    r = np.random.default_rng(seed)
    age = np.clip(r.normal(40+shift*8,11,n),21,70).round()
    income = r.lognormal(10.6-0.15*shift,0.5,n).round(-2)
    util = np.clip(r.beta(2,3,n)+0.1*shift,0,1.2).round(2)
    late = r.poisson(0.5+0.4*shift,n)
    z = -3.2 - 0.025*(age-40) - 0.6*np.log(income/40000) + 2.0*util + 0.55*late
    bad = (r.random(n) < 1/(1+np.exp(-z))).astype(int)
    return pd.DataFrame(dict(age=age,income=income,util=util,late=late,bad=bad))
# Step 1: data and split
df = make_loans(); print("bad rate", round(df.bad.mean(),3))
train = df.iloc[:20000].copy(); test = df.iloc[20000:].copy()

# Step 2: WoE / IV
def woe_table(x, y, edges):
    b = pd.cut(x, edges, include_lowest=True)
    g = pd.crosstab(b, y).rename(columns={0:"good",1:"bad"}) + 0.5     # smoothing avoids log(0)
    g.columns.name=None
    g["dist_good"]=g.good/g.good.sum(); g["dist_bad"]=g.bad/g.bad.sum()
    g["woe"]=np.log(g.dist_good/g.dist_bad)
    g["iv"]=(g.dist_good-g.dist_bad)*g.woe
    return g
def quant_edges(x, k=5): return sorted(set(np.quantile(x, np.linspace(0,1,k+1))))
edges = {c: quant_edges(train[c]) for c in ["age","income","util"]}
edges["late"] = [-0.5,0.5,1.5,2.5,99]
ivs = {}
for c,e in edges.items():
    t = woe_table(train[c], train.bad, e); ivs[c] = t.iv.sum()
print("IV:", {k: round(float(v),3) for k,v in ivs.items()})
print(woe_table(train["util"], train.bad, edges["util"]).round(3)[["good","bad","woe","iv"]])

# Step 3: model on WoE features
def to_woe(d):
    out = pd.DataFrame(index=d.index)
    for c,e in edges.items():
        t = woe_table(train[c], train.bad, e)["woe"]
        b = pd.cut(d[c].clip(e[0], e[-1]), e, include_lowest=True)
        out[c] = b.map(t).astype(float)
    return out
Xtr, Xte = to_woe(train), to_woe(test)
m = LogisticRegression(C=1.0, max_iter=1000).fit(Xtr, train.bad)
print("coefs:", dict(zip(Xtr.columns, [round(float(c),2) for c in m.coef_[0]])))
ptr, pte = m.predict_proba(Xtr)[:,1], m.predict_proba(Xte)[:,1]
def ks(y,p): return ks_2samp(p[y==1], p[y==0]).statistic
for nm,y,p in [("train",train.bad,ptr),("test",test.bad,pte)]:
    auc=roc_auc_score(y,p); print(f"{nm}: AUC={auc:.3f} Gini={2*auc-1:.3f} KS={ks(y.values,p):.3f}")

# Step 4: points; Step 5: PSI: score = 600 + 20/ln2*ln(odds_good) , PDO=20, base odds 50:1 at 600
pdo, base, odds0 = 20, 600, 50
factor = pdo/np.log(2); offset = base - factor*np.log(odds0)
def score(p_bad): return offset + factor*np.log((1-p_bad)/p_bad)
s_tr, s_te = score(ptr), score(pte)
print("score range test:", int(s_te.min()), int(s_te.max()), "mean", round(s_te.mean(),1))

def psi(expected, actual, edges):
    e = np.histogram(expected, edges)[0]/len(expected); a = np.histogram(actual, edges)[0]/len(actual)
    e, a = np.clip(e,1e-4,None), np.clip(a,1e-4,None)
    return float(np.sum((a-e)*np.log(a/e)))
sedges = np.quantile(s_tr, np.linspace(0,1,11)); sedges[0]-=1; sedges[-1]+=1
print("PSI train vs test:", round(psi(s_tr, s_te, sedges),4))
drift = make_loans(10000, seed=9, shift=1.0)
s_dr = score(m.predict_proba(to_woe(drift))[:,1])
print("PSI train vs drifted applicants:", round(psi(s_tr, s_dr, sedges),3))

Reading the output. Late payments carry the most information (IV 0.197) and utilisation next (0.142), matching the generator. In the utilisation table WoE falls steadily from +0.580 for the lowest-use bin to -0.539 for the highest: a clean, monotonic pattern that an auditor can read. All four coefficients are near -1, as expected. Train Gini is 0.383 and test Gini is 0.342, KS 0.283 versus 0.247. A small drop is normal; a large drop means overfitting. Cut-offs for PSI are conventions, not laws.

Evaluation and acceptance criteria.

  • Test Gini within 0.05 of train Gini.
  • WoE monotonic for the main continuous variables, or a written reason when it is not.
  • KS and Gini reported on train and test.
  • PSI computed monthly in a monitor.py function; alert level written in the README.
  • Points table exported as a CSV a non-technical reader can follow.

Common pitfalls and how to detect them.

  1. Bins fitted on all data: leaks the test set. Detect: code review; fit bins on train only, as here.
  2. Zero count in a bin: infinite WoE. Detect: min count per bin; add smoothing.
  3. Non-monotonic WoE ignored: confusing for a reviewer. Detect: print WoE per bin.
  4. Good Gini but bad calibration: separation is not the same as correct probabilities. Detect: compare predicted and actual bad rate by score band.
  5. Reject inference ignored: you only see outcomes for approved loans. Detect: ask how the data was selected; say it in the limits.

Three extensions.

  1. Compare with gradient boosting and report the Gini gap; discuss the value of explainability.
  2. Add an approval cut-off from a cost table: loss from a bad loan versus profit from a good one (Chapter 12).
  3. Add a characteristic stability index (PSI per variable) to find which input drifted.

Interview talking points.

  • Q: What is WoE and why use it? A: Weight of evidence turns each bin into a number that says how much it favours good over bad customers. It handles missing values, outliers and non-linear effects, and keeps the model easy to audit.
  • Q: KS versus Gini? A: Both measure how well the score separates bad from good. Gini is a rescaled AUC over all thresholds. KS is the single best gap at one threshold. A model can have both a good Gini and a poor business cut-off.
  • Q: What does PSI of 0.17 mean? A: The score distribution of today's applicants differs noticeably from the build sample. I would check which inputs moved, and re-validate the model before trusting it.

16.3 Project: Causal analysis with propensity scores and difference-in-differences (#30)

Goal and why employers care. Many business questions ("did the loyalty club raise spending?") cannot be tested with a coin flip. Employers want to see that you know the difference between correlation and effect, that you can use two standard tools, and, most of all, that you test your own answer for weak spots.

Skills used. Chapter 8, Causal Inference When You Cannot Randomise (confounding, propensity scores, difference-in-differences); Chapter 4, Statistical Thinking: Ways Data Fools You; Chapter 7, Experimentation (what the ideal test would be).

Data. Two generators in one script. Part A: 20,000 shoppers, where "engagement" drives both joining a loyalty club and spending, and the true effect of joining is +10. We observe only a noisy proxy (prior spend) and age. Part B: 20 cities over 12 months; 10 get free delivery from month 7 with a true effect of +8 orders per 1,000 customers. Real data alternatives: public policy-evaluation datasets; check licences.

Architecture.

Part A (observational):  naive difference -> propensity model -> balance check (SMD)
                         -> IPW estimate + bootstrap CI -> sensitivity: hide confounder
Part B (panel):          2x2 means -> DiD -> city-level bootstrap CI
                         -> placebo test + pre-trend check

Step-by-step build.

  1. Compute the naive difference in means. It is wrong when joiners differ from non-joiners.
  2. Fit logistic regression for the chance of joining from the observed covariates (the propensity score). Check overlap (both groups have similar score ranges) and covariate balance with the standardised mean difference (SMD = gap in means divided by pooled spread; below 0.1 is the common target).
  3. Estimate the effect with inverse-probability weighting (IPW): weight treated people by 1/ps and others by 1/(1−ps). Trim extreme scores. Bootstrap a confidence interval.
  4. Sensitivity: remove the best covariate and see how far the answer moves. This shows what hidden confounding would do.
  5. DiD: compute the change over time in treated cities minus the change in control cities.
  6. Uncertainty: resample cities, not rows, because rows in one city are not independent.
  7. Placebo and pre-trend: pretend the policy began earlier, using pre-period data only, and compare pre-period slopes.
import numpy as np, pandas as pd
from sklearn.linear_model import LogisticRegression, LinearRegression

# Step 1: data: propensity scores. Treatment = joined loyalty club; outcome = spend next 3 months. True effect = +10
r = np.random.default_rng(21); n = 20000
engage = r.normal(size=n); age = r.normal(40,10,n); prior = 50 + 15*engage + r.normal(0,10,n)
p_join = 1/(1+np.exp(-(-1.0 + 1.2*engage + 0.02*(age-40))))
T = (r.random(n) < p_join).astype(int)
Y = 60 + 12*engage + 0.3*(age-40) + 10*T + r.normal(0,15,n)
df = pd.DataFrame(dict(engage=engage, age=age, prior=prior, T=T, Y=Y))
print("naive diff:", round(df.Y[df['T']==1].mean()-df.Y[df['T']==0].mean(),2), "(true effect 10)")

# Step 2: propensity score and balance observe: prior spend (proxy of engagement) and age
Xc = df[["prior","age"]]
Xs = (Xc-Xc.mean())/Xc.std()
ps = LogisticRegression().fit(Xs, df['T']).predict_proba(Xs)[:,1]
df["ps"]=ps
print("propensity range treated:", df.ps[df['T']==1].quantile([.01,.99]).round(2).tolist(), "control:", df.ps[df['T']==0].quantile([.01,.99]).round(2).tolist())
def smd(x, t):
    a,b = x[t==1], x[t==0]; return (a.mean()-b.mean())/np.sqrt((a.var()+b.var())/2)
print("SMD before:", {c: round(float(smd(df[c], df['T'])),2) for c in ["prior","age"]})
# Step 3: IPW with trimming
d = df[(df.ps>0.02)&(df.ps<0.98)]
w = np.where(d['T']==1, 1/d.ps, 1/(1-d.ps))
ate = np.average(d.Y[d['T']==1], weights=w[d['T']==1]) - np.average(d.Y[d['T']==0], weights=w[d['T']==0])
print("IPW ATE:", round(ate,2))
def wsmd(x,t,w):
    m1=np.average(x[t==1],weights=w[t==1]); m0=np.average(x[t==0],weights=w[t==0])
    return (m1-m0)/np.sqrt((x[t==1].var()+x[t==0].var())/2)
print("SMD after weighting:", {c: round(float(wsmd(d[c].values, d['T'].values, w)),2) for c in ["prior","age"]})
# bootstrap CI
bs=[]
g=np.random.default_rng(0)
for _ in range(200):
    s=d.sample(len(d), replace=True, random_state=int(g.integers(1e9)))
    ww=np.where(s['T']==1,1/s.ps,1/(1-s.ps))
    bs.append(np.average(s.Y[s['T']==1],weights=ww[s['T']==1])-np.average(s.Y[s['T']==0],weights=ww[s['T']==0]))
print("bootstrap 95% CI:", np.round(np.percentile(bs,[2.5,97.5]),2).tolist())
# Step 4: sensitivity the proxy (hidden confounder) -> estimate with age only
Xa = ((df[["age"]]-df.age.mean())/df.age.std())
pa = LogisticRegression().fit(Xa, df['T']).predict_proba(Xa)[:,1]
wa = np.where(df['T']==1,1/pa,1/(1-pa))
ate_h = np.average(df.Y[df['T']==1],weights=wa[df['T']==1]) - np.average(df.Y[df['T']==0],weights=wa[df['T']==0])
print("IPW with engagement hidden (age only):", round(ate_h,2))

# Step 5: DiD data: difference-in-differences. 20 cities, 10 get free delivery from month 7. true effect = +8 orders/1000 customers
r = np.random.default_rng(4)
rows=[]
for c in range(20):
    treated = int(c<10); base = 100 + 5*r.normal() + (6 if treated else 0)   # treated cities start higher (levels differ: fine)
    for m in range(12):
        post = int(m>=6)
        y = base + 1.5*m + 8*treated*post + r.normal(0,2)
        rows.append((c,m,treated,post,y))
p = pd.DataFrame(rows, columns=["city","month","treated","post","y"])
means = p.groupby(["treated","post"]).y.mean().unstack()
print(means.round(2))
did = (means.loc[1,1]-means.loc[1,0]) - (means.loc[0,1]-means.loc[0,0])
print("DiD estimate:", round(did,2))
# Step 6: uncertainty with city-clustered bootstrap
def did_est(q):
    mm = q.groupby(["treated","post"]).y.mean().unstack(); return (mm.loc[1,1]-mm.loc[1,0])-(mm.loc[0,1]-mm.loc[0,0])
g=np.random.default_rng(1); est=[]
for _ in range(500):
    cs_t = g.choice(range(10),10); cs_c = g.choice(range(10,20),10)
    q = pd.concat([p[p.city==c] for c in list(cs_t)+list(cs_c)])
    est.append(did_est(q))
print("cluster bootstrap 95% CI:", np.round(np.percentile(est,[2.5,97.5]),2).tolist())
# Step 7: placebo and pre-trend pretend treatment began at month 3, use only pre months 0-5
pre = p[p.month<6].copy(); pre["post"]=(pre.month>=3).astype(int)
print("placebo DiD (fake start month 3, pre-data only):", round(did_est(pre),2))
# parallel-trend check: slope of pre-period by group
for tr in [1,0]:
    q = p[(p.treated==tr)&(p.post==0)].groupby("month").y.mean()
    print("pre-trend slope treated=%d:"%tr, round(np.polyfit(q.index,q.values,1)[0],2))

Reading the output. The naive difference is 21.74, more than double the truth (10). Before weighting, prior spend differs between groups by 0.87 SMD; after weighting both SMDs are about 0. Even so, the IPW estimate is 14.02 with a CI of 13.36 to 14.74, which excludes the truth of 10. Balance on what we measured did not remove bias, because prior spend is only a noisy proxy for engagement. This is the key lesson: good balance does not prove there is no hidden confounder. In the sensitivity run, using age alone gives 21.26, nearly the naive number, which shows how much the proxy mattered. DiD gives 8.25 (true 8), with a city-bootstrap CI of 7.54 to 8.88. The placebo effect is 0.13, close to 0, and pre-trend slopes are 1.60 and 1.53: parallel. The treated cities start higher, and DiD does not mind, because it uses changes.

Evaluation and acceptance criteria.

  • Report naive, adjusted and true (for synthetic data) side by side.
  • SMD after weighting below 0.1 for all observed covariates; overlap plot shown.
  • DiD placebo effect within its CI of zero; pre-trend slopes within 0.2 of each other.
  • A written paragraph naming at least two unmeasured confounders and which direction each would bias the result.
  • Cluster-level resampling used for panel data.

Common pitfalls and how to detect them.

  1. Conditioning on a post-treatment variable: detect by drawing the timeline; only use pre-treatment covariates.
  2. No overlap: some people have almost no chance of treatment. Detect: histogram of scores by group; trim.
  3. Treating balance as proof: detect with sensitivity analysis, as in step 4.
  4. Parallel trends assumed, not checked: detect with pre-period slopes and a placebo.
  5. Row-level standard errors in a panel: intervals too narrow. Detect: compare with a city-level bootstrap.

Three extensions.

  1. Add propensity-score matching and doubly robust estimation and compare all estimates.
  2. Add an event-study plot with an effect for each month before and after.
  3. Add an E-value or similar sensitivity measure (not run here) and explain it in one paragraph.

Interview talking points.

  • Q: Why not just compare joiners with non-joiners? A: Joiners are different: more engaged people join and also spend more. The gap mixes the effect of the club with the effect of who joins.
  • Q: What does difference-in-differences assume? A: That without the policy, treated and control groups would have moved in parallel. I check pre-period trends and a placebo date, but I can never prove it.
  • Q: Your adjusted estimate is still off. How would you tell? A: In real data I cannot see the truth. I would remove covariates one at a time, compare methods and ask how strong a hidden confounder must be to erase the result. Then I would say what experiment would settle it.

16.4 Worked Debugging Problems and Marking Guide

Each project in this chapter has a classic failure that produces a flattering number. Here are three, with a test that catches each. Spot the bug first, then read the steps.

INTUITION
Ask of every number: "which rows and which dates did this calculation see?" Metrics break when the evaluation sees information the real system will not have, or when the formula quietly changes the target.

Problem 16.4.1 (recommender, wrong NDCG) A user has 3 relevant items in the catalogue. Your ranked top 5 has relevance [0, 1, 0, 1, 0]. The code reports NDCG@5 of 0.651. Is that right?

FormulaDCG = Σ rel / log2(rank + 1). Ideal DCG is the DCG of the best possible top 5 for that user, using ALL their relevant items.
DCGRank 2: 1/log2(3) = 0.6309. Rank 4: 1/log2(5) = 0.4307. Sum 1.0616.
Wrong idealSorting the shown list gives [1, 1, 0, 0, 0]: 1 + 0.6309 = 1.6309. NDCG 1.0616 / 1.6309 = 0.651.
Right idealThree relevant items fit in the top 5: 1 + 0.6309 + 0.5 = 2.1309. NDCG 1.0616 / 2.1309 = 0.498.
import numpy as np
def dcg(rels): return sum(r / np.log2(i + 2) for i, r in enumerate(rels))
shown = [0, 1, 0, 1, 0]            # relevance of the 5 items we ranked
total_relevant = 3                 # the user actually has 3 relevant items in the catalogue
wrong_ideal = dcg(sorted(shown, reverse=True))
right_ideal = dcg([1] * min(total_relevant, 5))
print("DCG@5:", round(dcg(shown), 4))
print("wrong ideal (sorts the shown list):", round(wrong_ideal, 4), " NDCG", round(dcg(shown) / wrong_ideal, 3))
print("right ideal (all relevant items):  ", round(right_ideal, 4), " NDCG", round(dcg(shown) / right_ideal, 3))
DCG@5: 1.0616
wrong ideal (sorts the shown list): 1.6309  NDCG 0.651
right ideal (all relevant items):   2.1309  NDCG 0.498
  • Step 1 The bug inflates NDCG from 0.498 to 0.651 because the ideal list was built only from items the system chose to show. A system that retrieves poorly looks good.
  • Step 2 The test: a ranking that shows none of the user's relevant items must score 0, and a perfect one must score 1 regardless of what is retrieved.
COMMON MISTAKE
Computing the ideal from the retrieved list. Candidate generation errors then disappear from your metric. Ideal DCG must come from the ground truth, truncated to k.

Problem 16.4.2 (scorecard, leakage through binning) A noise feature with no relationship to default is cut into 60 quantile bins, WoE is computed, and the score is tested on a held-out set. Gini is 0.435. Real or leak?

SuspectWere the bins and WoE values learned on all 1,000 rows before the split? Then each held-out row's WoE was computed partly from its own label.
TestLearn bins and WoE on training rows only, then apply them to the held-out rows.
RuleAnything that learns from labels (WoE, target encoding, binning for IV) belongs inside the training fold.
import numpy as np
from sklearn.metrics import roc_auc_score
rng = np.random.default_rng(15)
n = 1000
x = rng.normal(size=n)                                   # a pure-noise feature
y = (rng.random(n) < 0.2).astype(int)                    # labels unrelated to x
idx = rng.permutation(n); tr, te = idx[:600], idx[600:]
def woe_map(x_fit, y_fit, bins=60):
    edges = np.quantile(x_fit, np.linspace(0, 1, bins + 1)); edges[0], edges[-1] = -np.inf, np.inf
    b = np.digitize(x_fit, edges[1:-1])
    g = np.bincount(b, weights=1 - y_fit, minlength=bins) + 0.5
    bd = np.bincount(b, weights=y_fit, minlength=bins) + 0.5
    return edges, np.log((g / g.sum()) / (bd / bd.sum()))
def apply(x_new, edges, woe): return woe[np.digitize(x_new, edges[1:-1])]
# bug: WOE learned from ALL rows, then evaluated on the test rows
e_all, w_all = woe_map(x, y)
leaky = roc_auc_score(y[te], -apply(x[te], e_all, w_all))
e_tr, w_tr = woe_map(x[tr], y[tr])
honest = roc_auc_score(y[te], -apply(x[te], e_tr, w_tr))
print("test AUC with WOE fitted on all rows (leak):", round(leaky, 3), " Gini", round(2*leaky - 1, 3))
print("test AUC with WOE fitted on train only:     ", round(honest, 3), " Gini", round(2*honest - 1, 3))
test AUC with WOE fitted on all rows (leak): 0.718  Gini 0.435
test AUC with WOE fitted on train only:      0.542  Gini 0.083
  • Step 1 The leaky Gini is 0.435 on a feature that is pure noise. The honest Gini is 0.083, which is just small-sample luck.
  • Step 2 More bins and smaller samples make this leak bigger. With 60 bins and about 17 rows per bin, each bin's WoE mostly memorises its own labels.

Problem 16.4.3 (causal project, parallel trends fail) A pilot region has been growing faster than the control region even before launch. The true effect of the launch is +4. Show that the plain DiD overstates it and what to do.

Step 1Plot or fit the gap between treated and control in the pre-period. If it trends, parallel trends fail.
Step 2The plain DiD attributes the pre-existing extra growth to the launch.
Step 3Option: extrapolate the pre-period gap trend and subtract it. This relies on the trend continuing, which is its own assumption.
import numpy as np
rng = np.random.default_rng(13)
T, T0 = 16, 10
t = np.arange(T)
ctrl = 100 + 1.0*t + rng.normal(0, 0.5, T)
treat = 110 + 2.0*t + rng.normal(0, 0.5, T)                  # already growing faster BEFORE launch
treat[T0:] += 4.0                                            # true effect 4
pre_gap = (treat - ctrl)[:T0]
slope = np.polyfit(t[:T0], pre_gap, 1)[0]
did = (treat[T0:].mean() - treat[:T0].mean()) - (ctrl[T0:].mean() - ctrl[:T0].mean())
print("pre-period gap slope per period:", round(slope, 3), "(should be about 0)")
print("naive DiD estimate:", round(did, 2), " true effect: 4.0")
# fix: allow a group-specific linear trend estimated on the pre-period
cf = np.polyval(np.polyfit(t[:T0], treat[:T0] - ctrl[:T0], 1), t[T0:])
est = ((treat - ctrl)[T0:] - cf).mean()
print("trend-adjusted estimate:", round(est, 2))
pre-period gap slope per period: 1.091 (should be about 0)
naive DiD estimate: 11.83  true effect: 4.0
trend-adjusted estimate: 3.1
  • Step 1 The pre-launch gap grows by 1.09 per period, so the "should be about 0" check fails.
  • Step 2 The plain DiD returns 11.83, nearly three times the truth of 4.
  • Step 3 The trend-adjusted estimate is 3.10. It is much closer, but extrapolating a noisy slope adds error. Report both, with the pre-trend check, and prefer a better control group or a synthetic control when you can build one.
KEY IDEA
A causal estimate is only as good as its pre-launch diagnostics. Publish the pre-trend plot and the placebo test next to the headline number.

Chapter recap

  • Two-stage recommenders pair a fast candidate generator with a better ranker; report recall for stage 1 and NDCG for stage 2.
  • Compare with popularity; judge warm and cold items separately; test cold start with a cold-only ranking.
  • A scorecard is bins, WoE, logistic regression and points; every step is auditable.
  • Gini and KS measure separation; PSI measures drift; none of them measures calibration.
  • Fit bins on training data only; watch zero counts and non-monotonic WoE.
  • Naive group comparisons overstate effects when the groups differ.
  • Propensity weighting fixes imbalance on measured variables only; test with sensitivity runs.
  • DiD needs parallel trends; check pre-trends and a placebo, and resample units, not rows.

Practice set

1. (easy) A relevant item appears at ranks 1 and 3 of the top 10; the user has 2 relevant items in total. Compute NDCG@10. Answer: DCG = 1/log2(2) + 1/log2(4) = 1 + 0.5 = 1.5. Ideal = 1 + 1/log2(3) = 1.631. NDCG = 1.5/1.631 = 0.920.

2. (easy) A bin holds 60% of goods and 30% of bads. Compute its WoE and its IV contribution. Answer: WoE = ln(0.6/0.3) = ln 2 = 0.693. IV = (0.6 − 0.3) × 0.693 = 0.208.

3. (easy) Treated sales went from 100 to 110; control from 90 to 95. DiD estimate? Answer: (110 − 100) − (95 − 90) = 5.

4. (medium) Score is 600 at odds 50 to 1 with PDO of 20. What score has odds 100 to 1? Answer: doubling the odds adds 20 points, so 620.

5. (medium) Expected score share per bin is [0.5, 0.5]; today it is [0.6, 0.4]. Compute PSI. Answer: 0.1 × ln(1.2) + (−0.1) × ln(0.8) = 0.0182 + 0.0223 = 0.0405. Below 0.1, stable.

6. (find the bug) A scorecard builder computes quantile bins and WoE on the full dataset, then splits into train and test. Test Gini is 0.40, but production Gini is 0.31. Why? Answer: the bins and WoE values saw the test labels, which leaked information. Fit bins and WoE on training data only.

7. (scenario) After weighting, SMD for all measured covariates is below 0.05, and a manager says the estimate is causal. Reply. Answer: balance holds only on measured variables. Ask about unmeasured drivers, show what happens when a covariate is dropped, report a sensitivity analysis and say what test would confirm it.

8. (interview) "Your recommender has NDCG@10 of 0.30 offline. Why might a live test show no gain?" Answer: offline data reflects past exposure, so the metric rewards items users already saw. Candidate recall may be limited, popularity may already capture most gain and users react to new lists. Run an A/B test with a pre-set sample size and guardrails.

9. (medium) A ranker retrieves only 1 of a user's 4 relevant items, at rank 1. Compute NDCG@5 correctly. Answer: DCG = 1. Ideal DCG at k = 5 with 4 relevant items = 1 + 0.6309 + 0.5 + 0.4307 = 2.5616. NDCG = 1 / 2.5616 = 0.390. A buggy ideal built from the shown list would give 1.0 and hide the missed items.

10. (hard) Pre-launch trends differ and the trend-adjusted DiD gives 3.1 while the plain DiD gives 11.8. Which do you report to the board? Answer: Report the adjusted estimate as the main figure, show the plain DiD and the pre-trend plot, and state that the adjustment assumes the pre-period trend gap would have continued. Offer a synthetic control or a holdout in the next rollout to remove that assumption.
