Reading about data science does not make you hireable. A finished project does: one that a stranger can open, rerun, understand in five minutes, and trust. This chapter gives you eight capstone briefs. Each brief says what business question to answer, what data to use, what to deliver, and, most important, the acceptance criteria: checks that are either passed or failed, so you know when you are done. After the projects comes an interview bank. For each common question you get the key points of a strong answer and, where numbers are involved, a worked and verified calculation. By the end you will have a plan for a portfolio of three to four finished projects and a set of answers you can say aloud.

14.1 How to Run a Capstone: Definition of Done and the Baseline Gate

INTUITION
A building inspection is "done" when the report answers: is it safe, what must be repaired, what does it cost? Not when the inspector has walked through every room. A data science project is the same. It is done when the decision is answered, the result beats the simple alternative, and someone else can rerun it.

Words you need.

WordMeaningExample
BriefOne page that states the problem, data, metric, baseline, risks (Chapter 1)Capstone 3 brief
Acceptance criterionA pass/fail check written before you start"Model AUC beats recency rule with CI above 0"
Baseline gateThe rule that your model must beat the simple baseline, or you ship the baselineRecency rule AUC
DeliverableA file someone else will read or runMemo, notebook, model card
Stretch goalExtra credit after all acceptance criteria passA Streamlit demo

The standard folder and the five deliverables. Every capstone uses the folder from Chapter 13.4 (README, requirements.txt, Makefile, config, src/, tests/, reports/). Five deliverables are common to all eight projects:

  1. A one-page brief written first (problem, decision, metric, baseline, risks, timeline).
  2. A memo with the answer first (Chapter 13.1).
  3. A rerunnable pipeline (one command; seeds, pinned environment).
  4. A model card or analysis card with limits and monitoring plan.
  5. A 5-minute talk without formulas (record yourself).

The baseline gate, run for real. Before you call any model a success, ask whether it beats the simple rule. We test this on the shop churn data (Chapter 1; from ds_common import *). The baseline is "rank by days since last order". The model is logistic regression on four features. Same split of 1,700 train and 862 test customers, AUC on the test part, and a bootstrap of the difference (1,000 resamples).

from ds_common import *
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import roc_auc_score
customers, orders = make_data()
d = make_label_table(customers, orders)
past = orders[orders.order_ts < PRED_DATE]
g = past.groupby("customer_id").agg(last=("order_ts", "max"), f=("order_id", "count"))
d = d.merge(g, left_on="customer_id", right_index=True)
d["rec"] = (PRED_DATE - d["last"]).dt.days; d["logf"] = np.log1p(d.f)
d["pro"] = (d.plan == "pro").astype(int); d["ads"] = (d.channel == "ads").astype(int)
idx = np.random.default_rng(0).permutation(len(d)); tr, te = idx[:1700], idx[1700:]
y = d.churn.values; X = d[["rec", "logf", "pro", "ads"]].values
mu, sd = X[tr].mean(0), X[tr].std(0)
lr = LogisticRegression().fit((X[tr] - mu) / sd, y[tr])
pt = lr.predict_proba((X[te] - mu) / sd)[:, 1]; rt = d.rec.values[te]; yt = y[te]
base, model = roc_auc_score(yt, rt), roc_auc_score(yt, pt)
print("baseline recency AUC", round(base, 3), "model", round(model, 3), "gain", round(model - base, 3))
rng = np.random.default_rng(1); gains = []
for _ in range(1000):
    i = rng.integers(0, len(te), len(te))
    gains.append(roc_auc_score(yt[i], pt[i]) - roc_auc_score(yt[i], rt[i]))
print("gain 95% CI", np.percentile(gains, [2.5, 97.5]).round(3))

Before you run it: do you expect the four-feature model to beat the one-line rule?

baseline recency AUC 0.884 model 0.878 gain -0.006
gain 95% CI [-0.016  0.005]
  • Answer The model does not beat the recency rule. The gain is −0.006 and the interval, −0.016 to +0.005, contains zero. The honest conclusion is "no evidence the model improves ranking".
  • Check Chapter 1 reported the same pattern: a one-line rule almost matches ML on this data. Here we measured it with an interval.
  • Why it matters A capstone whose acceptance criterion is "beats the baseline" may fail it, and that is a valid, publishable result. Reporting "I tried, here is the interval, ship the rule" shows more judgment than a model that was never compared. (The model can still be useful for other reasons: calibrated probabilities for the cost analysis of Chapter 12.)

Problem 14.1.1 Write three acceptance criteria for a churn capstone, so that each is a pass/fail check.

Step 1Pick a measurable claim about performance: "On the out-of-time test set, AUC is reported with a 95% bootstrap interval, compared with the recency baseline."
Step 2Pick a measurable claim about the decision: "The memo gives profit at the cost-based threshold, with a Monte Carlo range and P(loss)."
Step 3Pick a measurable claim about delivery: "Deleting models/ and reports/ and running make report reproduces the numbers within rounding."
AnswerCriteria: (1) AUC with interval against baseline; (2) profit with range and P(loss); (3) one-command reproduction.
CheckEach can be answered yes or no by a reviewer in two minutes. "The model is good" cannot.
Why it mattersWriting criteria before coding stops you from moving the goalposts after you see the results.

Time budget. Each capstone is about 15 to 25 study hours, roughly 3 to 4 weeks at one hour per day. Do three to four properly instead of eight badly. A good order for most learners: 3, 2, 7, then the rest, choosing the domain you want to work in.

Connection to the job. Hiring managers open the README, the memo and the first notebook, in that order. Many reject a repository within a minute if there is no README, no results table, or no clear question.

Applications

  • Job search: portfolio pieces for data science, analytics and ML roles.
  • Interview prep: each project becomes a 3-minute story (problem, approach, result, limit).
  • Team work: the same folder structure is used in real projects.
COMMON MISTAKE
Starting with a Kaggle dataset and the sentence "predict the target". Without a decision, a cost and a baseline, the project cannot be judged. Start from the brief.

Check yourself

  1. What do you do if your model does not beat the baseline? Answer: Report it honestly with the interval, and recommend the simpler baseline or find a new signal.
  2. Why write acceptance criteria before the work? Answer: So the result cannot quietly redefine success.
  3. How many capstones should you finish? Answer: Three or four, done properly, beat eight half-done.

14.2 Capstones 1 to 4: Analysis, Experiment, Churn Decision, Forecast

INTUITION
These four are the "core" projects: understand data and write a memo, design and judge an experiment, turn a prediction into a decision, and forecast with honest backtesting. If you finish only these four, you cover most of what a data science interview tests.

Each brief below has the same shape: Question, Data, Deliverables, Acceptance criteria, Stretch, Pitfalls, Chapters used.

Capstone 1: EDA and business recommendations on a messy dataset

  • Question "What should the business change, based on this data?" Choose a messy real dataset (public e-commerce, transactions, ride or listing data) or the shop dataset with injected problems from Chapter 2.
  • Data At least 50,000 rows, at least 8 columns, with missing values, duplicates and odd codes.
  • Deliverables An EDA notebook that someone else can rerun, plus a 2-page memo with 3 findings in the form hypothesis, evidence, so what (Chapter 3.4).
  • Acceptance criteria
    1. A data-quality table: nulls by column and segment, duplicates, impossible values, with the action taken for each.
    2. Row counts reconcile with a known total or a stated source.
    3. At least three findings, each with a number, a chart, a stated uncertainty and a recommended action.
    4. A Simpson's-paradox check on one key trend, and a leakage check if a target exists.
    5. The notebook runs top to bottom after a kernel restart.
  • Stretch One A/B-test suggestion based on a finding.
  • Pitfalls Charts without a message; findings with no "so what"; deleting outliers without checking if they are real.
  • Chapters used 2, 3, 4, 13.

Capstone 2: A/B test analysis with a ship or no-ship decision

  • Question "Should we ship the new checkout (or similar) change?" Use a public experiment dataset or simulate one with fixed seed, including a planted sample-ratio mismatch (SRM) or a novelty effect for extra difficulty.
  • Deliverables A pre-registered test plan (hypothesis, primary metric, guardrails, unit, MDE, sample size, duration), an analysis notebook, and a decision memo.
  • Acceptance criteria
    1. Sample size computed and shown before analysis.
    2. SRM check performed and reported.
    3. Lift reported as absolute and relative, with a 95% interval.
    4. One variance-reduction method (CUPED or stratification) shown with its effect on the interval width.
    5. Guardrails reported; a clear ship, no-ship or iterate decision with the reason.
  • Stretch A sequential or Bayesian analysis and a comparison of decisions.
  • Pitfalls Peeking at the p-value each day; analysing many segments until one is "significant"; ignoring guardrails.
  • Chapters used 4, 7, 12.4, 13.

Problem 14.2.1 (Capstone 2 sizing) Baseline conversion 4%. You want to detect an absolute lift of 0.5 percentage points (to 4.5%) with 5% significance (two-sided) and 80% power. How many users per arm?

Formulan = 2 × (z_α/2 + z_β)² × p(1 − p) / δ², the usual approximation with the same variance in both arms
Plug inz_α/2 = 1.960, z_β = 0.8416, p = 0.04, δ = 0.005
Compute(1.960 + 0.8416)² = 2.8016² = 7.849. Then 2 × 7.849 × 0.04 × 0.96 = 0.6028. Divide by 0.005² = 0.000025: 0.6028 / 0.000025 = 24,112
AnswerAbout 24,112 users per arm, so about 48,200 in total. The more exact formula (separate variances for 4.0% and 4.5%) gives 25,551 per arm, so plan for about 25,600 per arm.
CheckBoth numbers were produced by code (24,112 and 25,551). Halving the detectable lift to 0.25 points roughly quadruples the sample size, because n depends on 1/δ².
Why it mattersIf the shop gets 3,000 checkout users a day, 51,200 users takes about 17 days, so you must cover at least two full weekly cycles anyway. A sample-size number that is not turned into days is not yet a plan.

Capstone 3: Churn model to retention decision

  • Question "Whom should we send a retention offer, and will it pay?" Use the shop dataset (Chapter 1) or a public telecom churn dataset.
  • Deliverables Point-in-time label table, baseline rule, model, calibration plot, cost matrix, profit-by-threshold curve, Monte Carlo profit range, memo, model card with a fairness check.
  • Acceptance criteria
    1. Prediction time and label window written down; no feature from after prediction time (a leakage test in tests/).
    2. Baseline gate: model vs recency rule with an interval (Section 14.1).
    3. Calibration table by quintile; recalibrate if the gap is large.
    4. Cost matrix with stated assumptions; the threshold from break-even and a sweep; profit in rupees.
    5. A simulation showing P(loss) and a tornado of the assumptions (Chapter 12.3).
    6. Group-wise selection rate and TPR (Chapter 13.3); a monitoring plan with PSI.
  • Stretch An uplift model on simulated A/B data (Chapter 8).
  • Pitfalls Using cancel_ticket-like leakage; reporting AUC with no money; assuming the save rate without a test.
  • Chapters used 1, 2, 3, 8, 12, 13.

Capstone 4: Demand forecasting with backtesting and an inventory decision

  • Question "How much should we stock next week, per item?" Use a public retail demand dataset or simulate 20 daily series with weekly seasonality, trend and promotions.
  • Deliverables Baselines (naive, seasonal naive, moving average), at least one classical and one ML model, rolling-origin backtest, interval forecasts, and a stock rule.
  • Acceptance criteria
    1. Rolling-origin backtest (never a random split), at least 5 origins, with the metric by horizon.
    2. Beats seasonal naive on WAPE, or an honest statement that it does not.
    3. Prediction intervals with a measured coverage (does the 80% interval cover about 80%?).
    4. Safety stock and reorder point computed from forecast errors (Chapter 11.5), with the service level stated.
    5. A bias check (mean error), not only absolute error.
  • Stretch Hierarchical reconciliation or intermittent-demand handling.
  • Pitfalls MAPE near zero demand; leaking future holidays as unknowns; ignoring that forecasts must be made with data available at forecast time.
  • Chapters used 9, 11.5, 12.

Problem 14.2.2 (Capstone 4 metric) Actual demand over three days is 100, 120, 80 and the forecast is 110, 100, 90. Compute WAPE and the mean absolute error.

FormulaWAPE = Σ|actual − forecast| / Σ actual
ComputeErrors are 10, 20, 10, so Σ|error| = 40. Σ actual = 300. WAPE = 40 / 300 = 0.1333. MAE = 40 / 3 = 13.33
AnswerWAPE is 13.3%: forecasts are off by about 13% of total demand. MAE is 13.3 units per day.
CheckHere WAPE (as a fraction) and MAE equal each other numerically only because mean demand is 100, so 13.33 / 100 = 0.1333. They differ in general.
Why it mattersWAPE weights big items more and is stable when one day has zero demand, unlike per-row MAPE.

Connection to the job. These four projects cover the daily work of most analytics and product data scientists: understand data, test changes, decide actions, plan supply.

Applications

  • Product and growth teams: capstones 1 to 3.
  • Retail, e-commerce and supply chain: capstone 4.
  • Consulting: capstone 1 as a sample case.
COMMON MISTAKE
Skipping the memo and the decision step because "the model is the project". The brief says the deliverable is a decision, so a notebook without a memo is half a capstone.

Check yourself

  1. In capstone 2, what comes first: analysis or sample size? Answer: Sample size and the plan, before any data is looked at.
  2. Why use rolling-origin backtesting in capstone 4? Answer: It respects time order; random splits leak future patterns into training.
  3. What turns AUC into something a manager can use in capstone 3? Answer: The cost matrix and profit in rupees at a chosen threshold.

14.3 Capstones 5 to 8: Recommender, Causal, Scorecard, Operations Data

INTUITION
The second four are the "specialist" projects that make a portfolio stand out: a two-stage recommender, a causal analysis with sensitivity checks, a bank-style scorecard with a model card, and an operations-data analysis of queues and capacity. Pick the ones that match the jobs you want.

Capstone 5: Recommender system (two-stage) with offline metrics and cold start

  • Question "What ten items should we show each user?" Use MovieLens-style or a public implicit-feedback dataset (clicks, purchases).
  • Deliverables Popularity and item-item baselines, matrix factorization (or another collaborative method), a candidate-then-rank design, time-split offline evaluation, a cold-start strategy, and an A/B test plan.
  • Acceptance criteria
    1. A time-based split (no random split), with leakage of future interactions ruled out.
    2. Baselines: popularity and recently popular; the new model's Recall@K and NDCG@K compared with an interval or several seeds.
    3. Coverage and diversity reported next to accuracy.
    4. A cold-start rule for new users and for new items.
    5. A written online test plan (primary metric, guardrails), because offline gains often do not carry over.
  • Stretch A learning-to-rank re-ranker with business rules.
  • Pitfalls Random splits; evaluating only on popular items; ignoring exposure and position bias.
  • Chapters used 10, 7, 12.4.

Problem 14.3.1 (Capstone 5 metric) A user has 2 relevant items. Your top-3 list has relevant items at ranks 1 and 3. Compute NDCG@3.

FormulaDCG = Σ rel_i / log₂(i + 1); NDCG = DCG / ideal DCG
ComputeDCG = 1/log₂(2) + 1/log₂(4) = 1 + 0.5 = 1.5. Ideal: relevant items at ranks 1 and 2: 1 + 1/log₂(3) = 1 + 0.6309 = 1.6309. NDCG = 1.5 / 1.6309 = 0.920
AnswerNDCG@3 is 0.92: nearly ideal, penalised a little for placing one relevant item third.
CheckIf the relevant items were at ranks 1 and 2, NDCG would be exactly 1.0.
Why it mattersRanking metrics reward getting good items to the top, which accuracy cannot see.

Capstone 6: Causal analysis of observational data

  • Question "Did programme X cause outcome Y?" Use a public dataset with a treatment (a policy, a feature roll-out) or a simulated one with known true effect and planted confounding.
  • Deliverables A DAG, a naive estimate, adjusted estimates (regression, propensity weighting), balance table, and a sensitivity analysis. A difference-in-differences version if you have before/after data.
  • Acceptance criteria
    1. A drawn DAG with confounders, mediators and colliders labelled, and the reason for each control choice.
    2. Overlap check and covariate balance (standardised mean difference) before and after weighting.
    3. At least two estimators that agree (or an explanation if they do not).
    4. If simulated, the estimate is compared with the known true effect.
    5. A sensitivity analysis for unobserved confounding and a plain-language statement of assumptions.
  • Stretch A synthetic-control or regression-discontinuity analysis.
  • Pitfalls Controlling for a collider or mediator; claiming causation without stating assumptions.
  • Chapters used 4, 8.

Problem 14.3.2 (Capstone 6 check) Treated stores average 10 units before and 16 after. Control stores average 9 before and 12 after. What is the difference-in-differences estimate?

FormulaDiD = (treated after − treated before) − (control after − control before)
Compute(16 − 10) − (12 − 9) = 6 − 3 = 3
AnswerThe estimated effect is 3 units. Control stores grew by 3 anyway, so only 3 of the treated stores' 6-unit growth is credited to the programme.
CheckThe naive before/after change was 6, double the DiD estimate. The assumption is parallel trends: without the programme, treated stores would have grown by 3 too.
Why it mattersAlways state the assumption; a visual check of pre-period trends is part of the acceptance criteria.

Capstone 7: Credit-risk scorecard with a model card

  • Question "Which applicants should we approve, and how is the score monitored?" Use a public credit dataset (for example the German credit or similar), or the synthetic generator of Chapter 11.2.
  • Deliverables WoE binning with IV table, logistic scorecard, points table (base score and PDO), KS, Gini, PSI over time, a model card, and a reject-inference discussion.
  • Acceptance criteria
    1. Out-of-time split; bins and coefficients fitted on train only.
    2. WoE monotonic for the main variables, or a justification for each exception.
    3. KS, Gini and AUC on train and test, with a statement on overfitting.
    4. Score points table that a person can recompute by hand for one applicant (show the example).
    5. PSI of the score and of each variable between train and a later period.
    6. Model card with limits, fairness check, reason-code logic and a section on selective labels.
  • Stretch Compare with gradient boosting and discuss explainability trade-offs.
  • Pitfalls Any variable with IV above 0.5 (check leakage); using test data to choose bins; no reason codes.
  • Chapters used 11.2, 12.4, 13.3, 13.4.

Problem 14.3.3 (Capstone 7 check) Test AUC is 0.74. Report Gini. Then, at base score 600 with odds 50:1 and PDO 20, how many points does a +1 change in log-odds of good represent?

ComputeGini = 2 × 0.74 − 1 = 0.48. Factor = PDO / ln 2 = 20 / 0.6931 = 28.85
AnswerGini is 0.48, and one unit of log-odds is worth 28.85 points (doubling the odds is 20 points).
Check28.85 × 0.6931 = 20.0, which is the PDO.
Why it mattersThis is the sentence that shows you really understand the points scale.

Capstone 8: Operations-data analytics (queues, delivery times, capacity)

  • Question "When will this operation run out of capacity, and when does it misbehave?" Use a public operations dataset (taxi trips, hospital appointments, delivery logs, bike-share) with no personal data. If you have none, generate synthetic data as in Chapter 11.6.
  • Deliverables Percentiles of waiting or delivery time by hour, a plot of waiting time against utilisation with the point where it explodes, a regression of waiting time on load, anomaly detection, a capacity-date forecast with a bootstrap interval, and a one-page memo for an operations manager.
  • Acceptance criteria
    1. p50, p90, p99 by hour or segment; never averages alone.
    2. Little's law check: items in the system ≈ arrival rate × time in the system, within a stated tolerance.
    3. The utilisation level where waiting explodes, compared with the M/M/1 shape (Chapter 11.6).
    4. Anomaly rule evaluated on injected or known incidents, with detection rate and false alarms reported, and compared with a simple global threshold.
    5. Capacity date with a 90% interval and the assumptions (linear growth, no campaigns).
    6. Memo with a recommendation: add capacity by date X, or fix step Y.
  • Stretch A discrete-event simulation of a proposed staffing plan (Chapter 12.3).
  • Pitfalls Aggregating percentiles by averaging them; personal data in a public repo; ignoring the start-up period when the system is still empty.
  • Chapters used 11.6, 12.3, 13.

Problem 14.3.4 (Capstone 8 check) A hospital emergency room records 80 arrivals per hour and an average stay of 0.5 hours. It has 30 beds and no waiting room is counted. How many patients are in the ER on average, and is the record consistent?

FormulaL = λ × W
ComputeL = 80 × 0.5 = 40
AnswerAbout 40 patients must be present on average, but only 30 beds exist, so the numbers cannot all be right: the stay may exclude time in the corridor, the arrival rate may cover a different time window, or patients are counted twice. Investigate before trusting any conclusion.
CheckWith 30 beds and a 0.5 hour stay, the maximum rate the ER can handle is 30 / 0.5 = 60 patients per hour, below 80.
Why it mattersLittle's law is a cheap consistency check on operations data; failing it means the data or the setup is wrong.

Connection to the job. Capstones 5 to 8 map to recommendation teams, causal/experimentation teams, BFSI risk teams and operations or supply-chain analytics teams.

Applications

  • E-commerce and media: capstone 5.
  • Product and marketing science: capstone 6.
  • Banks, NBFCs and fintech: capstone 7.
  • Logistics, healthcare and operations teams: capstone 8.
COMMON MISTAKE
Publishing a public repo with real company data, credentials or customer information from your work. Use public or synthetic data, remove secrets, and check your employer's rules before sharing anything derived from work.

Check yourself

  1. In capstone 6, why compare the estimate with the known truth in a simulation? Answer: It shows whether your method actually recovers the effect, which real data cannot show.
  2. Why is IV above 0.5 a warning in a scorecard? Answer: It is suspiciously strong; check for leakage.
  3. What does Little's law check in operations data? Answer: Whether the number in the system, the arrival rate and the time spent in the system are consistent with each other.

14.4 Mastery Tests and Scoring Your Own Work

INTUITION
A driving test has a checklist, a time limit, and an examiner who does not know you. Mastery tests are the same: timed tasks with a rubric, so you can see honestly whether a topic is obvious yet (the rule from the start of this document).

The six mastery tests. Do each under time, then score yourself with 0 (not done), 1 (partly) or 2 (clear and correct) on every rubric line. Convert to a percentage: points / (2 × number of lines).

TestTimeRubric lines (score 0 to 2 each)
1. One-page brief from a vague ask30 minDecision named; framing; prediction time and label window; metric at 3 levels; baseline; risks
2. Find leakage in an unfamiliar notebook45 minFinds the leaking feature; explains why; fixes the split; re-measures; writes what changed
3. Design an A/B test end to end45 minHypothesis; primary and guardrail metrics; unit; sample size; analysis plan; pitfalls
4. Explain Simpson's paradox, confounding, selection bias20 minNumeric example each; which view is right; how to check
5. Backtest a forecast against naive60 minRolling origin; baselines; metric by horizon; honest result; interval coverage
6. Five-minute stakeholder talk with no formulas30 minAnswer first; one number per slide; uncertainty; risks; clear ask

A reasonable target before interviews is 75% or more on every test.

Problem 14.4.1 You score tests 1 to 6 as 83%, 67%, 92%, 75%, 58%, 50%. Which should you redo first, and what is your average?

ComputeSum = 83 + 67 + 92 + 75 + 58 + 50 = 425. Average = 425 / 6 = 70.8%
AnswerYour average is 70.8%. Redo test 6 (50%, the lowest: the stakeholder talk) first, then test 5 (58%) and test 2 (67%). Test 4 (75%) just meets the target.
CheckThree tests are below the 75% target, so the redo list has three items.
Why it mattersA written score removes the feeling of "I think I know it". Repeat a test after a week; the second score is the real one.

Problem 14.4.2 Using the leakage test as the example, what would you check in a notebook where a "days to cancel" column is a feature in a churn model?

Step 1Ask when each feature is created: "days to cancel" exists only after the customer has cancelled.
Step 2Measure its single-feature AUC: a near-perfect value (like the 94% precision of cancel_ticket in Chapter 3.4) is the alarm.
Step 3Drop it, rebuild the validation as time-ordered, and report the AUC before and after.
AnswerThe feature is leakage, because it is created by the outcome. Remove it and re-measure.
CheckAfter removal the best single feature should be a plain behaviour one such as recency.
Why it mattersLeakage is the most common reason for "too good to be true" results.

Connection to the job. These tests mirror live case rounds. Doing them alone, under time, with a rubric is the cheapest interview practice you can get.

Applications

  • Self-assessment before applying for roles.
  • Study groups: score each other's briefs.
  • Mock interviews with an AI partner (Prompt pack).
COMMON MISTAKE
Scoring yourself generously because you "could do it with more time". The test includes the time limit. Interviews do too.

Check yourself

  1. What do you do when one test scores low? Answer: Redo the matching chapter's worked problems, then repeat the test after a week.
  2. Why time the tests? Answer: Interviews are timed; speed reveals if the idea is truly obvious to you.
  3. Who should read your brief? Answer: Someone who does not know the project; if they cannot state the decision after one read, rewrite it.

14.5 The Data Science Interview Bank

INTUITION
Interview questions are not random. They test whether you can frame a problem, spot traps, use statistics correctly, and communicate. A strong answer has a structure you can reuse: clarify, frame, method, risks, decision. Practise saying them aloud, in short sentences.

A reusable answer shape. (1) Clarify the goal and the decision. (2) Define the metric and the baseline. (3) State the method and why. (4) Name the main risks. (5) Say what you would do next and how you would know it worked.

Product and metrics questions

Question 1: "DAU dropped 10%. What do you do?"

Key points: first check the data (pipeline delay, logging change, bots, timezones), then the shape (sudden or gradual, all segments or one, new vs returning, platform, country, acquisition channel), then external causes (holiday, outage, release, competitor), then act.

Problem 14.5.1 Daily active users fell from 100,000 to 90,000. New users fell from 20,000 to 19,000; returning users fell from 80,000 to 71,000. Where is the drop?

Step 1Total drop = 100,000 − 90,000 = 10,000.
Step 2New users explain 20,000 − 19,000 = 1,000, which is 1,000 / 10,000 = 10% of the drop.
Step 3Returning users explain 80,000 − 71,000 = 9,000, which is 90%. Returning fell 9,000 / 80,000 = 11.25%.
Answer90% of the drop is returning users, so look at retention, notifications, product bugs, or a segment (a platform or country) rather than at acquisition.
Check1,000 + 9,000 = 10,000. Correct.
Why it mattersDecomposing a total into parts is the first move; it narrows the search before you form a hypothesis.

Question 2: "How would you measure the success of feature X?"

Key points: state the goal of the feature; one primary metric plus guardrails; method (A/B test if possible, else a quasi-experiment); sample size and duration (Problem 14.2.1); watch for novelty and cannibalisation; decide in advance what result means ship.

Question 3: "Design an experiment for a new recommendation widget."

Key points: randomise by user; metric (click-through is a proxy; prefer conversion or retention), guardrails (page latency, returns), SRM check, run full weeks, avoid peeking, segment analysis only as a hypothesis, pre-define the ship rule (Chapter 7).

Question 4: "Offline AUC is great, but online results are flat. Why?"

Key points: offline metric is not the business metric; selection bias in training data; position and exposure bias; feedback loops (Chapter 12.4); training-serving skew (Chapter 13.5); novelty; the action does not change when the score changes; wrong threshold; low traffic and no power.

Statistics and data questions

Question 5: "Explain a p-value to a manager."

Key points: "If nothing really changed, how often would we see a difference this big just by luck? A p-value of 0.03 means about 3 times in 100." It is not the chance the idea is true, and it does not say how big or how useful the effect is. Follow with the interval and the effect size.

Question 6: "A test is 95% sensitive and 95% specific. The condition affects 1% of people. A person tests positive. What is the chance they have it?"

Problem 14.5.2 Compute the positive predictive value.

FormulaPPV = sens × prev / (sens × prev + (1 − spec) × (1 − prev))
Plug insensitivity 0.95, specificity 0.95, prevalence 0.01. True positives: 0.95 × 0.01 = 0.0095. False positives: 0.05 × 0.99 = 0.0495
ComputePPV = 0.0095 / (0.0095 + 0.0495) = 0.0095 / 0.0590 = 0.161
AnswerAbout 16%. Out of every 100 positives, only about 16 are real, because the condition is rare. (With sensitivity 0.90 instead, the answer is 0.154, which we also confirmed by code.)
CheckIn 10,000 people: 100 sick, 95 detected; 9,900 healthy, 495 false alarms. 95 / (95 + 495) = 0.161. Same.
Why it mattersBase-rate neglect (Chapter 4.2) explains why fraud and screening alerts are mostly false alarms.

Question 7: "How do you handle missing data, imbalanced classes and outliers?"

Key points. Missing: first ask why it is missing (not applicable, not recorded, error); use indicators, impute inside the pipeline only on train; do not drop silently. Imbalance: use PR-AUC and cost-based thresholds, stratified or time splits, class weights; resampling is a last resort and must be applied only to train. Outliers: check if error or real; transform (log) or cap, but keep the evidence (Chapter 3).

Question 8: "What is data leakage? Give an example."

Key points: using information at training time that will not exist at prediction time. Example: a cancel_ticket feature created after the customer decided to leave scored 94% precision; once removed, the best feature was recency with AUC 0.88 (Chapter 3.4). Detect with single-feature AUC, time-ordered validation and asking "when is this created?".

Question 9: "How do you decide between two models?"

Key points: same split, the metric that matches the decision (profit, recall at capacity), intervals on the difference (Section 14.1), calibration, latency and cost, simplicity, explainability, stability over time; and the baseline gate.

Question 10: "Correlation versus causation: how do you answer a causal question without an experiment?"

Key points: DAG, adjust for confounders, propensity or DiD, check overlap and balance, state assumptions, run sensitivity analyses, and say what an experiment would add (Chapter 8).

Modelling-in-business questions

Question 11: "How would you predict churn?" Key points: define churn and the prediction time and label window; build a point-in-time table; baseline rule; features such as recency, frequency, trends; model; calibration; cost matrix and threshold; fairness; monitoring (Chapters 1 to 3, 11, 12, 13).

Question 12: "How would you forecast demand?" Key points: baselines (seasonal naive), rolling-origin backtest, features such as calendar, price and promotions, intervals, forecast to decision (safety stock), bias check (Chapters 9, 11.5).

Question 13: "How would you detect fraud?" Key points: extreme imbalance, precision at review capacity, cost threshold c_review / (c_review + c_miss), time-based validation, graph and velocity features, latency, drift (Chapter 11.3).

Problem 14.5.3 A bank loses 3,000 per missed fraud and spends 60 per review. A model has probability 0.03 for a transaction. Review it?

FormulaBreak-even p* = c_review / (c_review + c_miss)
Computep* = 60 / (60 + 3,000) = 60 / 3,060 = 0.0196
AnswerYes: 0.03 is above 0.0196. Expected loss if ignored is 0.03 × 3,000 = 90, against a review cost of about 0.97 × 60 = 58.2.
CheckAt p = 0.0196 the two costs are equal (about 58.8 each), so any larger p favours reviewing.
Why it mattersThe threshold comes from costs, not from 0.5.

Behavioural and career questions

Question 14: "Tell me about a project you are proud of." Use the shape: situation, task, action (with numbers), result (with numbers), what you learned, what you would change. Use a capstone from this chapter. Include a limit or a failure: honest answers are trusted.

Question 15: "Why are you moving into data science?" A strong answer has four parts: what you did before and a number that shows it ("I cut the monthly reporting time from three days to four hours"), what you enjoyed (asking why, predicting what happens next), the skills you added (statistics, machine learning, decision analysis), and the project that proves it (one capstone, with its result and its limit). Keep it to 45 seconds and honest.

Question 16: "A stakeholder disagrees with your result. What do you do?" Listen; check if they know something about the data you do not; reproduce your result; show uncertainty and what would change your mind; propose a small test to settle it (Chapter 13.2).

Your 60-second story. Prepare one story from your own past work: the problem you solved, the numbers (before and after), the method, and the decision it enabled. Then link it to the role: a reporting automation links to analytics engineering; a forecast links to demand planning; a quality check links to data quality and monitoring.

Connection to the job. The same structured thinking appears in design reviews and stakeholder meetings. Interview practice is job practice.

Practice set

1. (Easy) Baseline AUC 0.80, model AUC 0.83. Gini of each? Answer: Baseline 2 × 0.80 − 1 = 0.60; model 2 × 0.83 − 1 = 0.66.

2. (Easy) Forecast 90, actual 100 on one day. Absolute error and percentage error? Answer: 10 units; 10 / 100 = 10%.

3. (Easy) Control grows 5 to 8 and treated grows 6 to 13. DiD? Answer: (13 − 6) − (8 − 5) = 7 − 3 = 4.

4. (Medium) What is the output? 2 * 0.62 - 1 Answer: 0.24, the Gini for AUC 0.62.

5. (Medium) Find the bug: "Our model beat the baseline: 0.881 vs 0.879 AUC on one test split. Ship it." Answer: The gain of 0.002 is well inside noise (our own gain interval was about ±0.01). Bootstrap the difference; if the interval contains zero, report no evidence of improvement.

6. (Medium) A test must detect 2 points on a 10% baseline, alpha 0.05, power 0.8. Approximate n per arm with the simple formula. Answer: 2 × 7.849 × 0.10 × 0.90 / 0.02² = 1.4128 / 0.0004 = 3,532 per arm.

7. (Medium) A call centre gets 200 calls per hour and each call lasts 0.3 hours including waiting. It has 50 phone lines. Consistent? Answer: L = 200 × 0.3 = 60 calls in the system, more than 50 lines. Not consistent: check the measurement window, what the duration includes, or the line count.

8. (Medium) Users: 50,000 yesterday, 45,000 today; mobile 30,000 to 24,000 and web 20,000 to 21,000. Where is the problem? Answer: Total drop 5,000. Mobile fell 6,000 (20%), web rose 1,000. Mobile explains more than the whole drop; investigate a mobile release, outage or tracking change.

9. (Hard) A screening test has sensitivity 0.99 and specificity 0.99 and prevalence 0.1%. PPV? Answer: TP = 0.99 × 0.001 = 0.00099; FP = 0.01 × 0.999 = 0.00999. PPV = 0.00099 / 0.01098 = 0.090, about 9%.

10. (Interview) "Walk me through one of your projects and what you would do differently." Answer: Use situation, action, result with numbers, then the limit (for example the baseline gate showing the model did not beat the simple rule) and what you would change (collect new features, run an A/B test of the offer).

11. (Interview) "Your A/B test is stat-sig on the primary metric but a guardrail dropped. What do you do?" Answer: Do not ship yet. Check the size and the interval of the guardrail drop, the cost of that drop in money, segments where it concentrates, and whether it is a novelty effect; decide using expected value, discuss with the owner, and consider iterating on the design.

12. (Interview) "How would you explain overfitting to a manager?" Answer: "The model memorised last year's customers instead of learning general patterns, like a student who memorised old exam papers. We test it on new customers, ones it has never seen, to check."
