Reading about data science does not get you hired. A small number of finished, honest, well-explained projects does. A hiring manager opens your repository for about two minutes, so those two minutes must show a clear question, clean code, a fair baseline, a number you can defend and a clear sentence about what to do next. This chapter first gives you a method for running any project in this area. Then it walks through three projects: a churn model that ends in a spending decision (#3), an A/B test toolkit (#25) and a demand forecast with a proper backtest (#26). Every script below was run in this session with numpy, pandas, scipy and scikit-learn, and every output shown is the real output. All data is synthetic with fixed seeds, so you get the same numbers.

15.1 How to run a project in this area

INTUITION
A project is like cooking a meal for a guest. You decide the dish first (the question), buy fresh ingredients (data), cook in a clean kitchen (repo), taste as you go (tests and baselines), and serve it on a plate the guest understands (README and post). Nobody judges the meal by how many pots you used.

Plan the question and success criteria

Write one sentence before any code: "For [decision maker], I will [predict or estimate X] so that they can [take action Y], and I will call it a success if [measurable result]." A good example: "For the retention team, I will rank customers by churn risk so they can send a 5-rupee offer only where it pays back, and I will call it a success if expected profit beats 'send to everyone' on held-out data." Also write the baseline (the dumb method you must beat) and the metric you will use. Do it on day one and do not change it after you see results.

Environment and dependencies

Use a virtual environment: python3 -m venv .venv, activate it, then list only what you import in requirements.txt. Pin versions with pip freeze once the project works, and write the Python version in the README. Set every random seed in one place (SEED = 7). If a stranger cannot run make data && make test in five minutes, the project is not finished.

Data sourcing or generation

Prefer a public dataset with a clear licence, and write the licence and download date in data/README.md. When none fits, generate data with a documented rule. A generator is a strength, not a cheat: you know the true answer, so you can check that your method recovers it. The three projects here use generators. State plainly in the README that the data is synthetic and that real data would be messier.

Commit rhythm and good commit messages

Commit when one small thing works, usually every 30 to 60 minutes. A good message says what and why in one line, in the imperative: Add SRM check with chi-square test, Fix leakage: compute tenure at snapshot date. Bad messages: update, final, fix stuff. A short history that reads like a story is a portfolio asset.

a1f3c2e  Add synthetic customer generator with fixed seed
b7d9011  Add logistic regression baseline and AUC check
c40e8aa  Add calibration table; gradient boosting is not better
d55f2b9  Add cost-based targeting and profit comparison
e91a7c4  Write README with results and limits

Definition of done

  • The question, baseline and metric from your plan are answered in reports/results.md.
  • make test passes; at least one test checks a number you computed by hand.
  • The README has a result table, one chart, the limits and how to reproduce.
  • A stranger can run it from a clean clone.
  • You can explain every line to an interviewer, including why you rejected one idea.

Demo and deploy options

Free and simple options: a Streamlit app on a free community hosting tier, a static HTML report from a notebook, or a short screen recording of the notebook running. The core ideas for hosting do not change when the platform does, so check current documentation before you choose. Write the LinkedIn or blog post

Use five short parts: (1) the question in plain words, (2) one surprising finding with a number, (3) what you did in three bullets, (4) one mistake you caught and how, (5) link and one honest limit. Example opening: "A retention model with AUC 0.75 made less money than a simpler rule. Here is why." Avoid jargon walls. Show one chart.

Testing and debugging checklist for this area

  1. Leakage: does any feature use information from after the prediction date? Rebuild features with a hard cut-off date.
  2. Split: random split for independent customers, time split for forecasts, group split when one user has many rows.
  3. Baseline first: if your model cannot beat a simple rule, say so.
  4. Sanity numbers: class balance, row counts before and after each join, no duplicate IDs.
  5. Known-answer test: generate data with a known effect and check that the code finds it.
  6. Metric vs decision: does the metric you report match the business action?
  7. Seeds: rerun twice; numbers should match exactly or within a stated tolerance.
  8. Uncertainty: report an interval or a range, never only a point.
COMMON MISTAKE
Tuning on the test set "just once more". Each peek makes the test score a little less honest. Fix the test set on day one and look at it at the end.

Check yourself

  1. Why write the success criteria before coding? Answer: Otherwise you can bend the goal to fit whatever result appears.
  2. Why is a data generator useful? Answer: You know the true answer, so you can test whether your method finds it.
  3. Name two things that must be in a README. Answer: A result table with a baseline, and the limits, plus how to reproduce.

15.2 Project: Churn analysis and retention decision (#3)

Goal and why employers care. Predict which shop customers will stop ordering, then decide whom to contact. Most candidates stop at "AUC = 0.75". Employers want the next step: turning a probability into a rupee decision. This is the exact thread of a real retention team.

Skills used. Chapter 3, Exploratory Data Analysis for Modelling; Chapter 6, Feature Engineering II (leakage-safe features); Chapter 11, Applied Domains (churn); Chapter 12, From Prediction to Decision (cost matrices and thresholds).

Data. The generator in the script below makes 20,000 customers with tenure, recent orders, days since last order, support tickets and basket size. Churn is drawn from a known formula, so higher recency and more tickets raise risk. Real alternative: any public telecom or subscription churn file; check its licence.

Architecture.

make_customers() -> split 70/30 (stratified) -> baselines
        |                                             |
        v                                             v
 logistic regression + gradient boosting      majority class, send-to-all
        |
        v
 AUC + Brier + calibration table -> pick model
        |
        v
 expected gain = P(churn) x P(save) x value - offer cost
        -> send only where gain > 0 -> compare profit

Step-by-step build.

  1. Generate data, check the churn rate (15.4%) and compute the majority-class accuracy (84.6%). A model must beat the ranking quality, because 84.6% accuracy is free.
  2. Fit logistic regression (simple, explainable) and gradient boosting (more flexible). Score both with AUC (can the model rank churners above non-churners) and Brier score (average squared error of the probability; lower is better).
  3. Make a calibration table: sort customers by predicted risk, cut into 5 equal bins, compare average predicted risk to the actual churn rate. If a bin says 12% but 10.7% churn, the probabilities are roughly honest.
  4. Convert probability to money. Assumptions (state them in the README): an offer costs 5, it saves 30% of would-be churners, and a saved customer is worth value. Send if P × 0.30 × value − 5 > 0.

Before you run it, predict: will gradient boosting win? Many people expect so. Check the output.

import numpy as np, pandas as pd
from sklearn.model_selection import train_test_split
from sklearn.linear_model import LogisticRegression
from sklearn.ensemble import HistGradientBoostingClassifier
from sklearn.metrics import roc_auc_score, brier_score_loss
from sklearn.calibration import calibration_curve

def make_customers(n=20000, seed=7):
    r = np.random.default_rng(seed)
    df = pd.DataFrame({
        "tenure_months": r.integers(1, 61, n),
        "orders_90d": r.poisson(3, n),
        "days_since_last": r.integers(0, 120, n),
        "support_tickets": r.poisson(0.8, n),
        "avg_basket": r.gamma(4, 15, n).round(2)})
    z = (-2.0 - 0.03*df.tenure_months - 0.25*df.orders_90d + 0.02*df.days_since_last
         + 0.30*df.support_tickets + 0.004*df.avg_basket)
    p = 1/(1+np.exp(-z))
    df["churned"] = (r.random(n) < p).astype(int)
    df["value"] = (df.avg_basket*df.orders_90d/3*4).round(2)   # rough yearly margin proxy
    return df
# Step 1: data and baseline
df = make_customers()
print(df.shape, "churn rate", round(df.churned.mean(),3))
X = df.drop(columns=["churned","value"]); y = df.churned
Xtr, Xte, ytr, yte, vtr, vte = train_test_split(X, y, df.value, test_size=0.3, random_state=0, stratify=y)
base = max(yte.mean(), 1-yte.mean())
print("majority-class accuracy", round(base,3))
# Step 2: two models, judged by ranking (AUC) and probability quality (Brier)
lr = LogisticRegression(max_iter=2000).fit(Xtr, ytr)
gb = HistGradientBoostingClassifier(random_state=0).fit(Xtr, ytr)
for name, m in [("logreg", lr), ("gboost", gb)]:
    p = m.predict_proba(Xte)[:,1]
    print(name, "AUC", round(roc_auc_score(yte,p),3), "Brier", round(brier_score_loss(yte,p),4))
# Step 3: calibration table, 5 equal-size bins
p = gb.predict_proba(Xte)[:,1]
fr, mp = calibration_curve(yte, p, n_bins=5, strategy="quantile")
print("gb calibration (pred -> actual):", [(round(float(a),3),round(float(b),3)) for a,b in zip(mp,fr)])
# Step 4: cost-based targeting: offer cost 5, saves customer with prob 30%, saved value = vte
cost, save = 5.0, 0.30
pl = lr.predict_proba(Xte)[:,1]
gain = pl*save*vte.values - cost          # expected profit per customer if we send
print("send if gain>0:", (gain>0).sum(), "of", len(gain), "profit", round(gain[gain>0].sum(),0))
print("send to all   :", len(gain), "profit", round(gain.sum(),0))
top = np.argsort(-pl)[:int(0.2*len(pl))]
print("top-20% by prob profit", round(gain[top].sum(),0))

gb calibration (pred -> actual): [(0.043, 0.037), (0.079, 0.075), (0.12, 0.107), (0.186, 0.209), (0.355, 0.34)]
send if gain>0: 3424 of 6000 profit 35390.0
send to all   : 6000 profit 28825.0

Reading the output. Logistic regression (AUC 0.752) beats gradient boosting (0.737) here. This is not a bug. The generator is a logistic formula, so the simple model is the right shape, and boosting adds only variance. The calibration pairs sit close to the diagonal. The profit line is the real finding: sending only where the expected gain is positive earns 35,390 on 3,424 customers, against 28,825 when sending to all 6,000, and a "top 20% by probability" rule earns only 17,123, because the riskiest customers are not always the most valuable or the most savable. These profit numbers depend entirely on the assumptions (5 cost, 30% save rate), so show a small sensitivity table in your README.

Evaluation and acceptance criteria.

  • Test AUC at least 0.70 and above the baseline you wrote down.
  • Brier score reported; calibration table within about 3 percentage points per bin.
  • Profit under the decision rule beats send-to-all on the held-out 30%, by a stated margin.
  • A sensitivity table: profit when save rate is 10%, 20%, 30% and offer cost is 3, 5, 8.

Common pitfalls and how to detect them.

  1. Leakage: a feature like "cancelled_flag_date". Detect: one feature has implausibly high importance, or AUC above 0.95.
  2. Accuracy trap: reporting 84.6% accuracy. Detect: compare with the majority-class number first.
  3. Probability as truth: using uncalibrated scores in a cost formula. Detect: the calibration table.
  4. Treating "will churn" as "will respond": the offer works only on persuadable customers. Detect: ask whether you have any experiment data (Chapter 7).
  5. Random split on time-ordered data: detect by training on early months and testing on later ones.

Three extensions.

  1. Add isotonic or Platt calibration (CalibratedClassifierCV, not run here) and compare Brier scores.
  2. Replace the fixed 30% save rate with an uplift model trained on A/B test data (Chapter 8).
  3. Add a SHAP or permutation-importance chart and explain the top 3 drivers in plain words.

Interview talking points.

  • Q: Why did logistic regression win? A: The true pattern was close to linear, so extra flexibility only added noise. I would check this on real data too, not assume.
  • Q: How do you pick the contact threshold? A: I do not use 0.5. I compute expected gain per customer from probability, save rate, value and cost, and contact only when it is positive.
  • Q: How do you know the probabilities are trustworthy? A: A calibration table. In each risk bin, predicted and actual churn should match.

README outline. Question; baseline (send to all); results table (AUC, Brier, profit); calibration plot; assumptions and sensitivity; limits (synthetic data, no causal effect of the offer); how to reproduce.

15.3 Project: A/B test toolkit (#25)

Goal and why employers care. Build a small, tested library that does the four jobs every experimentation team needs: size a test, detect a broken split, reduce noise with CUPED, and stop safely. It shows statistical judgement, which is rarer than modelling skill.

Skills used. Chapter 4, Statistical Thinking: Ways Data Fools You; Chapter 7, Experimentation: A/B Testing Done Properly (sample size, SRM, CUPED, peeking).

Data. Simulated in the script: a binary conversion metric for sizing, two arm counts for SRM, a continuous spend metric with a pre-period spend for CUPED, and A/A simulations (both arms identical) for the peeking study.

Architecture.

abtoolkit/
  sizing.py     n_per_arm(p1, p2, alpha, power)
  srm.py        srm_p(n_a, n_b, expected)
  cuped.py      theta, adjust(), diff_se()
  sequential.py aa_false_positive(looks, alpha)
  tests/        known-answer tests for each module
notebooks/demo.ipynb   runs all four on one example

Step-by-step build.

  1. Sample size. Implement the formula from Chapter 7. Test it: 10% to 11% must give 14,751 per arm.
  2. SRM. The chi-square test compares the counts you got with the split you intended. A tiny p-value means the assignment or logging is broken, so do not read the results.
  3. CUPED. Fit θ = cov(post, pre) / var(pre), subtract θ × (pre − mean pre) from the outcome, then compare arms. The adjusted metric has the same expected lift and less noise.
  4. Peeking. Run many A/A tests (no true effect) and stop at the first p < 0.05 over 5 looks. Count false alarms.
  5. Fix. Use a stricter alpha per look; here 0.016 is found by simulation, in the spirit of Pocock boundaries. For a real programme use a vetted group-sequential method.
import numpy as np
from scipy import stats

# Step 1: sample size
def n_per_arm(p1, p2, alpha=0.05, power=0.8):
    za, zb = stats.norm.ppf(1-alpha/2), stats.norm.ppf(power)
    pb = (p1+p2)/2
    return (za*np.sqrt(2*pb*(1-pb)) + zb*np.sqrt(p1*(1-p1)+p2*(1-p2)))**2/(p2-p1)**2
print("n per arm:", round(n_per_arm(.10,.11)))

# Step 2: sample-ratio-mismatch check
def srm_p(n_a, n_b, expected=0.5):
    n = n_a+n_b
    return stats.chisquare([n_a,n_b],[n*expected, n*(1-expected)]).pvalue
print("SRM ok  :", round(srm_p(5030,4970),3))
print("SRM bad :", srm_p(5300,4700))

# Step 3: CUPED on a continuous metric (spend), pre-period spend as covariate
r = np.random.default_rng(1)
n = 4000
pre = r.gamma(4, 10, 2*n)
post = 0.8*pre + r.normal(0, 8, 2*n)
t = np.r_[np.zeros(n), np.ones(n)]
post = post + 1.0*t                                 # true lift = +1.0
def diff_se(y, t):
    a, b = y[t==0], y[t==1]
    return b.mean()-a.mean(), np.sqrt(a.var(ddof=1)/len(a)+b.var(ddof=1)/len(b))
theta = np.cov(post, pre)[0,1]/pre.var(ddof=1)
adj = post - theta*(pre-pre.mean())
d0,s0 = diff_se(post,t); d1,s1 = diff_se(adj,t)
print(f"theta={theta:.3f}")
print(f"raw   lift={d0:.3f} se={s0:.3f}")
print(f"CUPED lift={d1:.3f} se={s1:.3f}  var cut={1-(s1/s0)**2:.1%}  corr^2={np.corrcoef(post,pre)[0,1]**2:.3f}")

# Step 4: peeking inflates false alarms: A/A tests, 5 looks, stop at first p<0.05
def aa_false_positive(looks, per_look=400, sims=2000, alpha=0.05, seed=2):
    g = np.random.default_rng(seed); hits=0
    for _ in range(sims):
        a = g.normal(size=per_look*looks); b = g.normal(size=per_look*looks)
        for k in range(1, looks+1):
            m = k*per_look
            p = stats.ttest_ind(a[:m], b[:m]).pvalue
            if p < alpha: hits += 1; break
    return hits/sims
print("one look  FPR:", aa_false_positive(1))
print("five looks FPR:", aa_false_positive(5))
# Step 5: fix: stricter alpha per look: same alpha per look, calibrated by simulation
print("five looks, alpha=0.016 each FPR:", aa_false_positive(5, alpha=0.016))

SRM bad : 1.973175290075393e-09

CUPED lift=1.086 se=0.176  var cut=80.7%  corr^2=0.806

Reading the output. The size function returns 14,751. A 5,030 to 4,970 split passes SRM (p = 0.549), while 5,300 to 4,700 fails with p about 2e-9. In the CUPED step the pre-period explains 80.6% of the variance of the outcome, so the standard error falls from 0.401 to 0.176, a variance cut of 80.7%. Notice that the raw lift (1.758) is far from the true lift of 1.0, and CUPED (1.086) is much closer: less noise means less luck. Peeking five times inflated false alarms from 4.7% to 15.0%. Using 0.016 per look brings it back to 5.0%.

Evaluation and acceptance criteria.

  • Sizing agrees with a simulation: at the computed n, power is 0.80 plus or minus 0.02 (use 2,000 runs).
  • SRM test rejects 5,300/4,700 and accepts 5,030/4,970.
  • CUPED variance reduction is close to the squared correlation ρ² of pre and post metrics.
  • A/A false positive rate: about 5% for one look, and about 5% for five looks with the corrected alpha.

Common pitfalls and how to detect them.

  1. Using post-treatment data as the covariate: CUPED needs a covariate measured before assignment. Detect: the covariate differs between arms.
  2. Skipping SRM: detect by always running it first and refusing to report if it fails.
  3. Peeking without correction: detect with the A/A simulation above.
  4. Wrong unit: randomise by customer but analyse by order. Detect: compare the number of rows with the number of customers.
  5. Underpowered "no effect": a non-significant result at low power says little. Report the confidence interval.

Three extensions.

  1. Add a two-sided confidence interval and a Bayesian credible interval to the output.
  2. Add a multiple-metric correction (Bonferroni and Benjamini-Hochberg).
  3. Add a sequential method with a proper alpha-spending function and compare with the simulation.

Interview talking points.

  • Q: What is SRM and why check it first? A: Sample ratio mismatch means the arm sizes differ from the plan more than chance allows. It means the experiment is broken, so any lift number is untrustworthy.
  • Q: How does CUPED help? A: It uses each customer's past behaviour to remove noise that has nothing to do with the treatment, so the same traffic gives a tighter answer or the test ends earlier.
  • Q: Why is peeking bad? A: Each look is another chance to see a fluke. With five looks, false alarms went from 5% to about 15% in my simulation.

15.4 Project: Demand forecasting with backtesting and intervals (#26)

Goal and why employers care. Forecast daily shop demand and prove the model is better than naive guesses, with an honest range around each number. Stock, staffing and delivery plans depend on forecasts, and a forecast without a baseline is just a story.

Skills used. Chapter 9, Forecasting and Time Series for Decisions (rolling-origin backtests, MASE, intervals); Chapter 5, Feature Engineering I (dates, lags); Chapter 12, From Prediction to Decision.

Data. The generator makes 730 days of orders: a slow upward trend, a yearly wave and a weekend bump, with Poisson noise (counts of orders). Real alternative: any public daily retail sales file; check the licence.

Architecture.

series y (730 days)
   |
   +-- fold k: train on days [0, cut), forecast the next 14 days
   |     models: naive | seasonal naive | ridge on lag1, lag7, weekday
   |     cut moves forward 14 days each fold (26 folds)
   v
errors per fold -> MAE, MAPE, MASE -> interval from past errors

Step-by-step build.

  1. Generate the series. Keep the last value, last week and the model all as callable functions with the same signature f(h, hist).
  2. Use a rolling-origin backtest: at each cut, use only the past, predict 14 days, record the error, move the cut forward. This copies real use. A random split would leak the future.
  3. Always include two baselines: naive (repeat the last value) and seasonal naive (repeat the same weekday last week).
  4. Report MAE (average absolute miss), MAPE (average percent miss) and MASE (error divided by the error of the in-sample seasonal naive; below 1 is better).
  5. Build an 80% prediction interval from past backtest errors. Check its coverage: about 80% of actuals should fall inside.
import numpy as np, pandas as pd
from sklearn.linear_model import Ridge

# Step 1: data
def make_sales(n_days=730, seed=3):
    r = np.random.default_rng(seed)
    d = pd.date_range("2023-01-01", periods=n_days, freq="D")
    t = np.arange(n_days)
    mu = 100 + 0.05*t + 15*np.sin(2*np.pi*t/365.25) + np.where(d.dayofweek>=5, 20, 0)
    return pd.Series(r.poisson(mu).astype(float), index=d)
y = make_sales()

# Step 2: models
def naive(h, hist): return np.repeat(hist.iloc[-1], h)
def seasonal_naive(h, hist): return np.array([hist.iloc[-7 + (i % 7)] for i in range(h)])
def lag_model(h, hist):
    # recursive model: lag1, lag7, dow
    idx = hist.index; v = hist.values
    rows = [(v[i-1], v[i-7], *np.eye(7)[idx[i].dayofweek]) for i in range(7, len(v))]
    m = Ridge(alpha=1.0).fit(np.array(rows), v[7:])
    out=[]; buf=list(v); day=idx[-1]
    for _ in range(h):
        day += pd.Timedelta(days=1)
        out.append(m.predict([[buf[-1], buf[-7], *np.eye(7)[day.dayofweek]]])[0]); buf.append(out[-1])
    return np.array(out)

# Step 3: rolling-origin backtest, 14-day horizon, origin moves 14 days each fold
H, step, start = 14, 14, 365
res = {k: [] for k in ["naive","seasonal_naive","lag_ridge"]}; actuals=[]; resid=[]
for cut in range(start, len(y)-H+1, step):
    hist, fut = y.iloc[:cut], y.iloc[cut:cut+H].values
    actuals.append(fut)
    for k, f in [("naive",naive),("seasonal_naive",seasonal_naive),("lag_ridge",lag_model)]:
        res[k].append(f(H, hist))
A = np.array(actuals)
print("days", len(y), "mean daily sales", round(y.mean(),1))
print("folds", len(A))
for k in res:
    P = np.array(res[k]); mae = np.abs(A-P).mean()
    print(f"{k:15s} MAE={mae:6.2f}  MAPE={np.mean(np.abs(A-P)/A)*100:5.2f}%")
# Step 4: MASE vs naive-7 in-sample scale
scale = np.abs(y.values[7:]-y.values[:-7]).mean()
P = np.array(res["lag_ridge"]); print("MASE lag_ridge:", round(np.abs(A-P).mean()/scale,3))
# Step 5: empirical 80% prediction interval prediction interval from backtest residuals (first half folds calibrate, second half test)
E = A-P; half = len(E)//2
lo, hi = np.quantile(E[:half], [0.1, 0.9])
cov = np.mean((E[half:]>=lo)&(E[half:]<=hi))
print(f"80% interval offsets [{lo:.1f}, {hi:.1f}] coverage on later folds: {cov:.3f}")
# Step 6: rolling calibration: use residuals from the 8 most recent finished folds
hits=[]
for k in range(8, len(E)):
    lo, hi = np.quantile(E[k-8:k], [0.1, 0.9])
    hits.append(np.mean((E[k]>=lo)&(E[k]<=hi)))
print(f"rolling-8-fold 80% interval coverage: {np.mean(hits):.3f} over {len(hits)} folds")

Reading the output. Naive misses by 21.07 orders a day, seasonal naive by 13.12, the ridge model by 12.61. So the model beats the strong baseline by only about 4%. That is an honest and useful message: most of the gain comes from knowing the weekly pattern, and a fancy model adds little. MASE of 1.005 says the model is about as good as the in-sample seasonal naive. Interval coverage was the surprise: an interval learned from the first half of the folds covered only 69.2% of later actuals, because the early errors were biased (the model underestimates a growing trend). Calibrating on only the 8 most recent folds gave 75.0%, closer to the 80% target. Say this in your README: intervals must be re-checked, and they drift when the world drifts.

Evaluation and acceptance criteria.

  • The model beats naive and seasonal naive in MAE on at least 60% of folds (count it; not printed above).
  • MASE reported; result below 1.1 and the README says whether it beats seasonal naive.
  • 80% interval coverage between 70% and 90% on held-out folds.
  • Backtest has at least 20 folds, and a time plot of forecast vs actual for 3 folds.

Common pitfalls and how to detect them.

  1. Shuffled split: future leaks into the past. Detect: the score is better than the rolling-origin score.
  2. Beating only naive: always compare with seasonal naive. Detect: print all baselines side by side.
  3. MAPE with small or zero values: huge or undefined errors. Detect: min of actuals; use MASE or MAE.
  4. Recursive forecast error compounding: errors at day 14 are bigger than day 1. Detect: error by horizon.
  5. Intervals from in-sample residuals: too narrow. Use backtest errors as shown.

Three extensions.

  1. Add holiday and promotion flags and measure the gain in MAE.
  2. Replace Ridge with gradient boosting on lag features and compare to the baselines.
  3. Add a quantile-regression interval and compare its coverage with the empirical one.

Interview talking points.

  • Q: Why a rolling-origin backtest? A: It repeats how the forecast is used, always predicting forward from the past. Shuffled splits let future patterns leak and flatter the model.
  • Q: Your model is only 4% better than seasonal naive. Ship it? A: Maybe not. I would weigh the 4% against the extra maintenance, and check whether the gain holds on busy weeks.
  • Q: How do you know the interval is honest? A: I count how often the actual falls inside across many backtest folds. Mine was 75% for an 80% target, so I would widen it slightly.

Chapter recap

  • A project starts with one sentence: who decides, what you predict, what action follows, and what number means success.
  • The repo should let a stranger run it in five minutes; commits should read like a story.
  • Generated data is fine if you say so, and it gives you a known answer to test against.
  • Churn: judge ranking (AUC) and honesty (calibration), then convert probability to money with a cost rule.

  • Forecasting: rolling-origin backtest, two baselines, MASE, and check interval coverage.

Practice set

1. (easy) Using the rule of thumb, how many customers per arm to detect a lift of 2 points on a 10% baseline? Answer: 16 × 0.1 × 0.9 / 0.02² = 3,600 per arm.

2. (easy) Arms of 5,300 and 4,700 were planned as 50/50. Compute the chi-square statistic. Answer: expected 5,000 each; (300²/5000) + (300²/5000) = 18 + 18 = 36. With 1 degree of freedom that is far beyond 3.84, so SRM fails.

3. (easy) A customer has churn probability 0.20, a save rate of 30%, a value of 100 and an offer cost of 5. Send or not? Answer: 0.2 × 0.3 × 100 − 5 = +1, so send. With probability 0.04 it is −3.8, so do not send.

4. (medium) Pre and post metrics have correlation 0.7. How much variance does CUPED remove? Answer: about ρ² = 0.49, so 49% is removed and 51% remains.

5. (medium) What is the maximum false alarm rate if you check 5 times at alpha 0.05 and the looks were independent? Why did our simulation show 15%, not this? Answer: 1 − 0.95⁵ = 22.6%. Looks share the same accumulating data, so they are positively correlated, and the real rate is lower (15% in our run).

6. (find the bug) A forecaster scores a model with train_test_split(shuffle=True) on daily sales and reports MAPE 3%. What is wrong and what do you do? Answer: shuffling leaks neighbouring days into training. Use a rolling-origin backtest; expect the error to rise.

7. (scenario) The churn model has AUC 0.82, but the marketing team says the offer made no difference. Give two reasons. Answer: (a) The model finds customers likely to leave, not customers who are persuadable; the save rate may be near zero. (b) No control group existed, so the effect cannot be measured. Fix: run a randomised holdout.

8. (interview) "Your A/B test shows p = 0.04 after the fifth daily look. Ship?" Answer: Not yet. Ask whether the stopping rule was fixed in advance. With five unplanned looks, the false alarm rate is far above 5%. Use the planned sample size or a sequential boundary, and check SRM first.
