In Chapter 5 you prepared single columns. But for churn, fraud, credit and demand, the strongest signals are rarely in one column. They are in behaviour over time: how recently did the customer act, how often, how much, is the pace rising or falling? In this chapter you will build those features from an orders table (recency, frequency, monetary value, rolling windows, trends, gaps, category shares), test whether each helps, choose the ones to keep with several selection methods, check that they are stable over time, and package everything in a pipeline so the feature you test is exactly the feature you serve. You will end with a function build_features(c, o, T) that you can reuse on any event table. A warning you will see proven: more features is not always better, and in our data a handful of simple ones carry nearly all the signal.

Running example. The shop data (make_data()), churn at prediction date T. For training we build a snapshot table at several dates (T = 1 May, 1 June, ..., 1 Nov 2024), stack them (16,152 rows), and test on T = 2025-01-01 (2,562 rows). Using several snapshots gives the model more examples, and the time split (train earlier, test later) copies real use. The label window of the last training snapshot (1 Nov plus 60 days = 31 Dec) ends before the test date, so there is no overlap in time.

6.1 RFM and Rolling-Window Features

BASIC EXPLANATION
RFM features summarise customer behaviour by recency, frequency and monetary value of purchases. Rolling-window features aggregate values over a recent period, such as the last 30 days.
INTUITION
A shopkeeper who knows his regular customers does not need a model to guess who is drifting away. He thinks: "She came yesterday, she comes every week, she spends a lot: safe." "He last came two months ago, and used to come weekly: gone." Those are three numbers: how recently (R), how often (F), how much (M). Rolling windows are the same idea measured over the last 7, 30 and 90 days.

The core function. Everything is computed from rows with order_ts < T; this is the point-in-time rule from Chapter 2. Read it slowly; we use it for the rest of the chapter.

def build_features(c, o, T):
    """One row per ACTIVE customer at T. Uses only orders with order_ts < T. Label from T..T+60d."""
    T = pd.Timestamp(T)
    base = make_label_table(c, o, pred_date=T)               # customers + churn label
    past = o[o.order_ts < T].copy()                           # <-- the leakage guard
    past["age_d"] = (T - past.order_ts).dt.days               # 1 = yesterday
    f = pd.DataFrame(index=base.customer_id)
    g = past.groupby("customer_id")
    f["recency_days"] = g.age_d.min()                         # R
    f["frequency_all"] = g.size()                             # F
    f["monetary_all"] = g.amount.sum()                        # M
    for w in (7, 30, 90):                                     # rolling windows
        s = past[past.age_d <= w].groupby("customer_id")
        f[f"orders_{w}d"] = s.size(); f[f"spend_{w}d"] = s.amount.sum()
    s = past[(past.age_d > 30) & (past.age_d <= 60)].groupby("customer_id")     # previous windows
    f["orders_30_60d"] = s.size(); f["spend_30_60d"] = s.amount.sum()
    s = past[(past.age_d > 60) & (past.age_d <= 90)].groupby("customer_id")
    f["orders_60_90d"] = s.size(); f["spend_60_90d"] = s.amount.sum()
    f = f.reindex(base.customer_id).fillna({k: 0 for k in f.columns if k != "recency_days"})
    f["avg_order_90d"] = np.where(f.orders_90d > 0, f.spend_90d / f.orders_90d.clip(lower=1), np.nan)
    f["ratio_7_30"] = f.orders_7d / (f.orders_30d + 1)
    f["trend_30_vs_prev60"] = (f.orders_30d + 1) / ((f.orders_30_60d + f.orders_60_90d) / 2 + 1)
    f["velocity_spend"] = f.spend_30d - f.spend_30_60d
    f["accel_spend"] = (f.spend_30d - f.spend_30_60d) - (f.spend_30_60d - f.spend_60_90d)
    # gaps between consecutive orders in the last 180 days
    p2 = past[past.age_d <= 180].sort_values(["customer_id", "order_ts"])
    p2["gap"] = p2.groupby("customer_id").order_ts.diff().dt.days
    gg = p2.groupby("customer_id").gap.agg(["mean", "max", "std"]); gg.columns = ["gap_mean", "gap_max", "gap_std"]
    f = f.join(gg, how="left")
    f["rec_over_gap"] = f.recency_days / (f.gap_mean.fillna(90) + 1)
    # customer x category shares in the last 90 days (cross-entity feature)
    q = past[past.age_d <= 90]
    cs = pd.crosstab(q.customer_id, q.category, normalize="index"); cs.columns = [f"share_{x}" for x in cs.columns]
    f = f.join(cs, how="left").fillna({k: 0 for k in cs.columns})
    out = base.merge(f.reset_index(), on="customer_id", how="left")
    out["tenure_days"] = (T - out.signup_date).dt.days
    out["is_pro"] = (out.plan == "pro").astype(int)
    out["T"] = T
    return out

Problem 6.1.1 A customer's orders before T were, in days before T: 2, 5, 9, 20 and 45, for Rs 100, 200, 150, 300 and 250. Compute orders_7d, orders_30d, spend_30d, orders_30_60d, spend_30_60d, trend_30_vs_prev60, gap_mean, gap_max, and rec_over_gap.

Step 1 (windows)orders_7d counts age_d <= 7: ages 2 and 5, so 2. orders_30d counts age_d <= 30: ages 2, 5, 9, 20, so 4. spend_30d = 100 + 200 + 150 + 300 = 750. The window 30 to 60 days holds age 45 only, so orders_30_60d = 1 and spend_30_60d = 250. The window 60 to 90 days is empty: orders_60_90d = 0.
Step 2 (trend)Formula (orders_30d + 1) / ((orders_30_60d + orders_60_90d)/2 + 1). Plug in (4 + 1) / ((1 + 0)/2 + 1) = 5 / 1.5 = 3.33. The "+1" terms are smoothing: they avoid dividing by zero and calm down tiny counts.
Step 3 (gaps)Sort the order times oldest to newest (ages 45, 20, 9, 5, 2). Gaps are 45-20 = 25, 20-9 = 11, 9-5 = 4, 5-2 = 3 days. Mean = (25 + 11 + 4 + 3) / 4 = 10.75; max = 25.
Step 4 (recency over gap)recency_days = 2 (the most recent order was 2 days ago). rec_over_gap = 2 / (10.75 + 1) = 0.17.
Answer2, 4, Rs 750, 1, Rs 250, trend 3.33, mean gap 10.75, max gap 25, rec_over_gap 0.17.
CheckTotal spend over all five orders = 1,000; windows 0-30 and 30-60 give 750 + 250 = 1,000 ✓. Verified in code too.
Why it mattersIn plain words: this customer is buying about three times faster in the last month than before, and ordered 2 days ago against a usual gap of 11 days, so they look very active. A value of rec_over_gap above 3 would say "three missed cycles": a warning sign.

RFM scoring and segments. Marketers rank each of R, F and M into 5 groups (5 = best) and combine them. pd.qcut cuts into quantile groups. For recency, a small number of days is good, so labels are reversed.

rfm = te[["customer_id", "recency_days", "frequency_all", "monetary_all", "churn"]].copy()
rfm["R"] = pd.qcut(rfm.recency_days, 5, labels=[5, 4, 3, 2, 1]).astype(int)
rfm["F"] = pd.qcut(rfm.frequency_all.rank(method="first"), 5, labels=[1, 2, 3, 4, 5]).astype(int)
rfm["M"] = pd.qcut(rfm.monetary_all.rank(method="first"), 5, labels=[1, 2, 3, 4, 5]).astype(int)
def seg(r):
    if r.R >= 4 and r.F >= 4: return "Champions"
    if r.R >= 4: return "Recent"
    if r.R <= 2 and r.F >= 4: return "At risk (were frequent)"
    if r.R <= 2: return "Lapsing"
    return "Middle"
rfm["segment"] = rfm.apply(seg, axis=1)

CheckSizes add up: 608 + 510 + 423 + 770 + 251 = 2,562 ✓. Overall rate: (608×0.028 + 510×0.069 + 423×0.121 + 770×0.536 + 251×0.538) / 2562 = (17.0 + 35.2 + 51.2 + 412.7 + 135.0) / 2562 = 651.1 / 2562 = 0.254 ✓.

Connection to the real job. RFM-style features are the first thing built for churn, CLV (Chapter 11), fraud (transactions in the last hour, day, week) and credit (utilisation over the last 3, 6 and 12 months). Windows are almost always 7, 30, 90 days or similar, chosen to match the business rhythm.

Applications

  • E-commerce and retail: churn and next-purchase propensity.
  • Fraud: card transactions in the last 1 hour and 24 hours.
  • Banking: average balance and credit utilisation over 3, 6, 12 months.
  • Operations: failed-payment counts in the last 5, 15, 60 minutes (the same rolling windows).
COMMON MISTAKE
Computing windows from the whole table and filtering by "last 30 days" relative to today, not to T. A training snapshot at 2024-08-01 must use 2024-08-01 as its "today". Always pass T into the function.

6.2 Trends, Lags, Cross-Entity Features, and Do They Help?

BASIC EXPLANATION
Trend features measure change over time, and lag features use earlier values. Cross-entity features aggregate over related entities, and a feature is checked by testing whether it improves a validation metric.
INTUITION
Two customers both ordered 3 times last month. One used to order 10 times a month (falling), the other used to order once (rising). Same count, opposite story. Trends, gaps and changes carry that story. A car's speed tells you where you are; velocity and acceleration tell you where you are heading.

We have not yet checked whether these help. A strong habit: add features in groups and measure each group on the later test period. We train a gradient boosting model (a tree-based model that handles missing values; see study/ml/) on the stacked snapshots and test on January 2025.

AnswerBehavioural features are the big win (+0.28 AUC over a profile-only model). The extra 21 features add nothing measurable in this dataset.
CheckOur synthetic customers churn according to their order rate and silence, so recency already captures nearly all of it (a single feature had AUC 0.880 in Chapter 3). Real data is richer, but the lesson holds.

Here both agree, because this synthetic world does not change over time. In real data with trends, promotions or a changing user base, the random split is optimistic and the time split is honest. 2,085 of the 2,562 test customers were also in training: this is normal in churn, but it means customer-level repeats must stay on one side of any random split (use group splits, GroupKFold, in that case).

Problem 6.2.2 Design three more features for fraud on card transactions: velocity, entity aggregates and a graph feature. Write them as precise definitions.

6.3 Feature Selection and Stability

BASIC EXPLANATION
Feature selection chooses a useful subset of features to reduce noise and complexity. Stability checks whether the selected features stay the same across different samples and time periods.
INTUITION
Packing for a trip: you could take everything, but a heavy bag slows you down, and half of it you never use. Selection removes features that are useless (no information), redundant (same information twice), dangerous (leaky) or unstable (behave differently now than before).

Step 0: hygiene. Remove (1) leakage features (Chapter 3), (2) constant and near-constant columns (nunique() <= 1), (3) duplicated information (correlation above 0.95).

Selection methods

FamilyIdeaTools

CheckThe difference of 0.005 is within noise, so the honest statement is "equal". Remember we looked at test importances to choose the features, which is a mild form of peeking (Chapter 4); in production you would pick the features on a validation period and keep the January test untouched.
Why it mattersA model with 5 features is cheaper to compute, easier to explain, easier to monitor and has fewer ways to break. Also, different methods choose different sets: that is a sign that many features are interchangeable, so prefer the cheapest to compute and the most stable.

Stability: PSI per feature. A feature can be strong in training and then change meaning or shape in production. The Population Stability Index compares the distribution of a feature in an old period (expected) and a new period (actual) over bins:

PSI = Σ (actual% − expected%) × ln(actual% / expected%) over bins.

Common reading: below 0.1 stable, 0.1 to 0.25 moderate shift (watch), above 0.25 large shift (investigate or retrain). (These are rules of thumb from credit risk, not laws.)

Now on real data: compare May 2024 customers (old) with January 2025 customers (new), then simulate a shift.

def psi(expected, actual, bins=10):
    qs = np.unique(np.nanquantile(expected, np.linspace(0, 1, bins + 1)))
    qs[0], qs[-1] = -np.inf, np.inf
    e = np.histogram(expected.dropna(), qs)[0] / expected.notna().sum()
    a = np.histogram(actual.dropna(), qs)[0] / actual.notna().sum()
    e = np.clip(e, 1e-4, None); a = np.clip(a, 1e-4, None)
    return float(np.sum((a - e) * np.log(a / e)))
old = tr[tr["T"] == pd.Timestamp("2024-05-01")]
print({f: round(psi(old[f], te[f]), 3) for f in ["recency_days", "orders_90d", "spend_90d", "tenure_days", "gap_mean"]})
for k in (1.0, 1.2, 1.5, 2.0):
    print("spend x", k, "PSI", round(psi(old.spend_90d, te.spend_90d * k), 3))

6.4 Leakage-Safe Pipelines and Training-Serving Skew

BASIC EXPLANATION
A leakage-safe pipeline performs all preprocessing inside the training procedure so that test data do not influence it. Training-serving skew is a difference between how features are computed in training and in production.
INTUITION
A recipe must be the same in the test kitchen and the restaurant. If the test kitchen uses a hand-crafted sauce and the restaurant a factory sauce, the dish tastes different, and nobody knows why customers complain. In ML this is training-serving skew: the features at training time are computed one way, in production another way.

Words you need

WordMeaningExample
PipelineOrdered steps (impute, scale, encode, model) that are fitted togetherPipeline([...])
ColumnTransformerApplies different steps to different columnsnumbers vs categories

Why pipelines. Every learned number (medians, means, category lists, selected columns, encoders) must be learned from training rows only, and then applied unchanged to validation, test and live data. A scikit-learn Pipeline does this for you and also makes cross-validation honest: in each fold it refits all steps using only that fold's training part.

Problem 6.4.1 Show the danger. We make 400 rows of pure noise (1,000 random features, random labels). The true AUC of any model is 0.5. Compare selecting the 20 "best" features before cross-validation versus inside a pipeline.

from sklearn.feature_selection import SelectKBest, f_classif
from sklearn.model_selection import cross_val_score, StratifiedKFold
from sklearn.pipeline import Pipeline
rng = np.random.default_rng(0)
n, p = 400, 1000
X = rng.normal(size=(n, p)); y = rng.integers(0, 2, n)
cv = StratifiedKFold(5, shuffle=True, random_state=0)
Xk = SelectKBest(f_classif, k=20).fit_transform(X, y)                 # selection uses ALL labels (leak)
leak = cross_val_score(LogisticRegression(max_iter=1000), Xk, y, cv=cv, scoring="roc_auc").mean()
pipe = Pipeline([("sel", SelectKBest(f_classif, k=20)), ("clf", LogisticRegression(max_iter=1000))])
safe = cross_val_score(pipe, X, y, cv=cv, scoring="roc_auc").mean()   # selection refit inside each fold
print("pure-noise data: selection outside CV AUC", round(leak, 3), " selection inside pipeline AUC", round(safe, 3))
pure-noise data: selection outside CV AUC 0.757  selection inside pipeline AUC 0.517
  • Answer Selecting features on all the data first produced AUC 0.757 on random noise, a fake "skill". Inside the pipeline the AUC is 0.517, correctly near 0.5.
  • Check The labels were random coin flips, so any honest AUC must be near 0.5 ✓.
  • Why it matters With 1,000 features, a few correlate with the labels by chance; picking them with the labels in view and then "testing" on the same labels fools you. This is the same leak as Chapter 4's validation peeking. Rule: every step that looks at the target (selection, target encoding, imputation by group mean, resampling) belongs inside the cross-validation loop.

A full production-style pipeline. Numeric columns: median imputation (with missing flags), scaling. Categorical: one-hot with unknown categories ignored. Then logistic regression.

from sklearn.compose import ColumnTransformer
from sklearn.preprocessing import OneHotEncoder, StandardScaler
from sklearn.impute import SimpleImputer
num = ["recency_days", "orders_30d", "orders_90d", "spend_90d", "gap_mean", "rec_over_gap", "tenure_days"]
cat = ["plan", "channel", "city"]
pre = ColumnTransformer([
    ("num", Pipeline([("imp", SimpleImputer(strategy="median", add_indicator=True)), ("sc", StandardScaler())]), num),
    ("cat", OneHotEncoder(handle_unknown="ignore"), cat)])
pipe = Pipeline([("pre", pre), ("clf", LogisticRegression(max_iter=2000))]).fit(tr[num + cat], tr.churn)
print("pipeline AUC on Jan-25:", round(roc_auc_score(te.churn, pipe.predict_proba(te[num + cat])[:, 1]), 3))
new = te[num + cat].head(2).copy()
new.loc[new.index[0], "city"] = "Jaipur"; new.loc[new.index[1], "gap_mean"] = np.nan
print("scores for odd rows (unseen city, missing gap):", pipe.predict_proba(new)[:, 1].round(3))
print("n transformed columns:", pipe.named_steps["pre"].transform(te[num + cat].head(1)).shape[1])
pipeline AUC on Jan-25: 0.893
scores for odd rows (unseen city, missing gap): [0.102 0.631]
n transformed columns: 19

Line by line: add_indicator=True adds a 0/1 column for each numeric feature that had missing values in training (gap_mean), which is why we get 19 columns: 7 numeric + 1 flag + 2 + 3 + 6 one-hot levels = 19. handle_unknown="ignore" means a city never seen in training ("Jaipur") becomes all zeros instead of crashing. The odd rows still get scores. A plain logistic regression pipeline with 7 numeric features and 3 categoricals gives 0.893, equal to the boosted trees with many features. We can save the fitted pipeline as one object (joblib.dump(pipe, "model.joblib"), not run here) and load it in the serving code, which guarantees the same median, same scaling and same categories.

Problem 6.4.2 Why is our build_features(c, o, T) also a skew-prevention tool? Explain, and name two ways it could still go wrong in production.

Step 1The same function creates features for training (T = 1 May to 1 Nov) and for scoring (T = today). One definition, no rewriting in another language.
Step 2Risk one: in production the orders table may be updated late (Chapter 2: today's data is 59% complete), so orders_7d is smaller than in training, where we used final data. Fix: train on data "as of T" or apply the finalisation lag.
Step 3Risk two: time zones or a changed definition of an "order" (cancelled orders now counted). Fix: tests on feature distributions (PSI) and unit tests on build_features.
AnswerOne shared function removes duplicated logic; the remaining risks are late data and definition changes, caught by monitoring.
CheckIf you score yesterday's customers with partially loaded data and recency looks 1 day longer than it was, the model will think more of them have churned: monitor the mean of key features daily.
Why it mattersMost "the model got worse in production" stories are skew, not algorithms. Production topics continue in Chapter 13 and study/mlops/.

Tools (not installed or run here, so check their documentation): feature-engine (transformers for scikit-learn), category_encoders (many encoders), featuretools (automatic features from related tables), tsfresh (automatic time-series features), polars and duckdb (fast aggregations on big tables), a feature store such as Feast.

The picture

TRAIN:  raw rows --build_features(T_i)--> features --[impute -> scale -> encode -> model]--> fitted pipeline

Connection to the real job. The ML engineer will ask you for exactly this: one function (or SQL view) that creates features at a given time, a fitted pipeline file, and a list of expected ranges. Giving them a messy notebook delays deployment by weeks.

Applications

  • MLOps: shipping one fitted pipeline object; schema checks at the API.
  • Fraud and credit: real-time feature computation with strict latency.
  • Data Engineering: feature tables that are point-in-time correct.
  • Any CV-based model comparison: pipelines inside cross-validation.
COMMON MISTAKE
Fitting an imputer, scaler or selector on the full dataset "to save time". The effect is sometimes small (scalers) and sometimes huge (target-aware steps, as 0.757 vs 0.517 showed). Use a pipeline always; it costs nothing.

Chapter recap

  • Behaviour over time (recency, frequency, monetary, windows, trends, gaps) is the strongest feature family: it lifted AUC from 0.612 (profile only) to 0.891.
  • Always compute features from rows before T, with age_d relative to T, and pass T into the feature function.
  • Do one example by hand before running it on millions of rows.
  • RFM segments with no model separated customers 19 to 1 (53.8% vs 2.8% churn).
  • Add features in groups and test on a later period: 21 more features added no AUC in our data.
  • Time-split your validation; keep customer repeats on one side if you split randomly.
  • Selection methods: hygiene, filter (correlation, MI), embedded (L1), wrapper (RFE), permutation importance; five features matched twenty-five.
  • PSI per feature (below 0.1 stable, 0.1 to 0.25 watch, above 0.25 act); "time since" features drift by design.
  • Put everything that learns from data, especially from the target, inside a pipeline; selection outside CV gave 0.757 on pure noise vs 0.517 inside.
  • One feature function and one fitted pipeline for training and serving prevents skew.

Problem 6.P.8 (hard) A random split on stacked snapshots gives AUC 0.93, a time split gives 0.86. Which do you report, and why do they differ? Answer: 0.86. The random split puts the same customers and similar periods in train and test, so it is optimistic; the time split copies real use (predict the future from the past).

Problem 6.P.9 (interview) "Your model's AUC in production is 0.08 lower than in testing. How do you investigate?" Answer: Check training-serving skew first: compare feature distributions (PSI, means, missing rates) between training data and live data; check late-arriving data, time zones and definition changes; check label delay in monitoring; then check population drift and leakage in the original validation (random split, target encoding outside folds).

Problem 6.P.10 (interview) "How would you select features for a model that must run in 50 ms?" Answer: Start with permutation importance and a cost column (compute time and data-source latency) per feature; drop leakage, duplicates and unstable features; prefer features from fast stores (precomputed aggregates); keep the smallest set within 1 to 2 AUC points of the full model; test latency end to end.
