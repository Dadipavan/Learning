A notebook or a single script is fine for an experiment. A real job gives you a repository with fifty files, ten libraries, three teammates and a deadline. Then new questions appear. How do I split code into files and import between them? Why does my laptop work but the server break? Why did my pipeline crash because someone passed a string instead of a number? 9.1 Modules, Packages and __main__

INTUITION
A module is a chapter, a package is the whole book, and an import is a bookmark to a chapter in another book. You split code into files so each file does one job and you can find things. Without modules you would scroll through a 5,000-line file.

Words you need

WordPlain meaning
moduleOne .py file. import utils loads utils.py
packageA folder of modules (it has an __init__.py)
__init__.pyRuns when the package is first imported; defines what the package exposes
__name__Variable holding the module's name. It is "__main__" when the file is run directly
absolute importfrom shop.utils import round2 (full path)
relative importfrom .utils import round2 (dot means "this package")
sys.modulesPython's cache of already imported modules

How an import works. Python looks in sys.modules first. If the module is not there, it searches folders (the script's folder, then installed libraries), runs the file top to bottom once, and stores the result in the cache. Any later import reuses it.

Problem 9.1.1 Build a tiny package called shop and run it.

Step 1Make a folder shop/ containing __init__.py, pricing.py, utils.py and __main__.py.
Step 2pricing.py imports from utils.py with a relative import. __init__.py re-exports total_with_tax.
Step 3Run with python3 -m shop 250.

The files (each with a print so you can see when it runs):

# shop/__init__.py
"""shop package."""
from .pricing import total_with_tax
__all__ = ["total_with_tax"]
__version__ = "0.1.0"
print("shop/__init__ ran")
# shop/pricing.py
from .utils import round2
TAX = 0.18
def total_with_tax(amount):
    return round2(amount * (1 + TAX))
print("pricing imported, __name__ =", __name__)
# shop/utils.py
def round2(x):
    return round(x, 2)
# shop/__main__.py
from shop import total_with_tax
import sys
def main():
    amount = float(sys.argv[1]) if len(sys.argv) > 1 else 100.0
    print("total:", total_with_tax(amount))
if __name__ == "__main__":
    main()

Before you run it, predict: which line prints first, shop/__init__ ran or pricing imported?

python3 -m shop 250
python3 -c "import shop; print(shop.__version__, shop.total_with_tax(1000))"
pricing imported, __name__ = shop.pricing
shop/__init__ ran
total: 295.0
pricing imported, __name__ = shop.pricing
shop/__init__ ran
0.1.0 1180.0

Line by line: __init__.py begins running, hits from .pricing import ..., and jumps into pricing.py first. So "pricing imported" appears before "shop/__init__ ran", which is the last line of __init__. Inside pricing, __name__ is shop.pricing (not __main__), since it was imported. python3 -m shop runs __main__.py. 250 * 1.18 = 295.0 and 1000 * 1.18 = 1180.0.

  • Answer pricing imported prints first, because the package's __init__ has to import pricing before it can reach its own last line.
  • Check 250 x 1.18 = 295.0. Correct. The import message does not repeat within one run, which shows the cache at work.
  • Why it matters python -m package is the clean way to run a package. Entry points like uvicorn app.main:app rely on the same import rules.

Why if __name__ == "__main__":? When the file is imported, __name__ is the module name and main() does not run. When the file is run directly, __name__ is "__main__" and main() runs. This lets one file be both a library and a script. Without the guard, importing the file would start the whole program.

Problem 9.1.2 The most common relative-import error. Run a module file directly instead of as part of a package:

python3 shop/pricing.py
    from .utils import round2
ImportError: attempted relative import with no known parent package

Running a file directly makes Python treat it as a top-level script, with no package around it, so the dot has nothing to point to.

  • Answer Run it as python3 -m shop.pricing from the project root, or run the package with -m shop.
  • Check -m sets __package__, so the relative import has a parent.
  • Why it matters Every new Python engineer hits this error in week one.

The picture

project/
  shop/                  <- package (folder with __init__.py)
    __init__.py          <- runs on "import shop"
    __main__.py          <- runs on "python -m shop"
    pricing.py  --uses--> utils.py   (from .utils import round2)

Read it as: you run from project/, import shop finds the folder, runs __init__.py, and from there Python can reach sibling files.

Connection to real projects. A data repository usually has src/yourproject/ with ingest.py, transform.py, models.py. Airflow DAGs, FastAPI apps and CLI tools are all packages. __all__ and __init__ decide the public surface other teams depend on.

Applications

  • Data Engineering: one package of reusable transforms shared by many pipelines.
  • Machine Learning: features.py, train.py, evaluate.py imported by notebooks and jobs.
  • MLOps: python -m mypackage.serve as the container start command.
  • Backend: app/ package with routers/, models/, services/.
COMMON MISTAKE
Naming your file after a library, for example random.py or json.py. Python then imports your file instead of the standard one and strange errors follow. Never name your files after standard or installed libraries.

Check yourself

  1. What does __name__ equal when a file is run with python file.py?

Answer: "__main__".

  1. Why does the import message print only once even if three files import the same module?

Answer: Python caches the module in sys.modules after the first import.

  1. What does from .utils import x need?

Answer: The file must be part of a package that was imported or run with -m.

9.2 Circular Imports and How to Avoid Them

INTUITION
Two people each say "I will leave only after you leave first." Nobody leaves. A circular import is the same deadlock: a.py needs b.py and b.py needs a.py, and Python is stuck halfway through loading one of them.

Problem 9.2.1 Create the problem. a.py imports from b.py, and b.py imports from a.py.

# a.py
from b import fb
def fa(): return "fa"
# b.py
from a import fa
def fb(): return "fb"

Predict: what happens on import a?

python3 -c "import a"
  File "/private/tmp/c9/circ/b.py", line 1, in <module>
    from a import fa
ImportError: cannot import name 'fa' from 'a' (consider renaming '/private/tmp/c9/circ/a.py' if it has the same name as a library you intended to import)

Step by step: Python starts a, reaches line 1, and starts loading b. b asks for fa from a, but a is only half loaded and fa is defined on line 2, which has not run yet. So the name does not exist, and Python raises ImportError.

  • Answer An ImportError because a is still only partly loaded when b asks for fa.
  • Check The traceback points at line 1 of b.py.
  • Why it matters In real projects the cycle is often three or four files long, which makes it hard to see.

Fixes, best first

  1. Move shared code into a third module that both import (the usual best fix).
  2. Import inside the function that needs it (a deferred import).
  3. Import the module, not the name (import a and use a.fa later).

Here is fix 2 in action:

# b.py
def fb():
    from a import fa      # deferred import
    return "fb+" + fa()
python3 -c "import a; print(a.fb())"
fb+fa

By the time fb() is called, both modules are fully loaded, so the import succeeds.

  • Answer It prints fb+fa.
  • Check fb() returns "fb+" followed by what fa() returns, "fa".
  • Why it matters A deferred import is a quick patch. A cycle often means the design should change: one module is doing two jobs (see Single Responsibility in Chapter 8).

Connection to real projects. Cycles appear when models.py needs services.py for a helper while services.py imports models.py. The cure is a layered design: models imports nothing from services; services may import models.

Applications

  • Backend: layered packages with one-way dependencies.
  • Machine Learning: keep config.py free of imports from training code.
  • Type hints: if TYPE_CHECKING: imports avoid cycles that only exist for annotations.
COMMON MISTAKE
"Fixing" a cycle by shuffling import lines until it happens to work. It will break again after the next edit. Break the cycle by design.

Check yourself

  1. Why does a circular import fail?

Answer: One module is only partly loaded when the other asks for a name from it.

  1. Name the cleanest fix.

Answer: Move the shared code into a third module.

  1. What is a deferred import?

Answer: An import written inside a function, so it runs at call time.

9.3 Virtual Environments and Package Managers

INTUITION
Imagine each project has its own toolbox. Project A needs a hammer version 1; project B needs version 2. If you keep one shared toolbox for the whole house, you cannot have both. A virtual environment (venv) is a private toolbox for one project, so libraries and their versions never clash.

Words you need

WordPlain meaning
package (library)Code written by others that you install, like pandas
pipThe standard tool that installs packages from PyPI (the public package index)
virtual environmentA folder with its own Python and its own installed packages
site-packagesThe folder where installed packages live
dependencyA library your project needs
lock fileA file that records the exact versions installed

Problem 9.3.1 Create a venv and prove it is isolated.

Step 1python3 -m venv venvdemo creates the folder.
Step 2Look inside, and ask the venv's Python whether it is in a venv.
Step 3Ask the normal Python the same question.
python3 -m venv venvdemo
ls venvdemo
./venvdemo/bin/python -c "import sys; print(sys.prefix != sys.base_prefix)"
./venvdemo/bin/pip freeze | wc -l
python3 -c "import sys; print(sys.prefix != sys.base_prefix)"
bin
include
lib
pyvenv.cfg
True
0
False
  • Answer The venv is a small folder with its own bin (Python and pip), lib (packages) and a pyvenv.cfg file. Inside it, sys.prefix differs from sys.base_prefix (so the check is True). pip freeze lists nothing: the venv starts empty. The normal Python prints False.
  • Check pip freeze printing 0 lines proves your global libraries do not leak in.
  • Why it matters "It works on my machine" is usually a different set of library versions.

On macOS and Linux you "activate" with source venvdemo/bin/activate; on Windows venvdemo\Scripts\activate. Activating just puts the venv's bin first on your PATH, so python and pip point at it. You can skip activation by calling ./venvdemo/bin/python directly, which is what scripts and CI do.

The standard workflow (not run here, needs network)

python3 -m venv .venv
source .venv/bin/activate
pip install requests pandas
pip freeze > requirements.txt     # exact versions recorded
pip install -r requirements.txt   # on another machine

Tool comparison (not run here: none of these were installed, and there was no network)

Typical commands, shown for orientation only (check each tool's own docs, as options change by version):

pip-compile requirements.in           # pip-tools
poetry add requests                   # poetry
uv venv && uv pip install requests    # uv
conda create -n ds python=3.12        # conda

Connection to real projects. CI servers and Docker images build a fresh environment from your lock file, so your program runs the same way everywhere. ML projects often need conda or Docker because GPU libraries are not pure Python.

Applications

  • Data Science: one environment per project so a library upgrade never breaks an old analysis.
  • Machine Learning: pinned versions of numpy, scikit-learn, torch so results can be reproduced.
  • MLOps: a lock file copied into the Docker build.
  • Data Engineering: the same pinned environment locally and in the scheduler.
COMMON MISTAKE
Running pip install while no venv is active, so packages go into your global Python. Check which python (or python -c "import sys; print(sys.prefix)") before installing. Also, never commit the .venv folder to Git; add it to .gitignore.

Check yourself

  1. What problem does a venv solve?

Answer: It stops different projects from sharing, and clashing over, library versions.

  1. What does pip freeze print?

Answer: Every installed package with its exact version.

  1. When prefer conda over pip?

Answer: When you need non-Python binaries such as CUDA or C libraries.

9.4 pyproject.toml, Version Pinning and Supply-Chain Awareness

INTUITION
pyproject.toml is the project's ID card: its name, version, which Python it needs and which libraries it depends on. One file, readable by pip, poetry, uv and build tools.

How it works. The file uses TOML, a simple config format. Python 3.11+ can read it with the built-in tomllib.

Problem 9.4.1 Write a minimal pyproject.toml and parse it.

import tomllib
text = """
[project]
name = "shop"
version = "0.1.0"
requires-python = ">=3.10"
dependencies = ["requests>=2.31"]
"""
print(tomllib.loads(text))
{'project': {'name': 'shop', 'version': '0.1.0', 'requires-python': '>=3.10', 'dependencies': ['requests>=2.31']}}
  • Answer TOML becomes a normal nested dictionary. Section [project] holds metadata. dependencies is a list of requirement strings.
  • Check d["project"]["name"] would give "shop".
  • Why it matters Everything that builds, installs or publishes your project reads this one dictionary.

A fuller file also names a build tool (not run here, since building needs a build backend that may need download):

[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"

[project.scripts]
shop = "shop.__main__:main"

[project.scripts] makes pip install . create a shop command that calls main(). Chapter 13 covers building and publishing.

Version specifiers

WrittenMeaningUse
requests==2.31.0Exactly this versionLock files (reproducible)
requests>=2.31This or newerLibraries (flexible)
requests~=2.31Compatible: at least 2.31, below 3.0Apps wanting safe updates
requests>=2.31,<3A rangeWhen a major version breaks

Rule of thumb: libraries declare flexible ranges; applications ship a fully pinned lock file.

Dependency security and supply chain

A supply-chain attack is when attackers hide bad code inside a library you install, or inside one of that library's own dependencies. Your project may depend on hundreds of packages you never chose. Protect yourself:

  • Pin exact versions and review upgrades.
  • Run pip-audit (not run here) to check installed packages against known vulnerability lists. Dependabot on GitHub opens pull requests for risky or old versions.
  • Install only from sources you trust. Watch for look-alike names (reqeusts instead of requests) called typosquatting.
  • Keep dependencies few. Every library is trust you give away.

Problem 9.4.2 List the installed distributions with the standard library (works in any environment).

import importlib.metadata as m
print(sorted(d.metadata['Name'] for d in m.distributions())[:5])
['Jinja2', 'MarkupSafe', 'PyYAML', 'Pygments', 'Send2Trash']
  • Answer This is what is installed in the global Python on this machine. Inside a clean venv the list would be much shorter (just pip, maybe setuptools).
  • Check Compare with pip freeze output.
  • Why it matters In an audit you must be able to say exactly what code runs in production.

Connection to real projects. Security teams at large companies scan dependencies. A pinned lock file plus pip-audit in CI is a normal requirement, and it is also a strong signal in an interview.

Applications

  • MLOps: reproducible model builds and audit trails.
  • Data Engineering: upgrading one library without breaking twenty pipelines.
  • Security / compliance: list of dependencies with versions.
COMMON MISTAKE
Leaving versions unpinned in an application, so the next pip install silently downloads a new major version and your code breaks on Monday. Pin applications. Flexible ranges are for libraries.

Check yourself

  1. What does ~=2.31 allow?

Answer: Versions from 2.31 up to, but not including, 3.0.

  1. Why pin versions in an application?

Answer: So every install gets the same code and results are reproducible.

  1. What is typosquatting?

Answer: A malicious package with a name close to a popular one, hoping you mistype.

9.5 Type Hints and mypy

INTUITION
A label on a jar tells you what is inside before you open it. A type hint is a label on a variable or function: "this takes a list of floats and gives back a float". Python does not enforce the label when running, but tools and your teammates can read it, and an editor can warn you before you run anything.

Words you need

WordPlain meaning
type hint (annotation)A note like x: int or -> float about the expected type
static type checkerA tool (mypy, pyright) that reads hints and finds mismatches without running the code
Optional[X]Either an X or None (same as `X \
Union[A, B]Either an A or a B (same as `A \
Callable[[int], int]A function taking an int and returning an int
TypeVarA placeholder type, so "the output type equals the input type"
ProtocolAn interface matched by shape (Chapter 8)

Problem 9.5.1 Common hints, run together.

from typing import Optional, Union, Callable, TypeVar, Protocol, Iterable

def mean(xs: list[float]) -> float:
    return sum(xs) / len(xs)

def find_user(users: dict[int, str], uid: int) -> Optional[str]:
    return users.get(uid)

def parse(v: Union[int, str]) -> int:
    return int(v)
def parse2(v: int | str) -> int:    # modern spelling
    return int(v)

def apply(f: Callable[[int], int], xs: Iterable[int]) -> list[int]:
    return [f(x) for x in xs]

T = TypeVar("T")
def first(xs: list[T]) -> T:
    return xs[0]
def first_new[T](xs: list[T]) -> T:   # Python 3.12+ syntax
    return xs[0]

class HasName(Protocol):
    name: str
def greet(x: HasName) -> str: return "hi " + x.name

print(mean([1,2,3]), find_user({1:"a"}, 2), parse("7"), parse2(8))
print(apply(lambda n: n*n, [1,2,3]), first(["x","y"]), first_new([10,20]))
2.0 None 7 8
[1, 4, 9] x 10
  • Answer mean([1,2,3]) = 6/3 = 2.0. find_user returns None because key 2 is missing, which is exactly why its hint is Optional[str]. first returns the same type as the list holds (str for strings, int for ints). On Python 3.9 and later, built-in list[float] and dict[int, str] replace the old typing.List and typing.Dict. On 3.10+ you can write int | str. The def first_new[T] syntax needs Python 3.12 or later.
  • Check 1+2+3 = 6, divided by 3 = 2.0. 1*1, 2*2, 3*3 = 1, 4, 9.
  • Why it matters Old code uses List[int] and Optional. You will see both styles at work, so know both.

Hints are not enforced at runtime. Predict: does mean("abc") complain about the hint?

try:
    print(mean("abc"))
except TypeError as e: print("TypeError:", e)
from typing import get_type_hints
print(get_type_hints(mean))
TypeError: unsupported operand type(s) for +: 'int' and 'str'
{'xs': list[float], 'return': <class 'float'>}
  • Answer No. Python ignored the hint. The error came from sum() trying 0 + "a", not from the label. The hints are stored in mean.__annotations__ for tools to read.
  • Check The error is about int and str, not about list[float].
  • Why it matters If you want checking, you need a checker such as mypy or runtime validation (section 9.6).

mypy (not run here, no network). mypy is the standard static checker. You run it on your files and it reports mismatches without executing the program:

pip install mypy
mypy shop/

For the call mean("abc") above, mypy would report an error similar to Argument 1 to "mean" has incompatible type "str"; expected "list[float]". Exact wording varies by version. Treat mypy as a test that runs in CI. Start with the default settings, and tighten gradually (for example --strict) on new code.

Connection to real projects. Teams add hints to shared functions, so the editor can autocomplete and catch mistakes. FastAPI (Chapter 12) reads hints to build request validation and API docs automatically.

Applications

  • Data Engineering: typed transform functions reduce bugs in large pipelines.
  • Machine Learning: hints on function inputs ("expects a DataFrame with these columns" in docstrings plus pd.DataFrame hints).
  • Backend: FastAPI uses hints for validation and docs.
  • Code review: hints act as documentation that cannot go stale unnoticed.
COMMON MISTAKE
Thinking hints make Python check types at runtime. They do not. A function annotated -> int can happily return a string. Also avoid the old List, Dict imports in new code.

Check yourself

  1. What does Optional[str] mean?

Answer: A str or None.

  1. Does Python raise an error when you pass the wrong type to an annotated function?

Answer: No. Only a checker like mypy, or your own validation, would.

  1. What is TypeVar for?

Answer: To say that the output type depends on the input type.

9.6 Data Validation: By Hand and with pydantic

INTUITION
A security guard at a building door checks every visitor. Data arriving from outside (a web request, a CSV, a model output) cannot be trusted. Validation is the guard: it checks types and rules at the door, and rejects bad data with a clear message, before it spreads through your pipeline.

Why not just trust type hints? Hints are not enforced (section 9.5). Real input is a string like "42" where you wanted the number 42, or "nomail" where you wanted an email. A validation library converts what it can and rejects the rest.

Problem 9.6.1 Write a small validator using only the standard library. It converts ("coerces") values to the declared type and collects every error.

from dataclasses import dataclass, fields

class ValidationError(Exception):
    pass

@dataclass
class Order:
    order_id: int
    email: str
    amount: float
    def __post_init__(self):
        errors = []
        for f in fields(self):
            v = getattr(self, f.name)
            try:
                setattr(self, f.name, f.type(v))   # coerce like pydantic lax mode
            except (TypeError, ValueError):
                errors.append(f"{f.name}: cannot convert {v!r} to {f.type.__name__}")
        if not errors and "@" not in self.email: errors.append("email: missing @")
        if not errors and self.amount <= 0: errors.append("amount: must be > 0")
        if errors: raise ValidationError("; ".join(errors))

print(Order("42", "a@b.com", "99.5"))
for bad in [("x", "a@b.com", 5), (1, "nomail", 5), (1, "a@b.com", -3)]:
    try: Order(*bad)
    except ValidationError as e: print("rejected:", e)
Order(order_id=42, email='a@b.com', amount=99.5)
rejected: order_id: cannot convert 'x' to int
rejected: email: missing @
rejected: amount: must be > 0

Step by step: fields(self) lists the declared fields. For each one we call its type as a function: int("42") gives 42 and float("99.5") gives 99.5, but int("x") raises ValueError, which we turn into a message. After conversion we apply business rules (an email needs @, amount must be positive).

  • Answer The good order is accepted and its text values are converted to int and float. The three bad ones are each rejected with a clear reason.
  • Check 42 is now an int (the repr shows order_id=42, without quotes).
  • Why it matters This is the pattern behind every validation library. Note that this tiny version assumes plain types such as int, str, float; real libraries handle lists, nested objects and more.

pydantic (not run here, not installed and no network). The library pydantic does this with far more features. This is the standard usage in version 2 (check the docs for your version):

from pydantic import BaseModel, EmailStr, Field, ValidationError

class Order(BaseModel):
    order_id: int
    email: EmailStr          # needs: pip install "pydantic[email]"
    amount: float = Field(gt=0)

try:
    Order(order_id="42", email="a@b.com", amount=-3)
except ValidationError as e:
    print(e)                 # lists every failing field

The expected behaviour: "42" is converted to 42, and amount=-3 fails the rule gt=0 with an error that names the field. You also get .model_dump() to convert back to a dictionary. FastAPI uses pydantic models for request and response bodies.

ApproachStrengthWeakness
Hints onlyFree documentationNothing is checked at runtime
Hand-written validatorNo dependency, full controlYou maintain it, limited features
dataclass + __post_init__Standard libraryBasic only
pydanticRich rules, nested data, clear errors, JSONAnother dependency

Connection to real projects. Every data pipeline should validate input at its boundary: API payloads, config files, rows from vendors. A bad row caught at the door costs minutes; the same row found in a dashboard costs days.

Applications

  • Data Engineering: validate each record from an upstream feed and send failures to a quarantine file.
  • Machine Learning: validate prediction-request schemas in a model-serving API.
  • GenAI: validate that an LLM's JSON output matches the expected structure before using it.
  • Backend: request and response models in FastAPI.
COMMON MISTAKE
Validating only the happy path. Test with a missing field, a wrong type, an empty string, a negative number and a huge number. Also, never put secrets or passwords in error messages you log.

Check yourself

  1. Why validate even if you have type hints?

Answer: Hints are not enforced at runtime, and outside data may be wrong.

  1. What is coercion?

Answer: Converting a value to the expected type, like "42" to 42.

  1. Which standard-library tool gave us the list of fields?

Answer: dataclasses.fields.

9.7 Jupyter Notebooks vs Scripts, nbconvert and Reproducibility

INTUITION
A notebook is a lab notebook: you try an idea, see the result next to it, and keep notes. A script is a recipe card: anyone can follow it from start to finish and get the same dish. You explore in notebooks, and you ship scripts and packages.

What a notebook really is. A .ipynb file is just JSON: a list of cells with source text and saved outputs. Prove it:

import json
nb = {"cells":[{"cell_type":"code","source":["print(1+1)\n"],"outputs":[],"execution_count":None,"metadata":{}}],"metadata":{},"nbformat":4,"nbformat_minor":5}
open("/tmp/c9/x.ipynb","w").write(json.dumps(nb))
d = json.load(open("/tmp/c9/x.ipynb"))
for c in d["cells"]:
    print("".join(c["source"]), end="")
    exec("".join(c["source"]))
print(1+1)
2
  • Answer The notebook file loads as ordinary JSON, and each code cell's source is plain text we can run. (exec is used here only to show the idea. Never exec untrusted notebooks, because they can run any code.)
  • Check 1+1 = 2.
  • Why it matters Because it is JSON, it works badly with Git diffs (outputs and execution counts change) and can hide problems such as cells run out of order.
NotebookScript / package

Reproducibility checklist

  1. Restart the kernel and "Run All" before sharing. If it fails, the notebook was not reproducible.
  2. Set random seeds (for example random.seed(42)) and record them.
  3. Keep a pinned requirements.txt or lock file next to the notebook.
  4. Move reusable code into a package (from shop import total_with_tax) and import it in the notebook.
  5. Never keep API keys in a notebook. Read them from environment variables (Chapter 13).
  6. Strip outputs before committing, or use a tool made for it (for example nbstripout), so diffs stay readable.

9.8 Typing in Depth, Import Order and Packaging Layout

Section 9.5 gave you the basics: annotations and a type checker. Real code needs more precise promises: "this dictionary has exactly these keys", "this string is one of three values", "this decorator keeps the signature of the function it wraps". This section adds those tools. A key fact first: Python itself ignores annotations at run time. A separate program, a type checker such as mypy or pyright, reads them. Every code block below really ran, so its output is real. Checker messages are labelled not run here because mypy is not installed in this environment.

How to read it: start at the grey box. If the name is already in sys.modules the answer is immediate. If not, Python walks sys.path in order and the first match wins. That is why a file of yours called random.py in the script folder breaks import random everywhere: the script folder is searched first.

Typing a JSON payload with TypedDict

A TypedDict describes a dictionary with fixed string keys. At run time it is an ordinary dict. A checker, however, flags a misspelt key or a wrong value type. NotRequired marks a key that may be missing.

Problem 9.8.1 Describe a user payload that always has id and name and sometimes email, then read it from JSON.

Step 1Subclass TypedDict and list the keys with their types.
Step 2Mark email as NotRequired[str].
Step 3Parse the JSON and annotate the result as User. Python does no checking here: you are promising the checker what the data looks like.
CheckPrint the required and optional key sets Python recorded.
from typing import TypedDict, NotRequired
import json

class User(TypedDict):
    id: int
    name: str
    email: NotRequired[str]

payload = json.loads('{"id": 7, "name": "Ada"}')
u: User = payload
print(u["name"], type(u).__name__, "email" in u)
print(sorted(User.__required_keys__), sorted(User.__optional_keys__))

Compare with pydantic from 9.6: a TypedDict costs nothing and checks nothing at run time, so it suits data you already trust (your own functions passing dicts around). For data from outside, validate first, then type it.

COMMON MISTAKE
Believing an annotation validates data. u: User = {"id": "oops"} runs without any error. Only the checker (not run here: mypy file.py would report an incompatible type) objects. Validate untrusted input with code, not with hints.

Literal, Final, Self and Protocol

Problem 9.8.2 Restrict a log level to three strings, mark a constant as not reassignable, make a chainable builder whose methods return the subclass, and accept any object that has a close() method.

LiteralLiteral["debug", "info", "error"] says "exactly one of these values". Passing "verbose" is a checker error but still runs.
FinalMAX_TRIES: Final = 3 tells the checker never to reassign it.
SelfA method returning Self returns whatever class it was called on, so chaining keeps the subclass methods.
ProtocolStructural typing: any class with a matching close() fits, with no inheritance needed (duck typing, made checkable).
from typing import Literal, Final, Self, Protocol

Level = Literal["debug", "info", "error"]
def set_level(level: Level) -> str:
    return level.upper()
print(set_level("info"))
print(set_level("verbose"))   # a checker rejects this line; Python runs it

print(MAX_TRIES)

class Builder:
    def __init__(self) -> None:
        self.parts: list[str] = []
    def add(self, p: str) -> Self:
        self.parts.append(p)
        return self
class SqlBuilder(Builder):
    def build(self) -> str:
        return " ".join(self.parts)
print(SqlBuilder().add("SELECT 1").add("FROM t").build())

overload: one function, return type depends on the input

Problem 9.8.3 Write parse that turns one string into an int and a list of strings into a list of int, and tell the checker which return type goes with which input.

IdeaStack @overload stubs (signature only, body ...), then write one real implementation with no decorator.
Run timeOnly the real implementation exists. The stubs are thrown away.
Benefitparse("5") + 1 type checks. Without overloads the result would be int | list[int] and the addition would be flagged.
from typing import overload

@overload
def parse(v: str) -> int: ...
@overload
def parse(v: list[str]) -> list[int]: ...
def parse(v):
    return int(v) if isinstance(v, str) else [int(i) for i in v]
print(parse("5"), parse(["1", "2"]))
5 [1, 2]

Typing the retry decorator with ParamSpec

The retry decorator from Chapter 7 loses its signature for a checker if you annotate the wrapper as Callable[..., Any]. ParamSpec captures "whatever parameters the wrapped function has" and reuses them. Since Python 3.12 you write it as [**P, R] after the function name (earlier versions import ParamSpec and TypeVar by hand).

Problem 9.8.4 Write retry(times) that retries on ValueError, keeps the name and signature of the wrapped function, and test it with a function that fails twice.

Step 1Generic parameters [**P, R]: P is the parameter list, R the return type.
Step 2The wrapper takes *args: P.args, **kwargs: P.kwargs and returns R.
Step 3functools.wraps copies the name and docstring at run time.
CheckThe call flaky(5, scale=10) succeeds on the third attempt and prints 50.
import functools
from collections.abc import Callable

def retry[**P, R](times: int) -> Callable[[Callable[P, R]], Callable[P, R]]:
    def deco(fn: Callable[P, R]) -> Callable[P, R]:
        @functools.wraps(fn)
        def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
            last: Exception | None = None
            for attempt in range(1, times + 1):
                try:
                    return fn(*args, **kwargs)
                except ValueError as e:
                    last = e
                    print(f"attempt {attempt} failed")
            assert last is not None
            raise last
        return wrapper
    return deco

calls = {"n": 0}
@retry(3)
def flaky(x: int, *, scale: int = 2) -> int:
    calls["n"] += 1
    if calls["n"] < 3:
        raise ValueError("boom")
    return x * scale
print(flaky(5, scale=10), flaky.__name__)
attempt 1 failed
attempt 2 failed
50 flaky

With this typing, a checker would reject flaky("a", scale="b") exactly as it would reject a direct call (not run here). Without it, the decorated function accepts anything.

Going deeper

  • Gradual typing strategy. Do not try to type a legacy code base in one week. Turn on the checker for new files first, then enable strict options one at a time (disallow_untyped_defs first, then warn_return_any). Strict mode (strict = true in the [tool.mypy] table of pyproject.toml) is a goal, not a day-one requirement.
  • Escape hatches. Any switches checking off for a value. cast(T, x) and # type: ignore[code] silence the checker without changing behaviour. Each one is a place where a bug can hide, so grep for them in reviews.
  • Packaging layout. Prefer a src/ layout: src/mypkg/__init__.py plus pyproject.toml at the top. Tests then import the installed package, so a missing file in the build shows up in testing instead of in production. A command-line entry point is declared in [project.scripts], for example mytool = "mypkg.cli:main", and the installer creates a mytool executable that calls main(). Building a wheel with python -m build and uploading with twine (or trusted publishing from CI) is not run here because it needs those tools and a package index.

More practice: types and imports

Problem 9.P.1 (warm-up) Your script folder contains a file named json.py and your code says import json. What happens, and how do you diagnose it?

Answer: Python finds your file first, because the script folder is first on sys.path. Anything that expects the standard library module fails with an AttributeError such as "module 'json' has no attribute 'loads'". Diagnose by printing json.__file__, then rename your file.

Problem 9.P.2 (build) Define a TypedDict called Order with sku: str, qty: int and an optional note: str, then write total_units(orders: list[Order]) -> int. Run it on two orders.

from typing import TypedDict, NotRequired

class Order(TypedDict):
    sku: str
    qty: int
    note: NotRequired[str]

def total_units(orders: list[Order]) -> int:
    return sum(o["qty"] for o in orders)

print(total_units([{"sku": "A1", "qty": 3}, {"sku": "B2", "qty": 4, "note": "gift"}]))
7

Answer: 7. Reading o["note"] without checking would be flagged by a checker, because the key is not required. Use o.get("note").

Problem 9.P.3 (what is the output?) def f(x: int) -> int: return x * 2 then print(f("ab")). Does the annotation stop it?

def f(x: int) -> int:
    return x * 2
print(f("ab"))
abab

Answer: It prints abab. Annotations are not enforced at run time, and str * int is legal. A checker would flag the call (not run here).

Problem 9.P.4 (stretch) Add @overload stubs to def first(x) so that a str input returns str and a list[int] input returns int. Rubric: (1) two stubs with ... bodies, (2) one undecorated implementation, (3) implementation handles both cases, (4) you called both forms.

Answer: Pattern: @overload def first(x: str) -> str: ..., @overload def first(x: list[int]) -> int: ..., then def first(x): return x[0]. The implementation body is the same for both, because indexing works on both. Common error: forgetting the final undecorated implementation, which raises no error until you call the function and find it is a stub that returns None.

Problem 9.P.5 (interview) When would you pick Protocol over an abstract base class?

Answer: Pick Protocol when the classes that should fit are not yours to change (third-party or standard library), or when you want callers to pass anything with the right methods without inheriting. Pick an abstract base class when you want shared code in the base, run-time isinstance checks without extra decorators, or to force subclasses to declare they implement the contract.

Chapter recap

  • A module is a file, a package is a folder with __init__.py. Python runs a module once and caches it in sys.modules.
  • Use if __name__ == "__main__": so a file can be both imported and run. Run packages with python -m package.
  • Relative imports (from .x import y) only work inside a package; running the file directly breaks them.
  • Circular imports mean two modules need each other. Fix the design with a third shared module; deferred imports are a patch.
  • Give every project its own virtual environment, and never install into global Python by accident.
  • Libraries declare flexible versions, applications ship pinned lock files; scan dependencies with pip-audit and beware look-alike package names.
  • Type hints are labels. Python does not enforce them; mypy and runtime validation (pydantic) do.
  • Notebooks are for exploration, scripts and packages are for production. Always "Restart and Run All" before sharing.

Problem 9.8.10 (interview) Your lead says "pin your dependencies and run pip-audit in CI". Explain both.

(3) Move reusable code into a package and install it into the environment, so imports are the same for everyone.
