Think of the worst moment of a big task: the program is half done and it dies with a wall of red text. If you can read that text, you fix the problem in two minutes. If you cannot, you lose the afternoon. In data work it is the same: a nightly job reads 2 million rows, row 1,400,001 has a strange value, and the job stops. This chapter teaches you four skills: reading a traceback, handling errors with try/except, writing your own errors, and leaving evidence with logging. Then you learn pdb, Python's built-in debugger, so you can stop a program in the middle and look inside it. By the end you can take any crash and walk to its cause step by step.

Running example: a small function that adds up shop prices like "Rs100". We make it fail, read the failure, handle it, log it and debug it. All code was run with python3 (Python 3.14). File paths in tracebacks (like /private/tmp/w6/tb.py) will be different on your computer.

6.1 Reading Tracebacks and the Common Exceptions

INTUITION
A traceback is like the receipt of a failed journey. It lists every road the program took, in order, and says where the car finally broke down. A beginner reads the top and panics. A professional reads the last line first (what broke), then the line above it (where it broke), then walks up the list (how we got there).

Words you need

WordPlain meaning
exceptionAn object Python creates when something goes wrong; it stops the normal flow
raiseTo create and throw an exception (Python does it for you, or you do it)
tracebackThe printed list of function calls that led to the exception
call stackThe chain of "function A called B, B called C" at one moment
bugA mistake in your code. An exception is how Python tells you about it

How to read one

Here is a real failure. total calls parse_price for each text. The third text is "N/A".

Predict: Before you run it, which line of the three functions do you think will be named last in the traceback?

def parse_price(text):
    return float(text.replace("Rs", ""))

def total(prices):
    s = 0
    for p in prices:
        s += parse_price(p)
    return s

print(total(["Rs100", "Rs250", "N/A"]))

    print(total(["Rs100", "Rs250", "N/A"]))
          ~~~~~^^^^^^^^^^^^^^^^^^^^^^^^^^^
  File "/private/tmp/w6/tb.py", line 7, in total

         ~~~~~~~~~~~^^^
  File "/private/tmp/w6/tb.py", line 2, in parse_price

  • Explain Read from the bottom. The last line says the type (ValueError) and the message (could not convert string to float: 'N/A'). The block above it points to line 2 in parse_price: that is where Python stopped. The two blocks above that show the callers: total at line 7, and the main script at line 10. The ~~~~^^^^ marks show which part of the line failed (newer Python versions draw them).
  • Answer The program failed in parse_price because "N/A" is not a number. The bad value is in the input data, but the failing line is in our function. The fix is to handle the case, which is the topic of 6.2.

Connection to the real job

In production you rarely sit next to the program. The traceback in a log file or an Airflow task page is often all you get. A teammate who reads it correctly fixes the job in minutes. It is like a hospital reading a patient's chart to find where a problem began; reading a traceback is the same skill.

Applications

  • Data Analytics: a notebook cell dies with KeyError: 'revenue'; you check the column names.
  • Data Engineering: an Airflow task fails with FileNotFoundError; you check whether the upstream job produced the file.
  • Machine Learning: ValueError: shapes not aligned points to a matrix mismatch.
  • MLOps: a deployed API returns 500; the error type in the logs tells you which input broke it.
COMMON MISTAKE
Reading from the top and getting lost in library code. Start at the last line, then find the first frame that is your own file.
COMMON MISTAKE
Fixing the line named in the traceback when the real problem is in the data or in a caller. Ask who passed the bad value.
COMMON MISTAKE
Copying only the last line when asking for help. Always paste the whole traceback.

Check yourself

  1. In a traceback, which line tells you the exception type? Answer: the last line.
  2. Which exception does {"a": 1}["b"] raise? Answer: KeyError.
  3. None.upper() raises which error, and what does it usually mean? Answer: AttributeError; a variable you thought held text is None.

6.2 Handling Errors: try, except, else, finally

INTUITION
Picture a shop counter. Most customers pay normally. Sometimes a card is declined. A good cashier does not close the shop; she says "please try another card" and carries on. try/except lets your program react to a known kind of problem and keep working, while still stopping on problems you did not expect.

How it works

try:        code that might fail
except SomeError:   what to do if THAT error happens
else:       runs only if the try block had NO error
finally:    runs ALWAYS (cleanup: close, release, unlock)
  • Catch specific exceptions. except ValueError is good. A bare except: or except Exception: hides bugs.
  • You can catch several types: except (ValueError, TypeError) as e:. The as e gives you the exception object.
  • else is for code that should run only on success. It keeps the try block short.
  • finally runs even when there is a return or an error. Use it for cleanup.
  • Python style prefers EAFP: "Easier to Ask Forgiveness than Permission" (just try, and catch the error). The other style is LBYL: "Look Before You Leap" (check first with if). EAFP is often shorter and avoids race conditions (the file could vanish between the check and the use).

Worked examples

Problem 6.2.1 Make parse_price safe: return None for bad text, and show what else and finally do.

Step 1Wrap the risky call (int(s)) in try. Catch only ValueError.
Step 2Put the "success" message in else.
Step 3Put the "always" message in finally.

Predict: For the input "x", does the finally message print? In what order do the lines appear?

def read_num(s):
    try:
        n = int(s)
    except ValueError:
        print("  bad number")
        return None
    else:
        print("  parsed", n)
        return n
    finally:
        print("  finally runs for", repr(s))

read_num("42")
read_num("x")
  parsed 42
  finally runs for '42'
  bad number
  finally runs for 'x'
  • Explain For "42", int works, so Python skips except, runs else, and then finally. For "x", int raises ValueError, except runs and returns None, and finally still runs before the function actually returns.
  • Answer finally ran in both cases, and after the except or else block.
  • Check Count the lines: two calls produce two finally lines. They did.
  • Why it matters Anything that must happen (closing a connection, releasing a lock) belongs in finally, because it runs even on failure.

The typical wrong version. A bare except: hides real mistakes:

try:
    total = prise + 1      # typo: should be price
except:
    total = 0

This never shows an error, and the total is silently 0. Python would have told you NameError: name 'prise' is not defined. Catching everything turns a loud bug into a quiet one. The fix: except ValueError: (or the exact type you expect).

Problem 6.2.3 Compare LBYL and EAFP for a dictionary lookup, and use the loop else.

Step 1LBYL: if "b" in d. EAFP: try ... except KeyError.
Step 2Both give the same answer here. EAFP is better when the check itself is as costly as the action, or when things change between check and use.
Step 3A for ... else runs its else only if the loop did not break.
d = {"a": 1}
if "b" in d:
    x = d["b"]
else:
    x = 0
try:
    y = d["b"]
except KeyError:
    y = 0
print(x, y)

for n in [3, 5, 7]:
    if n % 2 == 0:
        print("found even"); break
else:
    print("no even")
0 0
no even
  • Answer Both styles gave 0. The loop printed no even because no number was even, so break never ran.
  • Check 3, 5, 7 are all odd: n % 2 is 1 each time, so the condition is never true.
  • Why it matters For simple dict defaults you will use d.get("b", 0) instead; both patterns are good to know for interviews.

The picture

 try block ──no error──▶ else block ──▶ finally ──▶ continue
     │
   error ──▶ matching except block ──▶ finally ──▶ continue
     │
   no match ──▶ finally ──▶ error keeps travelling up to the caller

Connection to the real job

ETL jobs process millions of rows. A good job catches the expected row-level problem (ValueError on a bad cell), counts it, and moves on, but lets unexpected problems (a database outage) stop the job loudly. Retry loops (Chapter 7) are built from try/except.

Applications

  • Data Engineering: skip and quarantine bad rows; always close database connections in finally.
  • Data Analytics: cleaning scripts that convert messy text to numbers and report the failures.
  • Machine Learning: a training loop that catches a corrupt image file and continues.
  • API / Backend: return a clear 400 message for bad input instead of crashing with a 500.
COMMON MISTAKE
except Exception: pass. You are hiding the problem. At least log it (6.4).
COMMON MISTAKE
Putting a lot of code inside try. Then you do not know which line failed. Keep try small, and use else for the rest.
COMMON MISTAKE
Catching an exception and then using a variable that was never set (because the failing line was the one that set it).

Check yourself

  1. When does else in a try block run? Answer: only if no exception happened in try.
  2. When does finally run? Answer: always, even after return or an unhandled error.
  3. What does EAFP stand for? Answer: Easier to Ask Forgiveness than Permission.

6.3 Raising, Custom Exceptions and Chaining

INTUITION
Sometimes your code finds the problem, not Python. A function that receives an age of -3 must refuse it with a clear message. Raising your own exception is like a quality inspector stopping the production line and writing a note about why.

How it works

  • raise ValueError("age must be >= 0") throws an exception you choose.
  • A bare raise inside an except block re-throws the same exception. Use it after logging.
  • A custom exception is a small class that inherits from Exception. Give your project one base error (AppError) and children for each case. Callers can then catch the whole family or one member.
  • Chaining: raise NewError("...") from e links the new error to the old cause. The traceback then says "The above exception was the direct cause of the following exception", so nothing is lost. Without from, Python still links them as __context__, but with the message "During handling of the above exception, another exception occurred".
  • assert condition, "message" raises AssertionError if the condition is false. Use it for checks of your own assumptions in tests and quick scripts, not for validating user input (Python can run with asserts switched off).
  • e.add_note("text") adds extra hints to an exception (Python 3.11 and later). ExceptionGroup and except* handle several errors that happened together (3.11 and later; you will meet them with asyncio).

Worked examples

Problem 6.3.1 Create AppError and ValidationError, raise one, and catch it through the base class.

Step 1Define class AppError(Exception) as the base.
Step 2Define ValidationError(AppError) that stores the field.
Step 3Catch AppError (the parent) and read the child's field.

Predict: The except names AppError, but we raise ValidationError. Will it be caught?

class AppError(Exception):
    """Base error for our app."""

class ValidationError(AppError):
    def __init__(self, field, message):
        super().__init__(f"{field}: {message}")
        self.field = field

def validate(rec):
    if rec.get("age", 0) < 0:
        raise ValidationError("age", "must be >= 0")
    return rec

try:
    validate({"age": -3})
except AppError as e:
    print(type(e).__name__, e, e.field)
ValidationError age: must be >= 0 age
  • Explain ValidationError is a kind of AppError, so except AppError catches it. super().__init__(...) sets the message that print(e) shows (the chapter on classes explains super() fully). We added our own attribute field so callers can know which field failed.
  • Answer It was caught, and we could read both the message and e.field.
  • Check The printed class name is ValidationError (the child), proving that a parent except catches children.
  • Why it matters In plain words: your API can turn any AppError into a clean "400 Bad Request" and show field to the user.

Connection to the real job

Libraries like requests, pydantic and sqlalchemy each have their own exception families. Your own services should too, so that a failure in a data-quality check is different from a database outage and gets a different reaction (skip, retry, page someone).

Applications

  • Data Engineering: DataQualityError fails the pipeline with a precise message; TransientError triggers a retry.

  • Testing: assert states what you expect after the code runs.

6.4 Logging

INTUITION
print is shouting in a room. logging is a flight recorder: every message has a time, a severity, a source, and can be sent to the screen, a file or a monitoring system, and switched on or off without editing code. When a nightly job fails at 3 a.m., the log is the only witness.

Words you need

WordPlain meaning
loggerThe object you call (log.info(...)); it has a name like etl.load
levelImportance: DEBUG 10, INFO 20, WARNING 30, ERROR 40, CRITICAL 50
handlerDecides where a message goes (screen, file)
formatterDecides how a message looks
propagateA child logger passes its messages up to its parent's handlers
LevelUse forExample
DEBUGDetails for developersrow 5 parsed as ...
INFONormal milestonesloaded 120 rows
WARNINGStrange but continuingmissing column city
ERRORAn operation failedcannot connect
CRITICALThe program may stopdisk full

How it works

  • logging.basicConfig(level=..., format=...) sets up logging quickly. Call it once, at the start of the program.
  • logging.getLogger("etl.load") returns a named logger. Convention in a module: log = logging.getLogger(__name__). Dots in names make a tree: etl.load is a child of etl.
  • Messages below the chosen level are ignored. At level INFO, debug calls do nothing.
  • log.exception("message") logs at ERROR level and adds the traceback. Use it inside except.
  • Use lazy formatting: log.info("loaded %d rows", n), not log.info(f"loaded {n} rows"). With the first form, the text is built only if the message is actually emitted.
  • Never log secrets, passwords, or personal data.

Worked examples

Problem 6.4.2 Send everything (DEBUG) to a file and only warnings to the screen, using two handlers, and see how a child logger propagates.

Step 1Make a logger svc at level DEBUG.
Step 2Add a FileHandler (level DEBUG) and a StreamHandler (level WARNING).
Step 3Log at debug, info, warning. Print the file. Then log an error from the child svc.db.
import logging, sys, tempfile, os
d = tempfile.mkdtemp(); fn = os.path.join(d, "app.log")

Problem 6.4.3 Produce structured (JSON) log lines so a tool can parse them.

Step 1Subclass logging.Formatter and override format.
Step 2Return json.dumps of level, message and logger name.
Step 3Attach it to a handler. Set propagate = False to avoid double printing.
import logging, sys, json
logging.basicConfig(stream=sys.stdout, level=logging.INFO, format="%(message)s")
class JsonFormatter(logging.Formatter):
    def format(self, r):
        return json.dumps({"level": r.levelname, "msg": r.getMessage(), "logger": r.name})
h = logging.StreamHandler(sys.stdout); h.setFormatter(JsonFormatter())
l2 = logging.getLogger("json"); l2.addHandler(h); l2.propagate = False; l2.setLevel(logging.INFO)
l2.info("order %s paid", 17)
{"level": "INFO", "msg": "order 17 paid", "logger": "json"}
  • Answer The message became one JSON object per line, which log tools (ELK, CloudWatch, Datadog) can index.
  • Check "order %s paid" % 17 is order 17 paid. Matches.
  • Why it matters Searching for level = ERROR in JSON logs is easy; searching free text is slow and fragile.

 your code: log.info("..")
        │
     [Logger "svc.db"] ──level check──▶ pass? ──▶ [Handler: file, level DEBUG]  ──▶ app.log
        │ propagate                                [Handler: screen, level WARNING] ──▶ terminal
        ▼

Connection to the real job

Every production system writes logs: Airflow tasks, FastAPI services, Spark jobs, training runs. During an incident, you search logs by time and level. Logging itself has a cost, like a restaurant kitchen that stops to write a note for every single egg it cracks: a DEBUG line inside a loop of 10 million rows slows the job. Set INFO in production and DEBUG when investigating.

Applications

  • Data Engineering: row counts and durations of each pipeline step, with warnings for rejected rows.
  • MLOps: log model version, input size and prediction time of each request.
  • Machine Learning: log loss and metrics per epoch to a file.
  • Security / Compliance: audit trail of who ran what (without logging secrets).
COMMON MISTAKE
Calling basicConfig after other code already configured logging. It then does nothing. Call it once, first.
COMMON MISTAKE
Logging passwords, tokens or customer personal data. Logs are copied around and kept for years.
COMMON MISTAKE
Using log.error(str(e)) inside except and losing the traceback. Use log.exception(...).

Check yourself

  1. At level WARNING, is log.info(...) shown? Answer: no.
  2. Which call logs a message together with the traceback? Answer: log.exception(...).
  3. Why write log.info("n=%d", n) rather than an f-string? Answer: the text is built only if the message is emitted (lazy formatting).

6.5 Debugging with pdb

INTUITION
print debugging is like looking at a crime scene through a keyhole. A debugger lets you walk in: freeze the program at a line, look at every variable, move forward one line at a time, and ask "what is the value now?". It is the difference between guessing and seeing.

How it works

pdb is Python's built-in debugger. Three ways to start it:

  1. Put breakpoint() in your code. Execution stops there.
  2. Run python3 -m pdb script.py to start the script under the debugger.
  3. Post-mortem: python3 -m pdb -c continue script.py. If the script crashes, pdb opens at the crash line and you can inspect the variables.

Set PYTHONBREAKPOINT=0 to switch every breakpoint() off without editing code.

CommandShortMeaning
helphlist commands
list / lllshow source around the current line / the whole function
nextnrun the current line, stay at this level
stepsrun the current line, go into a function call
continuecrun until the next breakpoint or the end
print xp xshow the value of an expression
break 12b 12set a breakpoint at line 12
wherewshow the call stack
up / downu / dmove between stack frames
quitqleave the debugger

The VS Code debugger does the same with clicks: click in the gutter to set a breakpoint, press F5, look at the Variables panel, and use the step buttons (not run here, because it needs the VS Code window; the ideas are identical to pdb).

Worked examples

For these examples we feed the commands to pdb through a pipe, so you can see a real session. When you work by hand, you type the same commands at the (Pdb) prompt.

Problem 6.5.1 Stop inside average just before the division, inspect the variables, and move one line.

Step 1The function has a breakpoint() before return total / len(nums).
Step 2At the prompt we type p nums, p total, n (next), ll (list function), c (continue).
Step 3The second call, average([]), stops at the breakpoint again. We look at nums.
def average(nums):
    total = 0
    for n in nums:
        total += n
    breakpoint()
    return total / len(nums)

print(average([10, 20, 30]))
print(average([]))

Predict: What will p total show for [10, 20, 30]?

-> breakpoint()
(Pdb) [10, 20, 30]
(Pdb) 60
(Pdb) > /private/tmp/w6/bug.py(6)average()

  • Explain The line > ...bug.py(5)average() says: file, line number, function. The -> line is the next line to run. p nums printed the list, p total printed 60. n moved to line 6. ll printed the function with an arrow at the current line. c ran on: the program printed 20.0 (60 / 3), then reached the breakpoint for the empty list. p nums shows []: the cause of the next crash is visible before it happens. (The last line appears because our pipe ended; typing y quits.)
  • Answer The average of [10, 20, 30] is 20.0, and for [] we can see that len(nums) would be 0.
  • Check 10 + 20 + 30 = 60 and 60 / 3 = 20.0. The debugger's values match.
  • Why it matters In plain words: you saw the empty list before the program crashed, instead of guessing from the error message.

The typical wrong version. Without looking, the second call fails:

ZeroDivisionError: division by zero

and with PYTHONBREAKPOINT=0 the breakpoint() line does nothing, so the script runs straight to that same ZeroDivisionError (we ran it: the last lines were return total / len(nums) and ZeroDivisionError: division by zero). The fix is a guard such as if not nums: return 0.0 (or raise a clear error). Remove breakpoint() before you commit anyway.

Problem 6.5.2 Find a logic bug with no crash. buggy_max([-5, -2, -9]) should return -2, but returns 0.

Step 1Start python3 -m pdb -c "b 4" -c continue bug2.py. This sets a breakpoint on line 4 (the if) and runs.
Step 2At each stop, print n and best.
Step 3Notice best starts at 0, bigger than every number in the list.
def buggy_max(nums):
    best = 0
    for n in nums:
        if n > best:
            best = n
    return best
print(buggy_max([-5, -2, -9]))

Predict: What is best at the first stop?

Breakpoint 1 at /private/tmp/w6/bug2.py:4
> /private/tmp/w6/bug2.py(4)buggy_max()
-> if n > best:
(Pdb) (-5, 0)
(Pdb) > /private/tmp/w6/bug2.py(3)buggy_max()
-> for n in nums:
(Pdb) 0
(Pdb) > /private/tmp/w6/bug2.py(4)buggy_max()
-> if n > best:
(Pdb) (-2, 0)
  • Explain The command p n, best printed (-5, 0): n is -5, best is 0. -5 > 0 is false, so best never changes. We continued to the next stop: (-2, 0), again false. The initial value 0 is the bug.
  • Answer The function returns 0 because best starts at 0. Fix: best = nums[0] (and handle the empty list), or use the built-in max(nums).
  • Check With the fix, max([-5, -2, -9]) is -2. Run print(max([-5, -2, -9])) to confirm.
  • Why it matters There was no error message at all. Only looking at the variables revealed the problem. Many data bugs are silent like this.

Step 1Script: data = {"a": [1, 2]} then print(data["a"][3]).

Connection to the real job

Notebook debugging uses the same ideas (%debug in Jupyter opens pdb after an error). For bugs that only appear on a server, you add logging (6.4) since you cannot attach a debugger. In a data pipeline, write the failing row to a file and reproduce it locally with pdb.

Applications

  • Data Analytics: step through a cleaning function on one failing row.
  • Machine Learning: stop inside a loss function to see tensor shapes.
  • Data Engineering: reproduce a bad-record failure from yesterday's job with the saved record.
  • Backend: debug a failing request by running the handler with a breakpoint.
COMMON MISTAKE
Committing code with breakpoint() left in. A server would freeze waiting for input. Search for it before you commit (a pre-commit hook can check this, Chapter 10).
COMMON MISTAKE
Typing n when you wanted s. n runs a whole function call as one step; s goes inside it.
COMMON MISTAKE
Using variable names that match pdb commands (like c or n) and then printing them. Use p n explicitly with p.

Check yourself

  1. How do you stop the program at a chosen line in code? Answer: write breakpoint() there.
  2. What is the difference between n and s? Answer: n runs the line as one step; s steps into a function call.
  3. Which command shows the call stack? Answer: w (where).

Chapter recap

  • Read a traceback from the last line upward: type and message first, then the first frame that is your own code.
  • Learn the ten common exceptions: ValueError, TypeError, KeyError, IndexError, AttributeError, NameError, FileNotFoundError, ModuleNotFoundError, ZeroDivisionError, AssertionError.
  • Catch specific exceptions, keep the try block small, use else for success code and finally for cleanup.
  • Never use a bare except:; it hides bugs.
  • EAFP (try and catch) is the Python style; LBYL (check first) is fine for simple cases.
  • Raise your own exceptions with a clear message; make a base AppError class and children.
  • Use raise X from e to keep the original cause, and bare raise to re-raise after logging.
  • Use logging, not print: levels, handlers, log.exception, lazy %s formatting, and never log secrets.
  • Use breakpoint(), python3 -m pdb and post-mortem to look inside a running program.

Practice set

Problem 6.P.1 What exception does int("3.5") raise?

Answer: ValueError (int does not accept text with a decimal point; use int(float("3.5"))).

Problem 6.P.2 What is the output?

try:
    print("A")
except ValueError:
    print("B")
else:
    print("C")
finally:
    print("D")

Answer: A, C, D on separate lines. No error, so else runs, then finally.

Problem 6.P.3 What is the output?

def f():
    try:
        return "try"
    finally:
        print("cleanup")
print(f())

Answer: cleanup then try. The finally block runs before the function returns.

Problem 6.P.4 Find the bug:

try:
    value = int(text)
except:
    pass
print(value * 2)

Answer: The bare except hides all errors, and if int(text) failed, value is not defined, so print raises NameError. Catch ValueError and set a default or stop.

Problem 6.P.5 Which exception does d = {}; d["x"] += 1 raise?

Answer: KeyError: 'x', because d["x"] is read first. Use d.get("x", 0) + 1 or defaultdict(int).

Problem 6.P.6 Write a function to_float(s) that returns None for text that is not a number, but lets other errors through.

Answer:

def to_float(s):
    try:
        return float(s)
    except ValueError:
        return None

Note that to_float(None) raises TypeError, which is correct: None is a programming error, not bad data. Decide this on purpose.

Problem 6.P.7 Logging level is WARNING. Which of these appear: debug, info, warning, error?

Answer: warning and error.

Problem 6.P.8 Find the bug: a function does except ValueError as e: raise AppError("bad input") and an engineer says the original error is lost.

Answer: Without from e the link is only implicit. Write raise AppError("bad input") from e so the traceback shows the direct cause.

Problem 6.P.9 Scenario: your nightly job crashes at 2 a.m. with KeyError: 'amount' after 1.2 million rows. You have only the log. List your steps.

Answer: (1) Read the traceback bottom-up and find the line in your code. (2) Check the log for which file or row it was processing (this is why you log file names and row counts). (3) Reproduce with that one row on your laptop. (4) Use pdb or a print of the row to see which keys exist. (5) Decide: skip and count bad rows with a warning, or fail the job with a clear DataQualityError. (6) Add a test with that bad row.

Problem 6.P.10 Interview: what is the difference between except Exception and a bare except:? Why avoid both when possible?

Answer: A bare except: also catches KeyboardInterrupt and SystemExit (they inherit from BaseException), so you cannot stop the program with Ctrl+C. except Exception skips those but still hides bugs. Catch the specific exception you can handle.

Problem 6.P.11 Interview: explain EAFP versus LBYL with an example, and say when LBYL is better.

Answer: EAFP: try: value = d[key] except KeyError: .... LBYL: if key in d: value = d[key]. EAFP is idiomatic and avoids a race (a file may disappear between exists() and open()). LBYL is clearer when failure is common and cheap to check, and when an exception would be costly in a hot loop.

Problem 6.P.12 Interview: you must find why a function returns the wrong number, but there is no error. How do you debug it?

Answer: Reproduce with the smallest input. Put breakpoint() before the suspicious line, print the inputs and intermediate values (p), step with n, and compare with what you expect by hand. Then write a failing test that captures the bug, fix, and keep the test.
