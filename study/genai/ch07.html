Your company has 3,000 policy documents. A new employee asks, "How long does a refund take?" A plain LLM may confidently invent an answer, because it has never read your policies. RAG fixes that by splitting the work: first a retriever finds the relevant pages, then the model writes an answer using only those pages, and points to them as sources. This is the most requested GenAI skill in industry because it works on private, changing data without retraining anything. By the end of this chapter you will build every stage yourself in plain Python with a fake generator and see it run: ingestion, chunking, retrieval, prompt assembly and citations. You will also learn the advanced variants and the failure modes you must test for. Chapter 6 gave you retrieval; Chapter 4 gave you prompting; here we join them. Chapter 8 measures the result.

Words you need first

WordPlain meaning
RAGRetrieve relevant text, then generate an answer from it
IngestionLoading and preparing documents into the index (the offline part)
ChunkA piece of a document stored and retrieved as one unit
GroundedThe answer is supported by the retrieved text
CitationA pointer from an answer sentence to its source chunk
HallucinationFluent text that is not supported by facts or sources

7.1 The Pipeline and Ingestion

INTUITION
An open-book exam. The student (the model) is clever but has not memorised your syllabus. A librarian (the retriever) fetches the right pages from your own shelves. The student answers using those pages, and writes "see page 12" in the margin. If the librarian fetches the wrong pages, even the best student fails: so most RAG quality work is about the librarian.

How to read the picture: the top row runs offline, once and whenever documents change: documents are parsed and cleaned, split into chunks, embedded into vectors, and stored in an index together with metadata. The bottom row runs online, for every question: embed the question (maybe rewrite it first), retrieve the top chunks (with filters), rerank, assemble a prompt that includes the chunks and citation instructions, and let the model answer. The arrow shows the online part searching the offline index.

Ingestion steps in detail.

  1. Collect sources: PDFs, web pages, wikis, tickets, databases, spreadsheets.
  2. Parse to clean text, keeping structure.
    • Text PDFs: extract text, watch for two-column layouts, headers, footers and page numbers repeating on every page (remove them).
    • Scanned PDFs and images: need OCR (optical character recognition: turning a picture of text into text), for example Tesseract or a document-AI service; check quality by eye.
    • HTML: strip menus, ads, cookie banners; keep headings and lists.
    • Tables: do not flatten into one long line. Keep rows with their column headers (for example convert each row to "Plan: Premium; Support: 24x7"), or store tables as Markdown.
  3. Clean and enrich: remove duplicates, fix encodings, record metadata: source, title, section, date, version, owner, permissions.
  4. Chunk (next section), embed, index.
  5. Keep it fresh: store a document hash; re-ingest only changed documents; delete chunks of deleted documents (otherwise the system answers from deleted policies).

Problem 7.1.1 A 100-page PDF has about 500 tokens per page. You chunk at 300 tokens with an overlap of 45 tokens. How many chunks, and how many tokens will you embed in total?

Formulastride = chunk size − overlap; chunks = ceil((total − chunk size) / stride) + 1
Plug intotal = 100 × 500 = 50,000; stride = 300 − 45 = 255
Compute(50,000 − 300) / 255 = 194.9, ceiling 195, plus 1 = 196 chunks. Tokens to embed = 196 × 300 = 58,800 (the last chunk may be shorter, so slightly fewer in practice).
AnswerAbout 196 chunks and about 58,800 tokens to embed, 17.6% more than the 50,000 original tokens because of overlap.
Check196 × 255 = 49,980, close to 50,000, as expected for a stride-based walk. 58,800 / 50,000 = 1.176.
Why it mattersOverlap costs embedding money and index size, and it duplicates text in results; it must earn its place by improving retrieval.

Problem 7.1.2 After ingestion, a user is told the refund window is 14 days, but the policy was changed to 30 days last month. What are the two most likely pipeline causes?

Step 1The new document version was never re-ingested (no change detection or the job failed).
Step 2The old version's chunks were not deleted, so both versions are in the index and the old one ranked higher.
AnswerStale or duplicated chunks. Fix with hash-based re-ingestion, deleting superseded chunks, and a valid_from or version metadata filter.
CheckQuery the index directly for "refund window" and list the chunk source and date: if both versions appear, you found it.

  • Data Engineering: the ingestion pipeline is a normal ETL job with a quality gate.
  • GenAI: internal knowledge assistants, support bots, policy Q&A.
  • Legal, finance, healthcare: answers with sources that can be audited.
COMMON MISTAKE
Treating ingestion as "just run a loader". Bad parsing (merged columns, lost table headers, repeated footers) silently ruins retrieval. Open 20 random chunks and read them before you build anything else.

Check yourself

  1. Which parts of the pipeline run offline and which online?

Answer: Parse, chunk, embed and index run offline; query embedding, retrieval, reranking, prompting and generation run online.

  1. Why store metadata with each chunk?

Answer: For filters, permissions, freshness and citations.

  1. Why delete chunks of removed documents?

Answer: Otherwise the system answers from content that should no longer exist.

7.2 Chunking Strategies

INTUITION
Cutting a recipe book into index cards. Cut every 50 words and you split "add salt" from "to taste". Cut by recipe, and each card is a complete idea. Too big a card and the cook has to read a lot to find one step; too small a card and no card has the full instruction.

Strategies.

StrategyHowGoodBad
Fixed size (+ overlap)Every N tokens or wordsSimple, predictableCuts facts in half
By structureSplit on headings, paragraphs, list itemsKeeps ideas wholeSections can be very long or very short
RecursiveTry big separators first (headings), then paragraphs, then sentences, until pieces fit the sizeGood defaultNeeds tuning
SemanticStart a new chunk where embedding similarity between neighbouring sentences dropsFollows topic changesExtra cost, can be unstable
Parent-childEmbed small chunks, but return the larger parent section to the modelPrecise search, rich contextMore storage and logic

Typical starting point: 200 to 500 tokens, 10 to 20% overlap, split on structure first, and always attach the heading path ("Refund policy > Exceptions") to the chunk text. Then measure (Chapter 8). The best size depends on your documents and questions, not on a blog post.

How to read the picture: the top row shows four fixed-size chunks that overlap by a few words; a fact near a boundary can be cut in two. The bottom row shows two chunks that each follow a heading, so each section is complete.

A real, runnable RAG in plain Python. This is the full code of the tiny system used in this chapter and in Chapter 8. It has three small "policy" documents, two chunkers, a TF-IDF retriever (a stand-in for embeddings), a prompt builder and a fake generator that picks the context sentence most similar to the question. The fake generator is not an LLM: it exists so you can run the whole pipeline offline and see every step. Save it as rag.py.

import re, numpy as np
from sklearn.feature_extraction.text import TfidfVectorizer
DOCS={
"refund_policy.md":"""# Refund policy
Refunds are available within 30 days of purchase.
Refunds are processed within 7 business days after approval.

# Exceptions
Gift cards cannot be refunded. Digital downloads are refundable only if not opened.""",
"shipping.md":"""# Shipping
Standard shipping takes 5 to 7 days. Express shipping takes 2 days.

# International
International orders ship in 10 to 14 days. Customs fees are paid by the buyer.""",
"support.md":"""# Support hours
Phone support is open 9am to 6pm on weekdays.

# Escalation
If a ticket is not answered in 24 hours, reply to the ticket to escalate it to a manager."""}
STOP={"the","is","a","an","do","does","how","are","can","i","of","to","in","on","if","it","be",
      "or","and","not","what","long","by","for","after","within"}
USE_STOP=True
def stem(w):
    if w.endswith("ed") and len(w)>4: w=w[:-2]
    elif w.endswith("s") and not w.endswith("ss") and len(w)>3: w=w[:-1]
    return w
def tok(s):
    ws=[stem(w) for w in re.findall(r"[a-z0-9]+",s.lower())]
    return [w for w in ws if not (USE_STOP and w in STOP)]
def chunk_fixed(text,size=12,overlap=3):
    w=text.split(); out=[]; i=0
    while i<len(w):
        out.append(" ".join(w[i:i+size])); i+=size-overlap
    return out
def chunk_sections(text):
    parts=re.split(r"\n(?=# )",text.strip()); return [p.strip() for p in parts]
def build(chunker):
    chunks=[(f,i,c) for f,t in DOCS.items() for i,c in enumerate(chunker(t))]
    vec=TfidfVectorizer(tokenizer=tok,token_pattern=None,sublinear_tf=True)
    M=vec.fit_transform([c[2] for c in chunks]); return chunks,vec,M
def retrieve(index,q,k=3):
    chunks,vec,M=index; s=(M@vec.transform([q]).T).toarray().ravel()
    return [(chunks[i],float(s[i])) for i in np.argsort(-s)[:k]]
def assemble(q,hits):
    ctx="\n".join(f"[{n}] ({c[0]}) {c[2]}" for n,(c,_) in enumerate(hits,1))
    return ("Answer ONLY from the context. Cite sources like [1]. If the context lacks the answer, say 'I do not know'.\n"
            f"Context:\n{ctx}\n\nQuestion: {q}\nAnswer:")
def fake_llm(prompt):
    """Stand-in for a real model: picks the context sentence with most word overlap with the question."""
    q=prompt.split("Question:")[1].split("\nAnswer:")[0]
    ctx=prompt.split("Context:\n")[1].split("\n\nQuestion:")[0]
    best,bs=None,0
    for line in ctx.split("\n"):
        m=re.match(r"\[(\d+)\]",line)
        if m: cur=m.group(1)
        for sent in re.split(r"(?<=[.])\s+",line):
            ov=len(set(tok(q))&set(tok(sent)))
            if ov>bs: best,bs=(sent,cur),ov
    if bs<2: return "I do not know."
    return re.sub(r"^\[\d+\]\s*\([^)]*\)\s*","",best[0])+f" [{best[1]}]"

Now run the chunkers. Predict first: how many chunks will the shipping document make with fixed size 12 words, overlap 3, versus section splitting? Notice the second chunk of the fixed version will start in the middle of a section.

from rag import *
print(chunk_fixed(DOCS["shipping.md"])[:3])
print(len(chunk_fixed(DOCS["shipping.md"])),"fixed chunks vs",len(chunk_sections(DOCS["shipping.md"])),"section chunks")
['# Shipping Standard shipping takes 5 to 7 days. Express shipping takes', 'Express shipping takes 2 days. # International International orders ship in 10', 'ship in 10 to 14 days. Customs fees are paid by the']
4 fixed chunks vs 2 section chunks

Explain: the shipping document has 31 words (counting each # as a word). With size 12 and overlap 3, each new chunk starts 9 words after the previous one, giving 4 chunks. Look at chunk 2: it holds the end of the "Shipping" section glued to the "International" heading, because the splitter does not know what a heading is. Chunk 3 starts with ship in 10 to 14 days and chunk 2 ended with ship in 10: the fact "International orders ship in 10 to 14 days" is cut across two chunks, and "paid by the" is cut from "buyer". The section version has 2 clean chunks.

Problem 7.2.1 Check by hand: how many fixed chunks do 31 words make with size 12 and overlap 3?

Formulachunks = ceil((words − size) / stride) + 1, stride = 12 − 3 = 9
Plug in(31 − 12) / 9 = 2.11
Computeceiling of 2.11 is 3, plus 1 = 4. But the loop stops when all words are covered: starts at 0, 9, 18, 27; the start at 27 covers words 27 to 30, so the 4th chunk is short.
Answer4 chunks, the last one short, matching the program.
CheckThe program printed 4.

Chunking changes what is retrieved. We ask the same question with both chunkers and look at the top two chunks (file, chunk number, score):

for name,ch in [("fixed",chunk_fixed),("sections",chunk_sections)]:
    idx=build(ch); q="How long does a refund take to process?"
    hits=retrieve(idx,q,2)
    print("==",name,"->",[(h[0][0],h[0][1],round(h[1],2)) for h in hits])
== fixed -> [('refund_policy.md', 1, 0.46), ('refund_policy.md', 0, 0.31)]
== sections -> [('refund_policy.md', 0, 0.43), ('shipping.md', 0, 0.28)]

Both found the refund policy first, so for this question both chunkers work. Look at the second place: with fixed chunks both top results are from the refund policy (good, but the answer is spread over two chunks); with sections the second result is the shipping section, a noise chunk with a low score (0.28). The right number of results (k) depends on the question; Chapter 8 shows how to measure it.

Problem 7.2.2 The same experiment with the stop-word list switched off (rag.USE_STOP = False) returned support.md chunk 1 first. Why would removing stop words fix the refund question?

Step 1Without removal, words like how, does, a, to, take count as query words. The support chunk contains "to", "a", "in", "is" many times ("reply to the ticket to escalate it to a manager").
Step 2Those common words match many chunks and push the score of the real topic words (refund, process) down.
AnswerStop words matched an unrelated chunk; with them removed the real topic words dominate. This is a small version of a real problem: retrieval quality depends on text normalisation as much as on models.
CheckWe ran both: with no stop-word removal the winner was support.md chunk 1; with removal it was refund_policy.md.

Applications

  • GenAI engineering: tuning chunk size, overlap and structure for each document type (FAQs, contracts, code, tables).
  • Legal and compliance: section-aware chunks so a clause is never split.
  • Customer support: one chunk per FAQ answer.
COMMON MISTAKE
Choosing chunk size once, by guess, and never testing it. Compare at least two or three settings on an eval set and keep the winner. Also keep the heading path in each chunk; without it a chunk saying "30 days" does not say what is 30 days.

Check yourself

  1. Name two drawbacks of fixed-size chunking.

Answer: It cuts facts in half and ignores headings and structure.

  1. What is a parent-child (parent-document) strategy?

Answer: Search small chunks, but give the model the larger parent section they came from.

  1. Why attach the heading path to each chunk?

Answer: So a chunk carries its own context (what the number or rule refers to).

7.3 Retrieval, Prompt Assembly, Generation and Citations

INTUITION
After the librarian returns the pages, you must hand them to the student in a clear folder: numbered pages, a clear instruction ("answer only from these pages, cite the number, and say 'I don't know' if the answer is not here"), and the question. The numbering is what makes citations possible: the model can only cite what you labelled.

Prompt assembly rules.

  • Number each chunk [1], [2], ... and include its source name.
  • Tell the model to use only the context, to cite by number, and what to say when the context lacks the answer.
  • Put instructions first, context next, question last (Chapter 4).
  • Keep total tokens inside the budget (Chapter 4 context math). Retrieve more than you finally use, rerank, then keep the best few.
  • Treat chunk text as untrusted data (Chapter 9).

Here is the assembled prompt from our system for the refund question, and the fake generator's answer:

idx=build(chunk_sections)
q="How long does a refund take to process?"
p=assemble(q,retrieve(idx,q,2)); print(p); print("LLM:",fake_llm(p))
q="What is the CEO's name?"; p=assemble(q,retrieve(idx,q,2)); print("LLM:",fake_llm(p))
Answer ONLY from the context. Cite sources like [1]. If the context lacks the answer, say 'I do not know'.
Context:
[1] (refund_policy.md) # Refund policy
Refunds are available within 30 days of purchase.
Refunds are processed within 7 business days after approval.
[2] (shipping.md) # Shipping
Standard shipping takes 5 to 7 days. Express shipping takes 2 days.

Question: How long does a refund take to process?
Answer:
LLM: Refunds are processed within 7 business days after approval. [1]
LLM: I do not know.

Read it line by line. Chunk [1] is the refund section, which contains the answer; [2] is noise. The answer is the sentence "Refunds are processed within 7 business days after approval." with the citation [1], which points to refund_policy.md. For the second question, nothing in the context overlaps enough, so the system says "I do not know": this is the behaviour you want when the knowledge base has no answer. With a real LLM the instruction line does this job; with our fake it comes from a minimum-overlap rule.

Showing citations to the user. Map [1] back to the file name, section title and a link or page number from the chunk's metadata. In regulated work, also store the exact quote used. Verify citations in code: check that each cited number exists in the context and, ideally, that the quoted text really appears in the chunk. Models sometimes cite a chunk that does not support the sentence.

Problem 7.3.1 Your context budget is 3,000 tokens for chunks. Each chunk averages 350 tokens including its metadata line. How many chunks can you pass? If you retrieve 20 and rerank, how many are used?

Formulachunks that fit = floor(budget / chunk size)
Plug in3,000 / 350
Compute8.57, so 8 chunks (8 × 350 = 2,800 ≤ 3,000; 9 × 350 = 3,150 > 3,000)
AnswerAt most 8 chunks fit. Retrieve 20, rerank, and pass the top 3 to 8 depending on how many keep a good score.
Check2,800 + the instruction and question tokens must still be under the window (Chapter 4).
Why it mattersMore chunks raise cost and distraction; the right k is found by evaluation.

Problem 7.3.2 The answer cites [3] but only two chunks were provided. What do you do?

Step 1Detect it with a simple check: all cited numbers must be in 1..len(chunks).
Step 2Reject the answer, retry once with a reminder, or fall back to "I could not verify this answer".
AnswerTreat as a failed generation and do not show it to the user.
CheckAdd this check to your eval harness (Chapter 8) as a "citation validity" metric.

Predict, run, explain: a failure traced. For "Who pays customs fees on international orders?", the shipping document holds the fact "Customs fees are paid by the buyer." We run with both chunkers:

fixed:    0.45 shipping.md 1 | Express shipping takes 2 days. # International International orders ship in 10
          0.42 shipping.md 2 | ship in 10 to 14 days. Customs fees are paid by the
          answer: # International International orders ship in 10 [1]
sections: 0.70 shipping.md 1 | # International / International orders ship in 10 to 14 days. Customs fees are paid by the buyer.
          0.00 refund_policy.md 0 | # Refund policy / ...
          answer: International orders ship in 10 to 14 days. [1]

What happened: retrieval did its job in both runs (the shipping chunks are the top results). But with fixed chunks, the fact "paid by the buyer" is cut: the word "buyer" has been left out of both retrieved chunks, so even a perfect reader could not answer. With section chunks, the whole fact is in one chunk (score 0.70, much higher). The fake generator still picked the wrong sentence, because it only counts shared words ("International orders" shares two with the question, as does "Customs fees"; the first wins the tie). A real LLM reads meaning and would answer "the buyer". This is the point of the exercise: debug RAG in layers (was the right chunk retrieved? was the full fact inside it? did the generator use it?). Chapter 8 turns this into metrics.

Applications

  • Support and HR assistants: every answer links to the policy it came from.
  • Compliance: citations allow audit.
  • Analytics assistants: "answer only from this report".
COMMON MISTAKE
Trusting a citation because it is present. A citation shows where the model claims the answer came from; check it. Also, never let the model invent source names: build citations from your metadata, not from model-written text.

Check yourself

  1. Why number the chunks in the prompt?

Answer: So the model can cite them and you can map citations back to sources.

  1. What should the system say when the context lacks the answer?

Answer: That it does not know (as instructed), rather than guessing.

  1. What are the three layers to check when an answer is wrong?

Answer: Retrieval (right chunk found), chunk completeness (whole fact present), generation (used it correctly).

7.4 Advanced RAG

INTUITION
Basic RAG assumes the user's question is a good search query and that one lookup is enough. Real questions are vague ("what about that policy?"), multi-part ("compare plan A and plan B"), or need several hops. Advanced RAG adds smarter steps around the same core.
TechniqueWhat it doesWhen it helpsCost
Query rewriting / expansionAn LLM rewrites a vague or conversational question into a clear search query (and resolves "it", "that" using chat history)Chat assistantsOne extra LLM call
Multi-queryGenerate 3 to 5 paraphrases, search each, merge with RRF (Chapter 6)Ambiguous wordingMore searches
HyDE (Hypothetical Document Embeddings)The LLM writes a short imaginary answer, and you embed that instead of the question, because answers resemble documents more than questions doShort or vague queriesOne LLM call; can mislead if the imaginary answer is wrong
Parent-document retrievalSearch small chunks, return their parent sectionPrecise match plus full contextExtra storage
Contextual retrievalBefore embedding, prepend a one- or two-sentence context to each chunk ("This chunk is from the 2025 refund policy for digital goods")Chunks that lose meaning aloneAn LLM call per chunk at ingestion
Hybrid + rerankBM25 + vectors, then cross-encoder (Chapter 6)Almost alwaysLatency
GraphRAGExtract entities and relations into a graph, search the graph and summaries of communities"Global" questions across many documents, relationship questionsHeavy ingestion cost
Agentic RAGAn agent decides whether to search, what to search, and may search several times (Chapter 11)Complex or multi-hop questionsMore latency, cost and variance
Multi-hopThe answer needs fact A to find fact B ("Who manages the author of document X?")Linked dataIterative search

Problem 7.4.1 Chat history: User: "What is the refund window for gift cards?" Assistant: "Gift cards cannot be refunded." User: "And for digital downloads?" Write the rewritten standalone query, and say why it is needed.

Step 1The last question has no subject: "And for digital downloads?" searched alone would match anything about downloads.
Step 2Combine with the history: "What is the refund policy for digital downloads?"
AnswerRewritten query: "What is the refund policy for digital downloads?". Without rewriting, retrieval sees a fragment and fails.
CheckSearch both versions on your eval set (Chapter 8) and compare recall@k.
Why it mattersEvery multi-turn chatbot needs this step.

Problem 7.4.2 A question like "Compare the refund and shipping policies" needs two sets of facts. Which technique fits, and what is the risk?

Step 1Decompose into two sub-queries ("refund policy", "shipping policy"), search each (multi-query or agentic RAG), and merge.
Step 2Risk: one sub-query returns noise and the answer mixes sources; keep citations per sub-answer.
AnswerMulti-query or an agentic decomposition, with per-claim citations.
CheckVerify that the final answer cites at least one chunk from each policy.

Rule of thumb for adding complexity. Start with the simplest pipeline (chunk with headings, hybrid search, rerank, a clear prompt). Add one advanced technique at a time, and keep it only if the eval score improves enough to pay for the extra latency and cost. Frameworks such as LangChain, LlamaIndex and Haystack package these ideas; they speed up prototypes but hide the details. Prefer plain Python you understand until you know why you need a framework, as we did here.

Applications

  • Enterprise search: contextual retrieval and hybrid search over messy documents.
  • Research assistants: multi-hop and GraphRAG across papers or reports.
  • Customer chat: query rewriting from conversation history.
COMMON MISTAKE
Adding fashionable techniques without measuring. GraphRAG or agentic RAG on a simple FAQ adds cost and failure modes for no gain. Measure each change against the baseline.

Check yourself

  1. What does HyDE embed instead of the question?

Answer: A hypothetical answer generated by an LLM.

  1. Why does contextual retrieval help?

Answer: A chunk may be unclear alone; adding a short context makes its embedding and keywords more informative.

  1. Which technique fixes "And for digital downloads?"

Answer: Query rewriting using the chat history.

7.5 Failure Modes, Permissions and Operating RAG

INTUITION
A RAG system is a chain, and the chain breaks at its weakest link. The goal is to know every link, test each one separately, and make failures visible instead of silent. Think of a restaurant kitchen: if a dish is bad, check the ingredients, the cooking and the plating one by one.

Failure modes and fixes.

FailureWhat you seeTypical fix
Bad parsingGarbage text, merged columns, missing table headersBetter parser, OCR check, read samples
Bad chunkingFacts cut in half; chunk lacks contextStructure-aware chunks, heading paths, tune size
Missing documentThe answer is not in the index at allCoverage audit; answer "I do not know"
Retrieval missRight chunk exists but is not in the top kHybrid search, query rewriting, better embeddings, higher k, rerank
Too much noiseMany irrelevant chunks distract the modelLower k, rerank, score threshold
Conflicting sourcesOld and new policy both retrievedVersion metadata, prefer latest, show both with dates
Stale dataAnswer based on outdated contentRe-ingestion schedule, freshness filter
Generation ignores contextAnswer uses model memoryStricter prompt, lower temperature, faithfulness check (Chapter 8)
Wrong or fake citationCitation does not support the claimCode check, quote verification
Permission leakUser sees content they should notFilters inside retrieval (below)

Permissions-aware retrieval. Store each chunk's allowed groups or users as metadata and filter inside the vector search using the caller's identity from your login system, not from anything the user types. Never retrieve everything and rely on the prompt ("only show allowed content"), because a clever prompt or a model slip can leak it. Test with two users who should see different answers.

Problem 7.5.1 An HR bot is asked "What is Priya's salary?" by an ordinary employee. The salary sheet is in the index. Describe a correct design.

Step 1Each chunk of the salary sheet carries allowed_groups: ["hr-admin"].
Step 2The search call includes a filter allowed_groups intersects user.groups; the employee's groups do not include hr-admin, so those chunks are never retrieved.
Step 3The model sees no salary data and says it has no information.
AnswerEnforce access control in the retrieval filter, using trusted identity, before the model sees anything.
CheckWrite a test: ask as an admin and as a normal user; assert the normal user's retrieved chunk list contains no restricted chunk.

Problem 7.5.2 Your RAG assistant answers correctly in a demo but fails 40% of real questions. List the first four things you check, in order.

Step 1Collect 50 real failing questions (not demo questions) with the expected answers.
Step 2For each, check retrieval: is the gold chunk in the top 5? (This separates retrieval failures from generation failures.)
Step 3For retrieval failures, read the gold chunk: is it parsed and chunked sensibly? Then try hybrid search, rewriting and reranking, one at a time.
Step 4For generation failures (the right chunk was present), tighten the prompt, reduce noise chunks, and check faithfulness.
AnswerBuild a real eval set, then diagnose layer by layer; do not change several things at once.
CheckAfter each change, rerun the same 50 questions and record the score; keep a table of changes and results.

Operating RAG. Track per request: retrieved chunk ids and scores, prompt tokens, answer, citations validity, latency per stage, user feedback (thumbs up or down). Review thumbs-down cases weekly; they are your free eval set (Chapter 13).

Applications

  • Data Engineering: freshness and deletion jobs, access-control metadata.
  • GenAI engineering: layered debugging and eval-driven iteration.
  • Security and compliance: permission tests and audit logs.
COMMON MISTAKE
Blaming the LLM first. In most RAG failures the right text never reached the prompt. Always check what was retrieved before changing the prompt or the model.

Check yourself

  1. Where should access control be enforced in RAG?

Answer: In the retrieval filter, before the model sees any content.

  1. First diagnostic question for a wrong answer?

Answer: Was the right chunk retrieved?

  1. Why keep thumbs-down feedback?

Answer: It is a stream of real hard cases for the evaluation set.

Chapter recap

  • RAG = retrieve relevant chunks, then generate an answer from them with citations.
  • Ingestion quality (parsing, cleaning, metadata, freshness) caps everything after it.
  • Chunk by structure, keep heading context, start near 200 to 500 tokens with modest overlap, and test.
  • Prompt assembly: numbered chunks, "answer only from context", cite by number, say "I do not know" when unsupported.
  • Verify citations in code; build citations from metadata, not model text.
  • Advanced techniques (rewriting, multi-query, HyDE, parent-document, contextual retrieval, GraphRAG, agentic RAG) each cost something; add one at a time with measured gains.
  • Debug in layers: retrieval, chunk completeness, generation.
  • Enforce permissions in the retrieval filter with trusted identity.
  • Track retrieved ids, scores, tokens, latency and feedback for every request.

Practice set

Problem 7.P.1 (easy) What are the two phases of a RAG system? Answer: Offline indexing (parse, chunk, embed, store) and online answering (retrieve, assemble, generate).

Problem 7.P.2 (easy) Why must the prompt number the chunks? Answer: So the model can cite them and the app can map citations to sources.

Problem 7.P.3 (computation) 10,000 tokens, chunk size 500, overlap 100. Number of chunks? Answer: stride 400; (10,000 − 500)/400 = 23.75, ceiling 24, plus 1 = 25 chunks.

Problem 7.P.4 (computation) Chunk budget 2,400 tokens, average chunk 300. How many chunks fit? Answer: 2,400 / 300 = 8.

Problem 7.P.5 (what is the output?) With our code, what does fake_llm return when the best overlap between the question and any context sentence is 1? Answer: I do not know. because the overlap is below the minimum of 2.

Problem 7.P.6 (find the bug) A pipeline never deletes chunks of removed documents. A deleted discount policy is still quoted. Fix? Answer: Track document ids and hashes; on removal, delete all chunks with that document id from the index; add a nightly consistency check.

Problem 7.P.7 (find the bug) The code filters by permission after the model has produced the answer, by deleting sentences from the answer text. What is wrong? Answer: The model has already seen restricted content and may paraphrase it in ways the filter cannot catch. Filter chunks before generation.

Problem 7.P.8 (scenario) Users ask "what about its warranty?" after discussing a laptop model, and retrieval returns random warranty pages. What do you add? Answer: A query-rewriting step using the chat history to produce a standalone query naming the laptop model.

Problem 7.P.9 (interview) Explain the difference between a retrieval failure and a generation failure and how you tell them apart. Answer: A retrieval failure means the chunk with the answer was not in the prompt; a generation failure means it was in the prompt but the answer was wrong or ungrounded. Check whether the gold chunk is among the retrieved chunks for each failing question.

Problem 7.P.10 (interview) How would you decide chunk size for a contracts assistant? Answer: Start with structure-based chunks by clause, with the clause title as the heading path; build an eval set of real questions with the clause that answers each; try two or three sizes and strategies; compare recall@k and answer correctness; choose the smallest setup that meets the target, and re-test when documents change.
