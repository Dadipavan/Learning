In chapter 7 you built a prediction service, and in chapter 2 you packaged it in a Docker image. One container on your laptop is easy. But production needs three copies behind one address, restarts when a copy crashes, new versions without downtime, more copies when traffic grows, and GPU machines for the heavy jobs. Doing this by hand is a full-time job. Kubernetes (often written K8s) is the system most companies use to do it for you. This chapter teaches the small set of Kubernetes ideas that an ML engineer actually uses: pods, deployments, services, resource settings, probes, autoscaling, GPU nodes and KServe. We reuse one running example, the churn-api service from chapter 7, and a real YAML file that we parsed and checked. There is no cluster on this machine, so every kubectl command and cluster YAML is not run here. What we can run, we run: the YAML parser, the autoscaler formula and the scheduling arithmetic.

Words you need:

WordPlain meaning
ClusterA group of machines (nodes) that Kubernetes manages as one big computer.
NodeOne machine (virtual or physical) in the cluster.
PodThe smallest unit Kubernetes runs: one or more containers that share a network address.
ManifestA YAML file that describes what you want. You declare, Kubernetes makes it so.
LabelA key-value tag such as app: churn-api, used to find and group objects.
ControllerA loop inside Kubernetes that compares "what you asked for" with "what exists" and fixes the difference.
NamespaceA named folder inside a cluster, used to separate teams or environments.

11.1 Pods, Deployments and Services

INTUITION
Think of a restaurant. You tell the manager "I want three cooks on shift." You do not hire each cook yourself. If one cook falls sick, the manager brings another. Customers do not ask for a particular cook; they talk to the front desk, which sends them to any free cook. Kubernetes works the same: the Deployment is the manager's rule ("keep 3 copies"), each pod is a cook, and the Service is the front desk.

Declarative, not step by step

With a script you say how: "start a container, then start another." With Kubernetes you say what: "there should be 3 copies of this image." This is called declarative configuration. A controller keeps checking. If a pod dies, the count is 2 instead of 3, so the controller starts one. This loop is called the reconciliation loop, and it is the one idea behind most of Kubernetes.

The three objects you need first

ObjectJobChurn exampleWhere it appears in the job
PodRuns your container(s)One copy of the APIYou rarely create it by hand; you read its logs
DeploymentKeeps N identical pods running and rolls out new versionsreplicas: 3 of churn-api:1.4.0Every model service is a Deployment
ServiceA stable address that load-balances across pods with matching labelschurn-api on port 80Other apps call http://churn-api, not pod IPs

Why a Service at all? Pods are mortal. Each new pod gets a new IP address. If clients stored pod IPs, they would break at every restart. The Service gives one fixed name and spreads requests across healthy pods, like the reception desk of a clinic that sends each patient to whichever doctor is free.

The real manifest

This file is deploy.yaml from our lab. It is the Deployment and the Service for churn-api. It is not applied to a cluster here (not run here), but we parsed it with PyYAML to confirm that it is valid and the labels line up.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: churn-api
  labels: {app: churn-api}
spec:
  replicas: 3
  selector:
    matchLabels: {app: churn-api}
  template:
    metadata:
      labels: {app: churn-api}
    spec:
      containers:
        - name: api
          image: registry.example.com/churn-api:1.4.0
          ports: [{containerPort: 8000}]
          resources:
            requests: {cpu: "500m", memory: 512Mi}
            limits: {cpu: "1", memory: 1Gi}
          readinessProbe: {httpGet: {path: /ready, port: 8000}, periodSeconds: 5}
          livenessProbe: {httpGet: {path: /health, port: 8000}, periodSeconds: 10}
---
apiVersion: v1
kind: Service
metadata: {name: churn-api}
spec:
  selector: {app: churn-api}
  ports: [{port: 80, targetPort: 8000}]

Read it from the top.

  • kind: Deployment says what type of object this is. apps/v1 is the API version for it.
  • replicas: 3 means keep three pods.
  • selector.matchLabels says "this Deployment owns the pods labelled app: churn-api". The template block describes the pod to create, and its labels must match the selector.
  • image is the Docker image from chapter 2. Always use an exact tag such as 1.4.0, never latest, so you know what runs (same reasoning as pinning versions in chapter 2).
  • ports.containerPort: 8000 documents the port the app listens on.
  • resources and the two probes are explained in 11.2.
  • The Service has a selector for the same label. Traffic to Service port 80 goes to targetPort: 8000 on a matching pod.

Explain. safe_load_all reads both YAML documents (the --- line separates them) and refuses to run arbitrary code, as you learned in chapter 2. The first check proves the Deployment can find its own pods. The last line is the classic failure: with a typo the Service matches no pod, so it has no endpoints and every request fails, although all pods look healthy. In a real cluster you would see this with kubectl get endpoints churn-api showing <none>.

Problem 11.1.1 A Deployment has replicas: 3. One node crashes and takes one pod with it. How many pods exist right after the crash, and what does the controller do?

Formulamissing = desired − actual
Plug in3 − 2
Computemissing = 1
AnswerTwo pods remain. The Deployment's controller sees 2 of 3 and creates one new pod on a healthy node. The Service stops sending traffic to the dead pod at once, because it is no longer ready.
CheckAfter the new pod passes its readiness probe, the count is again 3, which equals the desired value.
Why it mattersThis is self-healing. You never log in to restart anything.

Problem 11.1.2 Rolling update. You change the image from 1.4.0 to 1.5.0 with replicas: 3, maxSurge: 1 and maxUnavailable: 0. At most how many pods exist during the update, and at least how many must be ready?

Formulamax pods = replicas + maxSurge; min ready = replicas − maxUnavailable
Plug in3 + 1 and 3 − 0
Compute4 and 3
AnswerUp to 4 pods may exist and at least 3 stay ready, so capacity never drops during the rollout. Kubernetes starts one new pod, waits until it is ready, stops one old pod, and repeats.
CheckThe script ch11a.py printed "at most 4 pods exist, at least 3 must stay ready".
Why it mattersThis is the zero-downtime release. It depends on the readiness probe (11.2) being honest. If the new model fails to load and the probe still says ready, bad pods get traffic.
COMMON MISTAKE
Label mismatch. The Deployment selector, the pod template labels and the Service selector must agree. A one-letter typo gives a Service with no pods. Always run kubectl get endpoints <service> after creating a Service.

Applications

  • ML Engineering: serve a model as a Deployment with 2-3 replicas for availability.
  • Data Engineering: run an API that serves features next to a model.
  • MLOps: roll out a new model version with a rolling update, then roll back with kubectl rollout undo deployment/churn-api.

Check yourself

  1. What object keeps N identical pods alive? Answer: a Deployment.
  2. Why do clients call a Service and not a pod IP? Answer: pod IPs change on every restart; the Service name stays fixed and load-balances.
  3. What does the selector connect? Answer: it connects a Deployment or Service to the pods that carry the same labels.

11.2 Resources, Probes, Config and Everyday Troubleshooting

INTUITION
A shared flat has a rule: each person tells the landlord how much space they need (the request) and the maximum they may ever use (the limit). The landlord only moves you into a flat that has the requested space. If you exceed the limit on memory, you are asked to leave. That is how Kubernetes treats a pod.

Requests and limits

  • A request is the amount the scheduler reserves for the pod. The scheduler (the part that picks a node) only places a pod on a node with enough unreserved capacity.
  • A limit is the maximum the pod may use. If a pod goes over its CPU limit, it is slowed down (throttled). If it goes over its memory limit, the container is killed (status OOMKilled, where OOM means out of memory).

CPU is measured in millicores: 1000m equals 1 vCPU, so 500m is half a vCPU. Memory uses Mi (mebibytes) and Gi (gibibytes). A mebibyte is 1,048,576 bytes, close to a megabyte.

Problem 11.2.1 One node has 4 vCPU and 16 GiB memory. The system needs 500m CPU and 1 GiB for itself. Each churn-api pod requests 500m CPU and 512 Mi memory. How many pods fit?

Formulapods = min( free CPU ÷ CPU request, free memory ÷ memory request )
Plug infree CPU = 4000 − 500 = 3500m; free memory = 16,384 − 1,024 = 15,360 Mi
ComputeCPU: 3500 ÷ 500 = 7. Memory: 15,360 ÷ 512 = 30. min(7, 30) = 7
Answer7 pods fit; CPU is the limiting resource, memory would allow 30.
CheckThe script printed 7 (cpu allows 7 , memory allows 30 ).
Why it mattersThis is capacity planning (chapter 14) in Kubernetes form. If one pod handles about 100 requests per second (an assumed number), this node is good for roughly 700 requests per second before you add a node.

Probes: the two questions again

Remember chapter 7: /health says "alive" and /ready says "able to serve". Kubernetes uses exactly these.

ProbeQuestionIf it failsOur endpoint
LivenessIs the process stuck?Kubernetes restarts the container/health
ReadinessCan it serve right now?The pod is removed from the Service until it recovers/ready
Startup (optional)Has a slow start finished?Delays the other probesFor big models that load slowly

A model that takes 90 seconds to load must not receive traffic at second 10. The readiness probe keeps it out of the Service until the model is loaded. Keep liveness cheap and not dependent on a database, or a database outage will cause a restart storm.

A CronJob for nightly batch scoring (not run here):

apiVersion: batch/v1
kind: CronJob
metadata: {name: churn-batch-score}
spec:
  schedule: "0 2 * * *"          # minute hour day month weekday: every day at 02:00
  concurrencyPolicy: Forbid       # do not start a second run if the last is still going
  jobTemplate:
    spec:
      backoffLimit: 2             # retry a failed pod up to 2 times
      template:
        spec:
          restartPolicy: Never
          containers:
            - name: scorer
              image: registry.example.com/churn-batch:1.4.0
              args: ["--date", "yesterday"]
              resources:
                requests: {cpu: "2", memory: 4Gi}

concurrencyPolicy: Forbid and the retry count connect to chapter 6: the batch task should be idempotent, so a retry cannot double the output.

Helm and Kustomize

You will need almost the same YAML for dev, staging and prod, with a few values different (replica count, image tag, memory). Copying files invites mistakes. Helm packages manifests as a template with a values.yaml file (helm install churn ./chart -f values-prod.yaml). Kustomize keeps a base set of manifests and applies small patches per environment (kubectl apply -k overlays/prod). Both are not run here. Pick whichever your team uses; learning one makes the other easy.

Troubleshooting drill

When something fails, use this ladder. Run the commands in order (not run here).

kubectl get pods                       # status: Pending, CrashLoopBackOff, ImagePullBackOff, OOMKilled?
kubectl describe pod churn-api-7d9f-abc   # the Events section at the bottom explains most problems
kubectl logs churn-api-7d9f-abc           # app output; add --previous for the crashed container
kubectl get endpoints churn-api           # does the Service have pods behind it?
kubectl rollout status deployment/churn-api
kubectl rollout undo deployment/churn-api # go back one version

Applications

  • MLOps: batch scoring CronJob with retries and no overlapping runs.
  • ML Engineering: ConfigMap holds the model alias, so promotion needs no new image.
  • Platform teams: namespaces and RBAC separate dev and prod, with quotas per team.

Check yourself

  1. What happens when a container goes over its memory limit? Answer: it is killed with OOMKilled and restarted.
  2. Which probe removes a pod from the Service without restarting it? Answer: the readiness probe.
  3. Is a base64-encoded Secret encrypted? Answer: no, it is only encoded; control access and enable encryption at rest.

11.3 Autoscaling: HPA, VPA, KEDA and Knative

INTUITION
A supermarket opens extra checkout lanes when the queue grows and closes them when it is empty. Too late, and customers wait. Too eager, and cashiers stand idle. Autoscaling is the rule for opening and closing lanes, and it has the same trade-off.

The HPA formula

The Horizontal Pod Autoscaler (HPA) changes the number of replicas. "Horizontal" means more copies, not bigger copies. Every cycle (about 15 seconds by default) it computes:

desiredReplicas = ceil( currentReplicas × currentMetric ÷ targetMetric )

then clamps the result between minReplicas and maxReplicas. It also ignores small differences (default tolerance 10%) to avoid flapping, and it waits before scaling down (a stabilisation window, 5 minutes by default) so a short dip does not remove capacity. Check defaults against your Kubernetes version.

The HPA manifest (not run here):

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: {name: churn-api}
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: churn-api}
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: {type: Utilization, averageUtilization: 60}

CPU Utilization is measured as a percent of the pod's request, not the limit. So HPA only works if you set the CPU request. With a request of 500m, 60% means 300m average per pod.

Problem 11.3.1 Three pods, CPU averages 90% of request, target 60%. How many replicas does the HPA want?

Formuladesired = ceil(current × metric ÷ target)
Plug inceil(3 × 90 ÷ 60)
Compute3 × 90 = 270; 270 ÷ 60 = 4.5; ceil(4.5) = 5
Answer5 replicas. The pods are 1.5 times too busy, so the HPA wants 1.5 times the pods, rounded up.
CheckWith 5 pods the same total load gives 270 ÷ 5 = 54% each, below the 60% target.
Why it mattersRounding up is deliberate: it is safer to have a little spare capacity.

Problem 11.3.2 Same service, now load drops: 3 pods at 20% CPU. And a second case: 8 pods at 150% with maxReplicas: 10. What does HPA choose in each?

Formuladesired = ceil(current × metric ÷ target), then clamp to [min, max]
Plug inCase 1: ceil(3 × 20 ÷ 60); Case 2: ceil(8 × 150 ÷ 60)
ComputeCase 1: 60 ÷ 60 = 1, so 1, but minReplicas is 2, so 2. Case 2: 1200 ÷ 60 = 20, but maxReplicas is 10, so 10.
Answer2 replicas in case 1 and 10 in case 2. In case 2, the cap protects your bill but the service stays overloaded, so you should alert when HPA sits at max.
CheckThe script printed current=3 metric=20% -> 2 and current=8 metric=150% -> 10.
Why it mattersminReplicas gives availability (never go below 2 so one failure is survivable) and maxReplicas gives a cost ceiling.

The catch: scaling is slower than a spike

A new pod must be scheduled, the image pulled, the model loaded, and the readiness probe passed. For a large model that can take minutes. If traffic doubles in 30 seconds, HPA cannot save you. The remedies connect to chapter 7: keep a higher minReplicas for known peaks, scale at 50-60% not 90%, use small images, and use warm pools. Test it like anything else: ramp the load up in steps and watch response time while the replica count changes (chapter 14).

Other autoscalers

ToolWhat it scalesUse for ML
HPAPod count, on CPU, memory or custom metricsDefault for APIs
VPA (Vertical Pod Autoscaler)The size (requests) of each podFinding the right request values; do not combine with HPA on the same CPU metric
Cluster Autoscaler or KarpenterNumber of nodesAdds nodes when pods are Pending, removes empty ones
KEDA (Kubernetes Event-Driven Autoscaling)Pods based on queue length, Kafka lag, Prometheus queries; can scale to zeroQueue workers for batch inference
KnativePods based on requests in flight; scale to zeroServerless-style model endpoints, used under KServe

For GPU services, CPU is often a poor signal. Better signals are request concurrency, queue length, or GPU utilisation exported to Prometheus.

COMMON MISTAKE
Autoscaling on CPU for a model that is memory-bound or GPU-bound. The HPA never fires and latency climbs. Pick the metric that actually saturates first, which you find by load testing.

Applications

  • ML Engineering: HPA on an online scoring API with min 2, max 10.
  • Data Engineering: KEDA scales workers by Kafka consumer lag.
  • GenAI: scale on concurrent requests or queue depth for a self-hosted LLM.
  • FinOps: scale to zero overnight for internal tools.

Check yourself

  1. 4 pods at 30% CPU, target 60%. Desired replicas (min 2)? Answer: ceil(4 × 30 ÷ 60) = 2.
  2. Why must a CPU request be set for CPU-based HPA? Answer: utilisation is a percentage of the request.
  3. Why can HPA fail on a sudden spike? Answer: new pods need time to start and load the model.

11.4 GPU Nodes, KServe and the ML Tool Landscape

INTUITION
A GPU node is a specialist who costs ten times a normal worker. You do not want ordinary jobs sitting in the specialist's office, and you do not want the specialist idle. Kubernetes lets you reserve the office (taints), say "I need a specialist" (resource requests), and send only the right work there.

GPUs in Kubernetes

Chapter 6 covered GPU cost. Kubernetes adds three ideas.

  1. Device plugin. An add-on (for NVIDIA, the NVIDIA device plugin and GPU operator) tells Kubernetes how many GPUs each node has. The pod then asks for them as nvidia.com/gpu.
  2. Whole units. GPUs are requested as integers in limits. You cannot ask for 0.5 GPU in plain Kubernetes. Sharing needs extra features (time slicing, or MIG, Multi-Instance GPU, which splits some GPUs into isolated slices). Support depends on hardware and version.
  3. Taints and tolerations. A taint on a node says "keep out unless you tolerate me". GPU node pools are tainted so that ordinary pods do not occupy expensive GPUs. A GPU pod carries a matching toleration (and a nodeSelector or affinity to choose the pool).

A GPU inference pod (not run here):

apiVersion: v1
kind: Pod
metadata: {name: llm-server}
spec:
  nodeSelector: {pool: gpu-a10}         # label set by the cloud node pool; name is an example
  tolerations:
    - {key: nvidia.com/gpu, operator: Exists, effect: NoSchedule}
  containers:
    - name: server
      image: registry.example.com/llm-server:0.3.1
      resources:
        limits: {nvidia.com/gpu: 1, memory: 32Gi}

Problem 11.4.1 Two GPU nodes with 4 GPUs each. Jobs arrive needing 1, 1, 2, 4 and 1 GPUs, in this order, and the scheduler puts each on the first node with enough free GPUs. What happens?

Step 1Job 1 (1 GPU) goes to node 0: node 0 has 3 free.
Step 2Job 2 (1 GPU) goes to node 0: 2 free. Job 3 (2 GPUs) goes to node 0: 0 free.
Step 3Job 4 (4 GPUs) needs a whole node. Node 0 has 0 free, node 1 has 4, so it goes to node 1: 0 free.
Step 4Job 5 (1 GPU): no node has a free GPU, so it stays Pending.
AnswerFour jobs run, the fifth waits. All 8 GPUs are busy, so the right action is to queue or add a node, not to debug the job.
CheckThe script printed job needing 1 GPU -> Pending (no node has 1 free) with free [0, 0].
Why it mattersPending jobs with "Insufficient nvidia.com/gpu" are the most common GPU complaint. Fragmentation is real too: if job 4 had arrived last, it could not find 4 free GPUs on one node even if 4 were free in total across two nodes.

Problem 11.4.2 A GPU node costs $2.50 per hour (an assumed price). Compare always-on for a 730-hour month against running 10 hours on 22 working days (220 hours).

Formulacost = hourly price × hours
Plug in2.50 × 730 and 2.50 × 220
Compute1,825 and 550
Answer$1,825 versus $550, a saving of $1,275, or 70%, by scaling the GPU pool to zero outside working hours.
Check220 ÷ 730 = 0.30, so the cost is 30% of always-on; the saving is 70%.
Why it mattersIdle GPUs are the biggest avoidable bill. Use the Cluster Autoscaler with a node pool whose minimum size is 0.

KServe: a model-serving layer on Kubernetes

Writing a Deployment, Service, HPA and canary logic for every model is repetitive. KServe adds a custom object, InferenceService, that does it for you. You say where the model is and what format it has; KServe creates the pods, the Service and the autoscaling (through Knative, including scale to zero, or through plain HPA depending on mode), and it speaks a standard inference protocol. Chapter 7 introduced it; here is the manifest (not run here; field names evolve, check the KServe documentation for your version):

apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata: {name: churn-model}
spec:
  predictor:
    minReplicas: 1
    maxReplicas: 5
    model:
      modelFormat: {name: sklearn}
      storageUri: s3://ml-models/churn/v2      # the registry's artifact location (chapter 3)

A canary release is one extra line, canaryTrafficPercent: 10, on the updated predictor: 10% of traffic goes to the new revision while 90% stays on the old one. Chapter 8 explains why and when to promote.

KServe is a good answer to "how would you deploy a model on Kubernetes at scale?" The other honest answer is "a plain Deployment, if I have one model and a small team". Do not use a heavy platform for a single small model.

Applications

  • MLOps: KServe InferenceService per model, with canary percent.
  • Deep Learning: GPU Jobs for training with a queue (Kueue or Volcano).
  • GenAI: vLLM Deployment on a GPU pool, scaled by queue length.
  • Platform engineering: namespace quotas so one team cannot take all GPUs.

Check yourself

  1. Why taint GPU nodes? Answer: so that ordinary pods do not occupy expensive GPUs.
  2. Can plain Kubernetes give a pod half a GPU? Answer: no, GPU requests are whole numbers; sharing needs MIG or time slicing.
  3. What does KServe's InferenceService replace? Answer: hand-written Deployment, Service, autoscaler and rollout logic for a model.

Chapter recap

  • Kubernetes is declarative: you state the desired state, and controllers keep reconciling reality to it.
  • Pod runs containers, Deployment keeps N copies and does rolling updates, Service gives a stable address by matching labels.
  • A label typo gives a Service with no endpoints: we parsed the real YAML and showed the mismatch.
  • Requests reserve capacity; limits cap it. Memory over limit means OOMKilled. Our example node fits 7 pods (CPU is the limit).
  • Liveness restarts, readiness removes from traffic; a slow-loading model needs readiness (and perhaps a startup probe).
  • HPA: ceil(current × metric ÷ target), clamped to min and max. 3 pods at 90% against 60% target need 5.
  • Scaling is slower than spikes; keep headroom and test it under load.
  • GPUs are whole units, tainted pools protect them, and idle GPU time is the big cost: $1,825 always-on versus $550 for work hours in our assumed example.
  • KServe turns "model location plus format" into a scaled service with canary support; start simple.

Practice set

Problem 11.1 (easy) What does 1500m CPU mean? Answer: 1.5 vCPU, because 1000m is one vCPU.

Problem 11.2 (easy) A Deployment says replicas: 4. How many pods exist when it is healthy, and which object keeps it so? Answer: Four pods, kept by the Deployment's controller (through a ReplicaSet).

Problem 11.3 (what is the output?) desired = ceil(5 × 45 ÷ 60) with min 2, max 8. What is it? Answer: 5 × 45 = 225; 225 ÷ 60 = 3.75; ceil = 4. Within 2 to 8, so 4.

Problem 11.4 Pods request 250m CPU and 256 Mi memory. A node has 2 vCPU and 4 GiB free for pods. How many fit? Answer: CPU: 2000 ÷ 250 = 8. Memory: 4096 ÷ 256 = 16. Minimum is 8 pods.

Problem 11.5 (find the bug) A Service has selector: {app: churn}, the pods have app: churn-api. kubectl get pods shows all Running, yet calls fail. Why? Answer: The selector does not match the pod labels, so the Service has no endpoints. Fix the selector, then check kubectl get endpoints.

Problem 11.6 (find the bug) An HPA with CPU target 60% never scales, but the pods are slow. kubectl describe hpa says the metric is <unknown>. What is likely missing? Answer: A CPU request on the container (utilisation is relative to the request), or the metrics server is not installed.

Problem 11.7 The HPA is at maxReplicas: 10 for an hour with CPU at 140%. What should you do? Answer: Alert on it. Raise max if budget allows, add node capacity, find the bottleneck, or shed load. Capping protects cost but not users.

Problem 11.8 (scenario) A pod with an LLM is Pending with event "0/3 nodes are available: 3 Insufficient nvidia.com/gpu". Give two causes. Answer: All GPUs are already requested by other pods, or the GPU node pool has scaled to zero or is at its maximum size so no node can be added. Check quotas and the cluster autoscaler.

Problem 11.9 (interview) "How do you deploy a new model version with no downtime on Kubernetes?" Answer: Rolling update with maxUnavailable: 0, a truthful readiness probe, an exact image tag, and a rollback command ready. For risk control, a canary (KServe canaryTrafficPercent or traffic splitting) with metrics comparison before full promotion.

Problem 11.10 (interview) "Would you use Kubernetes for one small model?" Answer: Perhaps not. A managed endpoint (SageMaker, Vertex, Azure ML) or serverless container service gives autoscaling with less operational work. Kubernetes pays off with many services, GPU pools, or a platform team to run it.

Problem 11.11 A GPU pool of 4 nodes at $3 per hour (assumed) runs 24/7 but is used 8 hours a day. What is the monthly waste, 730 hours? Answer: Always-on: 4 × 3 × 730 = $8,760. Used share: 8/24 = one third, so useful cost is $2,920 and waste is about $5,840, about 67%.
