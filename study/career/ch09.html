In interviews for data engineer, ML engineer and AI engineer roles, this is the round that decides the offer. 9.1 The ML Design Framework and the Data Platform

INTUITION
A model is the chef; the data platform is the whole supply chain. A brilliant chef with late, dirty or missing ingredients cooks bad meals. Most ML failures in companies are supply-chain failures, not model failures.

The framework (eleven steps)

Use it for any ML or AI design question.

  1. Business objective. What outcome do we want (fewer chargebacks, more orders)?
  2. Metrics. Offline (measured on past data: precision, recall, NDCG) and online (measured live: conversion, revenue, complaints). Add guardrail metrics that must not get worse (latency, complaints).
  3. Data. Sources, volume, labels, freshness, privacy.
  4. Features. Inputs the model uses, and how they are computed.
  5. Model options. Start with a simple baseline, then something stronger.
  6. Training. How often, on what, with what split.
  7. Evaluation. Offline tests, then an A/B test (Chapter 7 and the learner's statistics document).
  8. Serving. Batch (scores computed ahead) or online (scores computed per request); latency and cost.
  9. Monitoring. Data drift, model quality, system health.
  10. Iteration. How you ship version 2 safely.
  11. Risks. Bias, privacy, abuse, failure modes.

The data platform

A data platform moves data from where it is produced to where it is used, reliably. Words you need:

WordPlain meaning
IngestionBringing data in: batch (files on a schedule) or streaming (events as they happen)
CDCChange Data Capture: copying each database change as an event
Raw zone / data lakeCheap storage (object storage) keeping data exactly as received
TransformCleaning and joining (Spark, dbt)
WarehouseA database built for analysis; clean tables
OrchestrationA scheduler that runs steps in order and retries (Airflow)
LineageA record of where each table came from
FreshnessHow old the newest data is

Left to right: sources (apps, databases, logs) enter through ingestion (CDC, Kafka or batch), land untouched in the raw zone, are cleaned by transforms into the warehouse, then feed dashboards, APIs, the feature store and model training. The bottom band says orchestration, quality tests, lineage and access control touch every box.

Data engineers build this picture daily. Analysts consume the warehouse. ML engineers add the feature store. Quality tests (nulls, duplicates, row counts) and freshness alerts are the platform's equivalent of a shop's daily till check.

COMMON MISTAKE
Drawing the model box first. Ask for the metric and the data freshness before the model.

Check yourself

  2. What does CDC copy? Answer: each database change, as an event.
  3. What is a guardrail metric? Answer: one that must not get worse, such as latency.

9.2 Feature Pipelines and Training-Serving Skew

INTUITION
A student practises with a past paper and the answers revealed would score 100% in practice and fail the real exam. Leaking the future into training does the same to a model. A feature is an input column the model reads, such as "average spend in the last 30 days".

How it works

A feature store keeps feature values so that training and serving use the same definitions. It has an offline store (history, for training) and an online store (latest values, for fast lookup). Two dangers:

  • Training-serving skew: the feature is computed one way in training (SQL) and another in serving (Python), so the model sees different data live than it learned on.
  • Leakage: training rows use information that did not exist at prediction time.

The cure for leakage is a point-in-time join: for each label at time t, use the latest feature value at or before t.

Problem 9.2.1 Table feat holds avg_spend per user over time; table label says whether the user churned (left) at a time. Compare the wrong and the right join.

import sqlite3
c = sqlite3.connect(":memory:")
c.executescript("""
create table feat(user_id int, ts text, avg_spend real);
insert into feat values (1,'2026-01-01',100),(1,'2026-01-10',500),(2,'2026-01-05',80);
create table label(user_id int, ts text, churned int);
insert into label values (1,'2026-01-08',0),(1,'2026-01-12',1),(2,'2026-01-04',0);
""")
print("WRONG (latest feature, leaks future):")
for r in c.execute("""select l.user_id,l.ts,l.churned,
  (select avg_spend from feat f where f.user_id=l.user_id order by ts desc limit 1) from label l order by 1,2"""): print(r)
print("RIGHT (latest feature at or before label time):")
for r in c.execute("""select l.user_id,l.ts,l.churned,
  (select avg_spend from feat f where f.user_id=l.user_id and f.ts<=l.ts order by ts desc limit 1) from label l order by 1,2"""): print(r)
WRONG (latest feature, leaks future):
(1, '2026-01-08', 0, 500.0)

(1, '2026-01-08', 0, 100.0)
(1, '2026-01-12', 1, 500.0)

  • Step 1 Wrong query: the sub-select takes the newest feature for the user, whatever its date. User 1 at 2026-01-08 gets 500, which was only computed on 2026-01-10, two days in the future. User 2 at 2026-01-04 gets 80, from 2026-01-05, one day in the future.
  • Step 2 Right query adds f.ts <= l.ts. User 1 at 01-08 gets 100 (from 01-01). User 1 at 01-12 gets 500 (from 01-10). User 2 at 01-04 gets None: no feature existed yet.
  • Answer The right join shows what the model could really have known; the wrong join gave 2 of 3 rows information from the future.
  • Check For every row in the right output, the feature date is at or before the label date. For user 2 the honest answer is "missing", not 80.
  • Why it matters Leakage makes offline scores look great and online results disappointing. It is the commonest cause of "the model worked in the notebook".

Problem 9.2.2 Your fraud model uses avg_txn_30d. Training computes it in SQL with calendar days; serving computes it in code with the last 720 hours. What is the risk and the fix?

Step 1The two definitions differ for a user active near a day boundary, so training and serving feature values disagree.
Step 2The model sees a distribution at serving time it never trained on: skew.
Step 3Fix: define the feature once (one code path or one feature-store definition) and log the served feature values, then compare them to training values regularly.
AnswerOne definition, shared by training and serving, plus a logged comparison.
CheckIf the logged and recomputed values differ for the same user and time, the skew exists.

Where it is used

ML engineers own this daily. Data engineers build the pipelines that fill the stores. AI engineers have the same problem for retrieval metadata.

COMMON MISTAKE
Random train-test split on time data. Use a time split (train on the past, test on later weeks), or you leak the future.

Check yourself

  1. What does a point-in-time join do? Answer: uses the latest feature at or before the label time.
  2. What is skew? Answer: features computed differently in training and serving.
  3. Offline versus online store? Answer: history for training versus latest values for fast serving.

9.3 Worked Design: Recommender System

INTUITION
A shop assistant cannot show you all 1 million products. She first picks a few hundred that might suit you (fast, rough), then ranks them with more care (slow, precise), then arranges the shelf. Recommenders work in these stages because a heavy model on every item is too slow.

The funnel

A catalogue of 1 million items and a budget of about 100 ms per request. The standard design is a funnel:

  1. Candidate retrieval: an approximate nearest neighbour (ANN) search over embeddings (vectors that place similar things close together) gives about 500 items.
  2. Light ranker: a fast model cuts 500 to 100.
  3. Heavy ranker: a richer model scores 100 and keeps 20.
  4. Rules and diversity: remove out-of-stock and duplicates, mix categories, return 10.
stages = [("retrieval ANN", 1_000_000, 500, 15), ("light ranker", 500, 100, 10),
          ("heavy ranker", 100, 20, 40), ("rules + diversity", 20, 10, 5)]
total = 0
for name, n_in, n_out, ms in stages:
    total += ms
    print(f"{name:18s} {n_in:>9,} -> {n_out:>4}  {ms:3d} ms  cumulative {total} ms")
relevant = {3, 7, 9}
ranked = [7, 1, 3, 4, 5, 9, 2]
for k in (2, 4, 6):
    hits = len(relevant & set(ranked[:k]))
    print(f"precision@{k} = {hits}/{k} = {hits/k:.2f}   recall@{k} = {hits}/{len(relevant)} = {hits/len(relevant):.2f}")
items = 1_000_000; d = 64
print("item embeddings MB (float32, d=64):", items * d * 4 / 1e6)
retrieval ANN      1,000,000 ->  500   15 ms  cumulative 15 ms
light ranker             500 ->  100   10 ms  cumulative 25 ms
heavy ranker             100 ->   20   40 ms  cumulative 65 ms
rules + diversity         20 ->   10    5 ms  cumulative 70 ms

precision@4 = 2/4 = 0.50   recall@4 = 2/3 = 0.67

Two more points an interviewer expects. Cold start: a new user or item has no history, so use popularity, content features and exploration. Online metrics and bias: the model only learns from items it showed, so keep a small share of random exploration and run A/B tests with guardrails (return rate, latency). Chapter 8.8 gave the feed side of delivery.

Where it is used

E-commerce home pages, video and music queues, job and course suggestions, "similar items" on product pages. An ML engineer owns the ranker, a data engineer the feature and event pipelines.

COMMON MISTAKE
Optimising an offline metric that does not match the business goal (for example clicks when you care about purchases). Define the online metric first.

Check yourself

  1. Why a funnel? Answer: a heavy model on every item would exceed the latency budget.
  2. precision@3 if 2 of the top 3 are relevant? Answer: 2/3 = 0.67.
  3. What is cold start? Answer: no history for a new user or item.

9.4 Worked Design: Fraud Detection

INTUITION
A bank sees 999 genuine transactions for every fraud. If your alarm is even slightly jumpy, it rings mostly for innocent people. The fight is not "is my model accurate"; it is "how many false alarms per real catch can the team handle".

Why accuracy lies

Fraud is rare. If 0.1% of transactions are fraud, a model that says "never fraud" is 99.9% accurate and catches nothing. Use recall (the share of frauds caught), false positive rate (FPR: the share of genuine transactions flagged) and precision (the share of flags that are really fraud). By Bayes' rule, with base rate b:

precision = recall × b / (recall × b + FPR × (1 − b))

Problem 9.4.1 5,000 transactions per second, 0.1% fraud. For three models, find precision and the flags per second.

tps = 5000; fraud_rate = 0.001
print("fraud tx/s:", tps * fraud_rate, " per day:", tps * fraud_rate * 86400)
for recall, fpr in ((0.8, 0.005), (0.8, 0.001), (0.9, 0.02)):
    tp = recall * fraud_rate
    fp = fpr * (1 - fraud_rate)
    prec = tp / (tp + fp)
    flagged_per_s = tps * (tp + fp)
    print(f"recall {recall} fpr {fpr}: precision {prec:.3f}, flagged/s {flagged_per_s:.1f}, false alarms/s {tps*fp:.1f}")
fraud tx/s: 5.0  per day: 432000.0
recall 0.8 fpr 0.005: precision 0.138, flagged/s 29.0, false alarms/s 25.0
recall 0.8 fpr 0.001: precision 0.445, flagged/s 9.0, false alarms/s 5.0
recall 0.9 fpr 0.02: precision 0.043, flagged/s 104.4, false alarms/s 99.9
  • Step 1 Model A: true positives per transaction = 0.8 × 0.001 = 0.0008. False positives = 0.005 × 0.999 = 0.004995.
  • Step 2 Precision = 0.0008 / (0.0008 + 0.004995) = 0.0008 / 0.005795 = 0.138.
  • Step 3 Flags per second = 5,000 × 0.005795 = 29; of these 25 are false alarms.
  • Answer A catches 80% of fraud but only 14% of its flags are real: about 6 false alarms for every real fraud. Model C catches 90% but only 4% of flags are real, with 100 flags per second.
  • Check Real frauds caught per second for A = 5 × 0.8 = 4; flags 29; 4 / 29 = 0.138. Matches.
  • Why it matters A model with a 0.5% false-positive rate sounds excellent and still gives 25 false alarms per second. Base rates decide.

Problem 9.4.2 Pick the threshold by money. Per 1 million transactions: a missed fraud costs 8,000 (rupees, assumed), reviewing one flag costs 40 (assumed). Compare model A (recall 0.8, FPR 0.005) and model B (recall 0.9, FPR 0.02).

loss_per_fraud = 8000; review_cost = 40
n = 1_000_000
frauds = n * fraud_rate
for name, recall, fpr in (("A", 0.8, 0.005), ("B", 0.9, 0.02)):
    caught = frauds * recall
    fa = (n - frauds) * fpr
    net = caught * loss_per_fraud - (caught + fa) * review_cost
    print(name, "caught", caught, "false alarms", round(fa), "net saving", round(net))
A caught 800.0 false alarms 4995 net saving 6168200
B caught 900.0 false alarms 19980 net saving 6364800
  • Step 1 Frauds: 1,000,000 × 0.001 = 1,000. Model A catches 800; model B catches 900.
  • Step 2 A: savings 800 × 8,000 = 6,400,000; review cost (800 + 4,995) × 40 = 231,800; net 6,168,200.
  • Step 3 B: savings 900 × 8,000 = 7,200,000; review cost (900 + 19,980) × 40 = 835,200; net 6,364,800.
  • Answer B is worth 196,600 more per million transactions, even with four times the false alarms, because each caught fraud is worth 200 reviews.
  • Check 6,364,800 − 6,168,200 = 196,600. This assumes every flag is reviewed and every caught fraud is fully saved; real analyst capacity, customer annoyance and review time would change the answer.

The design in one view

  • Data: transactions, device, merchant, history. Labels arrive late (chargebacks take weeks), so train on older data and expect label delay.
  • Features: velocity (count in the last 1, 10, 60 minutes), amount versus the user's usual, new device, geography. Use streaming aggregates and a point-in-time join (9.2).
  • Serving: online scoring inside the payment path with a strict budget (for example under 100 ms, a business choice). Fallback rules if the model service is slow: apply rules and fail safe.
  • Decision: approve, step-up verification (one-time password), or block. Threshold by cost (9.4.2), not by 0.5.
  • Monitoring: drift, flag rate, review outcomes; fraudsters adapt, so retrain often.
  • Risks: unfair bias against groups, privacy rules (India's data protection law and your company's policy; check with your compliance team).

Where it is used

Banks, UPI apps, card networks, insurance claims, e-commerce returns, ad click fraud.

COMMON MISTAKE
Judging by accuracy or by ROC curve alone. Always compute precision and the alert volume at the base rate, and the cost at the chosen threshold.

Check yourself

  1. 0.2% fraud, recall 0.5, FPR 0.01. Precision? Answer: 0.001 / (0.001 + 0.00998) = 0.091.
  2. Why are labels delayed? Answer: chargebacks and confirmations arrive weeks later.
  3. Why not threshold 0.5? Answer: costs of misses and false alarms are unequal; pick by expected cost.

9.5 Worked Design: RAG Chatbot for Company Documents

INTUITION
An open-book exam. The model does not memorise your policies. When a question arrives, a librarian fetches the 3 most relevant pages and the model answers from them, quoting the page. That is RAG (retrieval-augmented generation).

Offline (top): documents are cleaned and cut into chunks, each chunk is turned into an embedding by an embedding model, and stored with metadata in a vector database. Online (bottom): the user's question is embedded, a top-k search finds similar chunks (optionally reranked), and the large language model (LLM) answers from them with citations. A band says guardrails and evaluation wrap the whole path: log every question, chunk and answer.

First: prompt, RAG, fine-tune or agent?

NeedChooseWhy
Change tone or format, general knowledge is enoughPromptingCheapest, fastest
Answers must use private or changing documentsRAGUpdate the index, not the model
Consistent style or a narrow task at scaleFine-tuningBakes behaviour into weights; needs data and evaluation
Multi-step actions with tools (look up, calculate, book)AgentLoop of plan and tool calls; higher risk and cost

Start with prompting, add RAG, fine-tune only with evidence it is needed, add agents only when the task needs actions.

Evaluation, guardrails, failures

You cannot improve what you do not measure. Build a golden set: 50 to 200 real questions with the correct source chunk. Measure retrieval first (hit@k: is the right chunk in the top k?) and answer quality separately (is it correct, grounded in the chunks, with citations?).

Problem 9.5.3 Four questions have gold chunks d4, d9, d2, d7. The retriever returned: q1 [d4, d1, d3], q2 [d5, d6, d9], q3 [d8, d1, d5], q4 [d7, d2, d3]. Compute hit@1 and hit@3.

Step 1hit@1 looks at the first item only: q1 yes (d4), q2 no, q3 no, q4 yes (d7). That is 2 of 4.
Step 2hit@3 looks at all three: q1 yes, q2 yes (d9 is third), q3 no, q4 yes. That is 3 of 4.
Answerhit@1 = 0.50 and hit@3 = 0.75. Question q3 never finds its chunk, so inspect q3's chunks (perhaps the document was split badly).
CheckThe code printed hit@1 = 2/4 = 0.50 and hit@3 = 3/4 = 0.75.

Design points for the interview: chunk size (too small loses context, too large dilutes meaning; test 300 to 800 tokens), metadata filters (department, date, access rights: never show a user a document they may not read), hybrid search (keyword plus vectors helps with names and codes), rerank, refusal ("I could not find this in the documents"), prompt injection (text inside a document that tries to give the model orders; treat retrieved text as data, never as instructions), human in the loop for risky answers, and logging every question, chunk and answer for review. Chapter 4 covers the README and design doc to write this up.

Where it is used

Internal helpdesks, policy and HR assistants, customer-support copilots, search over contracts and manuals. AI engineers own it, data engineers feed and refresh the index.

COMMON MISTAKE
Judging the chatbot by a few good demos. Without a golden set you cannot tell whether a change helped, and you will ship hallucinations (confident wrong answers).

Check yourself

  1. RAG or fine-tuning for changing policies? Answer: RAG; update the index.
  2. What is hit@k? Answer: the share of questions whose correct chunk is in the top k results.
  3. What is prompt injection? Answer: text in the data that tries to command the model.

Chapter recap

  • Use the eleven-step ML design framework; metric and data come before the model.
  • A data platform ingests, stores raw data, transforms into a warehouse and serves features; test freshness and quality.
  • Avoid leakage with point-in-time joins; avoid skew with one feature definition.
  • Recommenders use a funnel of retrieval, light ranking, heavy ranking and rules because of the latency budget.
  • Fraud is a base-rate problem: compute precision and alert volume, and choose the threshold by cost.
  • RAG: chunk, embed, store, retrieve, rerank, answer with citations; measure retrieval and answers separately.
  • Choose prompting, then RAG, then fine-tuning, then agents.
  • Always size the system: events per second, bytes, memory, tokens, concurrent users (Little's law).

Practice set

  1. (Easy) 200 million events per day. Events per second? Answer: 200,000,000 / 86,400 = 2,315.
  2. (Easy) 2 million chunks, 384 dimensions, float32. Size? Answer: 2,000,000 × 384 × 4 = 3.07 GB.
  3. (Easy) Top 5 results, 2 relevant of 4 total. precision@5 and recall@5? Answer: 2/5 = 0.40 and 2/4 = 0.50.
  4. (Medium) 1% fraud, recall 0.9, FPR 0.02. Precision? Answer: 0.009 / (0.009 + 0.0198) = 0.3125.
  5. (Medium) What is the output of the point-in-time join if a feature is dated after the label? Answer: it is not picked; the earlier feature, or None if there is none.
  6. (Medium) Find the bug: a model is trained with a random split on one year of daily data, then fails in production. Answer: time leakage; use a time-based split (train earlier, test later).
  7. (Medium) A funnel has stages of 12, 8, 35 and 5 ms. Budget 70 ms. Does it fit? Answer: 12 + 8 + 35 + 5 = 60 ms, yes, with 10 ms spare.
  8. (Hard) A chatbot gets 10,000 questions per day, 4,000 tokens each in total. Tokens per month? And if 60% of questions are repeats, how many tokens can a cache save? Answer: 10,000 × 4,000 × 30 = 1.2 billion; repeats save 60%, about 720 million tokens (if answers can safely be reused and nothing in them goes stale).
  9. (Hard, interview) "Design fraud detection for UPI payments." Answer: Follow the framework: objective (loss prevented with low friction), metrics (recall at fixed false-alarm volume, review cost, customer friction guardrail), delayed labels, streaming velocity features, online scoring under a strict budget with fallback rules, threshold by cost, step-up verification for middle scores, drift and retraining, bias and privacy risks.
  10. (Hard, interview) "Our RAG bot gives wrong answers. How do you debug?" Answer: Build a golden set; measure hit@k. If retrieval fails, change chunking, add hybrid search or reranking, check metadata filters. If retrieval is fine, fix the prompt (answer only from context, cite, refuse), check context length and ordering, then model choice. Log failures into the golden set.
