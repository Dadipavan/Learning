A recruiter opens your resume for about the time it takes to drink a sip of tea. A hiring manager opens your GitHub link if the resume made them curious. A referrer checks your LinkedIn before putting their name on you. These three places tell one story or three confusing ones. This chapter shows you how to build proof (a small set of strong projects), how to present the proof (README, GitHub, resume bullets with numbers, LinkedIn headline) and how to write your first public post. You already own good raw material: years of finding bottlenecks, explaining bad news and reading percentiles. By the end you will have a project plan with hours, a README that a stranger can run, five resume bullets with impact numbers, a headline, and a first post draft. Chapter 4 gave the README and post templates; Chapter 7 covered interview stories. Here we assemble them into a hireable profile.

11.1 Portfolio Strategy: Fewer, Stronger Projects

INTUITION
A restaurant with 30 dishes done badly loses to a restaurant with 6 dishes done well. A hiring manager has little time. Six solid projects show range, depth and finishing power. Thirty half-done tutorials show only that you started things.

The rule and the mix

Aim for 6 to 8 strong projects, not 30. A project is strong when it has:

  • a business or problem statement in one sentence;
  • a named data source (public or simulated; never company data);
  • an approach, and results with numbers;
  • "what I would do next";
  • an architecture diagram (Chapter 8 and 9 style);
  • clear steps to run it, so anyone can reproduce it;
  • some tests;
  • a demo where possible (a hosted app, or a 2 to 3 minute video);
  • a short blog post: problem, approach, results, mistakes (Chapter 10.5).

A good mix for a working professional moving to data:

TypeHow manyExample idea
Analytics2Sales dashboard with a written recommendation (Chapter 5)
Data engineering2Event pipeline with orchestration and data-quality tests
ML or deep learning2Churn model with a proper time split and error analysis
GenAI or agents1 to 2RAG chatbot with a golden evaluation set (Chapter 9.5)
MLOps or operations1Traffic test of an ML endpoint with a cost model

Your signature pieces

Most applicants build the same Titanic and house-price projects. You can build four things that stand out:

  1. Daily order files to warehouse to dashboard (a food-delivery or shop example), with slowdown detection across weeks.
  2. Anomaly detection on real monitoring metrics, with documented precision and recall.
  3. Traffic test of a data pipeline or ML endpoint (for example with Locust), with bottleneck analysis and a cost model.
  4. A blog series: "What my first job taught me about data engineering."

Use public or simulated data only. Never publish company logs, client names or internal numbers. If a project is inspired by your work, rebuild it from scratch on open data, and check your employment contract and policy first.

The picture

Resume bullet -> "see GitHub: repo link"  -> README (30 s) -> demo or diagram -> blog post (details)
                      ^                                              |
                      +----------- LinkedIn Featured section --------+

Each layer lets a reader stop when they are convinced or go deeper when curious.

Connection to the real job

Interviewers pick questions from your projects ("why SQLite and not Postgres?"). A project you cannot explain for 3 minutes is a liability; remove it from your resume (Chapter 7.4).

Applications

  • Data analyst: dashboards with a clear recommendation.
  • Data engineer: pipelines with tests and scheduling.
  • ML engineer: a model plus serving and monitoring.
  • AI engineer: RAG or agent with evaluation and guardrails.
COMMON MISTAKE
Copying a tutorial and listing it as a project. Change the data, add your own question, measure something, and write what went wrong.
REAL JOB TIP
Write the blog post while you build, not after. Notes from the first week make the best "mistakes I made" section.

Check yourself

  1. How many strong projects do you need? Answer: 6 to 8; start applying after about 3.
  2. Which data may you use? Answer: public or simulated data, never company data.
  3. Name one signature project. Answer: daily order files into a warehouse with slowdown detection.

11.2 The Project README and Your GitHub Profile

INTUITION
Your GitHub page is a shop window. A visitor looks for 30 seconds. If the window is clean, labelled and shows the best items, they step in. If it shows 40 forked repos with no description, they walk on. The README is the label on each item.

The README template for a portfolio project

Chapter 4.2 gave the basic README. A portfolio project adds proof. Copy this and fill it in.

# Project name: one-line promise
What problem it solves, for whom, in one or two sentences.

## Result
One headline number or screenshot.
Example: "Detects delivery-time slowdowns with 92% precision and 85% recall on 40 simulated weeks."

## Demo
Link to hosted app or a 2-3 minute video. Screenshot if neither exists.

## Architecture
Diagram (image) and 5 bullets: what each box does and why it is there.

## How to run (reproducible)
1. git clone <repo>
2. python -m venv .venv && source .venv/bin/activate
3. pip install -r requirements.txt
4. python -m pytest        # tests pass
5. python run.py           # prints the result above

## Data
Source, size, license, how to download. Never real secrets or private data.

## Method and results
Baseline, what I tried, table of numbers, what worked and what failed.

## Decisions and limits
What I chose and why (link to ADR); what does not work yet.

## Next steps
Three bullets.

The numbers in the Result example are an example for the template, not a real result. Your README must contain only numbers you measured.

GitHub hygiene checklist

  • Pin 6 repositories (the profile allows 6): your best, one per type.
  • Profile README: a repository with the same name as your username holds a short intro. Write 5 lines: who you are, what you build, your top 3 projects with links, how to reach you.
  • Each repo: a description, topics (labels), a licence (a file stating how others may use the code), a .gitignore, and no large data files.
  • Secrets: never commit passwords, keys or tokens. Use environment variables and add .env to .gitignore. If a secret is committed, revoke it at once (deleting the file does not remove it from history).
  • Commit messages: short and clear ("Add null-check test for orders"), not "final2".
  • History: steady small commits show real work; one giant commit looks pasted.
  • Tests and CI: a few tests and a simple automated test run give confidence (GitHub Actions can run tests on every push; check current free limits).
  • Tidy: delete or archive dead repos; forks you never changed add noise.

Problem 11.2.2 (Predict, run, explain) A quick script checks that a repository folder has the needed files. Before you run it, which of the three files do you think will be flagged missing?

import os, tempfile
d = tempfile.mkdtemp()
for name in ["README.md", "requirements.txt", ".gitignore"]:
    if name != ".gitignore":
        open(os.path.join(d, name), "w").close()
need = ["README.md", "requirements.txt", ".gitignore", "LICENSE"]
missing = [n for n in need if not os.path.exists(os.path.join(d, n))]
print("missing:", missing)

Run it with python3 file.py; the real output is:

missing: ['.gitignore', 'LICENSE']
  • Step 1 tempfile.mkdtemp() makes an empty temporary folder.
  • Step 2 The loop creates README.md and requirements.txt as empty files and skips .gitignore on purpose.
  • Step 3 The list comprehension keeps every needed name whose path does not exist: .gitignore and LICENSE.
  • Answer The script prints .gitignore and LICENSE as missing.
  • Check Four names needed, two created, so two missing.
  • Why it matters A ten-line script like this can run before every portfolio push; it is the same habit as a smoke test (a quick test that the basics work).

Connection to the real job

Teams read READMEs daily; a clear one saves onboarding days. Hiring managers for data and ML roles often open a pinned repo before the interview.

Applications

  • Hiring: a clean repo is proof of working style.
  • Open source: the same README and tests earn pull-request acceptance (Chapter 14).
  • Teamwork: every internal tool needs a run-it-in-5-minutes README.
COMMON MISTAKE
A README that says "This project does X" with no way to run it and no numbers. Add a result line and a command that prints it.
COMMON MISTAKE
Committing a secret or a dataset with personal data. Check git status and your .gitignore before every push.

Check yourself

  1. How many repositories can you pin? Answer: 6.
  2. What should the first screen of a README show? Answer: promise, result, demo.
  3. What do you do if you commit a password? Answer: revoke it immediately; deleting the file does not remove it from history.

11.3 Resume Bullets With Impact Numbers

INTUITION
A resume bullet is an advertisement of one line. "Responsible for delivery operations" tells the reader what your role title was. "Cut delivery time 40% by finding a slow dispatch step" tells the reader what you achieved. People hire results, not job descriptions.

The bullet formula

Action verb + what you did + how (tool or method) + result with a number + scale

Examples of numbers you can use (all must be true and explainable): percent improvement, time saved, users or requests, volume of data, money saved or protected, error rate, number of teams or releases. Percent improvement is (old − new) / old × 100, from the learner's math work.

Rules:

  • One page. Reverse chronological order. Skills and projects near the top for a career changer.
  • Start with a strong verb: built, reduced, automated, designed, found, wrote, led, shipped.
  • Avoid weak openings: "responsible for", "worked on", "helped", "involved in".
  • One idea per bullet, about 12 to 28 words.
  • Keywords from the job description, but only for skills you actually have. If you cannot talk about it for 3 minutes in an interview, delete it.
  • Truth: every number must be real and defensible. If you do not have an exact number, give a range or a careful estimate and be ready to explain how you got it. Never invent.
  • Confidential details: no client names, internal system names or secret numbers if your contract forbids; say "a large Indian bank" if allowed, or "a retail banking application".

Problem 11.3.1 Compute the percent improvements for four real-looking results and write each as a bullet fragment.

def pct(old, new): return round((old - new) / old * 100, 1)
print("delivery time 50 -> 30 min:", pct(50, 30), "% lower")
print("report preparation 6 h -> 90 min:", pct(360, 90), "% shorter")
print("orders handled 450 -> 900 per hour:", round((900 - 450) / 450 * 100), "% higher")
print("cost 40000 -> 31000 per month:", pct(40000, 31000), "% lower")
delivery time 50 -> 30 min: 40.0 % lower
report preparation 6 h -> 90 min: 75.0 % shorter
orders handled 450 -> 900 per hour: 100 % higher
cost 40000 -> 31000 per month: 22.5 % lower
  • Step 1 Delivery time: (50 − 30) / 50 = 20 / 50 = 0.40, so 40% lower.
  • Step 2 Report preparation: the same units are needed. 6 hours is 360 minutes: (360 − 90) / 360 = 0.75, so 75% shorter.
  • Step 3 Orders handled per hour go up, so the base is the old value: (900 − 450) / 450 = 1.0, which is 100% higher (it doubled).
  • Step 4 Cost: (40000 − 31000) / 40000 = 0.225, so 22.5% lower.
  • Answer 40% lower delivery time, 75% shorter report preparation, orders per hour doubled, 22.5% lower monthly cost.
  • Check Reverse the first: 50 × (1 − 0.40) = 30. Correct. (These numbers are for practice; use your real ones.)
  • Why it matters Unit mistakes (hours versus minutes) are the commonest error in impact numbers, and an interviewer will recompute them.

Problem 11.3.2 (Predict, run, explain) A small "bullet checker" scores a bullet: 2 points for a digit, 1 point for not starting weakly, 1 point for 12 to 28 words. Predict which of the four bullets scores 4 out of 4.

import re
bullets = [
 "Responsible for operations of a food-delivery app.",
 "Worked on reports and dashboards for many projects.",
 "Cut 95th-percentile delivery time from 50 to 30 minutes (40%) by finding a slow dispatch step in an app serving 5,000 orders a day.",
 "Built a Python tool that loads daily order files into a warehouse and flags late-delivery spikes; used by 3 teams on 12 weekly reports.",
]
weak_starts = ("responsible for", "worked on", "helped", "involved in", "assisted")
for b in bullets:
    words = len(b.split())
    has_num = bool(re.search(r"\d", b))
    weak = b.lower().startswith(weak_starts)
    score = (2 if has_num else 0) + (0 if weak else 1) + (1 if 12 <= words <= 28 else 0)
    print(f"score {score}/4 | words {words:2d} | number {has_num!s:5} | weak start {weak!s:5} | {b[:48]}...")
score 0/4 | words  7 | number False | weak start True  | Responsible for operations of a food-delivery ap...
score 0/4 | words  8 | number False | weak start True  | Worked on reports and dashboards for many projec...
score 4/4 | words 24 | number True  | weak start False | Cut 95th-percentile delivery time from 50 to 30 ...
score 4/4 | words 24 | number True  | weak start False | Built a Python tool that loads daily order files...
  • Step 1 re.search(r"\d", b) looks for any digit. startswith(weak_starts) accepts a tuple of prefixes.
  • Step 2 Bullets 1 and 2 start weakly, have no digit and are short, so score 0.
  • Step 3 Bullets 3 and 4 have numbers, strong verbs (Cut, Built) and 21 to 23 words, so score 4.
  • Answer Bullets 3 and 4 score 4 of 4.
  • Check The checker is only a rough filter. It cannot tell whether a number is true. You are the final judge.

Connection to the real job

The same formula appears in performance reviews and promotion documents: result, number, scale. Writing bullets now trains the habit.

Applications

  • All data roles: bullets with metrics get past the first screen.
  • Internal transfers: a one-page "impact summary" helps managers.
  • Performance reviews: the same bullets feed your self-review.
COMMON MISTAKE

INTERVIEW TIP

11.4 LinkedIn: Headline, About and Featured

INTUITION
Recruiters search LinkedIn the way you search a database: by keywords and filters. The headline is the title of your row. A headline that says only your current job title is found by people looking for that job, not the one you want.

The parts that matter

  • Headline: the line under your name, which also appears in search results and comments. It is limited in length (about 220 characters at the time of writing; check the current limit). Use the formula: what you are now moving to + key skills + proof or niche.
  • About: 3 short paragraphs: who you are, what you built (with 1 or 2 numbers), what you want next.
  • Featured: pin your best repository, blog post and demo video.
  • Experience: reuse your resume bullets (shorter lines).
  • Skills: 10 to 20 real skills; ask a colleague to endorse the main ones.
  • Recommendations: ask 2 or 3 colleagues or managers who saw your work; give them 3 facts to mention.
  • Photo, location, links: a clear face photo, your city, and your GitHub link.
  • Open-to-work signals and privacy: LinkedIn has settings to tell only recruiters you are looking, hiding it from your current employer's company page. Check the current settings; they change.
  • Confidentiality: do not post client names, internal numbers or screenshots from work.

11.5 Writing Your First Post (and Keeping a Rhythm)

INTUITION
Your first post is like the first day of a new restaurant: it will not be perfect, and its purpose is to find out how things really run. Nobody remembers it. What they notice is whether you kept going.

What to write

Chapter 4.4 gave the weekly-post template and the ethics of posting. Your first post should be a small project write-up or a "what I learned" note with one real number. Good first topics:

  • "What 2 million delivery records taught me about percentiles."
  • "I rebuilt a rate limiter in Python (token bucket) and tested it with a small script that sends many requests."
  • "My first data pipeline: three bugs I made."

Structure in six lines:

  1. Hook: one sentence with a number or a surprise.
  2. Problem: what you tried to do.
  3. What I did: 3 to 5 lines, with a small code snippet or screenshot.
  4. Result: the number.
  5. Mistake or lesson: one honest line.
  6. Question: invite a reply.

CheckThe draft contains one number (2 million), one surprise (doubled on Fridays), one mistake and one question. It contains no company or client name.
Why it mattersPosts with a concrete number and an honest mistake are read and remembered; vague advice is scrolled past.

Connecting well, not loudly

Send a connection request with a short note ("I read your post on rate limiting; I am a working professional moving into data and would like to follow your work"). Comment with something useful, not "great post". Never ask strangers only for a job; ask a specific question, offer thanks, and share what you made. Chapter 14 covers mentors and communities.

Connection to the real job

Writing is a daily part of data work (Chapter 4). A public post is also a small proof that you can explain things, which every team values.

Applications

  • Referrals: people who know your work refer you more readily.
  • Interviews: a post can start the interviewer's first question.
  • Learning: teaching forces understanding (Chapter 2).
COMMON MISTAKE
Waiting until the post is perfect. Publish at "good and honest"; improve the next one.
REAL JOB TIP
Keep a running file of "things I fixed this week". Each line is a future post or resume bullet, and a ready story for the interview.

Check yourself

  1. What must a first post contain? Answer: a hook with a number, the problem, what you did, the result, a lesson, and a question.
  2. Can you post work screenshots? Answer: no, not confidential ones; use public or simulated data.
  3. How many connections per month does the plan suggest? Answer: five genuine ones.

ATS: what the screening software actually does

An ATS (applicant tracking system, Chapter 12) stores resumes and lets a recruiter search by words. Your job is to be findable and readable, not to trick it.

  • Use a single-column file with standard headings: Experience, Projects, Skills, Education. Avoid text inside images, tables for layout and icons in place of words.
  • Use the same words as the JD for skills you truly have ("Airflow", not "workflow orchestrator").
  • Save as PDF unless the posting asks for Word. Name it FirstName_LastName_DataEngineer.pdf.
  • Keep to one page under 8 years of experience, two pages at most.

Problem 11.6.3 A JD lists 10 keywords: SQL, Python, Airflow, dbt, Snowflake, Git, dashboards, data modelling, testing, communication. Your resume v1 contains 4 of them in the plain text. You do use Airflow, Git, dashboards and data modelling at work, but never wrote them down. How many can you honestly add, and what is the new coverage?

Count v14 of 10 = 40%
Honest additionsOnly skills you truly use: 4 more (Airflow, Git, dashboards, data modelling). dbt and Snowflake stay out if you have not used them.
New count4 + 4 = 8 of 10 = 80%
Answer80% coverage, with 2 missing keywords (dbt, Snowflake) that become your next study items (see 1.4).
COMMON MISTAKE
Keyword stuffing: pasting the whole JD in white text or listing tools you have only watched a video about. Wrong: "Skills: Spark, Kafka, dbt, Snowflake, Kubernetes" with no project using them. Right: list only what you can discuss for 5 minutes. The interview will test every word on the page.

Going deeper

  • One resume per role family, not per application. Keep 2 or 3 master versions (Analyst, Data Engineer, ML) and tweak only the top summary and skills line for each JD, a 10-minute change.
  • Test it on a stranger. Give the resume to someone for 30 seconds, then take it away and ask what role you want and one thing you did. If they cannot say, the top third is unclear.
  • Consistency check. Dates, titles and tools must match across resume, LinkedIn and what you say in interviews. A mismatch is a more common reason to lose trust than a gap.

Check yourself

  1. Why write before and after numbers? Answer: they show the change you caused, and a reader can judge its size.
  2. Bullet says cost fell from Rs 80,000 to Rs 60,000 a month. What percentage? Answer: 20,000 / 80,000 = 25%.
  3. Should you add a tool to your resume because the JD asks for it? Answer: only if you have really used it.

Chapter recap

  • Build 6 to 8 strong projects, not 30; start applying after about 3 are solid.
  • Use signature projects: order-files-to-warehouse, anomaly detection, traffic tests of pipelines and endpoints.
  • Every project needs a problem, data source, numbers, a diagram, run steps, tests and a short blog post.
  • A README shows promise, result and demo on the first screen; GitHub needs pinned repos, a profile README, licences and no secrets.
  • Resume bullets follow: action, what, how, result with number, scale; use percent change (old − new) / old × 100 and keep units consistent.
  • Never invent a number; never list a skill you cannot explain for 3 minutes.
  • The LinkedIn headline names the target role, key skills and your niche; About and Featured carry proof.
  • Publish a first post with one real number and one honest mistake, then keep a light rhythm.
  • Rewrite weak bullets as verb, what, how, result with a number, and check them against ATS keywords (section 11.6).

Practice set

  1. (Easy) Latency fell from 500 ms to 350 ms. Percent reduction? Answer: 150 / 500 = 30%.
  2. (Easy) Throughput rose from 200 to 260 tps. Percent increase? Answer: 60 / 200 = 30%.
  3. (Easy) How many repositories can you pin on GitHub? Answer: 6.
  4. (Medium) A job takes 2 hours and falls to 45 minutes. Percent shorter? Answer: 2 hours = 120 minutes; (120 − 45) / 120 = 62.5%.
  5. (Medium) What does the bullet checker (11.3.2) score for "Built a tool for testing"? Answer: no digit (0), strong start (1), only 5 words (0), so 1 out of 4.
  6. (Medium) Find the bug: a README says "pip install requirements.txt". Answer: it should be pip install -r requirements.txt; without -r, pip looks for a package named requirements.txt.
  7. (Medium) Which is a better headline: "Data Enthusiast" or "IT professional moving into data engineering | SQL, Python | reliable pipelines"? Answer: the second; it has a target role, searchable skills and a niche.
  8. (Hard) Rewrite "Helped the team improve release quality": you wrote 120 automated checks for 4 releases and caught 7 defects before production. Answer: "Wrote 120 automated checks across 4 releases and caught 7 defects before production." (Starts with a verb, has 3 numbers, 13 words.)
  9. (Hard, interview) "Walk me through your portfolio project." Answer: Use a 2-minute structure: problem in one sentence; data and why; architecture in three boxes; one result with a number; one mistake and its fix; what you would do next; why you chose the main tool over an alternative.
  10. (Hard, interview) "Your resume says 40% delivery-time improvement. How did you measure it?" Answer: Name the setup (same period, same order volume, several weeks), the metric (95th percentile), the before and after values (50 to 30 minutes), and the cause (a slow dispatch step). Keep the report to show.
  11. (Medium) Rewrite: "Responsible for reports." Answer: Example: "Built a weekly sales report in SQL and Excel for 3 managers, cutting preparation from 5 hours to 1 hour." (use your own real numbers)
  12. (Easy) A bullet cuts a task from 5 hours to 1 hour. Percent saved? Answer: 4 / 5 = 80%.
