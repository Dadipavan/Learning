In a system design interview someone says "design a URL shortener" and watches how you think for 45 minutes. At work, the same skill decides whether your service survives launch day. You already know the hard part: load, bottlenecks, percentiles and capacity. What you may lack is a vocabulary (cache, shard, queue) and a framework that turns a vague request into a clear design. By the end of this chapter you will estimate load from a few assumptions, choose between a cache, a shard and a queue with a reason, and walk through three classic designs: a URL shortener, a rate limiter and a news feed. Chapter 6 taught estimation as a thinking tool; here we apply it to machines.

8.1 The Design Framework and the Words You Need

BASIC EXPLANATION
System design is the process of planning the parts of a software system, such as services, storage and queues, and how they work together to meet requirements. It is used in interviews and at work.
INTUITION
Designing a system is like planning a restaurant before it opens. You do not start by buying stoves. You ask how many guests come, what they order, how fast they expect food, and what happens if the chef is ill. Weak answers draw boxes in minute one. Strong answers spend the first five minutes on questions and numbers.

The eight steps

Use the same order every time.

  1. Requirements. Functional (what the system does) and non-functional (how well: latency, availability, scale, cost, consistency).
  2. Estimates. Requests per second, storage, bandwidth, memory. Say your assumptions aloud.
  3. API. The few calls a client makes.
  4. Data model. What is stored, the lookup key, the read and write pattern.
  5. High-level design. Boxes and arrows for one request, end to end.
  6. Deep dives. The two or three hardest parts.
  7. Bottlenecks. What breaks first at 10 times the load? Capacity thinking lives here.
  8. Trade-offs. What you gave up and why.

SQL or NoSQL? SQL gives rules, joins and transactions (all-or-nothing changes). NoSQL stores (key-value, document, wide-column) usually trade some of that for easier scaling. Choose by access pattern: "find one row by key, billions of rows" leans NoSQL; "many questions with joins" leans SQL.

CAP in one paragraph. When the network between machines breaks (a partition), a system must choose: stay consistent (everyone sees the same data, some requests fail) or stay available (every request is answered, some answers are stale). PACELC adds that even without a partition you trade latency against consistency. Partitions do happen, so the real choice is C or A during a failure. Observability (logs, metrics, traces) is how you see all of this at run time; it is your home ground.

Data engineers design ingestion services, ML engineers prediction APIs, AI engineers chat backends. All start with these eight steps.

8.2 Estimation With Little's Law

BASIC EXPLANATION
Little's Law states that the average number of items in a system equals the arrival rate times the average time each item spends in the system. It is used to estimate load and capacity.
INTUITION
A bank manager sets the number of counters by asking how many customers arrive per minute and how long each takes. If 60 arrive per minute and each needs 30 seconds, about 30 customers are being served at any moment, so you need about 30 counters. That is Little's law, which planners use to size counters, tills and servers.

Formal definition

Little's law: L = λ × W. L is the average number of requests inside the system, λ (lambda) is the arrival rate per second, W is the average seconds each request spends inside. It holds for any stable system. For a system with think time (the pause between a user's actions): users = throughput × (response time + think time).

Peak traffic is not average. A common assumption is peak = 2 to 3 times the average; state it as an assumption. A month has about 2.6 million seconds, a day 86,400.

Problem 8.2.1 100 requests per second, each in the system 0.2 s. How many in flight?

FormulaL = λ × W
Compute100 × 0.2 = 20
AnswerAbout 20 requests in flight, so you need at least 20 worker slots.
CheckOne slot serves 1 / 0.2 = 5 per second; 20 slots serve 100 per second.

8.3 Caching

BASIC EXPLANATION
Caching stores copies of frequently used data in fast storage. It is used to reduce response time and the load on the main data store.
INTUITION
You keep a water bottle on your desk instead of walking to the kitchen. The kitchen is the database: complete but slow. The bottle is the cache: small, near, quick, and sometimes out of date.

How it works

A cache keeps popular results in fast memory. A read asks the cache first: found is a hit; not found is a miss, so read the database, store the result, return it (the cache-aside pattern). The share of hits is the hit ratio h.

average latency = h × cache_time + (1 − h) × database_time

Levels: the browser, the CDN, and an application cache such as Redis (an in-memory key-value store). Invalidation (removing stale data) is the hard part: use a TTL (time to live, the entry expires), or delete the entry when the row changes. LRU (least recently used) evicts the item untouched longest when the cache is full.

Problem 8.3.1 Cache 1 ms, database 10 ms, hit ratio 80%. Average latency?

Compute0.8 × 1 + 0.2 × 10 = 0.8 + 2.0 = 2.8
Answer2.8 ms, against 10 ms without a cache.
Checkh = 0 gives 10 and h = 1 gives 1; 2.8 is between.

  • Step 2 At h = 0.9 the database sees 386 per second (a 10 times cut); at 0.99, 38.6.
  • Step 3 Cache: 20,000,000 URLs × 500 bytes = 10 GB, one Redis machine.

A failure mode: stampede. If a viral key expires while 50,000 requests per second ask for it, all miss together and crush the database. Fixes: let one request refill while others wait, add random jitter to TTLs, refresh popular keys early. A traffic spike right after a cache flush (a test you can run with a tool such as Locust or k6) reproduces it.

Where it is used

Feature stores cache features for model serving. RAG systems cache embeddings and repeat answers (saves tokens). BI tools cache query results; pre-aggregated tables are a cache of an expensive query.

COMMON MISTAKE
Caching without an invalidation plan. For each cached item write down how stale is acceptable. A profile photo can be minutes old; an account balance cannot.

Check yourself

  1. h = 95%, cache 2 ms, database 20 ms. Average? Answer: 1.9 + 1.0 = 2.9 ms.
  2. TTL means? Answer: how long an entry lives before it expires.
  3. Stampede means? Answer: many requests miss at once and all hit the database.

8.4 Sharding, Replication and Consistent Hashing

BASIC EXPLANATION
Sharding splits data across several machines, replication keeps copies of data on several machines, and consistent hashing is a way to assign keys to machines with little data movement when machines change. They are used to scale and protect a data store.
INTUITION
A library with one librarian has long queues. Copy popular books to more branches (replication: more readers served). Or split the collection, A to M in one building and N to Z in another (sharding: more data and writes fit). One helps reading, the other helps size.

Definitions

  • Replication: the same data on several machines. A primary takes writes, replicas copy it and serve reads. If the primary dies, a replica takes over (failover). Replicas lag a little, so a replica read can be slightly old.
  • Sharding: each machine owns a slice of the keys. The shard key picks the slice. A skewed key makes a hot shard.
  • Choosing the shard: hash(key) mod N is easy, but when N changes nearly all keys move. Consistent hashing puts machines (many virtual points each) on a circle; a key belongs to the next machine clockwise, so adding a machine takes keys only from its neighbours.

Problem 8.4.1 Shard = id mod 4. Ids 10 to 14. Where do they go, and what if we move to 5 shards?

Step 1Mod 4: 10→2, 11→3, 12→0, 13→1, 14→2.

Problem 8.4.2 Compare mod and consistent hashing on 100,000 keys, 4 to 5 machines.

import hashlib, bisect
def h(s): return int(hashlib.md5(s.encode()).hexdigest(), 16)
keys = [f"key{i}" for i in range(100000)]
moved = sum(1 for k in keys if h(k) % 4 != h(k) % 5)
print("mod 4 -> mod 5 moved:", moved / len(keys))
def ring(nodes, vn=100):
    pts = sorted((h(f"{n}#{v}"), n) for n in nodes for v in range(vn))
    return [p for p, _ in pts], [n for _, n in pts]
def owner(r, k):
    ps, ns = r
    i = bisect.bisect(ps, h(k)) % len(ps)
    return ns[i]
r4 = ring(["A","B","C","D"]); r5 = ring(["A","B","C","D","E"])
moved = sum(1 for k in keys if owner(r4, k) != owner(r5, k))
print("ring 4 -> 5 moved   :", moved / len(keys))
from collections import Counter
print(sorted(Counter(owner(r5, k) for k in keys).items()))

  • Step 2 Mod moved 80.0% of keys; the ring moved 19.3%. The ideal is 1/5 = 20%.

Where it is used

Kafka topics split into partitions by key. Spark and warehouses shuffle by key; one customer producing 40% of events gives the "slow last task" you know from performance work. Vector indexes and embedding tables are sharded too.

COMMON MISTAKE
Sharding by a skewed key (country, or date, where today's shard takes all writes). Check the key's distribution first.

Check yourself

  1. Which helps write scale, replicas or shards? Answer: shards.
  2. Why is mod N bad when N changes? Answer: almost all keys move.
  3. What is a hot shard? Answer: one shard getting far more load than the rest.

8.5 Queues, Retries and Reliability

BASIC EXPLANATION
A queue holds tasks until a worker can process them, and a retry repeats a failed task. Together they are used to make systems handle bursts and temporary failures.
INTUITION
A restaurant counter takes orders and sends tickets to the kitchen on a rail. In the rush the rail fills, but the counter does not collapse. The kitchen works at its own speed. A queue separates how fast work arrives from how fast it is done.

How it works

A queue sits between a producer and consumers. It smooths bursts, lets slow work happen later, and lets you add consumers. A stream (Kafka) is a queue that keeps a log so many readers can replay it. At-least-once delivery never loses a message but may repeat it, so consumers must be idempotent (store a message ID, skip repeats).

The utilization curve. In a simple random queue (the M/M/1 model), time in the system is service_time / (1 − utilization). Utilization is the share of time a worker is busy. Near 100% small increases cause huge waits: the hockey-stick you see in any latency-versus-load graph. It is a simplified model; the shape is right, real numbers differ.

Retries help brief faults but can crush a struggling service. Use exponential backoff (0.1 s, 0.2, 0.4, ...), a cap, and jitter (randomness, so clients do not retry together). A circuit breaker stops calling a failing service and fails fast; graceful degradation shows a simpler result instead of an error.

8.6 Worked Design 1: URL Shortener

BASIC EXPLANATION
A URL shortener is a service that maps a short code to a long web address. It is a standard design exercise that covers storage, code generation and redirects.
INTUITION
A shortener is a giant phone book: short code in, long address out. Few writes, many reads. The clever parts are making unique short codes and answering reads very fast.

Read it left to right. A request passes a load balancer to stateless app servers. A read asks Redis first and falls back to the database on a miss. A write asks the ID generator (counter ranges) for a number, turns it into a code and stores it.

The eight steps

  1. Requirements. Create a short URL; open it and be redirected; optional alias and expiry. Redirect p99 under about 100 ms (assumed), high availability, links never change.
  2. Estimates. From 8.2: 39 writes and 3,858 reads per second (11,574 peak), 3 TB, 10 GB hot cache.
  3. API. POST /urls with {long_url} returns {short_code}. GET /{short_code} redirects: 301 (permanent, browsers may cache) or 302 (temporary, you count every click). Choose by whether analytics matter.
  4. Data model. One table: short_code (key), long_url, created_at, expires_at, user_id. Lookup by key only.
  5. High-level design. The picture above.
  6. Deep dive: codes. (a) Hash the long URL and take 7 characters: needs collision checks. (b) A counter converted to base62 (digits 0-9a-zA-Z): no collisions, but guessable. (c) Random 7 characters with a retry on collision.
  7. Bottlenecks. At 10 times load the cache still absorbs 90%; the database sees about 11,500 reads per second, so shard and add replicas. The counter is a single point of failure: give each app server a range of numbers (say 1,000,000 at a time).
  8. Trade-offs. Counter codes are short and collision-free but predictable; random codes hide order but need a collision check. 302 gives analytics but more traffic.

Click analytics is a data pipeline: redirect logs flow through a queue into a warehouse. It makes a good portfolio project (Chapter 11).

Check yourself

  1. Reads or writes bigger here? Answer: reads, by 100 times.
  2. Why counter ranges? Answer: no call to the counter on every write, and no single point of failure.
  3. 301 or 302 for click counting? Answer: 302.

8.7 Worked Design 2: Rate Limiter

BASIC EXPLANATION
A rate limiter is a component that limits how many requests a user can make in a given time. It is used to protect a service from overload and misuse.
INTUITION
A nightclub lets in 5 people a minute, and a group of 10 at once if it has been quiet. The bouncer holds a bucket of tokens; each guest takes one; the bucket refills slowly; when empty, guests wait.

The problem

A rate limiter rejects requests from a client above an allowed speed. It protects servers, controls cost and stops abuse. The reply is HTTP status 429 (too many requests), often with a Retry-After header.

A token bucket keeps two numbers per client: tokens and last_time. On each request, add (now − last) × rate tokens (up to capacity), then spend one if at least one is there.

Problem 8.7.1 Rate 5 per second, capacity 10, bucket starts full. 15 requests arrive at t = 0. Then 16 requests arrive 0.125 s apart from t = 1. Predict which pass, then run.

class TokenBucket:
    def __init__(self, rate, capacity):
        self.rate, self.capacity = rate, capacity
        self.tokens, self.last = capacity, 0.0
    def allow(self, now):
        self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)
        self.last = now
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False

b = TokenBucket(rate=5, capacity=10)
out = [b.allow(0.0) for _ in range(15)]
print("burst of 15 at t=0:", "".join("Y" if x else "N" for x in out))
out = [b.allow(1.0 + i * 0.125) for i in range(16)]
print("8 req/s for 2 s   :", "".join("Y" if x else "N" for x in out))
burst of 15 at t=0: YYYYYYYYYYNNNNN
8 req/s for 2 s   : YYYYYYYYYYYNYYNY
  • Step 1 At t = 0 there are 10 tokens and no time passes: 10 pass, 5 are refused.
  • Step 2 Tokens are 0. At t = 1 the refill is 5. Each next request is 0.125 s later: +0.625 tokens, then −1.
  • Step 3 Levels after each allowed request: 4, 3.625, 3.25, 2.875, 2.5, 2.125, 1.75, 1.375, 1.0, 0.625, 0.25: eleven in a row.
  • Step 4 Request 12 sees 0.875: refused. Request 13 sees 1.5: allowed (0.5 left). Request 14 sees 1.125: allowed (0.125). Request 15 sees 0.75: refused. Request 16 sees 1.375: allowed.
  • Answer 14 of 16 pass: the saved burst credit drains, then traffic settles toward 5 per second.
  • Check Tokens supplied after t = 1: 5 + 1.875 × 5 = 14.375, so at most 14 can pass. We got exactly 14.
  • Why it matters A limiter must give a predictable answer you can verify by hand.

Problem 8.7.2 Memory for 10 million users at 64 bytes each (tokens 8, time 8, key and overhead about 48, an assumption)?

Compute10,000,000 × 64 = 640,000,000 bytes
AnswerAbout 640 MB: one Redis instance. At 50,000 API requests per second with two Redis operations each, Redis sees 100,000 operations per second, which you must confirm with a traffic test.
Check6.4 × 10⁸ bytes = 640 MB.

Deep dive: many servers

The counters must be shared, so use Redis. "Read then write" is a race (two servers read the same value), so use an atomic operation (INCR or a script). If Redis is down, fail open (allow all, risk overload) or fail closed (block all, risk an outage). A payment API leans closed; a search page leans open.

Where it is used

LLM providers limit tokens per minute, so a RAG client needs its own limiter plus backoff (8.5). Data extraction and scrapers must respect limits and site terms.

COMMON MISTAKE
A fixed window: a client sends the full limit at 11:59:59 and again at 12:00:00, doubling the rate. Use a bucket or sliding window when it matters.

Check yourself

  1. Which status code? Answer: 429.
  2. Rate 2 per second, capacity 4, full: instant requests passed? Answer: 4.
  3. Fail open means? Answer: allow requests when the limiter store is down.

8.8 Worked Design 3: News Feed

BASIC EXPLANATION
A news feed is a list of recent posts from the people or topics a user follows. Designing one covers how posts are stored and delivered to many users.
INTUITION
Each person has a notice board. When a friend posts, a helper copies the post onto each follower's board (push): reading is instant, posting costs more. Or you walk to each friend's board when you open the app (pull): posting is cheap, reading is slow.

A post goes to a post service and a queue. Workers fan it out into each follower's feed cache (a list of post IDs) for normal users. Accounts with millions of followers skip fan-out; their posts are merged in when a follower opens the feed.

Assume 50 million daily active users (DAU), 10 feed opens per user per day, 20% of users post once a day, 200 followers on average, 16 bytes per feed entry.

Problem 8.8.1 What is the read-to-post ratio, and does it favour push or pull?

Step 15,787 / 115.7 = 50 reads per post.
Step 2Push: each post becomes 200 writes (23,148 per second); each read is one cache lookup.
Step 3Pull: each read gathers from about 200 sources: 5,787 × 200 = 1,157,400 lookups per second.
AnswerReads dominate 50 to 1, so push is cheaper: 23 thousand writes per second versus 1.16 million lookups per second for pull.
Check1,157,400 / 23,148 = 50, the read-to-post ratio.

Problem 8.8.2 A celebrity with 10 million followers posts. What goes wrong with push, and what is the fix?

Step 1Push means 10,000,000 feed writes: 500 seconds of the whole fan-out capacity at 20,000 per second, so followers wait.
Step 2Hybrid: push for accounts under a threshold (say 100,000 followers; set it by measurement). Larger accounts store the post once and are merged in at read time.
Step 3Read path: take the precomputed list, add recent posts of the few celebrities this user follows, sort, return the top 20.
AnswerPush for normal users, pull for celebrities. It caps write cost and adds only a few lookups per read.
CheckStorage: 2 billion entries per day at 16 bytes is 32 GB per day, so keep only the latest 500 entries per user.

Other deep dives: ranking by a model (Chapter 9), cursor pagination ("posts older than ID X", since new posts shift page numbers), and deletes (mark deleted and filter at read time).

Where it is used

Fan-out is the pattern behind notification services and event distribution. E-commerce uses it for personalised home pages; ML systems precompute recommendations per user.

COMMON MISTAKE
Presenting push or pull as the answer. Show the numbers and the hybrid, with a threshold and a reason.

Check yourself

  1. Which is cheaper for readers? Answer: push.
  2. Why skip fan-out for celebrities? Answer: one post would cause millions of writes.
  3. What is cursor pagination? Answer: asking for posts after a given ID instead of a page number.

Chapter recap

  • Use the eight steps in order; tools come last.
  • Little's law L = λ × W turns rates and latency into concurrency and servers.
  • Estimate first: numbers tell you read-heavy or write-heavy, large or small.
  • A cache cuts database load by the miss ratio; plan invalidation; beware stampedes.
  • Replicas help reads and failover; shards help size and writes; consistent hashing moves about 1/N of keys.
  • Queues smooth bursts; keep utilization near 60 to 70%, since waits grow like 1 / (1 − u).
  • Retries need backoff, a cap, jitter and idempotency.
  • Shortener: read-heavy, cache plus ID ranges. Limiter: token bucket in Redis, atomic. Feed: hybrid push and pull.
