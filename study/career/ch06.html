CHAPTER 6

Problem Solving and Debugging Method

Strong engineers are not people who know every answer. They are people who have a method for finding answers when they do not know.

Most of your time in a data job is spent on problems nobody has solved before in your company: "why did the dashboard number drop?", "why is this pipeline slow?", "how big should this system be?". Beginners guess or panic. Professionals follow a short method. You already own one of the best methods, because a working professional hunts root causes every day. This chapter writes that method down: a framework for coding problems, issue trees for business problems, a debugging loop, root-cause analysis, and estimation (back-of-envelope) problems. By the end you will have a repeatable approach for coding interviews, for real bugs, and for "how many..." questions.

6.1 The Coding Problem Framework

BASIC EXPLANATION
A coding problem framework is a repeatable set of steps for solving a problem: understand it, work through examples, plan, code and test. It is used to solve problems in a calm, ordered way.
INTUITION
A good doctor does not operate before diagnosis. She asks questions, repeats back what she heard, tests simple ideas first, and only then treats. In a coding problem, the code is the treatment. Everything before it is diagnosis.

The eight steps

  1. Clarify: ask about inputs, outputs, size, edge cases ("Can the list be empty? Are there duplicates? How large?").
  2. Restate the problem in your own words.
  3. Examples: write 2 small examples and 1 edge case with the expected answers.
  4. Brute force: say the simplest solution aloud, even if slow, and its cost.
  5. Optimize: find what is repeated and remove it (a hash map, sorting, two pointers, a better data structure).
  6. Code it, with clear names.
  7. Test on your examples, by hand.
  8. Analyze complexity: time and memory in Big-O terms.

Big-O describes how the work grows as the input size n grows. O(n) means work grows in direct proportion. O(n²) means doubling n makes the work 4 times as much.

Running example: Two Sum

Problem: given a list of numbers and a target, return the positions of two numbers that add up to the target.

Problem 6.1.1 Walk the framework on the list [2, 7, 11, 15] with target 9.

Step 1Clarify: exactly one answer exists; the same element cannot be used twice; return indices.
Step 2Restate: find i and j, i not equal to j, with nums[i] + nums[j] = 9.
Step 3Example: [2, 7, 11, 15], 9 gives (0, 1) because 2 + 7 = 9. Edge: [3, 3], 6 gives (0, 1).
Step 4Brute force: try every pair. For n numbers there are n(n-1)/2 pairs. For n = 4000 that is 4000 x 3999 / 2 = 7,998,000 checks. This is O(n²).
Step 5Optimize: for each number x, we need target - x. Store numbers already seen in a dictionary (a hash map, which finds a key in about one step). Then each number needs one lookup: O(n).
AnswerThe code below (both versions run and agree).
def two_sum_brute(nums, target):
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):
            if nums[i] + nums[j] == target:
                return (i, j)
    return None

def two_sum_fast(nums, target):
    seen = {}                       # value -> index
    for i, x in enumerate(nums):
        if target - x in seen:
            return (seen[target - x], i)
        seen[x] = i
    return None

print(two_sum_brute([2, 7, 11, 15], 9), two_sum_fast([2, 7, 11, 15], 9))

Before you run it, what do you think prints? Both functions should return the same pair. Real output:

(0, 1) (0, 1)
  • Check In the fast version at i = 0, x = 2: 9 - 2 = 7 is not in seen (empty), so store {2: 0}. At i = 1, x = 7: 9 - 7 = 2 is in seen at index 0, so return (0, 1). Same as brute force. I also ran both on 4,000 random numbers and they returned the same pair (2088, 2332).
  • Why it matters In plain words: the fast version does about 4,000 steps; the brute version up to 7,998,000. In an interview, saying the brute force first and then the improvement is exactly what is scored.

Problem 6.1.2 What if the input is a sorted list, and memory must be tiny?

Step 1Clarify: sorted ascending; extra memory should be O(1).
Step 2Idea: two pointers, one at each end. If the sum is too small, move the left pointer right; if too big, move the right pointer left.
Step 3Example [2, 7, 11, 15], target 9: left = 2, right = 15, sum 17 > 9, so move right. Right = 11, sum 13 > 9, move right. Right = 7, sum 9. Found.
AnswerTwo pointers solve it in O(n) time and O(1) memory when the list is sorted.
CheckIt took 3 comparisons for 4 numbers, at most n - 1.
Why it mattersA trade-off: hash map uses more memory; two pointers needs sorted input. Naming trade-offs earns marks.

Picture

Clarify -> Restate -> Examples -> Brute force -> Optimize -> Code -> Test -> Complexity
   ^ ask       ^ say it     ^ write 3     ^ say cost     ^ find the repeated work

Connection to the real job

SQL and pandas problems follow the same method: clarify the grain (one row means what?), test on a tiny table, then scale. Chapter 7 uses this in interviews.

Applications

  • Data Analyst: SQL challenges (clarify the question, test on 5 rows).
  • Data Engineer: finding why a join explodes (brute force thinking about row counts).
  • ML Engineer: optimizing feature computation from O(n²) to O(n).
COMMON MISTAKE
Starting to code in the first 30 seconds. You then solve the wrong problem, and the interviewer sees no thinking. Spend the first 3 to 5 minutes on steps 1 to 4.

Check yourself

  1. Why state the brute force first? Answer: it proves you understand the problem and gives a base to improve.
  2. What does O(n²) mean? Answer: doubling the input makes work 4 times larger.
  3. Why use a hash map in Two Sum? Answer: it finds a needed value in about one step.

6.2 Structured Thinking: Issue Trees, MECE and Hypotheses

BASIC EXPLANATION
An issue tree breaks a problem into smaller parts. MECE means the parts do not overlap and cover everything, and a hypothesis is an answer you can test. They are used to structure analysis.
INTUITION
Imagine your phone bill doubled. You do not stare at the total. You split it: calls, data, roaming, extra services. Then you split the biggest piece again. Splitting a big problem into non-overlapping parts is how you find where to look.

Words you need

TermMeaning
Issue treeA diagram that splits a problem into smaller parts, branch by branch
MECE"Mutually Exclusive, Collectively Exhaustive": parts do not overlap and together cover everything
HypothesisA guess you can test ("The drop is caused by a data load failure")
First principlesBreak a problem to basic facts and rebuild, instead of copying what others do

Example issue tree: "Revenue fell 10%"

Revenue = number of orders x average order value (AOV). This is MECE: a change must come from orders, from AOV, or both.

Revenue fell 10%
|-- Orders fell?
|    |-- Fewer visitors (traffic)?
|    |    |-- by channel: search, ads, email, direct
|    |-- Lower conversion (visitor -> order)?
|         |-- by device, by product category, by new vs returning
|-- AOV fell?
|    |-- fewer items per order?
|    |-- lower prices or more discounts?
|-- Data problem? (always check first)
     |-- missing days, duplicates, definition change

Hypothesis-driven analysis

Do not open ten dashboards hoping to see something. Write a hypothesis, decide which one cheap query would disprove it, run it, then move on.

Problem 6.2.1 Revenue fell from 295 to 284 lakh. Orders went from 59,000 to 52,000 and AOV is the rest. Which branch of the tree explains the drop?

Formularevenue = orders x AOV, so AOV = revenue / orders
Plug inJan AOV = 295 lakh / 59,000 = 29,500,000 / 59,000 rupees; March AOV = 28,400,000 / 52,000 rupees
ComputeJan = 500 rupees. March = 546.15 rupees (28,400,000 / 52,000 = 546.15).
AnswerOrders fell 11.9% ((52,000 - 59,000) / 59,000), AOV rose 9.2% (546.15 / 500 = 1.0923). So the drop comes from fewer orders, not from smaller baskets. Go down the Orders branch (traffic or conversion).
Check52,000 x 546.15 = 28,399,800, close to 28,400,000 (rounding). Also 0.881 x 1.0923 = 0.962, a 3.8% fall, near the actual -3.7%.
Why it mattersIn plain words: customers are buying fewer times, but spending more when they buy. A discount on price would be the wrong fix.

Problem 6.2.2 Which of these splits is MECE for "why did the pipeline fail": (a) network, database, bug; (b) bug in my code, bug in someone else's code, human error?

Step 1Test exclusive: in (a) "network" and "database" can overlap (a database network timeout). In (b) a human error can be the cause of a bug in the code: overlap.
Step 2Test exhaustive: in (a) missing "infrastructure, data, configuration"; in (b) missing "input data problem".
AnswerNeither is perfectly MECE. A better split: by stage (ingest, transform, load), because every failure happens in exactly one stage.
CheckTake any failure and ask "which stage?": there is exactly one answer.
Why it mattersA good split means you never forget a branch and never check the same thing twice.

Picture

The tree above reads left to right in time: you check the top branches first, then go down only the branch that holds the cause. At each node ask: is the cause here? One cheap check closes or opens the branch.

Connection to the real job

This is how analysts handle "why did the KPI move?" questions. It is also how a restaurant manager splits a customer's total wait into ordering, cooking, plating and serving time.

Applications

  • Analytics: KPI drop analysis, funnel diagnosis.
  • Data Engineering: pipeline failure triage by stage.
  • Data Science: error analysis by segment.
  • Consulting-style case interviews (Chapter 7).
COMMON MISTAKE
Checking random things because they "feel" likely. Write the tree, so you can see what you have not yet checked.

Check yourself

  1. What does MECE stand for? Answer: mutually exclusive, collectively exhaustive.
  2. Revenue splits into what two factors? Answer: orders and average order value.
  3. What do you always check first in a KPI drop? Answer: a data problem.

6.3 Debugging and Root-Cause Analysis

BASIC EXPLANATION
Debugging is finding and fixing the cause of wrong behaviour in code or data. Root-cause analysis means tracing a problem back to its first cause instead of fixing symptoms.
INTUITION
Your house lights go out. You do not replace all the bulbs. You check the fuse box first, then the room. You halve the problem each time. Debugging is a search, and good searches cut the space in half.

The debugging loop

Reproduce -> Isolate -> Hypothesize -> Test -> Fix -> Prevent.

  • Reproduce: make it fail on demand. If you cannot reproduce it, you cannot know you fixed it.
  • Isolate: shrink the failing case. Fewer rows, fewer lines, fewer services.
  • Hypothesize: write one specific guess.
  • Test: change one thing; observe.
  • Fix the cause, not the symptom.
  • Prevent: add a test, an alert, or a check, and write a short note.

Bisecting

If something worked in build 1 and fails in build 1000, test build 500. If it fails, the bug is in 1 to 500. Repeat. The number of tests needed is log₂(n) rounded up. For 1,000 builds that is 10 tests.

lo, hi, steps = 1, 1000, 0
first_bad = 637
while lo < hi:
    mid = (lo + hi) // 2
    steps += 1
    if mid >= first_bad:     # build 'mid' is bad
        hi = mid
    else:
        lo = mid + 1
print("first bad build", lo, "after", steps, "tests")

What do you think prints? Real output:

first bad build 637 after 10 tests

5 Whys and root cause

The 5 Whys technique: ask "why?" until you reach a cause you can fix and prevent. Stop when the answer is a process or a design, not a person.

Problem 6.3.1 Apply 5 Whys. A dashboard showed yesterday's revenue as 0.

Step 1Why was revenue 0? The orders table had no rows for yesterday.
Step 2Why no rows? The nightly load job failed at 2 am.
Step 3Why did it fail? The source file arrived with a new column.
Step 4Why did a new column break the job? The code used fixed column positions.
Step 5Why fixed positions with no alert? We had no schema check and no alert on zero-row loads.
AnswerRoot cause: no schema validation and no zero-row alert. Fix: read columns by name, add a schema check, alert if row count is below 50% of the 7-day average. A person was not the cause; the process was.
CheckIf the check had existed, would the failure have been caught at 2 am? Yes: the new column would have triggered the schema alert.
Why it mattersFixing only "re-run the job" leaves the same bug for next week.

Problem 6.3.2 A query that took 4 seconds now takes 40. You have 10 recent changes. How many tests do you need with bisecting versus testing one by one?

Step 1One by one: up to 10 tests.
Step 2Bisecting: log₂(10) = 3.32, so 4 tests.
AnswerAt most 4 tests against up to 10.
Check2⁴ = 16 which is at least 10, but 2³ = 8 is less than 10. So 4 is right.
Why it mattersThe gap grows quickly: for 1,000 changes it is 10 tests against 1,000.

Reading logs

Read from the first error, not the last. The first error is usually the cause; later errors are consequences. Note timestamps and compare with deployment times. Search for the request ID across services.

Decisions under uncertainty

  • Ask whether the decision is reversible (easy to undo, like a feature flag) or irreversible (like deleting data). Decide reversible things fast; slow down for irreversible ones.
  • Write the trade-off: options, cost, benefit, risk, and why you chose.
  • Do the cheapest test that can change your mind.

Picture

Reproduce -> Isolate -> Hypothesize -> Test -> Fix -> Prevent
    ^                                          |
    +----------- if not fixed, loop -----------+

Connection to the real job

A restaurant kitchen shows this well. Orders are coming out slowly: you reproduce it at the Friday rush, isolate the slow station by timing each station, hypothesize (only one grill cook?), and test by changing one thing. This is root-cause analysis.

Applications

  • Data Engineering: broken pipelines, slow Spark jobs, duplicate rows.
  • ML: model accuracy dropped (data drift? feature bug? label delay?).
  • Analytics: wrong numbers after a definition change.
COMMON MISTAKE
Changing three things at once. If it works, you do not know which fix did it; if it breaks, you do not know which one broke it. Change one thing at a time.

Check yourself

  1. Name the debugging loop. Answer: reproduce, isolate, hypothesize, test, fix, prevent.
  2. How many tests to bisect 1,000 builds? Answer: 10.
  3. When do you stop the 5 Whys? Answer: at a process or design cause you can fix.

6.4 Estimation: Fermi Problems and Back-of-the-Envelope Math

BASIC EXPLANATION
A Fermi problem is an estimate of a quantity made by splitting it into simple parts with reasonable assumptions. Back-of-the-envelope math gives a quick approximate answer.
INTUITION
Before you drive to another city you estimate: 300 km at 60 km per hour is 5 hours. You do not need exact numbers; you need the right order of magnitude. A Fermi problem (named after the physicist Enrico Fermi) is an estimate built from simple guesses that are probably within a factor of 2 or 3.

The method

  1. State the question and what unit the answer has.
  2. Break it into factors you can estimate.
  3. Write each assumption clearly and label it as an assumption.
  4. Multiply or add.
  5. Sanity-check against something you know.

Numbers worth remembering

FactValue
Seconds in a day86,400 (about 10⁵)
Seconds in a monthabout 2.6 million
1 million per dayabout 12 per second
1 billion per dayabout 11,600 per second
1 KB, 1 MB, 1 GB, 1 TB10³, 10⁶, 10⁹, 10¹² bytes
1 lakh, 1 crore10⁵, 10⁷

Problem 6.4.1 (Assumptions are made up for practice.) Estimate cab rides per second in a city with 13 million people, if 3% take a ride per day and rides happen mostly in 16 hours.

Formularides per second = rides per day / seconds of activity
Plug inRides per day = 13,000,000 x 0.03; seconds = 16 x 3,600
Compute13,000,000 x 0.03 = 390,000 rides per day. 16 x 3,600 = 57,600 seconds. 390,000 / 57,600 = 6.77 rides per second.
AnswerAbout 7 rides per second on average. If the peak is 3 times the average, plan for about 20 rides per second.
Check390,000 rides over 86,400 seconds would be 4.5 per second; concentrating them into 16 hours gives a higher number, 6.8. The direction is correct.
Why it mattersIn plain words: this system needs a modest server, not a giant one; the important traffic is the location pings, which are far more frequent. Estimation tells you where the real load is.

Problem 6.4.2 A bank has 5 million app users. Each opens the app about 3 times a day, and each open makes about 8 API calls. Estimate average and peak API calls per second.

Formulacalls per second = users x opens x calls per open / 86,400
Plug in5,000,000 x 3 x 8 / 86,400
Compute5,000,000 x 3 = 15,000,000 opens; x 8 = 120,000,000 calls per day; / 86,400 = 1,388.9 per second.
AnswerAbout 1,400 calls per second on average. If peak is 3 times average, about 4,200 per second.
CheckBy the shortcut "1 million per day is about 12 per second": 120 million per day gives 120 x 12 = 1,440 per second. Close to 1,389.
Why it mattersA capacity planner would turn this directly into a staffing target and compare with Little's law. If each call takes 0.2 s, concurrent calls = 4,200 x 0.2 = 840.

Picture

Big unknown -> factors -> each factor: assumption (labelled) -> multiply -> sanity check

Connection to the real job

System design interviews begin with this (Chapter 8). On the job, you estimate storage and cost before you build, and the estimate can save weeks.

Applications

  • Data Engineering: data volume per day, storage cost, cluster size.
  • ML/AI: GPU hours, tokens per month, cost per 1,000 predictions.
  • Analytics: market sizing, campaign reach.
COMMON MISTAKE
Hiding assumptions or giving one false-precise number. Say the assumptions aloud and give a range ("between 1,000 and 2,000 per second").

Check yourself

  1. How many seconds are in a day? Answer: 86,400.
  2. How do you check a Fermi estimate? Answer: compare with a known fact or a quick shortcut.
  3. What do you do with assumptions? Answer: state them clearly and label them.

6.5 Three Worked Problems: KPI Drop, Estimate, Bug

BASIC EXPLANATION
A worked problem is a full example solved step by step. These three cover a drop in a KPI (key performance indicator), an estimation and a bug, and show how to apply the earlier methods.
INTUITION
A doctor does not order every test for every patient. She asks, checks the obvious things first, and narrows down. Problem solving is the same: cheap checks first, then deeper tests.

Three short worked problems, one each for a KPI drop, an estimate and a bug. Follow the steps, then rework with different numbers.

Problem 6.5.1 Weekly revenue fell from 50 lakh to 44 lakh. Orders fell from 25,000 to 23,000. Break it down.

Formularevenue = orders x average order value (AOV)
AOV before50,00,000 / 25,000 = 200
AOV after44,00,000 / 23,000 = 191.3
SplitOrders fell 8% (2,000 / 25,000). AOV fell 4.3% (8.7 / 200). Revenue fell 12%.
Next checkData first (did the load complete?), then what changed: a campaign, a stock-out, a price change, a region.
Check0.92 x 0.957 = 0.88, a 12% fall. Yes.

Problem 6.5.2 Estimate how many cups of chai a city of 20 lakh people drinks in a day, to size a vending machine business.

Assumptions60% of people drink chai; average 2 cups a day.
Compute20,00,000 x 0.6 x 2 = 24,00,000 cups
RangeLow (50%, 1.5 cups) = 15,00,000; high (70%, 3 cups) = 42,00,000.
AnswerAbout 24 lakh cups a day, with a range of 15 to 42 lakh (assumptions, not data).
CheckThe order of magnitude is millions, not thousands. Sensible for a city of 20 lakh.

Problem 6.5.3 This function should return the average of positive numbers but crashes for an empty list: sum(x for x in a if x > 0) / len([x for x in a if x > 0]). Find and fix it.

Reproducea = [] gives division by zero. a = [-1, -2] also fails.
CauseThe denominator is 0 when no positive values exist.
Fixp = [x for x in a if x > 0] then return sum(p)/len(p) if p else None
Test[2, 4, -1] returns 3.0; [] and [-1] return None.
Why it mattersEdge cases (empty, all negative) are what interviewers test.
COMMON MISTAKE
Jumping to a cause. Wrong: "Revenue fell, so it must be the competitor." Right: split the metric, check data quality first, and list three hypotheses with a test for each.

Check yourself

  1. AOV for revenue 60 lakh and 20,000 orders? Answer: 300.
  2. First check in a KPI drop? Answer: Data quality and load completeness.
  3. Why give a range in an estimate? Answer: Because assumptions are uncertain.

Chapter recap

  • For coding problems: clarify, restate, examples, brute force, optimize, code, test, complexity.
  • State the brute force first; it shows understanding.
  • Split problems into MECE branches and test one hypothesis at a time.
  • Revenue = orders x average order value is a good first split.
  • Debug by reproducing, isolating, hypothesizing, testing, fixing and preventing.
  • Bisecting finds the first bad change in log₂(n) tests.
  • 5 Whys ends at a process cause, not a person.
  • Estimate with labelled assumptions and sanity-check the result.
  • Break a revenue drop into orders and AOV, give estimates as ranges, and fix bugs by reproducing and testing edge cases (section 6.5).

Practice set

  1. (Easy) How many tests to bisect 16 builds? Answer: log₂(16) = 4.
  2. (Easy) 2 million events per day is about how many per second? Answer: 2,000,000 / 86,400 = 23.1.
  3. (Easy) Expand MECE. Answer: Mutually exclusive, collectively exhaustive.
  4. (Medium) Find the output: two_sum_fast([3, 3], 6). Answer: At i = 0, store {3: 0}. At i = 1, 6 - 3 = 3 is in seen, return (0, 1).
  5. (Medium) Orders fell from 1,000 to 900, AOV rose from 200 to 210. Revenue change? Answer: 0.9 x 1.05 = 0.945, a 5.5% fall.
  6. (Medium) Find the bug in the plan: "The job failed, I re-ran it, it passed, done." Answer: No root cause and no prevention; it will fail again. Do 5 Whys and add a check.
  7. (Medium) Scenario: a dashboard number is 20% lower than finance's number. What do you check first? Answer: Definitions (what counts as revenue), date range and time zone, duplicates, missing partitions.
  8. (Hard) Interview: "How many bytes does an app store if 10 million users each send 5 messages of 200 bytes per day for a year?" Answer: 10,000,000 x 5 x 200 = 10,000,000,000 bytes (10 GB) per day; x 365 = 3.65 TB per year before replication.
  9. (Hard) Interview: "Walk me through how you would debug a sudden latency spike at 3 pm." Answer: Reproduce or find the time window; compare p50/p95 by endpoint; check deployments, traffic, GC, DB slow queries and connection pool; test one hypothesis at a time; fix and add an alert.
  10. (Hard) Scenario: you must choose between a quick fix that deletes old data (irreversible) and a slower reversible one. Answer: Choose the reversible one unless the cost of waiting is higher than the cost of a mistake; if you must delete, take a backup first and record the decision.
  11. (Easy) Orders 10,000, AOV 300. Revenue? Answer: 30,00,000.
  12. (Medium) Orders fall 10% and AOV falls 10%. Revenue change? Answer: 0.9 x 0.9 = 0.81, a 19% fall.
  13. (Interview) Walk through a sudden 20% drop in a metric. Answer: Check data first, split the metric, compare segments and time, list hypotheses with a test each, then report.
