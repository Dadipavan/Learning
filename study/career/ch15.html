15.1 How to Run a Project in This Area

INTUITION
Building a project is like cooking a meal for guests. You decide the menu first (the question), buy ingredients (data and tools), cook in steps and taste as you go (small commits and tests), and you only serve when the plate is ready (definition of done). Guests also need a menu card (the README) and a photo of the dish (the demo and the post).

In this area (career proof: sites, contributions, interview material, resumes) the "data" is often text and the "tests" are checks on links, files and wording. The method is the same as for a data project.

Words you need

TermMeaning
Repository (repo)A folder tracked by git, holding your files and their full history
CommitA saved snapshot of your files with a message
BranchA separate line of work, so experiments do not break the main version
Static siteA website made of plain HTML files; no server code runs when someone visits
ForkYour own copy of someone else's repository on a hosting site
Pull request (PR)A request to the owner: "please take my change into your project"
Definition of doneA written list of checks; when all pass, the project is finished

Plan the question and the success criteria

Write one sentence: "I will build X so that Y can do Z." Then write three measurable success criteria before coding. Example for Project 43: "A visitor can open my site, read three posts and reach my GitHub in two clicks; the build script runs in under one second; a link check finds 0 broken links." If you cannot measure a criterion, rewrite it until you can. Then time-box: choose hours (Chapter 11.1 suggests about 25 hours per project) and stop when they run out, shipping what works.

Repo layout (a pattern that fits every project here)

project-name/
├── README.md            # the menu card: what, why, how to run, result
├── LICENSE              # MIT is a common, simple choice
├── .gitignore           # keeps junk (__pycache__/, .env, data dumps) out
├── src/ or scripts/     # the code you run
├── data/                # small sample or generated data (never private data)
├── tests/               # checks that prove it works
├── docs/                # output or notes (GitHub Pages can serve this folder)
└── notes/decisions.md   # why you chose A over B (gold in interviews)

Environment and dependencies

Use a virtual environment (an isolated set of Python packages for one project): python3 -m venv .venv, then source .venv/bin/activate. Prefer the Python standard library when it is enough. Every project in this chapter uses only the standard library, so there is nothing to install and nothing to break. When you do add packages, list them in requirements.txt, and state your Python version in the README (the examples here ran on Python 3.14; any recent Python 3 should work).

Data sourcing or generation

Never use company data, client names or private messages. Good sources: your own writing, public datasets, open-source repositories, or data you generate with a short script and a fixed random seed (so anyone gets the same numbers). Write the source and the licence in the README.

Commit rhythm and good commit messages

Commit when one small thing works, at least once per work session. A good message says what changed, in the imperative mood, in under about 60 characters, with a longer body only if the reason is not obvious.

WeakStrong
updateAdd link checker for built pages
fix stuffClose open list before code block in builder
final final v2Write README with run steps and result

Why it matters: your commit history is a diary a reviewer can read in 30 seconds. A tidy history says "careful engineer".

Definition of done

A project is done when all of these are true: it runs from a clean clone using only the README steps; your success criteria are met and measured; at least three checks or tests pass; the README has a result with a number; known limits are written down; and one public write-up exists. "Done" is not "perfect".

README template

# Project title: one-line result

**Problem.** One sentence a non-expert understands.
**Result.** The headline number or screenshot.

## Demo
Link to the live page or a 2-minute video.

## How to run
git clone <url> && cd project-name
python3 -m venv .venv && source .venv/bin/activate

## Data
Source, licence, size, how it was generated.

## Method
3-5 bullets: what you did and why.

## Results
Table or numbers. State what the numbers mean.

What does not work yet; what you would do next.

How to write the LinkedIn or blog post

Use five short paragraphs: (1) the problem in one sentence; (2) why you cared; (3) what you built, with one picture; (4) the result with a number; (5) one mistake you made and what you learned, then the link. Chapter 4 covered tone, and Chapter 11.5 covered posting rhythm. Post within a week of finishing, while the details are fresh.

Testing and debugging checklist for this area

  • Does the project run from a fresh clone in an empty folder? (Most "works on my machine" failures show here.)
  • Do all links work? Run a link checker (you will write one in 15.2).
  • Open the output in a different browser and on a phone-sized window.
  • Are there secrets, private names or personal phone numbers in any file or in the git history? Search before you push.
  • Is .gitignore in place before the first commit? Files added by mistake stay in history.
  • Spell-check the README and the posts; read them aloud once (Chapter 3).
  • When something breaks: reproduce it, shrink it to the smallest case, read the full error message from the bottom up, change one thing at a time, and write the fix as a test.
REAL JOB TIP
Keep a notes/decisions.md file with one line per decision ("Used plain HTML, not a framework, because the site is small and I wanted zero dependencies"). In interviews you will be asked "why did you choose that?" and the file answers for you.

Check yourself

  1. Why write success criteria before coding? Answer: so "done" is measurable and you do not keep polishing forever.
  2. What goes in .gitignore? Answer: files that should never be committed, such as __pycache__/, .env, .venv/ and big data dumps.
  3. Name two things in a strong commit message. Answer: what changed, in the imperative mood, short; plus a reason in the body when it is not obvious.

15.2 Project: Portfolio Website and Three Blog Posts (Project #43)

Goal and why employers care

You will build a small website of your own, generated by a Python script you wrote, with a home page and three blog posts, and publish it free on GitHub Pages. Recruiters often search your name. A clean site with three clear posts shows that you can build, explain and finish. Writing the generator yourself proves you can handle files, text and automation, which are everyday data skills.

Skills used

  • Python file handling and string processing (the Python study document).
  • Clear writing, headline and structure (Chapter 4, Written Communication).
  • Explaining results with numbers (Chapter 5, Data Storytelling).
  • README, profile and project selection (Chapter 11, Portfolio, GitHub, LinkedIn and Resume).
  • Git basics: commit, push (15.1 above).

Data

Your data is your writing. For this lab the three posts are tiny placeholders about neutral topics (loading shop orders into SQLite, chart mistakes, a first pull request). Replace them with your real posts. Do not copy other people's text.

  1. Write the builder. It reads each post, converts a small subset of Markdown (headings, paragraphs, bullets, code blocks) into HTML, escapes special characters so text cannot break the page, and makes an index page sorted newest first.
"""Tiny static site builder. Usage: python3 build_site.py posts docs"""
import html, re, sys
from pathlib import Path

PAGE = """<!doctype html><html lang="en"><head><meta charset="utf-8">
<meta name="viewport" content="width=device-width, initial-scale=1">
<title>{title}</title>
<style>body{{font-family:sans-serif;max-width:42rem;margin:2rem auto;padding:0 1rem;line-height:1.6}}
pre{{background:#f4f4f4;padding:.8rem;overflow:auto}}</style></head>
<body><nav><a href="index.html">Home</a></nav>{body}</body></html>"""

def parse_post(text):
    head, _, body = text.partition("\n---\n")
    meta = dict(line.split(": ", 1) for line in head.splitlines())
    return meta, body

def md_to_html(md):
    out, in_code, in_list = [], False, False
    for line in md.splitlines():
        if in_list and not in_code and not line.startswith("- "):
            out.append("</ul>"); in_list = False
        if line.startswith("```"):
            out.append("</pre>" if in_code else "<pre>")
            in_code = not in_code
            continue
        if in_code:
            out.append(html.escape(line))
            continue
        if line.startswith("## "):
            out.append(f"<h2>{html.escape(line[3:])}</h2>")
        elif line.startswith("# "):
            out.append(f"<h1>{html.escape(line[2:])}</h1>")
        elif line.startswith("- "):
            if not in_list:
                out.append("<ul>"); in_list = True
            out.append(f"<li>{html.escape(line[2:])}</li>")
        elif line.strip():
            out.append(f"<p>{html.escape(line)}</p>")
    if in_list: out.append("</ul>")
    return "\n".join(out)

def main(src, dst):
    src, dst = Path(src), Path(dst)
    dst.mkdir(exist_ok=True)
    posts = []
    for f in sorted(src.glob("*.md")):
        meta, body = parse_post(f.read_text())
        slug = re.sub(r"^\d+-", "", f.stem) + ".html"
        (dst / slug).write_text(PAGE.format(title=meta["title"], body=md_to_html(body)))
        posts.append((meta["date"], meta["title"], slug))
    items = "\n".join(f'<li>{d} - <a href="{s}">{html.escape(t)}</a></li>'
                      for d, t, s in sorted(posts, reverse=True))
    index = f"<h1>Asha Rao: Data Portfolio</h1><p>Short bio here.</p><h2>Posts</h2><ul>{items}</ul>"
    (dst / "index.html").write_text(PAGE.format(title="Portfolio", body=index))
    (dst / ".nojekyll").write_text("")
    print(f"built {len(posts)} posts + index into {dst}/")

if __name__ == "__main__":
    main(sys.argv[1], sys.argv[2])

How it works, line by line: parse_post splits the file at the first --- line and turns the header lines into a dictionary. md_to_html walks line by line and keeps two flags, in_code and in_list, so it knows when to open and close <pre> and <ul>. html.escape turns " and < into safe codes. The slug removes the leading number: 01-first-pipeline becomes first-pipeline.html. The empty .nojekyll file tells GitHub Pages to serve the files as they are.

  1. Write the link checker. It reads every page, finds each href, and complains if a local target file does not exist.
import re, sys
from pathlib import Path
docs = Path(sys.argv[1]); bad = 0
for f in docs.glob("*.html"):
    for href in re.findall(r'href="([^"#]+)"', f.read_text()):
        if not href.startswith("http") and not (docs / href).exists():
            print("BROKEN", f.name, "->", href); bad += 1
print("pages:", len(list(docs.glob('*.html'))), "broken links:", bad)
sys.exit(1 if bad else 0)

After a minute the site appears at https://<your-username>.github.io/<repo-name>/. Menu names change over time, so follow the current GitHub Pages documentation if a label differs. Put the link in your README, LinkedIn Featured section and resume.

Evaluation and acceptance criteria

  • build_site.py finishes with no error and writes 4 HTML pages plus .nojekyll.
  • check_site.py reports broken links: 0 and exits 0.
  • Index lists 3 posts, newest first (dates 2026-11-01, 2026-10-15, 2026-10-01 in this lab).
  • Each post has a title, a result with at least one number, and a closing "what I would do next".
  • Site loads on a phone-sized window with readable text.
  • The public URL works from a private browser window.
  • A friend can reach your GitHub link within 2 clicks.

Common pitfalls

  1. Raw characters break the page. A < in your text vanishes or breaks a tag. Detect it: view the page source; fix it with html.escape.
  2. Broken links after moving to Pages. Links starting with / point to the site root, not your repo folder. Use relative links like first-pr.html; the link checker will catch missing files.
  3. Stale output. You edit a post but forget to rebuild, so the live site is old. Make rebuilding part of your commit routine.
  4. Pages shows a 404. Usually the wrong branch or folder is selected, or the repository is private on a plan that does not allow it. Re-check the Pages settings.
  5. Posts with no numbers. A post that says "improved a lot" persuades nobody. Detect it by searching each post for digits.

Three extensions

  1. Add an RSS feed file (feed.xml) generated from the same list of posts.
  2. Add a tags field to the header and generate one page per tag.
  3. Add a GitHub Actions workflow that runs the builder and link checker on every push (not run here).

Interview talking points

Q1. Why did you write your own site generator instead of using a template? Model answer: "I wanted to learn how static sites work and keep zero dependencies. The generator is 59 lines. I also learned to test it: I wrote a link checker and made it fail on purpose to prove it worked. For a bigger site I would use a ready tool."

Q2. What was the hardest bug? Model answer: "My bullet list stayed open when a code block started, so the HTML was invalid. I found it by reading the generated file, not the source. I fixed the order of two checks and I now always inspect the output."

Q3. How do you know the site works? Model answer: "The build prints a count, the link checker returns zero broken links, and I open the public link in a private window. I do not rely on 'it looked fine on my laptop'."

15.3 Project: First Open-Source Contribution (Project #44)

Goal and why employers care

You will find a beginner-friendly issue in a real open-source project, understand the repository, make a small correct change, and open a good pull request. Before that you rehearse the whole workflow locally with git, so the commands are familiar. Employers care because a merged pull request is public proof that you can read other people's code, follow a team's rules, communicate in writing, and take review feedback calmly.

Skills used

  • Git: branch, commit, remote, rebase (15.1 and this section).
  • Reading unfamiliar code and tests (Chapter 6, Problem Solving).
  • Writing clearly: issue comments and PR descriptions (Chapter 4, Written Communication).
  • Python basics and testing (the Python study document).
  • Professional presence on GitHub (Chapter 11).

Data

No dataset. Your "data" is a practice repository you create in /tmp, containing a tiny Python helper library, plus (later) a real project you choose. A small but real project beats a famous giant one: maintainers answer faster and the codebase is readable in an afternoon.

Architecture: who owns which copy

 upstream.git  (the maintainer's original repo)
      |   ^
 fork |   | pull request (you ask them to merge)
      v   |
 fork.git      (your copy on the server)
      |   ^
 clone|   | push
      v   |
 myfork/       (your laptop)  -- remote "origin" = fork.git
                              -- remote "upstream" = upstream.git

Read it as follows. You cannot push to the maintainer's repo. You push to your fork, then ask the maintainer to pull from it. You add upstream as a second remote so you can fetch their newest changes.

Step-by-step build

  1. Find a good first issue (not run here: needs the internet). On GitHub, open a project you actually use, go to Issues, and filter by labels such as good first issue or help wanted. Look for: a recent maintainer reply (the project is alive), a clear description, no one already assigned, and a fix that touches one or two files. Read README.md, CONTRIBUTING.md and the code of conduct. Comment on the issue: "I would like to work on this. My plan is X. Is that okay?" and wait for a yes. Good first changes: a documentation typo, a missing test, a clearer error message.
  1. Read the repository in this order: README (what it is) → CONTRIBUTING (the rules) → the test folder (how it should behave) → the file named in the issue → git log --oneline -10 (the style of past changes). Run the tests before you change anything, to know what "passing" looks like.
  1. Rehearse locally. The script below creates a maintainer's repo with a small bug (mean([]) raises a confusing ZeroDivisionError), forks and clones it, makes the fix on a branch with a test, lets the maintainer push a new commit while you work, and then rebases your branch.   1. Make the real contribution. Repeat the same steps with the real project: click Fork, clone your fork, add the upstream remote, branch, change, run the project's tests, commit, push, and open the PR on GitHub (not run here). If the project has a formatter or linter, run it.
  1. Write a good pull request. Use this shape.
Title: Raise ValueError for empty input in mean()

What: mean([]) now raises ValueError("mean() needs at least one value").
Why: it used to raise ZeroDivisionError, which hides the real cause. Fixes #1.
How tested: added a test in tests/test_stats.py; all tests pass locally.
Notes: no behaviour change for non-empty lists. Happy to adjust the message.

Keep it small (under about 100 changed lines), link the issue, say how you tested, and be polite. When the maintainer asks for changes, reply "Thanks, done" and push to the same branch; the PR updates by itself.

  1. After the merge. Delete the branch, sync your fork, and add the PR link to your resume and LinkedIn. Then write post 3 from Project 43 ("My first open-source pull request").

Evaluation and acceptance criteria

  • The local rehearsal runs without error and ends with your commit on top of upstream/main.
  • Your fix has at least one test that fails before the change and passes after.
  • The PR is under about 100 changed lines, has a title, a "what and why" and a "how tested" part, and links an issue.
  • You received a response (merged, or review comments answered within two days).
  • git status is clean and no unrelated files (__pycache__, editor settings) are in the diff.
  • For the real PR: the project's own checks pass.

Common pitfalls

  1. Committing junk files. In my first attempt a __pycache__ file got staged because the repo had no .gitignore. Detect with git status and git diff --stat before every commit. The final script puts __pycache__/ into .gitignore first.
  2. Missing git identity. git commit fails with "Author identity unknown". Set git config user.name and user.email for the repo.
  3. A giant PR. Maintainers avoid reviewing 800 lines from a stranger. Split by topic; one PR, one idea.
  4. Working without asking. You may build something the maintainers do not want. Comment on the issue first.
  5. Force-pushing carelessly. After a rebase you may need to force-push your own branch; prefer git push --force-with-lease, which refuses if someone else pushed. Never force-push the shared main branch.

Three extensions

  1. Fix a second issue in the same project and ask to be added to a review rota (or simply review someone else's PR politely).
  2. Improve the project's documentation with a "how to run the tests" section.
  3. Add a small GitHub Actions test workflow to your practice repo (not run here).

Interview talking points

Q1. Tell me about your open-source contribution. Model answer: "I chose a small library I use. I commented on a good-first-issue to confirm my plan, read the tests, fixed an unclear error and added a test. The change was 12 lines. The maintainer asked me to reword the message; I did, and it was merged. I learned to keep changes small."

Q2. What is the difference between merge and rebase? Model answer: "Both bring in new upstream commits. Merge keeps both histories and adds a merge commit. Rebase replays my commits on top of the newest upstream, so history is a straight line. I rebase my own unpublished branch and never rewrite shared history."

Q3. How did you handle review feedback? Model answer: "I read every comment as help, not criticism. I answered each one, pushed the fix to the same branch, and asked when something was unclear. I did not argue about style the project had already chosen."

Chapter recap

  • A project is finishable when you write measurable success criteria and a definition of done before you start.
  • A repo should run from a fresh clone using only README steps; add .gitignore before the first commit.
  • Commit small and often with imperative messages; the history is your diary.
  • Use public or generated data; never company or private data.
  • A static site is plain HTML; a 59-line Python script can build one from text posts.
  • Always test your checker by making it fail once (the broken-link test).
  • Open-source flow: fork, clone, add upstream, branch, change, test, push to your fork, open a PR.
  • Rebase your own branch onto upstream/main to keep a straight history; use --force-with-lease if you must force-push.
  • A good PR is small, linked to an issue, explains what, why and how tested.

Practice set

1. (Easy) Rewrite the commit message update for a change that adds a link checker. Answer: Add link checker for built pages (imperative, specific, short).

2. (Easy) What does 01-first-pipeline.md become after build_site.py runs? Answer: first-pipeline.html, because the regex removes the leading digits and dash.

3. (Easy) List three things that belong in .gitignore for a Python project. Answer: __pycache__/, .venv/, .env (secrets). Data dumps are also common.

4. (Medium) What is the output of check_site.py if index.html links to about.html and no such file exists, with 4 pages in docs/? Answer: BROKEN index.html -> about.html then pages: 4 broken links: 1, exit code 1.

5. (Medium) Find the bug: a builder opens <ul> for each bullet line and never closes it before a heading. What does the browser show and how do you detect it? Answer: following content is indented inside the list or the layout breaks; detect by reading the generated HTML, and fix by closing the list when a non-bullet line arrives.

6. (Medium) You ran git rebase upstream/main and then git push origin my-branch was rejected. Why, and what do you do? Answer: rebase rewrote your commits, so the remote branch has different history. Use git push --force-with-lease origin my-branch on your own branch only.

7. (Interview) "Why do you keep an upstream remote?" Answer: origin is my fork; upstream is the original. I fetch from upstream to get new changes and rebase my branch, so my PR has no conflicts.

8. (Scenario) You found an issue labelled good first issue that is 2 years old with no replies. Do you start? Answer: Not yet. Comment and ask if it is still wanted; if no answer after a few days, pick a project with recent activity. A dead project will not review your PR.
