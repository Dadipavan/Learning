Think about an online shop that ran fine on one server, then went strange after the team added three more behind a load balancer. Some users saw old data, some requests were charged twice, and one slow node dragged everything down. These problems are not simple coding mistakes. They are the normal behaviour of distributed systems, systems that spread work and data over many computers connected by a network. In this chapter you learn the few ideas behind them: copies of data (replication), splitting data (partitioning), agreeing on one answer (consensus), the trade-off called CAP, and safe ways to handle failures (retries, idempotency, timeouts, backpressure). You will run small Python simulations, so every claim has a number behind it. We use one running example: an orders service that stores "order 77 = paid" on several machines.

12.1 Why Distributed, and What Can Go Wrong

INTUITION
One cashier can serve only so many customers, and if she falls sick the shop closes. Hire three cashiers and you serve more people and survive one sick day. But now the three must agree on prices, and they can only talk by shouting across a noisy room. Messages get lost, and nobody can be sure if a silent cashier is busy or gone. That noisy room is the network.

Words you need

Replicaone copy of the same data on a node

Why we do it

  • Scale: one machine has a limit on CPU, memory and disk.
  • Availability: if one node dies, others keep working.
  • Latency: put copies near users (Mumbai, Frankfurt, Virginia).

The hard part: partial failure

On one computer, a program either works or crashes. In a distributed system, a request can fail in a confusing way: the message was lost, or the server did the work but its reply was lost, or the server is just slow. From the caller's side these look the same: silence. This is why timeouts and idempotency (12.6) matter so much.

Failure typeExampleWhat you see

Byzantinea node sends wrong or malicious datawrong replies (rare, hard)

Most systems you will use assume crashes, omissions and slowness, and not Byzantine faults.

Applications

  • Data Engineering: Kafka clusters, HDFS, object stores keep 3 copies of data.
  • MLOps: model-serving replicas behind a load balancer.

Assuming "the network is reliable" and "latency is zero". These are the first two famous false beliefs about distributed systems. Always design for lost, late and duplicated messages.

Check yourself

  1. What does a caller see when a server crashes versus when its reply is lost? Answer: The same thing: no reply (silence).
  2. Why do 3 replicas beat 1 for availability? Answer: The service survives any single failure, and two failing together is rare.
  3. When does the independence assumption fail? Answer: When nodes share a cause, such as one rack, one power line, one bad deployment.

12.2 Replication and Consistency

INTUITION
A teacher writes today's homework on the board (the leader). Students copy it to their notebooks (followers). A student who copies late has an old version. If you ask that student, you get a stale answer. If the teacher waits until every student confirms before saying "done", it is safe but slow, and one sleeping student blocks everybody.

Replication means keeping the same data on several nodes. There are two common designs.

  • Leader-follower: all writes go to one leader, which copies them to followers. Reads can go to followers (fast, maybe stale).
  • Leaderless (quorum): the client writes to several nodes and reads from several; the overlap gives fresh data.

Synchronous replication waits for followers before saying "ok". Asynchronous replication says "ok" first and copies later (fast, but if the leader dies you can lose the last writes).

How to read it: the arrow numbered 1 is the client write. The leader stores "order 77 = paid", then sends copies (arrows 2) to both followers. Only after enough followers confirm does the leader answer ok (label 3).

Quorum rule

With N replicas, write to W of them and read from R of them. If W + R > N, every read set overlaps every write set in at least one node, so a read sees the latest write (when versions are compared). This is the quorum rule.

NWRW + R > N?Behaviour
311No (2 > 3 false)fast, can read stale data
322Yes (4 > 3)balanced, fresh reads
331Yes (4 > 3)writes need all nodes, reads are cheap

Predict, Run, Explain

We simulate a write of version 1 to W random replicas, then a read from R random replicas, 10,000 times. Before you run it, predict: for W=1, R=1, what fraction of reads are stale? (Hint: the read hits the one fresh node with probability 1 out of 3.)

import random
# quorum replication: N=3 replicas, write to W, read from R
random.seed(1)
class Cluster:
    def __init__(s,n=3): s.rep=[(0,None)]*n  # (version,value)
    def write(s,ver,val,W):
        for i in random.sample(range(len(s.rep)),W): s.rep[i]=(ver,val)
    def read(s,R):
        got=[s.rep[i] for i in random.sample(range(len(s.rep)),R)]
        return max(got)
for W,R in [(1,1),(2,2),(3,1)]:
    stale=0
    for t in range(10000):
        c=Cluster(); c.write(1,"new",W)
        if c.read(R)[0]!=1: stale+=1
    print(f"N=3 W={W} R={R} W+R>N={W+R>3}  stale reads: {stale} of 10000")

Real output:

N=3 W=1 R=1 W+R>N=False  stale reads: 6723 of 10000
N=3 W=2 R=2 W+R>N=True  stale reads: 0 of 10000
N=3 W=3 R=1 W+R>N=True  stale reads: 0 of 10000

Line by line: write updates W randomly chosen replicas to version 1. read picks R random replicas and returns the highest version it saw (max of tuples compares version first). If that version is not 1, the read is stale. With W=1, R=1, the read hits the fresh node with chance 1/3, so stale is 2/3 = 66.7%, and we measured 6,723 of 10,000. With W=2, R=2 or W=3, R=1, the sets must overlap, so 0 stale reads.

Consistency models, from strong to weak

ModelPromiseExample
Strong (linearizable)reads always see the latest completed write, as if there is one copybank balance, leader election

Eventualif writes stop, all copies become equal after some timelikes counter, DNS

Eventual consistency needs a rule for conflicts. A simple one is last-write-wins (LWW): keep the value with the highest timestamp. It is easy but can silently drop an update. Our run of ch12e.py showed it: merging {'x': (1, 'red')} with {'x': (2, 'blue')} gave {'x': (2, 'blue')}.

Connection to the real job

Reading from a database read-replica right after writing may return old data (replication lag). Your data pipelines and dashboards may show yesterday's number for a moment. Anyone checking data must know whether they read from the leader or a follower.

Applications

  • Data Engineering: Kafka partitions have leader and follower replicas; Cassandra uses tunable quorums.
  • Data Analytics: read replicas serve BI queries without loading the main database.
  • MLOps: feature stores keep an online copy that may lag the offline copy.
COMMON MISTAKE
Thinking W + R > N gives full "strong consistency" in all cases. With sloppy quorums, concurrent writes and clock problems, you can still see odd results. It is a good rule for freshness, not a total guarantee.

Check yourself

  1. N=5, W=3, R=3: is W+R>N? Answer: Yes, 6 > 5.
  2. Asynchronous replication risk? Answer: If the leader dies before copying, the last writes can be lost.
  3. What does eventual consistency promise? Answer: If updates stop, all replicas converge to the same value.

12.3 Partitioning and Consistent Hashing

INTUITION
A library with a million books cannot keep them all on one shelf. You split them: A to F in room 1, G to M in room 2, and so on. Now each room is small and many readers work in parallel. The question is: how do you decide which room holds which book, and what happens when you add a new room?

Partitioning (also called sharding) splits data across nodes, so each node holds only a part. Replication copies; partitioning splits. Big systems do both: each partition is replicated.

Ways to choose the partition:

  • Range: keys A-F here, G-M there. Good for range scans, but a popular range makes a hot spot (one overloaded node).
  • Hash: node = hash(key) mod N. Spreads load evenly. But there is a trap.

The trap with mod N

If you go from N=4 to N=5 nodes, almost every key changes node, and the whole cache or dataset must move. Consistent hashing fixes this. Put nodes on a circle (a ring) of hash values. Each key goes to the first node clockwise from its hash. Adding a node only takes keys from its neighbour. Using many virtual nodes (many points per machine) smooths the load.

          hash ring (0 ... max)
       A1      B2
     /            \
   D3              C1       key k -> go clockwise to the next node point
     \            /
       B1      A2

Predict, Run, Explain

Before running it, predict: with 1,000 keys, roughly what fraction should move when a 5th node joins, for the best possible scheme? (Answer: 1/5 = 20%, since the new node should own one fifth.) Then compare mod N with the ring.

import hashlib, bisect
def h(s): return int(hashlib.md5(s.encode()).hexdigest(),16)
def simple_assign(keys, n): 
    return {k: h(k)%n for k in keys}
keys=[f"user{i}" for i in range(1000)]
a=simple_assign(keys,4); b=simple_assign(keys,5)
moved=sum(a[k]!=b[k] for k in keys)
print("mod-N: keys moved going 4->5 nodes:",moved,"of 1000")

class Ring:
    def __init__(s,nodes,vnodes=100):
        s.ring=sorted((h(f"{n}#{v}"),n) for n in nodes for v in range(vnodes))
        s.hashes=[x[0] for x in s.ring]
    def get(s,k):
        i=bisect.bisect(s.hashes,h(k))%len(s.ring)
        return s.ring[i][1]
r4=Ring(["A","B","C","D"]); r5=Ring(["A","B","C","D","E"])
moved=sum(r4.get(k)!=r5.get(k) for k in keys)
print("ring: keys moved going 4->5 nodes:",moved,"of 1000")
from collections import Counter
print("ring load with 5 nodes:",sorted(Counter(r5.get(k) for k in keys).items()))

Real output:

mod-N: keys moved going 4->5 nodes: 795 of 1000
ring: keys moved going 4->5 nodes: 185 of 1000
ring load with 5 nodes: [('A', 200), ('B', 230), ('C', 215), ('D', 170), ('E', 185)]

Line by line: h turns text into a big number using MD5 (used here only for spreading, not for security). With mod N, 795 of 1,000 keys moved, close to the 4/5 = 80% expected, because a key stays only when h mod 4 == h mod 5. The ring moved 185 of 1,000, near the ideal 200. The load per node on the ring ranged from 170 to 230, which is reasonably even with 100 virtual nodes per machine.

Connection to the real job

Choosing a partition key is the biggest design choice in Cassandra, DynamoDB, Kafka and Spark. A key with skew (for example country = India holds 60% of rows) creates a hot partition and the slowest task decides the job time. Think of a kitchen with several cooks: the slowest cook sets the time the whole table is served.

Applications

  • Data Engineering: Kafka topic partitions, Spark repartition, warehouse distribution keys.
  • Machine Learning: sharded embedding tables and sharded training data.
  • Web and MLOps: cache clusters (memcached) and load balancing by session.
COMMON MISTAKE
Picking a partition key like date or status. All today's writes go to one partition (a hot spot). Pick a key with many values and even traffic, such as user ID.

Check yourself

  1. Replication or partitioning splits data? Answer: Partitioning. Replication copies.
  2. Why do virtual nodes help? Answer: They spread each machine over many ring points, so load is more even.
  3. What breaks when you add a node with mod N? Answer: Most keys change node.

12.4 Consensus and Leader Election

INTUITION
Five friends must choose one restaurant by text messages. Some phones are off, messages arrive late. They agree on a rule: a choice counts only when at least 3 of 5 say yes, and each person votes once per round. Because any two groups of 3 share a person, two different choices can never both win. That rule is a majority quorum.

Consensus means a group of nodes agrees on one value (or one order of events) even when some nodes fail. Famous algorithms are Paxos and Raft. Raft was designed to be easier to understand. You do not need to code them; you need the intuition.

Raft in 5 sentences

  1. One node is the leader. All writes go through it.
  2. The leader sends each write to followers. The write is committed when a majority has stored it.
  3. Followers expect heartbeats from the leader. If a follower hears nothing for a random time (for example 150 to 300 ms), it becomes a candidate and asks for votes.
  4. A candidate that gets a majority of votes becomes the new leader of a new term (a number that only increases).
  5. Random timeouts make it unlikely that two candidates start together, and if they do, they retry.

Majority maths

A cluster of N nodes survives floor((N - 1) / 2) crashes.

Nodes NMajorityCrashes tolerated
321
431
532
743

Notice 4 nodes tolerate no more crashes than 3, so clusters use odd sizes.

Predict, Run, Explain

Predict: in a 5-node cluster, can it still elect a leader with 3 alive? With 2 alive?

import random
random.seed(3)
# simplified leader election: highest alive id wins (bully); and raft-style majority vote
nodes={1:True,2:True,3:True,4:True,5:True}
def bully():
    return max(n for n,a in nodes.items() if a)
print("leader:",bully()); nodes[5]=False; print("5 crashed, new leader:",bully())
def majority(total,alive): return alive>total//2
for alive in (5,3,2):
    print(f"5-node cluster, {alive} alive -> can elect/commit? {majority(5,alive)}")
# raft-like election with random timeouts
def election():
    t={n:random.uniform(150,300) for n in range(1,6)}
    first=min(t,key=t.get)
    return first,round(t[first],1)
for term in range(1,4):
    print("term",term,"first candidate (node, timeout ms):",election())
# eventual consistency: last-write-wins merge
a={"x":(1,"red")}; b={"x":(2,"blue")}
merged={k:max(a.get(k,(0,)),b.get(k,(0,))) for k in {*a,*b}}
print("LWW merge:",merged)

Line by line: bully is a simple older method where the highest alive id leads: node 5 leads, and after it crashes node 4 takes over. majority(5, alive) is true only when alive > 2, so 3 alive works and 2 alive does not. The election function mimics Raft's random timeout: the node with the smallest random timeout asks for votes first, and so usually wins without a clash. The numbers (timeouts in ms) are random with a fixed seed. Our simulation does not implement real vote messages or logs; it only shows the ideas.

Problem 12.4.2 A network partition splits a 5-node cluster into groups of 3 and 2. What happens?

Step 1The group of 3 has a majority (3 > 2.5), so it can elect a leader and commit writes.
Step 2The group of 2 has no majority. It cannot commit writes, and its nodes will keep trying and failing to be elected.
AnswerOnly the group of 3 serves writes. Two leaders cannot exist at the same time, because two majorities of 5 must share a node.
Check3 + 2 = 5, and a second majority would need at least 3 more nodes, which do not exist.
Why it mattersThis is how consensus avoids split brain: two parts both believing they lead and accepting conflicting writes.

Connection to the real job

Consensus runs under tools you use: etcd (Kubernetes' brain), ZooKeeper (older Kafka and Hadoop), Consul, and many databases. When Kubernetes becomes unavailable, often the reason is lost quorum in etcd.

Applications

  • Data Engineering: Kafka controller election, HBase master election (via coordination services).
  • MLOps: Kubernetes control plane stores cluster state with Raft.
  • Databases: distributed SQL stores replicate each partition with Raft or Paxos.
COMMON MISTAKE
Running an even number of nodes (such as 2 or 4) and believing it is safer. 2 nodes tolerate zero crashes, because the majority of 2 is 2.

Check yourself

  1. Why odd cluster sizes? Answer: An extra even node adds cost but no extra crash tolerance.
  2. What stops two leaders at once? Answer: Any two majorities share a node, and each node votes once per term.
  3. What is split brain? Answer: Two parts of the system each think they are the leader.

12.5 CAP and PACELC

INTUITION
Two bank branches share a ledger by phone. The phone line breaks. A customer asks branch A for a balance. Branch A can either refuse to answer until the line is fixed (safe but unavailable) or answer with what it knows (available but maybe wrong). It cannot do both. That is CAP.

CAP theorem: when a network partition happens, a system must choose between Consistency (every read sees the latest write or gets an error) and Availability (every request gets an answer, maybe old). Partitions are a fact of life, so the real choice is between C and A during a partition. Saying "pick any 2 of 3" is misleading, because you cannot choose to skip partition tolerance on a real network.

StyleDuring a partitionExample behaviour
CPrefuses some requests to stay correctconsensus stores, ledgers
APkeeps answering, merges latershopping cart, social feed, DNS

PACELC adds the normal times: if there is a Partition, choose A or C; Else (no partition), choose between Latency and Consistency. Even on a healthy network, waiting for many replicas (consistency) costs latency. That makes PACELC more useful day to day.

Real-world mapping

ItemExample valueWhere it appears
Strong readwait for the leader or a quorumbank balance, inventory count
Fast readlocal replica, may be stalerecommendation feed, analytics dashboard
Latency costextra cross-region round trip, often tens to hundreds of msmulti-region writes

Problem 12.5.2 Classify each as CP or AP behaviour: (a) a seat-booking system refuses to sell when it cannot reach the master; (b) a shopping cart accepts items on any replica and merges later.

CheckAsk: during a partition, does the system answer all requests? (a) no, (b) yes.

Connection to the real job

When you test a database that claims "high availability", ask what happens to reads and writes when a node is cut off. A practice drill with failure injection (switch off one node on purpose) shows which side of CAP it chose.

Applications

  • Data Engineering: Cassandra and DynamoDB are tunable (AP leaning); Spanner-like systems lean CP.
  • Data Analytics: dashboards accept stale data (AP); finance reports need correct data (CP).
  • GenAI: caches of embeddings can be stale without harm; usage billing cannot.
COMMON MISTAKE
Saying "we are CA" for a multi-node system. On a network that can partition, a distributed system cannot give up partition tolerance. CA is only meaningful for a single node.

Check yourself

  1. What do you choose between during a partition? Answer: Consistency and availability.
  2. What does the "ELC" in PACELC add? Answer: Without a partition you still trade latency against consistency.
  3. Is a shopping cart usually CP or AP? Answer: AP.

12.6 Retries, Timeouts, Idempotency and Backpressure

INTUITION
You call a restaurant to book a table and the line goes silent. Did they hear you? You call again. If the second call books another table, you now have two. Retrying is natural, but it is only safe if the booking is idempotent: doing it twice gives the same result as doing it once.

Words you need

WordPlain meaning
Timeouthow long you wait before you give up on a reply
Retrysend the same request again after a failure
Backoffwait longer between each retry
Jitteradd randomness to the wait so clients do not retry together
Idempotentrepeating the operation has no extra effect
Backpressurea full or slow system tells senders to slow down or stop
Retry stormmany retries make an overloaded system fall over

Retries

Retries fix short failures. If each call fails 30% of the time independently, then with at most 3 tries the failure chance is 0.3³ = 0.027, so success is 97.3%.

Predict, Run, Explain

Predict the success rate for 1, 2, 3 and 5 tries using 1 - 0.3^m. Then run:

import random
random.seed(7)
# retries: server fails 30% of calls
def call(p=0.3): return random.random()>p
def trial(max_try):
    for t in range(1,max_try+1):
        if call(): return True
    return False
for m in (1,2,3,5):
    ok=sum(trial(m) for _ in range(100000))
    print(f"max tries {m}: success {ok/1000:.1f}%   (theory {100*(1-0.3**m):.1f}%)")
# backoff with full jitter
def delays(n,base=0.1,cap=5):
    return [round(random.uniform(0,min(cap,base*2**i)),3) for i in range(n)]
print("full-jitter delays (s):",delays(6))
print("max possible per attempt:",[min(5,0.1*2**i) for i in range(6)])
# idempotency
class Bank:
    def __init__(s): s.bal=100; s.seen={}
    def pay(s,key,amt):
        if key in s.seen: return s.seen[key]
        s.bal-=amt; s.seen[key]="paid"; return "paid"
b=Bank()
for _ in range(3): b.pay("order-77",30)

Problem 12.6.1 A service fails 30% of calls. Each request is tried up to 3 times. How many calls on average reach the server per request?

Formulaexpected calls = 1 + q + q² where q = failure rate (second call happens if first fails, third if two fail)
Plug in1 + 0.3 + 0.3²
Compute1 + 0.3 + 0.09 = 1.39
AnswerOn average 1.39 calls per request: a 39% load increase.
CheckOur ch12f.py printed 1.39. If the server is fully down (q = 1), calls per request become 3, so retries triple the load.
Why it mattersRetries add load exactly when the server is weak. That is a retry storm. Backoff, jitter and a retry limit protect the server.

Timeouts

Without a timeout, a slow server holds your thread forever. Choose a timeout slightly above the normal worst case (for example, near p99 latency), not a huge round number. Every layer should have a shorter timeout than the layer above, or the outer caller gives up while the inner work continues.

Backpressure and Little's law

Little's law: the average number of requests inside a system L equals the arrival rate λ times the average time each spends inside W: L = λ x W. You can see it in a bank: customers arriving per minute x minutes each spends inside = customers in the bank right now. For a service, throughput x time per request = requests in flight.

Problem 12.6.2 A service handles 200 requests per second, each taking 0.05 s inside. How many requests are in flight on average, and what is the maximum throughput of a pool of 10 threads?

FormulaL = λ x W, and max throughput = threads / W
Plug inL = 200 x 0.05, and 10 / 0.05
ComputeL = 10, and 10 / 0.05 = 200 per second
AnswerAbout 10 requests are in flight, and 10 threads can do at most 200 requests per second. At 200 per second the pool is at its limit.
Checkch12f.py printed 10.0 and 200.0. If arrivals reach 220 per second, the queue grows by 20 each second without limit.
Why it mattersAt the limit, tiny rises in load cause huge waiting. This is the knee in a waiting-time graph: a bank is calm at 80% busy and chaotic at 99% busy.

Now we compare an unbounded queue with a bounded one when arrivals (120 per second) beat service (100 per second). Predict: what happens after 10 seconds in each case?

# backpressure: bounded queue vs unbounded. arrivals 120/s, service 100/s, 10 s
def sim(limit):
    q=0;drop=0;lat=[]
    for sec in range(10):
        for _ in range(120):
            if limit is not None and q>=limit: drop+=1
            else: q+=1
        done=min(q,100); q-=done
    return q,drop
for lim in (None,50):
    q,d=sim(lim)
    print(f"limit={lim}: queue left={q}, rejected={d}, wait for last queued = {q/100:.2f}s")
# Little's law: L = lambda * W
lam=100; W=0.2
print("Little's law: throughput 100/s x 0.2s latency =",lam*W,"requests in flight")

Real output:

limit=None: queue left=200, rejected=0, wait for last queued = 2.00s
limit=50: queue left=0, rejected=700, wait for last queued = 0.00s
Little's law: throughput 100/s x 0.2s latency = 20.0 requests in flight

Line by line: each second, 120 requests arrive and the system serves up to 100. With no limit, 20 extra requests pile up each second: after 10 seconds, 200 are waiting, and the last one waits 2 seconds, and it keeps growing. With a limit of 50, the queue fills to 50, the rest are rejected right away (70 per second, 700 in total), and every second the server clears the queue. Waiting stays short, but some users get an error. That is backpressure: be honest and fast about saying no, rather than slow for everyone. In a real system the rejected client should back off (return HTTP 429 or 503).

Connection to the real job

In a real service, a rising error rate with falling throughput after a peak is often a retry storm or missing backpressure. Good teams rehearse an overload beyond capacity (tools such as Locust or k6 can simulate it) to check that the system fails gracefully. In data pipelines, Kafka consumers apply backpressure by pausing when downstream is slow.

Applications

  • Data Engineering: idempotent writes (upserts with a key) so a re-run of a failed job does not duplicate rows.
  • MLOps: model servers with bounded request queues and timeouts.
  • Payments and orders: idempotency keys on every POST.
COMMON MISTAKE
Retrying instantly in a tight loop, or retrying non-idempotent actions. Always use backoff with jitter, a retry cap, and idempotency keys for actions that change data.

Chapter recap

  • A distributed system uses many computers over a network, for scale, availability and low latency.
  • The key difficulty is partial failure: silence can mean crash, loss or slowness.
  • Replication copies data. Partitioning splits data. Big systems do both.
  • Quorum rule: with N replicas, W + R > N gives reads that overlap the latest write.
  • Consistent hashing moves only about 1/N of keys when a node is added. Mod N moves most of them (795 of 1,000 in our run).
  • Consensus (Raft, Paxos) needs a majority. Use odd cluster sizes. Majority prevents split brain.
  • CAP: during a partition choose consistency or availability. PACELC: otherwise choose latency or consistency.
  • Retry only with timeouts, backoff and jitter. Make writes idempotent with keys.
  • Backpressure protects a system: a bounded queue and fast rejection beat an unlimited queue.
  • Little's law (L = λ x W) links throughput, latency and concurrency.

Practice set

Problem 12.7.1 (easy) How many nodes must be up in a 9-node Raft cluster to commit writes?

Answer: 5, because a majority of 9 is 5 (more than 4.5).

Problem 12.7.2 (easy) N = 3, W = 1, R = 3. Do reads always see the latest write?

Answer: Yes, W + R = 4 > 3. Reads query all nodes, so they always meet the written node. Writes are fast but a write on one node can be lost if that node dies before copying.

Problem 12.7.3 (what is the output) In our simulation, what happens to the balance if the same payment is sent 3 times with the same idempotency key, starting at 100 with amount 30?

Answer: 70. Only the first request changes the balance. (Real output from the run above.)

Problem 12.7.4 (computation) Three nodes, each up 99.9% of the time, independent. The service needs at least 2 up. Availability?

Answer: 3 x 0.999² x 0.001 + 0.999³ = 0.002994 + 0.997003 = 0.999997 (about 99.9997%). Quick check by computing: 3 x 0.998001 x 0.001 = 0.002994003; 0.999³ = 0.997002999; sum = 0.999997002.

Problem 12.7.5 (computation) 1,000 req/s arrive, each takes 80 ms. How many concurrent requests are in the system? What if latency doubles to 160 ms?

Answer: L = 1,000 x 0.08 = 80, and with 0.16 s it becomes 160. Double latency, double concurrency, so connection pools must grow or requests wait.

Problem 12.7.6 (find the bug) A client retries a failed "create order" call up to 5 times, instantly, with no key. The customer is charged 3 times. What went wrong and how do you fix it?

Answer: The first calls succeeded on the server but replies were lost, so retries created new orders. Add an idempotency key per order (the server remembers it), use backoff with jitter, and set a retry limit.

Problem 12.7.7 (find the bug) A team shards data by order_date. One day the cluster slows down although most nodes are idle. Why?

Answer: Today's date is one key, so all new writes go to one partition (hot spot). Shard by a high-cardinality key such as order_id, or hash it.

Problem 12.7.8 (scenario) You add a node to a 10-node cache that uses hash mod N. What do you expect, and what is the better design?

Answer: About 10/11 = 91% of keys move (a key stays only when h mod 10 = h mod 11, which is 10 of every 110 residues, about 9%). The cache goes almost cold and the database is hit hard. Use consistent hashing so about 1/11 = 9% of keys move.

Problem 12.7.9 (interview) Explain CAP in two sentences to a manager.

Answer: When the network between our servers breaks, we must choose: refuse some requests to stay correct, or answer and risk old data. Our product decides which is worse (for example, wrong balance versus a stale feed).

Problem 12.7.10 (interview) Your service is slow; CPU is at 30% but latency is climbing under load, and clients retry. Give a plan.

Answer: Check queue length and thread pool use (Little's law: L = λ x W), find the slow dependency, add timeouts shorter than the caller's, add backoff with jitter and retry caps, and add a bounded queue with fast rejection. Re-test with load beyond the capacity point to confirm graceful failure.
