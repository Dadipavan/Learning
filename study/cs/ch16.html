16.1 Project: Mini Key-Value Store with Persistence

INTUITION
Think of a shop ledger where you never erase anything. You only write new lines at the bottom: "order 1: 3 pens", then later "order 1: 5 pens". To know the current value you read from the bottom. To find things fast you keep a small index card with "order 1 is on line 3 of the ledger". When the ledger gets very long, you copy only the current entries into a fresh ledger and throw the old one away. That is an append-only log with an index and compaction.

Goal and why employers care

Build a store with put, get and delete that survives a restart and a half-written last line. It uses a hash map in memory for speed and an append-only file on disk for safety, with compaction to reclaim space. Employers care because this design (a log plus an in-memory index) appears inside real databases and message systems, and explaining it shows you understand durability, not only syntax.

Skills used

Chapter 7, Complexity, Arrays, Strings, Hashing and Sorting (hash map, O(1) average lookup); Chapter 5, Operating Systems for People Who Test Performance (files, file offsets, fsync, atomic rename); Chapter 12, Distributed Systems Fundamentals (logs and recovery by replay).

Data

None needed. The demo uses shop orders such as order:1 with a value like {"item": "pen", "qty": 3}, plus one hot key overwritten 1,000 times so compaction has something to remove.

 put(k, v)  -> append one JSON line to the file -> index[k] = byte offset
 get(k)     -> offset = index[k] -> seek there -> read ONE line
 delete(k)  -> append a "del" marker (a tombstone) -> remove k from index
 start up   -> read the file top to bottom, rebuild index (last record wins)
 compact()  -> write live keys to a new file -> atomically replace the old file

 disk file:  {"k":"order:1","v":{...}}\n  {"k":"order:2",...}\n  {"k":"order:1",...}\n  {"k":"order:2","del":1}\n
 memory:     index = {"order:1": 70}      (byte position of the newest line)

A tombstone is a record that means "this key was deleted". We cannot erase a line in an append-only file, so we add a note that cancels it.

Step-by-step build

  1. The class and the replay. The constructor opens the file, then _rebuild reads each line, remembers its starting byte (offset), and updates the index. A deleted key is removed from the index. A line that is not valid JSON is a half-written line from a crash, so we stop there and cut it off.
import json, os

class KV:
    def __init__(self, path):
        self.path, self.index = path, {}
        open(path, "ab").close()          # make sure the file exists
        self._rebuild()
        self.f = open(path, "ab")

    def _rebuild(self):
        with open(self.path, "rb") as f:
            offset = 0
            for raw in f:
                try:
                    rec = json.loads(raw)
                except ValueError:        # half-written last line after a crash
                    break
                if rec.get("del"): self.index.pop(rec["k"], None)
                else:              self.index[rec["k"]] = offset
                offset += len(raw)
        if offset < os.path.getsize(self.path):
            with open(self.path, "r+b") as f: f.truncate(offset)
  1. Writes. _append writes one line, flushes Python's buffer, and calls os.fsync to ask the operating system to put it on disk. It returns the offset where the line began.
    def _append(self, rec):
        pos = self.f.tell()
        self.f.write((json.dumps(rec) + "\n").encode()); self.f.flush(); os.fsync(self.f.fileno())
        return pos

    def put(self, k, v):  self.index[k] = self._append({"k": k, "v": v})
    def delete(self, k):
        if k in self.index: self._append({"k": k, "del": 1}); del self.index[k]
  1. Reads. One dictionary lookup, one seek, one readline.
    def get(self, k, default=None):
        if k not in self.index: return default
        with open(self.path, "rb") as f:
            f.seek(self.index[k]); return json.loads(f.readline())["v"]
  1. Compaction. Write only the live keys to shop.db.tmp, flush it to disk, then os.replace swaps it over the old file in one step. If the program dies halfway, the old file is still complete.
    def compact(self):
        tmp = self.path + ".tmp"; new_index = {}
        with open(tmp, "wb") as out:
            for k in self.index:
                pos = out.tell()
                out.write((json.dumps({"k": k, "v": self.get(k)}) + "\n").encode())
                new_index[k] = pos
            out.flush(); os.fsync(out.fileno())
        self.f.close(); os.replace(tmp, self.path)
        self.index = new_index; self.f = open(self.path, "ab")

    def size(self): return os.path.getsize(self.path)
    def close(self): self.f.close()
  1. Predict, then run the demo. Before you run it: after one update and one delete, how many lines are in the file, and how many keys are alive? (Four lines, one key.)

Evaluation and acceptance criteria

  • A deleted key stays deleted after restart.
  • The last write wins after restart, and get for a missing key returns the default.
  • Compaction keeps every live key with the same value and leaves exactly one line per live key.
  • A torn last line never stops start-up and never causes a later write to be lost.
  • Your README shows the file size before and after compaction (here 23,065 to 72 bytes).

Common pitfalls

  1. Forgetting tombstones. The deleted key comes back after restart. Detect: delete, close, reopen, get.
  2. Using character counts as offsets. Offsets must be bytes. We open the file in binary mode and use len(raw) of bytes. Detect: non-ASCII values (for example "café") make get read the wrong place.
  3. Compacting in place. A crash halfway destroys data. Always write a new file and os.replace. Detect: kill the program during compaction in a test.
  4. No flush or fsync. The program says "saved", but a power cut loses the data. Detect: read the file from another process right after put. Note that fsync costs time, a real trade-off between safety and speed.
  5. Updating the index before the write succeeds. If the write fails, memory says the key exists but the disk does not. Our put sets the index only after _append returns. Detect: force a write error in a test and check get.

Three extensions

  1. Run compaction automatically when the file is more than 3 times the size of the live data.
  2. Add a checksum (for example zlib.crc32) to each line so a damaged line in the middle is detected, not only at the end.
  3. Add a simple TCP or command-line front end (set k v, get k) and a second reader process.

Interview talking points

Q1. Why is an append-only file a good idea? Appending is simple and safe: old data is never overwritten, so a crash cannot damage earlier records. Sequential writes are also fast on most disks. The cost is that the file grows, so I need compaction.

Q2. Why keep the index in memory? Without it, get would scan the whole file, O(n). With the hash map of offsets, get is one lookup plus one seek, O(1) on average. The limit is that all keys must fit in memory, while values stay on disk.

Q3. What happens if the program crashes during a write? The last line may be half-written. On start-up I replay the log, stop at the first line that is not valid, and truncate it. Lines I had already confirmed with fsync are safe. A checksum per line would make this stronger.

16.2 Project: Graph-Based Route Planner

INTUITION
On a map, "fewest turns" and "shortest time" are different questions. A road with three small streets might be faster than one with a long, slow road. BFS (breadth-first search) counts stops. Dijkstra's algorithm adds up the minutes. This project builds both on a small city and shows them giving different answers.

Goal and why employers care

Build a planner that stores a city map as a graph, finds the route with the fewest stops (BFS) and the route with the least travel time (Dijkstra), and handles places that cannot be reached. Graphs are everywhere in data work: dependency tasks, delivery routes, networks, recommendation links. A tested, correct implementation shows you can pick the right algorithm for the question.

Skills used

Chapter 10, Trees and Graphs (adjacency lists, BFS); Chapter 9, Linked Lists, Stacks, Queues, Heaps and Top-K (queue with deque, min-heap with heapq); Chapter 14, Interview Patterns Bank (shortest path pattern); Chapter 7, Complexity, Arrays, Strings, Hashing and Sorting (dictionaries, Big-O).

            |                             |

     fewest stops                  least minutes, needs non-negative weights
            |                             |
            +--- prev map --> walk back from goal --> route

The prev map records, for each place, the place we came from. Walking back from the goal through prev and reversing gives the route.

Step-by-step build

  1. Build the graph. An adjacency list is a dictionary from each place to its neighbours and the minutes to reach them. Since roads are two-way we add both directions.
  2. BFS. Visit places in rings: all places one stop away, then two stops. It uses a queue (first in, first out). The first time we reach the goal is with the fewest stops.
  3. Dijkstra. Always expand the place with the smallest known total minutes, using a min-heap. The line if d > dist[u]: continue skips outdated heap entries (a place can be pushed twice when a better route is found later).
  4. Code, all together:
import heapq
from collections import deque

ROADS = [("Depot","Market",4), ("Depot","Station",2), ("Station","Market",1),
         ("Market","School",5), ("Station","Hospital",8), ("School","Hospital",3),
         ("Hospital","Park",2), ("School","Park",6), ("Island","Lake",2)]

def build(roads):
    g = {}
    for a, b, w in roads:
        g.setdefault(a, []).append((b, w)); g.setdefault(b, []).append((a, w))
    return g

def bfs(g, start, goal):
    prev, q = {start: None}, deque([start])
    while q:
        u = q.popleft()
        if u == goal: break
        for v, _ in g[u]:
            if v not in prev: prev[v] = u; q.append(v)
    return path(prev, goal)

def dijkstra(g, start, goal):
    dist, prev, heap = {start: 0}, {start: None}, [(0, start)]
    while heap:
        d, u = heapq.heappop(heap)
        if d > dist[u]: continue          # stale entry
        if u == goal: break
        for v, w in g[u]:
            nd = d + w
            if nd < dist.get(v, float("inf")):
                dist[v] = nd; prev[v] = u; heapq.heappush(heap, (nd, v))
    p = path(prev, goal)
    return (p, dist[goal]) if p else (None, None)

def path(prev, goal):
    if goal not in prev: return None
    out = []
    while goal is not None: out.append(goal); goal = prev[goal]
    return out[::-1]

def minutes(g, p):
    return sum(w for a, b in zip(p, p[1:]) for n, w in g[a] if n == b)
  1. Predict, then compare. From Depot to School, which route has fewer stops, and which is faster? The direct-looking Depot > Market > School has 2 stops and takes 4 + 5 = 9 minutes. The route Depot > Station > Market > School has 3 stops and takes 2 + 1 + 5 = 8 minutes. Run it:
g = build(ROADS)
p = bfs(g, "Depot", "School");      print("BFS     :", " > ".join(p), "| stops:", len(p)-1, "| minutes:", minutes(g, p))
p, m = dijkstra(g, "Depot", "School"); print("Dijkstra:", " > ".join(p), "| stops:", len(p)-1, "| minutes:", m)
print("Depot -> Park :", dijkstra(g, "Depot", "Park"))
print("Depot -> Lake :", bfs(g, "Depot", "Lake"), dijkstra(g, "Depot", "Lake"))

  1. Verify with brute force. A slow, obviously-correct method tries every simple path (no repeated place) and takes the smallest total. It is a good test for a clever algorithm.
def all_paths(u, goal, seen):
    if u == goal: yield [u]; return
    for v, _ in g[u]:
        if v not in seen:
            for rest in all_paths(v, goal, seen | {v}): yield [u] + rest
best = min(minutes(g, q) for q in all_paths("Depot", "School", {"Depot"}))
print("brute-force best Depot -> School:", best)

Real output: brute-force best Depot -> School: 8, which matches Dijkstra. Check Depot to Park by hand: Depot > Station (2) > Hospital (8) > Park (2) = 12. The alternative through Market and School is 2 + 1 + 5 + 6 = 14. So 12 is right.

Evaluation and acceptance criteria

  • BFS returns the fewest stops and Dijkstra the fewest minutes; on the Depot-to-School query they differ (2 stops with 9 minutes versus 3 stops with 8 minutes).
  • Dijkstra matches the brute-force minimum on every pair of places on the small map (write a loop over all pairs).
  • An unreachable place returns None, not a crash or an endless loop.
  • Start equal to goal returns a one-place route with 0 minutes.
  • Complexity is written in the README: BFS is O(V + E); Dijkstra with a heap is O((V + E) log V), where V is places and E is roads.

Common pitfalls

  1. Using BFS for weighted roads. It gives the fewest stops, not the fewest minutes. Detect: compare with brute force on a weighted query (like Depot to School above).
  2. Marking places as visited too late in BFS. The same place enters the queue many times and the work explodes. Detect: count queue pushes in a test.
  3. Negative road times with Dijkstra. The algorithm assumes that adding a road never makes a trip shorter. Detect: reject negative weights when you build the graph. For negative weights you need a different algorithm.
  4. Forgetting the reverse road. The route works one way only. Detect: assert that A to B and B to A have equal minutes on a two-way map.
  5. No stale-entry check in the heap loop. Results are still right but work is wasted. Detect: count how many times each place is expanded.

Three extensions

  1. Add one-way streets and road closures, and show how the best route changes.
  2. Implement A* with a straight-line distance guess, and compare the number of places expanded against Dijkstra.
  3. Read the map from a CSV file and print the route with a minute-by-minute timetable.

Interview talking points

Q1. BFS or Dijkstra? If every road counts the same, such as fewest stops or fewest clicks, BFS is enough and simpler. If roads have different costs, such as minutes, I use Dijkstra. In my city map they gave different routes to the School, 9 minutes against 8.

Q2. Why does Dijkstra use a heap? At each step I need the place with the smallest total so far. Scanning all places takes O(V) every time, but a min-heap gives it in O(log V). With many places this is the difference between slow and fast.

Q3. How did you know your answer was right? I compared it with a brute-force search that tries every path on the small map, and I checked one answer by hand: Depot to Park is 2 + 8 + 2 = 12. For big maps brute force is too slow, so I would keep the small-map tests as a regression check.

Chapter recap

  • A key-value store can be a hash map of byte offsets plus an append-only file.
  • Replay the log at start-up: the last record for a key wins, a tombstone means deleted.
  • Compact by writing live keys to a new file and swapping it in with os.replace.
  • A half-written last line is expected after a crash; skip and truncate it.
  • fsync buys safety at a cost in speed. State this trade-off in the README.
  • BFS finds fewest stops, Dijkstra finds least cost (non-negative weights only).
  • Always check a clever algorithm against a slow, obviously-correct one on small data.
  • Handle the unreachable case and the start-equals-goal case explicitly.

Practice set

Problem 16.1 (easy) You write put("a",1), put("a",2), delete("a"), put("b",3). How many lines are in the log, and how many are alive after replay?

Answer: Four lines: put a, put a, delete a (a tombstone), put b. After replay only b is alive, so one live key.

Problem 16.2 (easy) Why must offsets in the index be byte positions?

Answer: seek moves by bytes. If a value contains a non-ASCII character, one character can be several bytes, so a character count would point to the wrong place.

Problem 16.3 (what is the output) With the 16.1 demo, the hot key was written 1,000 times and the file was 23,065 bytes before compaction and 72 after. What percent was removed?

Answer: (23,065 − 72) / 23,065 = 22,993 / 23,065 = 0.9969, about 99.7%.

Problem 16.4 (find the bug) A teammate's compact opens the live file with mode "wb" and writes live keys into it. What can go wrong?

Answer: Opening with "wb" empties the file at once. If the program crashes before all keys are written, data is lost. Write to a temporary file and os.replace it over the original.

Problem 16.5 On the city map, what is the total time of Depot > Station > Hospital?

Answer: 2 + 8 = 10 minutes.

Problem 16.6 On the city map, why does dijkstra(g, "Depot", "Lake") return (None, None)?

Answer: Lake is connected only to Island, and Island is not connected to the rest, so there is no route. The code finds no entry for Lake in prev and returns None.

Problem 16.7 (interview) Your store has 10 million keys. What limits it and what would you change?

Answer: The in-memory index must hold every key and its offset, so memory is the limit. Options: store the index on disk (for example in sorted segment files with a sparse index), or shard keys across several stores by hash. I have not built this here.

Problem 16.8 (interview) Explain why Dijkstra fails with a road of -5 minutes.

Answer: Dijkstra fixes the best answer for the nearest place as final, assuming later roads only add time. A negative road can make a later route cheaper, so a "final" answer would be wrong. On a two-way road, a negative time would also let you loop forever to reduce time. Use an algorithm made for negative weights, and check the graph has no negative cycle.
