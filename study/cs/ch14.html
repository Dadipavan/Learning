14.1 How to Approach an Interview Problem

BASIC EXPLANATION
An interview problem is solved by a fixed process: restate the problem, ask about constraints, work through examples, propose a method, code it, test it and state the complexity.
INTUITION
Think of opening a restaurant. You do not start with random choices. You first ask: what is the goal, how many customers will come, what will slow the kitchen down? An interview problem is the same. First understand the target, then pick a known pattern, then build.

Words you need. Big-O describes how the work grows when the input size n grows: O(n) means double the input, double the work; O(n²) means double the input, four times the work; O(log n) means doubling the input adds only one extra step. Time complexity counts steps, space complexity counts extra memory. A brute force solution tries everything and is simple but slow.

There are only about ten patterns behind most interview problems. Once you learn to recognize the pattern from the words of the problem, the code is short.

The 6-step routine

  1. Restate the problem in your own words. Ask about input size, duplicates, negative numbers, empty input, and sorted or not.
  2. Do a tiny example by hand. Use 4 to 6 items. Write the expected answer.
  3. Say the brute force and its cost. Even a slow answer shows you understand.
  4. Spot the pattern using the table below, and improve the brute force.
  5. Code it, speaking while you write. Use clear variable names.
  6. Test with your example, then edge cases (empty, one item, all same, negative). State time and space.

14.2 Hashing Patterns

BASIC EXPLANATION
Hashing patterns use a hash map or set for fast lookup. Common uses are counting items, finding duplicates, grouping items and storing values already seen.
INTUITION
A hash map is a coat-check room. You hand over a key and get your item back in one step, with no searching through the whole room. Whenever the brute force "looks again through the list", a hash map may replace the search.

A dictionary or set in Python gives average O(1) insert and lookup. Counter is a dictionary that counts. defaultdict(list) makes groups.

Problem 14.2.1 (Problem 1: Two Sum) Given [2, 7, 11, 15] and target 9, return the two indexes whose values add to 9.

PredictBefore you run it, think: what should the answer be for this input? Work it by hand on the tiny example.
Step 1Idea (the pattern): For each number x, ask: have I already seen target - x? A dictionary answers in O(1). One pass.
Step 2Code and run (tests passed with assert):
def two_sum(nums, target):
    seen = {}                      # value -> index
    for i, x in enumerate(nums):
        if target - x in seen:
            return [seen[target - x], i]
        seen[x] = i
    return []
r1 = two_sum([2, 7, 11, 15], 9); assert r1 == [0, 1]
print("P1 two_sum ->", r1)

Problem 14.2.3 (Problem 3: Longest Consecutive Sequence) Find the longest run of consecutive integers in an unsorted list [100, 4, 200, 1, 3, 2] (answer 1,2,3,4).

PredictBefore you run it, think: what should the answer be for this input? Work it by hand on the tiny example.
Step 1Idea (the pattern): Put numbers in a set. Only start counting from a number whose predecessor is missing. Each number is visited at most twice.
Step 2Code and run (tests passed with assert):
def longest_consecutive(nums):
    s, best = set(nums), 0
    for x in s:
        if x - 1 not in s:         # x starts a run
            y = x
            while y + 1 in s:
                y += 1
            best = max(best, y - x + 1)
    return best

Problem 14.2.4 (Problem 4: Subarray Sum Equals K) Count the contiguous subarrays of [1, 2, 3, -3, 3] that add to 3.

Step 2Code and run (tests passed with assert):
def subarray_sum_k(nums, k):
    count, prefix, seen = 0, 0, Counter({0: 1})
    for x in nums:
        prefix += x
        count += seen[prefix - k]
        seen[prefix] += 1
    return count

14.3 Two Pointers, Sliding Window, Prefix Sums and Kadane

BASIC EXPLANATION
Two pointers and sliding window move indexes along an array in one pass. Prefix sums store running totals for range sums, and Kadane's algorithm finds the best contiguous subarray sum.
INTUITION
Imagine reading a long log file with two fingers. You move them in a smart way so that each finger passes each line only once. Brute force would restart from the beginning for each pair of positions.

Two pointers work when moving a pointer has a clear reason (sorted data, or the limiting side). Sliding window works for contiguous pieces: grow the right side, shrink the left side when a rule breaks. Prefix sums and Kadane turn "sum of a piece" into a running total.

Problem 14.3.1 (Problem 5: Container With Most Water) Heights [1,8,6,2,5,4,8,3,7]: choose two bars to hold the most water (width times the shorter height).

PredictBefore you run it, think: what should the answer be for this input? Work it by hand on the tiny example.
Step 1Idea (the pattern): Two pointers at both ends. The shorter bar limits the area, so moving the taller one can never help. Move the shorter one.
Step 2Code and run (tests passed with assert):
def max_area(h):
    l, r, best = 0, len(h) - 1, 0
    while l < r:
        best = max(best, min(h[l], h[r]) * (r - l))
        if h[l] < h[r]: l += 1
        else: r -= 1
    return best

Problem 14.3.2 (Problem 6: 3Sum) Find all unique triples in [-1, 0, 1, 2, -1, -4] that sum to 0.

def three_sum(nums):
    nums.sort(); out = []
    for i in range(len(nums) - 2):
        if i and nums[i] == nums[i - 1]: continue
        l, r = i + 1, len(nums) - 1
        while l < r:
            s = nums[i] + nums[l] + nums[r]
            if s < 0: l += 1
            elif s > 0: r -= 1
            else:
                out.append([nums[i], nums[l], nums[r]]); l += 1
                while l < r and nums[l] == nums[l - 1]: l += 1
    return out

14.4 Binary Search Patterns

BASIC EXPLANATION
Binary search repeatedly halves a sorted range to find a value in O(log n). The same idea applies to finding a boundary or the smallest answer that satisfies a condition.
INTUITION
Guessing a number from 1 to 1000 with "higher or lower" hints takes only 10 guesses if you always guess the middle. Each answer throws away half the possibilities.

Binary search needs a monotone idea: a property that is false, false, ..., then true, true, true. The array may be sorted, or rotated (Problem 11), or it may be an imaginary range of answers (Problem 12, "search on the answer").

Problem 14.4.1 (Problem 11: Search in Rotated Sorted Array) Find 0 in [4,5,6,7,0,1,2].

PredictBefore you run it, think: what should the answer be for this input? Work it by hand on the tiny example.
Step 1Idea (the pattern): One half is always sorted. Check whether the target lies in the sorted half, and discard the other half.
Step 2Code and run (tests passed with assert):
def search_rotated(nums, target):
    lo, hi = 0, len(nums) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if nums[mid] == target: return mid
        if nums[lo] <= nums[mid]:                 # left half sorted
            if nums[lo] <= target < nums[mid]: hi = mid - 1
            else: lo = mid + 1
        else:                                     # right half sorted
            if nums[mid] < target <= nums[hi]: lo = mid + 1
            else: hi = mid - 1
    return -1
r11 = search_rotated([4, 5, 6, 7, 0, 1, 2], 0); assert r11 == 4
assert search_rotated([4, 5, 6, 7, 0, 1, 2], 3) == -1
print("P11 search_rotated ->", r11)
  • Step 3 Complexity: Time O(log n), space O(1).
  • Answer Real output of the run above: 4

Problem 14.4.2 (Problem 12: Koko Eating Bananas (search on the answer)) Piles [3,6,7,11], 8 hours. Find the smallest speed (bananas per hour) that finishes in time.

def min_eating_speed(piles, hours):
    lo, hi = 1, max(piles)
    while lo < hi:
        mid = (lo + hi) // 2
        if sum(ceil(p / mid) for p in piles) <= hours: hi = mid
        else: lo = mid + 1
    return lo

14.5 Stacks, Queues, Heaps and Linked Lists

BASIC EXPLANATION
A stack is last-in first-out, a queue is first-in first-out, a heap gives the smallest or largest item first, and a linked list is a chain of nodes. This section lists the standard interview patterns for each.
INTUITION
A stack is a pile of plates (last in, first out). A queue is a line at a ticket counter (first in, first out). A heap is a waiting room where the most urgent person is always at the front, no matter who arrived first.
  • Stack: Python list with append and pop.
  • Queue and deque: collections.deque, with O(1) at both ends. Do not use list.pop(0), which is O(n).
  • Monotonic stack or deque: keep values in order, popping those that can never be an answer.
  • Heap: heapq gives a min-heap. Push and pop cost O(log n). heapq.nlargest(k, ...) finds top-K.

Problem 14.5.1 (Problem 13: Valid Parentheses) Check that brackets in {[()]} are balanced and properly nested.

14.6 Trees and Graphs

BASIC EXPLANATION
A tree is a connected structure of nodes with no cycles, and a graph is a more general set of nodes and edges. Standard problems use traversals (DFS and BFS), shortest paths and connected components.
INTUITION
A tree is a company chart. A graph is a road map. Both ask: "how do I visit everything, or find the shortest route, without going around in circles?" The answer is to remember where you have been.
  • BFS (queue): visits level by level, finds the fewest steps in unweighted graphs.
  • DFS (recursion or stack): goes deep first. Good for components, cycles, and paths.
  • Topological sort: order of tasks with dependencies (a DAG, a directed acyclic graph).
  • Dijkstra: shortest paths with non-negative weights, using a min-heap.
  • Union-Find: groups items into sets; merge and ask "same group?" in near-constant time.

14.7 Backtracking, Dynamic Programming and Greedy

BASIC EXPLANATION
Backtracking tries all choices and undoes them, dynamic programming stores answers to overlapping subproblems, and greedy makes the best local choice at each step. This section shows how to recognise and apply each approach.
INTUITION
Backtracking is exploring a maze: try a path, hit a wall, step back, try another. Dynamic programming is the same maze, but you write on the wall "from here the best exit costs 7" so you never recompute. Greedy is picking the best-looking step each time, which works only when a proof says it is safe.
  • Backtracking: choose, explore, un-choose. Prune bad branches early.
  • Dynamic programming (DP): define the state in words ("dp[a] is the fewest coins for amount a"), write the transition, set the base case, choose the order.
  • Greedy: sort, then make a locally best choice. If you cannot argue why it is safe, suspect DP.

Problem 14.9.1 (Fenwick) For each element of [5, 2, 6, 1], count how many elements to its right are smaller. Expected: [2, 1, 1, 0].

Plain approachFor each i, scan everything to its right: O(n2). For n = 100,000 that is 5 billion steps: too slow.
IdeaWalk from right to left. A Fenwick tree stores how many values have been seen at each rank (position in sorted order). For value x, count seen values with rank below x's rank.
RanksSorted unique values 1, 2, 5, 6 give ranks 1, 2, 3, 4. So 5 is rank 3, 2 is rank 2, 6 is rank 4, 1 is rank 1.
TraceValue 1 (rank 1): prefix(0) = 0, add rank 1. Value 6 (rank 4): prefix(3) = 1 (the 1), add rank 4. Value 2 (rank 2): prefix(1) = 1, add rank 2. Value 5 (rank 3): prefix(2) = 2 (the 1 and the 2).
AnswerCollected right to left: 0, 1, 1, 2, reversed: [2, 1, 1, 0].
def count_smaller_right(a):
    rank = {v: i + 1 for i, v in enumerate(sorted(set(a)))}
    n = len(rank); t = [0] * (n + 1)
    def add(i):
        while i <= n: t[i] += 1; i += i & -i
    def prefix(i):
        s = 0
        while i > 0: s += t[i]; i -= i & -i
        return s
    out = []
    for x in reversed(a):
        out.append(prefix(rank[x] - 1))      # seen values with a smaller rank
        add(rank[x])
    return out[::-1]

def brute(a): return [sum(1 for y in a[i + 1:] if y < a[i]) for i in range(len(a))]

Problem 14.9.2 (Bellman-Ford with a limit) Four cities, flights (from, to, price): (0,1,100), (1,2,100), (2,0,100), (1,3,600), (2,3,200). Cheapest price from 0 to 3 with at most k stops in between.

Key ideaBellman-Ford pass number p lets a path use at most p edges. "At most k stops" means at most k + 1 edges, so run exactly k + 1 passes.
TrapIn each pass, read from a copy of the previous pass, otherwise one pass can chain several edges and ignore the limit.
k = 1 by handTwo edges allowed. Direct routes: 0→1→3 = 100 + 600 = 700. The cheaper route 0→1→2→3 = 400 needs 3 edges (2 stops).
k = 2 by handNow 0→1→2→3 = 100 + 100 + 200 = 400 is allowed.
def cheapest(n, flights, src, dst, k):
    INF = float("inf"); dist = [INF] * n; dist[src] = 0
    for _ in range(k + 1):
        prev = dist[:]                        # read from last pass only
        for u, v, w in flights:
            if prev[u] + w < dist[v]: dist[v] = prev[u] + w
    return dist[dst] if dist[dst] < INF else -1

Problem 14.9.3 (Two-colouring) Split n people into two groups so that nobody is with someone they dislike. Pairs: (1,2), (1,3), (2,4), then separately (1,2), (1,3), (2,3).

IdeaEach dislike is an edge. Two groups means bipartite (10.10).

from collections import deque
def possible_bipartition(n, dislikes):
    g = {i: [] for i in range(1, n + 1)}
    for a, b in dislikes: g[a].append(b); g[b].append(a)
    color = {}
    for s in g:
        if s in color: continue
        color[s] = 0; q = deque([s])
        while q:
            u = q.popleft()
            for v in g[u]:
                if v not in color: color[v] = 1 - color[u]; q.append(v)
                elif color[v] == color[u]: return False
    return True

A design-class (or "low-level design") question asks for a small working component with a clear interface and stated costs, not a diagram of ten servers. The standard routine: confirm the interface, state the operations and their target costs, pick the data structures, write it, then test the edge cases out loud. LRU cache

An LRU (least recently used) cache holds at most capacity items. get returns a value and marks it most recent. put inserts or updates and, if full, evicts the item that has gone unused the longest. Both must be O(1). A map alone cannot tell which item is oldest; a list alone cannot find a key fast. Together: the map finds the node, the doubly linked list orders the nodes, and moving a node to the front takes O(1) because you hold its neighbours.

How to read it: the blue arrows are the dictionary. The orange chain is the order of use, newest next to head, oldest next to tail. A get(A) unlinks A and re-links it right after head. A put into a full cache removes the node just before tail and also deletes its key from the map. The two sentinel nodes (head and tail) remove all the "is this the first or last node?" special cases.

class Node:
    __slots__ = ("key", "val", "prev", "next")
    def __init__(self, key=0, val=0): self.key, self.val, self.prev, self.next = key, val, None, None

class LRUCache:
    def __init__(self, capacity):
        self.cap = capacity; self.map = {}
        self.head, self.tail = Node(), Node()           # sentinels
        self.head.next, self.tail.prev = self.tail, self.head
    def _unlink(self, n): n.prev.next, n.next.prev = n.next, n.prev
    def _push_front(self, n):
        n.next, n.prev = self.head.next, self.head
        self.head.next.prev = n; self.head.next = n
    def get(self, key):
        if key not in self.map: return -1
        n = self.map[key]; self._unlink(n); self._push_front(n)
        return n.val
    def put(self, key, val):
        if key in self.map:
            n = self.map[key]; n.val = val; self._unlink(n); self._push_front(n); return
        if len(self.map) == self.cap:
            old = self.tail.prev; self._unlink(old); del self.map[old.key]
        n = Node(key, val); self.map[key] = n; self._push_front(n)

Rate limiter (token bucket)

A rate limiter allows at most some number of requests over time. In a token bucket of capacity C and refill rate r tokens per second, each request takes one token; if none is left it is refused. The bucket refills continuously but never above C. This allows a short burst of up to C requests and then a steady r per second. Instead of a background thread, compute the refill lazily from the elapsed time at each request.

Problem 14.10.2 Capacity 5, refill 2 tokens per second, bucket starts full. Seven requests at t = 0, then three at t = 1.0, then two at t = 1.5.

t = 05 tokens. The first 5 requests pass (tokens 0), requests 6 and 7 are refused.
t = 1.01 s passed: +2 tokens, so 2. The first two requests pass, the third is refused.
t = 1.50.5 s passed: +1 token. The first passes, the second is refused.
class TokenBucket:
    def __init__(self, capacity, rate, now=0.0):
        self.cap, self.rate = capacity, rate
        self.tokens, self.last = float(capacity), now
    def allow(self, now):
        self.tokens = min(self.cap, self.tokens + (now - self.last) * self.rate)
        self.last = now
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False

Distributed counter

One counter updated by thousands of clients is a bottleneck: each update must lock the same value. A sharded counter keeps N sub-counters. An increment picks a random shard; the total is the sum of all shards. Writes spread over N locks, reads cost N additions. If an exact instantaneous total is not needed, this is a standard trade.

import random
class ShardedCounter:
    def __init__(self, shards): self.s = [0] * shards
    def incr(self): self.s[random.randrange(len(self.s))] += 1
    def total(self): return sum(self.s)

random.seed(1)
c = ShardedCounter(8)
for _ in range(10000): c.incr()
print("total:", c.total(), " largest shard:", max(c.s), " smallest shard:", min(c.s))
total: 10000  largest shard: 1307  smallest shard: 1196

The total is exactly 10,000 and the shards share the load roughly evenly (the exact spread comes from the seed). Section 12.8 shows the next step, a counter that merges across data centres without any coordination.

Problem 14.11.2 Producer-consumer: one producer puts the numbers 1 to 100 on a queue, three consumers add them up. Total must be 5050 and every worker must stop.

Structurequeue.Queue is already thread-safe, so no extra lock for the queue.
StoppingPut one sentinel (None) per consumer at the end. A consumer that reads None exits. A single sentinel would stop only one consumer and leave the others waiting forever, a classic hang.
TotalsEach consumer keeps its own subtotal and returns it, so nothing is shared except the queue.
import queue, threading

q = queue.Queue(maxsize=10)          # bounded: the producer waits if consumers are slow
subtotals = [0, 0, 0]

def producer():
    for i in range(1, 101): q.put(i)
    for _ in range(3): q.put(None)   # one stop signal per consumer

def consumer(k):
    while True:
        item = q.get()
        if item is None: return
        subtotals[k] += item

ts = [threading.Thread(target=producer)] + [threading.Thread(target=consumer, args=(k,)) for k in range(3)]
for t in ts: t.start()
for t in ts: t.join()
print("total:", sum(subtotals))
total: 5050

The bounded queue gives backpressure (12.6): when consumers fall behind, the producer blocks instead of using unlimited memory. The split between consumers varies from run to run, but the total never does.

Problem 14.8.14 (Medium) An LRU cache of capacity 3 sees the keys A, B, C, A, D, B. Which key is evicted when D arrives, and which when B arrives?

Answer: After A, B, C the order (newest first) is C, B, A. Reading A makes it A, C, B. D arrives: evict B (oldest), order D, A, C. Then B is a miss, and inserting it evicts C. So D evicts B, and the second B evicts C.

Problem 14.8.15 (Medium) How many IDs can 6 base-62 characters hold, and how many characters do you need for 10 billion IDs?

Answer: 626 = 56,800,235,584 (about 56.8 billion), so 6 characters already cover 10 billion. 625 is only 916,132,832, which is less than 10 billion.

Problem 14.8.16 (Medium) Count smaller numbers to the right for [3, 3, 1].

Answer: [1, 1, 0]: the first 3 has one smaller (the 1), the second 3 has one smaller, and 1 has none. Equal values are not smaller, which is why the Fenwick query uses rank - 1.

Problem 14.8.17 (Hard) A consumer thread reads from a queue until it sees None. You start 4 consumers but put one None in the queue. What happens?

Answer: One consumer stops; the other three block forever on q.get(), so the program never exits. Put one sentinel per consumer, or use daemon threads, or use q.join() with task_done().

Problem 14.8.18 (Hard) Why is a fixed-window rate limiter of 100 per minute able to let 200 requests through in two seconds?

Answer: If 100 requests arrive in the last second of one minute and 100 more in the first second of the next, each window sees only 100 and allows them all. A sliding window or token bucket removes the boundary effect.

Problem 14.8.19 (Interview) You must design "top 10 trending hashtags in the last hour" for a stream. What do you say?

Answer: Clarify scale and accuracy. Keep per-minute count maps, expire minutes older than 60, and sum the 60 maps (or maintain running totals). Pick the top 10 with a heap. At very large scale mention approximate counting such as a count-min sketch (described here, not run) and partitioning by hashtag.

Problem 14.8.20 (Interview) In a 45-minute interview you realise at minute 25 that your approach is wrong. What do you do?

Answer: Say so plainly, keep the correct parts, restate what the problem needs, and switch to the simplest correct approach (often the brute force) and finish it. Then discuss the optimisation. Finishing something correct usually beats an unfinished clever idea.
