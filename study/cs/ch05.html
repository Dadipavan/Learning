Every slow website raises the same question: "the page got slower, why?" The answer is almost always inside the operating system (OS): the CPU was busy, memory ran out, the disk was slow, or threads were waiting on each other. This chapter gives you the mental model and the commands. By the end you will be able to explain why a server is slow in terms of CPU, memory, disk and waiting, run a race condition and a deadlock yourself, and read the output of vmstat and top. We use one running example: a small web service with 4 CPU cores, 16 GB of RAM and a pool of worker threads, the kind that serves an online shop. Examples run on a Mac with Python 3.14. Commands that exist only on Linux are marked Linux only, not run here, and their output is labelled illustrative.

5.1 Processes, Threads, Context Switches and Scheduling

BASIC EXPLANATION
A process is a running program with its own memory. A thread is a unit of execution inside a process that shares its memory. The scheduler decides which one runs on the CPU, and a context switch saves one and loads another.
INTUITION
Think of a restaurant kitchen. A process is a whole kitchen with its own stove, fridge and cooks. A thread is one cook inside that kitchen: cooks share the fridge (memory) but each has their own cutting board (stack). There are only a few stoves (CPU cores) and many cooks. Someone must decide who gets a stove now. That someone is the scheduler.

How it works

  • A process is a running program. It has its own private memory, open files and a process ID (PID). One process cannot read another's memory by default.
  • A thread is a path of execution inside a process. Threads of one process share memory. This makes sharing data cheap, and also dangerous (section 5.2).
  • A CPU core runs one thread at a time. The OS gives each runnable thread a short time slice (often a few milliseconds), then switches to another. This switch is a context switch: save the registers of the old thread, load those of the new one. It costs microseconds, and it also makes CPU caches colder.
  • A thread is in one of three broad states: running, ready (waiting for a core) or blocked (waiting for I/O or a lock).
  • The scheduler policy decides the order. FCFS (first come, first served) is simple but a long job blocks short ones. Round robin gives each job a fixed slice in turn. Linux uses a more complex fair scheduler, but round robin is the right first picture.

Read it left to right: threads wait in the ready queue, one runs on the core, and when its slice ends it goes to the back. A thread that must wait for the disk or network moves to the blocked box and comes back when the I/O completes.

Worked examples

Problem 5.1.1 Three jobs arrive together: A needs 24 ms of CPU, B needs 3 ms, C needs 3 ms. Compare the average finish time under FCFS and under round robin with a 4 ms slice. Ignore switch cost.

Step 1FCFS runs A, then B, then C. A finishes at 24, B at 27, C at 30. Average = (24 + 27 + 30) / 3 = 27.0.
Step 2Round robin with slice 4: A runs 0-4, B runs 4-7 (done), C runs 7-10 (done), then A runs alone until 30. Finish times: B = 7, C = 10, A = 30. Average = (7 + 10 + 30) / 3 = 15.67.
Step 3Check with code.
from collections import deque
def fcfs(jobs):
    t=0; res={}
    for n,b in jobs:
        t+=b; res[n]=t
    return res
def rr(jobs,q):
    dq=deque(jobs); t=0; res={}
    while dq:
        n,b=dq.popleft()
        run=min(q,b); t+=run; b-=run
        if b: dq.append((n,b))
        else: res[n]=t
    return res
jobs=[("A",24),("B",3),("C",3)]
for name,r in [("FCFS",fcfs(jobs)),("RR q=4",rr(jobs,4))]:
    print(name,r,"avg finish",round(sum(r.values())/len(r),2))

Predict first: before you run this, which policy do you think gives the smaller average finish time, and by roughly how much?

FCFS {'A': 24, 'B': 27, 'C': 30} avg finish 27.0
RR q=4 {'B': 7, 'C': 10, 'A': 30} avg finish 15.67
  • Line by line deque is a queue; popleft takes the next job. run=min(q,b) runs at most one slice. if b: means work is left, so the job goes to the back of the queue; otherwise we record its finish time t. fcfs just adds burn times in order.
  • Wrong version If you forget popleft() and write dq.pop(), you take the job from the wrong end and the order changes (that is a stack, not a queue).
  • Answer Round robin cuts the average finish time from 27.0 ms to 15.67 ms, because short jobs no longer wait behind the long one. The last job (A) finishes at 30 ms in both cases. This is why a busy server still feels responsive to small requests.
  • Check Total CPU work is 30 ms in both cases, and the last job ends at 30 in both. Only the order changed, so the averages can differ.
  • Why it matters Plain English: under round robin, 2 of your 3 users wait about a third as long, and the long job loses only a few milliseconds.

Problem 5.1.2 Python threads versus processes for CPU work. Run a CPU-heavy function four times: serially, in 4 threads, in 4 processes (12-core Mac).

Step 1The function adds i*i for 3 million numbers.
Step 2Run all three styles and time them.
import time, multiprocessing as mp, threading, os
def burn(n=3_000_000):
    s=0
    for i in range(n): s+=i*i
    return s
if __name__=="__main__":
    print("cores:", os.cpu_count())
    t=time.perf_counter(); [burn() for _ in range(4)]; print(f"serial x4: {time.perf_counter()-t:.2f}s")
    t=time.perf_counter()
    ts=[threading.Thread(target=burn) for _ in range(4)]
    [x.start() for x in ts]; [x.join() for x in ts]
    print(f"4 threads: {time.perf_counter()-t:.2f}s")
    t=time.perf_counter()
    with mp.Pool(4) as p: p.map(burn,[3_000_000]*4)
    print(f"4 processes: {time.perf_counter()-t:.2f}s")

Predict first: will 4 threads take about 1/4 of the serial time? Write your guess, then look.

cores: 12
serial x4: 0.31s
4 threads: 0.32s
4 processes: 0.38s
  • Line by line burn does pure arithmetic (no waiting), so it is CPU-bound. The list comprehension runs it 4 times one after another. The thread version starts 4 threads and join waits for all. mp.Pool(4).map sends the work to 4 separate processes.
  • Check Serial time 0.31 s for 4 calls is about 0.078 s per call. Threads at 0.32 s match serial, as the GIL predicts.
  • Answer Threads gave no speed-up (0.32 s vs 0.31 s), because standard Python has a GIL (global interpreter lock): only one thread runs Python bytecode at a time. Processes were not faster here (0.38 s) because the job is so small that starting processes costs as much as the work. With a job 100 times bigger, processes would win on a multi-core machine. Lesson: measure before you parallelise. Threads still help when work is I/O waiting (section 5.4).
KEY INSIGHT
Threads are cheap to create and share memory, but they share bugs too. Processes are isolated and safer, but sharing data needs copying or special channels. Most servers use both: several processes, each with many threads.

Connection to the real job

When a busy web service shows CPU at 100% and latency climbing, requests are sitting in the ready queue. The CPU is not "doing more work", it is making them wait. Thread-pool sizing in web servers, Spark executors (one process, many threads) and Python's multiprocessing for data preprocessing all rest on this model.

Applications

  • Web servers (worker processes plus thread pools)
  • Data pipelines (parallel file processing with processes)
  • Databases (one process or thread per connection)
  • Containers (a container is just isolated processes)
COMMON MISTAKE
Assuming more threads means more speed. If threads exceed cores for CPU-bound work, you only add context switches. In Python, CPU-bound threads do not run in parallel at all (standard build). Use processes or vectorised libraries like NumPy.

Check yourself

  1. What does a thread share with other threads of the same process, and what is private? Answer: It shares memory (heap, open files); its stack and registers are private.
  2. Why does round robin reduce average finish time in Problem 5.1.1? Answer: Short jobs finish early instead of waiting for the 24 ms job.
  3. Why did 4 threads not beat serial in Python? Answer: The GIL lets only one thread run Python bytecode at a time.

5.2 Concurrency Problems: Races, Deadlocks, Starvation, Locks

BASIC EXPLANATION
Concurrency problems occur when several threads or processes use shared data. A race condition gives a wrong result depending on timing, a deadlock is when tasks wait for each other forever, and starvation is when a task never gets a turn. Locks protect shared data.
INTUITION
Two people edit the same cell in a shared spreadsheet. Both read "100", both add 1, both write "101". Two additions happened but the cell moved by one. That lost update is a race condition. Locks are the "someone is editing, please wait" sign.

Definitions

  • Race condition: the result depends on the exact timing of threads. Typical form: read, modify, write, without protection.
  • Critical section: the code that touches shared data and must run by one thread at a time.
  • Lock (mutex): only one thread can hold it. Others wait. Always release it (use with).
  • Semaphore: a counter that allows up to N threads in at once. A semaphore of 5 is a "5 database connections only" gate.
  • Deadlock: thread 1 holds lock A and waits for B; thread 2 holds B and waits for A. Both wait forever. Four conditions must all hold: mutual exclusion, hold-and-wait, no pre-emption, circular wait. Break any one to prevent deadlock.
  • Starvation: a thread is always skipped and never gets the resource (for example, low-priority work under constant high-priority load).

Worked examples

Problem 5.2.1 Four threads each add 1 to a shared counter 2000 times. Expected total: 8000. Show the race and fix it with a lock. (We add time.sleep(0) between read and write to force a thread switch. Real races are rarer but just as real.)

Step 1Unsafe version: tmp = counter, yield, counter = tmp + 1.
Step 2Safe version: wrap the three lines in with lock:.
import threading, time
counter = 0
def work_unsafe(n):
    global counter
    for _ in range(n):
        tmp = counter
        time.sleep(0)
        counter = tmp + 1
lock = threading.Lock()
def work_safe(n):
    global counter
    for _ in range(n):
        with lock:
            tmp = counter
            time.sleep(0)
            counter = tmp + 1
def run(fn, label, threads=4, n=2000):
    global counter
    counter = 0
    ts = [threading.Thread(target=fn, args=(n,)) for _ in range(threads)]
    for t in ts: t.start()
    for t in ts: t.join()
    print(f"{label}: expected {threads*n}, got {counter}")
run(work_unsafe, "no lock  ")
run(work_safe,   "with lock")

Predict first: the right answer is 8000. What do you expect the no-lock line to print: 8000, a bit less, or a lot less?

no lock  : expected 8000, got 2055
with lock: expected 8000, got 8000
  • Line by line tmp = counter reads. time.sleep(0) politely gives up the CPU, so another thread runs and reads the same old value. counter = tmp + 1 then writes a stale result. with lock: makes read, sleep and write one unbreakable block.
  • Wrong version If you write counter = counter + 1 in a function without global counter, Python stops you:
UnboundLocalError cannot access local variable 'counter' where it is not associated with a value

Fix: add global counter as the first line of the function.

  • Check 4 threads x 2000 = 8000. The safe version printed exactly that, so the lock works.
  • Answer Without the lock we lost about 5,900 updates. The exact number changes on every run (that is what makes races hard to debug). With the lock the answer is always 8000. In plain words: about 3 of every 4 updates vanished, and nothing crashed, which is why races are dangerous.

Problem 5.2.2 Create a deadlock, then fix it by lock ordering. We use acquire(timeout=1) so the demo ends instead of hanging.

Step 1Thread 1 takes a, sleeps, then wants b. Thread 2 takes b, sleeps, then wants a.
Step 2Both time out: they were in a circular wait.
Step 3Fix: both threads always take a first, then b.
import threading, time
a, b = threading.Lock(), threading.Lock()
def t1():
    with a:
        time.sleep(0.2)
        ok = b.acquire(timeout=1)
        print("t1 got b?", ok)
        if ok: b.release()
def t2():
    with b:
        time.sleep(0.2)
        ok = a.acquire(timeout=1)
        print("t2 got a?", ok)
        if ok: a.release()
def t2_fixed():
    with a:
        time.sleep(0.2)
        with b:
            print("t2 got both")

Predict first: neither thread can finish. What will acquire(timeout=1) return for each?

t1 got b? False
t2 got a? False
--- fixed: both take locks in the same order (a then b) ---
t1 got b? True
t2 got both
  • Check After the fix there is no cycle: t2_fixed waits for a, which t1 releases when done, so progress is guaranteed.
  • Answer Opposite lock order gave a deadlock (both gave up after 1 s). The same order removed the circular wait, and both threads finished.

The picture

Deadlock:   T1 holds A --wants--> B held by T2 --wants--> A held by T1   (a cycle)
Fix:        order the locks (A before B) so a cycle cannot form

Real-world mapping

ItemExample valueWhere it appears in the job
Race conditionTwo requests update one counter, 2055 of 8000 surviveHit counters, inventory stock, caches

Connection to the real job

  • Database deadlocks: two transactions update rows in opposite order. The database kills one ("deadlock detected"). Users may see these as random errors when many people act at once, and the fix is the same: consistent ordering.
  • Lock contention shows up as low CPU but high latency: threads are blocked, not running. A thread dump (jstack for Java services) shows many threads in state BLOCKED or WAITING.
  • Connection pools are semaphores in disguise. When the pool is exhausted, requests queue.

Applications

  • Databases and transactions
  • Thread-safe caches and counters
  • Producer-consumer queues in data pipelines
  • Rate limiters and connection pools
COMMON MISTAKE
Locking too much. One giant lock makes the program correct but serial, so it is slow. Lock only the smallest critical section. Another mistake: testing a race once, seeing correct output and concluding it is safe. Races are timing luck.

Check yourself

  1. Name the four deadlock conditions. Answer: Mutual exclusion, hold-and-wait, no pre-emption, circular wait.
  2. What is the difference between a lock and a semaphore? Answer: A lock lets one thread in; a semaphore lets up to N in.
  3. Why is low CPU with high latency a hint of lock contention? Answer: Threads are blocked waiting, not using the CPU.

5.3 Memory: Stack, Heap, Virtual Memory, Swapping, OOM

BASIC EXPLANATION
The stack holds function calls and local variables, and the heap holds dynamically allocated data. Virtual memory gives each process its own address space, swapping moves memory pages to disk, and OOM (out of memory) is when the system cannot allocate more.
INTUITION
Memory (RAM) is a desk. Disk is the cupboard across the room. Your program thinks it has a huge private desk, but the OS secretly keeps only the papers you are using on the real desk and puts the rest in the cupboard. That trick is virtual memory.

How it works

  • Stack: small, fast memory for function calls and local variables. Each call adds a frame; return removes it. Too deep recursion causes stack overflow.
  • Heap: large memory for objects that live as long as needed. You (or a garbage collector) must free them.
  • Virtual memory: every process sees its own address space. The OS maps it to real RAM in blocks called pages (commonly 4 KB; this Mac uses 16 KB, as vm_stat reports). A page not in RAM causes a page fault: the OS loads it from disk.
  • Swapping: when RAM is full, the OS moves cold pages to disk (swap). Disk is thousands of times slower than RAM, so a swapping machine crawls.
  • Memory leak: the program keeps references to objects it no longer needs, so memory only grows.
  • OOM (out of memory): when memory truly runs out, Linux's OOM killer picks a process and kills it. Containers with a memory limit get killed at their limit, often shown as "OOMKilled" or exit code 137.
  • CPU caches: tiny, very fast memory on the chip. Reading data in order is much faster than jumping around (more in chapter 13).

Worked examples

Problem 5.3.1 Find a leak. A handler appends 10,000 characters to a global list on every request and never clears it. Measure after 1000 and 2000 requests with tracemalloc.

Step 1Expected by hand: 1000 x 10,000 bytes = 10 MB; 2000 requests = 20 MB.
Step 2Run it.
import tracemalloc, sys
cache = []
def handle(i):
    cache.append("x"*10_000)   # leak: never cleared
tracemalloc.start()

for i in range(1000): handle(i)
cur, peak = tracemalloc.get_traced_memory()
print(f"after 2000 requests: {cur/1e6:.1f} MB held")
print("list of 1000 ints:", sys.getsizeof(list(range(1000))), "bytes (pointers only)")
def rec(n): return rec(n+1)
try: rec(0)
except RecursionError as e: print("stack overflow guard:", type(e).__name__)

Predict first: by hand, 1000 strings of 10,000 bytes is how many MB? Then check.

after 1000 requests: 10.0 MB held
after 2000 requests: 20.1 MB held
list of 1000 ints: 8056 bytes (pointers only)
stack overflow guard: RecursionError

Each call appends a new 10,000-character string and nothing removes it. tracemalloc.get_traced_memory() returns (current, peak) bytes. rec calls itself with no stopping rule, so frames pile up on the stack until Python raises RecursionError.
  • Check 2000 x 10,000 bytes = 20,000,000 bytes = 20 MB, and the tool says 20.1 MB (small extras from object headers).
  • Answer Memory grows linearly with requests (10.0 MB then 20.1 MB), matching our hand calculation. A steady upward line like this over a long soak test is the signature of a leak. The last two lines show a list stores only pointers (8 bytes each, plus a small header), and that Python stops runaway recursion with RecursionError.

5.4 File Systems and I/O Models

BASIC EXPLANATION
A file system organises data on storage into files and directories. I/O models describe how a program waits for data: blocking waits until it is ready, non-blocking returns at once, and asynchronous is notified when done.
INTUITION
You order food. Option 1: stand at the counter until it is ready (blocking). Option 2: keep checking every minute while doing other things (non-blocking). Option 3: take a token and be called when ready (async / event-driven). The waiting is the same; what you do meanwhile differs.

How it works

  • A file system (ext4, XFS, APFS, NTFS) organises disk blocks into files and folders. A file is stored as an inode (metadata) plus data blocks. Reads and writes go through the OS.
  • Page cache: the OS keeps recently used file data in free RAM. A repeated read of the same file comes from RAM, not disk. Writes are often held in cache and flushed later (fsync forces them to disk).
  • Disk types: an HDD has a moving head, so random access is slow (milliseconds). An SSD has no moving parts, so random access is fast (tens to hundreds of microseconds), but still slower than RAM. Sequential reads are faster than random on both.
  • Blocking I/O: the thread sleeps until data arrives. Non-blocking: call returns at once ("not ready yet"). Async I/O: one thread manages thousands of waiting operations (asyncio, Node.js, epoll on Linux).

Worked examples

Problem 5.4.1 Five calls each wait 0.2 s (like five slow API calls). Compare sequential blocking calls with asyncio.gather.

Step 1Sequential: 5 x 0.2 = 1.0 s expected.
Step 2Together: all five wait at the same time, so about 0.2 s.
import asyncio, time
def blocking():
    t=time.perf_counter()
    for _ in range(5): time.sleep(0.2)
    print(f"blocking sequential: {time.perf_counter()-t:.1f}s")
async def one(): await asyncio.sleep(0.2)
async def main():
    t=time.perf_counter()
    await asyncio.gather(*[one() for _ in range(5)])
    print(f"asyncio, 5 waits together: {time.perf_counter()-t:.1f}s")
blocking(); asyncio.run(main())

Predict first: sequential is 1.0 s. How long do you think gather takes?

blocking sequential: 1.0s
asyncio, 5 waits together: 0.2s
  • Line by line time.sleep blocks the whole thread. await asyncio.sleep hands control back to the event loop (the scheduler of async code) so the other waits can start. gather starts all five and waits for all.
  • Wrong version If you call time.sleep(0.2) inside async def one(), the loop is blocked and the total is back to 1.0 s. Use await asyncio.sleep.
  • Answer Overlapping the waits gave a 5x speed-up (1.0 s to 0.2 s) using one thread. Async helps with waiting, not with computing.

Problem 5.4.2 See the page cache. Write a 200 MB random file in /tmp, read it twice, and time both reads. (The script deletes only its own temp file.)

Step 1Write the file, then read it in 1 MB chunks, twice.
import os, time, tempfile
d=tempfile.mkdtemp(dir="/tmp"); p=os.path.join(d,"f.bin")
with open(p,"wb") as f: f.write(os.urandom(200_000_000))
for label in ["first read","second read"]:
    t=time.perf_counter()
    with open(p,"rb") as f:
        while f.read(1<<20): pass
    print(f"{label}: {time.perf_counter()-t:.3f}s")
os.remove(p); os.rmdir(d)

Predict first: which read is faster, and why might the first one not be slow?

first read: 0.020s
second read: 0.012s
  • Answer Both reads were fast, and the second was faster. Honest note: we had just written the file, so it was already in the page cache and even the "first" read came from RAM. To see a cold read you must drop caches (needs root on Linux, so not done here). The lesson for any timing measurement: the first run after a restart can be slower than later runs because caches are cold. Always warm up.

Check yourself

  1. What is the page cache? Answer: Free RAM that the OS uses to keep recently used file data.
  2. Why can async finish five 0.2 s waits in about 0.2 s? Answer: The waits overlap; one thread starts all of them and resumes as each ends.
  3. Why is a cold-cache first run slower? Answer: Data must be read from disk before it lands in cache.

5.5 Diagnosing a Slow System on Linux

BASIC EXPLANATION
Diagnosing a slow Linux system means checking the four main resources: CPU, memory, disk and network. Tools such as top, free, iostat and vmstat show which resource is the bottleneck.
INTUITION
A doctor checks pulse, temperature and blood pressure before guessing. For a server, the four "vital signs" are CPU, memory, disk and network. The USE method says: for each resource, check Utilisation (how busy), Saturation (how much waiting) and Errors.

Problem 5.5.1 Read the illustrative vmstat line above. The machine has 4 cores. What is the likely problem?

Step 1r = 9: nine threads want a CPU, only 4 cores exist. The ready queue is about 2x the cores.
Step 2us + sy = 98, id = 2, wa = 0: the CPU is full and not waiting on disk.
Step 3si = so = 0: no swapping. b = 0: nothing is blocked on I/O.
Check9 runnable on 4 cores means 5 threads wait at any moment, which explains slow responses with no disk or swap activity.
AnswerThe system is CPU-bound and saturated. Plain English: your service is trying to do about twice as much work as the CPUs can handle. Fix by cutting CPU work (profile with perf), adding cores, or limiting concurrency. Adding RAM or faster disk would not help.

Problem 5.5.2 Load average. A 4-core server shows load average 8.2, 7.9, 4.1 (1, 5, 15 minutes). Interpret it.

Step 1Load average roughly counts threads running or waiting. Divide by cores: 8.2 / 4 = 2.05.
Step 2The trend: 4.1 (15 min) rising to 7.9 and 8.2 means the load grew about 10 minutes ago and is still high.
Check8.2 / 4 = 2.05, and 4.1 / 4 is about 1.0, so the load doubled.
AnswerEach core has about two threads wanting it, so work queues up, and the problem is recent and ongoing. On Linux, load average also counts threads blocked in disk I/O, so check vmstat (r vs b) to tell CPU from disk.

Now a real command on this Mac, to show process listing (macOS tools differ from Linux, but ps is similar):

ps -o pid,ppid,stat,%cpu,%mem,comm -p $$

21620 21529 Ss     0.0  0.0 /bin/zsh

This is the shell itself: PID 21620, started by parent 21529, state Ss (sleeping, session leader). The PPID column shows every process has a parent, which is how the process tree forms. macOS vm_stat (also run here) reported "page size of 16384 bytes" and counts of free, active and inactive pages.

5.6 Containers from the Inside: Namespaces, cgroups and Exit Code 137

BASIC EXPLANATION
A container is a normal Linux process that is isolated by namespaces (what it can see) and limited by cgroups (what it can use). Exit code 137 means the process was killed by SIGKILL, often because it exceeded its memory limit.
INTUITION
A container is not a small virtual machine. It is an ordinary Linux process that has been given two things: a restricted view of the machine (namespaces) and a restricted budget (cgroups). All containers on a host share one kernel. That one fact explains why they start in milliseconds, why one runaway container can still hurt its neighbours, and why a container "crashes with 137".

How to read it: the grey bar at the bottom is the single kernel. Each orange box is a container. Inside, the top rectangle (namespaces) is the world the process believes it lives in: its own process ID numbering, hostname, network interfaces and mounted file systems. The green rectangle (cgroup) is the accounting record the kernel keeps for that group of processes: how much memory and CPU time they may use.

The two building blocks

MechanismQuestion it answersExamples
PID namespaceWhich processes can I see?Inside the container your app is PID 1, on the host it is PID 48213
Network namespaceWhich network interfaces and ports do I own?Two containers can both listen on port 8080
Mount namespaceWhich file tree do I see?The image's file system appears as /

cgroup CPU limitHow much CPU time may this group use?--cpus=1.5 (150 ms of CPU per 100 ms window)

Problem 5.6.1 A training job in a container with --memory=512m exits with code 137. The exit code of a process killed by a signal is 128 plus the signal number. What happened?

Step 1Subtract: 137 - 128 = 9.
Step 2Signal 9 is SIGKILL, which cannot be caught or ignored.
Step 3Nobody on the application side sent it. The kernel's out-of-memory (OOM) killer did, because the cgroup tried to use more than 512 MiB.
Checkdocker inspect --format '{{.State.OOMKilled}}' NAME prints true (not run here, needs Docker), and dmesg shows a line such as "Memory cgroup out of memory: Killed process".
import signal
code = 137
print(code - 128, signal.Signals(code - 128).name)
print(143 - 128, signal.Signals(143 - 128).name)
9 SIGKILL
15 SIGTERM

Exit 143 is the polite one: SIGTERM, which is what docker stop sends first. If you see 137 right after a stop, the process ignored SIGTERM and was killed after the grace period (10 seconds by default).

Problem 5.6.2 A container has a 1 GiB limit. It runs a Python service whose resident memory grows 40 MiB per hour from a base of 300 MiB because of a cache that never evicts. When does it die?

SetupHeadroom = 1024 - 300 = 724 MiB.
Compute724 / 40 = 18.1 hours.
AnswerIt is killed after about 18 hours, so the symptom is "restarts every day at roughly the same time". A cache bound such as functools.lru_cache(maxsize=10000) fixes the cause. Raising the limit only moves the crash later.

Problem 5.6.3 A service is limited with --cpus=0.5. A request needs 80 ms of pure CPU time. How long does it take at minimum?

IdeaThe scheduler gives the cgroup 50 ms of CPU per 100 ms period, then throttles it until the next period starts.
Step 1First period: 50 ms of work done, 30 ms left, the cgroup is paused for the remaining 50 ms of the period.
Step 2Second period starts at 100 ms: the last 30 ms run, finishing at 130 ms.
Answer130 ms of wall time for 80 ms of work. This is CPU throttling: latency spikes while CPU usage graphs look low. Check cpu.stat for nr_throttled.

Problem 5.6.4 A process opens files in a loop and crashes with "Too many open files". Reproduce it safely by lowering the limit inside one Python process.

import resource, errno, tempfile, os
resource.setrlimit(resource.RLIMIT_NOFILE, (40, 40))
d = tempfile.mkdtemp()
handles = []
try:
    for i in range(100):
        handles.append(open(os.path.join(d, f"f{i}"), "w"))
except OSError as e:
    print("failed with", errno.errorcode[e.errno], "after opening between 30 and 40 files:", 30 <= len(handles) <= 40)
finally:
    for h in handles: h.close()
failed with EMFILE after opening between 30 and 40 files: True

The error name EMFILE is the "per-process file descriptor limit" (ulimit -n). Each socket, pipe and file uses one descriptor, so a server that leaks connections hits it. On a real service the fix is to close what you open (use with) and to raise the limit only after the leak is gone.

COMMON MISTAKE
Reading memory from the host's point of view. A container limited to 512 MiB on a 64 GiB host still sees "64 GiB total" in some tools, because free and old runtimes read host-wide files. Size heaps from the cgroup limit (/sys/fs/cgroup/memory.max on cgroup v2), not from the machine total. Java and Python data jobs that guess from the host get OOM-killed.

Going deeper

  • Page cache counts. File reads fill the kernel page cache, and cgroup v2 charges it to the container. The kernel reclaims clean cache before it kills anything, so rising "cache" in memory.stat is normal and a kill needs anonymous memory (heap and stack) to be the problem.
  • Requests versus limits (Kubernetes). A request is what the scheduler reserves when placing the pod, a limit is the cgroup ceiling. Memory over the limit means kill. CPU over the limit means throttle. A pod with no limit can use the whole node and trigger the node OOM killer, which may pick another pod.
  • Tools (Linux only, not run here). strace -c -p PID counts system calls by type; perf top samples where CPU time goes; iostat -x 1 shows disk await and %util; vmstat 1 shows the run queue and swap. Read them in the order of the USE method from section 5.5.

5.7 Python Concurrency in Practice: Threads, Processes and asyncio

BASIC EXPLANATION
Python offers threads, processes and asyncio for doing several things at once. Threads and asyncio suit waiting on I/O, and processes suit CPU-heavy work because they avoid the Global Interpreter Lock (GIL).
INTUITION
Waiting and computing are different problems. If your program spends its time waiting (network, disk, a database), you can overlap many waits cheaply. If it spends its time computing, you need more CPU cores working at once. CPython's Global Interpreter Lock (GIL) lets only one thread run Python bytecode at a time, so threads fix the first problem and not the second.

How to read it: each bar is a slice of CPU time and each colour is one task. In panel B the four threads take turns in thin slices, so the total is still about four units. In panel C each process owns a core, so the four tasks finish together in about one unit, minus start-up cost for creating the processes.

Problem 5.7.1 Four tasks each wait 0.2 s (a fake network call). Compare running them one after another with running them in four threads.

PredictSequential: 4 x 0.2 = 0.8 s. Threads: the waits overlap, so about 0.2 s plus a little overhead.
Whytime.sleep and network calls release the GIL while they wait, so other threads run.
import time
from concurrent.futures import ThreadPoolExecutor

def fake_call(i):
    time.sleep(0.2)
    return i * i

t = time.perf_counter()
seq = [fake_call(i) for i in range(4)]
t_seq = time.perf_counter() - t

t = time.perf_counter()
with ThreadPoolExecutor(max_workers=4) as pool:
    par = list(pool.map(fake_call, range(4)))
t_thr = time.perf_counter() - t

print(seq == par, seq)
print("sequential at least 0.8 s:", t_seq >= 0.8)
print("threads under 0.4 s:", t_thr < 0.4)
True [0, 1, 4, 9]
sequential at least 0.8 s: True
threads under 0.4 s: True

Problem 5.7.2 Now four tasks that burn CPU. Does a thread pool help? Does a process pool?

PredictThreads: about the same as sequential, because only one thread runs bytecode at a time. Processes: close to one quarter on a machine with at least 4 cores, less the cost of starting processes and copying arguments.
MeasureRun the script below. It prints only booleans, because exact timings depend on your machine.
import time, os
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

def burn(n):
    total = 0
    for i in range(n):
        total += i * i
    return total

def timed(fn):
    t = time.perf_counter(); fn(); return time.perf_counter() - t

if __name__ == "__main__":
    N = 20_000_000
    jobs = [N] * 4
    t_seq = timed(lambda: [burn(n) for n in jobs])
    with ThreadPoolExecutor(4) as tp:
        t_thr = timed(lambda: list(tp.map(burn, jobs)))
    with ProcessPoolExecutor(4) as pp:
        t_proc = timed(lambda: list(pp.map(burn, jobs)))
    print("threads save less than 40 percent:", t_thr > 0.6 * t_seq)
    print("processes beat sequential:", t_proc < t_seq, "(needs 2+ cores:", (os.cpu_count() or 1) >= 2, ")")
threads save less than 40 percent: True
processes beat sequential: True (needs 2+ cores: True )

Problem 5.7.3 One thread, many waits: asyncio. Fetch four fake resources with one thread and show that results keep their order.

IdeaA coroutine runs until it hits await, then hands control back to the event loop, which starts another. One thread, no locks needed for plain variables, thousands of waits at once.
RuleNever call blocking code (time.sleep, requests.get) inside a coroutine: it freezes the whole loop. Use await asyncio.sleep or an async client.
import asyncio, time

async def fetch(name, delay):
    await asyncio.sleep(delay)
    return f"{name} done"

async def main():
    t = time.perf_counter()
    results = await asyncio.gather(fetch("a", 0.3), fetch("b", 0.1), fetch("c", 0.2), fetch("d", 0.2))
    return results, time.perf_counter() - t

results, elapsed = asyncio.run(main())
print(results)
print("elapsed about the longest wait (0.3 s), not the sum (0.8 s):", 0.3 <= elapsed < 0.5)
['a done', 'b done', 'c done', 'd done']
elapsed about the longest wait (0.3 s), not the sum (0.8 s): True

Notice the result order: gather returns results in the order you passed the coroutines, not the order they finished (b finished first).

COMMON MISTAKE
Adding threads to a CPU-bound loop and expecting a speedup. Wrong: 4 threads on a pure-Python loop take about as long as 1 thread, sometimes longer from lock hand-offs. Right: use ProcessPoolExecutor, or move the hot loop into NumPy or a compiled extension.

Going deeper

  • Cost of processes. Arguments and results are pickled and copied between processes. If each task is tiny, the copying costs more than the work. Batch the work into chunks (pool.map(fn, items, chunksize=500)).
  • Oversubscription. A process pool of 8 workers where each worker calls a multithreaded BLAS with 8 threads makes 64 runnable threads on 8 cores. Set OMP_NUM_THREADS=1 in the workers.
  • Free-threaded Python. Recent CPython releases ship an optional build without the GIL. It is still opt-in and many extension modules need updating, so check the version and libraries before relying on it.
  • Check yourself. You must call a slow SQL query 500 times. Answer: a thread pool of 10 to 20 (the database is the limit, so do not use 500), because the program is waiting, not computing.

Chapter recap

  • A process has private memory; threads in one process share memory.
  • A core runs one thread at a time; the scheduler switches with context switches.
  • Round robin helps short jobs: average finish dropped from 27.0 to 15.67 ms in our example.
  • Python threads do not speed up CPU work (GIL); use processes or NumPy. Threads are fine for waiting.
  • A race condition loses updates (2055 instead of 8000); a lock fixes it.
  • Deadlock needs a circular wait; always take locks in the same order.
  • Virtual memory, swapping and OOM kills explain many slow or crashing servers; watch available memory and swap activity.
  • The page cache makes repeated reads fast, so warm up before measuring.
  • Async I/O overlaps waiting; it does not speed up computing.
  • Diagnose with USE: utilisation, saturation, errors for CPU, memory, disk and network.

Practice set

1. What is a context switch? Answer: The OS saves one thread's state and loads another's so a core can run it.

2. Three jobs of 5, 5 and 10 ms run FCFS in that order. What is the average finish time? Answer: Finish at 5, 10, 20. Average = 35 / 3 = 11.67 ms.

3. A container has a 2 GB memory limit and exits with code 137. Name two likely causes. Answer: A memory leak, or a workload (big DataFrame, large batch) that needs more than 2 GB. The OOM killer sent SIGKILL.

4. Find the bug:

lock.acquire()
total += compute()
lock.release()

Answer: If compute() raises an exception the lock is never released and others block forever. Use with lock:.

5. A 8-core machine has load average 2.0 but requests are slow and CPU is 15% busy. Give two hypotheses. Answer: Lock contention in the application, or waiting on a slow downstream service or database. Check thread dumps and downstream latency.

6. Scenario: during a 2-hour soak test, memory climbs 50 MB every 10 minutes and CPU stays flat. What do you report? Answer: A likely memory leak: about 5 MB per minute, 600 MB over the test. Recommend heap analysis, and estimate when the process will hit its limit (limit minus current, divided by 5 MB per minute).

7. Interview: "Explain the difference between a process and a thread and when you would use each." Answer: Processes have isolated memory, so they are safer and use multiple cores in Python, but cost more and need IPC to share data. Threads share memory, so they are cheap and good for I/O waiting, but need locks to avoid races. Many servers combine both.

8. Interview: "A service is slow but CPU is low. How do you investigate?" Answer: Apply USE to every resource: vmstat for blocked threads and swap, iostat for disk, ss for network queues, a thread dump for lock waits, and tracing for slow downstream calls. Low CPU points toward waiting, not computing.
