When a web page feels slow, the waiting time is not one number. It is the sum of finding the server's address, opening a connection, securing it, sending a request, waiting for the server, and receiving the answer. Someone who understands each piece can say "the server is fast, the network is slow", or the reverse, and be right. A data engineer needs the same knowledge to understand why a pipeline that calls an API 10,000 times is slow, or why a cross-region database call hurts. In this chapter we follow one request, GET /login, from your machine to a server. By the end you can explain the layers, TCP versus UDP, DNS, TLS, load balancers, CDNs, and the difference between latency and bandwidth, and you can calculate with them.

Our running example is a request to a web API at api.example.com. Because we do not want to hit the internet, all experiments here run on your own computer (127.0.0.1, which always means "this machine"). Python's socket module, curl, dig, ping and openssl were used for real. Tools needing special rights, such as tcpdump, traceroute and Wireshark, are explained but not run here.

4.1 Layers, IP Addresses and DNS

INTUITION
Sending a parcel involves layers. You write a letter (content). You put it in an envelope with a name (who inside the house). You put the envelope in a courier bag with a street address (which house). The courier uses a truck on a road (physical delivery). Each layer only talks to the same layer on the other side and does not care about the details of the layers below. Networks work the same way.

Words you need

WordPlain meaning
PacketA small chunk of data (about 1,500 bytes or less) with an address on it
IP addressThe street address of a machine, like 192.168.10.5 (IPv4) or ::1 (IPv6)
PortThe "room number" inside the machine; web HTTPS uses 443, HTTP 80, PostgreSQL 5432
ProtocolAn agreed set of rules for talking (HTTP, TCP, DNS)
RouterA device that forwards packets toward their destination

The layers

The internet uses 4 practical layers (the TCP/IP model). The textbook OSI model has 7 (it splits Application into three and Link into two), and interviewers like to ask about it, so the table maps both.

IP, subnets, NAT, DHCP

A subnet is a block of addresses that sit together, written as address/prefix. In 192.168.10.0/24 the 24 means the first 24 of 32 bits are fixed (the network part). The remaining 32 − 24 = 8 bits count the machines: 2⁸ = 256 addresses, minus 2 reserved (network and broadcast) = 254 usable. Python's ipaddress module can check this:

import ipaddress
net = ipaddress.ip_network("192.168.10.0/24")
print("network:", net.network_address, "mask:", net.netmask, "broadcast:", net.broadcast_address)
print("usable hosts:", net.num_addresses - 2)
print("10.0.5.77 in 10.0.0.0/16?", ipaddress.ip_address("10.0.5.77") in ipaddress.ip_network("10.0.0.0/16"))
print("subnets of /24 into /26:", [str(s) for s in net.subnets(new_prefix=26)])
print("private?", ipaddress.ip_address("192.168.1.5").is_private, ipaddress.ip_address("8.8.8.8").is_private)
print("bits for /20:", 32-20, "hosts:", 2**(32-20)-2)

Predict first: how many usable hosts in a /20? Real output:

network: 192.168.10.0 mask: 255.255.255.0 broadcast: 192.168.10.255
usable hosts: 254
10.0.5.77 in 10.0.0.0/16? True
subnets of /24 into /26: ['192.168.10.0/26', '192.168.10.64/26', '192.168.10.128/26', '192.168.10.192/26']
private? True False
bits for /20: 12 hosts: 4094

Line by line: /24 gives 254 usable hosts. 10.0.5.77 lies inside 10.0.0.0/16 (the first two numbers match). Cutting a /24 into /26 pieces makes 4 subnets of 64 addresses each (every extra prefix bit doubles the number of subnets: 2² = 4). 192.168.x.x is private (not reachable from the internet), 8.8.8.8 is public. In cloud work you will design VPC subnets like this.

  • NAT (network address translation): your home or office router shares one public IP among many private machines, rewriting addresses on the way out. That is how 50 laptops share one internet address.
  • DHCP: the service that hands an IP address to your laptop when it joins the network (like a hotel giving you a room number).
  • Routing: each router looks at the destination address and forwards the packet to the next hop. traceroute host prints the hops (not run here, it needs network access).

DNS: the phone book

Humans use names (api.example.com). Machines need IP addresses. DNS (domain name system) translates one to the other. Your computer asks a resolver, which may ask other servers, and caches the answer for a time called the TTL (time to live). Common record types: A (name to IPv4), AAAA (name to IPv6), CNAME (alias to another name), MX (mail).

dig +short localhost
127.0.0.1

dig localhost also prints a status line (status: NOERROR) and an ANSWER SECTION. With a real name you would also see the TTL number. DNS lookups cost time, typically a few ms to tens of ms, but a cached answer costs almost nothing. Here is a tiny simulation of a cache with TTL 60 seconds:

cache={}; lookups=0
def resolve(name,t,ttl=60):
    global lookups
    if name in cache and cache[name]>t: return "cache"
    lookups+=1; cache[name]=t+ttl; return "network"
print([resolve("api.example.com",t) for t in (0,10,59,61,70)], "network lookups:",lookups)
['network', 'cache', 'cache', 'network', 'cache'] network lookups: 2

The first lookup at time 0 goes to the network. Times 10 and 59 are inside the 60 s lifetime (cache). At time 61 the entry expired, so a new lookup. Time 70 is served from the fresh entry. So 5 requests cost only 2 network lookups.

  1. How many bits are the host part in /26? Answer: 6 bits, so 64 addresses (62 usable).
  2. What does DNS do? Answer: translates names to IP addresses (and caches them for the TTL).
  3. What is a port? Answer: a number that selects the program on a machine, for example 443 for HTTPS.

4.2 TCP versus UDP

INTUITION
TCP is a phone call: you dial, the other side picks up, you both confirm "can you hear me?", and during the call missed words are repeated. UDP is posting postcards: fast and simple, but some may be lost and they may arrive out of order, and nobody tells you.

How it works

TCP (transmission control protocol) gives a reliable, ordered stream of bytes:

  • Handshake: three messages open a connection. The client sends SYN ("synchronise, can we talk?"), the server answers SYN-ACK ("yes, I hear you"), the client replies ACK ("connection open"). This costs one round trip (RTT, round-trip time: the time for a message to go to the server and the answer to come back).
  • Acknowledgements and retransmission: the receiver confirms what it got. If the sender gets no confirmation in time, it sends the data again.
  • Congestion control: TCP starts slowly (slow start) and increases its sending speed until it detects loss, then backs off. That is why the first seconds of a download are slower, and why new connections are expensive.
  • Flow control: the receiver says how much data it can accept (the window size), so a slow receiver is not flooded.

UDP (user datagram protocol) sends independent packets: no handshake, no retransmission, no ordering. It is used when speed matters more than perfect delivery or the application handles loss itself: DNS queries, video calls, games, and QUIC (the base of HTTP/3).

TCPUDP
Connectionhandshake firstnone
Deliveryguaranteed, in ordernot guaranteed
Overheadhigherlower
Typical useHTTP, databases, SSHDNS, streaming, QUIC

How to read it: the two vertical lines are the client and the server; time flows downward; each arrow is one message. Arrows 1 to 3 are the TCP handshake (one round trip). Arrow 4 is the TLS set-up (section 4.3). Arrow 5 is your first real request. With a 50 ms RTT, you wait about 50 ms (TCP) plus about 50 ms (TLS 1.3) before the request even leaves.

Predict, run, explain

Predict what a TCP echo and a UDP message look like on 127.0.0.1. We start a tiny TCP server, send a hand-written HTTP request, then send a UDP packet.

import socket, threading
srv = socket.socket(); srv.bind(("127.0.0.1", 0)); srv.listen()
port = srv.getsockname()[1]
def serve():
    c, _ = srv.accept()
    data = c.recv(1024); c.sendall(b"ECHO:" + data); c.close()
threading.Thread(target=serve, daemon=True).start()
c = socket.create_connection(("127.0.0.1", port))   # the handshake happens here
c.sendall(b"hello"); print("TCP reply:", c.recv(1024)); c.close()

u = socket.socket(socket.AF_INET, socket.SOCK_DGRAM); u.bind(("127.0.0.1", 0))
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.sendto(b"ping", ("127.0.0.1", u.getsockname()[1]))
print("UDP got:", u.recvfrom(1024)[0])
TCP reply: b'ECHO:hello'
UDP got: b'ping'
  • bind(("127.0.0.1", 0)): port 0 means "pick any free port".
  • create_connection does the 3-way handshake before returning.
  • The UDP code has no listen, accept or connect. You just send. On a quiet local machine nothing is lost; on a real network the UDP packet could vanish and nobody would notice.

Problem 4.2.1 The RTT to a server is 80 ms. How long does TCP need before you can send the first byte of data, and how long before the answer to a small request arrives (ignore server time and TLS)?

Step 1Handshake = 1 RTT = 80 ms (SYN out, SYN-ACK back; the ACK travels along with the first data).
Step 2Request out and response back = 1 more RTT = 80 ms.
AnswerAbout 80 ms to be connected and about 160 ms to receive the first byte of a small answer.
CheckReusing the same connection (HTTP keep-alive) removes the first 80 ms for the next request, which is why connection reuse is the number one trick in web browsers and API clients.

Problem 4.2.2 A client calls an API 30 times in a loop, each over a new TCP connection with RTT 50 ms. What is the minimum wasted time on handshakes?

Formulawasted = calls × RTT
Plug in30 × 50 ms
Compute1,500 ms
Answer1.5 seconds of pure handshake waiting; with a reused connection it would be 50 ms once.
Check1,500 ms ÷ 30 = 50 ms each, as expected. In plain words, connection reuse saves 96.7% of the handshake cost here (1,450 / 1,500).

  • Data Engineering: database drivers use connection pools to avoid repeated handshakes.

  • Real-time ML: video and voice use UDP-based protocols.

Saying "UDP is unreliable so nobody uses it for important things". Important systems (DNS, HTTP/3 via QUIC) use it, adding their own reliability on top. The choice is about who handles loss.

Check yourself

  1. How many messages are in the TCP handshake? Answer: three (SYN, SYN-ACK, ACK).
  2. Why is a new connection slower at the start? Answer: handshake plus slow start.
  3. Name two things that use UDP. Answer: DNS and video calls (also QUIC).

4.3 HTTP, TLS and Other Application Protocols

INTUITION
HTTP is the language of ordering at a counter: "GET me the page /login" (request), "Here it is, status 200" (response). TLS is a sealed envelope plus an ID check: nobody on the road can read your letter, and you know that you are talking to the real shop.

HTTP basics

A request has a method (GET read, POST create, PUT replace, DELETE remove), a path, headers (extra information) and an optional body. A response has a status code, headers and a body.

Code familyMeaningExamples
2xxsuccess200 OK, 201 Created
3xxredirect301 Moved, 304 Not Modified
4xxclient's fault400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 429 Too Many Requests
5xxserver's fault500 Internal Error, 502 Bad Gateway, 503 Unavailable, 504 Gateway Timeout

We wrote a request by hand over a socket and a one-shot server that answers it:

c=socket.create_connection(("127.0.0.1",hp))
c.sendall(b"GET /login HTTP/1.1\r\nHost: localhost\r\n\r\n")

Real response (what the server sent back):

HTTP/1.1 200 OK
Content-Type: text/plain
Content-Length: 30
Connection: close

you asked: GET /login HTTP/1.1

HTTP is just text. The blank line separates headers from the body. Content-Length: 30 matches the 30 characters of the body. With curl against a local Python server we also read the headers (curl -sI):

HTTP/1.1 200 OK
Server: SimpleHTTP/0.6 Python/3.14.3
Date: Sat, 07 Nov 2026 06:33:42 GMT
Content-type: text/x-python

Timing a request with curl

curl can print the phases of a request, exactly the breakdown you want when something is slow:

curl -s -o /dev/null -w "dns=%{time_namelookup} connect=%{time_connect} start=%{time_starttransfer} total=%{time_total}\n" URL

On our local test server the numbers were tiny (connect about 0.0006 s, total about 0.017 s), and they change on every run, so we do not print them as a fixed result. Against a real server, read them as: connect − dns is the TCP time, starttransfer − connect is the server think time plus TLS, and total − starttransfer is the download time.

HTTP versions

VersionKey ideaWhy it exists
HTTP/1.1text, one request at a time per connection (keep-alive reuses it)the long-time default
HTTP/2binary, many requests multiplexed on one TCP connection, header compressionfixes the "many small files" waiting
HTTP/3HTTP over QUIC (UDP), avoids TCP head-of-line blocking, faster set-upbetter on mobile and lossy networks

Others you will meet: WebSocket (a long-lived two-way connection, for chat and live dashboards) and gRPC (fast binary calls between services, built on HTTP/2, used in model serving).

TLS (HTTPS)

TLS (transport layer security) gives three things: encryption (others cannot read), integrity (others cannot change it unseen) and authentication (the server proves its identity with a certificate signed by a trusted authority). HTTPS = HTTP inside TLS, on port 443. Idea of the handshake (TLS 1.3): the client says hello with supported algorithms and a key share; the server answers with its certificate and key share; both compute the same secret key and from then on encrypt everything with fast symmetric encryption. This costs about one extra RTT (see the diagram). Resuming a session can save that cost.

We made a throwaway self-signed certificate with openssl and ran a real TLS server and client on localhost:

TLS version: TLSv1.3
server saw: b'password=123'
client got: b'secret reply'
untrusted cert rejected: self-signed certificate

Line by line: the connection used TLS 1.3. Both sides exchanged data after encryption (an observer on the wire would see random bytes). When the client did not trust our certificate, it refused with self-signed certificate: this is the authentication check working. Never turn certificate verification off in production code (verify=False) just to make an error go away.

Problem 4.3.1 A browser gets 504 Gateway Timeout from a load balancer. Whose fault is it, and what do you check?

Step 15xx means the server side. 504 specifically means the gateway waited too long for the server behind it.
Step 2Check how long the backend takes to answer, its CPU and threads, and the load balancer's timeout setting.
AnswerThe backend (or the path to it) is too slow or down; it is not a client mistake.
CheckCompare with 502, where the backend sent an invalid answer or closed the connection. 504 is about time, 502 is about a bad reply. This distinction appears in many incident reports.

Problem 4.3.2 With RTT 100 ms, how long until the first byte of an HTTPS (TLS 1.3) response, with a new connection, ignoring server time?

Step 1TCP handshake = 1 RTT = 100 ms.
Step 2TLS 1.3 handshake = 1 RTT = 100 ms.
Step 3Request out + response back = 1 RTT = 100 ms.
AnswerAbout 300 ms. On a reused connection only the last step remains: 100 ms.
Check3 × 100 = 300. In plain words, 2/3 of the wait is set-up. That is why a script that opens a new connection for every request looks slower than a browser that reuses connections.

4.4 Load Balancers, Proxies, CDNs and Firewalls

INTUITION
A busy bank has one entrance queue that sends each customer to the next free teller. That queue manager is a load balancer. A CDN is like opening branch offices in many cities with copies of the popular forms, so most people never travel to the head office.

Words you need

WordPlain meaning
Backend / originThe real server(s) doing the work
ProxyA middleman that makes requests on behalf of a client (forward proxy)
Reverse proxyA middleman in front of servers (nginx, Envoy): clients talk to it, it talks to the backends
Load balancer (LB)A reverse proxy that spreads requests over several backends
Health checkA regular test call that tells the LB whether a backend is alive
CacheA saved copy that avoids repeating work

Load balancers: L4 and L7

  • L4 (transport layer): routes by IP and port only, without reading HTTP. Very fast, simple.
  • L7 (application layer): reads HTTP, so it can route by path (/api to one group, /images to another), by header or cookie, terminate TLS, and retry.

Common strategies: round robin (take turns), least connections (pick the least busy), hash/sticky (the same user goes to the same server, useful when a server keeps session state), weighted (bigger servers get more).

Predict: nine requests cost 9, 1, 1, 9, 1, 1, 9, 1, 1 ms of work. Which strategy balances better, round robin or "least loaded"?

costs=[9,1,1,9,1,1,9,1,1]
rr=[0,0,0]
for i,c in enumerate(costs): rr[i%3]+=c
lc=[0,0,0]
for c in costs: lc[lc.index(min(lc))]+=c
print("round robin load:",rr,"busiest:",max(rr)); print("least loaded    :",lc,"busiest:",max(lc))
round robin load: [27, 3, 3] busiest: 27
least loaded    : [11, 10, 12] busiest: 12

Round robin gave the first server every heavy request by bad luck of the pattern (request numbers 0, 3, 6): 27 ms against 3 ms and 3 ms. Least loaded kept all three within 10 to 12. This is a constructed worst case, but it shows why equal turns do not mean equal work when requests differ in cost. We also tested simple modulo-based sticky routing: the same user always landed on the same server.

Proxies, CDNs, firewalls, VPNs

  • A reverse proxy hides backends, adds TLS, caching and compression, and protects them.
  • A CDN (content delivery network) stores copies of static files (images, scripts, model files, public datasets) on servers close to users. If the edge server has the file, it is a hit; otherwise it fetches from the origin (a miss) and keeps it.
  • A firewall allows or blocks traffic by rules (IP range, port, direction). A cloud security group is a firewall per machine.
  • A VPN builds an encrypted tunnel to a private network, so remote engineers reach internal servers.

Average latency with a CDN is a weighted average of hit and miss times. With an edge time of 20 ms and an origin time of 200 ms:

hit ratio   0%: avg latency =  200.0 ms
hit ratio  50%: avg latency =  110.0 ms
hit ratio  90%: avg latency =   38.0 ms
hit ratio  99%: avg latency =   21.8 ms

Problem 4.4.1 Verify the 90% row by hand.

Formulaaverage = hit × edge + (1 − hit) × origin
Plug in0.9 × 20 + 0.1 × 200
Compute18 + 20 = 38
Answer38 ms average, an 81% cut from 200 ms.
Check(200 − 38) / 200 = 0.81, matching. In plain words, raising the hit ratio from 90% to 99% gains 16.2 ms more, so the last few percent of cache hits still matter.

Problem 4.4.2 A load balancer health check runs every 5 s and marks a server dead after 3 failed checks. A server crashes. At worst how long are users sent to the dead server?

Step 1The crash may happen right after a successful check; the first failed check is up to 5 s later.
Step 2Three failed checks take 3 × 5 = 15 s (the first failure is at most 5 s after the crash, so the total is between 10 and 15 s).
AnswerAbout 10 to 15 seconds of failed requests, unless the LB also retries on another backend.
CheckMore frequent checks (1 s) shrink it to 2 to 3 s, at the cost of more check traffic. This trade-off appears in system design interviews.

Check yourself

  1. What is the difference between L4 and L7 load balancing? Answer: L4 routes by IP and port; L7 reads HTTP and can route by path or header.
  2. What is a cache hit? Answer: the requested item was found in the cache, so no trip to the origin.
  3. What does a health check do? Answer: tests regularly whether a backend is alive so the LB stops sending it traffic when it is not.

4.5 Latency, Bandwidth and Throughput

INTUITION
Think of a water pipe. Latency is how long the first drop takes to travel to the other end (depends on pipe length). Bandwidth is how wide the pipe is, how much water per second can flow. Throughput is how much water actually arrives per second in practice (often less than the width). A long thin pipe and a short fat pipe behave very differently for small and large jobs.

Formal definitions

TermMeaningUnit
Latencytime for one message to go from A to B (or RTT for a round trip)ms
Bandwidthmaximum data per second the link can carryMbps (megabits per second)
Throughputdata per second actually achieved; also, in testing, requests per secondMbps or req/s
Bandwidth-delay product (BDP)data "in flight" needed to fill the pipe = bandwidth × RTTbytes

Remember: 8 bits = 1 byte. Network speeds are in bits per second, file sizes in bytes. A 100 Mbps link moves at most 100 / 8 = 12.5 megabytes per second.

Transfer time estimate: time = RTT + size × 8 / bandwidth. Run this for three jobs on two links at RTT 50 ms:

def transfer_ms(size_bytes, rtt_ms, mbps, round_trips=1):
    return round_trips*rtt_ms + size_bytes*8/(mbps*1e6)*1000
for name,size in [("1 KB API reply",1_000),("1 MB image",1_000_000),("1 GB dataset",1_000_000_000)]:
    print(f"{name:15s} RTT=50ms: 10Mbps={transfer_ms(size,50,10):10.1f} ms   1000Mbps={transfer_ms(size,50,1000):9.1f} ms")
print("BDP at 100 Mbps, 80 ms RTT:", 100e6*0.080/8/1e3, "KB in flight")

Predict which job benefits from the faster link. Real output:

1 KB API reply  RTT=50ms: 10Mbps=      50.8 ms   1000Mbps=     50.0 ms
1 MB image      RTT=50ms: 10Mbps=     850.0 ms   1000Mbps=     58.0 ms
1 GB dataset    RTT=50ms: 10Mbps=  800050.0 ms   1000Mbps=   8050.0 ms
BDP at 100 Mbps, 80 ms RTT: 1000.0 KB in flight

Reading it: for the small API reply, a 100 times faster link changes nothing (50.8 vs 50.0 ms): latency dominates. For the 1 GB dataset, the faster link saves almost everything (800 s down to 8 s): bandwidth dominates. The image sits in between. BDP says that on a 100 Mbps, 80 ms path, about 1,000 KB must be on the wire at once to keep it full, which is why TCP window size matters on long-distance links.

KEY INSIGHT
Many small calls are limited by latency, so you cannot fix them by buying bandwidth. Batch them (one call with 30 items instead of 30 calls), reuse connections, or move the client closer to the server (same region).

Problem 4.5.1 Copy a 2 GB file over a 200 Mbps link. Ignore RTT. How long?

Formulatime = size × 8 / bandwidth
Plug in2 × 10⁹ bytes × 8 / 200 × 10⁶ bits per second
Compute16 × 10⁹ / 200 × 10⁶ = 80
Answer80 seconds at best (real transfers are slower due to overheads).
Check200 Mbps = 25 MB/s, and 2,000 MB / 25 = 80 s. Both routes agree.

Problem 4.5.2 A page needs 12 sequential API calls, each with RTT 40 ms and 10 ms of server time. What is the minimum total time, and what would parallel calls change?

Step 1Each call costs 40 + 10 = 50 ms.
Step 2Sequential: 12 × 50 = 600 ms.
Step 3If all 12 run in parallel (and nothing else limits them): about 50 ms.
Answer600 ms sequential, about 50 ms in parallel, a 12 times gain.
CheckIn practice, limits such as server capacity and browser connection counts keep the gain below 12. In Chapter 12 you will see how this connects to Little's law (concurrency = throughput × latency).

Tools

  • ping host measures RTT (ICMP). On our loopback it printed 2 packets transmitted, 2 packets received, 0.0% packet loss and an average of about 0.15 ms.
  • traceroute host lists hops; mtr combines ping and traceroute (not run here).
  • ss -tulpn (Linux) or netstat shows listening ports and connections. A pile of TIME_WAIT or ESTABLISHED sockets can explain why a server stops accepting new visitors.
  • tcpdump and Wireshark capture packets to see handshakes, retransmissions and resets. They need administrator rights, so they were not run here. A first command to try on Linux: sudo tcpdump -i any port 443 -c 20.

Applications

  • Web operations: separate network time from server time; place servers near users to cut long-distance delay.
  • Data Engineering: bulk loads are bandwidth-bound; row-by-row inserts over a network are latency-bound (use batches).
  • ML: downloading a 20 GB model is bandwidth; thousands of tiny feature-store calls are latency.
  • Cloud design: keep chatty services in one region.
COMMON MISTAKE
Mixing megabits and megabytes. A "1 Gbps" link moves about 125 MB/s, not 1,000 MB/s. Also: measuring bandwidth with a tiny file; slow start makes tiny transfers look slow.

Check yourself

  1. Which dominates for a 1 KB reply, latency or bandwidth? Answer: latency.
  2. How many MB/s is a 100 Mbps link? Answer: at most 12.5 MB/s.
  3. Why batch API calls? Answer: each call pays at least one round trip, so fewer calls pay less.

Chapter recap

  • Networks work in layers: Application (HTTP, DNS, TLS), Transport (TCP, UDP), Internet (IP), Link (Wi-Fi, Ethernet).
  • A /24 has 254 usable addresses; each prefix bit doubles or halves the block.
  • DNS turns names into IPs and caches them for the TTL; DNS changes are not instant.
  • TCP is reliable and needs a handshake (1 RTT); UDP is simple and unreliable; QUIC (HTTP/3) is built on UDP.
  • A new HTTPS connection costs about 2 RTT of set-up (TCP + TLS 1.3) before the request; reuse connections.
  • TLS gives encryption, integrity and authentication. Never disable certificate checks in production.
  • 4xx are client errors, 5xx server errors; 429 means slow down, 502 vs 504 means bad reply vs timeout.
  • Load balancers (L4 or L7), reverse proxies, CDNs and firewalls sit between users and servers; a CDN hit ratio changes average latency.
  • Latency dominates small transfers; bandwidth dominates large ones. 8 bits = 1 byte.

Practice set

  1. (Easy) How many usable hosts are in a /28? Answer: 2⁴ − 2 = 14.
  2. (Easy) Which port does HTTPS use by default? Answer: 443.
  3. (Easy) Convert 100 Mbps to MB/s. Answer: 100 / 8 = 12.5 MB/s.
  4. (Medium) What is the output type of dig +short localhost? Answer: the IP address 127.0.0.1 (loopback: this machine).
  5. (Medium) RTT is 25 ms. How long until the first response byte on a fresh plain HTTP (no TLS) connection, ignoring server time? Answer: 1 RTT handshake + 1 RTT request/response = 50 ms.
  6. (Medium) CDN: edge 30 ms, origin 300 ms, hit ratio 80%. Average? Answer: 0.8 × 30 + 0.2 × 300 = 24 + 60 = 84 ms.
  7. (Find the bug) A script uses requests.get(url, verify=False) to avoid an SSL error. What is wrong and what is the right fix? Answer: it turns off server authentication, so a man-in-the-middle can read or change traffic. Fix: install the correct CA certificate (or use the right trusted chain) and keep verification on.
  8. (Find the bug) A speed check of a web site gets 100% cache hits and "great" waits of 15 ms. Production users see 300 ms. Why? Answer: the check hit the CDN or cache for the same URL; use unique URLs or test the origin.
  9. (Scenario) After a deploy, 5% of requests return 502. Give three things to check. Answer: backend crashes or restarts (health checks, logs), backend closing keep-alive connections earlier than the LB expects (timeout mismatch), and the LB-to-backend protocol or port mismatch.
  10. (Scenario) A nightly job inserts 1 million rows one at a time to a database 20 ms RTT away and takes hours. Why, and how do you fix it? Answer: each insert costs at least 20 ms: 1,000,000 × 0.02 s = 20,000 s (about 5.6 hours). Batch thousands of rows per call, or use bulk load.
  11. (Interview) Explain what happens when you type https://api.example.com/login and press Enter. Answer: DNS lookup (cache first), TCP handshake to port 443, TLS handshake (certificate check, keys), HTTP request sent encrypted, maybe through a CDN and a load balancer to a backend, the backend replies, the client reads the status and body, and may keep the connection for reuse.
  12. (Interview) Difference between latency, bandwidth and throughput? Answer: latency is delay for one message; bandwidth is the maximum capacity of the link; throughput is what you actually achieve (data or requests per second).
