Think of the last time you saved report_final.xlsx, then report_final_v2.xlsx, then report_final_v2_REAL.xlsx. Now imagine 10 people doing that to one codebase, every day. That is the problem Git solves. Git records every change you make as a numbered snapshot, lets you go back in time, and lets many people work in parallel without overwriting each other. GitHub is a website that stores Git projects online and adds teamwork features: code review, issue lists and automatic tests. Every data and ML team uses them, and interviewers expect you to know them. By the end of this chapter you can create a repository, work on branches, merge and rebase, resolve a conflict, undo mistakes safely, hunt down the commit that broke something with bisect, and understand a GitHub pull request and a CI file.

Our running example is a tiny shopping-cart project called shop with one Python file, cart.py. Everything below was run for real in /tmp/cs_lab/ch3. Git commit IDs (hashes such as d96abba) are different on every machine, so yours will not match ours. That is normal.

3.1 Commits: The Daily Loop

BASIC EXPLANATION
A Git commit is a saved snapshot of your project with a message. The daily loop is edit files, stage them with git add, and record them with git commit.
INTUITION
Imagine writing a thesis. At the end of each good day you take a photograph of the whole desk and write a label on it: "Added chapter 2". You never throw the photos away. Git does exactly that. A photo is a commit. The desk is your project folder.

Words you need

WordPlain meaning
Repository (repo)A project folder plus its whole history (kept in a hidden .git folder)
Working directoryThe files you see and edit now
Staging area (index)A waiting room where you place the changes you want in the next commit
CommitA saved snapshot with a message, an author, a time and a unique ID (hash)
BranchA movable label that points to a commit
HEAD"You are here": the commit you are working on

How it works

The daily loop has three moves: edit, add (move changes to the waiting room), commit (take the photo).

 edit files ──► git add ──► git commit
 (working dir)  (staging)    (repository history)

The commands you use every day:

CommandWhat it does
git initstart a new repo in this folder
git clone URLcopy an existing repo (with its history) from the internet
git statuswhat changed, what is staged
git add filestage a file
git commit -m "message"save the staged changes
git log --onelineshort history
git diffwhat changed but is not staged yet
git push / git pullsend your commits to GitHub / bring others' commits to you
git fetchdownload others' commits but do not change your files yet

git pull is just git fetch plus a merge. Fetch is the safe way to look first.

Predict, run, explain

Before you run this, predict what git status --short prints before and after git add.

git init -q -b main shop && cd shop
printf 'def total(prices):\n    return sum(prices)\n' > cart.py
git status --short
git add cart.py
git status --short
git commit -q -m "Add total()"

Real output of the two status commands, then git log --oneline after two commits:

?? cart.py
A  cart.py
  • ?? means "Git sees this file but is not tracking it".
  • A means "added to the staging area, waiting for a commit".

After we added a second function tax() and committed:

d96abba Add tax()
3b81e41 Add total()

Each line is one commit: a short hash and the message. Newest is on top.

Typical wrong version. You edit a file and run git commit -m "fix" without git add. Git answers no changes added to commit. Fix: git add file first, or use git commit -am "message", which stages all already-tracked files for you. (-am does not pick up brand new files.)

Good commit messages

Write the message as an order: "Add tax()", "Fix null check in loader". One idea per commit. Small commits make bisect and code review easy (sections 3.3 and 3.4).

Problem 3.1.1 You have changed cart.py and created notes.txt. You run git add cart.py then git commit -m "Update cart". What is committed?

Step 1Only staged files go into a commit.
Step 2cart.py is staged. notes.txt is new and never staged.
AnswerOnly cart.py is committed. notes.txt stays untracked (?? in git status --short).
CheckRun git status --short. It still lists ?? notes.txt. The waiting room (staging area) lets you build clean commits even when your folder is messy.

Problem 3.1.2 git diff shows nothing, but git status says Changes to be committed. Why?

Step 1git diff compares the working directory to the staging area.
Step 2If every change is already staged, there is no difference between those two.
AnswerUse git diff --staged (or --cached) to see staged changes.
CheckRun both: the first prints nothing, the second prints the + and - lines. In plain words, the diff command has two views, and you must ask for the right one.

3.2 Branches and Merging

BASIC EXPLANATION
A branch is a separate line of commits inside a repository, used to work on a change without affecting the main line. Merging combines the commits of one branch into another.
INTUITION
A branch is a parallel copy of the story. While the main storyline continues, you try a new idea on a side road. If it is good, you join the road back to the main one (a merge). If not, you abandon the side road and nothing is lost. Branches are cheap in Git: a branch is only a small label pointing to a commit.

How it works

  • git branch lists branches. git switch -c name creates a branch and moves to it. (git checkout -b name is the older way.) git switch main goes back.
  • git merge other brings the commits of other into your current branch.
  • If the other branch did not diverge, Git just moves the label forward. This is a fast-forward. If both sides changed, Git creates a merge commit with two parents.

Predict, run, explain

We add discount() on a feature branch, meanwhile someone adds a README on main. Then we merge.

git switch -q -c feature/discount
printf '\ndef discount(x):\n    return x * 0.9\n' >> cart.py
git commit -qam "Add discount()"
git switch -q main
printf '# README\n' > README.md; git add README.md; git commit -qm "Add README"
git merge -q --no-edit feature/discount
git log --oneline --graph

Before you look: how many parents will the last commit have? Real output:

*   389eee1 Merge branch 'feature/discount'
|\  
| * 5889617 Add discount()
* | bfe94eb Add README
|/  
* d96abba Add tax()
* 3b81e41 Add total()

Line by line: the * marks a commit. The two lines |\ and |/ show the history splitting and joining. The merge commit at the top has two parents: bfe94eb (main) and 5889617 (feature). Both sides changed different files, so Git merged them automatically.

How to read the picture: time goes left to right. The blue line is main; the green dots are commits made on the feature branch. The orange circle is the merge commit, joining the two lines.

Merge conflicts

A conflict happens when both branches changed the same lines. Git cannot guess which is right, so it stops and asks you. We make two branches that set the tax rate differently (20% and 12%) and merge them:

CONFLICT (content): Merge conflict in cart.py
Automatic merge failed; fix conflicts and then commit the result.

Git writes both versions into the file with markers:

def tax(x):
<<<<<<< HEAD
    return x * 0.12
=======
    return x * 0.20
>>>>>>> a
  • Between <<<<<<< HEAD and ======= is your version (the branch you are on).
  • Between ======= and >>>>>>> a is their version (branch a).

To resolve: Step 1 edit the file so it holds the one correct version and delete all three marker lines. Step 2 git add cart.py. Step 3 git commit. We chose 20%, so the file became:

def tax(x):
    return x * 0.20

The log then shows Resolve conflict: tax 20% on top. If you panic, git merge --abort returns you to before the merge. Never leave the marker lines in the file: Python would raise a SyntaxError.

Problem 3.2.1 main has commits A-B-C. You branch from B and make D. Then you merge your branch into main. Is it a fast-forward?

Step 1main moved forward (C) after you branched, so histories diverged.
Step 2Git cannot just move the main label to D, because that would lose C.
AnswerNo. Git makes a merge commit with parents C and D.
CheckNow suppose main had stayed at B. Then D simply extends it and Git moves the label: a fast-forward. The test is "is my current branch an ancestor of the other branch?".

Problem 3.2.2 After a conflict you run git status --short and see UU cart.py. What does it mean?

Step 1The two letters describe the state in each side.
Step 2UU means "unmerged, both modified".
AnswerThe file needs your manual fix, then git add.
CheckAfter you git add cart.py, the status changes to M (staged), which tells you Git accepts the resolution.

3.3 Rebase, Stash, Cherry-pick, Reset, Revert, Reflog

BASIC EXPLANATION
These Git commands change or recover history. rebase replays commits on a new base, stash saves unfinished changes, cherry-pick copies one commit, reset and revert undo commits, and reflog shows where the branch pointers have been.
INTUITION
Merging is like stapling two notebooks together: the history shows both. Rebase is like copying your pages onto the end of the newest notebook, so the story looks like a straight line. Stash is a drawer where you put unfinished work to answer a phone call. Cherry-pick takes one single page from another notebook. Revert adds a new page that cancels an old page. Reset tears pages out (dangerous when others have them). Reflog is a security camera that remembers everything you did locally, even what you "lost".

Rebase

Before: main got a new commit (Add config) after we started feat2. git rebase main replays our commit on top of the new main.

before:                          after:
* a04b3df Add config  (main)     * 4d6f240 docs: v2        (feat2)
| * 699a356 docs: v2  (feat2)    * a04b3df Add config
|/                               * 78e2825 Resolve conflict...
* 78e2825 Resolve ...

Notice that docs: v2 has a new hash (699a356 became 4d6f240). The commit was rewritten. This is why the golden rule exists: never rebase commits that other people already pulled. Rebase your own private branch freely; never rebase shared main.

Interactive rebase (git rebase -i HEAD~3) opens an editor where you can squash several small commits into one, reword messages or drop commits before you open a pull request. (We did not run an interactive session here because it needs an editor; the idea is simple: change the word pick to squash or reword on a line.)

Stash

echo "work in progress" >> README.md
git status --short      # shows: " M README.md"
git stash -q            # put the work in the drawer
git status --short      # nothing printed: clean
git stash list
git stash pop -q        # take it out again
 M README.md
(clean)
stash@{0}: WIP on main: a04b3df Add config
 M README.md

(The (clean) line is an echo we printed because git status --short printed nothing at that point.)

Cherry-pick

git switch -q -c hotfix main~1
echo "fix" > fix.txt; git add fix.txt; git commit -q -m "Hotfix"
git switch -q main
git cherry-pick <hash-of-hotfix>
git log --oneline | head -2
a3ae49b Hotfix
a04b3df Add config

The hotfix commit was copied onto main with a new hash. Used for "port this one bug fix to the release branch".

Reset versus revert

git revert <commit>git reset --hard <commit>
What it doesAdds a new commit that undoes an old oneMoves the branch label back; discards later commits
HistoryPreservedRewritten
Safe on shared branches?YesNo
Use whenThe bad commit is already pushedThe bad commit is only local

Real run of both:

0779375 Revert "Bad commit"     <- after git revert: file bad.txt is gone
e8e6243 Bad commit
a3ae49b Hotfix

and after git reset --hard HEAD~1 removed a second local bad commit, the log returned to the line above (0779375 ... e8e6243 ...).

Reflog

You reset by mistake and the commit disappeared? git reflog lists where HEAD has been:

0779375 HEAD@{0}: reset: moving to HEAD~1
e42a11b HEAD@{1}: commit: Bad commit 2
0779375 HEAD@{2}: revert: Revert "Bad commit"
e8e6243 HEAD@{3}: commit: Bad commit

The "lost" commit e42a11b is still there. git reset --hard e42a11b brings it back. Reflog entries live locally for some weeks (the default is configurable), so act soon.

Tags

A tag is a permanent label on a commit, for releases. git tag -a v1.0 -m "release 1.0" creates one, git tag lists them, git push --tags shares them. In ML, tag the commit that produced the model you shipped.

Problem 3.3.1 You have just run git reset --hard HEAD~2 and realise you needed those commits. How do you get them back?

Step 1Run git reflog and find the line from before the reset, for example HEAD@{1}.
Step 2Run git reset --hard HEAD@{1}.
AnswerBoth lost commits return, because Git had not deleted them yet.
Checkgit log --oneline now lists the two commits again. This is why Git is hard to destroy by accident, as long as the work was committed once.

Problem 3.3.2 A bad commit was pushed to main 3 hours ago and 4 colleagues have pulled it. Reset or revert?

Step 1Resetting would rewrite shared history, so the colleagues' copies would disagree with yours.
Step 2Revert adds one new commit that cancels the bad one.
AnswerUse git revert <hash> and push. Everyone just pulls one extra commit.
CheckIn our real run, after git revert the file bad.txt was gone (ls: bad.txt: No such file or directory) while the "Bad commit" line stayed in history for audit.

Check yourself

  1. Which is safe on shared branches, reset or revert? Answer: revert.
  2. Why does a rebased commit have a new hash? Answer: the commit is rewritten with a new parent, and the hash covers the parent.
  3. What does git stash pop do? Answer: re-applies the stashed changes and removes them from the stash list.

3.4 Bisect: Find the Commit That Broke Things

BASIC EXPLANATION
git bisect uses binary search over the commit history to find the first commit that introduced a bug. You mark commits as good or bad until Git points to the culprit.
INTUITION
Your model's accuracy was fine last month and is bad today, and 100 commits happened between. Reading all of them is slow. Instead, play "guess my number": test the commit in the middle. Good or bad? Throw away half. After 7 tests (since 2⁷ = 128 ≥ 100) you find the exact culprit. That is binary search on history (you meet it in Chapter 8).

How it works

  1. git bisect start
  2. git bisect bad (current commit is bad) and git bisect good <old commit>.
  3. Git checks out the middle commit. You test, then say git bisect good or git bisect bad. Repeat.
  4. Or automate: git bisect run <command>, where the command's exit code (0 = good, 1-127 = bad) decides. This is why exit codes from Chapter 2 matter.
  5. git bisect reset returns to where you were.

Predict, run, explain

We built 8 commits. From commit 5 on, a file state.txt contains slow instead of fast. The test command is grep -q fast state.txt, which exits 0 when the word fast is found.

git bisect start
git bisect bad HEAD
git bisect good HEAD~7
git bisect run sh -c 'grep -q fast state.txt'

Real output (trimmed to the key line):

dc957cb681eecc87764fb4ab9247bf8f75bd3876 is the first bad co...

Before this, git log --oneline had shown dc957cb commit 5. So Git found "commit 5" as the first bad commit, which matches how we built the data.

Problem 3.4.1 There are 100 commits between a good and a bad one. At most how many tests does bisect need?

Formulatests = ⌈log₂(N)⌉
Plug inlog₂(100)
Compute2⁶ = 64 is less than 100, and 2⁷ = 128 is at least 100, so ⌈log₂ 100⌉ = 7
AnswerAt most 7 tests.
CheckAfter 7 halvings, 100 / 128 is below 1 commit left. Compare with checking commits one by one: up to 100 tests. In plain words, bisect turns a day of reading into a few minutes.

Problem 3.4.2 Why does git bisect run need a script that returns exit code 0 or non-zero?

Step 1Bisect must know good or bad automatically.
Step 2It uses the exit code: 0 good, 1 to 127 (except 125) bad, 125 means "skip this commit".
AnswerAny test (a unit test, a grep, a performance threshold) can drive it, as long as it returns a correct exit code.
CheckIn our run grep -q returned 1 when fast was missing, so those commits counted as bad.

ItemExampleWhere it appears in the job

  2. What does git bisect reset do? Answer: ends the session and returns you to your original branch.

3.5 GitHub: Pull Requests, Review and Actions

BASIC EXPLANATION
GitHub is a hosting service for Git repositories. A pull request (PR) proposes merging one branch into another and lets others review it, and GitHub Actions runs automated workflows such as tests.
INTUITION
Git works on your laptop. GitHub is the shared office. A pull request (PR) says: "I finished branch feature/discount. Please review it before it joins main." Colleagues read the diff, comment, and approve. Meanwhile robots (GitHub Actions) run the tests. Nothing reaches production without a second pair of eyes and green checks.

How it works

Not run here: GitHub needs an account and internet, so the following is the standard workflow.

  1. git clone the repo (or fork it on GitHub, if you are not a member).
  2. git switch -c feature/discount, edit, commit.
  3. git push -u origin feature/discount (publishes your branch).
  4. On GitHub, click Compare and pull request, write a clear description (what, why, how tested).
  5. Reviewers comment on specific lines. You fix with new commits and push again.
  6. When approved and checks pass, merge (merge commit, squash, or rebase, depending on team rule).
  7. Delete the branch.

GitHub features a data professional meets:

FeatureWhat it is

Good code review habits

  • Keep PRs small (under about 400 changed lines is a common rule of thumb).
  • As an author: explain why. As a reviewer: be kind, be specific, ask questions.
  • Review for correctness, readability, tests and security (no secrets).

GitHub Actions intro

CI (continuous integration) means: every push automatically builds the project and runs the tests, so a broken change is caught within minutes. A workflow is a YAML file in .github/workflows/. A YAML file is a text format of nested key: value lines, where indentation shows structure. Here is a standard Python test workflow:

name: CI
on:
  push:
    branches: [main]
  pull_request:
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install -r requirements.txt
      - run: python -m pytest -q

We checked here that this file is valid YAML and has the keys name, on, jobs, and 4 steps in the test job. We could not run it (it needs GitHub). Version tags such as @v4 change over time; look up the current ones in the docs.

Read it like a recipe: on is the trigger (a push to main, or any pull request). runs-on chooses the machine. Each step either uses a ready-made action (uses) or runs a shell command (run). If any command exits non-zero (Chapter 2!), the job fails and the PR shows a red cross.

Secrets (cloud keys, tokens) go in GitHub Secrets, never in the YAML file. Reference them as ${{ secrets.NAME }}.

Problem 3.5.1 A PR changes 1,200 lines in 25 files. Why will review quality suffer, and what do you do?

Step 1Reviewers lose focus on large diffs, so bugs slip through.
Step 2Split by topic: for example 3 PRs of about 400 lines each (1,200 / 3 = 400).
AnswerBreak it into smaller, ordered PRs, each with its own description and tests.
Check3 x 400 = 1,200, so no code is lost. Smaller PRs also merge sooner and cause fewer conflicts.

Problem 3.5.2 In the YAML above, what happens when pytest finds one failing test?

Step 1pytest exits with a non-zero code when a test fails.
Step 2A step with a non-zero exit code fails the job, and later steps do not run.
AnswerThe workflow shows red, and with branch protection the PR cannot be merged.
CheckThis is the same exit-code rule you tested in Chapter 2 (false; echo $? printed 1).

3.6 Advanced Git: Rebase Cleanup, Conflicts, Worktrees and Branching Strategy

BASIC EXPLANATION
Advanced Git covers cleaning up commits with interactive rebase, resolving merge conflicts, using worktrees to check out several branches at once, and choosing a branching strategy for a team.
INTUITION
Git history is a document other people will read for years. While you work, make as many tiny "wip" commits as you like. Before you share, edit the story: squash the noise, reorder, reword. That is interactive rebase. Conflicts are the other everyday skill: git asks you to pick, you decide what the file should say, and that decision is a normal commit.

Every example below was run with real git in a scratch folder (the commit hashes differ on your machine, so they are not shown). The setup line sets a name and email only for these demos.

Tidying commits with interactive rebase

Normally git rebase -i HEAD~4 opens an editor where you change the word pick in front of each commit to squash (merge into the previous), reword (edit the message), drop (delete) or reorder the lines. The demo below feeds the editor automatically so you can see the result.

Problem 3.6.1 A feature branch has four commits: a real one, two "fix typo" commits and a debug print. Turn them into one clean commit.

Step 1List the commits: git log --oneline. Decide that all four belong together.
Step 2Start git rebase -i HEAD~4. Keep the first line as pick, change the other three to squash.
Step 3Git combines the messages; edit them into one sentence.
WarningRebase rewrites history. Only do it on commits you have not shared, or on your own feature branch (then push with --force-with-lease).
export GIT_AUTHOR_NAME=Demo GIT_AUTHOR_EMAIL=d@example.com GIT_COMMITTER_NAME=Demo GIT_COMMITTER_EMAIL=d@example.com
git init -q -b main repo && cd repo
echo base > app.txt; git add .; git commit -q -m "initial"
echo "feature" >> app.txt; git commit -qam "add feature"
echo "feature typo fix" >> app.txt; git commit -qam "fix typo"
echo "another fix" >> app.txt; git commit -qam "fix typo again"
echo "print(debug)" >> app.txt; git commit -qam "remove debug print"
echo "--- before:"; git log --oneline | sed 's/^[0-9a-f]* /  /'
GIT_SEQUENCE_EDITOR="sed -i.bak '2,4s/^pick/squash/'" GIT_EDITOR="sed -i.bak '1s/.*/add feature (clean)/;2,\$d'" git rebase -i HEAD~4 >/dev/null 2>&1
echo "--- after:"; git log --oneline | sed 's/^[0-9a-f]* /  /'
echo "--- file content unchanged:"; cat app.txt
--- before:
  remove debug print
  fix typo again
  fix typo
  add feature
  initial
--- after:
  add feature (clean)
  initial
--- file content unchanged:
base
feature
feature typo fix
another fix
print(debug)
COMMON MISTAKE
Rebasing a branch that teammates already pulled. Wrong: git rebase main then git push --force on a shared branch, which makes their copies diverge and can erase their commits. Right: rebase only private branches, use --force-with-lease (it refuses if someone pushed meanwhile), and tell people before you rewrite anything shared.

Resolving a merge conflict, step by step

Problem 3.6.2 Two branches change the same line of a config file. Merge them and resolve the conflict.

export GIT_AUTHOR_NAME=Demo GIT_AUTHOR_EMAIL=d@example.com GIT_COMMITTER_NAME=Demo GIT_COMMITTER_EMAIL=d@example.com

Three helpful tools: git merge --abort to back out, git checkout --ours file or --theirs file to take one side whole, and git rerere (reuse recorded resolution) so a conflict you solved once is solved automatically when it repeats during a long rebase.

Worktrees: two branches, two folders, one repository

Problem 3.6.3 You are mid-change on a feature and must fix a bug on main now. Avoid stashing: check out main in a second folder.

export GIT_AUTHOR_NAME=Demo GIT_AUTHOR_EMAIL=d@example.com GIT_COMMITTER_NAME=Demo GIT_COMMITTER_EMAIL=d@example.com
git init -q -b main repo && cd repo
echo v1 > app.txt; git add .; git commit -q -m "v1"
git checkout -q -b feature; echo "half-done work" > wip.txt
git worktree add -q ../hotfix main
echo "--- worktrees:"; git worktree list | sed 's#.*/##' | awk '{print $1, $3}'
echo "--- hotfix folder has:"; ls ../hotfix
echo "--- feature folder still has:"; ls
git worktree remove ../hotfix
--- worktrees:
repo [feature]
hotfix [main]
--- hotfix folder has:
app.txt
--- feature folder still has:
app.txt
wip.txt

Each worktree has its own working files and checked-out branch but shares the same .git object database, so it is far cheaper than a second clone. Git refuses to check out the same branch in two worktrees, which prevents confusing overlaps.

Signed commits, CI caching and a test matrix

These need an account or a GitHub runner, so they are shown but not run here. Signing proves a commit came from the key holder (author names in git are only text anyone can type). With an SSH key: git config gpg.format ssh, git config user.signingkey ~/.ssh/id_ed25519.pub, git config commit.gpgsign true. A GitHub Actions workflow that tests two Python versions on two operating systems, with the pip cache turned on:

name: tests
on: [pull_request]
jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, macos-latest]
        python: ["3.11", "3.12"]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python }}
          cache: pip
      - run: pip install -r requirements.txt
      - run: pytest -q

The matrix expands to 2 x 2 = 4 jobs that run in parallel. fail-fast: false lets all four finish so you see every failure at once. The cache key is derived from requirements.txt, so the dependencies are downloaded only when that file changes.

KEY IDEA
Submodules pin another repository at an exact commit inside yours (git submodule add URL path). They are precise but easy to forget to update: after git pull run git submodule update --init --recursive. For internal code, prefer a versioned package over a submodule; for a monorepo, use path-filtered CI so a change in one folder tests only what it affects.

Chapter recap

  • Git stores snapshots (commits). The loop is edit, add, commit.
  • A branch is a cheap label. Create one for every task.
  • A merge joins histories; a conflict means both sides changed the same lines and you must choose.
  • Rebase replays your commits on a new base and gives them new hashes. Never rebase shared history.
  • Stash parks unfinished work; cherry-pick copies one commit.
  • Use revert on shared branches and reset only on local ones. reflog can rescue a mistake.
  • bisect is binary search on history and can run automatically from an exit code.
  • A pull request plus review plus CI is the standard way to change main.
  • GitHub Actions workflows are YAML files in .github/workflows/. Secrets go in GitHub Secrets.
  • Never commit data, passwords or keys. Use .gitignore from day one.

Practice set

  1. (Easy) What does git add . do? Answer: it stages all changes and new files in the current folder tree.
  2. (Easy) Which command shows only staged changes? Answer: git diff --staged.
  3. (Easy) What is HEAD? Answer: a pointer to the commit (usually via a branch) you are currently on.
  4. (Medium) What is the output type of git log --oneline for 3 commits? Answer: 3 lines, each with a short hash and the message, newest first.
  5. (Medium) You are on feature, and main has moved on. You want a straight history. Which command and which risk? Answer: git rebase main; the risk is that commits get new hashes, so do it only on a branch nobody else uses.
  6. (Find the bug) After a merge conflict, python cart.py shows SyntaxError: invalid syntax near <<<<<<< HEAD. Why? Answer: the conflict markers are still in the file. Edit them out, git add, commit.
  7. (Find the bug) You ran git commit -m "x" and Git replied nothing added to commit but untracked files present. Why? Answer: the new files were never staged. Use git add file.
  8. (Scenario) You are halfway through an experiment when your manager reports a production bug. What do you do? Answer: git stash (or commit to a WIP branch), switch to main, make a hotfix branch, fix, open a PR, then come back and git stash pop.
  9. (Scenario) A 40 MB data file was committed 3 commits ago and not pushed. How to remove it? Answer: git reset --soft HEAD~3 or an interactive rebase to rewrite the commits without the file, then add it to .gitignore. If it was pushed, history rewriting plus a coordinated force-push is needed, and any secrets in it must be rotated.
  10. (Interview) Explain merge versus rebase. Answer: merge keeps both histories and adds a merge commit (safe, shows the true timeline). Rebase moves your commits on top of the target, giving a linear history but new hashes, so it is for private branches only.
  11. (Interview) 500 commits ago the API p95 was 200 ms; now it is 900 ms. How do you find the culprit? Answer: git bisect with a script that times a batch of requests and exits 1 if the p95 is above a limit. About ⌈log₂ 500⌉ = 9 tests.
  12. (Interview) What is the difference between git fetch and git pull? Answer: fetch downloads remote commits without touching your files; pull = fetch + merge (or rebase).
