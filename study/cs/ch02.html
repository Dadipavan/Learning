2.1 Variables, Conditionals, Loops and Functions

BASIC EXPLANATION
A shell script is a file of shell commands run together. It uses variables to store values, conditionals (if) to make decisions, loops to repeat steps and functions to reuse code.
INTUITION
A script is a recipe. Variables are labelled jars (store a value). A conditional is "if the oven is hot, bake; else wait". A loop is "repeat for each tray". In kitchen terms: variables are the labelled jars, a loop is the cook repeating a step for every tray, and if is the cook checking the oven before baking.

How it works

  • Variable: name="perf" (no spaces around =). Read it with $name or ${name}. Always quote: "$name".
  • Command substitution: $(command) runs a command and inserts its output.
  • Arithmetic: $((count+1)).
  • Default value: ${VAR:-fallback} uses fallback if VAR is unset or empty. ${#name} is the length.
  • Conditions: [ ... ] or [[ ... ]]. Number tests: -eq -ne -gt -lt -ge -le. String tests: =, !=. File tests: -f (is a file), -d (folder), -s (not empty), -r (readable).
  • Loops: for x in a b c; do ...; done and while cond; do ...; done.
  • Function: greet() { echo "hi $1"; }. $1 is the first argument.

Worked example

name="perf"
count=3
echo "Hello $name, count=$count, next=$((count+1))"
files=$(ls *.csv | wc -l)
echo "csv files: $files"
echo "len of name: ${#name}; default: ${UNSET_VAR:-fallback}"
if [ "$count" -gt 2 ]; then echo "big"; elif [ "$count" -eq 2 ]; then echo "two"; else echo "small"; fi
if [ -f access.csv ] && [ -s access.csv ]; then echo "file exists and not empty"; fi
if [[ "$name" == p* ]]; then echo "starts with p"; fi
for e in /login /search /cart; do echo "$e: $(grep -c "$e" access.csv)"; done
i=0; while [ $i -lt 3 ]; do echo "i=$i"; i=$((i+1)); done

Real output:

Exit codes

Every command ends with a number called the exit code. 0 means success. Anything else means failure. The special variable $? holds the last exit code.

false; echo "exit of false: $?"
true; echo "exit of true: $?"
grep -q zzz access.csv; echo "grep no match exit: $?"
exit of false: 1
exit of true: 0
grep no match exit: 1

Notice that grep returns 1 when nothing matches. That is not an "error"; it is a "no". Schedulers like cron and Airflow decide success or failure only from the exit code.

KEY INSIGHT
Exit code 0 means OK. A script that fails silently with exit 0 is worse than a script that crashes loudly, because nobody notices.

The picture

Read this diagram from the top: every command produces a number, and && / || let you choose the next step from that number.

 command ──► runs ──► exit code
                         0 ─► success ─► next step (&&)
                         ≠0 ─► failure ─► stop or handle (||)
 cmd1 && cmd2   run cmd2 only if cmd1 succeeded
 cmd1 || cmd2   run cmd2 only if cmd1 failed

Connection to the real job

ETL scripts check file existence, loop over dates or partitions, and return the right exit code so the scheduler can retry. Test-automation scripts (start a service, run the checks, collect the results) use the same building blocks.

Applications

  • Data download and load scripts
  • Batch job wrappers (Airflow BashOperator, cron)
  • CI pipeline steps
  • Environment set-up on servers
COMMON MISTAKE
Forgetting quotes. [ $name = x ] breaks if name is empty or has spaces. Write [ "$name" = x ]. Also, spaces are required inside [ ], and none are allowed around = in an assignment.

Check yourself

  1. What is $?? Answer: the exit code of the last command.
  2. What does ${X:-5} give when X is unset? Answer: 5.
  3. What does a && b mean? Answer: run b only if a succeeded.

2.2 Safe Scripts: set -euo pipefail, Arguments, Traps

BASIC EXPLANATION
Safe scripting means making a script stop and report on errors instead of continuing. set -euo pipefail exits on failures and unset variables, and trap runs cleanup code when the script ends.
INTUITION
By default bash is dangerously relaxed: if step 2 of 5 fails, it happily runs steps 3 to 5 on bad data. Safe mode is like a factory line that stops the whole belt when one machine breaks.

How it works

Put this near the top of every script:

set -euo pipefail
OptionEffect
-eexit immediately if a command fails
-utreat use of an unset variable as an error (catches typos)
-o pipefaila pipeline fails if any part fails, not just the last

Real tests of each option:

bash -c 'false | true; echo "no pipefail: $?"'
bash -c 'set -o pipefail; false | true; echo "pipefail: $?"'
bash -c 'set -e; echo before; false; echo never'; echo "exit=$?"
bash -c 'set -u; echo $nothing'
no pipefail: 0
pipefail: 1
before
exit=1
bash: nothing: unbound variable

(The unbound variable line had a line-number prefix that we removed.) Without pipefail, false | true returns 0 because only the last command counts, so a failing download in the start of a pipe would be hidden.

A complete script with argument parsing

#!/usr/bin/env bash
set -euo pipefail
usage() { echo "Usage: $0 [-t threshold_ms] [-v] file" >&2; exit 2; }
threshold=200; verbose=0
while getopts "t:vh" opt; do
  case $opt in
    t) threshold=$OPTARG ;;
    v) verbose=1 ;;
    *) usage ;;
  esac
done
shift $((OPTIND-1))
[ $# -eq 1 ] || usage
file=$1
[ -r "$file" ] || { echo "cannot read $file" >&2; exit 1; }
[ $verbose -eq 1 ] && echo "threshold=$threshold file=$file"
slow=$(awk -F, -v t="$threshold" 'NR>1 && $4>t' "$file" | wc -l)
echo "slow requests (> ${threshold} ms): $slow"

Save it as report.sh, run chmod +x report.sh, and test four cases:

$ ./report.sh access.csv
slow requests (> 200 ms):        3
exit=0
$ ./report.sh -v -t 300 access.csv
threshold=300 file=access.csv
slow requests (> 300 ms):        2
exit=0
$ ./report.sh nofile.csv
cannot read nofile.csv
exit=1
$ ./report.sh
Usage: ./report.sh [-t threshold_ms] [-v] file
exit=2

What the pieces do:

  • #!/usr/bin/env bash (the shebang) says which program runs the file.
  • getopts "t:vh" opt reads options. t: means -t takes a value, v is a flag. The value lands in $OPTARG.
  • shift $((OPTIND-1)) removes the options so $1 is the file name.
  • >&2 sends a message to stderr, so it does not mix with normal output.
  • exit 2 for bad usage, exit 1 for a runtime problem. Pick consistent codes.
  • The slow requests above 300 ms are 340 and 900, so 2. Above 200 ms they are 340, 900, 210, so 3. Matches the output.

Clean-up with trap

tmp=$(mktemp -d /tmp/cs_lab/ch2/t.XXXX)
trap 'rm -rf "$tmp"; echo cleaned' EXIT
echo "working in a temp folder"

When the script ends, normally or by error, the trap runs and prints cleaned. (Real run: the script printed its work line and then cleaned.) mktemp -d makes a unique empty folder, so scripts never collide.

2.3 The Text Trio: grep, sed and awk

BASIC EXPLANATION
grep searches text for lines that match a pattern. sed is a stream editor that edits text, mostly by find and replace. awk processes each line as fields and can filter and calculate.
INTUITION
grep finds lines. sed edits lines (find and replace). awk treats each line as a small table row and computes on columns. Together they are the Swiss army knife for log and CSV work before you ever open Python or pandas.

grep: pattern search

A regular expression (regex) is a small language for text patterns. In grep -E (extended regex):

PatternMeaning
^ and $start and end of line
.any one character
[0-9]one digit
+, *, ?one or more, zero or more, optional
`(a\b)`
grep -E '^[0-9]+,/(login|cart),200' access.csv
grep -o '/[a-z]*' access.csv | sort -u
1,/login,200,120
4,/cart,200,210
6,/login,200,130
/cart
/login
/search

-o prints only the matching part. sort -u sorts and removes duplicates.

sed: stream editor

echo "2024-01-05 ERROR disk full" | sed 's/ERROR/WARN/'
printf 'a\nb\nc\n' | sed -n '2p'
printf 'a\nb\nc\n' | sed '/b/d'
echo "a  b   c" | sed -E 's/ +/ /g'
2024-01-05 WARN disk full
b
a
c
a b c
  • s/old/new/ substitutes (add g to replace every match on the line).
  • -n '2p' prints only line 2.
  • /b/d deletes lines that match.
  • -i edits a file in place. It differs between macOS (sed -i '') and Linux (sed -i), so test on a copy.

awk: columns and calculation

awk runs a rule on each line: pattern { action }. $1, $2 are columns, $0 is the whole line, NR is the line number, NF the number of columns, -F, sets the separator. BEGIN and END blocks run before and after all lines.

awk -F, 'NR>1{sum+=$4; n++} END{print "avg ms:", sum/n, "n:", n}' access.csv
awk -F, 'NR>1{c[$2]++} END{for(k in c) print k, c[k]}' access.csv | sort
awk -F, 'NR>1{s[$2]+=$4; n[$2]++} END{for(k in s) printf "%s %.1f\n", k, s[k]/n[k]}' access.csv | sort
awk -F, '$3>=400{print $1, $2}' access.csv
avg ms: 285.833 n: 6
/cart 1
/login 3
/search 2
/cart 210.0
/login 383.3
/search 177.5
ts endpoint
3 /login
5 /search

Check by hand: sum of ms is 120+340+900+210+15+130 = 1715; 1715 / 6 = 285.83. Login average is (120+900+130)/3 = 383.3. Search average is (340+15)/2 = 177.5. The ts endpoint line appears because the header's $3 is the text status, which awk compares as a string and finds greater than 400. That is a common surprise, so add NR>1 when a header exists.

PROFESSOR'S NOTE
awk arrays (c[$2]++) are hash maps. This is the same "group by and count" that SQL does with GROUP BY, and that you will do with Counter in Python (Chapter 7).

2.4 Scheduling with cron

BASIC EXPLANATION
cron is the Unix scheduler that runs commands automatically at set times. Each job is a line in a crontab with five time fields followed by the command.
INTUITION
An alarm clock for programs. You say "at 2 AM every night run this script". The computer does it while you sleep, for example a nightly data load.

How it works

cron is the Linux scheduler. You edit your schedule with crontab -e and list it with crontab -l. Each line has 5 time fields then the command:

┌───────── minute (0-59)
│ ┌─────── hour (0-23)
│ │ ┌───── day of month (1-31)
│ │ │ ┌─── month (1-12)
│ │ │ │ ┌─ day of week (0-7, Sunday is 0 or 7)
│ │ │ │ │
0 2 * * * /home/me/report.sh >> /home/me/report.log 2>&1

The last line means: at 02:00 every day, run the script and append all output (stdout and stderr) to a log file. (We only wrote this line, we did not install a cron job. Editing the real crontab is not done in this safe lab.)

ScheduleMeaning
*/15 * * * *every 15 minutes
0 9 * * 1-509:00 Monday to Friday
30 1 1 * *01:30 on the 1st of each month
@rebootonce at startup

Real-world mapping

ItemExample valueWhere it appears in the job
0 2 * * *every night at 2 AMNightly data load
*/15 * * * *every 15 minutesMetrics collection
>> log 2>&1append all output to a logDebugging "why did the job not run?"
Airflow schedulesame 5 fieldsSame idea in a bigger tool

Things that bite

  • cron runs with a tiny environment: a short PATH, no .bashrc. Use full paths to programs (/usr/bin/python3) and set variables inside the script.
  • cron mails or drops output unless you redirect it. Always add >> log 2>&1.
  • cron uses the server time zone (often UTC). Check with date.
  • Overlapping runs: if a job takes longer than its period, two copies run together. Use a lock (flock on Linux) or a proper scheduler.

Connection to the real job

cron is the simplest scheduler. Airflow, Prefect and cloud schedulers use the same 5-field cron syntax in their schedule settings, so you learn it once and use it everywhere.

Applications

  • Nightly data loads and backups
  • Periodic metrics collection
  • Log rotation and clean-up
  • Scheduled report e-mails
COMMON MISTAKE
Forgetting that */5 in the minute field with * in hours means every 5 minutes all day. Also, a script that works in your terminal may fail in cron because of the missing environment.

Check yourself

  1. What does 0 */6 * * * mean? Answer: at minute 0 of every 6th hour (00:00, 06:00, 12:00, 18:00).
  2. Why redirect with >> log 2>&1? Answer: to keep both normal output and errors in a log file.
  3. Why use absolute paths in cron? Answer: cron has a minimal PATH and environment.

2.5 Writing Scripts That Fail Safely: set flags, trap, getopts and shellcheck

BASIC EXPLANATION
Failing safely means a script stops cleanly when something goes wrong. It uses set flags, trap for cleanup, getopts to read options, and shellcheck to find mistakes before running.
INTUITION
By default a shell script keeps going after an error, as if nothing happened. A backup script that fails to cd into the backup folder and then runs rm -rf * deletes whatever folder it was started in. Production scripts therefore start by telling the shell to stop at the first problem and to clean up after itself.

All outputs below come from real runs with the system bash.

set -e, -u and pipefail

  • set -e: exit when a command fails (returns non-zero).
  • set -u: treat use of an unset variable as an error, so a typo like $BACKUP_DRI does not silently become an empty string.
  • set -o pipefail: a pipeline fails if any stage fails, not only the last.

Problem 2.5.1 Show what each flag changes.

echo "--- default: the script keeps going"
bash -c 'false; echo "still running after false"'
echo "--- set -e: stops at the first failure"
bash -c 'set -e; false; echo "never printed"'; echo "exit code: $?"
echo "--- set -u: catches a typo"
bash -c 'set -u; dir=/data; echo "$dri"' 2>&1; echo "script stopped, nothing was printed to stdout"
echo "--- pipeline hides failure without pipefail"
bash -c 'false | cat; echo "exit code of pipeline: $?"'
bash -c 'set -o pipefail; false | cat; echo "exit code of pipeline: $?"'
--- default: the script keeps going
still running after false
--- set -e: stops at the first failure
exit code: 1
--- set -u: catches a typo
bash: dri: unbound variable
script stopped, nothing was printed to stdout
--- pipeline hides failure without pipefail
exit code of pipeline: 0
exit code of pipeline: 1

Note the last two lines: the same pipeline reports 0 (success) by default, because only the last command (cat) is counted, and 1 with pipefail.

COMMON MISTAKE
Thinking set -e catches everything. It does not fire inside an if condition, on the left side of && or ||, or in a command whose failure is tested. Wrong: cmd || echo "ignored" hides the failure on purpose. Right: use set -e as a safety net, and still check the results that matter with explicit if tests.

trap: clean up on exit

Problem 2.5.2 A script creates a temp directory. Make sure it is removed even when the script fails halfway.

cat > job.sh <<'SCRIPT'
#!/bin/bash
set -euo pipefail
work=$(mktemp -d)
cleanup() { rm -rf "$work"; echo "cleanup ran, temp dir removed: $([ -d "$work" ] && echo no || echo yes)"; }
trap cleanup EXIT
echo "working in a temp dir"
false
echo "not reached"
SCRIPT
bash job.sh; echo "exit code: $?"
working in a temp dir
cleanup ran, temp dir removed: yes
exit code: 1

The EXIT trap runs on normal exit, on exit 1 and when set -e aborts. It does not run after kill -9, so never rely on it for correctness, only for tidiness.

Arguments with getopts

Problem 2.5.3 Give a script a -n COUNT option, a -v flag, and a usage message for bad input.

cat > greet.sh <<'SCRIPT'
#!/bin/bash
count=1; verbose=0
usage() { echo "usage: greet.sh [-n COUNT] [-v] NAME" >&2; exit 2; }
while getopts "n:v" opt; do
  case "$opt" in
    n) count="$OPTARG" ;;
    v) verbose=1 ;;
    *) usage ;;
  esac
done
shift $((OPTIND - 1))
[ $# -eq 1 ] || usage
if [ "$verbose" -eq 1 ]; then echo "greeting $1 $count time(s)"; fi
for ((i = 0; i < count; i++)); do echo "hello, $1"; done
SCRIPT
bash greet.sh -v -n 2 Asha
bash greet.sh -z Asha 2>&1; echo "exit code: $?"
bash greet.sh 2>&1; echo "exit code: $?"
greeting Asha 2 time(s)
hello, Asha
hello, Asha
greet.sh: illegal option -- z
usage: greet.sh [-n COUNT] [-v] NAME
exit code: 2
usage: greet.sh [-n COUNT] [-v] NAME

Exit code 2 by convention means "wrong usage". Send usage messages to standard error (>&2) so they do not pollute output that another command is reading. The wording of bash's own message for the bad option -z ("illegal option" or "invalid option") depends on the bash version.

Quoting bugs and shellcheck

Problem 2.5.4 Why does this loop break on a file name with a space, and what is the fix?

mkdir q && cd q
echo a > 'one file.txt'
echo "--- unquoted command substitution:"
for f in $(ls); do echo "got: $f"; done
echo "--- glob and quotes:"
for f in *.txt; do echo "got: $f"; done
--- unquoted command substitution:
got: one
got: file.txt
--- glob and quotes:
got: one file.txt

Unquoted $(ls) is split on whitespace, so one file looks like two. Glob directly (*.txt) and quote every expansion ("$f"). shellcheck (a free linter, brew install shellcheck or apt install shellcheck; not installed here, so not run) finds exactly this class of bug and prints a code such as SC2086 ("Double quote to prevent globbing and word splitting"). Run it in CI on every script.

systemd service units (Linux only, not run here)

cron (section 2.4) runs jobs on a schedule. For a long-running process that must restart when it dies, use a systemd unit:

# /etc/systemd/system/scorer.service
[Unit]
Description=Model scoring API
After=network-online.target

[Service]
User=svc-scorer
WorkingDirectory=/opt/scorer
ExecStart=/opt/scorer/venv/bin/python -m scorer
Restart=on-failure
RestartSec=5
EnvironmentFile=/etc/scorer.env

[Install]
WantedBy=multi-user.target

# then:  sudo systemctl daemon-reload && sudo systemctl enable --now scorer
#        journalctl -u scorer -f        (follow its logs)
KEY IDEA
A good script header, in order: #!/usr/bin/env bash, set -euo pipefail, a trap for cleanup, argument parsing with a usage message, then the work. Quote every variable. Test the failure paths on purpose, not only the happy one.

Chapter recap

  • A script is a text file of commands with a shebang. Make it runnable with chmod +x.
  • Variables have no spaces around =. Always quote "$var".
  • Exit code 0 means success; non-zero means failure. Schedulers rely on it.
  • set -euo pipefail makes scripts stop on errors, unset variables and hidden pipe failures.
  • getopts parses options such as -t 300; send errors to stderr with >&2.
  • trap ... EXIT cleans up temporary files.
  • grep finds, sed replaces, awk computes on columns.
  • awk arrays give group-by results in one line; add NR>1 for headers.
  • cron has 5 time fields and a small environment. Use full paths and log output.
  • For real CSV files with quotes, switch to Python or pandas.

Practice set

  1. (Easy) What does x=5; echo $((x*3)) print? Answer: 15.
  2. (Easy) What does echo "${NAME:-guest}" print if NAME is not set? Answer: guest.
  3. (Easy) Write the cron time for "every day at midnight". Answer: 0 0 * * *.
  4. (Medium) What is the output? printf 'a b\nc d\n' | awk '{print $2}' Answer: b then d.
  5. (Medium) What is the exit code of grep -q needle file when the word is not found? Answer: 1.
  6. (Medium) Write awk to print the maximum of column 4 in access.csv. Answer: awk -F, 'NR>1 && $4>m {m=$4} END{print m}' access.csv prints 900.
  7. (Find the bug) name = "perf" gives "command not found". Why? Answer: no spaces are allowed around = in an assignment. Write name="perf".
  8. (Find the bug) if [ $count -gt 2]; then fails. Why? Answer: a space is needed before ]: [ "$count" -gt 2 ].
  9. (Scenario) Your nightly script exits 0 although a download failed in curl ... | gzip > out.gz. Fix it. Answer: add set -euo pipefail (pipefail makes the pipeline fail when curl fails), and use curl -f so HTTP errors give a non-zero exit code.
  10. (Interview) Write a one-liner that prints how many times each HTTP status appears in access.csv, most frequent first. Answer: cut -d, -f3 access.csv | tail -n +2 | sort | uniq -c | sort -rn gives 200 four times, then 404 and 500 once each.
  11. (Interview) Explain the difference between cmd1 && cmd2, cmd1 ; cmd2 and cmd1 | cmd2. Answer: && runs cmd2 only if cmd1 succeeded; ; runs both in order regardless; | runs both at the same time and feeds the output of cmd1 to the input of cmd2.
