Imagine your team wants to run a 7-billion-parameter language model, and someone asks: "Will it fit on this GPU? How much will it cost to fine-tune?" Or imagine your numpy code is slow and you do not know why. The answers sit in a few hardware facts: where data lives (the memory hierarchy), how many numbers the chip can process at once (parallelism), and how fast data can be moved (bandwidth). In this chapter you learn these facts with real timings from this machine, then do the VRAM arithmetic that every ML engineer does on paper. At the end, a short Java primer lets you read JVM-based tools such as Spark, Kafka and Elasticsearch. The running example is one question: how many seconds does it take to do a sum over 2 million numbers, and why do the answers differ so much?

13.1 CPU, GPU and TPU

INTUITION
A CPU is a small team of very clever chefs. Each can cook any dish, fast, one after another. A GPU is a kitchen with thousands of cooks who each only know how to chop. For one tricky dish, the clever chef wins. For chopping ten million onions, the thousands of choppers win. Training neural networks is mostly "chopping": the same simple multiply-and-add, repeated billions of times.

Words you need

WordPlain meaning
Coreone independent processing unit inside a chip
FLOPone floating-point operation (one add or one multiply of decimal numbers)
FLOPSFLOPs per second (TFLOPS = 10¹² per second)
Matrix multiplicationthe core operation of neural networks: many multiply-and-add steps
Parallelismdoing many operations at the same time

The three chips

ChipCoresStrengthWeaknessTypical use
CPUa few to a few dozen, complexflexible, low latency, good at branching logiclow parallel throughput for matricesdata cleaning, web servers, small models
GPUthousands, simplehuge parallel throughput for matrix mathsneeds big batches, separate memory, less flexibletraining and serving deep learning
TPU (Tensor Processing Unit)specialised matrix unitsvery efficient on large matrix workloadslimited flexibility, tied to a vendor stacklarge training and inference on cloud

Why are GPUs good at matrix maths? A matrix multiplication of two 1000 x 1000 matrices has a million independent output cells. Each cell is a separate dot product, so a million small workers can compute them at the same time. That is called data parallelism.

Predict, Run, Explain: vectorization

Vectorization means replacing a Python loop with one operation on a whole array, done in fast compiled code (often using SIMD, "single instruction, multiple data": the CPU applies one instruction to 4, 8 or more numbers at once). Predict: how much faster is numpy than a Python loop for summing 2 million squares: 2x, 20x, or 200x?

import time, numpy as np

# 1. Python loop versus numpy (vectorization)
n = 2_000_000
xs = list(range(n))
a = np.arange(n, dtype=np.float64)
t = time.perf_counter(); s1 = sum(x * x for x in xs); t1 = time.perf_counter() - t
t = time.perf_counter(); s2 = float((a * a).sum()); t2 = time.perf_counter() - t
print("python loop:", s1)
print("numpy      :", s2)
print(f"loop {t1*1000:.1f} ms, numpy {t2*1000:.1f} ms, speedup about {t1/t2:.0f}x")

# 2. Memory access pattern: copy a matrix in order vs transposed (strided reads)
m = np.random.rand(6000, 6000)
t = time.perf_counter(); m.copy(); c1 = time.perf_counter() - t
t = time.perf_counter(); np.ascontiguousarray(m.T); c2 = time.perf_counter() - t
print(f"in-order copy {c1*1000:.0f} ms, transposed copy {c2*1000:.0f} ms, ratio {c2/c1:.1f}x")

# 3. Memory-bound (add) vs compute-bound (matmul)
x = np.random.rand(3000, 3000).astype(np.float32)
t = time.perf_counter(); y = x + x; ta = time.perf_counter() - t
t = time.perf_counter(); z = x @ x; tm = time.perf_counter() - t
bytes_add = 3 * x.nbytes          # read x twice (conservatively) + write y
print(f"add   : {ta*1000:.1f} ms, {x.size/ta/1e9:.2f} GFLOP/s, about {bytes_add/ta/1e9:.0f} GB/s moved")
print(f"matmul: {tm*1000:.1f} ms, {2*3000**3/tm/1e9:.0f} GFLOP/s")
print("FLOPs per byte  add:", round(x.size/bytes_add, 3), " matmul:", round(2*3000**3/(3*x.nbytes), 1))

Real output (run on an Apple M3 Pro laptop, 12 cores, 18 GB; your numbers will differ and vary between runs):

numpy      : 2.6666646666670003e+18
loop 54.6 ms, numpy 2.1 ms, speedup about 26x
in-order copy 50 ms, transposed copy 92 ms, ratio 1.8x

Line by line (first part): the Python loop visits each number as a Python object and runs interpreted bytecode, taking about 55 ms. a * a and .sum() run in compiled loops over contiguous raw numbers, about 2 ms, around 26x faster here. Both give the same sum (the float form is the same value in different notation). The wrong version, a Python for loop over a numpy array, is often even slower than a plain list. The fix is always: use whole-array operations.

Problem 13.1.1 The loop took 54.6 ms and numpy 2.1 ms. What is the speedup, and how long would the loop take for 200 million numbers at the same speed?

Formulaspeedup = slow time / fast time; scaled time = time x (new n / old n)
Plug in54.6 / 2.1; and 54.6 ms x (200,000,000 / 2,000,000)
Compute54.6 / 2.1 = 26.0; 54.6 x 100 = 5,460 ms

Check2.1 x 26 = 54.6. Correct. (Linear scaling is an assumption: memory limits matter at large sizes.)

Problem 13.1.2 A GPU does 20 TFLOPS in float32. A forward pass over a batch needs 4 x 10¹² FLOPs. Ideal time?

Formulatime = FLOPs / FLOPS
Plug in4 x 10¹² / (20 x 10¹²)
Compute4 / 20 = 0.2 s
AnswerAt best 0.2 seconds. Real time is longer because chips rarely reach their peak.
Check20 TFLOPS x 0.2 s = 4 TFLOP. Correct.
Why it matters"Peak FLOPS" is a ceiling, not a promise. Use it for quick estimates only.

Connection to the real job

Deep learning libraries (PyTorch, TensorFlow) send matrix work to the GPU. In your daily work, "use the GPU" often means: make batches big enough to keep it busy, and avoid copying data between CPU and GPU too often.

Applications

  • Deep Learning: training CNNs and Transformers on GPUs or TPUs.
  • GenAI: serving LLMs, where the batch size and memory decide cost per request.
  • Data Science: classic ML (scikit-learn, XGBoost trees) mostly runs fine on CPU.
  • Data Engineering: Spark workers are mostly CPU and memory machines; GPU Spark exists but is a special case.
COMMON MISTAKE
Assuming a GPU speeds up everything. Small data, lots of branching logic, or constant CPU-GPU copying can be slower on GPU than on CPU. Measure first.

Check yourself

  1. Why does a GPU suit neural networks? Answer: The work is huge numbers of independent multiply-adds, which thousands of simple cores do in parallel.
  2. What does vectorization mean? Answer: Operating on whole arrays in compiled code, not item by item in a Python loop.
  3. Is peak FLOPS what you will get? Answer: No, it is an upper limit.

13.2 The Memory Hierarchy

INTUITION
You are cooking. Spices you use every minute sit on the counter (cache). Rice and vegetables are in the kitchen cupboard (RAM). Bulk grain is in the store room downstairs (SSD). A rare ingredient needs a trip to the market (network). The closer the item, the faster you get it, but the counter is small. A good cook keeps what she needs next on the counter.

The memory hierarchy is this ladder of storage: small and fast at the top, large and slow at the bottom.

How to read it: each layer is wider (bigger capacity) and lower (slower, cheaper per byte). Registers sit inside the CPU core. Caches (L1, L2, L3) are small memories next to the core. RAM is the main memory. SSD is permanent storage. The bottom is anything over a network.

Real-world mapping

LayerRough latency (orders of magnitude)Typical sizeWhere it appears in the job
L1 cacheabout 1 nstens of KBtight loops in numpy
RAMabout 100 nsGBspandas DataFrames, model weights on CPU
SSDabout 100 microsecondshundreds of GB to TBdatasets on disk, checkpoints
Network (same data centre)about 0.5 msunlimitedS3 reads, database calls
Network (cross continent)about 100 msunlimitedcalls to a remote API

These latencies are rough, vary by hardware and generation, and are only meant to show the ratios: each step down is often 10 to 1,000 times slower.

Locality is the idea that makes caches work. Spatial locality: when you read one number, the chip also loads its neighbours (a cache line, commonly 64 bytes), so reading neighbours next is cheap. Temporal locality: data you used just now is likely to be used again soon.

Predict, Run, Explain: locality in action

Our test in the code above copied a 6000 x 6000 matrix in memory order, then copied its transpose, which reads with large jumps (strided reads). Predict which is slower. The output earlier showed in-order copy 50 ms and transposed copy 92 ms: about 1.8x slower, only because of access order. The data and the work are the same.

Problem 13.2.1 A float64 matrix of 6000 x 6000 is used above. How many MB is it?

Formulabytes = rows x columns x bytes per number
Plug in6000 x 6000 x 8
Compute36,000,000 x 8 = 288,000,000 bytes = 288 MB
Answer288 MB (decimal megabytes), larger than the cache of any normal CPU, so it lives in RAM.
CheckPython: np.zeros((6000,6000)).nbytes printed 288000000 when we ran it. (Arithmetic checked by hand: 6 x 6 = 36, with six zeros, times 8.)
Why it mattersWhether data fits in cache or RAM decides speed. This is also why a 20 GB DataFrame on a 16 GB laptop thrashes (see Chapter 5, swapping).

Problem 13.2.2 If one RAM access takes 100 ns and one L1 access 1 ns, and 95% of accesses hit L1, what is the average access time?

Formulaaverage = hit rate x fast time + miss rate x slow time
Plug in0.95 x 1 + 0.05 x 100
Compute0.95 + 5.0 = 5.95 ns
AnswerAbout 5.95 ns. Even a 5% miss rate makes the average about 6 times slower than the fast case.
CheckIf the hit rate were 100%, the result is 1 ns, and at 0% it is 100 ns, so 5.95 lies in between. Reasonable.
Why it mattersMisses dominate. This is the same logic as a library where most requests are served from the desk shelf (a hit) and only a few need the far warehouse (a miss).

Connection to the real job

Reading data from disk or the network is thousands of times slower than from RAM. That is why Spark caches data in memory, databases keep hot pages in a buffer pool, and ML training loops use data loaders that prefetch the next batch while the GPU works. On a GPU, the same ladder exists: fast on-chip memory, then VRAM, then the CPU RAM across a slower link.

Applications

  • Data Engineering: columnar formats (Parquet) read only needed columns; partitioned data reduces I/O.
  • Machine Learning: keep the training data in a fast format; use batches that fit memory.
  • MLOps: model loading time from network storage is part of "cold start" latency.
  • Systems work: cache hit ratio and page cache analysis.
COMMON MISTAKE
Looping over a matrix column by column in a language that stores rows contiguously (numpy default is row-major, "C order"). Jumping across rows ruins spatial locality. Traverse in memory order or use vectorized operations.

Check yourself

  1. Which is faster, RAM or SSD? Answer: RAM, by a factor of hundreds to a thousand.
  2. What is spatial locality? Answer: Nearby data gets loaded together, so reading neighbours is cheap.
  3. 8-byte numbers, 1,000 x 1,000 matrix: how many MB? Answer: 8 MB (10⁶ x 8 bytes).

13.3 Memory-bound versus Compute-bound

INTUITION
A factory can be slow for two reasons. Either the machines are too slow (compute-bound), or the trucks bringing material are too slow (memory-bound). Buying faster machines does nothing if the trucks are the problem.

A workload is compute-bound when the chip's arithmetic is the limit. It is memory-bound when moving data in and out of memory is the limit. The measure that decides this is arithmetic intensity: FLOPs done per byte moved.

arithmetic intensity = FLOPs / bytes moved

Each chip has a ridge point = peak FLOPS / memory bandwidth. Below the ridge, you are memory-bound; above it, compute-bound. This picture is the roofline model.

 speed (FLOPS)
   ^            ______________  <- compute ceiling (peak FLOPS)
   |          /
   |        /    slope = memory bandwidth
   |      /
   |    /
   +--/------------|-------------> arithmetic intensity (FLOPs/byte)
                ridge point
   left of ridge: memory-bound    right of ridge: compute-bound

How to read it: the x axis is how much work you do per byte fetched. At low intensity, your speed is limited by the slope (bandwidth x intensity). Once intensity is high enough, you hit the flat ceiling set by the chip's arithmetic.

Predict, Run, Explain

In the earlier script we added two 3000 x 3000 float32 matrices (x + x) and multiplied them (x @ x). Predict: which will use the chip's FLOPS better?

Output from above: add ran at 2.94 GFLOP/s but moved about 35 GB/s, far below its arithmetic speed, so the data movement (not the arithmetic) is what limits it. matmul ran at 1167 GFLOP/s (it uses all cores and optimised libraries), about 400 times the add. Intensities: add 0.083 FLOPs per byte, matmul 500 FLOPs per byte.

Problem 13.3.1 For x + x with 3000 x 3000 float32 numbers, compute the arithmetic intensity.

Formulaintensity = FLOPs / bytes moved
Plug inFLOPs = 9,000,000 additions. Bytes = 3 x 9,000,000 x 4 (we counted two reads and one write, 4 bytes each)
Computebytes = 108,000,000. Intensity = 9,000,000 / 108,000,000 = 0.0833
AnswerAbout 0.083 FLOPs per byte, very low: this operation is memory-bound.
CheckThe script printed 0.083. Count: one add per element, 12 bytes per element, so 1/12 = 0.0833.

Problem 13.3.2 For x @ x (n = 3000), FLOPs = 2 n³, and bytes moved is at best 3 n² x 4 (read two matrices, write one, each once). Intensity?

Formulaintensity = 2n³ / (12 n²) = n / 6
Plug inn = 3000
Compute3000 / 6 = 500
Answer500 FLOPs per byte, well above any ridge point: compute-bound.
CheckThe script printed 500.0. Notice intensity grows with n: bigger matrices reuse each loaded number more times.
Why it mattersBig matrix multiplications are why GPUs shine. Elementwise operations (add, ReLU, layer norm) are memory-bound and gain little from more FLOPS.

Problem 13.3.3 A GPU has 100 TFLOPS and 1 TB/s of memory bandwidth (example numbers). Find the ridge point and decide whether x + x (0.083 FLOPs/byte) is limited by memory.

Formularidge = peak FLOPS / bandwidth
Plug in100 x 10¹² / (1 x 10¹²)
Compute100 FLOPs per byte
AnswerThe ridge is at 100 FLOPs per byte. 0.083 is far left of it, so addition is memory-bound, running at bandwidth x intensity = 1 TB/s x 0.083 = 83 GFLOPS, which is 0.083% of peak.
Check83 GFLOPS / 100,000 GFLOPS = 0.00083. Right.
Why it mattersThis explains why LLM text generation (token by token) is memory-bound: every new token reads all the weights once, for just a few FLOPs per byte.

Connection to the real job

When someone says "the GPU is only 30% utilised", the first question is: is the workload memory-bound or is the data pipeline starving the GPU? It is like a restaurant with slow service: first find whether the kitchen, the waiters or the supply of ingredients is the bottleneck before hiring more cooks.

Applications

  • Deep Learning: fused kernels and mixed precision reduce memory traffic.
  • GenAI: LLM serving speed depends on memory bandwidth (decode) and compute (prefill).
  • Data Engineering: Spark jobs are usually I/O-bound, not CPU-bound.
COMMON MISTAKE
Quoting FLOPS to compare chips for every workload. For memory-bound work, bandwidth matters more than FLOPS.

Check yourself

  1. What is arithmetic intensity? Answer: FLOPs performed per byte moved from memory.
  2. Is a big matrix multiply memory-bound or compute-bound? Answer: Compute-bound, because intensity is high.
  3. Ridge point formula? Answer: Peak FLOPS divided by memory bandwidth.

13.4 Reading GPU Specs: Will the Model Fit?

INTUITION
A GPU's VRAM (its own memory) is a suitcase. Before a trip you add up what you must pack. If the sum is bigger than the suitcase, the lid will not close, however strong the GPU is.

Words you need

WordPlain meaning
VRAMvideo RAM, the GPU's own memory, where weights and activations live
Parameterone learned number in the model
Precisionhow many bytes store one number: float32 = 4, float16/bfloat16 = 2, int8 = 1, 4-bit = 0.5
Quantizationstoring numbers with fewer bits to save memory
KV cachememory a language model uses to remember earlier tokens while generating
Bandwidthbytes per second the memory can deliver

What a spec sheet tells you

A GPU spec sheet lists: VRAM (GB), memory bandwidth (GB/s or TB/s), peak FLOPS for each precision, number of cores, and power. For "does it fit", you need VRAM. For "how fast", you need bandwidth and FLOPS.

Rules of thumb

  • Inference weights: memory = parameters x bytes per parameter.
  • Training with Adam in mixed precision: about 16 bytes per parameter (weights, gradients, and optimiser states), before activations. This is a rule of thumb, and varies with the setup.
  • KV cache per sequence: 2 x layers x KV heads x head size x bytes x tokens (the 2 is for keys and values).
  • Add a safety margin of 10 to 20% for activations, framework overhead and fragmentation.

Predict, Run, Explain

Predict the weight size of a 7-billion-parameter model in float16 (2 bytes per parameter).

def gb(x): return x/1e9
def fit(params_b, bytes_per_param, name):
    w=params_b*1e9*bytes_per_param
    print(f"{name}: weights = {params_b}B x {bytes_per_param} bytes = {gb(w):.1f} GB")
    return w
for p in (7,13,70):
    fit(p,2,f"{p}B fp16"); fit(p,0.5,f"{p}B 4-bit")
# training with Adam, mixed precision rule of thumb: ~16 bytes per param
for p in (1,7):
    print(f"train {p}B params, ~16 B/param: {p*16} GB (before activations)")
# KV cache: 2 * layers * kv_heads * head_dim * bytes * tokens
layers,kvh,hd,tok,b=32,8,128,4096,2
kv=2*layers*kvh*hd*b*tok
print(f"KV cache example (32 layers, 8 KV heads, dim 128, 4096 tokens, fp16): {kv/1e9:.2f} GB per sequence")
# arithmetic intensity roofline
peak=100e12; bw=1e12
print("ridge point FLOPs/byte for 100 TFLOPS, 1 TB/s:",peak/bw)
print("decode speed upper bound for 14 GB weights at 1 TB/s:",round(bw/14e9,1),"tokens/s")
# cost
hours=20
for name,rate in (("on-demand",1.00),("spot (assume 60% off)",0.40)):
    print(f"{name}: {hours}h x rate {rate:.2f} units/h = {hours*rate:.2f} units")

Line by line: fit multiplies parameters by bytes per parameter. 7 billion x 2 bytes = 14.0 GB. In 4-bit form (0.5 bytes) it is 3.5 GB. A 70B model needs 140 GB in float16, more than any single common GPU, so it needs several GPUs or 4-bit compression (35 GB). The training line says a 7B model needs about 112 GB before activations. The KV cache example (a made-up but typical shape) needs 0.54 GB per sequence, so serving 20 users at once needs about 10.8 GB more. The last decode line: if each token must read all 14 GB of weights, and bandwidth is 1 TB/s, the ceiling is 1,000 / 14 = 71.4 tokens per second for one sequence. The example GPU numbers (100 TFLOPS, 1 TB/s) are illustrative, not a real product.

Problem 13.4.1 Will a 13-billion-parameter model in float16 fit on a GPU with 24 GB of VRAM for inference?

Formulaweights = parameters x bytes per parameter
Plug in13 x 10⁹ x 2
Compute26 x 10⁹ bytes = 26 GB
AnswerNo. 26 GB exceeds 24 GB even before the KV cache. In 4-bit form, it is 13 x 10⁹ x 0.5 = 6.5 GB, which fits with room for the KV cache.

Problem 13.4.2 You serve a model with a 14 GB weight file on a 24 GB GPU. Each user's KV cache is 0.54 GB. Keeping a 15% safety margin, how many concurrent sequences fit?

Formulausable = VRAM x (1 - margin); sequences = (usable - weights) / KV per sequence
Plug inusable = 24 x 0.85 = 20.4 GB; (20.4 - 14) / 0.54
Compute6.4 / 0.54 = 11.85, rounded down to 11
AnswerAbout 11 concurrent sequences of 4,096 tokens.
Check11 x 0.54 = 5.94 GB, plus 14 = 19.94 GB, under 20.4. Twelve sequences would need 6.48 + 14 = 20.48 GB, over the limit. Correct.
Why it mattersConcurrency is limited by memory, not only compute. This is capacity planning, like finding the largest number of diners a restaurant can seat.

Problem 13.4.3 A 1-billion-parameter model is trained with about 16 bytes per parameter. How much memory before activations, and does it fit in 16 GB?

Formulamemory = parameters x 16
Plug in1 x 10⁹ x 16
Compute16 x 10⁹ bytes = 16 GB
Answer16 GB, exactly the whole card with nothing left for activations. It will not fit in practice. Reduce the model, use gradient checkpointing, a smaller batch, or fine-tune with LoRA (training only small added layers).
CheckThe script printed 16 GB for 1B parameters.

Connection to the real job

"Out of memory" (OOM) is the most common GPU error you will see. A paper napkin estimate (like above) tells you in a minute what to try. Also, bandwidth explains why newer GPUs with the same FLOPS can serve LLMs faster.

Applications

  • GenAI: choose the model size and quantization for a given GPU.
  • Machine Learning: choose batch size and precision.
  • MLOps: size GPU nodes in a cluster and set the number of replicas.
  • Cost control: pick the smallest hardware that fits.
COMMON MISTAKE
Counting only the weights. Activations (training), the optimiser state, and the KV cache (inference) can double or triple the need. Always add them and a safety margin.

Check yourself

  1. Weights of a 3B model in int8? Answer: 3 GB (3 x 10⁹ x 1 byte).
  2. What does the KV cache depend on? Answer: Layers, KV heads, head size, bytes, and number of tokens, per sequence.
  3. Why is training memory so much bigger than inference? Answer: It also stores gradients and optimiser states (about 16 bytes per parameter in total).

13.5 The Cost of Compute

INTUITION
Hardware is like renting a car. A taxi on demand costs the most but is there right now. A pre-booked ride on a quiet day costs less but may be cancelled (spot). A free loaner from the company (free tier) is cheap but limited in time and choice.

The three buying styles

OptionWhat it isGood forRisk
On-demandpay by the hour, no commitment, always availableproduction serving, urgent jobshighest hourly rate
Spot (preemptible)spare capacity at a large discount, can be taken back with short noticetraining with checkpoints, batch jobsinterruption
Reserved or committedcommit for 1 to 3 years for a lower ratesteady, predictable loadpaying for unused time
Free tiers (Colab, Kaggle)free GPU time with limitslearning, small experimentssession limits, no guarantee of a GPU, slower

Do not rely on any price or free-tier limit written in a book. They change. Check the provider's page when you plan a budget.

Budgeting formula

cost = hours x number of GPUs x price per GPU-hour

Add storage, data transfer out (egress), and the cost of failed or repeated runs. A common beginner error is forgetting that experiments are run many times.

Problem 13.5.1 Using the assumed units from our script: on-demand 1.00 units per hour, spot 0.40 units per hour (assumed 60% off). A 20-hour job costs how much each way, and what do you save?

Formulacost = hours x rate
Plug in20 x 1.00 and 20 x 0.40
Compute20.00 units and 8.00 units, saving 12.00 units
AnswerSpot costs 8 units against 20 on-demand, a 60% saving, if you can tolerate interruptions.
CheckThe script printed 20.00 and 8.00. And 12 / 20 = 0.6. Correct.

Problem 13.5.2 The spot job gets interrupted once, and you lose the work since the last checkpoint. The job checkpoints every 30 minutes. At most how much work do you lose, and what is the worst-case cost of one interruption in this example?

Step 1Worst case, the interruption happens just before the next checkpoint: 0.5 hours lost.
Step 2Cost of redoing that work on spot: 0.5 x 0.40 = 0.20 units.
AnswerAt most 30 minutes of work, 0.20 units. Even with several interruptions, spot (8 units plus small losses) stays far below on-demand (20 units).
CheckTo beat spot, on-demand savings would need 12 / 0.2 = 60 interruptions. Very unlikely.
Why it mattersCheckpointing makes spot safe. Without checkpoints, one interruption could lose the whole job.

Connection to the real job

ML engineers are judged on results per cost. Practical habits: debug on a small sample on CPU or a free tier, use spot with checkpoints for long training, shut down idle GPU instances (the most common waste), and tag resources by project so costs can be tracked.

Applications

  • GenAI: pick quantized smaller models to cut serving cost.
  • MLOps: autoscale GPU replicas; use spot for batch inference.
  • Data Engineering: use spot or preemptible workers for Spark; keep drivers on-demand.
  • Learning: Colab and Kaggle free tiers for projects (not run here; their limits change).
COMMON MISTAKE
Leaving a GPU notebook running overnight. Set auto-shutdown and a budget alert.

Check yourself

  1. When is spot a good choice? Answer: For interruptible work that checkpoints, such as training or batch jobs.
  2. What else adds to cost besides GPU hours? Answer: Storage, data transfer, and repeated runs.
  3. Cost of 4 GPUs for 10 hours at 2 units per GPU-hour? Answer: 80 units (4 x 10 x 2).

13.6 Java for Data People: A Short Primer

INTUITION
Java is the language many data tools are written in, like the engine under a car. You may never build an engine, but when something breaks (or you need to tweak a Java-based data tool) you must be able to open the bonnet and read.

Why it matters

  • Spark, Kafka, Hadoop, Flink, Cassandra, Elasticsearch are written in Java or Scala, which both run on the JVM. When a Spark job fails, the error is a Java stack trace.
  • Many other tools (Elasticsearch, Neo4j, Jenkins, IDEs) are Java applications with JVM settings such as heap size. Understanding GC pauses helps you tune them.
  • Many enterprise data jobs in large companies need to read Java code.

JVM basics

Java source (.java) is compiled by javac into bytecode (.class), which the JVM (Java Virtual Machine) runs. The JVM manages memory: objects live on the heap, and a garbage collector (GC) frees objects nobody uses. GC can cause pause times, which show up as latency spikes. Key flags: -Xms and -Xmx set initial and maximum heap size.

Java is statically typed: every variable has a declared type that the compiler checks. Generics (List<String>) tell the compiler what a collection holds. A stream is a pipeline over a collection (filter, map, group), similar to pandas or list comprehensions.

Collections you should know

ArrayList (dynamic array), HashMap (hash table), HashSet, TreeMap (sorted keys), ArrayDeque (queue and stack), PriorityQueue (heap). These map to the structures you studied in Chapters 7 to 10.

Concurrency

Java has threads, and ExecutorService thread pools that run tasks and return a Future. Shared data needs care (locks, synchronized, concurrent collections), as in Chapter 5.

Build tools

Maven (pom.xml) and Gradle (build.gradle) download dependencies and build projects. A typical command is mvn package. Both produce a jar (a zip of classes) that you run with java -jar.

Predict, Run, Explain

java and javac (OpenJDK 21) were installed on this machine, so we ran this program. It sums order amounts per user with a stream, uses a generic method, catches an exception, and runs tasks in a thread pool. Predict what each of the four printed lines will be.

import java.util.*;
import java.util.stream.*;
public class Demo {
    record Order(String user, double amount) {}
    static <T extends Comparable<T>> T maxOf(List<T> xs) {
        T best = xs.get(0);
        for (T x : xs) if (x.compareTo(best) > 0) best = x;
        return best;
    }
    public static void main(String[] args) throws Exception {
        List<Order> orders = List.of(new Order("asha", 120.5), new Order("ravi", 80),
                                     new Order("asha", 40), new Order("meena", 200));
        Map<String, Double> totals = orders.stream()
            .collect(Collectors.groupingBy(Order::user, TreeMap::new, Collectors.summingDouble(Order::amount)));
        System.out.println(totals);
        System.out.println(maxOf(List.of(3, 9, 4)));
        try { Integer.parseInt("abc"); }
        catch (NumberFormatException e) { System.out.println("caught: " + e.getMessage()); }
        var pool = java.util.concurrent.Executors.newFixedThreadPool(4);
        List<java.util.concurrent.Future<Integer>> fs = new ArrayList<>();
        for (int i = 1; i <= 3; i++) { final int n = i; fs.add(pool.submit(() -> n * n)); }
        int sum = 0; for (var f : fs) sum += f.get();
        pool.shutdown();
        System.out.println("sum of squares via threads: " + sum);
    }
}

Real output:

{asha=160.5, meena=200.0, ravi=80.0}

caught: For input string: "abc"

Compile and run with javac Demo.java then java Demo. Line by line: the record Order stores user and amount. The stream groups orders by user into a sorted TreeMap, so you see asha=160.5 (120.5 + 40), meena=200.0, ravi=80.0. maxOf is a generic method that works for any type that can be compared; it printed 9. Integer.parseInt("abc") throws NumberFormatException, and we catch it and print its message. The thread pool computes 1, 4 and 9 in parallel, and the sum is 14.

A typical wrong version: calling maxOf with an empty list throws IndexOutOfBoundsException at xs.get(0) (not run here; standard Java behaviour). The fix is to check xs.isEmpty() first.

Problem 13.6.2 A Java data tool with a 1 GB heap shows 400 ms pauses every minute while the CPU and the disk are fine. What do you suspect and do?

Step 1Long pauses on a Java process point to garbage collection with a heap that is too small or too full.
Step 2Raise -Xmx (and set -Xms equal), check GC logs, and reduce what the program keeps in memory (for example, caches or lists that keep all results).
AnswerSuspect GC pauses: the program freezes while it cleans memory, which shows up as latency spikes. Fix the heap and what is kept in memory, then re-measure.
CheckIf the spikes disappear when the heap is larger or the in-memory lists are trimmed, the guess was right.

Connection to the real job

You will rarely write large Java programs as a data person. You will read stack traces, set JVM memory for Spark executors, and use Maven or Gradle to build a plugin. Python (PySpark) hides most of the Java, but the memory and GC issues remain.

Applications

  • Data Engineering: Spark executor memory settings, Kafka broker tuning, Flink jobs.
  • MLOps: JVM-based model servers and feature services.
  • Operations: JVM heap settings, GC logs, thread dumps.
COMMON MISTAKE
Giving a Spark executor or any Java service all of the machine's memory. The operating system and other processes need some, and a huge heap means long GC pauses. Leave headroom.

Check yourself

  1. What does the JVM run? Answer: Bytecode compiled from Java (or Scala, Kotlin) source.
  2. What is a generic type like List<String>? Answer: A collection whose element type is checked by the compiler.
  3. Why can a JVM cause latency spikes? Answer: Garbage collection pauses.

Chapter recap

  • CPUs are few and flexible; GPUs have thousands of simple cores for parallel matrix maths; TPUs are specialised for it.
  • Vectorized numpy beat a Python loop by about 26x in our run, because the work runs in compiled code over contiguous memory.
  • The memory hierarchy goes from registers and cache to RAM, SSD and network. Each step down is far slower and far larger.
  • Access order matters: a transposed copy was about 1.8x slower than an in-order copy of the same data.
  • Arithmetic intensity (FLOPs per byte) tells you if work is memory-bound or compute-bound. Matrix multiply is compute-bound, elementwise add is memory-bound.
  • VRAM arithmetic: weights = parameters x bytes per parameter. A 7B model is 14 GB in float16 and 3.5 GB in 4-bit.
  • Training needs about 16 bytes per parameter before activations. The KV cache adds memory per sequence for inference.
  • Compute cost is hours x GPUs x rate. Spot is cheaper with checkpoints; free tiers are for learning.
  • Java runs on the JVM, which Spark, Kafka and Elasticsearch use. Read stack traces and watch heap and GC.

Practice set

Problem 13.7.1 (easy) How many GB is a 3-billion-parameter model stored in float16?

Answer: 3 x 10⁹ x 2 bytes = 6 GB.

Problem 13.7.2 (easy) Name the two reasons a workload can be slow on a fast chip.

Answer: It is compute-bound (arithmetic is the limit) or memory-bound (moving data is the limit).

Problem 13.7.3 (computation) 1,000 x 1,000 float32 matrix: size in MB?

Answer: 10⁶ x 4 bytes = 4 MB.

Problem 13.7.4 (what is the output) In the Java demo, what does maxOf(List.of(3, 9, 4)) print?

Answer: 9. (Real output of the run above.)

Problem 13.7.5 (computation) Arithmetic intensity of adding two float64 vectors of length n (read 2, write 1)?

Answer: FLOPs = n. Bytes = 3 x 8 x n = 24n. Intensity = 1/24 = 0.042 FLOPs per byte: memory-bound.

Problem 13.7.6 (computation) Weights of a 70B model in 4-bit, and the minimum number of 24 GB GPUs just for weights?

Answer: 70 x 10⁹ x 0.5 = 35 GB. 35 / 24 = 1.46, so at least 2 GPUs, and in practice more because of the KV cache and overhead.

Problem 13.7.7 (find the bug) A student loops for i in range(len(a)): total += a[i] * a[i] over a numpy array of 10 million items and says "numpy is slow". What is wrong?

Answer: The loop runs in Python item by item, losing the benefit of vectorization (and numpy item access is slow). Use (a * a).sum() or np.dot(a, a).

Problem 13.7.8 (find the bug) A team estimates serving memory for a 13B float16 model as "13 GB" and buys a 16 GB GPU. What went wrong?

Answer: They forgot 2 bytes per parameter. The weights alone are 26 GB. They also forgot the KV cache. They need 4-bit quantization (6.5 GB) with room for the cache, or a bigger GPU.

Problem 13.7.9 (scenario) A 12-hour fine-tune on 4 GPUs at an assumed 1.50 units per GPU-hour on-demand. Spot is 50% cheaper and the job checkpoints every hour. Compute both costs.

Answer: On-demand: 12 x 4 x 1.50 = 72 units. Spot: 12 x 4 x 0.75 = 36 units, plus at most 1 hour lost per interruption (4 x 0.75 = 3 units each). Spot is far cheaper even after a few interruptions.

Problem 13.7.10 (interview) Why is LLM text generation (decode) usually memory-bound?

Answer: For each new token, the GPU reads all the model weights from memory but does only a few FLOPs per weight (low arithmetic intensity). So speed is limited by memory bandwidth: tokens per second is at most about bandwidth / weight bytes. Batching several requests together raises intensity.

Problem 13.7.11 (interview) A Java service on your machine shows rising latency spikes but low CPU. Name two JVM-related checks.

Answer: Check GC logs for long pauses and heap usage (raise -Xmx, reduce what is kept in memory). Also check thread count and whether the machine is swapping.
