15.1 How to Run a Project in This Area

INTUITION
A project is like cooking a dish for a guest, not just for yourself. You decide the menu first (the question), you prepare the kitchen (repo and environment), you cook in small steps and taste each one (commits and tests), and you plate it properly (README and demo). A dish that is only correct in your head is not served.

Plan the question and the success criteria

Write the question in one sentence and make it measurable. "Learn logs" is not a question. "From a 2,000-line shop access log, report the error rate and the three URLs with most server errors, in under one second" is a question. Then write three to five success criteria, each one a yes/no check:

  • The program runs with one command on a clean machine.
  • It gives the same answer as a second method (for example shell versus Python).
  • At least three automated checks pass.
  • One failure case (bad input) is handled and shown in the README.

Repo layout

Every project here follows the same shape, so a reader always knows where to look.

project-name/
  README.md          what, why, how to run, results, limits
  src/               the code you wrote
  tests/             small automated checks
  data/              small sample data, or the generator that makes it
  docs/              optional: diagrams, notes
  .gitignore         ignore caches, big files, secrets

Environment and dependencies

Use only the Python standard library when you can. It runs everywhere and a reviewer needs no install step. If you need extra packages, list them in requirements.txt with versions and say which Python version you used. Keep a virtual environment (python3 -m venv .venv) outside Git by listing .venv/ in .gitignore. Never commit passwords, tokens or personal data.

Data sourcing or generation

Prefer a small generator script with a fixed random seed. Then anyone gets the same data, you never commit a big file, and you know the true answer because you built the data. Use neutral data: shop orders, delivery times, exam marks, hospital appointments. If you use a public dataset, write its source and licence in the README.

Commit rhythm and good messages

Commit when one small thing works, not at the end of the day. A good rhythm is 8 to 20 commits per project. Write the message as an order, in the present tense, under about 60 characters: "Add log parser", "Fix empty-file crash", "Add test for bad lines". One idea per commit. See Chapter 3, Git and GitHub, for the daily loop.

Weak messageBetter message
updateCount 5xx errors per URL
fixSkip damaged log lines instead of crashing
final versionAdd README results table

Definition of done

A project is done when all of these are true: the success criteria pass; tests pass from a clean checkout; the README has the run command, a real output sample and a "limits" section; the history reads like a story; you can explain the main design choice and one thing you would change.

README template

# Project title: one line about what it does

## Why
The question this answers, in one or two sentences.

## Quick start
    python3 src/tool.py data/sample.log
Expected output (paste the real output here).

## How it works
A short diagram or 5 bullet points.

## Results
A table of real numbers, with the machine and Python version.

## Tests
    python3 tests/test_tool.py

## Limits and what I would do next
Be honest. Three bullet points.

Demo and deploy options

For these projects a "deploy" is a good README with pasted output. Options, from simplest to richest: (1) a terminal recording or screenshot of the run; (2) a GitHub repository with a short README and a tagged release; (3) a free GitHub Actions workflow that runs your tests on every push (not run here; see Chapter 3); (4) a notebook that shows the results as tables. Do not pay for hosting for a command-line project.

Writing the LinkedIn or blog post

Use five short parts: the question; what you built (one sentence and a link); one number you measured; one thing that surprised or broke; what you learned. Keep it under 200 words. Say "I measured", not "I achieved". Do not claim results you did not measure.

Testing and debugging checklist for this area

  1. Run on tiny data first. Three lines you can check by hand.
  2. Compare two methods. Shell versus Python, or brute force versus clever. If they disagree, one is wrong.
  3. Test the empty, the one-item and the damaged input.
  4. Check off-by-one and boundaries. First line, last line, first day, last day.
  5. For timings, repeat and take the median, warm up once, and never time with print inside the loop.
  6. For Git projects, run git status and git log --oneline --graph before and after every risky command.
  7. Read the error from the bottom up, then reproduce it with the smallest input.
  8. Write the failing test before the fix, so the bug cannot return.

15.2 Project: Log-Analysis Toolkit (Shell plus Python)

INTUITION
A web server keeps a diary: one line for every visitor request. A log toolkit is the person who reads the diary every morning and says "yesterday 12.6% of requests failed, mostly at the cart page". Nobody reads 2,000 lines by eye.

Goal and why employers care

Build a command-line toolkit that parses web-server style access logs, counts status codes, lists the top URLs and finds which URLs return server errors. It proves you can use the shell for quick answers and Python for repeatable, tested ones. Log reading is daily work in data engineering and support, and the same parse-count-rank pattern feeds dashboards and alerts.

Skills used

Chapter 1, Linux Command Line and the Shell (awk, sort, uniq, pipes); Chapter 2, Shell Scripting (set -euo pipefail, arguments); Chapter 7, Complexity, Arrays, Strings, Hashing and Sorting (hash-map counting); Chapter 4, Computer Networks and HTTP (status codes: 2xx success, 4xx client error, 5xx server error).

Data

A generator makes a log in the common access-log shape: IP - - [time] "METHOD URL HTTP/1.1" status size. The seed is fixed, so everyone gets the same file. It adds one damaged line at the end on purpose.

# src/gen_logs.py
import random, sys
from datetime import datetime, timedelta

def main(path, n=2000, seed=7):
    rnd = random.Random(seed)
    urls = ["/", "/products", "/products/42", "/cart", "/checkout", "/login", "/api/orders", "/missing-page"]
    weights = [30, 25, 12, 10, 6, 8, 7, 2]
    status = {"/": [200], "/products": [200], "/products/42": [200, 404], "/cart": [200, 500],
              "/checkout": [200, 500, 502], "/login": [200, 401], "/api/orders": [200, 500],
              "/missing-page": [404]}
    t = datetime(2026, 3, 1, 9, 0, 0)
    with open(path, "w") as f:
        for _ in range(n):
            t += timedelta(seconds=rnd.randint(0, 3))
            u = rnd.choices(urls, weights)[0]
            s = rnd.choice(status[u])
            ip = f"10.0.{rnd.randint(0,3)}.{rnd.randint(1,50)}"
            f.write(f'{ip} - - [{t:%d/%b/%Y:%H:%M:%S} +0000] "GET {u} HTTP/1.1" {s} {rnd.randint(200, 5000)}\n')
        f.write("this line is damaged\n")

if __name__ == "__main__":
    main(sys.argv[1])

  src/quick.sh           same questions with awk/sort/uniq (fast check)

Step-by-step build

  1. Make the data. Run python3 src/gen_logs.py data/access.log. Check wc -l data/access.log. Real output: 2001 data/access.log.
  2. Look at it by hand. head -3 data/access.log shows lines such as 10.0.0.5 - - [01/Mar/2026:09:00:02 +0000] "GET /api/orders HTTP/1.1" 500 4589.
  3. Ask in the shell first. Predict: which status will be most common? Then run quick.sh.

  1. Write the Python version so it is tested and reusable. A regular expression (a pattern for text) pulls out the fields, and a Counter (a dictionary that counts) does the counting.
# src/logstats.py
import re, argparse
from collections import Counter

LINE = re.compile(r'^(?P<ip>\S+) \S+ \S+ \[(?P<ts>[^\]]+)\] "(?P<method>\S+) (?P<url>\S+) [^"]*" (?P<status>\d{3}) (?P<size>\d+)$')

def parse(lines):
    bad = 0
    for line in lines:
        m = LINE.match(line.rstrip("\n"))
        if m: yield m.groupdict()
        else: bad += 1
    parse.bad = bad            # set after the generator is fully read

def summarise(path, top=3):
    status, urls, errors_by_url = Counter(), Counter(), Counter()
    total = 0
    with open(path) as f:
        for rec in parse(f):
            total += 1
            status[rec["status"]] += 1
            urls[rec["url"]] += 1
            if rec["status"].startswith("5"):
                errors_by_url[rec["url"]] += 1
    return {"total": total, "bad": parse.bad, "status": status,
            "urls": urls.most_common(top), "errors": errors_by_url.most_common(top)}

def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("logfile"); ap.add_argument("--top", type=int, default=3)
    a = ap.parse_args()
    r = summarise(a.logfile, a.top)
    print(f"lines parsed: {r['total']}  skipped (bad): {r['bad']}")
    print("status counts:", dict(sorted(r["status"].items())))
    print("top URLs:");     [print(f"  {c:5d}  {u}") for u, c in r["urls"]]
    print("top 5xx URLs:"); [print(f"  {c:5d}  {u}") for u, c in r["errors"]]
    five = sum(c for s, c in r["status"].items() if s.startswith("5"))
    print(f"server error rate: {five / r['total'] * 100:.2f}%")

if __name__ == "__main__":
    main()

    text = ('1.1.1.1 - - [01/Mar/2026:09:00:01 +0000] "GET /a HTTP/1.1" 200 10\n'

Evaluation and acceptance criteria

  • Shell and Python counts match exactly for all five status codes and the top-3 lists.
  • Parsed plus bad lines equals total lines: 2,000 + 1 = 2,001.
  • The 5xx rate is 12.60% on the sample log, and the test passes.
  • A damaged line never crashes the tool.
  • Runs in under one second on 2,000 lines (it did here; time it yourself with time).

Common pitfalls

  1. Counting the damaged line as data. Symptom: a blank or odd status in sort | uniq -c. Detect: parsed + bad must equal wc -l.
  2. Wrong field number in awk. Symptom: URLs show up as status codes. Detect: awk '{print $9}' file | head before counting.
  3. Forgetting sort before uniq -c. uniq only merges neighbouring equal lines. Detect: the same URL appears twice in the output.
  4. Reading a huge file into memory with f.read(). Loop over the file lines instead, as the code does.
  5. A regex that is too strict and drops real lines when a URL has a space or a quote. Detect: the bad-line count is high on real logs.

Three extensions

  1. Add --status 5xx filtering and a per-minute request count to find the busiest minute.
  2. Add a top-10 client IPs report and flag IPs with more than 20 failed logins.
  3. Stream a growing file like tail -f and print an alert when the error rate of the last 100 lines passes 20%.

Interview talking points

Q1. Why use both shell and Python? The shell answers a question in 10 seconds with no setup. Python is better when the work must be repeated, tested and shared. I used the shell result as a second opinion on the Python result.

Q2. What is the time and memory cost? Time is O(n) for n lines: each line is read once and each counter update is O(1) on average. Memory is O(u), where u is the number of different URLs and status codes, not the number of lines.

Q3. What if the log is 50 GB? The same code works, because it reads line by line. For speed I would split the file into chunks, count each chunk in parallel, and add the counters together. I did not build that here.

15.3 Project: Git Workflow Practice Repository

INTUITION
A team writing one recipe book cannot all edit page 5 at once. Git lets each person copy the book, change their copy on a "branch", and later bring the changes back. This project is a flight simulator: you play every role yourself in a safe folder, so the first real conflict at work is not your first conflict ever.

Goal and why employers care

Build a repository that shows a full team flow: branches, two pull-request style merges, a deliberate merge conflict, a rebase, tags and release notes. A script makes it repeatable, so you can show it and practise it. Employers care because every data and ML team works through branches and reviews, and many candidates have only ever used git add and git commit.

Skills used

Chapter 3, Git and GitHub (commits, branches, merge, rebase, conflicts, tags); Chapter 2, Shell Scripting (scripts with set -euo pipefail, environment variables); Chapter 1, Linux Command Line and the Shell.

Data

No data file. The "code" is a tiny shop pricing module, pricing.py, with one function discount(total). Two developers change it differently, which makes a conflict. A bare repository named remote.git plays the part of GitHub, so the whole project runs offline.

Architecture

gitlab/
  flow.sh            the whole simulation, repeatable
  remote.git/        bare repo = pretend GitHub (made by the script)
  work/              your clone (made by the script)
  README.md          explains each step and the final graph

main:        A ------------- M ---- C'     (M = merge of PR 1, C' = rebased PR 2)
              \             /
feature/ten    B ----------
              \
feature/five   C   (rebased on top of M, conflict fixed, then fast-forwarded)

A pull request (PR) on GitHub is a request to merge a branch, with a review. Locally, a PR is just "branch plus merge", so we simulate it with git merge --no-ff, which always writes a merge commit that marks where the PR landed.

Step-by-step build

  1. Create the remote and the first commit. git init --bare -b main remote.git, clone it, add pricing.py and a README, commit, push.
  2. Tag the first release. git tag -a v0.1.0 -m "First release" and git push origin v0.1.0. An annotated tag is a named, permanent label on a commit.
  3. Start two feature branches from the same commit. One gives 10% off orders of 1,000 or more, the other gives 5% off orders of 500 or more. Both edit the same lines of pricing.py. That is the setup for the conflict.
  4. Merge PR 1. git merge --no-ff feature/ten-percent -m "Merge PR #1: ten percent discount", then push.
  5. Rebase PR 2 onto the new main. Predict first: will it work cleanly? It will not. Real output:
== rebase, expect a conflict ==
CONFLICT (content): Merge conflict in pricing.py
UU pricing.py
def discount(total):
<<<<<<< HEAD
    return total * 0.10 if total >= 1000 else 0
=======
    return total * 0.05 if total >= 500 else 0
>>>>>>> 5cebf30 (Give 5% discount on orders of 500 or more)

UU means "both sides modified". The block between <<<<<<< and ======= is main's version (during a rebase, HEAD is the branch you are rebasing onto). The block after is your commit's version.

  1. Resolve by hand, then continue. Write the file so it keeps both rules, stage it and continue the rebase:
cat > pricing.py <<'PY'
def discount(total):
    if total >= 1000:
        return total * 0.10
    if total >= 500:
        return total * 0.05
    return 0
PY
git add pricing.py
GIT_EDITOR=true git rebase --continue

Real output: Successfully rebased and updated refs/heads/feature/five-percent. (GIT_EDITOR=true accepts the existing message without opening an editor.)

  1. Land PR 2 with a fast-forward (git merge --ff-only), push, and tag v0.2.0.
  2. Read the history and write release notes from it.

*   942780b Merge PR #1: ten percent discount

  1. Undo safely. git revert --no-edit HEAD adds a new commit that cancels the last one, and keeps history honest. Real output: bd86d79 Revert "Give 5% discount on orders of 500 or more".

The whole simulation is the script flow.sh (about 50 lines) made from these steps. Run it in an empty folder.

Evaluation and acceptance criteria

  • bash flow.sh runs from an empty folder to the end with no manual step, and can be run twice (it deletes work and remote.git first).
  • The graph shows one merge commit, one linear (rebased) branch and two tags.
  • git log v0.1.0..v0.2.0 --merges lists exactly one merge: PR 1.
  • After the run, git status is clean and main equals origin/main.
  • The README explains, in your own words, why the rebase conflicted.

Common pitfalls

  1. Rebasing a branch other people already use. Rebase rewrites commits. Detect: git push is refused ("non-fast-forward"). Rule: rebase only your own unshared branches.
  2. Leaving conflict markers in the file. Detect: grep -rn '<<<<<<<' . must print nothing before you commit.
  3. Wrong identity on commits. Detect: git log --format='%an %ae'. The script exports fixed names so the history is clean.
  4. Forgetting to push tags. git push does not push tags. Detect: git ls-remote --tags origin.
  5. Panic during a rebase. Run git rebase --abort to go back to the state before it started.

Three extensions

  1. Add git bisect practice: plant a bug in a later commit and find it with bisect run and a test script.
  2. Add a GitHub Actions file that runs a test on every push (not run here).
  3. Add a git cherry-pick of a hotfix to a release/0.1 branch, and tag v0.1.1.

Interview talking points

Q1. Merge or rebase? Merge keeps the true history and adds a merge commit. Rebase replays my commits on top of the new main, so the history is a straight line. I rebase my private branch to stay up to date, and I merge to land it, so the PR is visible as one unit.

Q2. What is a merge conflict? It happens when two branches change the same lines (or one deletes what the other edits) and Git cannot choose. Git writes both versions into the file between markers. I choose the right final text, remove the markers, stage the file and continue.

Q3. How do you undo a pushed mistake? I use git revert, because it adds a new commit that cancels the old one and does not rewrite shared history. git reset --hard plus a force push is only for private branches.

15.4 Project: Sorting and Searching Benchmark Harness

INTUITION
Sorting a pile of 4,000 exam papers by hand is not just "a bit slower" than sorting 500. A slow method needs about 64 times the work for 8 times the papers, while a clever method needs only about 11 times. Big-O is a promise about how the work grows. This project checks that promise with a stopwatch.

Goal and why employers care

Build a small harness that times two sorts and two searches at growing sizes and prints text tables with a growth-ratio column. It shows you can turn a theory (Big-O) into an experiment with fair timing, correctness checks and honest reporting. Data teams do this when choosing between two ways to process the same data.

Skills used

Chapter 7, Complexity, Arrays, Strings, Hashing and Sorting (Big-O, sorting); Chapter 8, Two Pointers, Sliding Window, Prefix Sums and Binary Search (binary search); Chapter 11, Recursion, Backtracking, Dynamic Programming and Greedy (recursive merge sort).

Data

Random integers from a seeded generator (random.Random(42)), so inputs are the same each run. For searching, a sorted list 0 … n-1, searching for the last item (the worst case for linear search).

Architecture

bench/
  algos.py      bubble_sort, merge_sort, linear_search, binary_search
  bench.py      correctness checks, timing helper, table printer
  README.md     results table + how to read it

for each size n:
   make data (seeded) -> run algorithm 3-5 times -> take the median -> print row
   growth column = time(n) / time(previous n)

Step-by-step build

  1. Write the four algorithms in algos.py. Bubble sort compares neighbours repeatedly, so its work grows with n². Merge sort splits the list, sorts halves and merges, so it grows with n log n. Linear search checks one by one (n). Binary search halves a sorted range each time (log n).
# algos.py
def bubble_sort(a):
    a = list(a); n = len(a)
    for i in range(n):
        swapped = False
        for j in range(n - 1 - i):
            if a[j] > a[j + 1]:
                a[j], a[j + 1] = a[j + 1], a[j]; swapped = True
        if not swapped: break
    return a

def merge_sort(a):
    if len(a) <= 1: return list(a)
    mid = len(a) // 2
    l, r = merge_sort(a[:mid]), merge_sort(a[mid:])
    out, i, j = [], 0, 0
    while i < len(l) and j < len(r):
        if l[i] <= r[j]: out.append(l[i]); i += 1
        else:            out.append(r[j]); j += 1
    return out + l[i:] + r[j:]

def linear_search(a, x):
    for i, v in enumerate(a):
        if v == x: return i
    return -1

def binary_search(a, x):
    lo, hi = 0, len(a) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if a[mid] == x: return mid
        if a[mid] < x: lo = mid + 1
        else: hi = mid - 1
    return -1
  1. Check correctness before timing. A fast wrong answer is worthless. Compare with Python's sorted, and include sizes 0, 1 and 2.
  2. Time fairly. Use time.perf_counter() (a high-resolution clock), repeat, and take the median (the middle value, which ignores one unlucky slow run).
# bench.py (main parts)
import random, time, statistics
from algos import *

def timeit(fn, *args, repeats=5):
    runs = []
    for _ in range(repeats):
        t0 = time.perf_counter(); fn(*args); runs.append((time.perf_counter() - t0) * 1000)
    return statistics.median(runs)          # milliseconds

def check_correct():
    rnd = random.Random(1)
    for n in (0, 1, 2, 10, 200):
        a = [rnd.randint(0, 50) for _ in range(n)]
        assert bubble_sort(a) == merge_sort(a) == sorted(a)
    s = list(range(0, 100, 2))
    assert binary_search(s, 42) == 21 and binary_search(s, 43) == -1 and linear_search(s, 42) == 21

def table(title, rows, header):
    print(title); print(" | ".join(f"{h:>12}" for h in header))
    for r in rows: print(" | ".join(f"{c:>12}" for c in r))
    print()

def growth(rows):
    return ["-"] + [f"{rows[i][1]/rows[i-1][1]:.1f}x" for i in range(1, len(rows))]

The driver loops over sizes [500, 1000, 2000, 4000] for the sorts (3 repeats) and [10_000, 100_000, 1_000_000] for the searches, builds the seeded data, calls timeit, and prints with table.

  1. Predict, then run. Prediction: when n doubles, bubble sort time should go about 4 times (n²: 2² = 4) and merge sort about 2.1 times (n log n: slightly more than 2). Real output:

Linear search: 10 times more data gave about 10 times more time (158 to 1,644 to 16,684 microseconds). Evaluation and acceptance criteria

  • Correctness checks pass before any timing.
  • Bubble-sort doubling ratios fall between 3 and 5 for sizes of 500 and above. Merge-sort ratios fall between 1.8 and 2.6.
  • Binary search time grows by less than 3 times when n grows 100 times.
  • Results come from the median of at least 3 repeats, with the seed and Python version in the README.
  • The README states one limit of the experiment.

Common pitfalls

  1. Timing tiny inputs. At n = 10 the clock noise dominates. Detect: ratios jump around (0.7x, 5x). Use bigger n.
  2. Sorting the same list in place twice. The second run sorts sorted data. The code copies (list(a)), and you can detect this when a repeat is mysteriously faster.
  3. Including data creation in the timing. Build data outside the timed call.
  4. Using a sorted list for bubble sort. With the swapped shortcut it finishes in one pass, which is the best case, not the typical case. Say which case you timed.
  5. Believing one run. Detect: run the harness twice. If the ratios change by more than 20%, add repeats.

Three extensions

  1. Add best, average and worst cases (sorted, random, reversed) and show them in one table.
  2. Add sorted() and a hash-set lookup (x in set) and compare with your own versions.
  3. Save the rows to a CSV and draw a chart with matplotlib (not run here), with n on the x-axis and time on a log scale.

Interview talking points

Q1. Why median and not average? One slow run (the computer was busy) can drag the average up. The median ignores a few extreme values, so it is a steadier summary.

Q2. How do you know the growth is n² and not n³? I look at the ratio when n doubles. For n² it should be about 2² = 4, for n³ about 8. I measured 4.4, 4.2 and 4.1, so n² fits.

Q3. Binary search is so fast; why not always use it? It needs sorted data. Sorting costs n log n once, so it pays off only if I search many times. For one search, linear search on unsorted data is cheaper.

15.5 Benchmark Statistics: Measure Like You Mean It

A single timing is a rumour. Your laptop is also running a browser, a backup and a clock update, so the same code takes 52 ms, then 49, then 71. To compare two programs you need several runs and a summary that ignores the occasional bad one.

The method

  1. Warm up once and throw the result away (imports, caches, memory allocation).
  2. Repeat the measurement at least 7 times. Each repeat should do enough work to take at least 10 ms.
  3. Report the median (middle value) as the typical time and the interquartile range (IQR: 75th percentile minus 25th) as the spread. The minimum is the best estimate of the code's own cost, since noise only adds time.
  4. Compare with a ratio of medians, and say how big the spread is. If the ranges overlap, you have no evidence that one is faster.

Problem 15.5.1 Nine timings in milliseconds from a benchmark: 50, 52, 49, 51, 120, 50, 53, 48, 51. Compute the mean, the median and the IQR, and say which summary to report.

Problem 15.5.2 Build a reusable benchmark helper and use it to compare summing a list with a loop against the built-in sum. The helper prints ratios as booleans here, because exact times depend on your machine; in your README, print the real numbers.

import time, statistics as st
import numpy as np

def bench(fn, repeats=9, min_time=0.01):
    fn()                                   # warm-up
    loops = 1
    while True:                            # find a loop count that takes at least min_time
        t = time.perf_counter()
        for _ in range(loops): fn()
        if time.perf_counter() - t >= min_time: break
        loops *= 2
    runs = []
    for _ in range(repeats):
        t = time.perf_counter()
        for _ in range(loops): fn()
        runs.append((time.perf_counter() - t) / loops)
    q1, q3 = np.percentile(runs, [25, 75])
    return {"median": st.median(runs), "iqr": q3 - q1, "min": min(runs)}

data = list(range(10_000))
def loop_sum():
    total = 0
    for x in data: total += x
    return total
def builtin_sum(): return sum(data)

a, b = bench(loop_sum), bench(builtin_sum)
print("same answer:", loop_sum() == builtin_sum())
print("builtin faster by at least 2x:", b["median"] * 2 < a["median"])
print("ranges do not overlap:", b["median"] + b["iqr"] < a["median"] - a["iqr"])
same answer: True
builtin faster by at least 2x: True
ranges do not overlap: True
COMMON MISTAKE
Benchmarking the first call, or reporting the best of many runs for one program and the average for another. Wrong: "version B took 40 ms and version A took 55 ms" from one run each. Right: same machine, same inputs, same summary statistic for both, warm-up first, and a spread. Also check you measure the right thing: a loop whose result is never used may be skipped by a compiler in other languages, and in Python the first run may pay import costs.

Practice set

Problem 15.1 (easy) In the sample log, 211 requests returned 500 and 41 returned 502, out of 2,000 parsed lines. What is the server error rate?

Answer: (211 + 41) / 2000 = 252 / 2000 = 0.126, so 12.6%.

Problem 15.2 (easy) What does uniq -c do and why must sort come before it?

Answer: It collapses neighbouring equal lines and prefixes each with a count. Without sort, equal lines that are not neighbours are counted separately.

Problem 15.3 (what is the output) After git switch -c fix; git commit ...; git switch main; git merge --no-ff fix, how many parents does the newest commit on main have?

Answer: Two. A --no-ff merge always creates a merge commit with two parents (the old main tip and the branch tip).

Problem 15.4 (find the bug) A tool counts the status with awk '{print $9}' and shows one empty row in the counts. Why, and how do you fix it?

Answer: The damaged line has no ninth field, so $9 is empty. Fix it by filtering with $9 ~ /^[0-9][0-9][0-9]$/ or by validating each line before counting.

Problem 15.5 A benchmark shows bubble sort taking 20 ms at n = 1,000. Estimate the time at n = 3,000.

Answer: Work grows with n², so 3² = 9 times: about 9 × 20 = 180 ms. Real runs may vary by a few tens of percent.

Problem 15.6 Why can the harness in 15.4 not use the same list object for every repeat of bubble_sort without copying?

Answer: An in-place sort would leave the list sorted, so later repeats would time the best case. Copy the list (as list(a) does) so every repeat sees the same input.

Problem 15.7 (interview) A teammate force-pushed a rebased shared branch and your push is now rejected. What do you do?

Answer: Do not force-push over their work. Fetch, look at git log --oneline --graph origin/branch, and either rebase my commits onto the new remote branch (git rebase origin/branch) or cherry-pick them. Then agree as a team never to rebase shared branches.

Problem 15.8 (interview) You are asked to prove that merge sort is "n log n" using timings. What do you show, and what would convince you?

Answer: Show the time at several doubling sizes with the median of repeats. For n log n the ratio is a little above 2 (here 2.2, 2.1, 2.1), which is clearly below the 4 of n². I would also check correctness first, and say the timings are one machine only.
