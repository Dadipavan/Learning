22.7 PySpark: partitions, shuffles, joins, skew, caching and the Spark UI

Beginner: the model

Apache Spark is an engine that runs a query across many machines (or many cores of one). PySpark is its Python API. A Spark program has one driver (your Python process, which plans the work) and many executors (processes that hold data and run tasks). The data is a DataFrame cut into partitions; each partition is processed by one task. Operations come in two kinds. Transformations (filter, select, groupBy, join) are lazy: they extend the plan. Actions (count, show, collect, write) trigger the run. A job is the work for one action; it is cut into stages at every shuffle; each stage is a set of parallel tasks.

The key distinction for performance: a narrow transformation (filter, select, withColumn) works on each partition independently and needs no data movement. A wide transformation (groupBy, join, distinct, orderBy, repartition) needs rows with the same key to meet, so data is shuffled: written to local disk, sent across the network, read by the next stage. Shuffles dominate the cost of most Spark jobs.

How to read it: the left boxes are input partitions holding mixed keys. Each computes partial sums locally (the middle boxes), which is why groupBy().sum() moves only small partial results, not raw rows. The nine arrows are the shuffle: each of three senders sends data to each of three receivers. On a cluster that is network and disk traffic, and the next stage cannot start until all of it has arrived. Fewer, smaller shuffles mean faster jobs.

Worked example 1 (realistic, not run): the running task in PySpark

from pyspark.sql import SparkSession, functions as F, Window spark = (SparkSession.builder.appName("ch22").master("local[*]") .config("spark.sql.shuffle.partitions", "8") # the default is 200, too many for tiny data .getOrCreate()) orders = spark.read.csv("orders.csv", header=True, inferSchema=True) tiers = spark.createDataFrame( [("c1", "gold"), ("c2", "silver"), ("c3", "gold"), ("c4", "bronze"), ("c5", "silver"), ("c6", "bronze")], ["customer_id", "tier"], ) rev = orders.groupBy("region", "customer_id").agg(F.sum("amount").alias("revenue")) w = Window.partitionBy("region").orderBy(F.col("revenue").desc()) result = (rev.join(tiers, "customer_id", "left") .withColumn("rank", F.row_number().over(w)) .select("region", "customer_id", "revenue", "tier", "rank") .orderBy("region", "rank")) result.show() result.explain() spark.stop()
  1. The session is the entry point. master("local[*]") runs Spark on all cores of this machine, ideal for learning and tests. On a cluster the platform sets the master for you.
  2. spark.sql.shuffle.partitions is the number of partitions after any shuffle; its default is 200. For ten rows that is 200 mostly empty tasks, so we lower it. On big data you raise it so each partition is a manageable size.
  3. read.csv(..., inferSchema=True) reads the file once extra to guess types. On big files supply a schema instead.
  4. groupBy().agg(F.sum(...)) is the wide step: partial sums per partition, shuffle by (region, customer_id), final sums.
  5. The window is defined once (Window.partitionBy("region").orderBy(...)) and applied with F.row_number().over(w). This needs all rows of a region together, so Spark shuffles by region.
  6. With tables this small Spark would pick a broadcast join for tiers automatically. explain() prints the physical plan; read it from the bottom up and look for Exchange (a shuffle) and BroadcastHashJoin.
  7. Expected output of show(): the same six rows as before, drawn in Spark's ASCII table. Spark does not guarantee row order without orderBy, and that is why we sort.
region customer_id revenue tier rank APAC c5 70 silver 1 APAC c6 5 bronze 2 EU c2 80 silver 1 EU c1 35 gold 2 US c3 75 gold 1 US c4 10 bronze 2

Intermediate: partitions, joins and caching

  • Partition count: when reading files, Spark makes about one partition per 128 MB of input by default. After a shuffle you get spark.sql.shuffle.partitions partitions. Rule of thumb: target partitions of about 100 to 200 MB, at least 2 to 3 times as many partitions as cores. Too few: underused cores and memory errors. Too many: scheduling overhead and tiny output files.
  • Join strategies: if one side is small (default threshold 10 MB, setting spark.sql.autoBroadcastJoinThreshold), Spark broadcasts it and no shuffle of the big side happens. Otherwise it does a sort-merge join: shuffle both sides by the key, sort, merge. Use F.broadcast(small) to force the cheap path when you know a table is small.
  • Join key quality: filter and select before the join so less data crosses the network; make sure both key columns have the same type, or Spark casts and may skip optimizations; check nulls (a null key never matches).
  • Caching: df.cache() marks a DataFrame to be kept in memory after its first action. Use it when the same expensive DataFrame feeds several actions (for example, a model's training loop or three reports from one cleaned table). Do not cache something used once, and call unpersist() when done. The Storage tab of the UI shows what is cached and how much space it uses.
  • Lazy plan, repeated work: without cache, every action re-runs the whole plan from the source files. Two count() calls on the same unmaterialized DataFrame read and process the data twice.
from pyspark.sql import SparkSession, functions as F spark = SparkSession.builder.master("local[*]").getOrCreate() events = spark.read.parquet("events_pq") # big users = spark.read.parquet("users_pq") # small (a few MB) slim = events.select("user_id", "price").filter(F.col("price") > 0) # prune early joined = slim.join(F.broadcast(users), "user_id", "left") # no shuffle of events joined.explain() # expect BroadcastHashJoin, no Exchange on events clean = joined.cache() # lazy: nothing happens yet print(clean.count()) # first action: computes and fills the cache print(clean.groupBy("country").agg(F.sum("price")).count()) # reuses the cache clean.unpersist()
  1. Selecting two columns and filtering before the join cuts the rows and the bytes that every later step handles.
  2. F.broadcast(users) promises Spark that users is small enough to ship to every executor. If the promise is false the executors run out of memory, so use it only for genuinely small tables.
  3. In explain() a BroadcastHashJoin with a BroadcastExchange on the small side only, and no Exchange hashpartitioning on the events side, confirms the shuffle is avoided.
  4. cache() itself does nothing. The first action (count) computes the join and stores the partitions; the second action reads from memory.
  5. unpersist() frees the memory for other work.

Expert (runnable): data skew and salting

Skew means a few keys have far more rows than the others. After a shuffle by key, one partition gets the hot key's rows and one task runs far longer than its peers while the rest of the cluster sits idle. The block simulates it: 1 million rows, 1,000 keys with a Zipf-like popularity (key 0 gets about 13 percent of all rows), hashed into 8 partitions. Salting adds a random suffix 0 to 7 to the key so the hot key is spread over several partitions; an aggregation is done in two stages so the answer stays exact.

import numpy as np import pandas as pd rng = np.random.default_rng(7) n, n_keys, n_parts = 1_000_000, 1000, 8 w = 1 / np.arange(1, n_keys + 1) keys = rng.choice(n_keys, n, p=w / w.sum()) vals = rng.integers(1, 100, n) def part_sizes(k): h = pd.util.hash_array(k.astype(np.int64)) return np.bincount(h % n_parts, minlength=n_parts) before = part_sizes(keys) print("hottest key share:", round((keys == 0).mean(), 3)) print("before:", before.tolist(), "max/mean =", round(before.max() / before.mean(), 2)) salt = rng.integers(0, 8, n) after = part_sizes(keys * 8 + salt) print("after :", after.tolist(), "max/mean =", round(after.max() / after.mean(), 2)) df = pd.DataFrame({"k": keys, "salt": salt, "v": vals}) stage1 = df.groupby(["k", "salt"])["v"].sum().reset_index() stage2 = stage1.groupby("k")["v"].sum() direct = df.groupby("k")["v"].sum() print("same answer:", stage2.equals(direct))
  1. Key popularity is proportional to 1/rank. This heavy-tailed shape is common: a few customers, bots or null values account for most rows.
  2. part_sizes mimics Spark's hash partitioning: hash the key, take the remainder by the number of partitions, count rows per partition.
  3. Before salting, the biggest partition holds nearly twice the average (max/mean about 2). That task decides when the whole stage finishes. With 1,000 keys the ratio is mild; with a real hot key holding 50 percent of rows, it is severe.
  4. After salting, the hot key's rows spread over all 8 partitions and the ratio falls. Not to exactly 1.0: other keys still hash unevenly.
  5. Stage 1 sums by (key, salt), stage 2 sums the partial sums by key. Because a sum of partial sums is the total, the answer equals the direct group-by (True). Salting works for decomposable aggregations; for joins, the small side must be replicated across all salt values.

How to read it: red bars are the partitions when hashing only by key, green bars when hashing key plus salt. The dotted line is the perfect split. Partition 0 in red holds a quarter million rows because the hot key lives there. Green is closer to the line. In Spark you would first try the built-in fix, adaptive query execution, which can split skewed shuffle partitions in sort-merge joins automatically; salt by hand only when the UI still shows one monster task.

from pyspark.sql import functions as F SALT = 8 # Two-stage aggregation for a skewed group-by key stage1 = (df.withColumn("salt", (F.rand(seed=1) * SALT).cast("int")) .groupBy("k", "salt").agg(F.sum("v").alias("s"))) total = stage1.groupBy("k").agg(F.sum("s").alias("v")) # Skewed join: salt the big side, replicate the small side across all salts big = big.withColumn("salt", (F.rand(seed=1) * SALT).cast("int")) small = small.withColumn("salt", F.explode(F.array([F.lit(i) for i in range(SALT)]))) joined = big.join(small, ["k", "salt"]) # Often enough: let Spark do it spark.conf.set("spark.sql.adaptive.enabled", "true") spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
  1. The first part is the Spark version of the pandas two-stage aggregate just run.
  2. F.rand(seed=1) gives a uniform number in [0, 1); times 8 and cast to int gives a salt from 0 to 7.
  3. For the join, each row of the big side gets one random salt. Each row of the small side is copied 8 times, once per salt, using explode on an array. The join then matches on (key, salt), so a hot key's rows split into 8 smaller joins.
  4. The cost is 8 times the small side. Salt only the hot keys if the small side is not small.
  5. Adaptive Query Execution (AQE) has been on by default since Spark 3.2. It coalesces tiny shuffle partitions, switches join strategy using real runtime sizes, and can split skewed partitions. Setting the flags explicitly documents your intent.

UDFs versus built-in functions

A plain Python UDF (user-defined function) is called once per row: Spark must serialize each row from the JVM to a Python process and back, and the optimizer cannot see inside it. Built-in functions (pyspark.sql.functions) run inside the JVM, are optimized and can be pushed down. The same effect shows up in pandas: df.apply(f, axis=1) is a row-by-row Python loop, vectorized column arithmetic is the built-in. The block measures the gap on 200,000 rows (timings are not checked because they vary).

import time import numpy as np import pandas as pd rng = np.random.default_rng(0) n = 200_000 df = pd.DataFrame({"amount": rng.integers(1, 500, n), "region": rng.choice(["EU", "US", "APAC"], n)}) rate = {"EU": 0.92, "US": 1.0, "APAC": 0.0065} def row_udf(row): # like a plain Spark UDF: called once per row return row["amount"] * rate[row["region"]] def best(fn, reps=3): times = [] for _ in range(reps): t0 = time.perf_counter(); fn(); times.append(time.perf_counter() - t0) return min(times) slow = best(lambda: df.apply(row_udf, axis=1)) fast = best(lambda: df["amount"] * df["region"].map(rate)) # column-at-a-time, like F.when / F.col arithmetic print("row-at-a-time:", round(slow, 3), "s; vectorized:", round(fast, 4), "s; ratio:", round(slow / fast)) print("same values:", np.allclose(df.apply(row_udf, axis=1), df["amount"] * df["region"].map(rate)))
  1. row_udf mimics a plain UDF: a Python function receiving one row.
  2. The vectorized line maps the region to its rate with a dictionary lookup (done once per distinct value internally) and multiplies whole columns.
  3. On one laptop run: 0.681 s for the row-at-a-time version and 0.0063 s for the vectorized one, about 108 times faster, with identical values. In Spark the penalty is usually larger because of the JVM-to-Python serialization on top.
  4. Escalation ladder in Spark: (1) a built-in function or F.expr SQL expression; (2) a pandas_udf, which receives whole pandas Series in batches via Arrow; (3) a plain UDF only when nothing else works.
from pyspark.sql import functions as F import pandas as pd rates = {"EU": 0.92, "US": 1.0, "APAC": 0.0065} # 1. Built-in: a map literal and column arithmetic (best) rate_col = F.create_map([F.lit(x) for kv in rates.items() for x in kv]) df = df.withColumn("eur", F.col("amount") * rate_col[F.col("region")]) # 2. Vectorized pandas UDF: batches of rows as pandas Series @F.pandas_udf("double") def to_eur(amount: pd.Series, region: pd.Series) -> pd.Series: return amount * region.map(rates) df = df.withColumn("eur2", to_eur("amount", "region")) # 3. Plain UDF: one row at a time (slowest) to_eur_slow = F.udf(lambda a, r: float(a * rates[r]), "double") df = df.withColumn("eur3", to_eur_slow("amount", "region"))

Reading the Spark UI

While a job runs, the driver serves a web page, by default at http://localhost:4040. Learn to read five tabs: Jobs (one row per action), Stages (the units between shuffles), Storage (cached data), Executors (memory, GC, failed tasks per executor) and SQL / DataFrame (the query plan with row counts). Open the page of a slow stage and read its summary metrics for completed tasks: min, 25th percentile, median, 75th percentile and max of duration, shuffle read size, spill.

How to read it: every bar is one task in the stage. The dashed line is the median. In the healthy stage all bars are about 10 seconds, so the stage ends in about 10 seconds' worth of work on each core. In the skewed stage 39 tasks finish quickly and then one task keeps running for about 55 seconds; the stage cannot end until it does. In the UI that appears as a Max duration far above the Median.

KEY IDEA
Debug Spark in this order: (1) explain() to see the plan; (2) the SQL tab to see where the rows are; (3) the slow stage's task summary for skew and spill; (4) only then change configuration. Most "tuning" is really fixing the data layout or the join order.
