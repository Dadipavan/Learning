
<h2>Chapter recap</h2>
<ul><li>Tests: arrange, act, assert. pytest uses plain <code>assert</code>, fixtures (by argument name, scoped), <code>parametrize</code>, markers, <code>tmp_path</code>, <code>monkeypatch</code>. unittest and <code>unittest.mock</code> in the standard library express the same ideas.</li>
<li>Mock where the name is <em>used</em>; inject dependencies (clock, client, random generator) so code is easy to test.</li>
<li><code>logging</code>: loggers produce records, handlers decide where, formatters decide how; two gates (logger level, handler level); configure once at start-up; pass arguments lazily.</li>
<li>CLIs: <code>main(argv)</code> returns an exit code; argparse for small tools, Typer or Click for larger ones; <code>BooleanOptionalAction</code> for flags, never <code>type=bool</code>.</li>
<li><code>pathlib.Path</code> for every path; anchor to <code>__file__</code> or an option, never to the current directory; write to a temporary name then <code>replace</code>.</li>
<li>Dataclasses (frozen, kw_only, <code>default_factory</code>, <code>__post_init__</code>) hold configuration; type hints document and are checked by mypy, not enforced at run time.</li>
<li>Environments: venv or uv per project, <code>pyproject.toml</code> as the single description, a lock file for applications, pre-commit for automatic checks.</li>
<li>Secrets come from the environment, are hidden in <code>repr</code>, and never enter git, logs or image layers; leaked means rotate.</li>
<li>Serving: validate at the edge, load the model once, plain <code>def</code> for blocking work, save preprocessing and model together as a Pipeline plus a metadata file.</li>
<li>joblib: <code>dump/load</code> for models (trusted sources only), <code>Memory</code> for pure slow functions, <code>Parallel</code> only for heavy tasks.</li>
<li>Reproducibility means recording seeds, data fingerprint, parameters, library versions and metrics for every run; MLflow and DVC scale that idea up. Docker ships the environment; Airflow and Prefect schedule idempotent tasks as a DAG.</li></ul>

<p class="problem"><span class="pl">Problem 23.13.8</span> Find the bug: the programmer wants DEBUG messages on stdout, but nothing appears there. Why, and how do you fix it?</p>
@@ex
import logging
import sys

logging.basicConfig(level=logging.DEBUG, stream=sys.stdout, format="%(message)s")
logging.debug("hello")
@@end
<p><strong>Answer:</strong> Nothing is printed to stdout. The first call, <code>logging.warning</code>, silently configures the root logger with a default stderr handler because none existed. <code>basicConfig</code> does nothing when the root logger already has handlers, so the later call is ignored (the message "starting" went to stderr). <p class="problem"><span class="pl">Problem 23.13.13</span> Name four problems in this Dockerfile and fix them.</p>
@@file dockerfile
FROM python:latest
COPY . /app
ENV API_KEY=sk-12345
RUN pip install -r /app/requirements.txt
CMD python /app/serve.py
@@end
<p><strong>Answer:</strong> (1) <code>latest</code> is a moving target, so rebuilds differ; pin a tag such as <code>python:3.12-slim</code>. <p class="problem"><span class="pl">Problem 23.13.14</span> What does this print, and why is the answer a trap for beginners?</p>
@@ex
from joblib import Parallel, delayed

seen = []

def record(i):
    seen.append(i)
    return i

out = Parallel(n_jobs=2)(delayed(record)(i) for i in range(4))
print(out, len(seen))
@@end
<p><strong>Answer:</strong> <code>[0, 1, 2, 3] 0</code>. With the default process-based backend each worker has its own copy of <code>seen</code>; appends happen there and are lost. The parent list stays empty. Workers communicate only through return values (or shared files or databases), so always <em>return</em> what you need.</p>
<p class="problem"><span class="pl">Problem 23.13.15</span> Your CLI should read from standard input when the file argument is <code>-</code>. Write the part of <code>main</code> that opens the input and test it without a real terminal.</p>
<p><strong>Answer:</strong></p>
@@ex
import io
import sys
from contextlib import contextmanager
from pathlib import Path

@contextmanager
def open_input(arg):
    if arg == "-":
        yield sys.stdin
    else:
        with Path(arg).open() as f:
            yield f

sys.stdin = io.StringIO("a,b\n1,2\n")           # a test replaces stdin by a string buffer
with open_input("-") as f:
    print(f.read().splitlines())
@@end
<p>Printed: <code>['a,b', '1,2']</code>. The context manager hides the difference between stdin and a file for the rest of the code. In pytest you would use <code>monkeypatch.setattr("sys.stdin", io.StringIO(...))</code>. <code>pandas.read_csv</code> also accepts the file object directly.</p>

<p class="problem"><span class="pl">Problem 23.13.17</span> Write a context manager <code>timed(name)</code> that logs <code>"name took X s"</code> at INFO level when the block ends, even if the block raises.</p>
<p><strong>Answer:</strong></p>
@@ex
import io
import logging
import time
from contextlib import contextmanager

buf = io.StringIO()
logging.basicConfig(stream=buf, level=logging.INFO, format="%(message)s", force=True)
log = logging.getLogger("timer")

@contextmanager
def timed(name):
    start = time.perf_counter()
    try:
        yield
    finally:
        log.info("%s took %.3f s", name, time.perf_counter() - start)

with timed("sleep"):
    time.sleep(0.05)
try:
    with timed("boom"):
        raise RuntimeError("fail")
except RuntimeError:
    pass
lines = buf.getvalue().splitlines()
print([line.split(" took")[0] for line in lines])
print(float(lines[0].split()[2]) >= 0.05)
@@end
<p>Printed: <code>['sleep', 'boom']</code> then <code>True</code>. The <code>try/finally</code> around <code>yield</code> guarantees the log line even when the block raises, and the exception still propagates to the caller. <code>perf_counter</code> is the right clock for durations because it never goes backwards. We print the names and one check rather than the times, which vary.</p>
<p class="problem"><span class="pl">Problem 23.13.18</span> Configuration precedence: command line beats environment variable beats file beats default. Write <code>merge(*layers)</code> that implements this and test it.</p>
<p><strong>Answer:</strong></p>
@@ex
def merge(*layers):
    """Later layers win; None means 'not set' and is ignored."""
    out = {}
    for layer in layers:
        out.update({k: v for k, v in layer.items() if v is not None})
    return out

defaults = {"C": 1.0, "seed": 0, "out": "runs.jsonl"}
file_cfg = {"C": 0.5}
env_cfg = {"seed": 7, "C": None}
cli_cfg = {"out": "tmp.jsonl", "seed": None}
print(merge(defaults, file_cfg, env_cfg, cli_cfg))
@@end
<p>Printed: <code>{'C': 0.5, 'seed': 7, 'out': 'tmp.jsonl'}</code>. Layers are applied from weakest to strongest. Treating <code>None</code> as "not provided" matters because argparse gives <code>None</code> for options the user did not pass; without that filter an unset flag would erase a value from a weaker layer. Note that <code>0</code> and <code>False</code> are valid values and must not be filtered (the test is <code>is not None</code>, not truthiness).</p>
<p class="problem"><span class="pl">Problem 23.13.19</span> A colleague saved a model with joblib yesterday. Today <code>joblib.load</code> fails or gives odd predictions on another machine. List five causes and one preventive habit.</p>
<p><strong>Answer:</strong> (1) Different scikit-learn version (the class layout changed). (2) Different numpy or Python version. (3) The model refers to your own module (a custom transformer class) which is not importable on the other machine. (4) The file was saved on a different operating system or architecture with an incompatible dependency. (5) The file was truncated or corrupted during copying (check a checksum). Habit: save a metadata file with versions and feature names beside the model (Recipe B), check them on load, pin versions in the container, and keep custom code in an installed package.</p>
<p class="problem"><span class="pl">Problem 23.13.20</span> Find the reproducibility bugs in this training script (list at least four).</p>
@@np
import numpy as np
from sklearn.ensemble import RandomForestClassifier
from sklearn.model_selection import train_test_split

np.random.seed(0)

<p class="problem"><span class="pl">Problem 23.13.21</span> A scheduler may run your task twice. Make <code>save_results(rows, day)</code> idempotent: running it twice for the same day must not duplicate rows.</p>
<p><strong>Answer:</strong></p>
@@ex
import json
import tempfile
from pathlib import Path

def save_results(rows, day, folder):
    target = Path(folder) / f"results_{day}.json"          # the name is derived from the day
    tmp = target.with_suffix(".tmp")
    tmp.write_text(json.dumps(rows))
    tmp.replace(target)                                    # overwrite, never append
    return target

with tempfile.TemporaryDirectory() as d:
    save_results([1, 2, 3], "2026-11-09", d)
    save_results([1, 2, 3], "2026-11-09", d)               # a retry
    print(sorted(p.name for p in Path(d).iterdir()))
    print(json.loads((Path(d) / "results_2026-11-09.json").read_text()))
@@end
<p>Printed: <code>['results_2026-11-09.json']</code> and <code>[1, 2, 3]</code>. The key idea: the output location depends only on the logical input (the day), and each run <em>replaces</em> that output. With a database use "delete the day's rows and insert" in one transaction, or an upsert on a unique key. Appending to a shared file would double the data on a retry.</p>
<p class="problem"><span class="pl">Problem 23.13.22</span> What does this print? (pandas 3 copy-on-write meets test fixtures)</p>
@@ex
import pandas as pd

fixture = pd.DataFrame({"a": [1, 2]})
alias = fixture
alias["b"] = 3
print(list(fixture.columns))

subset = fixture[["a"]]
subset.loc[0, "a"] = 99
print(fixture.loc[0, "a"], subset.loc[0, "a"])
@@end
<p><strong>Answer:</strong> <code>['a', 'b']</code> then <code>1 99</code>. <code>alias = fixture</code> only gives the same object a second name, so adding a column through <code>alias</code> changes it (copy-on-write protects derived objects, not aliases). <code>fixture[["a"]]</code> creates a derived object, and under pandas 3 copy-on-write modifying it never changes the original. In a test suite this means: return a fresh frame from a function-scoped fixture, or call <code>.copy()</code> when a test needs to mutate a shared one.</p>
<p class="problem"><span class="pl">Problem 23.13.23</span> Interview: you must add tests to a model service that has none. What do you test, in what order, and what do you refuse to test?</p>
<p><strong>Answer:</strong> Order by value and cost. (1) Pure functions of the data code (cleaning, feature building): small hand-computed examples, edge cases (empty input, missing values, unseen category). (2) The validation layer: a valid request, each rule violated once, a missing field (status 422). (3) The prediction path with a tiny model trained on synthetic data in a fixture: output shape, range 0 to 1, deterministic with a seed, same result for the same row in a batch of one and a batch of many. (4) A saved-model round trip (dump, load, equal predictions). (5) One smoke test of the whole API with <code>TestClient</code>. (6) A separate, slower suite with a real golden dataset and a metric floor (for example AUC above a threshold). Refuse to test: the exact accuracy of a random model, third-party library internals, and anything that needs the network or production data in the fast suite.</p>
