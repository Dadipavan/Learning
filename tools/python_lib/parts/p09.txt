
<h2 id="s17-19">17.19 Going Deeper: Internals, Memory, Speed and What Interviewers Probe</h2>
<h3>How a DataFrame is really stored</h3>
<p>A DataFrame is not a grid of Python objects. Each column is a typed array (a NumPy array for numbers, booleans and datetimes, an extension array for categories, nullable integers and strings). pandas keeps these arrays together with the Index objects that label the rows and columns. Operations on a column therefore run as loops over a contiguous typed array in compiled code, which is the whole source of pandas' speed. A Python-level function applied row by row throws that advantage away, because every cell must be boxed into a Python object again.</p>
<div class="callout blue"><div class="lab">KEY IDEA</div><div class="txt">The Index is a typed, <strong>immutable</strong> array with a lookup structure that is built lazily on first use. Looking up a label in a unique index is a hash lookup, not a scan, which is why <code>df.loc[label]</code> on a set index is fast and why a non-unique index makes lookups slower and sometimes returns several rows instead of one.</div></div>
@@CODE
import numpy as np
import pandas as pd

codes, uniques = pd.factorize(pd.Series(["b", "a", "b", "c"]))
print(codes.tolist(), list(uniques))

df = pd.DataFrame({"a": [1, 2, 3]})
shallow = df.copy(deep=False)
print(np.shares_memory(df["a"].to_numpy(), shallow["a"].to_numpy()))
shallow.loc[0, "a"] = 99
print(np.shares_memory(df["a"].to_numpy(), shallow["a"].to_numpy()), df["a"].tolist())

idx = pd.Index(["x", "y"])
try:
    idx[0] = "z"
except TypeError as e:
    print("Index is immutable:", type(e).__name__)
@@END
<ol>
<li><code>factorize</code> converts labels to small integer codes (b=0, a=1, c=2) plus a table of unique values. This is exactly the first step <code>groupby</code> and <code>category</code> use: integers are cheap to compare, hash and count.</li>
<li>A shallow copy shares the underlying memory with the original, so <code>shares_memory</code> is True: copying costs almost nothing.</li>
<li>When we write to the shallow copy, copy-on-write notices that the data is shared, copies just that column first, and then writes. The memory is no longer shared, and the original is untouched. This is the mechanism behind "never a surprise write".</li>
<li>Index objects refuse item assignment; to change labels you build a new Index (<code>rename</code>, <code>set_index</code>).</li>
</ol>
<h3>What the main operations do underneath</h3>
<ul>
<li><strong>groupby</strong> factorizes the key column(s) into integer group codes, then reduces each value column by those codes. Built-in reducers (<code>sum</code>, <code>mean</code>, <code>count</code>, <code>min</code>, <code>max</code>) are compiled loops. A lambda forces a Python call per group.</li>
<li><strong>merge</strong> is a hash join: it builds a hash table of keys from one side and probes it with the other. Cost grows roughly with the sum of the two sizes, plus the size of the output, which is why a many-to-many join can explode memory.</li>
<li><strong>sort_values</strong> sorts one or more keys; use <code>kind="stable"</code> when ties must keep their input order.</li>
<li><strong>Boolean masks</strong> allocate a full-length mask and a new frame; <code>query</code> and <code>eval</code> can avoid temporaries for large frames when the optional <code>numexpr</code> package is installed (not run here).</li>
<li><strong>String dtype:</strong> in pandas 3.0 the default <code>str</code> dtype stores text in a dedicated string array rather than as one Python object per cell. Missing values are NaN-like, and <code>.str</code> methods return typed results. With <code>pyarrow</code> installed it uses Arrow storage, which is smaller and faster; without it, a Python-backed storage is used. Check <code>pd.options.mode.string_storage</code>.</li>
<li><strong>Datetime resolution:</strong> timestamps are no longer always nanoseconds; the unit is inferred (our examples show microseconds). Arithmetic between different units converts to the finer one. Dates far outside the nanosecond range (year 1500 or 3000) now work without special handling.</li>
<li><strong>Nullable dtypes</strong> (<code>Int64</code>, <code>Float64</code>, <code>boolean</code>) keep a separate mask of missing values, so integers stay integers, at some cost in speed and memory compared with plain NumPy types.</li>
</ul>
<h3>Memory arithmetic you should be able to do in your head</h3>
<p>An <code>int64</code> or <code>float64</code> column takes 8 bytes per row, so 10 million rows take 80 MB per column. A table with 20 numeric columns and 10 million rows is about 1.6 GB before any temporaries. A <code>groupby</code>, <code>merge</code> or <code>sort</code> can need an extra copy or two, so plan for two to three times the table size. That arithmetic tells you when to downcast, read fewer columns, process in chunks, or switch tools.</p>
<div class="callout green"><div class="lab">INTERVIEW</div><div class="txt"><strong>What interviewers probe.</strong> (1) Difference between <code>loc</code> and <code>iloc</code> and what slice end points include. (2) Why <code>apply(axis=1)</code> is slow and what to use instead. (3) <code>merge</code> types, how to detect and prevent row multiplication. (4) <code>transform</code> vs <code>agg</code> vs <code>apply</code>. (5) What copy-on-write means and why chained assignment no longer works. (6) How to handle a file bigger than memory. (7) How to deduplicate keeping the latest record. (8) How <code>NaN</code> behaves in comparisons, sums and groupby keys. (9) Time series: <code>resample</code> vs <code>rolling</code>, time zones. (10) Reading code and predicting its output, which is why the practice set has many "what does this print" tasks.</div></div>
<h3>Processing a file bigger than memory</h3>
@@CODE
import io
import pandas as pd

lines = ["user,amount"] + [f"u{i % 4},{i}" for i in range(1, 21)]
text = "\n".join(lines)

totals = {}
for chunk in pd.read_csv(io.StringIO(text), chunksize=6):
    part = chunk.groupby("user")["amount"].sum()
    for user, value in part.items():
        totals[user] = totals.get(user, 0) + int(value)
print(totals)
print(sum(totals.values()), sum(range(1, 21)))
@@END
<ol>
<li>We fake a 20-row file; a real one might have billions of rows on disk.</li>
<li><code>chunksize=6</code> turns <code>read_csv</code> into an iterator of small DataFrames, so only six rows are in memory at a time.</li>
<li>For each chunk we compute the partial sum per user, then merge it into a running dictionary. This works for any aggregation that can be combined from partial results (sum, count, min, max). A mean needs a running sum and a running count; a median does not combine this way.</li>
<li>The grand total matches the arithmetic series 1 + 2 + ... + 20 = 210, a cheap correctness check.</li>
</ol>

<h2>Chapter recap</h2>
<ul>
<li>A DataFrame is a dict of typed Series sharing one Index. Think in columns; operations align on labels.</li>
<li>Read with explicit <code>dtype</code>, <code>parse_dates</code>, <code>na_values</code> and <code>usecols</code>; write with <code>index=False</code>.</li>
<li>Inspect first: <code>shape</code>, <code>info</code>, <code>describe</code>, <code>value_counts</code>, <code>isna().sum()</code>, <code>duplicated().sum()</code>.</li>
<li>Select with <code>loc</code> (labels, end included), <code>iloc</code> (positions, end excluded), Boolean masks with <code>&amp; | ~</code> and brackets, or <code>query</code>.</li>
<li>Assign with <code>df.loc[mask, col] = v</code>, <code>assign</code>, <code>np.where</code>, <code>np.select</code>; never chain indexing in pandas 3.0.</li>
<li>Pick dtypes on purpose: <code>category</code> for low-cardinality text, nullable integers for gaps, <code>str</code> for text, datetimes with <code>format=</code>.</li>
<li>Decide what missing means before filling; flag it; remember <code>groupby</code> drops NaN keys unless <code>dropna=False</code>.</li>
<li><code>groupby</code> is split-apply-combine: <code>agg</code> shrinks, <code>transform</code> keeps length, <code>filter</code> keeps groups. Use named aggregation.</li>
<li>Joins: choose <code>how</code>, always <code>validate</code>, use <code>indicator</code> to see mismatches, and check the row count.</li>
<li>Reshape with <code>melt</code>/<code>pivot</code>/<code>pivot_table</code>; windows with <code>rolling</code>, <code>expanding</code>, <code>resample</code>, <code>shift</code>.</li>
<li>Vectorise, use built-in aggregations, shrink dtypes, build once, measure; leave pandas when data does not fit memory.</li>
</ul>

<p class="problem"><span class="pl">Problem 17.P.21</span> (Expert, interview) Explain why <code>df.apply(f, axis=1)</code> is slow, and give three ways to avoid it with a concrete example for each.</p>
<p><strong>Answer:</strong> <code>apply(axis=1)</code> builds a Series object for every row and calls a Python function once per row, so the work is dominated by interpreter overhead and object creation, not arithmetic. Alternatives: (1) vectorised column arithmetic, <code>df["a"] * df["b"]</code>; (2) <code>np.where</code>/<code>np.select</code> for if/else logic, <code>np.where(df.x &gt; 0, "pos", "neg")</code>; (3) <code>map</code> with a dict for recoding, or the <code>.str</code>/<code>.dt</code> accessors for text and dates. If real per-row logic remains, a list comprehension over <code>zip</code> of columns, or <code>itertuples()</code>, is much cheaper than <code>apply</code>.</p>
<p class="problem"><span class="pl">Problem 17.P.22</span> (Expert) A cohort table shows retention above 100 percent for one cell. Name two likely causes in the code of Recipe 2 and the fix for each.</p>
<p><strong>Answer:</strong> (1) Counting rows (<code>size</code>) instead of distinct customers (<code>nunique</code>): a customer with several orders in the same month counts several times. Fix: <code>nunique</code>. (2) Dividing by the wrong denominator, for example the cohort size taken from a different filter, or computing the cohort from a table that was already filtered to repeat buyers. Fix: derive cohort size from the age-0 column of the same pivot, as the recipe does with <code>counts.div(counts[0], axis=0)</code>. Sanity check: age 0 must be exactly 100 percent and no cell can exceed it.</p>
<p class="problem"><span class="pl">Problem 17.P.23</span> (Expert, design) You must deduplicate and sum a 40 GB CSV of events on a 16 GB laptop. Sketch the approach and its limits.</p>
<p><strong>Answer:</strong> stream with <code>read_csv(chunksize=..., usecols=..., dtype=...)</code>, aggregate each chunk, and combine partial results, as in the "bigger than memory" example; this is exact for sums and counts. Exact global deduplication needs all keys at once: if the set of distinct keys fits in memory, keep a set of seen keys across chunks; if not, partition the data by a hash of the key into several files first, then deduplicate each partition separately. Better still, convert to Parquet once (not run here) and use a tool built for it, such as DuckDB or Polars lazy mode. State clearly that pandas holds everything it processes in memory.</p>
<p class="problem"><span class="pl">Problem 17.P.24</span> (Expert, find the bug) A monthly report uses <code>df.resample("M").sum()</code> and <code>df.applymap(str.strip)</code> and fails after upgrading to pandas 3.0. What changed?</p>
<p><strong>Answer:</strong> the month alias <code>"M"</code> was replaced by <code>"ME"</code> (month end) and the old <code>applymap</code> was removed in favour of <code>DataFrame.map</code>. Fix: <code>df.resample("ME").sum()</code> and <code>df.map(str.strip)</code> (on text-only columns). General lesson: pin your pandas version in <code>requirements.txt</code>, run the test suite after upgrades, and read the release notes.</p>
