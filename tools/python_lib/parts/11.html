22.12 How to solve any big-data and fast-dataframe problem: the playbook

Step 0: the questions to ask in order

  1. How big, really? Rows, columns, bytes on disk, estimated bytes in memory (Section 22.8).
  2. What is the answer's size? A report with 50 rows from 5 billion rows is an aggregation problem; a full-size output is a transformation problem and needs a writable sink.
  3. Which operation is expensive? Narrow steps are cheap. Joins, group-bys, distincts and sorts are the costs.
  4. Who else uses it, and how often? A one-off analysis tolerates minutes; a nightly job needs idempotence and monitoring.
  5. How will I know it is right? Decide the check before you scale up.

How to verify a result

Never ship a scaled-up pipeline without comparing it with a trusted slow version on a sample. Check row counts, key uniqueness, null counts, and totals (with a tolerance for floats). The helper below does that, and the demo shows it catching a planted bug (an inner join that silently drops rows).

import numpy as np import pandas as pd def compare(trusted, candidate, keys, value_cols): """Return a list of human-readable differences (empty list means they agree).""" problems = [] if len(trusted) != len(candidate): problems.append(f"row count {len(trusted)} vs {len(candidate)}") if candidate.duplicated(keys).any(): problems.append("duplicate keys in candidate") merged = trusted.merge(candidate, on=keys, how="outer", suffixes=("_t", "_c"), indicator=True) only = merged["_merge"].value_counts() if only.get("left_only", 0) or only.get("right_only", 0): problems.append(f"keys only in trusted: {only.get('left_only', 0)}, only in candidate: {only.get('right_only', 0)}") both = merged[merged["_merge"] == "both"] for c in value_cols: if not np.allclose(both[c + "_t"], both[c + "_c"]): problems.append(f"values differ in {c}") return problems orders = pd.DataFrame({"cid": [1, 2, 3, 4], "amount": [10.0, 20.0, 30.0, 40.0]}) tiers = pd.DataFrame({"cid": [1, 2, 3], "tier": ["g", "s", "g"]}) # customer 4 unknown trusted = orders.merge(tiers, on="cid", how="left").groupby("cid", as_index=False)["amount"].sum() buggy = orders.merge(tiers, on="cid", how="inner").groupby("cid", as_index=False)["amount"].sum() print("good:", compare(trusted, trusted.copy(), ["cid"], ["amount"])) print("bug :", compare(trusted, buggy, ["cid"], ["amount"]))
  1. compare checks four things in turn: row counts, duplicate keys, keys present on only one side, and values on the shared keys using np.allclose.
  2. The outer merge with indicator=True adds a _merge column saying whether each key is left-only, right-only or in both. It is the quickest way to see which keys went missing.
  3. The trusted version uses a left join and keeps customer 4. The buggy version uses an inner join and drops the unknown customer, so the totals lose 40 and a row.
  4. The good comparison prints an empty list. The buggy one reports the row-count mismatch and the key that exists only in the trusted result, which tells you where to look.

How to debug when it is slow or crashing

  1. Shrink the input (a sample, one partition, the first million rows) until the problem reproduces in seconds.
  2. Look at the plan before the clock: Polars explain(), DuckDB EXPLAIN ANALYZE, Spark explain("formatted"), Dask visualize().
  3. Bisect the pipeline: run it step by step, forcing each with collect() or count(), and time each. The slowest step is usually obvious.
  4. Check data shape: key distribution (value_counts().head()), null share, partition sizes.
  5. Read the right monitor: Spark UI stage task summary, Dask dashboard memory bars, htop or Activity Monitor for a local engine (one busy core means no parallelism, all cores with high memory means spill risk).
  6. Change one thing at a time and keep the measurement next to the change.

22.13 Going deeper: what is under the hood, and what interviewers probe

Memory formats

  • Apache Arrow lays a column out as contiguous buffers: a values buffer, an optional validity bitmap (one bit per row saying null or not), and for strings an offsets buffer plus a bytes buffer. Contiguous, typed memory is what makes vectorized CPU code and zero-copy sharing between libraries possible.
  • Parquet encodings: dictionary encoding (store distinct values once, codes per row), run-length and bit-packing for the codes, delta encoding for sorted numbers; then a general compressor per page. Low-cardinality and sorted columns compress extremely well, which is why sorting before writing helps.
  • pandas 3.0: copy-on-write is the default, so derived objects share memory until one is modified, which removes many hidden copies and makes chained assignment safe by construction; text columns default to the str dtype (backed by PyArrow when it is installed). Even so, a typical pandas operation needs more than one copy of the data in the worst case, which is why you size RAM generously relative to the file.

Execution models

  • DuckDB processes vectors of values per operator and parallelizes with small work units shared by threads; large hash tables and sorts can spill to disk.
  • Polars turns lazy plans into optimized physical plans (projection and predicate pushdown, common subexpression elimination) and has a streaming engine for larger-than-memory work, though not every operation is streamable; unsupported ones fall back to in-memory execution.
  • Dask builds a graph of small tasks and a scheduler runs them; overhead is per task, so partition size is the main tuning knob.
  • Spark converts your DataFrame code into a logical plan, optimizes it (the Catalyst optimizer), chooses physical operators (broadcast or sort-merge join), and generates JVM code for pipelines of narrow operations (whole-stage code generation). Adaptive query execution revises the plan at stage boundaries using real statistics.

Questions interviewers like

QuestionStrong answer, in one breath
Why is Parquet faster than CSV?Columnar (read only needed columns), typed with a schema (no parsing guesses), compressed with encodings, with min/max statistics that let readers skip row groups.
What is a shuffle and why is it expensive?Redistributing rows by key across partitions; it writes to disk, crosses the network and creates a stage barrier. Avoid with broadcast joins, pre-aggregation and fewer wide operations.
Narrow versus wide transformation?Narrow: each output partition depends on one input partition. Wide: depends on many, so a shuffle.
How do you handle skew?Detect it (max task time versus median), isolate or filter hot keys, AQE, salting with a two-stage aggregation or a replicated small side.
Lazy versus eager evaluation?Lazy builds a plan the optimizer can rewrite (pushdown, reordering) and runs on demand; eager runs each step immediately and is easier to debug.
UDF versus built-in?Built-ins are optimized and run in the engine; plain UDFs cross a process boundary per row. Use built-ins, then pandas UDFs, then plain UDFs.
When not to use Spark?When the data fits one machine: DuckDB or Polars is simpler and often faster; Spark startup and shuffles are overhead.
How would you dedupe 5 billion rows?Hash-partition by key, dedupe within partitions with a window or dropDuplicates; if exactness is not needed, a Bloom filter or approximate counts.

Chapter recap

  • Pandas is limited by memory (the whole table in RAM, often several times the file size) and by mostly one core. Measure before you change tools.
  • Cheap fixes first: read fewer columns, downcast integers, use category for repeated strings, and read in chunks. Our 1-million-row table went from 84 MB to 12 MB.
  • Chunking sets memory by chunk size, not file size, but only works for decomposable statistics: sums, counts, min, max, and means as sum over count.
  • Parquet is columnar, typed and compressed, with statistics. Partitioned folders (year=2025/region=EU) allow partition pruning.
  • Polars: expressions, group_by().agg(), over() windows, and lazy scan_* + collect() with pushdown. Use explain().
  • DuckDB: SQL on files and DataFrames, window functions, QUALIFY, COPY ... TO Parquet, memory limits with disk spill.
  • Dask: partitions plus a task graph; compute() is the action; combine partial results correctly; rank-in-group needs a shuffle.
  • Spark: transformations are lazy, actions run jobs, wide operations shuffle. Broadcast small tables, fix skew, cache only reused data, prefer built-ins to UDFs, read the Stages page.
  • Choose the smallest tool that finishes in time: pandas, then DuckDB or Polars, then Dask or Spark.
  • Verify every migration against a trusted slow version on a sample, with tolerance for floats and counts for rows.
