22.5 DuckDB: SQL straight on files and DataFrames

Beginner: what DuckDB is

DuckDB is a database that lives inside your Python process, like SQLite, but built for analytics instead of transactions. There is no server to install or start. You point SQL at a CSV or Parquet file, or at a pandas DataFrame sitting in a variable, and it answers using a columnar, multi-threaded engine that can spill to disk when a query is larger than memory. If you already know SQL (and the SQL document in this library teaches it), DuckDB lets you use that knowledge on files that do not fit in pandas.

The mental model: files are tables. SELECT ... FROM 'orders.csv' or FROM read_parquet('sales/*/*.parquet') works with no loading step. Results come back as a DataFrame with .df() (pandas) or .pl() (Polars). The comparison with SQLite is useful: SQLite stores rows and is excellent for many small reads and writes; DuckDB stores columns and is excellent for scanning, grouping and joining many rows.

INTUITION
Think of DuckDB as "SQLite for analysis". Same lightweight feel (one import, no server), opposite design (columns, vectors, parallel scans). It is a poor fit for an app that writes one row at a time from many users; for that, use PostgreSQL or SQLite.

Worked example 1 (trivial): SQL on a file and on a DataFrame

import duckdb import pandas as pd print(duckdb.__version__) # 1. Query a CSV file by name. No loading step. print(duckdb.sql("SELECT region, SUM(amount) AS revenue FROM 'orders.csv' GROUP BY region ORDER BY region").fetchall()) # 2. Query a pandas DataFrame by its variable name (a "replacement scan"). df = pd.read_csv("orders.csv") print(duckdb.sql("SELECT region, SUM(amount) AS revenue FROM df GROUP BY region ORDER BY region").df())
  1. duckdb.sql(...) parses and plans the query. The data is not read until you ask for results with fetchall() or .df().
  2. FROM 'orders.csv': DuckDB sees a file name in the table position, detects the delimiter, header and column types by sampling, and scans the file.
  3. In the second query df is not a table in any database. DuckDB looks up the Python variable named df in the calling code and scans it directly in memory with no copy of the data into a database.
  4. ORDER BY region makes the order reproducible; without it SQL gives no order guarantee.
  5. Expected values: APAC 75, EU 115, US 85 (hand check: APAC 40 + 30 + 5, EU 20 + 35 + 15 + 45, US 50 + 10 + 25). The runnable SQLite twin below returns exactly these.

The SQL text is standard enough to run in SQLite. This runnable block is the twin of both DuckDB queries: we load the same ten rows into SQLite from a DataFrame (the manual version of a replacement scan) and run the same SQL.

import io, sqlite3 import pandas as pd csv = """order_id,customer_id,region,category,amount 1,c1,EU,book,20 2,c2,EU,toy,35 3,c1,EU,toy,15 4,c3,US,book,50 5,c4,US,toy,10 6,c3,US,toy,25 7,c5,APAC,book,40 8,c5,APAC,book,30 9,c6,APAC,toy,5 10,c2,EU,book,45""" df = pd.read_csv(io.StringIO(csv)) con = sqlite3.connect(":memory:") df.to_sql("df", con, index=False) rows = con.execute("SELECT region, SUM(amount) AS revenue FROM df GROUP BY region ORDER BY region").fetchall() print(rows) print(pd.read_sql("SELECT category, COUNT(*) AS n, AVG(amount) AS avg_amount FROM df GROUP BY category ORDER BY category", con))
  1. The CSV text becomes a DataFrame; to_sql("df", con) copies it into an SQLite table named df, the table name the DuckDB version found by variable name.
  2. The first query is character-for-character the DuckDB query. The three revenues match the hand check.
  3. pd.read_sql runs a query and returns a DataFrame: pandas and SQL together, which DuckDB makes much faster for large inputs.
  4. Category stats: books are orders 1, 4, 7, 8, 10 (20 + 50 + 40 + 30 + 45 = 185 over 5 = 37.0), toys are orders 2, 3, 5, 6, 9 (35 + 15 + 10 + 25 + 5 = 90 over 5 = 18.0).

Worked example 2 (intermediate): window functions, the part SQL does best

A window function computes a value for each row using a "window" of related rows, without collapsing the rows the way GROUP BY does. The three clauses: PARTITION BY (which rows belong together), ORDER BY (their order inside the window) and optionally a frame such as ROWS BETWEEN 1 PRECEDING AND CURRENT ROW (which neighbours to include). SQLite 3.25 and later, and DuckDB, share this syntax.

Problem 22.5.1 Daily sales per region: compute the running total, the change from the previous day, a 2-day moving average, and the rank of each day by sales inside its region (with ties). Run it in SQLite; the same SQL runs in DuckDB.

import sqlite3 con = sqlite3.connect(":memory:") con.execute("CREATE TABLE sales(day INTEGER, region TEXT, amount INTEGER)") con.executemany("INSERT INTO sales VALUES (?, ?, ?)", [ (1, "EU", 10), (2, "EU", 30), (3, "EU", 30), (4, "EU", 20), (1, "US", 5), (2, "US", 15), (3, "US", 10), ]) q = """ SELECT region, day, amount, SUM(amount) OVER (PARTITION BY region ORDER BY day) AS running, amount - LAG(amount) OVER (PARTITION BY region ORDER BY day) AS change, AVG(amount) OVER (PARTITION BY region ORDER BY day ROWS BETWEEN 1 PRECEDING AND CURRENT ROW) AS avg2, RANK() OVER (PARTITION BY region ORDER BY amount DESC) AS rnk, DENSE_RANK() OVER (PARTITION BY region ORDER BY amount DESC) AS drnk FROM sales ORDER BY region, day """ print("region day amount running change avg2 rnk drnk") for r in con.execute(q): print(*r)
  1. The table holds four EU days (with a tie: days 2 and 3 both sold 30) and three US days.
  2. SUM(amount) OVER (PARTITION BY region ORDER BY day) is a running total: with an ORDER BY and no frame, the default frame runs from the first row to the current one. EU runs 10, 40, 70, 90.
  3. LAG(amount) reads the previous row's amount inside the partition; the first day has no previous row, so the subtraction gives None (SQL NULL).
  4. The frame ROWS BETWEEN 1 PRECEDING AND CURRENT ROW averages the current and previous row: EU day 2 is (10 + 30) / 2 = 20.0. The first row has only itself, so its average is 10.0.
  5. RANK gives tied rows the same rank and then skips: EU amounts 30, 30, 20, 10 get ranks 1, 1, 3, 4. DENSE_RANK does not skip: 1, 1, 2, 3.
  6. Remember this about ties for the Practice set: ROW_NUMBER never ties, RANK skips after a tie, DENSE_RANK does not.

Worked example 3 (realistic): the running task in DuckDB, with QUALIFY

import duckdb duckdb.sql(""" CREATE OR REPLACE TABLE rev AS SELECT o.region, o.customer_id, SUM(o.amount) AS revenue FROM 'orders.csv' o GROUP BY o.region, o.customer_id """) tiers = duckdb.sql(""" SELECT * FROM (VALUES ('c1','gold'),('c2','silver'),('c3','gold'), ('c4','bronze'),('c5','silver'),('c6','bronze')) AS t(customer_id, tier) """) duckdb.register("tiers", tiers) # All ranks, same SQL text as the SQLite block in Section 22.1: print(duckdb.sql(""" SELECT r.region, r.customer_id, r.revenue, t.tier, ROW_NUMBER() OVER (PARTITION BY r.region ORDER BY r.revenue DESC) AS rnk FROM rev r LEFT JOIN tiers t USING (customer_id) ORDER BY r.region, rnk """).fetchall()) # Only the top customer per region, using QUALIFY (DuckDB; SQLite does not have it): print(duckdb.sql(""" SELECT r.region, r.customer_id, r.revenue FROM rev r QUALIFY ROW_NUMBER() OVER (PARTITION BY r.region ORDER BY r.revenue DESC) = 1 ORDER BY r.region """).fetchall())
  1. The first statement reads the CSV and groups. CREATE OR REPLACE TABLE ... AS stores the small result inside DuckDB for reuse.
  2. The tiers are a literal VALUES list; AS t(customer_id, tier) names the columns.
  3. The first query is the same logic as the SQLite window query: six rows, ranks 1 and 2 in each region. USING (customer_id) is shorthand for ON r.customer_id = t.customer_id that also merges the key column.
  4. QUALIFY filters on a window function directly. Without it you need a subquery: SELECT * FROM (SELECT ..., ROW_NUMBER() OVER (...) AS rn FROM rev) WHERE rn = 1. The runnable block below uses that portable form.
  5. Expected: the first query returns the six rows already shown in Section 22.1; the second returns ('APAC', 'c5', 70), ('EU', 'c2', 80), ('US', 'c3', 75).
import io, sqlite3 import pandas as pd csv = """order_id,customer_id,region,category,amount 1,c1,EU,book,20 2,c2,EU,toy,35 3,c1,EU,toy,15 4,c3,US,book,50 5,c4,US,toy,10 6,c3,US,toy,25 7,c5,APAC,book,40 8,c5,APAC,book,30 9,c6,APAC,toy,5 10,c2,EU,book,45""" con = sqlite3.connect(":memory:") pd.read_csv(io.StringIO(csv)).to_sql("orders", con, index=False) q = """ SELECT region, customer_id, revenue FROM ( SELECT region, customer_id, SUM(amount) AS revenue, ROW_NUMBER() OVER (PARTITION BY region ORDER BY SUM(amount) DESC) AS rn FROM orders GROUP BY region, customer_id ) WHERE rn = 1 ORDER BY region """ print(con.execute(q).fetchall())
  1. This is the portable equivalent of QUALIFY: compute the window function in an inner query, filter it in the outer one.
  2. A window function can wrap an aggregate: ROW_NUMBER() OVER (... ORDER BY SUM(amount) DESC) works because windows are evaluated after GROUP BY.
  3. The result matches the DuckDB expectation above: APAC c5 70, EU c2 80, US c3 75.

Worked example 4 (expert): bigger than memory and Parquet output

import duckdb con = duckdb.connect("analytics.duckdb") # a persistent database file con.execute("SET memory_limit = '6GB'") # cap RAM; bigger operators spill to disk con.execute("SET temp_directory = '/tmp/duck_spill'") con.execute("SET threads = 4") # Convert a huge CSV into partitioned Parquet in one streaming query. con.execute(""" COPY ( SELECT *, year(CAST(ts AS TIMESTAMP)) AS year FROM read_csv('events.csv', header = true) ) TO 'events_pq' (FORMAT PARQUET, PARTITION_BY (year), COMPRESSION zstd) """) # Query it back; the WHERE prunes the year folders. top = con.execute(""" SELECT user_id, COUNT(*) AS n FROM read_parquet('events_pq/*/*.parquet', hive_partitioning = true) WHERE year = 2025 GROUP BY user_id ORDER BY n DESC LIMIT 10 """).df() print(top) con.execute("EXPLAIN ANALYZE SELECT COUNT(*) FROM read_parquet('events_pq/*/*.parquet')").fetchall()
  1. connect("analytics.duckdb") stores the database in a file you can reopen later. Only one process may write to it at a time.
  2. SET memory_limit and temp_directory tell DuckDB how much RAM it may use and where to spill. Sorts, big joins and large aggregates then continue from disk instead of failing.
  3. The COPY (SELECT ...) TO ... (FORMAT PARQUET, PARTITION_BY (year)) statement reads the CSV in a streaming fashion and writes one folder per year. This is the "convert once" step. The output folder must not already exist.
  4. The second query reads only the year=2025 folder; only the user_id column is touched.
  5. EXPLAIN ANALYZE runs the query and prints the plan with row counts and timings per operator; use it to see where time goes.
COMMON MISTAKE
Wrong: SELECT * FROM 'events.csv' followed by .df() on a 10 GB file. Symptom: DuckDB streams happily, then pandas runs out of memory building the result. Fix: do the filtering and aggregation in SQL and convert only the small result to pandas; or COPY ... TO a file. The engine can handle data larger than memory, but your Python variable cannot.

Going deeper: why DuckDB is fast

  • Vectorized execution: operators process batches of values (around 2,000) at a time instead of one row, keeping data in CPU caches and avoiding per-row interpretation costs.
  • Morsel-driven parallelism: the input is cut into small work units that threads pick up, so all cores stay busy.
  • Pushdown into Parquet: projection and filters are applied while reading, using the footer statistics to skip row groups.
  • Interview question: "When DuckDB and when Spark?" Answer with the data size, the number of machines, the existing platform, and the fact that one big machine with DuckDB beats a small cluster surprisingly often for datasets up to hundreds of GB, while data that must be written by many jobs concurrently belongs in a warehouse or lakehouse.
