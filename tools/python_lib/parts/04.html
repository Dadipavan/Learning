22.4 Polars: fast DataFrames with expressions and a lazy engine

Beginner: what Polars is and the mental model

Polars is a DataFrame library written in Rust. Three things make it different from pandas. It uses all your CPU cores by default. It stores data in the Arrow columnar format. And it has a lazy mode that builds a query plan and optimizes it before running. It also has no row index: rows are just rows, which removes a whole class of alignment surprises.

There are four objects to know. A Series is one column. A DataFrame is an eager table: every operation runs at once. A LazyFrame is a plan: operations are recorded and nothing runs until you call .collect(). An Expression (written pl.col("amount") * 2) is a recipe for computing a column; it does nothing until placed in a context such as select, with_columns, filter or group_by().agg.

How to read it: the left stack is the order in which you wrote the steps. The right stack is what the optimizer runs. It notices that only 3 columns are ever used (projection pushdown) and that the year filter can be applied inside the scan so whole row groups are skipped (predicate pushdown). You wrote four steps; the engine ran two cheaper ones.

The big change in thinking: in pandas you modify columns step by step. In Polars you describe columns as expressions, and several expressions inside one with_columns run in parallel and all see the original frame. They cannot see each other's new columns; chain a second with_columns if you need that.

Worked example 1 (trivial): create, inspect, compute

import polars as pl df = pl.DataFrame({ "region": ["EU", "EU", "US", "APAC"], "amount": [20, 35, 50, 40], }) print(df.shape) # (4, 2) print(df.schema) # region: String, amount: Int64 out = df.with_columns( amount_with_vat=pl.col("amount") * 1.2, big=pl.col("amount") > 30, ) print(out) print(df.select(pl.col("amount").sum()).item()) # 145
  1. pl.DataFrame({...}) builds a table from a dict of columns, like pandas. Polars infers String and Int64.
  2. df.shape is rows and columns: (4, 2). df.schema maps column names to dtypes. It is cheap and worth printing at every step.
  3. with_columns adds two new columns from two expressions in a single pass: the amount times 1.2 and a True/False flag.
  4. select(pl.col("amount").sum()) returns a one-cell DataFrame; .item() pulls out the number, 145 (20 + 35 + 50 + 40).

Expected result: (4, 2), the schema, a four-row table with the two new columns (24.0, 42.0, 60.0 and 48.0 for the VAT column), and the final number 145. The same in pandas runs everywhere: df["amount"].sum() gives 145.

Worked example 2 (realistic): the running task in Polars

The task from Problem 22.1.1: revenue per (region, customer), tier by left join, rank within region. Here orders.csv holds the same ten rows.

import polars as pl orders = pl.read_csv("orders.csv") tiers = pl.DataFrame({ "customer_id": ["c1", "c2", "c3", "c4", "c5", "c6"], "tier": ["gold", "silver", "gold", "bronze", "silver", "bronze"], }) result = ( orders .group_by(["region", "customer_id"], maintain_order=True) .agg(pl.col("amount").sum().alias("revenue")) .join(tiers, on="customer_id", how="left") .with_columns( pl.col("revenue").rank("ordinal", descending=True).over("region").alias("rank") ) .sort(["region", "rank"]) ) print(result)
  1. read_csv loads the ten rows eagerly.
  2. group_by([...], maintain_order=True).agg(...) sums the amount per pair. Without maintain_order=True Polars may return groups in any order, which matters only for tie-breaking later.
  3. .alias("revenue") names the aggregate. Without it the column would keep the name amount.
  4. join(..., how="left") keeps every revenue row and attaches the tier.
  5. rank("ordinal", descending=True).over("region") is the window function. over("region") means "do this separately inside each region but keep all rows". "ordinal" is pandas method="first": ties get distinct ranks in order of appearance.
  6. sort makes the output order reproducible.

Expected result (verified by the pandas and SQLite blocks in Section 22.1; Polars draws it in its own bordered table with dtype labels):

region customer_id revenue tier rank APAC c5 70 silver 1 APAC c6 5 bronze 2 EU c2 80 silver 1 EU c1 35 gold 2 US c3 75 gold 1 US c4 10 bronze 2

Worked example 3 (realistic): lazy scanning of a file bigger than memory

import polars as pl lf = ( pl.scan_csv("events.csv", try_parse_dates=True) .filter(pl.col("country") == "DE") .group_by("user_id") .agg( pl.len().alias("events"), pl.col("price").sum().alias("spend"), ) .filter(pl.col("events") >= 5) .sort("spend", descending=True) ) print(lf.explain()) # read the optimized plan first top = lf.head(1000).collect() # run it, keep the top 1000 only lf.sink_parquet("german_users.parquet") # or stream the whole result to disk
  1. scan_csv returns a LazyFrame. No data is read yet, so this line is instant even for 10 GB.
  2. The next four calls only add steps to the plan. pl.len() counts rows per group.
  3. lf.explain() prints the optimized plan as text. Look for the scan line listing only the needed columns (user_id, country, price) and a filter pushed into the scan. If you see every column, something blocked the pushdown.
  4. collect() executes the plan and returns a DataFrame. Because only the top 1000 rows are needed, ask for them in the plan (head) instead of collecting everything and cutting later.
  5. sink_parquet streams the result to disk in batches, so the final result need not fit in memory either. In recent Polars versions you can also request the streaming engine with lf.collect(engine="streaming") (older versions used collect(streaming=True); check the documentation for your version).

The output cannot be shown because there is no 10 GB file here; the structure to expect is a 1000-row table with columns user_id, events, spend sorted by spend. The idea of the plan is demonstrated by the runnable toy below.

Worked example 4 (expert, runnable): build a tiny lazy engine to see why it is faster

The toy below records filter and select steps without running them. At collect time, it works out which columns are really needed and reads only those from the CSV. It is a few lines, and it is the same trick as projection pushdown.

import io, os, tempfile import pandas as pd csv = """order_id,customer_id,region,category,amount 1,c1,EU,book,20 2,c2,EU,toy,35 3,c1,EU,toy,15 4,c3,US,book,50 5,c4,US,toy,10 6,c3,US,toy,25 7,c5,APAC,book,40 8,c5,APAC,book,30 9,c6,APAC,toy,5 10,c2,EU,book,45 """ path = os.path.join(tempfile.mkdtemp(), "orders.csv") open(path, "w").write(csv) class Lazy: def __init__(self, path): self.path, self.steps = path, [] def filter(self, col, test): self.steps.append(("filter", col, test)); return self def select(self, *cols): self.steps.append(("select", cols)); return self def collect(self, optimize=True): needed = set() for s in self.steps: needed.update([s[1]] if s[0] == "filter" else s[1]) usecols = sorted(needed) if optimize else None df = pd.read_csv(self.path, usecols=usecols) print("columns parsed:", list(df.columns)) out = list(df.columns) for s in self.steps: if s[0] == "filter": df = df[s[2](df[s[1]])] else: out = list(s[1]) return df[out] def plan(): return Lazy(path).filter("region", lambda s: s == "EU").select("customer_id", "amount") print("naive:") a = plan().collect(optimize=False) print("optimized:") b = plan().collect() print("same result:", a.equals(b)) print(b.to_string(index=False))
  1. The ten-row file is written to a temporary folder, so the block is standalone.
  2. The class Lazy stores steps in a list. filter and select run nothing, and they return self so calls can be chained like Polars methods.
  3. In collect, the optimizer step is the set of columns mentioned anywhere in the plan: region (filter), customer_id and amount (select).
  4. With optimize=False all five columns are parsed. With optimize=True only the three needed columns are parsed, the saving you saw in Figure 22.5.
  5. Both plans give the same rows. Optimization changes the cost, never the answer; that is the contract of every query optimizer, in Polars, DuckDB and Spark.
COMMON MISTAKE
Wrong: pl.read_csv("events.csv").filter(...).group_by(...) on a huge file. Symptom: memory spike or kill at the first line; the optimizer never gets a chance to skip columns. Fix: pl.scan_csv("events.csv") and a final .collect() (or sink_parquet). Use eager read_* only when the file is small or you need to look at the data interactively.

Going deeper: Polars internals worth knowing

  • Expressions are compiled into a plan and executed with parallelism across columns and within large columns. This is why pl.col(...).str.to_uppercase() beats a Python loop by a huge factor: the loop (via map_elements) hands one value at a time to the interpreter.
  • Strings repeated often are best stored as pl.Categorical or pl.Enum (a fixed set of allowed values). It is the same idea as pandas category.
  • Missing values are null everywhere, including integers, so an integer column with a missing value stays an integer column (in pandas classic dtypes it becomes float).
  • Interview question: "Why can Polars be faster than pandas on the same machine?" Good answer: columnar Arrow memory, multi-threaded Rust kernels, lazy plans with pushdown, and no row index. Always add: for small data the difference is small, and the pandas ecosystem is broader.
