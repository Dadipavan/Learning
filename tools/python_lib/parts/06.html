22.6 Dask: pandas in pieces, with a scheduler

Beginner: the idea

Dask splits a big table into many pandas DataFrames called partitions, and builds a task graph (a diagram of small jobs and what each one needs). Calling a method such as .sum() only adds boxes to the graph, which is lazy execution. Calling .compute() hands the graph to a scheduler that runs the small jobs on all cores (threads or processes), or on many machines through dask.distributed, and returns an ordinary pandas object. The API deliberately looks like pandas, so existing code often needs few changes. It does not copy the pandas API completely: operations that need all the data in order (a global sort, a rank within groups, an arbitrary row lookup) are expensive or missing.

DEFINITION
Partition: one pandas DataFrame inside the Dask DataFrame. Lazy: building a plan without running it. Persist: run the plan now and keep the result in (distributed) memory so later steps reuse it. Shuffle: move rows between partitions so that rows with the same key end up together; the expensive step.

Worked example 1 (trivial, not run): the Dask version of a pandas group-by

import dask.dataframe as dd ddf = dd.read_csv("orders.csv") print(ddf.npartitions) # 1 for a tiny file; many for a big one lazy = ddf.groupby("region").amount.sum() # nothing has been computed yet print(lazy.compute().sort_index()) # APAC 75, EU 115, US 85
  1. read_csv splits the file into blocks (default tens of MB) and returns immediately; nothing is parsed yet.
  2. ddf.npartitions is 1 for a ten-row file. A 10 GB file at 64 MB blocks gives about 160 partitions.
  3. The group-by is a plan: sum within each partition, then combine the partial sums. compute() runs it and returns a pandas Series. Expected: APAC 75, EU 115, US 85, the same numbers as the pandas, SQLite and DuckDB blocks.

Worked example 2 (runnable): what Dask does inside, in plain pandas

We can reproduce Dask's strategy with pandas alone: cut the table into partitions, reduce each partition separately, combine the partial results. The block also shows the classic trap: an average of averages is wrong when partitions have different sizes.

import numpy as np import pandas as pd rng = np.random.default_rng(1) n = 300_000 df = pd.DataFrame({"region": rng.choice(["EU", "US", "APAC"], n), "price": rng.normal(50, 15, n)}) cuts = [0, 20_000, 120_000, n] # unequal partitions on purpose parts = [df.iloc[a:b] for a, b in zip(cuts[:-1], cuts[1:])] print("partition sizes:", [len(p) for p in parts]) partials = [p.groupby("region")["price"].agg(["sum", "count"]) for p in parts] combined = sum(partials) # element-wise add, aligned on region mean_correct = combined["sum"] / combined["count"] mean_of_means = pd.concat([p.groupby("region")["price"].mean() for p in parts], axis=1).mean(axis=1) truth = df.groupby("region")["price"].mean() print("sum/count equals pandas:", np.allclose(mean_correct.sort_index(), truth.sort_index())) print("mean of means equals pandas:", np.allclose(mean_of_means.sort_index(), truth.sort_index())) print("worst error of mean-of-means:", float((mean_of_means - truth).abs().max()) > 1e-6)
  1. Three partitions of 20,000, 100,000 and 180,000 rows stand in for Dask partitions.
  2. Step one (the "map"): every partition computes the sum and the count of price per region. These are small and can be done anywhere, in parallel.
  3. Step two (the "reduce"): sum(partials) adds the small tables aligned on region. This is what Dask's tree reduction does, in a tree so it works for thousands of partitions.
  4. The correct mean is total sum divided by total count. Dask's mean() does exactly this internally.
  5. The wrong way averages the three partition means with equal weight, so the 20,000-row partition counts as much as the 180,000-row one. The result differs from pandas, so the equality check prints False, and the last line prints True because the error is bigger than 1e-6.
  6. Rule: only combine decomposable partial results (sum, count, min, max, sum of squares). Medians and exact distinct counts need other approaches.

A rank inside a group needs all of a group's rows in one place. In Dask that means a shuffle first. The running task in Dask (not run here):

import dask.dataframe as dd import pandas as pd orders = dd.read_csv("orders.csv") tiers = pd.DataFrame({"customer_id": ["c1", "c2", "c3", "c4", "c5", "c6"], "tier": ["gold", "silver", "gold", "bronze", "silver", "bronze"]}) rev = (orders.groupby(["region", "customer_id"]).amount.sum() .reset_index().rename(columns={"amount": "revenue"})) rev = rev.merge(tiers, on="customer_id", how="left") # small pandas side: cheap join def add_rank(part): part = part.copy() part["rank"] = part.groupby("region")["revenue"].rank(method="first", ascending=False).astype(int) return part ranked = rev.shuffle(on="region").map_partitions(add_rank, meta=rev._meta.assign(rank=0)) print(ranked.compute().sort_values(["region", "rank"]))
  1. The group-by and reset_index give one row per region and customer; rename gives the honest column name.
  2. The merge with a small pandas DataFrame is cheap: Dask sends the small table to every partition (a broadcast join) instead of shuffling the big one.
  3. Dask has no distributed "rank within group". The standard pattern is: shuffle(on="region") so that all rows of a region are in the same partition, then run an ordinary pandas function on each partition with map_partitions.
  4. meta= tells Dask the output columns and dtypes without running the function. Without it, Dask guesses by running your function on fake data, which can be slow or wrong.
  5. Expected: the same six rows as Problem 22.1.1.

Worked example 3 (runnable): a shuffle join, step by step

Joining two big tables is the hardest distributed operation. Both sides are hash-partitioned by the join key, so matching keys land in the same partition number, then each pair of partitions is joined locally. The block does that with pandas and checks it against a single big merge.

import numpy as np import pandas as pd rng = np.random.default_rng(2) orders = pd.DataFrame({"customer_id": rng.integers(0, 5_000, 100_000), "amount": rng.integers(1, 100, 100_000)}) customers = pd.DataFrame({"customer_id": np.arange(5_000), "tier": rng.choice(["gold", "silver", "bronze"], 5_000)}) K = 4 def split(frame): bucket = pd.util.hash_pandas_object(frame["customer_id"], index=False) % K return [frame[bucket == i] for i in range(K)] o_parts, c_parts = split(orders), split(customers) print("order rows per partition:", [len(p) for p in o_parts]) joined = pd.concat([o.merge(c, on="customer_id", how="left") for o, c in zip(o_parts, c_parts)]) direct = orders.merge(customers, on="customer_id", how="left") key = ["customer_id", "amount", "tier"] print("rows:", len(joined), len(direct)) print("same result:", joined.sort_values(key).reset_index(drop=True).equals(direct.sort_values(key).reset_index(drop=True)))
  1. Two tables: 100,000 orders and 5,000 customers, joined on customer_id.
  2. hash_pandas_object gives a stable hash for each key; the remainder modulo K (4) picks a partition. A stable hash is essential: both sides must agree where each key goes. (Python's built-in hash of strings changes between runs, which is a real production bug.)
  3. The orders table splits into four roughly equal parts, since customer ids are spread evenly.
  4. Each pair of partitions is merged independently; no pair needs rows from another pair. That independence is the whole trick, and it is what lets different machines do the pairs at the same time.
  5. The concatenated result equals one big merge (after sorting, because partition order is not row order). Moving rows to their partition is the shuffle, the expensive part on a real cluster because it crosses the network.
COMMON MISTAKE
Wrong: ddf.head() to peek at the data, or calling .compute() on a result as large as the input. Symptom: head() shows only rows from the first partition and misleads you; compute() of a huge frame crashes the notebook because the result becomes one pandas object. Fix: aggregate first and compute small results, write big results with to_parquet, and use ddf.sample(frac=0.01).compute() for a representative peek.

Going deeper: scheduling and sizing

  • Aim for partitions of roughly 100 MB. Thousands of tiny partitions drown the scheduler in overhead (each task costs about a millisecond of bookkeeping); a few giant ones lose parallelism and risk memory errors.
  • The threaded scheduler is good for NumPy/pandas code that releases Python's global interpreter lock. Pure-Python functions need processes (or a distributed cluster).
  • With Client() the dashboard shows the task stream, per-worker memory and progress. A worker bar turning orange or red means it is spilling to disk or close to being killed: use smaller partitions or fewer parallel tasks.
  • Recent Dask versions plan queries with an optimizer (the dask-expr layer), so column selection and filters are pushed into the read much like Polars; the API you use stays the same.
