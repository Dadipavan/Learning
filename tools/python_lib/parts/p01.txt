<p>It is Monday morning and the finance team has sent you three files: a CSV of last month's orders (40,000 rows), an Excel sheet with customer regions, and a JSON export from the payment provider. The question sounds simple: "Which regions grew, which customers stopped buying, and do our books match the payment provider?" With plain Python lists and dicts you could answer it, but you would write hundreds of lines and probably get a join wrong. With <strong>pandas</strong> the whole job is about thirty readable lines. Every analyst, data engineer and data scientist uses it daily, which is why interviews for data roles almost always include a pandas exercise.</p>
<p>This chapter is a practical handbook. It is organised by <em>task</em>: reading files, looking at data, selecting, cleaning, grouping, joining, reshaping, time series, speed. Each area starts with a reference table of the functions you will actually use, then worked examples that climb from trivial to realistic. Every code block runs on its own, and every printed result is the real output from pandas 3.0 on NumPy 2.x. By the end you will be able to solve a new pandas problem methodically instead of by search-and-paste.</p>
<p><em>Words you need.</em> <strong>Vectorised</strong> means one call works on a whole column at once, with the loop running in fast compiled code. <strong>Index</strong> is the set of row labels. <strong>dtype</strong> is the data type of a column. <strong>NaN</strong> is "not a number", the usual marker for a missing value. <strong>Copy-on-write</strong> is the rule (always on in pandas 3.0) that a changed object never silently changes another one.</p>

<h2 id="s17-1">17.1 What pandas Is, When to Use It, and the Mental Model</h2>
<div class="callout blue"><div class="lab">INTUITION</div><div class="txt">pandas is a spreadsheet you drive with code. A <strong>DataFrame</strong> is the sheet, a <strong>Series</strong> is one column, and the <strong>Index</strong> is the row labels. Unlike a spreadsheet it can hold millions of rows, never loses your steps (they are code), and can be re-run tomorrow on new data.</div></div>
<h3>What it is for, and what it is not for</h3>
<div class="tablewrap"><table class="data"><thead><tr><th>Use pandas when</th><th>Think twice when</th></tr></thead><tbody>
<tr><td>Data fits in memory (rule of thumb: comfortably under a quarter of your RAM)</td><td>Data is larger than memory: consider Polars (lazy engine), DuckDB (SQL on files) or Spark</td></tr>
<tr><td>Tabular data with mixed types: CSV, Excel, JSON, SQL results, Parquet</td><td>Pure numeric arrays with no labels: NumPy is simpler and faster</td></tr>
<tr><td>Exploration, cleaning, reshaping, joins, group summaries, time series</td><td>Heavy row-by-row logic with branching: plain Python or a database may be clearer</td></tr>
<tr><td>Glue between files, SQL, plotting and machine-learning libraries</td><td>Multi-user transactional storage: use a database</td></tr>
</tbody></table></div>
<h3>Install, version check, import convention</h3>
<p>Install with <code>pip install pandas</code> (add <code>openpyxl</code> for <code>.xlsx</code> files and <code>pyarrow</code> for Parquet; the second is <em>not run here</em>, because we only use what is installed). The universal import convention is <code>import pandas as pd</code> together with <code>import numpy as np</code>. Always check the version, because behaviour changed in 3.0.</p>
@@CODE
import pandas as pd
import numpy as np

print(pd.__version__)
print(np.__version__)
print(pd.options.display.max_rows)
@@END
<ol><li><code>import pandas as pd</code> loads the library under the short name every tutorial uses.</li><li><code>import numpy as np</code> is imported alongside because pandas columns are built on NumPy arrays and you will use <code>np.nan</code>, <code>np.where</code> and friends.</li><li><code>pd.__version__</code> prints the version string. Here it is a 3.0 release, so string columns default to the new <code>str</code> dtype and copy-on-write is always on.</li><li>The NumPy version should be 2.x. <code>pd.options</code> holds display and behaviour settings; <code>max_rows</code> is the number of rows printed before pandas truncates with <code>...</code>.</li></ol>
<h3>The mental model</h3>
<figure><img src="images/lib17_model.png" alt="A DataFrame drawn as an index column plus three coloured column boxes, each with its own dtype" loading="lazy"/><figcaption>A DataFrame is a dict of Series that share one Index. Each Series has exactly one dtype.</figcaption></figure>
<p><strong>How to read it:</strong> the grey box on the left is the Index (row labels 0, 1, 2). Each coloured box is a column, and its dtype is written underneath. Because columns are separate, a DataFrame can mix text, numbers and booleans, but inside one column everything has the same type. Operations <em>align on the Index labels</em>, not on position: that single rule explains most surprising pandas behaviour, including joins, arithmetic between Series and assigning a Series as a new column.</p>
<div class="callout green"><div class="lab">KEY IDEA</div><div class="txt">Think in columns, not rows. Instead of "for each row, do X", say "take this column, apply X to all of it". Almost every fast and readable pandas line is a whole-column statement.</div></div>

<h3>Beginner: build the three objects</h3>
@@CODE
import pandas as pd

s = pd.Series([10, 7, 3], index=["Oslo", "Rome", "Lima"], name="sales")
print(s)
print(s["Rome"], s.iloc[0])
print(s.index)
print(s.dtype)
@@END
<ol><li>A Series is built from a list plus an optional list of labels. <code>name="sales"</code> becomes the column name if the Series is later put in a DataFrame.</li><li><code>print(s)</code> shows labels on the left, values on the right, and a footer with the name and dtype.</li><li><code>s["Rome"]</code> looks up by <em>label</em>. <code>s.iloc[0]</code> looks up by <em>position</em>. Labels and positions are different things; keep them apart.</li><li><code>s.index</code> is an <code>Index</code> object. In pandas 3.0 an index of text has dtype <code>str</code>.</li><li><code>s.dtype</code> is <code>int64</code>, the type of the values.</li></ol>
<h3>Intermediate: a DataFrame from records, and index alignment</h3>
@@CODE
import pandas as pd

rows = [
    {"city": "Oslo", "sales": 10, "paid": True},
    {"city": "Rome", "sales": 7, "paid": False},
    {"city": "Oslo", "sales": 3, "paid": True},
]
df = pd.DataFrame(rows)
print(df)
print(df.dtypes)

a = pd.Series([1, 2, 3], index=["x", "y", "z"])
b = pd.Series([10, 20, 30], index=["y", "z", "w"])
print(a + b)
@@END
<ol><li>A list of dicts is the natural shape of JSON and of API responses. Each dict is a row; keys become columns.</li><li><code>df.dtypes</code> confirms that pandas guessed <code>str</code>, <code>int64</code> and <code>bool</code>. If a key were missing from some dict, that cell would be NaN.</li><li>Series <code>a</code> has labels x, y, z; <code>b</code> has y, z, w.</li><li><code>a + b</code> matches by <em>label</em>, not position. Labels y and z exist in both, so they add (12 and 23). Labels x and w exist in only one, so the result is NaN. The ints became floats because NaN needs a float column.</li></ol>
<div class="callout cream"><div class="lab">REAL JOB</div><div class="txt">Alignment is why pandas is safe for joining two columns from different tables: it will not silently pair row 5 of one with row 5 of the other if their ids differ. It is also why a stray duplicate or mismatched index suddenly fills a column with NaN. When you see unexpected NaN after arithmetic, compare the two indexes first.</div></div>
<h3>Expert: custom index, set_index, reindex</h3>
@@CODE
import pandas as pd

df = pd.DataFrame({"id": [101, 102, 103], "name": ["Ana", "Bo", "Cy"], "score": [88, 92, 75]})
by_id = df.set_index("id")
print(by_id)
print(by_id.loc[102, "name"])
print(by_id["score"].reindex([101, 999]))
print(by_id.reset_index().columns.tolist())
print(by_id.index.is_unique, df.index)
@@END
<ol><li>The <code>id</code> column becomes the index, so <code>loc[102, ...]</code> means "the row whose id is 102".</li><li><code>by_id.loc[102, "name"]</code> returns a single value, <code>Bo</code>.</li><li><code>reindex([101, 999])</code> asks for exactly those labels. 999 does not exist, so it gets NaN instead of an error. This is the safe way to "look up and tolerate misses".</li><li><code>reset_index()</code> puts <code>id</code> back as an ordinary column at the front.</li><li><code>is_unique</code> is worth checking before you rely on an index as a key. <code>df.index</code> shows the default <code>RangeIndex</code>, which stores only start, stop and step, so it costs almost no memory.</li></ol>
<div class="callout blue"><div class="lab">DEFINITION</div><div class="txt"><strong>axis</strong> names a direction. <code>axis=0</code> (or <code>"index"</code>) means "going down the rows", so <code>df.sum(axis=0)</code> gives one number per column. <code>axis=1</code> means "going across the columns", so <code>df.sum(axis=1)</code> gives one number per row. Writing the word (<code>axis="columns"</code>) is clearer than the digit.</div></div>
