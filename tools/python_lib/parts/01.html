Priya works at an online shop. On Monday the data team drops a file called events.csv into a shared folder: every click, cart and purchase from the last year. It is 10 GB. Her laptop has 16 GB of memory. She types pd.read_csv("events.csv"), the fan spins up, the notebook freezes for four minutes, and then the kernel dies with no message. She did nothing wrong. Pandas is a superb tool, but it was designed to hold a table in memory, and a table can be bigger than memory.

This chapter is the map of what to do next. You will learn to measure how big a problem really is, shrink it with cheap pandas tricks, read it in chunks, and then move to the right bigger tool: Parquet files (a compact column-based file format), Polars (a very fast DataFrame library), DuckDB (a database that runs SQL directly on files), Dask (pandas split across many pieces) and PySpark (the cluster engine used in many companies). By the end you will be able to choose between them on purpose, write the same task in each, read a Spark UI, and fix the usual disasters: out-of-memory kills, skewed joins and slow Python functions.

22.1 What these libraries are, and when to leave pandas

Beginner: the problem in one picture

A DataFrame is a table: rows are records, columns are fields. Pandas keeps the whole table in RAM (the fast working memory of your computer) and works on one CPU core for most operations. That gives two limits. Memory: if the table needs more RAM than you have, the program crashes or starts swapping to disk and crawls. Speed: if a job takes an hour on one core while your laptop has eight, seven cores sit idle.

The tools in this chapter attack those two limits with three ideas. Learn the ideas once and every library becomes easier.

  • Columnar storage. Store each column together, not each row. A question about one column reads only that column (figure below).
  • Lazy execution. Do not run each line immediately. Collect the whole plan, let an optimizer clean it up, then run once.
  • Partitioning. Cut the data into pieces that can be processed independently (in parallel, or one at a time), then combine the partial answers.

How to read it: each small square is one cell. In the row store (a CSV file or a sqlite3 table) the cells of a row sit next to each other on disk, so adding up amount forces the reader to walk past every other cell. In the column store the cells of a column sit together, so only the orange column is read. With 4 columns that saves about three quarters of the reading; with 100 columns it saves 99 percent. This is the main reason Parquet, Polars and DuckDB are fast on analytics.

KEY IDEA
There is no best library, only the smallest tool that finishes in time. Each step up (pandas, Polars/DuckDB, Dask, Spark) buys capacity and costs simplicity: more setup, less debugging comfort, more concepts (partitions, shuffles). Cheap fixes first: read fewer columns, use smaller dtypes, read in chunks.

The running task used in this chapter

To compare libraries fairly, we solve one small task in all of them. Ten orders, six customers. For each region, rank customers by their total revenue (rank 1 is the biggest), and attach each customer's loyalty tier. That needs a group-by, a join and a window function (rank within a group), which are the three operations that decide whether a tool is any good. First in pandas.

Problem 22.1.1 Using the ten orders and the customer tiers below, produce one row per (region, customer) with the customer's revenue, tier and rank within the region. Compute it with pandas.

import io import pandas as pd orders = pd.read_csv(io.StringIO("""order_id,customer_id,region,category,amount 1,c1,EU,book,20 2,c2,EU,toy,35 3,c1,EU,toy,15 4,c3,US,book,50 5,c4,US,toy,10 6,c3,US,toy,25 7,c5,APAC,book,40 8,c5,APAC,book,30 9,c6,APAC,toy,5 10,c2,EU,book,45""")) tiers = pd.DataFrame({"customer_id": ["c1", "c2", "c3", "c4", "c5", "c6"], "tier": ["gold", "silver", "gold", "bronze", "silver", "bronze"]}) rev = orders.groupby(["region", "customer_id"], as_index=False)["amount"].sum() rev = rev.rename(columns={"amount": "revenue"}) rev = rev.merge(tiers, on="customer_id", how="left") rev["rank"] = rev.groupby("region")["revenue"].rank(method="first", ascending=False).astype(int) print(rev.sort_values(["region", "rank"]).to_string(index=False))
  1. read_csv(io.StringIO(...)) reads CSV text from a string as if it were a file. This keeps the block standalone.
  2. groupby([...], as_index=False)["amount"].sum() adds up the amount per (region, customer) pair. as_index=False keeps the keys as normal columns.
  3. rename gives the new column an honest name, revenue.
  4. merge(tiers, on="customer_id", how="left") is a left join: every revenue row is kept and the tier is attached.
  5. groupby("region")["revenue"].rank(...) is the window function: it ranks within each region. method="first" breaks ties by order of appearance and ascending=False makes the largest revenue rank 1.
  6. The last line sorts for a stable, readable print. Check by hand: EU c2 = 35 + 45 = 80, c1 = 20 + 15 = 35. US c3 = 75, c4 = 10. APAC c5 = 70, c6 = 5.

Keep these six rows in mind. Every other library in the chapter must give the same six rows, and the next block proves the SQL version does.

import io, sqlite3 import pandas as pd csv = """order_id,customer_id,region,category,amount 1,c1,EU,book,20 2,c2,EU,toy,35 3,c1,EU,toy,15 4,c3,US,book,50 5,c4,US,toy,10 6,c3,US,toy,25 7,c5,APAC,book,40 8,c5,APAC,book,30 9,c6,APAC,toy,5 10,c2,EU,book,45""" con = sqlite3.connect(":memory:") pd.read_csv(io.StringIO(csv)).to_sql("orders", con, index=False) con.execute("CREATE TABLE tiers(customer_id TEXT, tier TEXT)") con.executemany("INSERT INTO tiers VALUES (?, ?)", [("c1","gold"),("c2","silver"),("c3","gold"),("c4","bronze"),("c5","silver"),("c6","bronze")]) sql = """ WITH rev AS ( SELECT region, customer_id, SUM(amount) AS revenue FROM orders GROUP BY region, customer_id ) SELECT r.region, r.customer_id, r.revenue, t.tier, ROW_NUMBER() OVER (PARTITION BY r.region ORDER BY r.revenue DESC) AS rnk FROM rev r LEFT JOIN tiers t ON t.customer_id = r.customer_id ORDER BY r.region, rnk """ for row in con.execute(sql): print(row)
  1. An in-memory SQLite database is created; the orders table is loaded from the same ten rows with to_sql.
  2. A small tiers table is created and filled with executemany (placeholders ? keep values out of the SQL text).
  3. The CTE (WITH rev AS (...)) is the group-by step: one row per region and customer.
  4. LEFT JOIN tiers attaches the tier, same as merge(..., how="left").
  5. ROW_NUMBER() OVER (PARTITION BY region ORDER BY revenue DESC) is the window function: number the rows inside each region, biggest revenue first.
  6. The tuples printed match the pandas table cell for cell (pandas prints a table, SQLite prints tuples; the values are the same). DuckDB accepts this exact SQL text, which is why the DuckDB section can reuse it.
REAL JOB
When you move a pipeline to a bigger tool, never trust it on faith. Keep a tiny sample dataset with a known answer (like these ten rows) and a test that compares the new output with the old output. Most migration bugs (different tie-breaking, null handling, integer overflow) show up on ten rows.
