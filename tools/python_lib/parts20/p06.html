20.10 Columnar files: Parquet and Arrow

A CSV stores data row by row as text. To read one column you still parse every line. Parquet stores data column by column, in compressed, typed blocks, with a footer that holds the schema and per-block statistics. Apache Arrow is the matching in-memory format: a standard layout for columns that lets libraries (pandas, Polars, DuckDB, Spark) share data without copying or re-parsing. The Python package is pyarrow. It was not installed on the study machine, so the pyarrow and pandas Parquet code below is labelled "not run here", followed by runnable demonstrations of the ideas that make Parquet fast.

When to use it, and when not to

  • Use Parquet for analytic tables of more than a few hundred thousand rows, for data you read again and again, for files that keep their types (dates stay dates, integers stay integers, no "007" surprises) and for data lakes where engines read only needed columns and row blocks.
  • Do not use it for tiny files people edit by hand, for append-one-row-at-a-time logging (write batches instead), or when the receiving system only accepts CSV.

Typical use (not run here)

# NOT RUN HERE: pyarrow is not installed on the study machine (pip install pyarrow)
import pandas as pd
import pyarrow.parquet as pq

df = pd.DataFrame({"year": [2024, 2025, 2025], "region": ["n", "s", "n"], "total": [1.5, 2.5, 3.5]})
df.to_parquet("orders.parquet", compression="zstd", index=False)

only_two = pd.read_parquet("orders.parquet", columns=["region", "total"])
recent = pd.read_parquet("orders.parquet", filters=[("year", "==", 2025)])

pf = pq.ParquetFile("orders.parquet")
print(pf.metadata.num_rows, pf.metadata.num_row_groups, pf.schema_arrow)
for batch in pf.iter_batches(batch_size=100_000, columns=["total"]):
    chunk = batch.to_pandas()            # process one slice at a time

df.to_parquet("orders_dataset", partition_cols=["year"])   # folder: year=2024/, year=2025/
  1. One call writes a typed, compressed file; index=False avoids storing the DataFrame index as a column.
  2. columns= reads only some column blocks; filters= compares the request with statistics in the file so row groups that cannot match are skipped.
  3. ParquetFile reads only the footer (rows, row groups, schema), which is cheap even for huge files; iter_batches is the Parquet equivalent of chunksize.
  4. partition_cols writes one sub-folder per value, so a filter on year never opens the other folders.

Runnable demonstration 1: why columns and encodings save space

import numpy as np
import pandas as pd

rng = np.random.default_rng(0)
n = 100_000
df = pd.DataFrame({
    "id": np.arange(n),
    "region": rng.choice(["north", "south", "east", "west"], n),
    "total": rng.normal(50, 10, n).round(2),
})
whole = df.to_csv(index=False)
one_column = df["total"].to_csv(index=False)
print("csv bytes:", len(whole), "| bytes of the total column alone:", len(one_column))
print("share of the file you need:", round(len(one_column) / len(whole), 2))

as_text = df["region"]
as_codes = df["region"].astype("category")
print("text column bytes:", as_text.memory_usage(deep=True))
print("dictionary-encoded bytes:", as_codes.memory_usage(deep=True))
print(as_codes.cat.categories.tolist(), as_codes.cat.codes.dtype)
@@
  1. The CSV text of the whole frame is compared with the CSV text of the total column alone, the size a column-by-column file would need for a query that wants only the total: about a third.
  2. A text column repeats four words 100,000 times. Dictionary encoding stores each distinct word once and replaces every row by a small integer code. The pandas category type is the same idea, and the memory printed shows the saving. The codes fit in int8. Parquet applies this automatically and then compresses again.

Runnable demonstration 2: skipping row groups with statistics

Parquet files are cut into row groups, and each group stores the minimum and maximum of every column. A filter such as "dates in March" lets the reader skip any group whose range does not overlap. The simulation below does exactly that with NumPy.

import numpy as np

rng = np.random.default_rng(1)
days = np.sort(rng.integers(0, 365, 100_000))        # one year of events, sorted by day
group_size = 10_000
groups = [days[i:i + group_size] for i in range(0, len(days), group_size)]
stats = [(g.min(), g.max()) for g in groups]
print("row groups:", len(groups))

lo, hi = 90, 120                                      # "the month of April"
to_read = [i for i, (mn, mx) in enumerate(stats) if mx >= lo and mn <= hi]
print("groups that can match:", to_read)
rows = sum(((g >= lo) & (g <= hi)).sum() for i, g in enumerate(groups) if i in to_read)
check = ((days >= lo) & (days <= hi)).sum()
print("rows found:", rows, "same as full scan:", rows == check)
print("fraction of data read:", len(to_read) / len(groups))
@@
  1. The data is sorted by day and cut into 10 blocks of 10,000 rows; per block we keep only (minimum, maximum), which Parquet writes in its footer for you.
  2. A block can contain matches only if its range overlaps the query: max >= lo and min <= hi. Only blocks 2 and 3 qualify, so 20 per cent of the data is read, and the count equals the full scan.
  3. Sorting matters: with shuffled days every block spans the whole year and nothing can be skipped. That is why people sort or partition by the column they filter on most.
WHY IT MATTERS
Reading Parquet with columns= and filters= is often the difference between a notebook that loads in seconds and one that runs out of memory. In pandas 3 you can also keep the Arrow types after reading (dtype_backend="pyarrow"), which avoids converting everything to NumPy and keeps missing integers as integers. Both parts need pyarrow installed and were not run here.

20.11 Logging, progress, big files and encodings

These four tools make a pipeline observable and survivable. Logging records what happened, with severity levels and without print. A progress bar tells you a long loop is alive. Example 1: logging that you can actually read

import logging, sys, tempfile
from pathlib import Path

logfile = Path(tempfile.mkdtemp()) / "etl.log"
root = logging.getLogger()
root.setLevel(logging.DEBUG)
root.handlers.clear()

console = logging.StreamHandler(sys.stdout)
console.setLevel(logging.INFO)
console.setFormatter(logging.Formatter("%(levelname)-7s %(name)s: %(message)s"))
to_file = logging.FileHandler(logfile)
to_file.setFormatter(logging.Formatter("%(levelname)s|%(name)s|%(message)s"))
root.addHandler(console)
root.addHandler(to_file)

log = logging.getLogger("etl.orders")
log.debug("raw row sample: %s", {"id": 1})
log.info("loaded %d rows from %s", 120, "orders.csv")
log.warning("%d rows rejected (%.1f%%)", 3, 100 * 3 / 120)
try:
    int("12x")
except ValueError as e:
    log.error("parse failed: %s", e)

print("--- file content ---")
print(logfile.read_text().strip())
@@
  1. Handlers on the root logger receive messages from every logger below it. The console handler shows INFO and above in a compact layout; the file handler keeps everything, including DEBUG.
  2. etl.orders is a child of etl; the dots form a hierarchy, so getLogger("etl") tunes a whole subsystem.
  3. The %d and %s arguments are passed separately, so Python builds the string only if the level is enabled.
  4. Real formats add %(asctime)s; it is omitted so the output is repeatable. Inside except, log.exception(...) adds the traceback.
COMMON MISTAKE
Wrong: log.info(f"calling {url} with token {token}"). Symptom: secrets end up in log files and ticketing systems, and the f-string is built even when INFO is off. Fix: log.info("calling %s", url) and never log tokens, passwords or personal data; mask them (token[:4] + "...").

Example 2: a progress bar without tqdm

The tqdm package (not installed here) is the usual choice. The idea is simple enough to build, which also shows how it works: wrap an iterable, count what passes, and report at intervals.

import sys

def progress(iterable, total, desc="", steps=4, out=sys.stdout, width=20):
    marks = {max(1, round(total * k / steps)) for k in range(1, steps + 1)}
    for i, item in enumerate(iterable, 1):
        yield item
        if i in marks:
            filled = round(width * i / total)
            print(f"{desc}: [{'#' * filled}{' ' * (width - filled)}] {100 * i // total:3d}% ({i}/{total})", file=out)

total = 0
for x in progress(range(1, 101), total=100, desc="load"):
    total += x
print("sum =", total)
@@
  1. progress is a generator wrapper: it yields every item unchanged and reports at 25, 50, 75 and 100 per cent. Real tqdm reports by elapsed time, which is why its output cannot be pasted exactly.
  2. Send progress to sys.stderr (the out argument) so stdout stays clean for data. The loop sums 1 to 100: 5050.

Example 3: encodings, byte-order marks and mojibake

import io
import pandas as pd

raw = "Zoë,Müller,café\n".encode("latin-1")          # a file saved by an old tool
try:
    raw.decode("utf-8")
except UnicodeDecodeError as e:
    print("utf-8 failed:", e.reason, "at byte", e.start)
print(raw.decode("latin-1").strip())
print(raw.decode("utf-8", errors="replace").strip())

bom = "id,name\n1,Zoë\n".encode("utf-8-sig")
print(bom[:3])
print(repr(bom.decode("utf-8").splitlines()[0]))
print(repr(bom.decode("utf-8-sig").splitlines()[0]))
print(pd.read_csv(io.BytesIO(bom), encoding="utf-8-sig").columns.tolist())

garbled = "café".encode("utf-8").decode("latin-1")
print(garbled, "->", garbled.encode("latin-1").decode("utf-8"))
@@
  1. A file is bytes. "Zoë" saved as Latin-1 uses the single byte 0xEB; UTF-8 expects a longer sequence there, so decoding fails and the error gives the reason and byte position. Decoding as Latin-1 works. errors="replace" never crashes but swaps bad bytes for �; use it to inspect, never to load data you care about.
  2. Some Windows tools start a UTF-8 file with a byte-order mark (EF BB BF). Plain utf-8 keeps it as an invisible character, so the first header becomes '\ufeffid' and df["id"] fails. utf-8-sig removes it; pandas accepts the same name.
  3. Mojibake is text decoded with the wrong codec (UTF-8 bytes read as Latin-1 give cafÃ©). It is reversible: encode with the wrong codec, decode with the right one.

How to read it: every bar is the same 27-character string. ASCII (red) cannot represent accented letters, so it fails. Latin-1 uses one byte per character. UTF-8 uses one byte for plain letters and two for accented ones, so it is slightly bigger. UTF-16 and UTF-32 use two and four bytes per character (plus a header for UTF-16 and UTF-32). UTF-8 is the safe default for new files; when reading old files, expect Latin-1 or cp1252 from Windows tools.

Example 4: big files in chunks

import os, tempfile
import numpy as np
import pandas as pd

rng = np.random.default_rng(42)
n = 50_000
df = pd.DataFrame({
    "region": rng.choice(["north", "south", "east"], n),
    "units": rng.integers(1, 20, n),
    "price": rng.uniform(1, 100, n).round(2),
})
path = os.path.join(tempfile.mkdtemp(), "sales.csv")
df.to_csv(path, index=False)

revenue, rows_seen = {}, 0
for chunk in pd.read_csv(path, chunksize=10_000, dtype={"region": "category"}):
    rows_seen += len(chunk)
    part = (chunk["units"] * chunk["price"]).groupby(chunk["region"], observed=True).sum()
    for region, value in part.items():
        revenue[region] = revenue.get(region, 0.0) + value

chunked = pd.Series(revenue).sort_index()
full = (df["units"] * df["price"]).groupby(df["region"]).sum().sort_index()
print(rows_seen)
print(chunked.round(0).to_dict())
print("matches full read:", np.allclose(chunked, full))

sample = pd.read_csv(path, usecols=["region", "units"], nrows=3)
print(sample)
@@
  1. The script writes a 50,000-row CSV so it is self-contained; in real life this is the file that does not fit in memory.
  2. chunksize=10_000 makes read_csv an iterator of five DataFrames, one in memory at a time. Each chunk yields a partial result (revenue by region) added into a running dictionary. This works for combinable statistics: sums, counts, min, max; a mean is a sum plus a count; a median is not combinable.
  3. The chunked result is compared with the all-at-once result using np.allclose, because additions in another order differ in the last digits. They match. usecols and nrows are the quickest way to peek at a big file.

How to read it: the red bar is the whole file loaded at once and the other bars use smaller chunks. Memory falls as the chunk shrinks and levels off, because each chunk still has fixed overhead. The trade-off: very small chunks mean more Python-level loop iterations, so pick a chunk that is comfortably small (tens of thousands of rows), not the smallest possible.
