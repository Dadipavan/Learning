20.7 Web APIs: requests and httpx

An API call is one question and one answer over HTTP: you send a method (GET to read, POST to create), a URL, optional headers and body, and you get back a status code, headers and a body, usually JSON. requests is the long-standing simple choice. httpx has almost the same API and adds async support and strict default timeouts. Wrong: requests.get(url) with no timeout. Symptom: a nightly job hangs forever when the server accepts the connection and then goes silent; requests has no default timeout. Example 2: timeouts, retries, backoff, pagination and 429

Retry only what can succeed later: timeouts, connection errors, 429 and 5xx. Never retry 400, 401, 403 or 404, because the answer will not change. Example 3: staying under a rate limit with a token bucket

A token bucket is the classic polite-client tool. The bucket refills at a steady rate, up to a maximum. Each request takes one token. If the bucket is empty you wait. This allows short bursts but a steady average. To keep the example repeatable, the clock is passed in, so we can use a fake clock.

class TokenBucket:
    def __init__(self, rate, capacity, clock):
        self.rate, self.capacity, self.clock = rate, capacity, clock
        self.tokens, self.last = capacity, clock()

    def take(self):
        """Return 0.0 if a request may go now, else the seconds to wait."""
        now = self.clock()
        self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)
        self.last = now
        if self.tokens >= 1:
            self.tokens -= 1
            return 0.0
        return round((1 - self.tokens) / self.rate, 3)

now = [0.0]
bucket = TokenBucket(rate=2, capacity=3, clock=lambda: now[0])
print([bucket.take() for _ in range(5)])
now[0] += 1.0
print([bucket.take() for _ in range(3)])
[0.0, 0.0, 0.0, 0.5, 0.5]

  2. take adds tokens for the time passed (capped), then spends one and returns 0.0, or returns how long to wait for the missing part of a token.
  3. At time 0 the first three calls pass (the burst); the fourth and fifth must wait 0.5 s. After one fake second two tokens are back, so two calls pass and the third waits again.
  4. In real code pass time.monotonic as the clock and time.sleep(wait) when the result is above zero.

During the burst at second 2 the line falls; the red cross shows a moment when the bucket was nearly empty and a request would have had to wait. Between bursts the line climbs at the refill rate and stops at the capacity of 5. The average rate stays at 2 requests per second, but short bursts are allowed.

Authentication in practice

  • Bearer token: Authorization: Bearer <token> in a header. Store the token in an environment variable (os.environ["API_TOKEN"]), never in the script, and never print it.
  • API key: usually a header such as X-API-Key. A key in the URL query string ends up in server logs and browser history, so prefer headers when the API allows.
  • Basic auth: auth=("user", "password"). Only over HTTPS.
  • OAuth 2: you exchange credentials for a short-lived token and must refresh it when it expires. Use a library built for the provider.
  • Proxies: requests and httpx read HTTP_PROXY and NO_PROXY from the environment. If a local test call is unexpectedly routed through a corporate proxy, set NO_PROXY=127.0.0.1 (as the examples do) or pass trust_env=False.

import numpy as np
import pandas as pd

def check_frame(df):
    problems = []
    required = {"id": "int", "total": "float", "region": "str"}
    for col, kind in required.items():
        if col not in df.columns:
            problems.append(f"missing column {col}")
        elif kind == "int" and not pd.api.types.is_integer_dtype(df[col]):
            problems.append(f"{col} should be integer, is {df[col].dtype}")
        elif kind == "float" and not pd.api.types.is_float_dtype(df[col]):
            problems.append(f"{col} should be float, is {df[col].dtype}")
    if "id" in df and df["id"].duplicated().any():
        problems.append(f"duplicate ids: {df.loc[df['id'].duplicated(), 'id'].tolist()}")
    if "total" in df:
        if df["total"].isna().any():
            problems.append(f"{int(df['total'].isna().sum())} missing totals")
        if (df["total"] < 0).any():
            problems.append("negative totals")
    return problems

20.10 Columnar files: Parquet and Arrow

A CSV stores data row by row as text. To read one column you still parse every line. Parquet stores data column by column, in compressed, typed blocks, with a footer that holds the schema and per-block statistics. Apache Arrow is the matching in-memory format: a standard layout for columns that lets libraries (pandas, Polars, DuckDB, Spark) share data without copying or re-parsing. The Python package is pyarrow. It was not installed on the study machine, so the pyarrow and pandas Parquet code below is labelled "not run here", followed by runnable demonstrations of the ideas that make Parquet fast.

When to use it, and when not to

  • Use Parquet for analytic tables of more than a few hundred thousand rows, for data you read again and again, for files that keep their types (dates stay dates, integers stay integers, no "007" surprises) and for data lakes where engines read only needed columns and row blocks.
  • Do not use it for tiny files people edit by hand, for append-one-row-at-a-time logging (write batches instead), or when the receiving system only accepts CSV.

Runnable demonstration 2: skipping row groups with statistics

Parquet files are cut into row groups, and each group stores the minimum and maximum of every column. A filter such as "dates in March" lets the reader skip any group whose range does not overlap. The simulation below does exactly that with NumPy.

import numpy as np

rng = np.random.default_rng(1)
days = np.sort(rng.integers(0, 365, 100_000))        # one year of events, sorted by day
group_size = 10_000
groups = [days[i:i + group_size] for i in range(0, len(days), group_size)]
stats = [(g.min(), g.max()) for g in groups]
print("row groups:", len(groups))

lo, hi = 90, 120                                      # "the month of April"
to_read = [i for i, (mn, mx) in enumerate(stats) if mx >= lo and mn <= hi]
print("groups that can match:", to_read)
rows = sum(((g >= lo) & (g <= hi)).sum() for i, g in enumerate(groups) if i in to_read)
check = ((days >= lo) & (days <= hi)).sum()
print("rows found:", rows, "same as full scan:", rows == check)
print("fraction of data read:", len(to_read) / len(groups))

  1. The data is sorted by day and cut into 10 blocks of 10,000 rows; per block we keep only (minimum, maximum), which Parquet writes in its footer for you.
  2. A block can contain matches only if its range overlaps the query: max >= lo and min <= hi. Only blocks 2 and 3 qualify, so 20 per cent of the data is read, and the count equals the full scan.
  3. Sorting matters: with shuffled days every block spans the whole year and nothing can be skipped. That is why people sort or partition by the column they filter on most.

import sys

def progress(iterable, total, desc="", steps=4, out=sys.stdout, width=20):
    marks = {max(1, round(total * k / steps)) for k in range(1, steps + 1)}
    for i, item in enumerate(iterable, 1):
        yield item
        if i in marks:
            filled = round(width * i / total)
            print(f"{desc}: [{'#' * filled}{' ' * (width - filled)}] {100 * i // total:3d}% ({i}/{total})", file=out)

total = 0
for x in progress(range(1, 101), total=100, desc="load"):
    total += x
print("sum =", total)

Recipe 1. How do I ingest a paginated API into SQLite, safely and repeatably?

Plan: fetch page by page with a cursor, validate each record, set aside the bad ones, and upsert the good ones so that running the job twice gives the same table. To keep the recipe short, fetch_page stands in for requests.get(url, params=..., timeout=5).json(); the real HTTP code with a local server is in 20.7.

import sqlite3

ITEMS = [{"id": i, "name": f"item{i}", "price": str(i * 1.5)} for i in range(1, 8)]
ITEMS[4]["price"] = "n/a"                               # one bad record from the provider

def fetch_page(after, limit):
    page = [x for x in ITEMS if x["id"] > after][:limit]
    return {"items": page, "next": page[-1]["id"] if len(page) == limit else None}

con = sqlite3.connect(":memory:")
con.execute("create table items(id integer primary key, name text not null, price real not null)")
UPSERT = """insert into items values (?, ?, ?)
            on conflict(id) do update set name = excluded.name, price = excluded.price"""
rejected = []

def ingest(page_size=3):
    after, loaded = 0, 0
    while True:
        body = fetch_page(after, page_size)
        good = []
        for rec in body["items"]:
            try:
                good.append((int(rec["id"]), rec["name"], float(rec["price"])))
            except (KeyError, ValueError) as e:
                rejected.append((rec.get("id"), str(e)))
        with con:
            con.executemany(UPSERT, good)
        loaded += len(good)
        if body["next"] is None:
            return loaded
        after = body["next"]

print("run 1 loaded:", ingest())
print("run 2 loaded:", ingest())
print("rows in table:", con.execute("select count(*) from items").fetchone()[0])
print("rejected:", rejected[:1])
print(con.execute("select * from items where id = 7").fetchone())
run 1 loaded: 6
run 2 loaded: 6
rows in table: 6
rejected: [(5, "could not convert string to float: 'n/a'")]
(7, 'item7', 10.5)
  1. Seven provider items; the fifth has a broken price. fetch_page does cursor paging: ids above after, and next is None on a short page.
  2. The table has a primary key and not null columns as the last line of defence. UPSERT overwrites an existing id, so a re-run is harmless.
  3. Each record is converted inside try; a bad one goes to rejected with the reason and the loop continues. with con: commits each page as one transaction.
  4. Each run loads 6 good rows (3, 2 and 1 per page). Run 2 changes nothing: still 6 rows. The bad record is rejected in both runs (only the first is shown).

Recipe 4. How do I do an incremental load with a watermark?

A watermark is the highest updated_at value you have already loaded. Each run asks the source only for rows at or after it. The watermark is stored in the target database and updated in the same transaction as the data, so a crash can never advance it without the rows.

import sqlite3
from datetime import datetime, timedelta

src, dst = sqlite3.connect(":memory:"), sqlite3.connect(":memory:")
for c in (src, dst):
    c.execute("create table orders(id integer primary key, total real, updated_at text)")
dst.execute("create table etl_state(name text primary key, watermark text)")
UPSERT = """insert into orders values (?, ?, ?) on conflict(id) do update
            set total = excluded.total, updated_at = excluded.updated_at"""

def load(overlap_hours=0):
    row = dst.execute("select watermark from etl_state where name = 'orders'").fetchone()
    wm = row[0] if row else "1970-01-01T00:00:00"
    start = (datetime.fromisoformat(wm) - timedelta(hours=overlap_hours)).isoformat()
    rows = src.execute("select id, total, updated_at from orders where updated_at >= ? order by updated_at",
                       (start,)).fetchall()
    with dst:                                         # data and watermark commit together
        dst.executemany(UPSERT, rows)
        if rows:
            dst.execute("""insert into etl_state values ('orders', ?)
                           on conflict(name) do update set watermark = max(watermark, excluded.watermark)""",
                        (rows[-1][2],))
    return len(rows)

src.executemany("insert into orders values (?, ?, ?)",
                [(1, 10.0, "2025-03-01T09:00:00"), (2, 20.0, "2025-03-01T10:00:00"), (3, 30.0, "2025-03-01T11:00:00")])

Recipe 10. How do I cache API responses so reruns are cheap?

from pathlib import Path

20.13 Performance and pitfalls

Where time and memory actually go

  • Round trips and syncs. Every network call and every SQLite commit has a fixed cost (a commit forces a disk sync). Batch, page, and reuse connections.
  • Parsing and memory. CSV and JSON are parsed character by character, and a DataFrame is often several times bigger than its file. Read fewer columns, use smaller dtypes (category, int32), and chunk.
  • Waiting. An HTTP loop is mostly idle; threads or httpx.AsyncClient help, within the provider's limits.
import os, sqlite3, tempfile, time

rows = [(i, f"name{i}", i * 0.5) for i in range(3000)]

def insert_seconds(per_row_commit):
    con = sqlite3.connect(os.path.join(tempfile.mkdtemp(), "t.db"))
    con.execute("create table t(id integer, name text, v real)")
    t0 = time.perf_counter()
    if per_row_commit:
        for r in rows:
            con.execute("insert into t values (?, ?, ?)", r)
            con.commit()
    else:
        with con:
            con.executemany("insert into t values (?, ?, ?)", rows)
    elapsed = time.perf_counter() - t0
    assert con.execute("select count(*) from t").fetchone()[0] == 3000
    con.close()
    return elapsed

slow, fast = insert_seconds(True), insert_seconds(False)
print("same 3000 rows, commit per row is slower than one batch:", slow > fast)

Common mistakes, with symptom and fix

Three more are shown earlier: yaml.load (20.3), no timeout (20.7) and secrets in logs (20.11).

COMMON MISTAKE 1: encoding and newlines
Wrong: open("export.csv") then csv.reader(f). Symptom: accented names turn into Ã© or the script crashes on another computer; on Windows, blank lines appear between rows. The default encoding depends on the machine. Fix: open("export.csv", newline="", encoding="utf-8") (or the encoding the provider documents).
COMMON MISTAKE 2: SQL built with an f-string
Wrong: con.execute(f"select * from users where name = '{name}'"). Symptom: a name such as O'Brien crashes the query, and a crafted name returns or destroys other rows (SQL injection). Fix: con.execute("select * from users where name = ?", (name,)).
COMMON MISTAKE 3: forgetting to commit
Wrong: con.execute("insert ..."); con.close(). Symptom: the script prints no error, but the next run finds an empty table. Fix: with con: con.execute("insert ...") (commits on success, rolls back on error). Remember that with con does not close the connection; call con.close() yourself, or use contextlib.closing.
COMMON MISTAKE 4: codes read as numbers
Wrong: pd.read_csv("zips.csv"). Symptom: zip code 02134 becomes 2134, a product id 1E5 becomes the float 100000.0, and a join to another table silently matches nothing. Fix: pd.read_csv("zips.csv", dtype={"zip": str}). Identifiers are labels, not numbers.
COMMON MISTAKE 5: page-number pagination on live data
Wrong: for page in range(1, 50): get(url, params={"page": page}). Symptom: the final table has duplicates and some missing rows, and the counts differ on every run. Fix: use the cursor or updated_since parameter when the API offers one, and de-duplicate on the primary key with an upsert.
COMMON MISTAKE 6: trusting that the element exists
Wrong: soup.find("span", class_="price").text. Symptom: AttributeError: 'NoneType' object has no attribute 'text' the day the site changes its layout, or on one product with no price. Fix: a helper such as text_or_none from 20.8, counting how many items had missing fields, and failing the job if the missing share suddenly jumps.
COMMON MISTAKE 7: to_sql with replace and an index column
Wrong: df.to_sql("orders", con, if_exists="replace"). Symptom: the table loses its primary key, indexes and column types, and an extra index column appears. Fix: create the table yourself with constraints, then df.to_sql("orders", con, if_exists="append", index=False), or load a staging table and upsert (Recipe 8).
COMMON MISTAKE 8: loading everything, committing everything
Wrong: df = pd.read_csv("40_million_rows.csv"), or a commit inside a row loop. Symptom: MemoryError or the process killed by the operating system; a load that takes hours. Fix: chunksize=, usecols= and dtype= when reading; one transaction per batch of thousands of rows when writing.
COMMON MISTAKE 9: retrying a POST that is not idempotent
Wrong: a retry policy that repeats POST /payments after a timeout. Symptom: the first request had actually succeeded, so the customer is charged twice. Fix: retry only GET, PUT and DELETE by default; for POST send an idempotency key header if the API supports one, or look up the result before repeating.
COMMON MISTAKE 10: swallowing every error
Wrong: try: load(row) except Exception: pass. Symptom: the job reports success while half the rows are missing, and nobody can tell why. Fix: catch the specific exceptions you expect, log the reason with the record key, count rejects, and fail the run when the reject rate passes a threshold.

HTML = ("<table><tr><th>sku</th><th>price</th></tr><tr><td>A</td><td>$1.50</td></tr>"
        "<tr><td>B</td><td>$2.00</td></tr><tr><td>C</td><td>oops</td></tr></table>")
API = '[{"sku": "A", "units": 10}, {"sku": "B", "units": 4}, {"sku": "D", "units": 7}]'

def extract_prices(html):
    rows = [[c.get_text(strip=True) for c in tr.find_all(["th", "td"])]
            for tr in BeautifulSoup(html, "html.parser").find_all("tr")]
    df = pd.DataFrame(rows[1:], columns=rows[0])

    return df

20.15 How to solve any data-access problem: the playbook

The decision flow

  1. Where does it live? Prefer a database or API, then a file download, then scraping.
  2. How big? Fits in about a quarter of RAM: read whole. Otherwise chunk, stream, or use a columnar format.
  3. How does it change? Never: load once. Otherwise pick watermark, cursor or changed-since.
  4. How much do you trust it? Validate at the boundary and keep rejects.
  5. What can fail? Network (timeouts, retries, 429), format (encoding, delimiter, schema drift), process (use transactions and idempotent writes).
  6. How will you know it worked? Counts, sums and key sets compared between source and target.

How to verify a load

  • Counts and totals: rows read = rows loaded + rows rejected; one numeric sum matches in source and target.
  • Keys and samples: compare id sets in both directions; eyeball 3 random rows from each side.
  • Idempotence: run the job twice; the second run must change nothing.

20.16 Going deeper: internals, memory, speed and what interviewers ask

Internals worth knowing

  • sqlite3 transactions. In the default (legacy) mode Python opens a transaction before INSERT, UPDATE and DELETE, so you must commit; since Python 3.12 connect(autocommit=...) gives explicit control. SQLite allows many readers but one writer; WAL mode (pragma journal_mode = wal) lets readers continue while a writer works. Typing is by affinity: a declared type is a preference unless the table is STRICT (below).
  • requests and httpx. requests sits on urllib3, which keeps a connection pool per host; a Session reuses it (HTTP keep-alive). requests blocks one thread per reply; httpx.AsyncClient overlaps thousands of waits in one thread. Threads also work for I/O because Python releases the GIL while waiting on a socket.
  • pandas 3. Strings default to a str dtype (Arrow-backed when pyarrow is installed) and copy-on-write is always on: sub = df[["a"]] behaves as an independent copy, so changing sub never changes df and defensive .copy() calls are no longer needed.
  • Parquet and memory. A file holds row groups, each with one compressed, dictionary-encoded column chunk per column, and a footer with the schema and min/max statistics. Repeated strings become millions of Python objects unless you use category or Arrow strings (20.10 showed about 5 MB shrink to 0.1 MB on the study machine).

  3. A STRICT table (SQLite 3.37 and later) refuses such values with an error. Use it for tables where type safety matters.

What interviewers probe

  • Idempotency: "What if your job runs twice?" Upsert on a natural key, a transaction per batch, the watermark advanced in the same transaction. Retries give at-least-once delivery; add idempotent writes for an exactly-once effect.
  • Late data and deletes: overlap windows, event time versus ingestion time, periodic reconciliation; a watermark cannot see deletes (soft deletes or change data capture can).
  • Pagination: offset versus cursor, and why a large offset gets slow (the database still walks past the skipped rows).
  • Security and failure design: parameter binding, secrets in the environment, least-privilege users; timeouts everywhere, retry only the retryable, backoff with jitter, dead-letter files.
  • Formats and scale: why Parquet over CSV (types, compression, column pruning, predicate pushdown), when CSV is still right, and what changes at 10x data (chunking, columnar files, a database server, a distributed engine).

Chapter recap

  • Every data-access job is extract, validate, transform, load. Validate once, at the boundary.
  • pathlib and glob find files; write results through a temporary file and replace. Give open an encoding (and newline="" for csv).
  • CSV has no types, JSON has no dates, YAML needs safe_load. openpyxl never calculates formulas.
  • sqlite3: bind with ?, use with con:, batch with executemany, upsert with on conflict. SQLAlchemy Core builds SQL, the ORM maps classes, text() binds :name.
  • pandas: read_sql_query(params=, chunksize=) in, to_sql(if_exists="append", index=False) out; replace destroys constraints.
  • HTTP: always a timeout, a Session, raise_for_status(), backoff with jitter on retryable errors only, cursor pagination, respect 429 and Retry-After.
  • BeautifulSoup parses static HTML; handle missing elements; read robots.txt and the terms; prefer an API.
  • Validate with dataclasses or pydantic, keep rejects, alarm on a high reject rate. Parquet and Arrow (not run here) store typed columns with statistics so you read fewer bytes.
  • Log counts at every stage, chunk what is large, and fix encoding errors by finding the right codec.

import io
import pandas as pd

def count_by(source, column, chunksize=2):
    totals = {}
    for chunk in pd.read_csv(source, usecols=[column], chunksize=chunksize):
        for key, n in chunk[column].value_counts().items():
            totals[key] = totals.get(key, 0) + int(n)
    return dict(sorted(totals.items()))

Problem 20.P.19 (expert) Show that an upsert-based load is idempotent: run the same load twice and report the row count and the total.

Answer:

import sqlite3

con = sqlite3.connect(":memory:")
con.execute("create table sales(id integer primary key, amount real)")
batch = [(1, 10.0), (2, 20.0), (3, 5.5)]
SQL = "insert into sales values (?, ?) on conflict(id) do update set amount = excluded.amount"
for run in (1, 2):
    with con:
        con.executemany(SQL, batch)
    print(run, con.execute("select count(*), sum(amount) from sales").fetchone())
batch[1] = (2, 25.0)
with con:
    con.executemany(SQL, batch)
print(3, con.execute("select count(*), sum(amount) from sales").fetchone())
1 (3, 35.5)
2 (3, 35.5)
3 (3, 40.5)

Running the load a second time leaves the count at 3 and the total at 35.5, because each key is overwritten with the same values. A changed record (id 2 now 25.0) updates in place instead of creating a duplicate: the total becomes 40.5. A plain insert would fail on the second run (primary key) or, without a key, double the rows.

Problem 20.P.20 (expert) Interview: a 500-million-row events table is queried mostly by date range and country, and rarely needs more than 4 of its 40 columns. Argue for Parquet over CSV and describe how to lay it out.

Answer: (1) Column pruning: 4 of 40 columns reads roughly a tenth of the bytes, while CSV parses every line.
