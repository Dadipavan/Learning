18.4 Scaffolding a Library Project: A Test Harness That Catches Your Bugs

The projects in this chapter ask you to rebuild algorithms and check them against scikit-learn. The risk is a harness so weak that wrong code passes. The remedy is a small, fixed set of checks you apply to every class you write, so a bug has to slip past all of them.

The five standard checks

  1. Match the reference: same data, same hyper-parameters, coefficients equal to a tolerance (np.allclose with atol=1e-8 for closed forms; looser for iterative solvers).
  2. Match predictions, not just parameters (a sign or scaling bug can hide in the parameters).
  3. Limit cases: a huge penalty should shrink weights to 0; zero penalty should recover ordinary least squares.
  4. Invariances: reordering the rows must not change the fit; adding a constant to y must shift predictions by that constant.
  5. Fail on purpose: run the harness on a deliberately broken version and confirm it reports FAIL. A harness that cannot fail proves nothing.

CheckThe first four lines print PASS, so the correct class passes every check while the broken one fails at least one. That is the property you want from a harness.
COMMON MISTAKE
Using the same random data for every test. A bug that only shows with correlated features, duplicated rows or a different scale will pass. Add at least one awkward data set per class (collinear columns, one constant column, feature scales that differ by 1000).
COMMON MISTAKE
Loosening the tolerance until the test passes. If a closed-form method disagrees at 1e-4, there is a bug or a different convention (such as the intercept above); find out which before widening it.
